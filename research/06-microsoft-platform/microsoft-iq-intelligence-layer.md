## What this source is
A family of pages, spread across five documentation sets that do not share an editor, describing a set of capabilities Microsoft has grouped under the name **Microsoft IQ**. The hub page calls it "a unified intelligence layer for enterprise AI — one where every agent and Copilot interaction is grounded in a shared, continuously evolving understanding of the organization." Underneath that sentence sit three named members that this note covers — Work IQ over Microsoft 365, Fabric IQ over analytical data, Foundry IQ over enterprise documents — and a fourth, **Web IQ**, which is listed on the hub page and on the Fabric IQ page and has **no Microsoft Learn documentation at all**; it is reachable only through two `aka.ms` redirects, one to a blog.

The material is worth reading for this repository for a reason other than product coverage. It is a natural experiment in what happens when a vendor names a layer before the layer exists as one thing. Some of what is named is a genuine new surface with its own protocol, its own policy engine and its own billing meter. Some of it is a workload of real new items in preview. And some of it is an existing product with a portal in front of it. **Telling those three apart from the documentation alone is the exercise**, and the documentation makes it possible because it is unusually candid in places and unusually inconsistent in others.

## The argument in full

**The claimed structure.** The Fabric IQ page gives the cleanest one-sentence division of labour anywhere in the family: "Work IQ provides context on how employees work, Foundry IQ provides context on an organization's policies and authoritative documents, Web IQ provides context from the web, and Fabric IQ provides context on business entities and data." That is a coherent carve-up of an enterprise's context by *provenance* — what people did, what the business is, what the organisation has written down, and what the world says — and it is the durable idea in the whole naming exercise. It survives the products. An agent that needs to answer a real question usually needs more than one of those four, and knowing which one a question actually requires is a genuine design skill. The Foundry IQ page states the composition rule plainly and modestly: "Each IQ workload is standalone, but you can use them together to provide comprehensive organizational context for agents." That is the whole of the published composition story. **There is no shared query planner across the three, no cross-layer ranking, no arbitration when two layers disagree, and no joint permission model.** Composition means an agent may hold three tools.

Even the membership is unstable. The hub page says four. The Foundry IQ page says "Microsoft provides three IQ workloads" and omits Web IQ. The Copilot Studio pages say three, and their three are Work, Fabric and Foundry. A reader who arrives at any one of these pages first will form a different picture of what Microsoft IQ contains. This is not pedantry; a student asked to draw the platform will draw whichever diagram they landed on.

**Work IQ is a real new surface, built over old machinery.** The Work IQ overview describes four components — **Chat**, **Context**, **Tools** and **Workspaces** — reachable over three protocols: Agent-to-Agent, a remote MCP server, and REST, with a local MCP server available through a CLI. Several things here are new in substance rather than in name. The A2A endpoint is a real endpoint at `https://workiq.svc.cloud.microsoft/a2a/`, taking JSON-RPC with the method name in the body rather than the path, supporting protocol versions 1.0 and 0.3 dispatched by an `A2A-Version` header, carrying multi-turn state in a `contextId`, and requiring `Location` metadata for time-sensitive queries. Authentication is Microsoft Entra delegated only: on-behalf-of flows are supported and **application-only authentication is not**, which is a strong and welcome constraint — there is no way to call Work IQ except as somebody. The Tools component makes a specific and interesting design claim: it "collapses hundreds of operations into just 10 generic tools", where the tools are verbs such as fetch, create and update and the resource path says what is being acted on, so that "the surface area small while remaining flexible" and agents "can dynamically discover how data is structured at runtime… turning every data source into a self-describing interface." That is a real architectural position about MCP tool design, it is contestable, and it is the kind of thing worth teaching. **Workspaces** are backed by SharePoint Embedded and give agents persistent working storage inside the tenant boundary for long-running tasks. And the governance model is specific: instead of "hundreds of static OAuth scopes", a small set of broad permissions establishes boundaries and **a Rego-based policy engine** — the Open Policy Agent language, cited to `openpolicyagent.org` — evaluates "resource paths, request methods, user identity, and data content" on every request.

The **Context** component is where the repackaging is. The overview page names its own mechanisms and every one of them predates the Work IQ name: **Copilot memory**, which "captures explicit user actions… and implicit signals from user activity patterns"; the **semantic index for Copilot**, described as mapping the organisation's data "into an advanced lexical and semantic index" and as "a superset of content within Microsoft Graph and ingested content from Copilot connectors"; and **Dataverse intelligence** for structured business data. So the honest reading is that Work IQ is a new *access surface* — protocols, a tool grammar, a policy engine, a billing meter, working storage — placed over the Microsoft 365 semantic index and Copilot personalisation that already existed. That is not nothing. It is also not a new understanding of work.

**Work IQ's documentation contradicts itself on three material points**, and each of them is the kind of thing a delivery team would find out the hard way. First, licensing. The Work IQ overview states that "Work IQ API access is independent of Microsoft 365 Copilot licensing and available through usage-based billing", and that users without a Copilot licence "are billed based on usage". The Work IQ MCP overview states, in an Important box, "You must have a Microsoft 365 Copilot license to use Work IQ MCP servers." The Foundry tool page lists a Microsoft 365 Copilot licence as a prerequisite and adds that "users who call Work IQ tools through your agent must also have this license." The API overview says billing runs on Copilot Credits. These can perhaps be reconciled — API versus MCP-server versus Foundry-tool are different doors — but no page reconciles them, and the one that says "independent" says it without qualification. Second, the layer model. Both the Copilot Studio and Agent 365 copies of the Work IQ MCP overview open with the identical sentence "Work IQ is built on three tightly integrated layers: **Data, Memory, and Inference**." The Copilot Studio copy's bullets then name Data, Memory and Inference. **The Agent 365 copy's bullets name Data, Context, and Skills and Tools** — three different layers, immediately below a sentence naming the other three. Third, storage. The CLI page's security section asserts "**No data storage**: Work IQ doesn't store your Microsoft 365 data. It retrieves information on-demand when you make queries", while the API overview describes Workspaces as persistent SharePoint Embedded storage for agent intermediate data. Those may be different components; nothing says so.

A fourth inconsistency concerns the topology. The Copilot Studio sources page is explicit: Work IQ "routes all M365 data access through a single Agent 365 MCP gateway (the `M365Copilot` server at `https://agent365.svc.cloud.microsoft`), **not through dedicated per-source MCP servers**." The Agent 365 tooling catalogue lists exactly those dedicated per-source servers — Work IQ Mail, Work IQ Calendar, Work IQ Teams, Work IQ SharePoint, Work IQ OneDrive, Work IQ User, Work IQ Word, Work IQ Copilot — alongside Windows 365 agents, Dataverse and, notably, **a Fabric IQ Ontology server**, which is the only place in the family where one IQ is delivered as a tool of another. And in the same Copilot Studio doc set, the "Microsoft IQ vs. knowledge sources" table promises that Microsoft IQ "Can read and write (take actions)" and the narrative promises actions "like drafting emails or creating documents", while the **source capabilities table on the next page shows an em dash under "Tools (actions)" for all seven sources.** Read the tables, not the prose.

**Fabric IQ is a workload, and the ontology inside it is the substantive part.** This is the member with the most genuine new engineering. Fabric IQ is a named Fabric workload in preview containing six items — ontology (preview), Power BI semantic model, Plan, Graph, Data agent and Operations agent — several shared with other workloads, over OneLake, which is the foundation but is not itself an item. The three layers are unified data in OneLake, business intelligence in Power BI semantic models, and operational intelligence in ontologies. **Ontology** is a first-class modelling item: entity types, entity instances, properties with declared types and semantic annotations, and typed directional relationships with attributes and cardinality rules. It has **data bindings** that connect those definitions to lakehouse tables, eventhouse streams and Power BI semantic models "without copying or moving the data", carrying identity keys, column mappings, schema-evolution rules, data-quality checks on nullability, ranges and uniqueness, and provenance. It projects an **ontology graph** through Graph in Microsoft Fabric, with lineage on every node and edge. It exposes **NL2Ontology**, a natural-language-to-structured-query layer that "converts business questions into structured queries" and routes them to the most efficient engine — GQL for Graph, KQL for Eventhouse. And it can carry actionable rules such as "If inventory < threshold, trigger replenishment", which Operations Agents evaluate against live data and act on through Activator.

The framing argument is sound and is not vendor-specific: "Organizations work with data at the level of tables and schemas, which are structures built for machines, not meaning. However, they run on business concepts like customers, shipments, and assets. Without semantic understanding, AI remains unfit for high-stakes decisions because each question requires manual translation by a domain expert." That is the case for a semantic layer, made in one paragraph, and it would be made the same way by anyone selling one. The pragmatic route the page offers is the interesting part: **ontologies can be generated from Power BI semantic models already in production**, so an organisation bootstraps its enterprise vocabulary from logic it already trusts rather than convening a modelling committee. That is good advice and it is testable.

**One caveat undercuts the "operational" and "real-time" language, and the page states it twice.** "Any updates in upstream data sources (like new rows) need to be **manually refreshed** before they're visible in the ontology item." A layer described as delivering operational intelligence over live data requires a manual refresh before new rows appear in it. The two claims are not compatible without qualification, and no qualification is given. Anyone teaching Fabric IQ should put that sentence on the slide next to the words "real-time".

**Foundry IQ is agentic retrieval in Azure AI Search, plus a portal.** The documentation says so, in the plainest terms available: "Agentic retrieval is the multi-query retrieval engine that powers Foundry IQ knowledge bases. For custom solutions, you can use agentic retrieval directly via the Azure AI Search APIs." And: "Is Azure AI Search required for Foundry IQ? **Yes.**" And, from the other side, the Azure AI Search pages now carry a standing note that the service "underpins Foundry IQ, the managed knowledge layer". The delta the name buys you is stated as knowledge bases, knowledge sources, native integrations with Azure OpenAI in Foundry Models and Foundry Agent Service, and "a streamlined, end-to-end setup experience" in the portal. **Foundry IQ is a branded assembly and an experience over an existing service, and the docs do not pretend otherwise.** That is a repackaging, and saying so is not a criticism — it is the finding.

The mechanism underneath is real and is documented in useful detail. A **knowledge base** groups one or more **knowledge sources** under a single endpoint with retrieval instructions and an output mode. Indexed sources — Azure Blob Storage, OneLake, SharePoint, existing search indexes — handle chunking, vectorisation, metadata extraction and ACL synchronisation. Remote sources — SharePoint via the Copilot Retrieval API, web via Grounding with Bing — issue on-demand queries and hold nothing. **Retrieval reasoning effort** is a single dial over the latency-quality trade-off with published limits: **minimal** allows up to ten knowledge sources with no LLM, no query planning and no answer synthesis; **low** allows three sources and three subqueries with a 5,000-token synthesis budget; **medium** allows five sources and five subqueries, adds iterative search, and gets a 10,000-token budget. The default is `low`. Query planning is restricted to gpt-4o, gpt-4.1 and gpt-5 series models. Collapsing a large parameter space into one legible dial is a good API design decision and worth teaching as one.

**The most important sentence in the Foundry IQ documentation is about permissions, and it says the opposite of the marketing.** Every summary page calls the knowledge bases "permission-aware". The FAQ says this: "User-level access controls are **only** enforced when the knowledge source supports document-level permissions **and** when those permissions have been explicitly configured for synchronization. **Unless support for out-of-the-box user permissions is explicitly stated in the knowledge source documentation, document-level access controls aren't automatically honored.**" Permission enforcement is opt-in, per source, and the default is off. Remote SharePoint is the exception that proves it — it enforces through the Copilot Retrieval API with ACLs and Purview sensitivity labels out of the box, and requires end users to hold a Microsoft 365 Copilot licence. Everything else must be configured. This joins directly to the material in [azure-ai-search-and-acl-patterns.md](/research/06-microsoft-platform/azure-ai-search-and-acl-patterns.md), which establishes that an index is a copy and copies do not inherit their originals' access rules; Foundry IQ adds that the copying machinery will happily run without being told to carry the rules across, and that the resulting system will look like it works.

**The 36% claim now has a methodology, and the methodology does not support the sentence Learn attaches to it.** This repository has prohibited the claim since it first appeared in internal vendor training with no methodology at all — see [03-accelerate-agentic-ai.md](/research/06-microsoft-platform/03-accelerate-agentic-ai.md), which records it as "no benchmark, metric definition or interval". **That characterisation is now out of date and this note supersedes it.** The Foundry IQ FAQ on Microsoft Learn states: "Benchmarks show that agentic retrieval achieves approximately 36% higher response quality than traditional single-shot RAG", linking to a Microsoft Foundry Blog post of 18 November 2025 by ten named Microsoft authors. That post is a substantial piece of engineering writing. It describes the seven-step retrieval flow; it names the datasets — a Microsoft-built multi-industry multi-language collection of ten indexes of roughly a thousand documents each, FinanceBench reorganised into nine industry-sector knowledge sources at several difficulty levels, Natural Questions, a thousand-query subsample of HotpotQA, and FRAMES; it names the metric as an answer-relevance score from zero to one hundred drawn from the RAG triad; it reports per-dataset results; it reports a second measurement using Microsoft Research's BenchmarkQED library as pairwise preference; and it reports a latency figure of under 150 milliseconds on H100 GPUs for a batch of eleven inferences at the largest supported chunk size.

**And what it measured is the product against itself.** The blog's own words: "We observed improvements ranging from 16% to 60%, with an average of 36% when comparing **medium to minimal retrieval reasoning effort**", and, in its summary bullets, "+20 points (36%) improvement in the quality of end-to-end RAG answer scores when using knowledge bases as opposed to **brute force searching all sources at once**." The averaged row of its main table reads 59 at minimal, 74 at low, 80 at medium. The baseline is Foundry IQ with its own reasoning dial turned down, which the blog describes as running "the exact caller query on all knowledge sources in parallel" — a multi-source brute-force fan-out. **That is not traditional single-shot RAG.** Nobody built a conventional single-query RAG system and compared it. The Learn FAQ's restatement changes the comparator, and a reader who trusts Learn and never opens the blog will believe a claim the experiment did not test. Further, the figure carries no confidence interval, no variance, no run count and no reported agreement between the LLM answer-relevance judge and human raters; the scoring methodology itself is deferred by reference to an earlier post that was not read here. By the standards this repository applies in [thakur-beir.md](/research/03-measurement-evaluation/thakur-beir.md), [miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md) and [zheng-mt-bench-chatbot-arena.md](/research/03-measurement-evaluation/zheng-mt-bench-chatbot-arena.md), **a single point estimate from an unvalidated LLM judge, against a self-baseline, on partly self-constructed data, is not a result that licenses the sentence it is being used to support.** The prohibition stands. Its justification changes from "there is no methodology" to "there is a methodology and it measures something else".

**What the blog does support is more useful than the headline.** The gains are concentrated where the theory predicts: on the sec-hardest split, queries requiring three or more sectors to answer scored 46 at low effort and 95 at medium, while single-sector queries scored 55 and 89. Removing three of nine sectors dropped the score from 89 to 53, and adding a web knowledge source recovered it to 77 at low and 84 at medium — a clean demonstration that federation fills gaps in private corpora. And a table of naming strategies shows that source selection degrades by up to 43 percentage points of recall when knowledge-source descriptions blur across domains, with the conclusion that "knowledge source name is most important — a good name with an adversarial description still scores well." That is an actionable, measured finding about a configuration decision that looks cosmetic, and it is far better teaching material than the headline number.

## Key concepts and practices
- **Microsoft IQ** groups **Work IQ**, **Fabric IQ**, **Foundry IQ** and **Web IQ**. Membership is stated as four on two pages and as three on three others. **Web IQ has no Learn documentation.**
- **The durable carve-up is by provenance:** how people work; what the business is; what the organisation has written down; what the world says.
- **Composition is by tool, not by planner.** "Each IQ workload is standalone, but you can use them together." No cross-layer ranking, arbitration or joint permission model is published.
- **Work IQ protocols:** A2A at `https://workiq.svc.cloud.microsoft/a2a/` (v1.0 and v0.3 via `A2A-Version`; JSON-RPC; method in body; `contextId` for multi-turn; `Location` metadata for time-sensitive queries), remote MCP, REST, and local MCP via the `@microsoft/workiq` CLI.
- **Work IQ auth: Entra delegated only. On-behalf-of supported. Application-only not supported.** In multitenant organisations the token issuer must be the user's home tenant or the call fails with `400 AuthenticationError`.
- **Work IQ scope of data:** email, meetings and calendar, OneDrive and SharePoint documents, Teams messages, people and organisational context, Microsoft Planner plans, enterprise search results.
- **Work IQ tool grammar:** "hundreds of operations into just 10 generic tools" — verbs plus resource paths, with runtime schema discovery so every source is "a self-describing interface".
- **Work IQ Workspaces:** persistent SharePoint Embedded working storage inside the tenant boundary for long-running agent workflows.
- **Work IQ policy:** broad permissions for boundaries, **a Rego policy engine** for per-request decisions on resource path, method, identity and data content; every tool invocation logged.
- **Work IQ's Context layer is assembled from Copilot memory, the Microsoft 365 semantic index and Dataverse intelligence** — all pre-existing. The semantic index is "a superset of content within Microsoft Graph and ingested content from Copilot connectors."
- **Work IQ CLI reached general availability on 16 June 2026**; preview builds 0.4.x and 0.5.x are unsupported and issues must be reproduced on a GA build.
- **Foundry's Work IQ tool requires** a Microsoft 365 Copilot licence for the developer and every calling user; Foundry User and Foundry Project Manager roles; **Entra Global Administrator consent for `WorkIQAgent.Ask`**; and **does not support VNet integration**.
- **Fabric IQ is a Fabric workload** containing ontology (preview), Power BI semantic model, Plan, Graph, Data agent and Operations agent, over OneLake.
- **Ontology** = entity types, entity instances, properties, typed relationships with cardinality, **data bindings** to OneLake without copying, an **ontology graph** with lineage, and **NL2Ontology** routing to GQL or KQL.
- **Ontologies can be generated from production Power BI semantic models** — bootstrap from trusted definitions rather than convene a committee.
- **Ontology data is not live: upstream changes "need to be manually refreshed"** before appearing. Stated twice.
- **Foundry IQ requires Azure AI Search.** Agentic retrieval is the engine; Foundry IQ is knowledge bases, sources, native Foundry integrations and a portal experience over it.
- **Knowledge source types:** indexed (Blob, OneLake, SharePoint, existing indexes — with chunking, vectorisation, metadata and ACL synchronisation) and remote (SharePoint via Copilot Retrieval API, web via Grounding with Bing — nothing stored, always current).
- **Retrieval reasoning effort:** minimal — 10 sources, no LLM, no planning, no synthesis; low — 3 sources, 3 subqueries, 5,000-token budget; medium — 5 sources, 5 subqueries, iterative search, 10,000-token budget. **Default `low`.** Planning models limited to gpt-4o, gpt-4.1 and gpt-5 series.
- **Permission enforcement in Foundry IQ is opt-in and off by default:** "Unless support for out-of-the-box user permissions is explicitly stated in the knowledge source documentation, document-level access controls aren't automatically honored."
- **Foundry IQ and Copilot knowledge sources are explicitly not interoperable** in either direction.
- **Web Knowledge Source waives protections:** the Data Protection Addendum does not apply, data flows outside the Azure compliance and geographic boundary, and use "waives all elevated Government Community Cloud security and compliance commitments to include data sovereignty".
- **Agentic retrieval bills by token across two services** — Azure AI Search for retrieval and reranking, Azure OpenAI for planning and synthesis — against the classic pipeline's per-query semantic-ranker charge.
- **The 36% figure compares medium against minimal reasoning effort of the same product**, averaged over five datasets (59 → 80, +21 absolute, range 16% to 60%). The Learn FAQ restates it as against "traditional single-shot RAG". **The blog did not measure that.**
- **Source naming matters measurably:** blurred or cross-domain descriptions cost up to 43 points of source-selection recall; a good name survives an adversarial description.

## Method and evidence base
Two different kinds of source, and they must not be pooled. The Learn pages are first-party product documentation whose authority is **definitional** — they establish what the system is, what it requires and what it refuses, and they are the only place those facts exist. They contain no measurement of anything. The blog is first-party engineering evaluation with named authors, named datasets, a named metric and reported per-dataset numbers, and its authority is **evidential but weak**: the baseline is the same system at a lower setting, roughly half the evaluation corpus was constructed by the authors, the judge is an LLM with no reported human-agreement rate, no interval or variance accompanies any figure, and the scoring method is deferred by reference to an earlier post. It is a competent internal experiment reported honestly and then restated inaccurately in the documentation that cites it. **Definitional authority is not evidential authority**, and the gap between the blog's careful sentence and the FAQ's confident one is the clearest illustration of that distinction in this repository's whole platform strand.

## Vocabulary the sources introduce
- **Microsoft IQ** — the umbrella name for the vendor's enterprise context layers.
- **Work IQ** — the access surface over Microsoft 365 work data, context and tools.
- **Fabric IQ** — the Fabric workload delivering business semantics over OneLake.
- **Foundry IQ** — knowledge bases, knowledge sources and Foundry integrations over Azure AI Search agentic retrieval.
- **Web IQ** — the named fourth member with no Learn documentation.
- **Knowledge base** — the top-level object grouping knowledge sources under one endpoint with retrieval behaviour.
- **Knowledge source** — a connection to indexed or remote content.
- **Retrieval reasoning effort** — the single dial collapsing the latency-quality parameter space into minimal, low and medium.
- **Iterative search / reflective search** — a second retrieval round triggered when the first is judged insufficient.
- **Semantic classifier** — the small language model acting as third-layer ranker and early-exit decision maker.
- **Ontology** — the shared, machine-understandable vocabulary of a business as entity types, properties and relationships.
- **Data binding** — the mapping from ontology definitions to OneLake data, without copying it.
- **NL2Ontology** — the natural-language-to-structured-query layer over an ontology.
- **Operations agent** — a Fabric item monitoring live ontology-bound data and triggering governed action.
- **Agent 365 MCP gateway** — the single `M365Copilot` server through which Copilot Studio says all Microsoft 365 access is routed.
- **Workspace** — SharePoint Embedded persistent working storage for a long-running agent.
- **Copilot Credits** — the consumption unit for Work IQ usage-based billing.

## What to remember
- **The layer is not one thing.** Work IQ is a new surface over old machinery; Fabric IQ is a workload of genuinely new items in preview; Foundry IQ is an existing service with a portal and a brand. A single name over three different kinds of thing is the lesson.
- **The durable idea is the carve-up by provenance** — what people did, what the business is, what is written down, what the world says. That survives every rename.
- **Composition is tool-level.** Three tools on one agent, with no shared planner, no cross-layer ranking, no arbitration, no joint permission model. "Standalone but usable together" is the whole published story.
- **"Permission-aware" is a capability, not a default.** Foundry IQ honours document-level access control only where the source supports it and someone configured synchronisation. Otherwise it does not, and the system will look like it works.
- **A layer marketed as real-time requires a manual refresh.** Fabric IQ's ontology says so twice.
- **The 36% figure measures the product against itself at a lower setting.** The documentation restates it as against traditional single-shot RAG. That comparison was never run.
- **The measured findings that are actually useful are the unheadlined ones** — gains concentrate on multi-source questions, web federation fills gaps in private corpora, and knowledge-source naming moves selection recall by tens of points.
- **First-party documentation contradicts itself here on licensing, on layer names, on storage, on topology and on whether actions are supported.** Read the tables, not the prose, and read more than one page.
- **Nothing anywhere publishes what fraction of a tenant's data is actually in any of these layers.** Coverage is unstated everywhere.
- **Work IQ cannot be called by an application on its own behalf.** Every request is somebody's request. That is a strong design choice and it constrains architecture.

## Why it matters for the course
Three reasons, in ascending order of value. First, coverage: this programme teaches retrieval, grounding and knowledge systems through generic Azure AI Search patterns, and a student who walks into a customer conversation not knowing that the vendor has named this layer will be talking past the customer's own vocabulary from the first minute. Second, mechanism: the ontology work in Fabric IQ is a genuine addition to what this repository holds about retrieval — it is the case for a semantic layer over an enterprise data estate, argued in a paragraph and implemented in a product, and it connects the requirements material in Stage 3 to the retrieval material in a way nothing else here does.

Third and most valuable: **this is the best available worked example of the difference between definitional and evidential authority, in a single family of pages, written by one vendor, about one product.** The blog is careful. The FAQ that cites the blog is not. The gap between them is one sentence wide and it changes what the number means. A student who can find that gap unaided can read any vendor evaluation, and finding it required nothing more than clicking the link in the citation. That is the whole skill, demonstrable in ten minutes, on live first-party material. It extends the critical-reading exercise proposed in [03-accelerate-agentic-ai.md](/research/06-microsoft-platform/03-accelerate-agentic-ai.md) from an internal training deck to public documentation, and it upgrades that note's account of the 36% claim from "no methodology" to something more interesting and more teachable. It links to [azure-ai-search-and-acl-patterns.md](/research/06-microsoft-platform/azure-ai-search-and-acl-patterns.md) on the permission default, to [barnett-rag-failure-taxonomy.md](/research/02-technical-foundations/barnett-rag-failure-taxonomy.md) on which failure modes federation does and does not address, and to [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md) on the build-path axes these layers sit above.

## How to teach it
- **Lecture:** teach the provenance carve-up — work, business, documents, web — without naming a single product. Then reveal that a vendor has named all four, and that two of its own pages disagree about how many there are.
- **Lecture:** distinguish three things a product name can denote: a new surface, a new workload, and a portal over an existing service. Assign each of the three IQs to one, from the documentation, and defend it.
- **Lecture:** teach the permission default as the headline fact about Foundry IQ, before any capability. "Permission-aware" and "permissions enforced" are different claims and the documentation says which one applies.
- **Lab:** give students the FAQ sentence and the linked blog and ask them to write the one sentence the experiment supports. Nothing else. This is the highest-value hour in the topic and it needs no tenant.
- **Lab:** build a knowledge base over two sources, name them well, measure source selection; rename them adversarially, measure again. The vendor's own table predicts the direction and rough size, so the lab is a replication.
- **Lab:** bind three ontology entity types to real data and count the bindings that fail. Then change an upstream row and observe that the ontology does not know until refreshed.
- **Lab:** retrieve through a knowledge base as two users of different entitlement, with permission synchronisation deliberately unconfigured, and observe that both get the same answer. Then configure it.
- **Assessment:** require every design that uses an IQ layer to state, in one page, which layer answers which question, what happens when two disagree, where authorisation is enforced, what the freshness bound is, and which of those five the documentation does not answer.
- **Assessment:** ask what evidence would be needed to justify choosing an IQ layer over a plain retrieval implementation, and note that no such evidence has been published by anyone.
- **Assessment:** never test recall of layer membership, component names, source lists or tool counts. All five moved during the writing of this note's source pages and at least one is internally inconsistent today.
- **Framing:** the most perishable material in the repository, and the only entry whose *names* are more perishable than its capabilities. Re-verify before every offering, and re-verify the membership of Microsoft IQ first.

## Limits and cautions
- **Everything here is dated 2026-07-31.** Preview status, limits, licence requirements and even the count of IQ layers may have moved by the time this is read.
- **Substantial parts of the family were not read**, including the Terms of Use, the A2A and REST sub-pages, both GitHub repositories, the ontology tutorials, the general-availability migration guide that carries the authoritative preview breakdown, and the earlier blog that the 36% post defers its scoring methodology to. **Any claim about scoring methodology beyond "it is an LLM-judged answer-relevance score from zero to one hundred" is unverified here.**
- **The blog's charts were not retrievable.** Only its tables were read, so any distribution or trend visible only in a chart is unread.
- **Web IQ is essentially unresearched**, because there is nothing on Learn to research. Its only presence is two `aka.ms` redirects, one to a blog. It should not be taught at all until documentation exists.
- **The contradictions recorded here are between pages, not necessarily in the product.** Licensing, layer names, storage, topology and action support may each be consistent in reality and merely documented by different teams. The safe conclusion is that no single page can be trusted alone, not that the product is broken.
- **The three layers were read as documentation, not exercised.** Nothing here was deployed, measured or tested. Every mechanism is as-described.
- **The 36% figure and every number in this note are recorded for analysis and are forbidden downstream.** They must not appear in any wiki page except the two prohibition registers, and must never be repeated as evidence of anything.
- **Single-vendor throughout.** No comparison exists to any non-Microsoft semantic layer, knowledge layer or work-graph product, and none is offered here.
- **The mapping in "Use cases, and the sessions they belong to" is this note's own proposal.** It is reasoned from published session anchors, has been agreed with nobody, and has never been taught.

### The silences, stated explicitly
1. **No published retrieval quality measure exists for Work IQ or for Fabric IQ.** None. The only quality figures anywhere in Microsoft IQ are Foundry IQ's, and they compare the product to itself.
2. **No evidence exists that any IQ layer outperforms a competently built plain retrieval implementation.** That comparison has not been published by anyone, and the one benchmark that exists deliberately does not make it.
3. **No indexing latency or freshness bound is published for any layer.** Foundry IQ says refresh "depends on your indexer schedule configuration". Fabric IQ's ontology requires a manual refresh. Work IQ's semantic index publishes nothing at all. There is no upper bound on staleness anywhere.
4. **No measure of permission-trimming completeness is published.** No false-negative rate, no false-positive rate, no revocation-propagation time, for any of the three, from any source.
5. **No coverage statement exists.** Nothing states what proportion of a tenant's mail, chat, meetings or files is actually reachable, what is excluded, or how a practitioner would find out. "A superset of content within Microsoft Graph and ingested content from Copilot connectors" is a set relation, not a coverage figure.
6. **Work IQ MCP asserts continuous evaluation measuring accuracy, latency and reliability, and publishes no value for any of the three.**
7. **No agreement rate is published between the LLM answer-relevance judge and human raters**, and no interval, variance or run count accompanies any figure in the benchmark.
8. **No service-level agreement covers any preview surface here**, and that is most of the surface.
9. **No latency bound is published for a Work IQ A2A call**, which sits synchronously in an agent turn.
10. **Nothing states what happens when two IQ layers return contradictory answers**, or which wins, or whether anything notices.
11. **No measure exists of how often an orchestration runtime selects the correct IQ source.** Copilot Studio states that the runtime decides; nothing states how well.
12. **Work IQ asserts rate limiting and quantifies no limit.**
13. **Fabric IQ's ontology page publishes no scale limits** — no maximum entity-type count, instance count, relationship depth or graph size.
14. **Web IQ publishes nothing.** It is a name on a hub page with no documentation behind it.
