# Cliff Notes — Document-Level Access Control in Azure AI Search

## Citation and access
- **Title:** "Document-level access control in Azure AI Search"
- **Publisher:** Microsoft, Microsoft Learn (Azure AI Search documentation).
- **Source consulted:** `https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview` — **fetched and read in full.**
- **Access status:** open documentation. **Highly perishable**: most of the page describes the **2026-05-01-preview REST API**, and preview surfaces change without notice.
- Referenced companion pages, not fetched: the security-trimming guide, the push-API and ADLS Gen2 indexer ACL guides, the SharePoint ACL configuration guide with its per-scenario permission matrix, the Purview sensitivity-label ingestion guide, and the query-time enforcement guide.

## What this source is
An overview page describing four distinct mechanisms by which Azure AI Search can enforce per-document permissions, "from data ingestion through query execution." It exists because retrieval-augmented generation created a new and severe version of an old problem: a search index is a copy of source content, and copies do not automatically inherit the access rules of their originals. The page is unusually valuable teaching material because it does not present a single blessed answer. It presents four approaches, gives explicit selection criteria, and is candid about the synchronisation lag that every one of them shares.

## The argument in full
The page's framing is that document-level access control "is essential for building secure AI agentic systems grounding data, retrieval-augmented generation (RAG) applications, and enterprise search solutions that require authorization checks at the document level." The reason RAG raises the stakes is worth stating explicitly, because the documentation assumes it: a conventional search interface that returns a forbidden document at least shows the user a link they cannot open, whereas a RAG system reads the document's contents into a generated answer. The leak is not a listing; it is the substance. Access control therefore has to happen before generation, which means it has to happen in retrieval, which means the permission model must live in or alongside the index.

Four approaches are offered. **Security filters** are "string comparison": the application passes a user or group identity as a string, which populates a query filter excluding non-matching documents. This approach "isn't bound to an API so you can use any version or package", which makes it the universal fallback. **POSIX-like ACL / RBAC scopes**, in preview, compare "the Microsoft Entra security principal behind the query token" against permission metadata stored on documents; ACLs apply to Azure Data Lake Storage Gen2 directories and files, RBAC scopes apply to ADLS Gen2 content and Azure blobs. **Microsoft Purview sensitivity labels**, in preview, have an indexer extract labels from Azure Blob Storage, ADLS Gen2, SharePoint in Microsoft 365 and OneLake, storing them as metadata that is "evaluated at query time to enforce user access based on Microsoft Entra tokens and Purview policy assignments". **SharePoint in Microsoft 365 ACLs**, in preview, have indexers extract document, list item and ASPX site page permissions directly from Microsoft 365.

The selection guidance is refreshingly concrete, and its logic is the most transferable content on the page. Custom identity systems, non-Microsoft security frameworks, or any push-model index get **security filters**, because the approach is "API-agnostic, generally available, and based on simple string matching." ADLS Gen2 or Blob content with existing assignments gets **ACL / RBAC scopes**, for native Entra integration. Content already governed by Purview policies gets **sensitivity labels**, because that "reuses centralized classification and policy assignments." SharePoint content gets **SharePoint ACLs**, because that honours native SharePoint permissions including site groups. The underlying principle — reuse the authoritative permission system rather than reimplementing it — is the correct default in almost any system, and it is worth extracting from the product context.

The security-filter pattern is spelled out in six steps: create a string field in the index for identities; load the index from source documents that include their ACLs; include a filter expression in the query logic; get the caller's identity at query time; pass it as the filter string; and let results be trimmed to exclude non-matches. Its weakness is stated indirectly but unmistakably. The page later contrasts it with the native pattern: "the permission filter metadata in the index and query is recognized as Microsoft Entra ID authentication, whereas the security trimming workaround is simple string comparison." The word *workaround* is the documentation's own. A string filter is only as trustworthy as the code that supplies the string; nothing at the search service validates that the caller is who the filter says they are. The security boundary sits in the application, not in the service.

The native ACL and RBAC pattern moves that boundary. The index must have **permission filters enabled** and a permission filter added to a string field; documents are loaded with their ACL metadata; and queries carry the **`x-ms-query-source-authorization`** header. The service then performs two checks in sequence, and the two-stage structure is the design insight: "First, it checks for **Search Index Data Reader** permission that allows your client application to access the index. Second, given the extra token on the request, it checks for user or group permissions on documents that are returned in search results, excluding any that don't match." Application-level authorisation and user-level authorisation are separate concerns evaluated separately — the app is trusted to query, the user is trusted to see specific documents. The documentation also gives a practical governance recommendation: "use group access over individual user access for ease of management." Two ingestion routes exist — a push model where JSON payloads include POSIX-like ACLs per document, with the Microsoft Graph SDK suggested for resolving identities, and a pull model via the ADLS Gen2 indexer or a Blob knowledge source, both requiring preview APIs.

The SharePoint pattern is the most operationally detailed and the most cautionary. Permissions cover libraries, list items and ASPX site pages. Supported principal types during preview are Entra user accounts, Entra security groups, Microsoft 365 groups, mail-enabled security groups, and SharePoint site groups (the last requiring extra index configuration). The required Graph permissions are substantial: **`Sites.FullControl.All`** to read SharePoint content and ACLs, plus **`User.Read.All`** when indexing list items or ASPX pages, "to resolve the email addresses returned by the SharePoint REST API into Microsoft Entra object IDs." Requiring full control over all sites in order to read permissions is a real privilege-escalation consideration and should be taught as one. The synchronisation model splits in two: "changes on items with unique permissions are detected and refreshed on each successful indexer run", while "changes inherited from parent scopes (site, library, list, or folder) require an explicit refresh, such as `/resync` with `options: ["permissions"]` or `/resetdocs`." That asymmetry is a trap — the inherited case is both the more common one and the one that does not self-heal. The page also states plainly that "SharePoint Information Management policies that gate user access aren't evaluated, ingested, or honored at query time", which is an explicit gap between what the source system enforces and what the index enforces.

The Purview pattern reuses an enterprise classification system rather than a per-document permission list. At query time the service "checks each document's sensitivity label, the user's Microsoft Entra token, and the organization's Purview policies to determine access." It requires a **system-assigned** managed identity — "user-assigned managed identities aren't supported for Purview label extraction; the service's own identity must hold the elevated Purview permissions" — and access granted by a tenant global administrator or privileged role administrator. Labels must be applied before indexing. The constraints are numerous and should be named whenever the pattern is taught: single-tenant only, RBAC authentication required, REST API and SDKs only during preview, and **Autocomplete and Suggest are unavailable on Purview-enabled indexes.** Labels surface through two consumption paths from the same indexed metadata — the direct query API, which also supports an auditable **elevated read** for administrative investigations, and knowledge sources and agentic retrieval, where the retrieve action and the MCP `knowledge_base_retrieve` tool return per-reference `sensitivityLabelInfo` and response-level `metadata.responseSensitivityLabelInfo` for display banners and policy enforcement.

Query-time enforcement is described as a cross-cutting capability spanning three of the four patterns, and the three-step mechanism is simple: extract user, group and scope claims from the token; compare them to permission metadata stored alongside indexed documents; return only documents whose metadata grants access. But the page is careful and repeated about the limitation, and this is the single most important sentence for a course to take from it: enforcement "evaluates the caller's Microsoft Entra claims against the permission metadata that's already stored in the index. Permission changes in the source system… are only reflected in search results after that metadata is synchronized to the index through the source-specific mechanism." A revocation in Entra, ADLS, Purview or SharePoint does not take effect in search until the index catches up. The preview terms say the same thing more bluntly: "a timing lag occurs before the 2026-05-01-preview recognizes changes to those access or permission restrictions."

Two further cautions from the page carry disproportionate weight. First, chunking breaks permission inheritance unless it is handled deliberately: when a skillset chunks documents — for example with the Text Split skill for integrated vectorization — "the permission metadata fields move from indexer field mappings to index projections", and for labels, "without this projection, chunk-level references aren't filtered." An unprojected chunk is an unprotected chunk, and chunking is standard practice in RAG. Second, the preview terms place responsibility explicitly on the implementer: "It's your responsibility to manage whether your data flows outside of your organization's compliance and geographic boundaries", and to review and test applications "in the context of your specific use cases."

## Key structural constraints and specifics
- **Four approaches:** security filters (generally available, API-agnostic, string comparison); POSIX-like ACL / RBAC scopes (preview); Purview sensitivity labels (preview); SharePoint in Microsoft 365 ACLs (preview).
- **Security filters are described by the documentation itself as a "workaround"** relative to Entra-recognised permission filters. The trust boundary sits in the application.
- **Native pattern requires:** permission filters enabled on the index, a permission filter on a string field, ACL metadata loaded with documents, and the **`x-ms-query-source-authorization`** header at query time.
- **Two-stage check:** **Search Index Data Reader** or **Search Index Data Contributor** for the application, then per-document user and group permissions from the token.
- **Documentation recommends group access over individual user access** for manageability.
- **ADLS Gen2** supports document-level RBAC scope preservation; **Azure blobs** preserve RBAC scope only **at container level**.
- **SharePoint requires Graph `Sites.FullControl.All`**, plus **`User.Read.All`** for list items and ASPX pages to resolve email addresses to Entra object IDs.
- **SharePoint principal types in preview:** Entra user accounts, Entra security groups, Microsoft 365 groups, mail-enabled security groups, and SharePoint site groups (extra configuration).
- **SharePoint sync asymmetry:** unique-permission changes refresh on each successful indexer run; **inherited changes require explicit `/resync` with `options: ["permissions"]` or `/resetdocs`.**
- **SharePoint Information Management policies "aren't evaluated, ingested, or honored at query time."**
- **Purview requires a system-assigned managed identity** — user-assigned is not supported — with access granted by a global or privileged role administrator; labels must exist before indexing.
- **Purview constraints:** single-tenant only, RBAC authentication required, REST and SDK only in preview, and **Autocomplete and Suggest APIs are unavailable on Purview-enabled indexes.**
- **Label surfacing:** direct query API with optional auditable **elevated read**; and knowledge sources / agentic retrieval returning `sensitivityLabelInfo` per reference and `metadata.responseSensitivityLabelInfo` per response, including via the MCP `knowledge_base_retrieve` tool.
- **Chunking moves permission fields from indexer field mappings to index projections.** Without projection, "chunk-level references aren't filtered."
- **Enforcement is against indexed metadata, not live source permissions.** Source-side changes take effect only after synchronisation.

## Method and evidence base
First-party product documentation covering a mixture of generally available and preview functionality. Its authority is definitional. It contains no measurements of synchronisation latency, no failure-rate data, and no security assessment of the four approaches against each other. It is trustworthy for what the system does and silent on how often it does it correctly under load.

## Vocabulary the source introduces
- **Document-level access control** — enforcing per-document permissions from ingestion through query execution.
- **Security trimming** — removing unauthorised documents from a result set rather than blocking the query.
- **Security filter** — a string-comparison filter carrying the caller's identity into the query.
- **Permission filter** — an index field flagged as carrying Entra-recognised permission metadata.
- **`x-ms-query-source-authorization`** — the request header carrying the end user's Entra token, distinct from the application's own authentication.
- **POSIX-like ACL** — the file and directory access model preserved from ADLS Gen2.
- **RBAC scope** — role assignment scope preserved into the index; per-document for ADLS Gen2, per-container for blobs.
- **Sensitivity label** — a Purview classification evaluated at query time against organisational policy.
- **Index projection** — the mechanism carrying document-level fields, including permissions, onto chunk rows.
- **Knowledge source** — the managed ingestion abstraction that agentic retrieval consumes, carrying label metadata into responses.
- **Elevated read** — an auditable administrative query path that bypasses label-based trimming.

## What to remember
- An index is a copy, and copies do not inherit their originals' access rules. Permissions must be deliberately propagated.
- RAG makes this urgent: the leak is the content in the generated answer, not merely a visible link.
- Four approaches exist, and the selection rule is to reuse the authoritative permission system rather than reimplement it.
- Security filters are a string comparison; the trust boundary is in your application code, and the docs call it a workaround.
- Application authorisation and user authorisation are separate checks. Both are needed.
- Blob RBAC scope is preserved only at container granularity; ADLS Gen2 goes to document level.
- SharePoint integration needs `Sites.FullControl.All`, and inherited permission changes do not self-heal.
- Purview reuses enterprise classification but costs you Autocomplete, Suggest, multi-tenancy and general availability.
- **Chunking silently discards permissions unless they are projected onto every chunk.**
- **Enforcement always lags the source system.** Revocation is not immediate, and the documentation says so repeatedly.

## Why it matters for the course
This is the clearest available demonstration that an AI system spans subsystems that are usually taught separately — retrieval, identity, information governance and generation — and that correctness at the boundaries between them is where real systems fail. It also converts an abstract security principle into a concrete engineering task with visible trade-offs: the four approaches differ in trust boundary, granularity, operational burden and feature cost, and choosing among them is exactly the kind of judgement the course exists to certify. Two specifics deserve to be taught as named failure modes because they are silent, plausible and consequential: unprojected chunks, and stale permissions after revocation. Both produce a system that appears to work. This connects directly to the retrieval material in [research/02-technical-foundations/barnett-rag-failure-taxonomy.md](research/02-technical-foundations/barnett-rag-failure-taxonomy.md) — access control is a failure mode that taxonomy does not centre — and to the governance material in [purview-dspm-for-ai-and-defender-ai-spm-docs.md](research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md).

## How to teach it
- **Lecture:** start from the principle that an index is a copy, and derive the whole problem from it before naming any product.
- **Lecture:** compare the four approaches on trust boundary, granularity, operational burden and capability cost. The comparison, not the mechanism, is the lesson.
- **Lab:** build a retrieval feature with two user personas of differing entitlement and demonstrate a leak, then close it with a permission filter and a scoped token.
- **Lab:** revoke a permission in the source system and measure how long the document remains retrievable. The lag is the lesson, and it must be experienced rather than described.
- **Lab:** chunk a document without projecting its permission fields and observe that the chunks are returned. This is the single most instructive failure in the topic.
- **Assessment:** require every retrieval feature to state its authorisation model, its trust boundary, its synchronisation mechanism and its revocation latency. Defend orally.
- **Assessment:** ask what `Sites.FullControl.All` grants, and whether the team would accept that on their own tenant.
- **Framing:** perishable, and more so than most — the majority of this page is preview API surface.

## Limits and cautions
- Most of the page describes the **2026-05-01-preview** API. Preview surfaces change, and the terms state that data may be processed outside the Azure compliance boundary.
- The documentation explicitly disclaims responsibility for compliance, geographic boundaries, testing and responsible-AI mitigations. That responsibility falls to the implementer.
- No latency figures for permission synchronisation are given, so the size of the revocation window is unknown and must be measured per deployment.
- The four approaches are not compared on security strength, only on fit. A course must supply that analysis.
- SharePoint Information Management policies are explicitly not honoured — a gap between source enforcement and index enforcement that will surprise people.
- Feature availability differs between REST API versions and SDK packages; any lab must pin versions and verify support.
- Single-vendor. The general principles transfer; the mechanisms do not.
