## What this source is
This is the **developer-facing build surface** for agents on Microsoft 365 — the thing a practitioner actually types, runs and debugs, as distinct from the platform-selection question of *which* agent to build and the measurement question of *whether it is any good*.

Those two questions are already covered in this repository and are **not repeated here**. [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md) carries the build-path comparison: the three-way platform/software/infrastructure split, prompt agents versus hosted agents, basic versus standard Foundry setup, declarative versus custom engine as an *architectural* fork, the four-way orchestrator-ownership table, and the Copilot Studio pros-and-cons list. [agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md) carries **everything about evaluation** — the three core types, the local-versus-cloud evaluator tiering, the conversation split strategies, the nineteen-evaluator catalogue and the threshold discipline. This note adds only one observation about evaluation, in the negative: **the toolchain has no evaluation surface at all**, and the seam between "my manifest is valid" and "my agent is good" is unbridged and undocumented.

What is new here is the *toolchain*: what it scaffolds, what a local loop looks like before anything is deployed, what the lifecycle file contains, how many environments the model supports, what the publishing routes actually permit per build path, and what the store gates test. Read together, the family answers a question the selection guidance cannot: **once the platform is chosen, what is the shape of the working day, and what does the tooling decide for you before you have written a line?**

## The argument in full

### The toolkit is a lifecycle harness, and its unit of work is an app package
The Agents Toolkit is described as "a suite of tools for building enterprise-ready agents and apps that work across Microsoft 365 Copilot, Teams, Office, web, and other third-party messaging channels", streamlining development "with built-in project scaffolding, testing, deployment, and integration with AI tools including Microsoft 365 Agents SDK, Azure AI Foundry, and TypeSpec for Copilot". It ships in three forms — a Visual Studio Code extension "optimized for TypeScript and JavaScript development", a Visual Studio workload "optimized for .NET development", and a command-line interface "for the terminal or CI/CD processes" — and the documentation states that the CLI "offers the same features as the IDE extensions". That last claim is the load-bearing one for any team that intends to automate, and it is the reason the toolkit belongs in a delivery course rather than a demo.

The scaffold is small and legible. A generated project holds `.vscode` for debugging configuration, `appPackage` for the manifest templates, `env` for environment files, `infra` for "templates for provisioning Azure resources", and `src` for the code. **Two of those five directories contain things the developer did not write and will be asked to own** — the Bicep under `infra/` and the identity configuration the lifecycle file performs — and that is the first honest observation the material supports.

The lifecycle is declared in `m365agents.yml`, with siblings `m365agents.local.yml` and `m365agents.playground.yml` for the local and sandbox targets. It has three stages — **provision**, **deploy**, **publish** — each a list of named actions, and the CLI commands map onto them one to one: `atk provision`, `atk deploy`, `atk publish` each "run the … stage in `m365agents.yml`". The full command surface is wider than the three stages and worth reading as a statement of what the vendor thinks the job is: `atk doctor` (prerequisite checking), `new`, `add`, `auth`, `entra-app`, `env`, `install`, `launchinfo`, `list`, `package`, `validate`, `preview`, `update`, `upgrade`, `collaborator`, `uninstall`. Three of those deserve notice. **`atk collaborator`** exists to "check, grant and list permissions for who can access and manage" the app and its Entra application — the toolkit models the fact that an app has more than one owner. **`atk uninstall`** cleans up "resources associated with Manifest ID, Title ID, or an environment" — the toolkit models estate hygiene as a first-class command, which is rarer than it should be. And **`atk upgrade`** exists to "upgrade the project to work with the latest version" of the toolkit, which is an admission, in the command list, that **a generated project can fall out of compatibility with the tool that generated it.**

### The environment model is the strongest idea in the family
Environments are `.env.<name>` files, with `${{VAR_NAME}}` placeholders resolved at provision time throughout the manifest, the declarative agent file and `m365agents.yml`. The convention is stated explicitly: `.env.<target>` for a tenant or stage, `.env.<target>-<variant>` for a version or branch within a target, `.env.<target>.user` for "secrets for that target, never committed", and `.env.local` generated during provisioning. Shell environment variables override file values on conflict.

The claim built on that is genuinely useful and generalises beyond this platform. **Target environment and agent version are the same problem and take the same mechanism.** To run a v2 agent beside a v1 agent in the same production tenant you add `.env.prod-v2` with a different Teams app ID, and "the platform treats apps with different IDs as separate installations, regardless of how much code they share". One manifest file produces two distinct installable apps; "users who received the preview install see v2; all other users remain on v1". Where the difference exceeds variable substitution, a second declarative agent file is referenced through a variable — `declarativeAgent.${{AGENT_VARIANT}}.json` — and **both files are stored in the repository and reviewed in pull requests like any other source file, with no feature flags required.** That is an unusually clean answer to a problem most teams solve with runtime flags, and it is durable reasoning independent of the product.

Promotion is then a flag rather than an edit: `atk provision --env staging`, `atk deploy --env staging`, `atk publish --env staging`. The stated benefit — "passing `--env prod` is the complete promotion step" — is what makes the CI/CD story coherent rather than aspirational. The published GitHub Actions pattern is a matrix over targets, one job per environment, each mapping an explicitly named secret, "because GitHub secret names only allow uppercase letters, digits, and underscores (for example, a target name like `prod-v2` can't be used directly as a secret name)". The warning attached is worth quoting in full because it is the failure this whole pattern exists to prevent: "Don't store production secrets in `.env.prod`. Use `.env.prod.user` for local development and your CI/CD secret store for pipeline runs. Ensure the `.user` files are excluded by `.gitignore` and never committed."

The pipeline prerequisites are equally concrete: a service principal with either certificate-based or password-based authentication, repository variables `AZURE_SERVICE_PRINCIPAL_CLIENT_ID`, `AZURE_TENANT_ID`, a client secret or base64 certificate, plus `BOT_AZURE_APP_SERVICE_RESOURCE_ID` and `TEAMS_APP_ID`, and the note that "you don't need to commit env files under the env folder to the repo". Both GitHub Actions and Azure Pipelines are supported, with a documented build-action mapping per language, and a documented escape hatch: if the CLI "doesn't meet your pipeline requirements", the `deploy` stage is just `build` and `deploy` actions and can be rewritten by hand.

### The local loop exists, is genuinely cheap, and is documented with its own limits
The Agents Playground is "an integrated sandbox to locally test and debug AI agents and traditional bots", eliminating "the need for a Microsoft 365 developer tenant, tunneling services like Ngrok, and app/bot registration". It runs a local web app that emulates the client and the connector service using mock data. The endpoint defaults to `http://localhost:3978/api/messages`. Accepted channel identifiers are `msteams`, `directline`, `webchat` and `emulator`, and "when you set a channel ID, the properties of the messages sent to the application changes accordingly to simulate a real environment".

A detail here is easy to miss and changes what the default loop means. **When the Playground is run standalone the default channel is `msteams`; when it is launched through the Agents Toolkit the default channel is `emulator`** — and the `emulator` channel "does not support some Teams-specific mock activities", specifically installation updates, channel and team conversation updates, and notification activities used by Agent 365 projects. The consequence is that the *convenient* local loop is less faithful than the *manual* one, silently, by default. The documentation states the fact and does not state the cost.

Activity mocking is the Playground's real contribution. Predefined triggers cover installation updates, member and channel and team additions and removals, and renames, each mapped to a named handler; a custom-activity facility sends an arbitrary JSON payload, so an activity absent from the menu can still be exercised. Mock Teams context — tenant, bot, current user, five named users, personal chat, group chat, team and channels — lives in an optional `.m365agentsplayground.yml`, and changing it has three declared effects: it changes what the connector APIs return, it changes the activity payload, and it changes the Playground's own user interface. **The file "requires exactly five users in the `users` section. Configurations with fewer or more than five users aren't supported."** No rationale is given for the constant.

Two configuration files with similar names coexist and are not the same thing: `m365agents.playground.yml` is generated by the toolkit and controls how the Playground *starts*; `.m365agentsplayground.yml` is optional and customises *mock data*. Authentication can be supplied by environment variable, command-line option or an in-browser form, and the Playground acquires a JSON Web Token and validates the token in the application's response.

The published limitations are the most valuable paragraph in the whole family, because a tool that states what it cannot emulate is a tool you can reason about. Manifest-enabled features are unavailable "as Agents Playground doesn't process it". Only Adaptive Cards are supported among card types, and four Adaptive Card features are excluded by name — typeahead search, user mention, stage view and full width. Mobile and meeting experiences are unsupported. And a comparison table is published: basic messaging, connector APIs answering with mocked data, and Teams events by mock activity are all available, while **typing indicators, tabs, message extensions, dialogs, single sign-on and non-Adaptive cards are not**.

There is also a programmatic path, documented in the extension skill rather than on Learn: `@microsoft/m365agentsplayground-cli` exposes a `TestClient` that drives conversations headlessly against the bot endpoint, with `newConversation()` to isolate tests, and a `BotResponse` carrying `text`, `attachments`, `suggestedActions` and `type`; and a `createConversationServer` HTTP facade so non-Node runners can post a scenario of turns and read back per-turn statuses of `Completed`, `TimedOut`, `Errored` or `Skipped`. **This is a conversation driver and an assertion surface. It is not an evaluator, it scores nothing, and nothing in the toolchain does.**

### The declarative agent has no local loop, and that is the sharpest asymmetry in the family
The Playground documentation states plainly: "**This is not supported for declarative agents.**" The extension skill repeats it — the Playground "applies to code-based Teams bots/agents only", and "declarative agents and API plugins must be tested in M365 Copilot". The published declarative-agent tutorial confirms the shape of the alternative: author, then select **Provision** in the Lifecycle pane, then "go to the Copilot application at `https://m365.cloud.microsoft/chat`", select the agent, and ask it a question.

**For a declarative agent, `provision` is the inner loop.** There is no sandbox, no mock, no tunnel-free path; the cheapest iteration requires a licensed tenant and a round trip through a live product surface. That is a substantial difference in cost of iteration between the two agent kinds, and the material states the facts that imply it without ever stating the implication.

Declarative agents are otherwise well served at authoring time. TypeSpec for Microsoft 365 Copilot is "a domain-specific language" offering decorators — `@agent`, `@instructions`, `@capabilities`, `@behaviorOverrides` — as "an alternative to manually authoring JSON manifest files", compiling to the required manifests and generating OpenAPI specifications for API plugins. Eleven built-in capabilities are named: `CodeInterpreter`, `CopilotConnectors`, `Dataverse`, `Email`, `GraphicArt`, `Meetings`, `OneDriveAndSharePoint`, `People`, `ScenarioModels`, `TeamsMessages`, `WebSearch`. **The default scoping rule is worth teaching on its own:** for the connector, Dataverse and several other capabilities, omitting the scoping array means the agent gets everything the signed-in user can reach. Declared narrowness is opt-in; the default is the user's whole permitted surface.

The scaffold catalogue is wide, and its shape is informative. Among the capabilities offered by `atk new -c` are `declarative-agent`, `declarative-agent-action`, `-action-bearer`, `-action-oauth`, `-action-from-existing-api`, `declarative-agent-with-action-from-mcp`, `declarative-agent-with-graph-connector`, `declarative-agent-typespec`, `basic-custom-engine-agent`, `weather-agent`, **`foundry-agent-to-m365`**, `copilot-connector`, `teams-agent`, three retrieval-augmented Teams agent variants, `teams-collaborator-agent`, and the older `tab`, `bot`, `message-extension` and Office add-in templates. A basic declarative agent requires no programming language at all.

### The Agents SDK is a transport layer, not an agent framework, and the documentation says so
The Agents SDK "is a development framework for building conversational agents … the plumbing layer between a user sending a message … and whatever logic you built to respond". It supports **C# on .NET 8.0, JavaScript on Node.js 18 and later, and Python 3.9 to 3.11**. It solves three named problems: multi-surface reach through a channel abstraction; AI-service independence, since it "provides the scaffolding for receiving messages, managing state, and routing events, but makes no assumptions about what generates the response"; and conversation state, through "the concept of a turn … and tracks state across turns without requiring developers to wire up their own persistence layer". Mechanically it normalises an inbound message into an `Activity`, routes it to a handler, and translates the response back to the channel format.

The disclaimer is unusually direct and should be read as the definition rather than as a caveat: "**The Agents SDK isn't an AI model, an orchestration engine, or a no-code builder. The Agents SDK doesn't decide what an agent says.**"

That settles the relationship with Agent Framework, which is the single most confused point in this area. **They are not alternatives; they are layers.** The Agents SDK "focuses on supporting the conversation management, channel/client management, and authentication functionality"; orchestration is pluggable, and the documentation walks through registering Semantic Kernel and then Agent Framework *inside* an Agents SDK agent, recommending that the orchestrating agent be abstracted into its own class separate from the `AgentApplication` that manages the `TurnContext`. Agent Framework is described as coming "out of a progression of multiple SDKs in Microsoft", and as combining "the Semantic Kernel and AutoGen orchestrators into one single orchestrator". Its own guidance on when to use it is the most quotable sentence in the family: agents suit open-ended or conversational tasks needing autonomous tool use, workflows suit well-defined steps needing explicit control of execution order, and — "**If you can write a function to handle the task, do that instead of using an AI agent.**"

The hosting shape the SDK assumes is visible in the documented program structure: a `CloudAdapter` accepting HTTP requests and creating the `TurnContext`; an `IStorage` registration where "many samples use `Memory Storage` that should be switched out to more persisted storage like `Blob` or `CosmosDb` for production use"; `AgentApplicationOptions`; the agent registration itself; and a route at `api/messages`. Behind it sits Azure Bot Service, which "handles the communication between channels and your code". **An Agents SDK agent is a web service with an inbound message contract and an external identity, and every deployment concern follows from that.**

### Bot Framework is superseded, the migration is documented in detail, and the end date is not
The Agents SDK "is the evolution of the Azure Bot Framework SDK". There is far more migration material than one would expect: a general guidance page, and language-specific guides for .NET and Python with package mapping tables, namespace find-and-replace instructions, configuration changes, troubleshooting sections and closing checklists. The framing is repeated in both: "Treat this work as a modernization effort, not only a package swap."

The published list of functionality that **is not supported** in the Agents SDK is the part with real planning consequence, since "bots requiring these functionalities can't migrate without implementing alternatives": Adaptive Dialogs; AdaptiveExpressions (available but "isn't actively supported"); the legacy Application Insights telemetry approach; the Bot Framework CLI, all of whose commands are deprecated; deprecated activity types such as payments; the Yeoman-style generators, "because the Microsoft 365 Agents Toolkit replaces them"; the Inspection tooling; Language Generation; Language Understanding; the previous generation of AI tooling — LUIS, Orchestrator and QnA Maker, whose "online services … are already disabled"; QueueStorage; streaming connections; and TemplateManager. Dialogs survive under a new namespace "as a practical bridge during migration".

Separately and more sharply dated, **TeamsFx** — the toolkit's own predecessor SDK — carries a repeated first-party notice: it "is no longer supported by Microsoft for building Microsoft 365 Copilot extensions, Microsoft 365 agents, or modern Teams app scenarios", is "currently in deprecation mode and will receive community-only support on GitHub until **September 2026**", and "new projects should not be built with TeamsFx". A second phrasing on the JavaScript reference gives the other end: "officially deprecated by September 2025, with support continuing until September 2026." That is a real, dated, first-party window — and it is the only one in this family.

### Publishing is where the build decision is finally paid for
The distribution options are three: share within a tenant, publish to an organisational catalogue, or offer through the Microsoft Commercial Marketplace via Partner Center's "Microsoft 365 and Copilot" program under the offer type "Apps and agents for Microsoft 365 and Copilot". Before submission an agent must meet the Commercial Marketplace certification policies, the Microsoft 365 store validation guidelines for agents, and the Responsible AI validation checks, with App Compliance Program certification optional.

The published per-build-path matrix is the concrete form of a constraint this repository already quotes in one-sentence form, and the matrix says more than the sentence does. For **declarative agents built with Agents Toolkit** and for **custom engine agents built with Agents Toolkit**: sideloading for personal use is supported, submission to an organisational catalogue is supported, submission to the Commercial Marketplace is supported, and **"share with others" is not supported**. For **declarative agents built with Microsoft 365 Copilot Agent Builder**: sideload, share and organisational catalogue are all supported and **Commercial Marketplace is not**. For **declarative agents built with Copilot Studio**: sideload, share and catalogue supported, **Marketplace not**. For **SharePoint agents**: sharing only, with organisational catalogue explicitly footnoted as not applicable because such agents are "a configurable part of each SharePoint site". For **custom agents built with Copilot Studio**: all four supported, with Marketplace via Partner Center and a preview multi-tenant path.

Read as a whole this is a **two-axis trade, not one**. The pro-code toolkit path is the only one that reaches the commercial marketplace, and it is the only one that *cannot* do informal person-to-person sharing. A team optimising for internal viral adoption and a team optimising for a route to market are pushed to opposite ends of the same table. The existing repository quotation captures the second axis and not the first.

Two further constraints are stated once each and are easy to miss. **"Publishing agents via the Microsoft 365 Agents Toolkit isn't supported in Microsoft 365 Government tenants."** And Copilot Studio custom engine agents "are only eligible for Microsoft Store publication. Declarative Agents aren't supported."

For an agent that already exists elsewhere, the documented bridge is to wrap it: the Agents SDK "supports C#, JavaScript, and Python. If your agent is written in one of these languages, you don't have to modify it significantly", and the work reduces to creating an app registration and Azure Bot Service record, adding an `OnActivity` listener, and producing a manifest package. For a Foundry agent specifically, two integration paths are published — direct publish from the Foundry portal, which "automatically provisions Azure Bot Service and Entra ID", or an Agents Toolkit proxy app enabling "advanced customization, debugging, and multi-environment deployment". That comparison is already recorded in [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md) and is not re-argued here.

### The store gates are published, specific, and partly numeric
This is the finding that most changes the picture, because the criteria are not vague. Among the *must-fix* technical requirements: the app manifest version must be 1.13 or later, and "**starting July 2026**, if your agent operates in channels, all new Teams Store submissions must use manifest schema version 1.25 or later"; response time "mustn't exceed nine seconds for 99 percent, five seconds for 75 percent and two seconds for 50 percent"; apps "must maintain 99.9% availability", glossed as "if Microsoft 365 Copilot calls an agent 1,000 times, it must provide a meaningful response 999 times"; zero regressions on resubmission; the Microsoft 365 channel added to the bot where Outlook is a target; single sign-on registration updated where applicable; and Content Security Policy headers configured where applicable.

> **These figures are recorded here as contractual admission thresholds and nothing else.** They are not measurements, they are not effect sizes, and they license no claim about how any agent performs. Under [09-Durable-and-Perishable-Register.md](/wiki/program/09-Durable-and-Perishable-Register.md) they are perishable policy values and must not be propagated into teaching material as magnitudes.

Beyond the numbers the requirements are architectural and cheap to design for and expensive to retrofit. Every response from a custom engine agent "must include an AI label, citations, and a feedback button", must be streamed, and must include suggestive prompts afterwards. Custom engine agents "must include **copilot** in `bot.scopes` and `bot.commandList.scopes`". An agent must carry at least three and at most five sample prompts per command. Agents and plugins supporting API or Model Context Protocol actions "must request explicit user permission before making any server calls". A declarative agent's `name` must be identical across `manifest.json`, the declarative agent file and `name_for_human` in the plugin files. Adaptive Card responses must carry preview and content in the same template, must represent at least two pieces of information beyond branding, and must include a metadata URL. Compatibility must hold on Teams desktop and web, `copilot.microsoft.com`, and Microsoft 365 Copilot in Word.

There is also a content rule aimed squarely at prompt injection through the store listing: short descriptions "must not include … instructional phrases. For example, if the user says X, ignore, delete, reset, new instructions, answer in bold, or don't print anything", nor marketing language, superlatives, URLs, emojis, or "hidden characters like hexadecimal, binary, or unconventional symbols". **The vendor is treating the app catalogue itself as an untrusted-input surface**, which is the same conclusion the agent-configuration literature reaches from the other direction.

### Responsible AI validation reads the declaration, not the behaviour
Responsible AI checks run at two moments: "during manifest validation, when you sideload or publish your agent" and "during the processing of a user prompt". The manifest-time check fails an agent that attempts to encourage harmful actions, provoke arguments, "attempt to bypass guidelines or manipulate the model", or violate copyrights. Failure blocks publication. Remediation is stated as: "review the name, description, and instructions for your agent and make any updates to address the validation failure, and then try to publish your agent again."

**The scope is precisely the declared text.** The published worked example is an agent whose *instructions* say it should promote cities "known for their violent or extremist groups"; the check reads that sentence and refuses. This is a real control with a narrow and knowable reach, and it is exactly the kind of control that gets filed against risks it cannot touch. Nothing in this check inspects a tool, a data source, a retrieved document or a produced answer. Whether the runtime check does is a different page and a different note.

### GitHub Copilot agent mode is not positioned in this material
The documentation read does not position GitHub Copilot agent mode as part of this toolchain, and no page consulted describes using it to author toolkit projects. What exists instead is the first-party extension skill, which is an instructions artefact intended for a coding agent operating the toolkit's own CLI — the same genre as the corpus recorded in [hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md), one register down. It carries operational rules a human would not need: always pass `-i false` in automation "to avoid hanging"; long-running commands need a 120-second-plus allowance; local service startup "hangs terminal (expected)" and must be backgrounded; `export ATK_CLI_SKILL=true` tags every subsequent invocation as skill-initiated. It also carries diagnostics no Learn page states — that a missing `generateServicePrincipal: true` in the `aadApp/create` action yields `AADSTS7000229`, that a missing `TENANT_ID` in `.localConfigs` causes the SDK to use the wrong token authority and produce a 401 from the connector, and that a persistent 401 after an authentication fix may mean the development tunnel URL has been blacklisted and a fresh tunnel is required. **The most operationally useful material about this toolchain is shipping inside an extension, versioned separately from the documentation, and is not discoverable from Learn.** That is itself a finding about where knowledge now lives.

## Key concepts and practices
- **The toolkit is a lifecycle harness.** Three stages — `provision`, `deploy`, `publish` — declared in `m365agents.yml`, with `m365agents.local.yml` and `m365agents.playground.yml` for other targets.
- **The CLI is stated to offer the same features as the IDE extensions**, which is what makes automation credible.
- **Scaffold shape:** `.vscode`, `appPackage`, `env`, `infra`, `src`. Two of the five hold generated infrastructure and identity configuration the developer will be asked to own.
- **`atk upgrade` exists**, which is an admission that a generated project can fall out of step with its generator.
- **`atk collaborator` and `atk uninstall` exist**, modelling shared ownership and estate cleanup as first-class commands.
- **Environments are `.env.<target>` files with `${{VAR}}` substitution.** Secrets live in `.env.<target>.user`, never committed; CI injects `SECRET_*` at runtime.
- **Target environment and agent version are the same mechanism.** A different Teams app ID makes two installable apps from one manifest, so v1 and v2 can run side by side in one tenant.
- **Variant agent definitions are files in the repository reviewed in pull requests, not runtime feature flags.**
- **Promotion is `--env`, not an edit.**
- **The Playground removes the tenant, the tunnel and the registration** from the inner loop, and mocks Teams context, connector API responses and activities.
- **Default channel differs by launch route:** `msteams` standalone, `emulator` through the toolkit — and `emulator` omits several Teams-specific activities.
- **The Playground publishes its own limitations**, including no manifest processing, Adaptive Cards only with four features excluded, no mobile or meeting, and no typing indicator, tabs, message extensions, dialogs or single sign-on.
- **The mock configuration requires exactly five users.** No rationale is published.
- **`playground-cli` gives a headless `TestClient` and an HTTP conversation server** for CI. It drives conversations and asserts on them. **It does not evaluate.**
- **Declarative agents have no local loop.** The Playground explicitly does not support them; `provision` into a licensed tenant is the inner loop.
- **TypeSpec is an alternative authoring surface** for declarative agents and API plugins, compiling to manifests and OpenAPI, with eleven named capabilities.
- **Omitting a capability's scoping array grants the whole surface the signed-in user can reach.** Narrowness is opt-in.
- **The Agents SDK is transport, state and identity — not orchestration.** "The Agents SDK doesn't decide what an agent says."
- **Languages:** C# on .NET 8.0; JavaScript on Node.js 18+; Python 3.9–3.11.
- **Agent Framework composes inside the Agents SDK.** It merges Semantic Kernel and AutoGen orchestrators; the recommended pattern separates the orchestrating agent class from the `AgentApplication` managing `TurnContext`.
- **"If you can write a function to handle the task, do that instead of using an AI agent."**
- **Sample storage is in-memory and documented as needing replacement** with Blob or Cosmos DB for production.
- **Bot Framework is superseded with detailed per-language migration guidance and a published unsupported list**, including Adaptive Dialogs, LUIS, QnA Maker, Composer, Language Generation, the Bot Framework CLI, streaming connections and QueueStorage.
- **TeamsFx carries a dated window: community-only support until September 2026.**
- **Distribution differs by build path on two axes.** Toolkit paths reach the commercial marketplace and cannot share person-to-person; Agent Builder, Copilot Studio declarative and SharePoint agents can share and cannot reach the marketplace.
- **Publishing via the Agents Toolkit is unsupported in Microsoft 365 Government tenants.**
- **Store gates are published and partly numeric** — manifest 1.13+, and 1.25+ for channel-operating agents from July 2026; stated latency percentiles; a stated availability figure; three to five sample prompts per command; mandatory AI label, citations and feedback button; `copilot` in `bot.scopes`; explicit user permission before API or MCP server calls.
- **Store listing text is treated as an injection surface**, with instructional phrases, hidden characters and emojis prohibited in descriptions.
- **Responsible AI manifest validation inspects the declared name, description and instructions** and blocks publication. It inspects nothing the agent does.

## Method and evidence base
First-party product documentation with an instructional and contractual purpose, plus one first-party configuration artefact shipped inside an extension. **Definitional and normative, not empirical.**

The distinction matters more here than in most of this folder, because two different kinds of authority are mixed and they are easy to conflate. The distribution matrix, the language support, the unsupported-migration list, the store thresholds and the Responsible AI failure categories are **statements of policy by the party that enforces the policy**, and on those the source is as authoritative as anything can be — if the page says the marketplace route is closed for Agent Builder agents, it is closed. The claims about ergonomics — that the toolkit "streamlines" development, that TypeSpec "dramatically simplifies" authoring and delivers "enhanced productivity", that the environment model gives "simplified onboarding" — are **marketing register with no supporting measurement anywhere in the material**, and they carry exactly the same weight as the benefit vocabulary already flagged in [hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md), which is none.

**Definitional authority is not evidential authority.** Microsoft may define what the Agents SDK is; it has published nothing that establishes that using it produces a better or faster outcome than not.

The extension skill is a third kind again. It is first-party, it is specific, and its diagnostic claims — the `AADSTS7000229` cause, the missing-`TENANT_ID` authority failure, the blacklisted tunnel — read as **field-derived rather than specified**, which makes them useful and unverifiable in equal measure. They are recorded here as reported, against a stated extension version, and should be treated as hypotheses a practitioner can test in ten minutes rather than as facts.

## Vocabulary the sources introduce
- **Agents Toolkit** — the lifecycle harness: scaffolding, environments, provisioning, deployment, publishing. Formerly Teams Toolkit.
- **`atk`** — the toolkit command-line interface, distributed as `@microsoft/m365agentstoolkit-cli`. Formerly the TeamsFx CLI.
- **Lifecycle stage** — `provision`, `deploy` or `publish`, each a named list of actions in `m365agents.yml`.
- **Action** — one step in a lifecycle stage, such as `aadApp/create`, `botFramework/create`, `teamsApp/zipAppPackage`, `teamsApp/extendToM365`, `arm/deploy`, `file/createOrUpdateEnvironmentFile`.
- **Environment file** — `.env.<target>`, with `.user` for secrets, resolving `${{VAR}}` placeholders at provision time.
- **App package** — the manifest-plus-assets zip that is the unit of distribution across Teams, Outlook, Microsoft 365 Copilot and the Office applications.
- **Teams app ID** — the identity that makes two builds separate installations, and therefore the mechanism for parallel versions.
- **Agents Playground** — the local sandbox emulating client and connector with mock data. Formerly the Teams App Test Tool.
- **Activity** — the normalised message object the SDK routes; also the unit the Playground mocks.
- **Turn** — "a single unit of work in a conversation", the SDK's state boundary.
- **Mock activity** — a synthesised event, predefined or custom JSON, used to exercise a handler with no real client.
- **Channel identifier** — `msteams`, `directline`, `webchat` or `emulator`; changes message properties and card rendering.
- **`TestClient` / conversation server** — the headless conversation drivers in `playground-cli`.
- **Declarative agent** — configuration over the host's orchestrator and models; from the toolchain's view, an agent with a manifest, a definition file and no local loop.
- **Custom engine agent** — an agent with its own orchestrator and models; from the toolchain's view, a web service with an `api/messages` route, an identity and a sandbox.
- **TypeSpec for Microsoft 365 Copilot** — a decorator-based domain-specific language compiling to manifests and OpenAPI.
- **Capability** — a declared knowledge or action surface for a declarative agent, defaulting to everything the user can reach when unscoped.
- **Organisational catalogue** — the tenant-scoped distribution target requiring administrator approval.
- **Commercial Marketplace / Agent Store** — the cross-tenant distribution target, gated by Partner Center validation.
- **Responsible AI manifest validation** — the publication-time check on declared name, description and instructions.
- **Sideload** — installation for personal use, bypassing catalogue approval.

## What to remember
- The toolkit is a lifecycle harness. Its stages are its argument: provisioning, deployment and publishing are separate acts with separate owners.
- **Two directories in every scaffold contain things you did not write and will be asked to own.** Read the Bicep and the identity actions before the first demo, not after the first incident.
- The environment model is the durable idea. **Target and version are the same problem**, and an identifier is what makes two builds separate rather than a flag.
- Promotion should be a flag, not an edit. If promoting requires editing a file, the environments are not modelled.
- **A sandbox that publishes its own limitations is worth more than one that does not.** Use the limitations table to write what your test did *not* cover.
- The convenient local loop is less faithful than the manual one, by default, silently. Know which channel you are emulating.
- **A conversation driver is not an evaluator.** Passing multi-turn tests establishes that the agent behaves as specified, and nothing about whether the specification was right.
- **The declarative agent has no cheap loop.** If your iteration cost includes a licensed tenant, that is a project cost and it should appear in a plan.
- The Agents SDK is transport. Orchestration is a separate, pluggable, replaceable decision — which is the point.
- "If you can write a function to handle the task, do that instead of using an AI agent." That sentence is in the vendor's own documentation and is the most useful thing in it.
- **Distribution is constrained on two axes, not one.** The path that reaches the marketplace is the path that cannot share informally.
- The store gates are published and specific. **A team that reads them at submission time will discover architecture decisions it made months earlier.**
- The Responsible AI check reads your declaration, not your behaviour. It is a real control with a narrow reach, and it must be filed against what it actually covers.
- The vendor treats its own catalogue listings as an untrusted-input surface. So should you.
- **Every principal name in this area has changed at least once.** Cite by version and date or do not cite.

## Why it matters for the course
The programme currently teaches building agents almost entirely through a coding agent and the Model Context Protocol, and knows the vendor's own build surface only as a name inside a quoted comparison. That is verifiable rather than impressionistic: searching the wiki for *Agents Toolkit*, *Agents SDK*, *Agents Playground*, *Bot Framework* or *TeamsFx* returns **ten matches across six files**, and every one of them is a quotation of the commercial-store constraint or of the Copilot Studio comparison drawn from [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md). *Agents Playground*, *Bot Framework* and *TeamsFx* appear **nowhere**. The toolchain is cited and never taught.

Three things here earn their place, in descending order of durability.

**First, the environment and version model is a genuinely good idea that survives the product.** Modelling deployment target and software version through the same mechanism, making identity rather than configuration the thing that separates two installations, keeping variant definitions as reviewable files rather than runtime flags, and reducing promotion to a flag — that is transferable reasoning about release engineering, and it happens to be demonstrable in an afternoon here. It is also the answer to a question the programme asks repeatedly and has not had a concrete instance of: what does it look like when the pilot and the production system are the same repository?

**Second, the Playground is the cleanest available teaching object for the difference between a test environment and the environment.** It is fast, it is free, it removes three dependencies, it mocks convincingly — and it publishes a table of what it cannot emulate, plus a default that is quietly less faithful than the alternative. A student who learns to open the limitations table before the sandbox has learned something they will need on every simulator, emulator and staging environment for the rest of their career. This is the seam the programme's measurement strand needs and has been asserting in the abstract.

**Third, the publishing and validation layer converts a distant abstraction into a dated, enumerable, external constraint.** The programme teaches that non-functional requirements must be verifiable and that constraints are discovered late at ruinous cost. Here is a published list of must-fix criteria, imposed by a third party with the power to refuse, containing architectural requirements — streamed responses, an AI label, citations, a feedback button, a specific scope value, explicit consent before a tool call — that are cheap at design time and expensive at submission. And the Responsible AI check is a control with a knowable and narrow scope, which is the exact worked example the assurance strand needs to teach that a control's existence is not evidence of coverage.

It connects to [hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md) for pinned-revision discipline and for the observation that benefit vocabulary in vendor prose is unwarranted; to [agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md) for everything about measuring the agent, which this toolchain does not do; to [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md) for the build-path decision this note picks up after; and to [learn-mcp-server-docs.md](/research/06-microsoft-platform/learn-mcp-server-docs.md) for the protocol that appears here both as a scaffold template and as a store policy obligation.

## How to teach it
- **Lecture:** put the distribution matrix on one slide and ask which column a team optimising for internal viral adoption should choose, then which column a team optimising for a route to market should choose. Let the contradiction land before naming any product.
- **Lecture:** teach the environment model as release engineering, not as tooling. Ask what an identifier buys that a feature flag does not, and require an answer about rollback and blast radius.
- **Lecture:** read the Agents SDK's "what it is not" paragraph aloud, then ask students to place Agent Framework, Semantic Kernel, a model deployment and a retrieval index into layers. Most will have been treating layers as alternatives.
- **Lab, highest value in the topic:** run the same agent in the Playground on channel `emulator` and on channel `msteams`, then in a real tenant. Record every behavioural difference and reconcile it against the published limitations table. Ask which differences the table predicted and which it did not.
- **Lab:** write the spike charter's *what this spike will not decide* section **from the limitations table** before running the spike. Then run it and check whether the section held.
- **Lab:** delete `generateServicePrincipal: true` from the `aadApp/create` action, predict the failure in writing, provision, and compare the prediction to the error. The exercise is the prediction, not the fix.
- **Lab:** provision the same project to two environments and promote by flag only. Then have a second student, on a second machine, promote it again from a clean clone. The second run is the assessment.
- **Lab:** write four `TestClient` conversation tests, get them green, and then write one paragraph on what green does not establish. Collect the paragraphs, not the tests.
- **Lab:** construct one agent that the Responsible AI manifest check correctly refuses and one that it passes but a human reviewer would not. Submit both. This is the control-scope exercise and it takes twenty minutes.
- **Assessment:** require every build-path decision to name the distribution routes it forecloses, with the source and the date of the page consulted. A decision that names no foreclosed route was not a decision.
- **Assessment:** require a handover to include an observed `atk provision` run performed by the recipient, with the observer's note on what was missing on the first attempt.
- **Assessment:** ask what would have to change for the team to pick a different toolchain, and what the switching cost would be *given work already done*. A student who answers "nothing much" has not looked at the manifest.
- **Framing:** the most perishable material in this repository after the Learn MCP Server. **Pin the version, record the date, assess the reasoning, and never assess the command.**

## Limits and cautions
- **Verification depth is uneven and is recorded per source above.** Six pages were fetched and read in full; roughly thirty were read only through search-returned excerpts; the Partner Center certification policy and the full Agent Store validation guidelines were **not fetched**, and the criteria quoted from them are the subset the excerpts returned. **The must-fix list in this note is not exhaustive and must not be presented as the complete gate.**
- **The extension skill is not published documentation.** It ships inside `teamsdevapp.ms-teams-vscode-extension` version 6.13.2026072312, has no public URL, is not covered by any documentation currency guarantee, and will change without a release note the reader can find. Its diagnostic claims are reported, not verified.
- **Names decay faster than behaviour.** Teams Toolkit, Teams App Test Tool, TeamsFx CLI, Teams AI Library, Semantic Kernel, Azure AI Foundry, Azure Bot Framework SDK and four Foundry role names have all been renamed. Documentation pages consulted still carry old names in URLs, in package names and in prose, sometimes on the same page as the new one.
- **Two npm packages for the Playground appear in current documentation**: `@microsoft/teams-app-test-tool` with the `teamsapptester` command, and `@microsoft/m365agentsplayground` with the `agentsplayground` command. Both appear on live pages. A course that picks one will be wrong for some readers.
- **Version numbers in this note are floors, not facts.** The extension skill's schema table — manifest `1.26`, declarative agent `v1.7`, lifecycle `v1.11` with "some C# templates still ship `v1.9`" — is accurate to that extension version and to nothing else.
- **Vendor selection material compares Microsoft options with each other.** Nothing here evaluates the toolkit against a non-Microsoft toolchain, and no such comparison was sought.
- **The ergonomics claims are marketing.** "Streamlines", "dramatically simplifies", "enhanced productivity", "simplified onboarding" and "rapid" appear without measurement and must not travel into teaching material.
- **The Playground's five-user constraint, the `emulator` default and the exact fidelity of card rendering are stated without rationale**, and any teaching built on them should be re-run rather than re-read.
- The Government-tenant publishing restriction is stated **once**, in a note on a single page, with no alternative offered. Treat it as a real constraint and re-verify it before advising anyone.
- **Teaching this material risks producing students fluent in `atk` and unable to say what the tool decided for them.** The scaffold, the identity model, the sandbox's default channel and the distribution route are all decisions taken before the first commit. Assess the account of those decisions, never the fluency.

## What the documentation does not say
Recorded explicitly, because each absence changes what a claim built on this material may assert.

1. **No measure exists, anywhere in the material, of how much the toolkit reduces time to a first working agent.** No baseline, no comparison, no sample, no study. The benefit is asserted in adjectives and never quantified. **In particular, nothing here supports any claim about agents launching in one duration rather than another**, and the standing prohibition on that sentence recorded in [09-Durable-and-Perishable-Register.md](/wiki/program/09-Durable-and-Perishable-Register.md) applies to this note's material without exception.
2. **Store validation criteria are published in detail — this is the opposite of a silence — but no outcome data accompanies them.** There is no published submission pass rate, no rejection rate, no rejection-reason distribution, no median time to approval, and no statement of how many resubmissions are typical. A team can read exactly what is required and cannot learn how often anyone meets it.
3. **No measurement method is published for the numeric store criteria.** The latency percentiles and the availability figure are stated as obligations with **no instrument, no population, no observation window and no sampling rule.** It is not stated whether Microsoft measures them, whether the publisher must, or what evidence is accepted.
4. **No calibration is published for the Responsible AI manifest check.** It is not stated whether the check is deterministic or model-judged, no false-positive or false-negative rate is given, no appeal path is described beyond "make any updates … and then try to publish your agent again", and **no evidence is offered that a manifest passing this check yields an agent that behaves acceptably.** The runtime check is a separate mechanism on a separate page and is not evaluated here.
5. **No evidence is published that the Agents Playground predicts deployed behaviour.** A *capability* difference table exists — what the sandbox can and cannot emulate — and that is valuable. A *fidelity* claim does not exist. Nothing states how often an agent that passes locally behaves differently in a tenant, and the `emulator` default makes the question sharper rather than softer.
6. **Bot Framework migration guidance is extensive — also the opposite of a silence — but the Bot Framework SDK itself carries no dated end-of-support in anything read here.** TeamsFx has a date (community-only support until September 2026). The Bot Framework SDK is described as superseded and its unsupported features are enumerated, and **no retirement date, no support policy and no migration deadline was found.** Nor is any migration-effort estimate published for any bot of any size.
7. **Compatibility between toolkit versions is partly documented and mostly not.** A Visual Studio 17.13-to-17.14 migration guide exists, and `atk upgrade` exists, so breakage is acknowledged. **No compatibility matrix, no support window for a toolkit version, and no statement of which toolkit versions emit which schema versions** were found on Learn — the schema table exists only inside the extension skill. There is no statement of how long a generated project remains buildable.
8. **The toolchain has no evaluation surface and does not say so.** `atk validate` checks the manifest against schema and rules; `playground-cli` drives conversations. **Nothing scores agent quality**, nothing connects to the evaluator catalogue recorded in [agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md), and no page consulted acknowledges the gap or tells a developer where to go next. The seam between *valid* and *good* is unmarked.
9. **No inner-loop guidance exists for declarative agents.** The Playground excludes them in one sentence and no substitute is proposed. The observed loop — provision into a licensed tenant and open a live product — is demonstrated in tutorials and never named as the recommended development cycle, nor is its cost discussed.
10. **The Playground's five-user requirement is stated as an unexplained constant**, with no rationale, no roadmap and no workaround for a scenario needing more.
11. **Nothing is published about what happens to a store-published agent when the toolchain that built it is renamed or superseded again** — whether listings persist, whether resubmission is triggered, or what the publisher's obligation becomes.
