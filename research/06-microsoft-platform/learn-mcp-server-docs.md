## What this source is
A small, unusually disciplined family of product pages describing a single hosted service, plus the host-side machinery that determines whether that service is ever actually used. The service half is straightforward: a remote MCP server at a fixed URL exposing three tools over the Microsoft Learn corpus. The interesting half is the second one, and it is the reason this note covers host documentation as well as product documentation.

**The pages are candid, in a specific and useful way, that attaching a tool to an agent does not cause the agent to use it.** The Get Started page carries a section headed "Set instructions (recommended)" whose opening line is "When the AI agent doesn't use the MCP tool when expected, it may be useful to configure specific instructions for the tool." The repository's troubleshooting section says it more bluntly still: "Even tool-friendly models like Claude Sonnet 4 sometimes fail to call MCP tools by default; use system prompts to encourage usage." That is a vendor documenting, in its own getting-started material, that its product's primary failure mode is silent non-invocation — and then shipping a remedy whose effectiveness it does not measure.

The other thing to hold about this source is what kind of authority it carries. **These pages establish what the Learn MCP Server is. They are not evidence that using it works.** The distinction is not pedantic here, because the marketing surface of the same project makes outcome claims — "Eliminate Hallucinations", "100% Trusted & Safe" — that nothing in the documentation supports and that no published measurement backs. The definitional content is excellent and should be taught. The outcome claims are unwarranted and must not cross into teaching material in any form.

## The argument in full
The service is described with commendable economy. **It is a remote MCP server using streamable HTTP at `https://learn.microsoft.com/api/mcp`.** There is no authentication — the overview states "There's no authentication required to access the Microsoft Learn MCP Server" — and no charge: "The Microsoft Learn MCP Server is publicly available. There's no charge to use the MCP server." Use is conditioned on the Microsoft Learn Terms of Use. The endpoint is not browsable: both the overview and the repository warn that it "does not support direct access from a web browser and may return a `405 Method Not Allowed` error if accessed manually," and the repository's troubleshooting table lists exactly that symptom. This combination — remote, unauthenticated, free, no local model, no tenant — is why it is a defensible first tool for a cohort with heterogeneous licensing, and the reasoning is worth making explicit rather than leaving as an accident of convenience.

**Three tools are published, and the way they are published is itself the lesson.** They are `microsoft_docs_search` (semantic search over Microsoft official technical documentation, taking a `query` string), `microsoft_docs_fetch` (fetch a documentation page and convert it to markdown, taking a `url` string), and `microsoft_code_sample_search` (search official code snippets and examples, taking a `query` string and an optional `language` filter). The parameter detail comes from the repository README; the developer reference deliberately withholds it, and says why: "Every time the client initializes the server, it should call list tool to get a tool list. Over time the list and the tools may change, so we are deliberately not describing request and response details here." The same page states the framing that follows from this — "Although the Learn MCP Server provides a public endpoint, it is not an Application Programming Interface (API) in the traditional sense... the interface may change dynamically including tools, and their request and response formats." The best-practices page turns that into a client contract: call `tools/list` on connection, never hardcode tool names or parameter schemas or expected behaviour, and on a 400 or 404 "assume your cache is stale — refresh via `tools/list` and retry", with the repository adding that a client should listen for `listChanged` notifications. **This is a genuinely different integration contract from a versioned REST API, and it is the single most transferable idea in the source.** A conventional API promises stability and breaks loudly; this promises instability and requires the client to rediscover. Neither is better; they are different bargains, and a student who does not notice which one they are in will build a brittle integration.

The retrieval mechanism is stated only at the level of provenance. The MCP server "provides an interface to the Learn knowledge service that powers Ask Learn and Copilot for Azure", and the FAQ confirms the same service backs the Azure portal, Ask Learn, Foundry and Copilot Studio. The 2024 engineering blog describes that service as an advanced retrieval-augmented generation system: Learn articles are chunked, embedded, and stored in a vector database, with pre-retrieval processing such as query rewriting, expansion and clarification, and post-retrieval processing such as re-ranking, chunk expansion, filtering and compression. The blog also records that the team built a "golden dataset" of questions, approved answers and best source articles, and used it for before-and-after tests on indexing changes, and that root-cause analysis of a single unsatisfactory response could take up to thirty minutes. **What the blog does not do — anywhere — is publish a result from any of that.** No recall figure, no ranking metric, no groundedness score, no before-and-after delta. The apparatus of measurement is described in detail and its outputs are withheld. That is the most important single observation in this note.

Freshness is described as cadence rather than as latency, and the difference matters. The overview's limitations section says "The underlying knowledge service refreshes incrementally after content updates and performs a full refresh once a day." The FAQ says "The data changes whenever new content is added, modified, or deleted, which is usually on a daily basis." **Neither statement bounds the interval between a page being published or corrected and that change being retrievable through the server.** "Incrementally after content updates" is compatible with seconds and compatible with hours. For a course whose entire platform posture is *check the documentation and record the date you checked it*, this is the exact quantity that would be most useful and it is the one not stated. The honest operational consequence is that the server can return a stale chunk and there is no published way to detect that it has.

Scope and filtering are handled in two short sentences that repay attention. The overview says "The MCP server contains publicly available documentation, not training or user profile information" — a negative definition that excludes personalisation and appears to exclude training modules, without positively enumerating what is included. Locale coverage, versioned-document handling, and whether Q&A or blog content is indexed are not addressed. The FAQ then says "The MCP doesn't provide filtering capability, although you can use a scope in your question" — so narrowing is a matter of prompt phrasing rather than a parameter, which means the narrowing is unauditable. And one FAQ answer describes a behaviour that anyone using `microsoft_docs_fetch` as a citation instrument needs to know: when content is modified or replaced a redirect is implemented, and when content is deprecated without replacement Microsoft will "redirect to the next best appropriate content, which may be a slightly modified scope, or to a landing page". **A fetch of a known-good URL can therefore silently return something other than what was there, and the documentation says so.** A citation to a Learn URL is a citation to a redirect target, not to a document.

Two operational levers are documented. The best-practices page describes `maxTokenBudget` as a query parameter appended to the endpoint URL — `https://learn.microsoft.com/api/mcp?maxTokenBudget=2000` — which "truncates content in results to stay within your budget", with the crucial qualification that "The parameter only affects search results — fetch always returns the full page." The repository files this under experimental features alongside an OpenAI-compatible endpoint at `https://learn.microsoft.com/api/mcp/openai-compatible` supporting the deep-research pattern. The default budget when the parameter is omitted is not stated. The second lever is throttling, and the FAQ handles it exactly as one would hope and not at all as one would want: "As a public and free endpoint, our service does have rate limits in place to ensure fair usage for all users. We encourage responsible use of this endpoint to help maintain its availability and performance for everyone." **Rate limits are confirmed to exist and no number, window, error code, retry guidance or backoff recommendation is published.** A team planning an agentic loop against this endpoint cannot size it from the documentation.

The configuration story across hosts is the section most likely to be wrong by the time anyone reads this note, and is recorded with that in mind. The developer reference gives the canonical shape as `{"microsoft.docs.mcp": {"type": "http", "url": "https://learn.microsoft.com/api/mcp"}}`; the repository gives it as `{"servers": {"microsoft-learn": {"type": "http", "url": "..."}}}`; a Windows setup page gives both a `settings.json` form nested under an `mcp` key and a `.vscode/mcp.json` form. VS Code documents workspace configuration at `.vscode/mcp.json` and user-profile configuration through **MCP: Open User Configuration**, plus gallery install by searching `@mcp` in the Extensions view. Visual Studio ships it built in — the repository's client matrix says "Upgrade to latest VS 2022 or 2026, 'Microsoft Learn' MCP is already built-in" — and Visual Studio's own documentation notes that its trust prompt is skipped when "The server is built in and shipped with the extension." Foundry takes a different route again: create a project, deploy a model, create an agent, paste instructions, then **Tools → Add → Custom → MCP**, enter the endpoint, and select **Authentication: Unauthenticated**. Fifteen or so clients are listed in the repository matrix with varying setup burdens, including one, Cline, that needs `"type": "streamableHttp"` rather than `"http"`. Since March 2026 there is also a plugin — `/plugin install microsoftdocs/mcp` in Copilot CLI — bundling the server with three agent skills named `microsoft-docs`, `microsoft-code-reference` and `microsoft-skill-creator`, and a CLI, `@microsoft/learn-cli`, giving the same three capabilities from a terminal with no MCP client at all. **The transport is stable and the configuration surface is not.** Teach the endpoint; verify the syntax.

Now the host machinery, which is where the actual failure modes live. **Trust is the first gate, and it fails quietly.** VS Code prompts for trust when a server is first started or its configuration changes, and its documentation states the consequence of declining precisely: "If you don't trust the MCP server, it will not be started, and chat requests will continue without using the tools provided by the server." The request succeeds. The answer arrives. It is simply ungrounded, and nothing in the transcript says so. Visual Studio adds a re-trust prompt when a server's configuration or capabilities change — explicitly including "tools, prompts, resources, resource templates, or instructions" — which is the same dynamic-tool-surface property surfacing as a governance event. **A dynamic tool list means trust is not a one-time decision.**

**Enablement is the second gate, and here the documentation and this repository's teaching material do not currently agree.** VS Code's chat-tools page says "Before you can use tools in chat, you need to enable them in the Chat view. You can enable or disable tools on a per-request basis by using the tools picker", and describes selecting or deselecting tools for the current request. Its MCP quickstart, however, says that after trust is confirmed "VS Code discovers the server's tools and makes them available in chat." Those two statements sit in tension, and **neither of them states that MCP tool checkboxes arrive cleared and must be selected.** Sessions [S001](/wiki/seminars/S001.md), [S012](/wiki/seminars/S012.md) and [S020](/wiki/seminars/S020.md) currently assert the cleared-by-default behaviour. That assertion is **not verified by the documentation read for this note**, and it should be treated as an observation about a particular editor build rather than as a documented product property. The durable claim underneath it — *a connected tool is not an invoked tool* — is separately and firmly documented, four times over: by the trust-decline behaviour above; by the "Set instructions (recommended)" section; by the repository's admission about Claude Sonnet 4; and by both getting-started walkthroughs, which include "Allow the agent to use the MCP server" as an explicit user step. **The claim survives; its stated evidence needs replacing.** A separate host constraint that the chat-tools FAQ raises but whose answer this note did not read is an error reading "Cannot have more than 128 tools per request" — recorded here as the wording of a question heading, not as a verified limit.

**Instruction delivery is the third gate, and it is the one with the most documented structure.** VS Code supports always-on instructions in `.github/copilot-instructions.md`, `AGENTS.md` and `CLAUDE.md`, and file-based instructions in `*.instructions.md` files found by default under `.github/instructions` and searched recursively, with alternates at `.claude/rules` and in the user profile, all configurable through `chat.instructionsFilesLocations`. The frontmatter carries `name`, `description` and `applyTo`, and the `applyTo` semantics are the load-bearing part: it is a glob relative to the workspace root, `**` applies to all files, and — the line that catches people — "If not specified, the instructions are not applied automatically, but you can still add them manually to a chat request." **An instructions file with no `applyTo` is inert by default.** The Learn Get Started page's own example uses `applyTo: '**'`, which is the blunt instrument; the sessions' narrower globs are the better practice and cost nothing. Two further properties matter for anyone reasoning about determinism: VS Code "combines and adds them to the chat context, no specific order is guaranteed", and matching is not purely mechanical — the agent decides "based on the file patterns specified in the `applyTo` property... or semantic matching of the instruction description to the current task." Precedence, where instructions conflict, runs personal, then repository, then organisation — the last spelled `Organization instructions` as a product label. And custom instructions "are not taken into account for inline suggestions as you type in the editor" — they govern chat, not completion.

**Verification that an instruction arrived is documented, and this is the most practically valuable thing the host pages contain.** The custom-instructions FAQ answers "Why is my instructions file not being applied?" with a checklist: confirm the file location; confirm the `applyTo` glob matches the file being worked on; and — the actionable one — "Verify the References section in the chat response to see which instructions files were used." Beyond that there is a chat customization diagnostics view, reached by right-clicking in the Chat view and selecting **Diagnostics**, which shows all loaded instruction files and any errors; a hover tooltip on **Chat: Configure Instructions** revealing each file's source; and, for deeper work, the Chat Debug view for inspecting language model requests. There are also settings that can switch the mechanism off entirely — `chat.includeApplyingInstructions` for pattern-based instructions and `chat.includeReferencedInstructions` for instructions pulled in by Markdown link. **A specification an executor has not received is not a specification, and the host gives you three separate ways to check receipt.** Not using them is a choice.

## Key concepts and practices
- **A remote MCP server over streamable HTTP at `https://learn.microsoft.com/api/mcp`.** No authentication, no charge, no local model, no tenant. Use is subject to the Microsoft Learn Terms of Use.
- **The endpoint is not browsable** and returns `405 Method Not Allowed` to a browser. It is for MCP clients.
- **Three tools:** `microsoft_docs_search` (semantic search, `query`); `microsoft_docs_fetch` (page to markdown, `url`); `microsoft_code_sample_search` (`query`, optional `language`).
- **The tool surface is explicitly dynamic.** Call `tools/list` on connection; never hardcode names, schemas or behaviour; treat 400 and 404 as a stale cache and refresh; listen for `listChanged`.
- **"Not an Application Programming Interface (API) in the traditional sense."** Reach it through an agent framework, not by calling the endpoint directly.
- **It fronts the Learn knowledge service** that also powers Ask Learn, Copilot for Azure, the Azure portal, Foundry and Copilot Studio — an advanced RAG system over chunked, embedded Learn content.
- **Freshness is stated as cadence, not latency:** incremental refresh after content updates, full refresh once a day, content changing "usually on a daily basis". **No indexing-lag bound is published.**
- **Scope is defined negatively:** "publicly available documentation, not training or user profile information". Locale, versioned-document and non-documentation coverage are unaddressed.
- **No filtering parameter exists.** Narrowing is done by phrasing the question, and is therefore unauditable.
- **Deprecated content redirects to "the next best appropriate content"**, so a fetch of a known URL can silently return something else.
- **`maxTokenBudget` truncates search results only; fetch always returns the full page.** The default is not published.
- **Rate limits exist and are not published**, along with no error code, no window and no retry guidance.
- **General availability was declared 2025-11-07**, five months after first release, on the stated basis that usage "grew without issues".
- **Configuration differs by host** — VS Code `.vscode/mcp.json` or user profile, Visual Studio built in, Foundry as a custom MCP tool with **Authentication: Unauthenticated**, Cline needing `"type": "streamableHttp"` — and there is also a plugin and a CLI.
- **Declining trust does not fail loudly.** In VS Code "chat requests will continue without using the tools provided by the server."
- **Trust is re-requested when a server's tools change**, so a dynamic tool list makes trust a recurring decision.
- **The vendor documents that agents fail to call the tool** and recommends instructions as the remedy, without measuring either the problem or the fix.
- **`applyTo` is a workspace-root-relative glob; without it an instructions file is not applied automatically.**
- **Multiple instruction files are combined with no guaranteed order**, and matching may be semantic as well as glob-based.
- **Receipt is checkable three ways:** the References section of a chat response, the chat customization Diagnostics view, and the Chat Debug view.
- **`microsoft_docs_fetch` is the citation instrument**; `microsoft_docs_search` is the discovery instrument. Record the page, not the answer.

## Method and evidence base
First-party product documentation, supported by a first-party engineering blog and a first-party repository README. **The authority is definitional throughout and evidential nowhere.** These pages are an accurate account of what the service is, what it exposes, what it costs and how it is wired up. They contain no evaluation of it.

The gap is not incidental, because the surrounding material makes claims that would need evaluation to support. The FAQ argues the mechanism — models "answer questions by predicting text based on patterns it learned during training or fill gaps by guessing", and with the server they "can link the user question to a potential answer in Microsoft Learn content... and provided a grounded answer" — which is a plausible and probably correct account of *how* grounding is meant to help, and is not a demonstration *that* it does. The repository goes considerably further and asserts outcomes: "Eliminate Hallucinations", "Get code that actually compiles", "100% Trusted & Safe". **No measurement of any of these is published.** The one place a measurement apparatus is described in detail — the golden dataset and the before-and-after indexing tests in the 2024 engineering blog — publishes no numbers at all.

The GA announcement is worth reading closely as an evidence claim, because it is the only one the source makes. Its stated basis is that the server "added an endpoint for AI agents to search through documentation, fetch a complete article, and search through code samples over the past five months, and saw usage grow without issues." That is an availability-and-adoption argument. It says nothing about whether the answers were right.

**The correct posture is to trust these pages completely on what the thing is, and to treat the question of whether grounding improves answers as open and locally testable.** It is locally testable, cheaply, and that is the redeeming feature of this source pedagogically.

## Vocabulary the sources introduce
- **Model Context Protocol (MCP)** — per the FAQ, "an open-source standard for connecting AI agents to data sources, tools and workflows", stated there to be governed under the Agentic AI Foundation.
- **Remote MCP server** — a server reached over the network rather than launched locally; no install, no process, no local execution risk.
- **Streamable HTTP** — the transport this server uses, and the value the host's `type` field usually takes.
- **`tools/list`** — the discovery call a client makes on connection, and the recovery action after a 400 or 404.
- **`listChanged`** — the server notification telling a client its tool cache is stale.
- **Knowledge service** — the shared RAG backend over Learn content that this server exposes and that Ask Learn and Copilot for Azure also consume.
- **`maxTokenBudget`** — a query parameter capping tokens in search responses by truncation; it does not affect fetch.
- **Grounding** — supplying retrieved source text so an answer is drawn from a corpus rather than from parameters.
- **Golden dataset** — the curated question-and-answer benchmark the knowledge-service team built to test indexing changes.
- **Trust prompt** — the host-side gate that must be cleared before a server starts, and which is re-raised when a server's capabilities change.
- **`applyTo`** — the workspace-root-relative glob determining whether an instructions file is applied automatically; absent, it is not.
- **References section** — the part of a chat response naming which instruction files were actually used; the receipt.
- **Agent skill** — a portable instruction package shipped alongside the server to make a model more likely to call its tools.

## What to remember
- The endpoint is durable, the configuration syntax is not, and the tool list is explicitly allowed to change under you. Memorise the URL and re-verify everything else.
- A dynamic tool contract is a different bargain from a versioned API. It promises change and requires rediscovery; it does not promise stability and break loudly.
- **Definitional authority is not evidential authority.** These pages tell you exactly what the server is and give you no reason to believe it makes answers better.
- Grounding makes an answer accurate within a corpus and silent outside it. The corpus here is defined negatively and its boundary is not published.
- **Refresh cadence is not indexing lag.** "Daily full refresh" bounds nothing about how long a correction takes to become retrievable.
- Rate limits exist and are unpublished. You cannot size an agentic loop against this endpoint from the documentation.
- A fetch of a known URL may return a redirect target chosen for you. Cite the page and the date you read it, never the URL alone.
- **A connected tool is not an invoked tool**, and the vendor says so in its own getting-started material. The recommended fix is an instructions file whose effect is unmeasured.
- Declining trust does not produce an error. It produces a confident, ungrounded answer with nothing in the transcript to mark it.
- An instructions file without `applyTo` is inert. Instruction files combine in no guaranteed order.
- Receipt is verifiable — References section, Diagnostics view, Chat Debug view. Verifying is cheap and almost nobody does it.
- Record the query you ran, the tool you used and the page you read. **The answer is not the artefact; the citation is.**

## Why it matters for the course
This is the platform anchor of [S001](/wiki/seminars/S001.md), [S012](/wiki/seminars/S012.md) and [S020](/wiki/seminars/S020.md), and until now those sessions rested on no note at all — a state they declared honestly rather than papering over, which is the behaviour the programme asks for and is also not a state to leave standing. This note closes that gap and, in closing it, changes one thing: the cleared-checkbox claim those sessions use as the evidence for *a connected tool is not an invoked tool* is not what the documentation says, while the claim itself turns out to be better supported than the sessions currently show. That is a net improvement in warrant and a required correction to a cited mechanism.

Pedagogically the source earns its place for three reasons that have nothing to do with Microsoft. First, it is the cheapest possible instrument for the habit the whole programme is built around: checking a platform premise against first-party documentation and recording the date. Free, unauthenticated, no tenant, no model deployment, no licence — every learner can hold one, which is why it belongs at the very start rather than later. Second, it is a compact worked example of an integration contract that promises instability, which most students will never have met and which is becoming the norm rather than the exception in agent tooling. Third, and most valuable, **it is a live, honest, first-party admission that a tool being available is not a tool being used** — a distinction that generalises to every system where capability and invocation are separated, and one that students who have only built deterministic software systematically fail to anticipate.

It is also, usefully, a RAG system a student can interrogate without building one. The failure taxonomy in [barnett-rag-failure-taxonomy.md](/research/02-technical-foundations/barnett-rag-failure-taxonomy.md) can be walked against this server directly — missing content, missed top-ranked documents, wrong extraction — using a corpus whose ground truth is a public web page. That is a rare teaching asset. The unpublished golden dataset connects to [husain-your-ai-product-needs-evals.md](/research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md) and [shankar-evalgen.md](/research/03-measurement-evaluation/shankar-evalgen.md) on validating the validator; the composition point — that a documentation server is one component an agent consumes among others — links to [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md); and the instructions-as-artefact machinery links directly to [hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md), which treats agent configuration as a versioned, reviewable engineering artefact and whose untrusted-content boundary — fetched pages are data, not authority — applies word for word to whatever this server returns. Governance of the perishable layer sits with [11-Microsoft-AI-Platform-Map.md](/archive/bsc-programme/program/11-Microsoft-AI-Platform-Map.md) and [09-Durable-and-Perishable-Register.md](/archive/bsc-programme/program/09-Durable-and-Perishable-Register.md).

## How to teach it
- **Lecture:** contrast a versioned REST contract with a dynamic tool contract. Ask which failure mode each one has, and which one a client can survive by caching.
- **Lecture:** separate definitional from evidential authority using this exact source. The pages say what it is with total authority and prove nothing about whether it helps. Ask students to name what evidence would settle it.
- **Lab, the core exercise:** attach the server, then ask a question you know the corpus can answer — and check whether the model called the tool at all. Then add an instructions file, and check again. **Report the invocation rate before and after, on your own trials.** The vendor recommends this fix and publishes no measure of it; the students can produce one in an hour, for their own model and host, which is the only place it would be valid anyway.
- **Lab:** decline the trust prompt deliberately and ask a grounded question. The answer arrives, is plausible, and is ungrounded. Nothing in the transcript says so. This is the most memorable ninety seconds available in the whole platform strand.
- **Lab:** write an instructions file with no `applyTo`, confirm from the References section that it was not applied, then add the glob and confirm that it was. Receipt before behaviour.
- **Lab:** run `microsoft_docs_search` on a question, then `microsoft_docs_fetch` the page it points at, and compare. Ask which of the two is the citation and why the other is not.
- **Lab:** find a documentation page changed recently and test whether the change is retrievable. Whatever the result, the students now know something the documentation does not state.
- **Assessment:** require every platform claim to carry the tool used, the query run, the page read, the read depth and the date. A claim without those is not a claim.
- **Assessment:** ask what this server cannot tell you. A student who answers only "non-Microsoft things" has missed the corpus boundary, the redirect behaviour, the unbounded indexing lag and the absence of filtering.
- **Framing:** among the most perishable material in the research set — seven documented changes across the nine months to 2026-03-23, two of them adding tools that did not previously exist. Assess the reasoning and the discipline. Never assess the configuration syntax.

## Limits and cautions
- **Extremely perishable.** Seven dated changes between 2025-06-12 and 2026-03-23 — including two tool additions after first release — and a developer reference that reserves the right to change the tool list and its formats without notice. Re-verify before every offering; the tool names are the least safe thing in this note.
