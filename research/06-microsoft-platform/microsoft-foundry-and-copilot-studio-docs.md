## What this source is
Not one document but a family of comparison pages, each written to answer a version of the same question: given that several ways exist to build an agent on this platform, which should you choose? Read individually they are product-selection guides. Read together they are something more useful — a set of decision axes along which any agent-building decision can be analysed, on this platform or another. That is the durable content, and it is why this material belongs in a course at all. The specific products will be renamed. The axes will not.

## The argument in full
The Cloud Adoption Framework sets the top-level frame with a three-way split by service model, which is the cleanest organising idea in the whole family. **Microsoft Foundry** is platform-as-a-service, supporting "no/low-code agent development (declarative agents) or pro-code agent development (hosted agents)", letting you "pick your own models" and consolidating "runtime, orchestration, and integration into a managed environment" without managing virtual machines or Kubernetes. **Copilot Studio** is software-as-a-service for low-code development, enabling business teams to deploy agents. **GPUs and containers** are infrastructure-as-a-service, offering maximum flexibility with code-first frameworks. The selection criteria are stated as "your organization's technical capabilities, timeline, and control requirements" — capability, speed, control. That triple is the actual decision, and it applies to build-versus-buy questions well outside this domain.

Foundry's own internal split is the next layer, and it is a hosting distinction rather than a capability one. **Prompt agents** use "declarative config in portal or code", are "managed by Foundry with no agent compute", and suit "agents that don't include custom code or require custom hosting". **Hosted agents** run "your code (containerized)", are "managed by Foundry (container compute)", and suit "agents with custom code running in a managed container". The line between them is whether you are running code, and therefore whether you are paying for and operating compute. Foundry's setup options add a second, orthogonal decision with real consequences: the **basic setup** is "for rapid prototyping and individual development when speed and ease of access are priorities" and "lacks network isolation"; the **standard setup** provides "fine-grained control over data, security, and networking", with public networking for non-confidential workloads needing enterprise data controls, and private networking for confidential workloads with strict compliance requirements. Stating plainly that the fast option has no network isolation is good documentation, and the correct lesson is not "always choose standard" — it is that prototyping topology and production topology are different things and the transition between them is a deliberate act.

The declarative-versus-custom-engine distinction is where the reasoning gets genuinely instructive, because it is a real architectural fork rather than a packaging one. **Declarative agents** "use Microsoft 365 Copilot for focused scenarios", are "designed to be used by individuals", are "limited to Copilot's orchestrator and models", do **not** support proactive interactions and "rely on user-initiated interactions", are "integrated into Microsoft 365 apps", and are "hosted in Microsoft 365". **Custom engine agents** handle "complex workflows or advanced integrations", "support both individual use and group collaboration", are "fully customizable, including choice of AI models and orchestration", "enable agents to trigger actions automatically, even without direct user input", are "available for Microsoft 365 and external apps", and are hosted either in Microsoft 365 via Copilot Studio or externally. Five axes are doing work here — orchestration control, model choice, initiation model, collaboration scope, and hosting location — and the initiation model is the one most often overlooked. An agent that cannot act without being asked is a fundamentally different system from one that can, in its architecture, its failure modes and its governance requirements.

The published triggers for choosing a custom engine agent function as a design checklist: custom orchestration for "complex workflows, specific business logic, precise decision-making rules, or multiple system integrations", with a loan-approval example given; wanting your own or domain-specific or multimodal models; group productivity where "multiple users can collaborate with or benefit from the same agent in a Teams channel or meeting"; integrating an existing conversational assistant; availability outside Microsoft 365; and proactive messaging that lets developers "define workflows and trigger agent behavior without the need for user interaction". Conversely, declarative agents suit faster implementation and workflows already inside Microsoft 365 apps, with an IT helpdesk agent responding to Teams mentions given as the example.

The tooling comparison for custom engine agents is the most operationally honest table in the family, because it compares four options — Copilot Studio, Teams AI, Agents SDK and Foundry — across dimensions that determine what a team can actually do. **Orchestrator** is the sharpest column: Copilot Studio uses its own, Teams AI uses the Action Planner, and both Agents SDK and Foundry are "bring your own (for example, Semantic Kernel, LangChain)". **AI models** follows the same pattern: Copilot Studio's own, "any model of your choice" for the two pro-code paths, and "Foundry OpenAI or custom models". **Supported programming languages** differ meaningfully — C#, TypeScript, JavaScript and Python for Teams AI; C#, JavaScript and Python for the Agents SDK; Python and C# for Foundry; not applicable for Copilot Studio. **Channels** and **publishing** differ too, and the documentation states a specific constraint worth remembering: "Only agents built with the Teams SDK, Microsoft 365 Agents SDK, or Foundry can be published to the Microsoft Commercial Store with the Agents Toolkit." Distribution is constrained by build choice, and that is a decision made at the start that binds at the end.

The Copilot Studio pros-and-cons table is unusually candid for vendor documentation and should be read closely for that reason. Advantages: a low-code drag-and-drop interface "without coding"; "hundreds of prebuilt connectors" for plug-and-play API integration; suitability for "smaller, targeted agents that don't require large-scale enterprise governance"; and prebuilt governance and deployment reducing IT complexity. Disadvantages, stated equally plainly: "limited ability to fine-tune API calls, actions, and response formatting compared with a pro-code environment"; source control and CI/CD supported through Power Platform pipelines, native Git integration and the Copilot ALM Starter but "less integrated than the project-based workflow in Agents Toolkit"; Adaptive Cards "limited to schema 1.6 and earlier"; and slower feature availability. The page also positions Copilot Studio as "designed for small-scale deployments, such as department-level solutions." That is a scale claim, and a course should treat it as the most important line in the table — a tool that is excellent at department scale is being used outside its design envelope when it is used at enterprise scale, and the symptoms of that mismatch show up as governance and lifecycle problems rather than as functional failures.

Two further framings are worth carrying. The serverless comparison adds authoring-model and hosting-cost axes across five options — the serverless agents runtime with `.agent.md` files on scale-to-zero Functions, Foundry prompt agents with no agent compute, Foundry hosted agents on container compute, Copilot Studio on Copilot credits, and Microsoft Scout running locally on a user device — and then makes the point that matters most: "These options aren't mutually exclusive. For example, a serverless agents runtime app can expose tools through MCP that Foundry agents or Copilot Studio agents consume." The choice is not a single platform for a system; it is a platform per component, composed through protocols. Second, the integration guidance shows the same composability at the deployment layer, with Foundry agents reaching Microsoft 365 either by direct publish, which "automatically provisions Azure Bot Service and Entra ID", or through an Agents Toolkit proxy app for "advanced customization, debugging, and multi-environment deployment". Rapid path versus controlled path, again — the same trade that runs through every one of these comparisons.

## Key concepts and practices
- **Three build paths by service model:** Foundry (PaaS), Copilot Studio (SaaS), GPUs and containers (IaaS). Selection criteria: **technical capabilities, timeline, control requirements.**
- **Foundry agent types:** **prompt agents** (declarative, no agent compute) and **hosted agents** (your containerized code on managed container compute).
- **Foundry setup options:** **basic** for rapid prototyping, which **lacks network isolation**; **standard** with public networking for enterprise controls or private networking for confidential workloads.
- **Declarative agents:** individual use, Copilot's orchestrator and models only, **no proactive interaction**, Microsoft 365 channels, hosted in Microsoft 365.
- **Custom engine agents:** complex workflows, individual or group use, **full orchestration and model choice**, **proactive triggering**, internal and external channels, flexible hosting.
- **Six published triggers for custom engine agents:** custom orchestration; own or domain-specific or multimodal models; group productivity; integrating an existing assistant; availability outside Microsoft 365; proactive messaging.
- **Orchestrator ownership differs by tool:** Copilot Studio's own; Teams AI Action Planner; bring-your-own for Agents SDK and Foundry.
- **Language support differs:** Teams AI (C#, TypeScript, JavaScript, Python); Agents SDK (C#, JavaScript, Python); Foundry (Python, C#); Copilot Studio (not applicable).
- **Only Teams SDK, Microsoft 365 Agents SDK and Foundry agents can be published to the Microsoft Commercial Store** via the Agents Toolkit.
- **Copilot Studio is "designed for small-scale deployments, such as department-level solutions."**
- **Copilot Studio's stated limits:** less fine-grained control over API calls, actions and response formatting; less integrated pro-dev tooling than Agents Toolkit; **Adaptive Cards schema 1.6 and earlier**; slower feature availability.
- **Tools connect via the Tool catalog, MCP and OpenAPI specifications**, with Logic Apps and Functions for serverless automation.
- **The options are explicitly not mutually exclusive** — components on different platforms compose through MCP.
- **Two Foundry-to-Microsoft-365 integration paths:** direct publish, which auto-provisions Azure Bot Service and Entra ID; or an Agents Toolkit proxy app for custom logic, SSO and multi-environment deployment.

## Method and evidence base
First-party product documentation with an explicit selection-guidance purpose. Its authority is definitional, and it is notably candid about limitations — the Copilot Studio cons list and the basic-setup network-isolation warning are both stronger admissions than vendor documentation usually contains. It offers no adoption data, no failure-rate data, no cost comparisons and no evidence that the recommended mappings produce better outcomes. The recommendations are reasoned assertions, and they should be taught as a well-constructed decision framework rather than as validated findings.

## Vocabulary the sources introduce
- **Declarative agent** — an agent defined by configuration, using the host's orchestrator and models.
- **Custom engine agent** — an agent with its own orchestration and model choices.
- **Prompt agent** — a Foundry agent with no agent compute, defined declaratively.
- **Hosted agent** — a Foundry agent running your containerized code on managed compute.
- **Orchestrator** — the component deciding what the agent does next; owning it is the main pro-code/low-code dividing line.
- **Proactive messaging** — agent-initiated action without user input.
- **Basic versus standard setup** — the prototyping topology without network isolation versus the controlled one with it.
- **Tool catalog / MCP / OpenAPI** — the three routes by which agents reach external systems.
- **Copilot credits** — the consumption unit for Copilot Studio hosting.
- **Agents Toolkit proxy app** — the controlled integration path from Foundry into Microsoft 365.

## What to remember
- The real decision axes are capability, timeline and control. Everything else is product packaging.
- Owning the orchestrator is the fundamental fork. It determines model choice, extensibility and lifecycle tooling together.
- An agent that can act without being asked is architecturally different from one that cannot, in failure modes and governance alike.
- Prototyping topology is not production topology. The basic setup lacking network isolation is a feature of prototyping, not a defect.
- Distribution is constrained by build choice, and that constraint binds at the end of the project from a decision made at the start.
- A tool designed for department scale used at enterprise scale fails through governance and lifecycle, not through function.
- Low-code buys speed and pays in control, tooling maturity, schema currency and feature latency. Each cost is separately real.
- The platforms compose. MCP means the choice is per component, not per system.
- Every comparison in this family reduces to the same trade: the fast path versus the controlled path.

## Why it matters for the course
This material is best taught not as product knowledge but as a worked example of platform selection under constraint, which is a skill students will exercise for their whole careers on tools that do not exist yet. The comparison tables are unusually good raw material for that because they are explicit about their axes, and extracting the axes from the products is exactly the durable-versus-perishable exercise the course architecture is built around. Two ideas here have particular weight. The initiation model — reactive versus proactive — is a genuine architectural fork that a student who has only built chatbots will not have considered. And the observation that a department-scale tool fails at enterprise scale through governance rather than function is the kind of judgement that separates an engineer who can pick a tool from one who can predict how it will disappoint. It links to [research/05-fde-craft/collected-materials.md](research/05-fde-craft/collected-materials.md) for the build-versus-configure judgement in customer settings, and to [purview-dspm-for-ai-and-defender-ai-spm-docs.md](research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md) for what happens when low-code agent creation outruns governance.

## How to teach it
- **Lecture:** extract the decision axes from the tables and discard the product names. Then reintroduce the products as instances.
- **Lecture:** teach reactive versus proactive initiation as an architectural distinction, and ask what changes in the failure model when an agent can act unprompted.
- **Lab:** give students one requirement and have them justify a build path against the axes, then change one constraint — proactive triggering, external distribution, model choice — and have them redo it.
- **Lab:** build the same simple agent twice, once low-code and once pro-code, and compare time-to-first-working-version against control and testability.
- **Lab:** compose two platforms through MCP so the non-exclusivity point is experienced rather than asserted.
- **Assessment:** require a written platform-selection rationale naming the axes, the constraints, the rejected alternatives and the conditions under which the decision should be revisited. Defend orally.
- **Assessment:** ask what would have to be true for the team to have chosen differently. A student who cannot answer did not make a decision.
- **Framing:** the most perishable material in the research set. Assess the axes and the reasoning only.

## Limits and cautions
- **Read through search excerpts, not full page fetches.** Page structure is reconstructed and should be re-verified.
- Extremely fast-moving. Product names are actively in flux — the Agent Framework SDK is documented as "formerly Semantic Kernel" — and any specific claim may already be stale.
- Vendor selection guidance is commercially framed. It compares Microsoft options with each other and not against non-Microsoft alternatives.
- No adoption, cost, failure-rate or outcome data supports the recommendations.
- Several comparison tables were truncated in the excerpts read; feature lists here are not exhaustive.
- Capability boundaries between products shift, so a limitation recorded today may be closed tomorrow — and a course must not teach a limitation as permanent.
- Teaching this material risks producing students who can navigate a product catalogue rather than reason about architecture, unless the axes are extracted explicitly and the products deliberately discarded.
