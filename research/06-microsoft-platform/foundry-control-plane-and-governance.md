## What this source is
A governance and operations documentation set, and — separately — a shipped product that carries the same name. Both meanings are live and they must be held apart or the reader will conflate them.

The lower-case sense is architectural: Azure divides every resource's operations into a **control plane** (manage the resource) and a **data plane** (use the resource), and Foundry inherits that division exactly. The upper-case sense is a product: **Microsoft Foundry Control Plane** is a set of panes in the Foundry portal, reached by a button labelled **Operate**, that aggregates agents, models, quota, cost and compliance across every project in a subscription.

**This note complements rather than repeats [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md).** That note is about *choosing a build path* — Foundry versus Copilot Studio, prompt agent versus hosted agent, declarative versus custom engine. It answers "what should I build this with?" This note answers "who is allowed to do that, what does it cost, what happens when the model underneath it retires, and how would anyone know it broke?" The overlaps are enumerated explicitly under **Where this overlaps the existing Foundry note**.

## The argument in full

### The plane split is the load-bearing idea, and it is not a Foundry invention
Foundry adopts Azure's standing division wholesale, and the documentation lays it out in a table worth memorising because it predicts almost every permission failure a team will hit. The **control plane** covers "setting up and configuring resource, projects, networking, encryption, and connections" — creating and deleting resources, assigning roles, rotating keys, setting up Private Link — reached through the Azure portal, CLI, ARM, Bicep and Terraform, and authorised by Azure RBAC **actions**. The **data plane** covers "running and using model inference, agent interactions, evaluation jobs, and content safety calls" — chat completions, embeddings, fine-tune jobs, agent messages — reached through SDKs, REST APIs and the portal playground, and authorised by RBAC **dataActions**.

The enumerated lists sharpen it further. Control-plane actions in Foundry are: resource creation, project creation, account capability-host creation, project capability-host creation, model deployment, and connection creation. Data-plane actions are: building agents, running an evaluation, tracing and monitoring, and fine-tuning.

**The consequence is the single most useful operational fact in this whole set, and Microsoft states it plainly in the rollout guidance: "Management roles such as Owner or Contributor are not sufficient for all development scenarios. For example, a user can manage resources but still need data plane roles to chat with an agent in Foundry."** The permission matrix confirms it — the Azure built-in **Owner** role can create Foundry accounts and projects, manage models, publish agents and assign any role, and **cannot** build in a project and **cannot** interact with an agent endpoint. An administrator with total authority over the resource cannot talk to the thing running inside it. That is not a bug; it is the plane split doing its job, and a team that does not understand it will spend its first day debugging an authorisation failure that is actually a design decision.

### The hierarchy is two levels, and the third thing is not inside it
A **Foundry resource** is `Microsoft.CognitiveServices/accounts` of kind `AIServices`. A **Foundry project** is `Microsoft.CognitiveServices/accounts/projects` — a *subresource*, not a peer. The resource is "the top-level scope that defines the administrative, security, and monitoring boundary"; the project is "a sub-scope... used to organize work and enforce access control for Foundry APIs, tools, and developer workflows." Project assets — files, agents, evaluations — are scoped to the project.

The third category is the one that catches people. **Connected resources — Storage, Key Vault, Azure AI Search, Cosmos DB — "are independent Azure resources with their own governance boundaries. You manage networking, access policies, and compliance settings for these resources separately from the Foundry resource."** Foundry references them through connections; it does not govern them. A team that has hardened Foundry and not hardened the storage account holding its conversation history has hardened nothing that matters. The networking documentation drives the same nail: "Private endpoints to Azure AI Search, Azure Storage, and Azure CosmosDB are NOT auto-created when you deploy your Foundry resource."

Two further asymmetries are recorded honestly and are easy to miss. **Most new APIs are project-scoped, but some are not** — the Translator API is given as an example of a capability available only at resource level. And **fine-tune training cannot be organised by project at all**: the rollout planning table marks it "No (default project only)" for project organisation and "No" for project-level RBAC isolation, with the blunt implication stated, "If each team needs independent fine-tuning, use separate Foundry resources." The project boundary is not uniform. It is a boundary for the new agent-centric surface and a leaky one for the inherited surface underneath.

### Foundry Control Plane, the product, is an aggregation layer with an honest justification
The overview page states what it is for without inflating it: "Without Foundry Control Plane, you manage agents, models, and compliance through individual Azure portal blades and separate per-project views. Foundry Control Plane adds cross-project visibility, unified compliance enforcement, and integrated security signals in a single interface." That is a claim about *where you look*, not about new capability, and it is the right claim — everything it surfaces is enforced by Azure Policy, Azure RBAC, Azure Monitor and Microsoft Entra underneath.

Five panes hang off **Operate**. **Overview** aggregates active agents, cost trends, run completion rate and prevented behaviours. **Assets** is a searchable inventory of every agent, model and tool across projects in a subscription. **Compliance** defines and monitors guardrail policies, with tabs for Policies, Assets, Guardrails and Security posture. **Quota** shows deployments against their allocations, with a **Show all** toggle to reveal undeployed models and regions. **Admin** lists projects across the subscription or tenant — including "active, inactive, and archived workspaces" — with owners, region, connected services and compliance posture, and can add or remove users from a project.

**Two constraints on it deserve to be stated whenever it is taught.** First, prerequisites include "an **AI gateway configured** for advanced governance features" — the governance story assumes the API Management AI gateway described in [apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md), and without it some of the surface is inert. Second, and more consequentially: **"These features are currently available through the Foundry portal only."** There is no API, no CLI and no Bicep for the Operate panes. A control plane that cannot be driven by code cannot be put in a pipeline, cannot be diffed, cannot be reviewed and cannot be handed over as configuration. Everything the panes do is *ultimately* backed by Azure Policy and RBAC, which are automatable — but the composed experience is click-only, and a team that builds a handover around it is building a handover around screenshots.

### Identity is now three-layered, and the middle layer is new
Foundry supports Entra ID and API keys, and is unambiguous about which to use: Entra ID for production, keys for "rapid prototyping" and "isolated test environments where single-secret rotation is acceptable". Keys are described as unable to "express user identity", "difficult to scope granularly", "harder to audit", and "generally not accepted by enterprise production workloads and not recommended by Microsoft."

That is not merely advisory, because the feature matrix makes several capabilities *impossible* on keys. **The Agents service, Evaluations, least-privilege roles, managed identity, per-request user attribution and the Toolbox are all marked "No" for API key.** The general-availability page restates it: "Foundry supports API key authentication for most areas. Exceptions: evaluations, dataset tab, Content Understanding, agents, and workflows require Microsoft Entra ID authentication." Anyone building agents is on Entra whether or not they chose to be. Token auth additionally requires a **custom subdomain** on the resource, which is the single most common cause of the "custom subdomain required" failure.

Five Foundry built-in roles exist, at scopes of subscription, resource group, Foundry resource, Foundry project, or **an individual agent**. **Foundry Agent Consumer** can only call agent endpoints. **Foundry User** gets reader access plus data actions — the developer role. **Foundry Project Manager** adds project management, agent publishing, and the conditional right to assign Foundry User. **Foundry Account Owner** can create accounts and projects and manage models but has **no data actions at all**. **Foundry Owner** is the only single role holding both planes, and is described as a "highly privileged self-serve role designed for digital natives" — which is a polite way of saying it is the role you grant when you have given up on separation of duties.

Three details from this section have direct operational consequences. **Fine-tuning requires both planes**, so it needs Foundry Owner, or Foundry User plus Foundry Account Owner. **Agent-scope role assignments are "currently evaluated only for agent endpoint access"** and grant no management permission — so the finest-grained scope is real but narrow. And **the Foundry User role is auto-assigned when you deploy from the portal UI and is not auto-assigned when you deploy from SDK or CLI** — meaning the infrastructure-as-code path silently produces a resource its creator cannot use.

Above all of this sits **Microsoft Entra Agent ID**, which gives an agent its own identity. An **agent identity** is "a special service principal in Microsoft Entra ID", created by an **agent identity blueprint** that holds the credentials and acquires tokens on its behalf. Agents authenticate either attended, through the OAuth 2.0 on-behalf-of flow carrying the user's delegated permissions, or unattended through client credentials under their own authority. The documentation is explicit that the blueprint's managed identity is not the thing you grant access to: **"The agent identity — not the managed identity — is the principal that requires RBAC role assignments on the target resource."** It is equally explicit about the failure mode next door: the token audience must match the downstream service's resource identifier — `https://storage.azure.com`, `https://graph.microsoft.com` — and **"An incorrect audience value causes authentication failures even when RBAC roles are correctly assigned."** Two mechanisms, one symptom, and the RBAC-shaped explanation is the wrong one about half the time.

The governance model around Entra Agent ID has one hard number and one hard limit. A blueprint principal is "limited to a maximum of 250 agent identity creations", and the `AgentIdentity.CreateAsManager` permission is granted automatically and **"can't be revoked"** — "To prevent a principal from creating agent identities, you must disable it or remove the principal from the tenant." That is a governance control with exactly one setting: on, or gone.

### Quota is the constraint that cannot be engineered around
Quota is assigned "per subscription, per region, and per model in units of tokens per minute (TPM)". Two REST APIs answer the two different questions — the **Usages API** for consumption against limits, and the **Model Capacities API** for available deployment capacity by model and region. The portal's Quota pane splits into a TPM tab and a provisioned-throughput-unit tab. Viewing needs **Cognitive Services Usages Reader**; editing allocations needs **Cognitive Services Contributor** with it; requesting increases needs **Owner** or **Contributor**. Changes take up to fifteen minutes to propagate.

Increases go through a form, and the stated policy is the thing to read closely: **"Quota increase requests are processed in the order they're received, and priority goes to customers who actively use their existing quota allocation. Requests that don't meet this condition might be denied."** There is a genuine logic there — capacity is finite per region and rationing it towards demonstrated consumption is defensible. But read it as a delivery dependency and it is a request with **no published response time, no published approval rate, and no published appeal route**, whose stated prioritisation rule actively disadvantages a new engagement that has not yet consumed anything. A **shared quota pool** exists for temporary testing, which softens the pilot case, and its duration is given as "The specific time duration depends on the use case" — which is to say, unquantified.

Three further limits bind. **Models from partners and community do not support quota increases at all**, Anthropic excepted. **Agent Service file, message and tool limits "are fixed service limits and can't be increased"** — design within them or not at all. And the portal and the capacity APIs "return quota/capacity information for models that are retired and no longer available", so the capacity report will happily describe a model you cannot deploy.

### Deployment lifecycle is the most predictable thing here, and the most dangerous
Every model sits in exactly one of five stages. **Preview** — weights, runtime and API schema might change. **Generally Available** — fixed. **Legacy** — optional, may be skipped. **Deprecated** — existing customers only, and *existing* is determined at subscription level, so "A new subscription under the same tenant doesn't inherit access." **Retired** — all inference returns `410 Gone`.

The clock is set at launch, not announced later: **"GA models have their retirement date set programmatically at launch to 18 months out—there's no separate 'announcement.'"** Anthropic, DeepSeek, Fireworks and Mistral GA models get twelve months instead of eighteen. Deprecation lands at twelve months from launch. The replacement appears in global standard about ninety days before retirement and in provisioned regions about thirty days before, and the documentation explains why it is not sooner in a passage that is unusually candid about the industry it operates in: declaring a replacement early "risks directing customers to a model that is no longer the best available option by the time they need to migrate."

Notice is **at least sixty days for GA models and at least thirty for preview models**, by email to subscription owners with active deployments and by Azure Service Health advisory. Two operational traps sit inside that. There is **no "Microsoft Foundry" service in Service Health** — you must configure alerts against `Azure OpenAI Service`. And **notification goes to subscription owners, not to the team that built the thing**, which for a forward-deployed engagement means the notice lands with someone who has never heard of the deployment.

Each deployment carries a `versionUpgradeOption` with three values, and choosing between them is a genuine engineering decision rather than a preference. `OnceNewDefaultVersionAvailable` accepts silent behaviour change in exchange for never breaking. `OnceCurrentVersionExpired` defers the change to the last possible moment. `NoAutoUpgrade` guarantees stability and then **stops working entirely at retirement**. Auto-upgrades roll region by region and "can occur even if the new model version isn't yet separately available in that region... the upgrade process will make it available."

**Provisioned deployments are not auto-upgraded, at all.** Anyone who has bought dedicated capacity — the economics of which are covered in [provisioned-throughput-for-foundry-models.md](/research/06-microsoft-platform/provisioned-throughput-for-foundry-models.md) — has bought a manual migration obligation with it, either in-place over a stated twenty-to-thirty-minute window or side by side. And retirement dates are not negotiable: asked directly whether an exception is possible, the FAQ answers **"No. Retirement dates aren't extendable."** Microsoft additionally "reserves the right to invoke an **emergency retirement** with shortened notice" for compliance or security issues, without saying how short.

One last trap is a naming one, and it is the kind that produces a wrong dashboard rather than an error. **The Models API uses different words than the documentation and the portal.** A model the docs call "Deprecated" — still serving, blocked to new customers — appears as `lifecycleStatus: "Deprecating"`. The API value `"Deprecated"` means **retired**. Code that tests for `"Deprecated"` and reports "still fine" has inverted the answer.

### Networking has three directions and one honest table
Isolation is planned in three areas: inbound to the Foundry resource, outbound from it, and outbound from the agent client to its dependencies. Inbound is governed by the public-network-access flag, set to Disabled with a private endpoint or to Selected networks with IP and VNet rules. Outbound agent traffic uses **container injection** into a subnet you delegate to `Microsoft.App/environments`, sized `/27` or larger, in either a customer-managed VNet or a Foundry-managed one.

The comparison table across the three setups is the crisp version, and it is materially more informative than the two-line summary carried in the existing Foundry note. **Basic setup** gets you started without managing resources, and gets nothing else in the table. **Standard setup with public networking** adds conversation history, files and vector stores in your own resources, and customer-managed keys. **Standard setup with private networking** adds bring-your-own-VNet isolation on top. Standard setups "require you to Bring Your Own (BYO) resources so that all agent data stays in your Azure tenant" — Storage, AI Search and Cosmos DB. Crucially the table's note separates the two directions: private network isolation refers to *outbound* agent communication and is standard-only, whereas *inbound* protection "can be applied to all of setups below, by adding a private endpoint and disabling the inbound public access". Basic setup can be given a private front door. It cannot be given a private back door.

Practical residue, all of it stated and all of it the kind of thing that eats a day: private endpoints to the connected data resources are not created for you; `172.17.0.0/16` is reserved by Docker bridge networking and must not be used; a private endpoint stays **Pending** until someone with Contributor or Owner approves it; some network-isolated configurations "aren't configurable through the portal UI" and require SDK or CLI; and there is **no automatic cross-region failover** — multi-region availability means separate Foundry resources with routing handled at the application layer. The vendor's own agent skill adds one more: **Foundry MCP tools cannot reach a VNet-isolated project even from inside the VNet**, so the tooling that provisions isolation cannot then operate what it provisioned.

### Observability is off until somebody turns it on
This is the fact most likely to be assumed wrongly, and the documentation states it three times. **"Tracing is off by default." "No trace data is collected or stored unless explicitly enabled by Foundry Account Owner or Foundry Owner."** Enabling means connecting an Application Insights resource to the project; disabling means disconnecting it, after which "Previously collected data remains subject to retention policies of the Application Insights."

What tracing captures, when on, is broad: "User inputs and prompts", "Agent and model inputs and outputs", "Tool calls and intermediate steps", and execution metadata including timestamps, latency, token usage and errors. Foundry emits OpenTelemetry with the GenAI semantic conventions and can export to OTLP backends as well as Azure Monitor; server-side traces are automatic for agents run in the portal, and client-side tracing of your own application code is **preview**.

The access surface is the part a delivery team must reason about rather than accept. **Anyone with Log Analytics Reader on the connected workspace can read prompts and completions** — the page says outright that trace data "might contain personal data and customer content", and that where the underlying tables are marked Protected, readers additionally need Privileged Monitoring Data Reader. The customer responsibilities are enumerated and are not small: informing end users what is collected, why, and who can see it; ensuring privacy and regulatory compliance; and configuring access and retention. **No default retention is stated** — it is whatever the Log Analytics workspace does.

Coverage is uneven and the documentation says so. **Azure Logic Apps agent loops appear in the inventory but "Observability features, including traces and metrics, aren't supported"** for them. Custom agents "require extra configuration to show details, including tools and LLM spans". Traces take two to five minutes to propagate. A dashboard built on this is a dashboard with known blind spots, and the professional act is to write down which ones.

### Continuous evaluation is a sampling mechanism, and its output is unvalidated
The Monitor settings panel exposes four features: **continuous evaluation**, which "Runs evaluations on sampled agent responses" with a configurable sample rate; **scheduled evaluations** (preview); **red team scans** (preview); and **alerts** (preview). Continuous evaluation is capped by `max_hourly_runs`, defaulting to **one hundred runs per hour**, past which "Evaluation runs are skipped." The risk dimensions offered are substantive — task adherence, intent resolution, tool call success, groundedness, sensitive data leakage, and exposure to jailbreak and cross-domain prompt injection.

The mechanism is coherent and the epistemics are unaddressed. **A sampled evaluation of a sampled trace, scored by an evaluator whose agreement with human judgement is not published, capped at a rate nobody has justified, is a number-generating apparatus.** That is not a criticism of the feature — it is the correct description of it, and it is the reason this material maps onto the measurement strand of the programme rather than the tooling strand. The related evaluator material is covered in [agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md), and the finding that no evaluator agreement rate is published is already on record in this repository.

The dashboard also ships two interpretive thresholds asserted without any basis: "Latency above 10 seconds might indicate model throttling, complex tool calls, or network issues" and "A rate below 95% warrants investigation into failed runs." **These are rules of thumb presented as guidance and must never be repeated as findings.**

### Compliance is Azure Policy with a friendlier front end
Guardrail policies "mandate minimum guardrail controls for your model deployments across a subscription or within a resource group" — content filters, prompt shields, protected materials, abuse detection. They scope to a subscription or resource group, take exceptions at resource-group or individual-deployment level, and are backed by Azure Policy so directly that "Deleting a policy in the Foundry portal also removes the associated policy assignment in Azure Policy." Creating one requires **Owner** or **Resource Policy Contributor**, so "Most users don't have permission to create guardrail policies" — they can only view compliance.

Enforcement is eventually consistent and slow enough to matter: allow **up to thirty minutes** for a policy to appear, after which "Compliance results appear after Azure Policy completes its scan. The duration of the scan varies by scope size and resources." No bound is given. A compliance dashboard that is green may simply not have looked yet.

Separately, two **built-in Azure Policy definitions** govern which models can be deployed at all. "Foundry model deployments should only use approved models" is generally available and enforces an allow-list by model or publisher. "Foundry model deployments should meet eligibility requirements" is preview and enforces attributes instead — `onlyAllowDirectFromAzure` and `denyPreviewModels`, both defaulting to `false`. Both evaluate at deployment time, both support Deny or Audit effects, and the developer experience is deliberately transparent: **"Models are not hidden from the catalog — instead, the Deploy action is disabled with a clear reason."** That is a good design decision and worth naming as one. Telling an engineer *why* they cannot do something converts a mysterious failure into a conversation with an administrator.

The **Guardrails** tab exists for a purpose worth quoting because it names its own worst case: comparing configurations across projects helps "uncover potential risks that might go unnoticed, such as subscriptions that lack content filtering entirely."

### Cost is attributable, estimable, and uncapped
Spend surfaces in three places with three different fidelities. The Operate Overview shows an **Estimated cost** tile per project and date range; the Assets pane shows per-agent monthly estimates; Azure Cost Management holds the truth. The exclusions on the estimates are stated and are large: **"These estimates don't include prompt agent and non-Foundry agent costs"**, and estimates "do not reflect discounts or contracted pricing" and "cover standard deployment costs only, not provisioned throughput". The reconciliation rule is given explicitly — "Use **Estimated cost** for near-real-time monitoring, and use Microsoft Cost Management and invoiced charges for financial reconciliation."

**Project-level attribution exists and is preview.** Every Foundry project is automatically tagged with a `project` tag on its underlying usage, and filtering Cost Analysis by that tag produces per-project chargeback with no manual tagging. It is "currently supported for Models sold by Azure (including Azure OpenAI)" and **"isn't yet supported for models served through Azure Marketplace"** — so a chargeback built on it is silently incomplete wherever a marketplace model is in play. A second navigational trap: Azure OpenAI does not appear as a service in Cost Management filters, because "Azure OpenAI usage appears under the broader **Cognitive Services** service classification"; use **Service tier: Azure OpenAI** instead.

Two cost facts belong in every design review. **Fine-tuned models bill hourly for hosting "even if the model is unused"** — a deployed and forgotten fine-tune is a standing charge with no traffic. And, stated without euphemism: **"While OpenAI has an option for hard limits that prevent you from going over your budget, Azure OpenAI doesn't currently provide this functionality."** Budgets and alerts exist; a stop does not. Anything resembling a spend ceiling must be built — the page suggests action groups triggered by budget notifications, and concedes that "this functionality requires additional custom development." **The cost control is an architecture decision, not a setting**, and the honest place to put it is the gateway, per [apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md).

### Topology is a decision the vendor has already made for you, twice
The rollout guidance offers two topologies and states the trade for each. **One Foundry resource with multiple projects**, typically one project per use case, fits experimentation and shared deployments, and pays with "Shared blast radius for production incidents, quota exhaustion, and misconfiguration." **One Foundry resource per production workload boundary** gives operational containment and independent quota and cost boundaries, and pays with setup overhead and harder self-service. The recommendation is unambiguous: **"For production, treat isolation as the default. Use colocation as a deliberate exception only when workload boundaries, data requirements, and risk acceptance are aligned."**

The landing-zone reference architecture goes further and rules a tempting pattern out: using a Foundry resource as a centralised business-group resource with a project per workload is described as something "we don't recommend... Because of resource organization factors, and cost allocation limitations", with the workload team owning its own Foundry resource as the recommended approach instead. **A published trade study with a stated recommendation is a reason not to run your own.**

### The fleet view is real, and its coverage is partial by design
Foundry Control Plane automatically discovers **Foundry agents (prompt agents, workflows and hosted agents), Azure SRE Agent, Azure Logic Apps agent loops, and manually registered custom agents**. It does not discover everything: **"Classic agents and Azure OpenAI assistants aren't supported."** Discovery is also permission-relative — "different users might see different agents listed on the **Assets** pane, depending on their access level on each resource" — so no two people's inventory is guaranteed to match, and an inventory is not an estate.

Lifecycle control varies by platform in ways a runbook must reflect exactly. Hosted and published agents support **start/stop**, which deallocates compute. SRE Agent and Logic Apps support start/stop, with the Logic Apps caveat that "Stopping a Logic Apps resource stops all the workflows associated with it." Custom agents support only **block/unblock**, because "Foundry doesn't have access to the underlying infrastructure where the agent runs" — blocked agents keep running and stop receiving requests. And unpublished prompt agents and workflows support **nothing**: "To stop an unpublished prompt agent or workflow, you must delete it." One further line belongs in any incident runbook that says "stop the agent": **"This operation *doesn't terminate existing runs*."**

## Key concepts and practices
- **Control plane versus data plane** is inherited from Azure, expressed as RBAC `actions` versus `dataActions`, and predicts most permission failures. **Owner and Contributor grant no data-plane access.**
- **Foundry resource** (`Microsoft.CognitiveServices/accounts`, kind `AIServices`) is the governance boundary; **Foundry project** (`.../projects`) is a subresource and the development boundary.
- **Connected resources — Storage, Key Vault, AI Search, Cosmos DB — have their own governance boundaries and are not governed by Foundry.** Their private endpoints are not auto-created.
- **Some capabilities are resource-scoped only** (Translator is the given example); **fine-tune training cannot be project-isolated at all.**
- **Foundry Control Plane** is reached by **Operate** and has five panes: Overview, Assets, Compliance, Quota, Admin. It requires **an AI gateway configured** for advanced governance, and is **portal-only — no API, CLI or template**.
- **Five built-in roles:** Foundry Agent Consumer, Foundry User, Foundry Project Manager, Foundry Account Owner, Foundry Owner. **Renamed from Azure AI \* during the documentation's own lifetime; role IDs unchanged; use GUIDs in code.**
- **Foundry Account Owner has no data actions. Foundry Owner is the only single role spanning both planes.** Fine-tuning needs both.
- **Do not use roles beginning "Cognitive Services" or the "Azure AI Developer" role** for Foundry projects — the latter is scoped to Azure ML workspaces and Foundry hubs despite its name.
- **Scopes include an individual agent**, but agent-scope assignments are evaluated only for endpoint access.
- **Foundry User is auto-assigned on portal deployment and not on SDK or CLI deployment.**
- **Entra ID scope is `https://ai.azure.com/.default` and requires a custom subdomain.** Agents, evaluations, datasets, Content Understanding and workflows **cannot** use API keys.
- **Entra Agent ID:** an agent identity is a service principal created by a blueprint; **the agent identity, not the managed identity, needs the downstream RBAC**; a wrong token audience fails even with correct RBAC; blueprint principals cap at **250** agent identities and their creation permission **cannot be revoked**.
- **Quota is per subscription, per region, per model, in TPM.** Usages API for consumption; Model Capacities API for availability. Fifteen minutes to propagate.
- **Quota increases are ordered by receipt and prioritised by existing consumption; requests failing that test "might be denied".** Partner and community models cannot get increases at all. Agent Service file, message and tool limits cannot be increased.
- **Capacity APIs return data for retired models.**
- **Nine deployment types** across global, data-zone and regional processing scopes, plus **Developer** — no residency guarantee, twenty-four-hour lifetime, no SLA.
- **Five lifecycle stages**; retirement returns `410 Gone`; "existing customer" for a Deprecated model is decided **per subscription**.
- **Eighteen months from launch for GA models, set programmatically at launch; twelve for Anthropic, DeepSeek, Fireworks and Mistral.** Sixty days' notice for GA, thirty for preview. **Retirement dates are not extendable. Emergency retirement with unspecified shortened notice is reserved.**
- **Three upgrade policies:** `OnceNewDefaultVersionAvailable`, `OnceCurrentVersionExpired`, `NoAutoUpgrade`. **Provisioned deployments are never auto-upgraded.**
- **The Models API inverts the documentation's vocabulary:** `Deprecating` means still serving; `Deprecated` means retired.
- **Service Health has no Foundry service** — alert on `Azure OpenAI Service`.
- **Basic setup:** managed storage, no CMK, no BYO data, **no outbound isolation** — but inbound private endpoints work on any setup. **Standard** adds BYO Storage, AI Search and Cosmos DB plus CMK; **standard private** adds BYO VNet and no public egress.
- **Subnet delegated to `Microsoft.App/environments`, `/27` or larger. Avoid `172.17.0.0/16`. No automatic cross-region failover.**
- **Tracing is off by default** and only Foundry Account Owner or Foundry Owner can enable it. It captures prompts, completions, tool calls and metadata into Application Insights, readable by **Log Analytics Reader**. No default retention is stated.
- **Logic Apps agent loops emit no traces or metrics.** Client-side tracing is preview. Traces take two to five minutes to appear.
- **Continuous evaluation samples**, at a configurable rate, capped by `max_hourly_runs` defaulting to **100 per hour**; excess runs are skipped. Scheduled evaluations, red team scans and alerts are all preview.
- **Guardrail policies are Azure Policy** scoped to subscription or resource group, with exceptions; need Owner or Resource Policy Contributor; take up to thirty minutes to appear and an unbounded scan to evaluate.
- **Two built-in model-deployment policies** — approved-models (GA) and eligibility (preview, `onlyAllowDirectFromAzure` and `denyPreviewModels`). Evaluated at deployment time; **the model stays visible and Deploy is disabled with a reason.**
- **Cost estimates exclude prompt agents, non-Foundry agents, PTU and discounts.** Cost Management and the invoice are authoritative.
- **Project-level chargeback uses an automatic `project` tag, is preview, and excludes Azure Marketplace models.** Azure OpenAI appears under **Cognitive Services** in Cost Management.
- **Fine-tuned models bill hourly for hosting even when unused. There is no hard spend cap.**
- **Topology:** isolation is the default for production; colocation's price is "shared blast radius for production incidents, quota exhaustion, and misconfiguration". The business-group-resource-with-workload-projects pattern is explicitly not recommended.
- **The fleet inventory covers Foundry agents, SRE Agent, Logic Apps agent loops and registered custom agents; not classic agents or OpenAI assistants; and is permission-relative, so two people see different estates.**
- **Lifecycle operations differ by platform:** start/stop for hosted, published, SRE and Logic Apps; block/unblock for custom; **nothing but deletion for unpublished prompt agents**; and **stopping does not terminate in-flight runs**.

## Method and evidence base
First-party product documentation, written for two audiences at once — enterprise administrators and developers — and unusually clear about the boundary between them. Its authority is **definitional**: it states what the platform does, what it permits, and what it commits to. **Definitional authority is not evidential authority.** Nothing here is measured. There is no adoption data, no failure-rate data, no benchmark, no comparison against competing governance surfaces, and no evidence that any of the recommended patterns produces better outcomes than its alternative.

Its candour is above the vendor average and should be credited specifically, because candour is the property that makes documentation teachable. It states that basic setup lacks isolation; that Owner is insufficient for development; that guardrail policy creation is beyond most users' permissions; that there is no hard spend cap; that the capacity API reports retired models; that its own API vocabulary contradicts its own prose; that a recommended-looking landing-zone topology is not recommended; that Logic Apps agents cannot be observed; and that quota requests from non-consuming customers may be denied. Each of those is a fact a vendor could have omitted.

The two commitments that do resemble measurable claims — the eighteen-month lifecycle and the sixty-day notice — are **promises, not observations**, and no record of their fulfilment is published.

## Vocabulary the sources introduce
- **Control plane / data plane** — manage the resource versus use it; RBAC `actions` versus `dataActions`.
- **Foundry Control Plane** — the portal product reached by **Operate** that aggregates fleet, compliance, quota and admin across projects. Distinct from the lower-case architectural sense.
- **Foundry resource / Foundry project** — the governance boundary and the development boundary; account and subresource.
- **Connected resource** — an independent Azure service referenced by a connection, with its own governance boundary.
- **Capability host** — an account- or project-level construct created as a control-plane action; the thing standard agent setup provisions and basic setup does not.
- **Agent identity / agent identity blueprint** — an Entra service principal representing an agent, and the object that holds credentials and mints tokens for a class of them.
- **Audience** — the resource identifier a token is minted for; wrong audiences fail like wrong permissions.
- **`versionUpgradeOption`** — the per-deployment choice between silent change, deferred change and scheduled breakage.
- **Legacy / Deprecated / Retired** — stages, where Deprecated still serves and Retired returns `410 Gone`, and where the API means the opposite by the same words.
- **Emergency retirement** — the reserved right to retire early for compliance or security, with unspecified notice.
- **Guardrail policy** — an Azure Policy assignment expressing minimum safety controls across a scope, with named exceptions.
- **Shared quota pool** — temporary borrowed capacity for testing, of unstated duration.
- **`max_hourly_runs`** — the cap on continuous-evaluation executions; excess is skipped rather than queued.
- **`project` tag** — the automatic Cost Management tag that makes per-project chargeback possible.
- **Block / unblock** — the only lifecycle control available for agents whose infrastructure Foundry cannot reach.

## What to remember
- **The plane split explains most permission failures.** An administrator who can create the resource may be unable to talk to what runs inside it, and that is the design working.
- **The governance boundary is the resource; the development boundary is the project; and the data lives in neither.** Storage, Key Vault, AI Search and Cosmos DB are governed separately or not at all.
- **Every governed platform has an ungoverned edge.** Here it is the connected resources, the unsupported agent types, and the Logic Apps loops that appear in the inventory and emit nothing.
- **A control plane you cannot call from code is a control plane you cannot hand over.** Portal-only governance is reviewable by screenshot.
- **Off by default is a decision the customer inherits.** Tracing collects nothing until someone with a senior role turns it on, and turning it on creates a personal-data surface with no stated retention.
- **Enabling telemetry is a privacy act before it is an engineering act.** Prompts and completions become readable by everyone holding a common monitoring role.
- **Capacity is not an engineering problem.** Quota can be refused, refusal has no published timeline, and the stated prioritisation rule disadvantages exactly the new workload a first engagement represents.
- **The clock starts at launch, not at announcement.** Every model you deploy is already counting down, and the date is discoverable on day one.
- **Choosing an upgrade policy is choosing which failure you prefer** — a silent behaviour change, a deferred one, or a scheduled outage. There is no option that is neither.
- **Buying dedicated capacity buys a migration obligation.** Provisioned deployments never auto-upgrade.
- **A compliance dashboard reports the last scan, not the current state**, and the scan has no published bound.
- **Telling someone why they are blocked is a design decision worth copying.** The model stays in the catalogue and the Deploy button explains itself.
- **There is no hard spend cap, so the cap is something you build.** Alerts notify; only architecture stops.
- **An inventory is permission-relative.** Two people running the same estate report will not agree, and neither is wrong.
- **Everything in this note is enforced by Azure Policy, Azure RBAC, Azure Monitor and Entra.** The durable skill is those four; the Foundry surface over them is the perishable part.

## Why it matters for the course
The programme teaches forward-deployed delivery, and forward-deployed delivery is distinguished from ordinary engineering by the fact that somebody else has to keep the thing running afterwards. Almost everything in this note is about that afterwards. A student who can build a Foundry agent and cannot say who is allowed to stop it, which model version it is pinned to, when that version dies, who receives the notice, what the run costs, who can read the prompts it logged, and what the compliance scan has not yet looked at, has built a demonstration rather than a system.

The material is also unusually well shaped for teaching a durable-versus-perishable distinction, because it contains both layers in the same paragraph. **The perishable layer is the pane names, the role names, the GUIDs, the preview flags and the eighteen-month figure.** The durable layer underneath is a small set of ideas that will outlive every one of them: management and usage are different authorities; a governance boundary that stops short of the data is not a boundary; defaults are decisions somebody inherits; a shared finite resource requires a rationing rule and the rule will not favour newcomers; a dependency with a published end date is a scheduled outage you have not yet booked; and a control you cannot express as code is a control you cannot transfer. Each of those transfers whole to a platform that does not exist yet.

It connects outward in three directions. To [apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md), which supplies the enforcement point Foundry's own cost story lacks — there is no hard cap here, and the gateway is where one gets built. To [purview-dspm-for-ai-and-defender-ai-spm-docs.md](/research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md), whose signals surface in the Compliance pane's Security posture tab, closing a loop this repository already documents from the other end. And to [microsoft-foundry-and-copilot-studio-docs.md](/research/06-microsoft-platform/microsoft-foundry-and-copilot-studio-docs.md), which chose the build path this note then has to operate — and whose warning that department-scale tools fail at enterprise scale "through governance and lifecycle, not through function" is precisely the failure mode this material describes in mechanism.

## How to teach it
- **Lecture:** teach the control-plane / data-plane split with no product attached — management authority and usage authority are different — then reveal that Azure Owner cannot chat with an agent. The surprise does the teaching.
- **Lecture:** teach defaults as inherited decisions. Tracing off, no hard spend cap, `versionUpgradeOption` unset, no private endpoints on connected resources. Ask who owns each default once the engagement ends.
- **Lecture:** teach the eighteen-month clock as a scheduled outage that has already been booked, and ask what else in a delivered system has a known end date nobody has written down.
- **Lab:** assign each of the five built-in roles to a test principal in turn and record, empirically, what each can and cannot do. Predict first. The predictions will be wrong in interesting places.
- **Lab:** deploy a model, deliberately set `NoAutoUpgrade`, then query the Models API for `lifecycleStatus` and `deprecation.inference` and compute the remaining life. Have students explain the `Deprecating`/`Deprecated` inversion before they are told about it.
- **Lab:** enable tracing on a project, run an agent that handles a fabricated personal detail, then sign in as a second principal holding only Log Analytics Reader and retrieve the prompt. The privacy lesson lands once and stays.
- **Lab:** assign the approved-models policy in Audit, deploy a disallowed model, observe it succeed and be flagged; switch to Deny and repeat. Compare what a developer sees in each case.
- **Lab:** enable continuous evaluation at a low sample rate, generate traffic above the hourly cap, and have students report what fraction of runs was actually scored — then ask what the resulting dashboard entitles anyone to say.
- **Assessment:** require an operating model as a deliverable alongside any built system — role assignments with scopes, upgrade policies with retirement dates, telemetry decisions with named readers, cost attribution, and the named receiving owner for each. Defend orally.
- **Assessment:** ask what breaks in ninety days if nobody touches the system. A student who answers "nothing" has not read the lifecycle policy.
- **Assessment:** require the unmeasured list. Marks for the absences found, not for the metrics quoted.
- **Framing:** among the most perishable material in the research set. **Assess the reasoning, the boundaries and the questions asked — never the pane names, the role names or the numbers.**

## Limits and cautions
- **Read at mixed depth.** Seven pages were fetched and read in full; roughly twenty more were read only through search-returned excerpts, so their structure is reconstructed and their tables may be truncated. Several referenced pages were not read at all and are listed by name under Citation and access.
- **This is vendor documentation about vendor governance.** It argues that centralised oversight is desirable and does not discuss what the oversight layer itself costs in latency, permissions overhead, or organisational friction.
- **Definitional, not evidential.** No adoption, failure-rate, performance, cost-saving or outcome data appears anywhere in this set.
- **Actively renaming.** The RBAC roles were renamed mid-documentation and the pages carry the notice inline. **The existing Foundry note already records that the Agent Framework SDK is documented as "formerly Semantic Kernel".** Treat every proper noun here as provisional and every GUID as more durable than the name attached to it.
- **Preview features are load-bearing in this story.** Client-side tracing, scheduled evaluations, red team scans, alerts, project-level cost attribution, the eligibility deployment policy, managed compute deployments and the AI gateway's Foundry integration are all preview. **A governance argument that depends on a preview feature is a governance argument without a service-level agreement.**
- **Classic and new are both live.** Foundry (classic), hub-based projects, standalone Azure OpenAI resources and the new Foundry portal coexist, several pages exist in both variants, and a search result can silently be the wrong one. Two pages consulted for this note carry "(classic)" in their titles.
- **Numbers appear throughout this note and are forbidden downstream.** Eighteen and twelve months, sixty and thirty days, ninety to a hundred and twenty days, a hundred runs per hour, two hundred and fifty agent identities, fifteen and thirty minutes, two to five minutes, thirty resources per region, `/27`, twenty to thirty minutes. **These are dated platform parameters, not findings.** Two are worse than the rest: the dashboard's "latency above 10 seconds" and "a rate below 95%" are **interpretive thresholds asserted with no stated basis** and must never be repeated as though they were measured.
- **The Q&A source is not evidence.** A community thread showing a customer frustrated by quota latency establishes that the question is asked. It establishes nothing about typical response times, and no inference about them may be drawn from it.
- **Portal-only governance is a real constraint on teaching.** Any lab built on the Operate panes cannot be automated, cannot be version-controlled and cannot be graded from an artefact. Plan assessments around the underlying Azure Policy and RBAC objects instead.
- **The local agent skill was read as an operational corroborant, not as documentation.** It is a Microsoft-authored skill file, version 1.2.1, MIT-licensed, resident on the machine at the time of reading. Its workflow claims are cited here only where they restate or sharpen a published fact.
