## The argument in full

### Two agent types, and the second one is a machine
The build-path note already carries the distinction: **prompt agents** are declarative and consume no agent compute; **hosted agents** are your containerised code on managed container compute. What it does not carry is what the second sentence means operationally, and the difference is large enough to change how a team plans.

A hosted agent is packaged as a container image and pushed to Azure Container Registry, **or** shipped as a zip of source and built for you. On deploy, the service pulls the image, provisions compute, **assigns a dedicated Microsoft Entra ID — an agent identity — and exposes a dedicated endpoint.** Hosted agents run on Azure Container Apps; each runs in a **Micro VM** attached to a delegated subnet with its own network interface and its own outbound IP. The published reasons to choose one are precise and worth quoting as a checklist: bring your own code in any framework; use custom protocols and accept non-OpenAI payloads; control CPU and memory; and run stateful workloads that persist files across turns.

The runtime shape is the part that surprises people. **Hosted agents scale per session, not per replica.** Each session gets a VM-isolated sandbox with a persistent `$HOME`; there is no replica count to configure and no warm pool to size. The published lifecycle numbers are **15 minutes idle timeout** before compute is deprovisioned and state persisted, **a maximum session lifetime of 30 days**, and **permanent session deletion after 30 days of inactivity.** Compute tiers are **0.5 vCPU / 1 GiB, 1 vCPU / 2 GiB, 2 vCPU / 4 GiB.** Disk budget is **up to 20 GiB at 1 vCPU or larger**, of which **about 20% is reserved for system use** and is neither visible nor available to the agent. Platform ceilings are **100 active revisions** and **1,000 total revisions per agent name**, with roughly **200 hosted agents per Foundry instance** against a separate instance-wide cap of about **250 projects**.

Two of those facts carry a consequence the documentation states outright and that a costing exercise will otherwise miss. **The CPU and memory you set describe a single session, not the aggregate footprint of the agent**, and billing is CPU plus memory across all active sessions — so **oversizing multiplies cost by your concurrency.** The published right-sizing procedure is empirical rather than analytical: run a representative workload, open the linked Application Insights resource, read CPU, available memory, request rate and average request duration over the tested range, and compare observed peaks against allocation. **All the stated thresholds in that procedure are heuristics with no evidence attached, and are forbidden downstream.**

### The definition file, and a live demonstration of decay
**AgentSchema** is published as an open specification for defining an agent in code-first YAML — model, instructions, tools, connections — and is described as a unified exchange format between Copilot Studio, Foundry and other platforms. It has two shapes. An **AgentDefinition** is concrete and executable, carrying a `kind` of `prompt`, `hosted` or `workflow`. An **AgentManifest** is a parameterised template that wraps a definition as its `template` field and adds `parameters` — prompted at init with `{{ param }}` substitution, and markable `secret: true` — and `resources`, the external dependencies. A **ContainerAgent** is an AgentDefinition with `kind: hosted`. Substitution runs in two layers, and the layering is the genuinely instructive part: `{{ param_name }}` resolves at init from prompted values, `${VAR_NAME}` resolves at deploy or run from the environment's own `.env`. One file then works across environments.

What is expressible: name, kind, protocols, environment variables, container CPU and memory, a prebuilt image path or a Dockerfile path; model resources by id; connection resources with a target, a category and credentials; and toolbox resources carrying built-in capabilities, connections and skill references. Two protocol values are defined — **`responses`**, the OpenAI Responses API, which **includes conversation history management**, and **`invocations`**, a custom payload protocol with **no built-in conversation management.** What is *not* expressible is stated as plainly: **"The schema doesn't include a skills field"**, and the init, run and up commands do not auto-download skills; you manage them as project-level resources and wire them in yourself. There is also an explicit instruction not to declare the project endpoint as an environment variable, because the platform injects it and a declaration risks shadowing the platform value.

**And now the demonstration.** The schema reference opens with a note that **agent manifests and standalone agent definitions are deprecated**, that as of a named extension version all hosted-agent configuration lives in a single `azure.yaml`, and that the whole schema model it then documents is **"retained for reference and is superseded."** The `azd` agent-development page says the same thing from the other side: **"There is no standalone `agent.yaml` or `agent.manifest.yaml` file in the current hosted-agent `azd` project model."** A third page, on deploying to a Foundry endpoint, still describes `agent.yaml` as the file `azd` deploys, states that `azd` validates `kind` and rejects any other value, and notes that AgentSchema is broader than what `azd` accepts — **prompt-only definitions are in the specification and are not accepted by deploy.** Meanwhile the locally installed first-party skill, version 1.2.1, still lists `agent.yaml` in its own description as a thing it helps you author.

**Four first-party surfaces, three positions, one of them formally deprecated, all rendering on the same day.** Nothing here is wrong exactly; the pages are at different points on a migration. But a student who reads one page and generalises has learned something false, and no amount of care in reading a single page would have caught it. **This is the strongest available argument for the pinned-citation standard this programme already teaches at [S050](/wiki/seminars/S050.md), and it should be taught as a specimen rather than merely cited as a caution.**

### The model catalogue, and a decision that is really two decisions
Model selection resolves to two questions the documentation names directly: **where your data is processed** and **how you pay** — with performance characteristics falling out of the second. Two categories, **standard** (pay-per-token) and **provisioned** (reserved capacity), cross three processing scopes, **global**, **data zone** and **regional**, giving the published list: Global Standard, Global Provisioned, Global Batch, Data Zone Standard, Data Zone Provisioned, Data Zone Batch, Standard, Regional Provisioned, and **Developer** — the last being fine-tuned-model evaluation only, with **a 24-hour lifetime, no SLA and no data-residency guarantee.**

The residency rule is stated crisply and is the part worth memorising because it is the part that gets a design rejected: **data stored at rest remains in the designated Azure geography for every deployment type, but inferencing data is processed differently** — global types may be processed in any Azure region where the model is deployed; data-zone types stay within the Microsoft-specified zone (US, EU or APAC); standard and regional types are processed in the deployment region. **All deployment types perform identical inference operations. Billing, scale and performance are what differ.** There is also **instant access (preview)**, where supported models are called by name with no deployment created at all.

The published selection criteria read as a decision table by residency requirement, workload pattern and latency requirement — bursty traffic to standard, consistent high volume to provisioned, large non-time-sensitive batches to batch, low latency *variance* to provisioned. **Note the wording: provisioned is offered for low latency variance, not low latency.** That distinction is the whole reason [research/03-measurement-evaluation/huyen-ai-engineering.md](/research/03-measurement-evaluation/huyen-ai-engineering.md) insists latency is a distribution, and the platform's own selection guidance quietly agrees. Capacity mechanics themselves are already covered at [provisioned-throughput-for-foundry-models.md](/research/06-microsoft-platform/provisioned-throughput-for-foundry-models.md) and are not repeated here. **One cost figure appears in the selection guidance and is forbidden downstream.**

### Tools: a catalogue, a bundle, and a governance argument
The build-path note records that tools reach external systems through the tool catalogue, MCP and OpenAPI, with Logic Apps and Functions for automation. The interior is more organised than that summary suggests.

The **tool catalogue** holds three kinds of entry: a **remote MCP server** the publisher hosts; a **local MCP server** you host and connect by endpoint; and **custom** entries, which are **MCP servers converted from Azure Logic Apps connectors.** Filters are by publisher, category and registry, and a **private tool catalog** scopes entries to one organisation. The custom-tool routes are MCP endpoints, OpenAPI 3.0 and 3.1 specifications, and **A2A** endpoints. OpenAPI tools support three authentication methods — **anonymous, API key and managed identity** — and are supported across the Python, C#, JavaScript, Java and REST surfaces on both basic and standard setups.

**Toolbox** is the more interesting object, because it is an argument rather than a feature. The stated problem is that agents connect directly to tools, APIs and MCP servers, each needing separate configuration, authentication and governance, which produces duplicated effort, inconsistent behaviour, fragile deployments and rising operational overhead as agent count grows. The stated answer is to define a curated set once and expose it through **a single MCP-compatible endpoint** consumed across frameworks and runtimes, with credential management, governance, observability, access control and versioning applied at the toolbox level — and, critically, **tool implementations updatable without changing agent code.** Its four pillars are Build, Discover, Consume and Govern, and the Discover pillar names a real failure mode: **a single toolbox can hold hundreds of tools without flooding the model's context, inflating token cost, or degrading selection accuracy**, because **tool search (preview)** finds the relevant ones at runtime.

The support matrix is where the honesty is. MCP, web search, Azure AI Search, code interpreter, file search, OpenAPI, A2A, browser automation, Fabric IQ and Work IQ work **both** through a toolbox and by direct integration. **Tool search, skills and the reminder tool are toolbox-only.** **Function calling is direct-only, because execution is client-side.** Grounding with Bing and computer use are direct-only. **The abstraction is not universal, and a design that assumes it is will discover the exception late.**

### Knowledge: three layers, and a naming collision worth pre-empting
Grounding runs at three levels of managedness. At the bottom, **the Azure AI Search tool** connects an existing index directly so the model answers with **inline citations**; the operational constraint recorded there matters — **with a private virtual network you must authenticate the search connection with a Microsoft Entra project managed identity, because key-based authentication is not supported.** In the middle, Azure AI Search's own agentic-retrieval objects: a **knowledge source** points at searchable content, a **knowledge base** is the top-level object that orchestrates retrieval over one or more sources, optionally with an LLM for query planning, answer synthesis or web-content summarisation, plus properties controlling routing, source selection and encryption. At the top, **Foundry IQ**, a managed knowledge layer connecting agents to Blob Storage, SharePoint, OneLake and public web sources, which **automates chunking, embedding generation and permission enforcement through AI Search**, and whose retrieval engine **decomposes complex queries into subqueries, runs them in parallel and reranks results.** Separately, **Work IQ** exposes Microsoft 365 signal — mail, meetings, documents, Teams messages — through a CLI and an MCP server, respecting user-level permissions.

Two things follow. First, **Foundry IQ is query decomposition and reranking sold as a service**, which is exactly the mechanism [research/02-technical-foundations/barnett-rag-failure-taxonomy.md](/research/02-technical-foundations/barnett-rag-failure-taxonomy.md) and the retrieval material treat as a design choice with failure modes — buying it does not remove the failure modes, it removes your visibility of them. Second, the permission story is the one already taught from [azure-ai-search-and-acl-patterns.md](/research/06-microsoft-platform/azure-ai-search-and-acl-patterns.md); "permission enforcement" here means enforcement through AI Search, and inherits whatever that layer does and does not do. **No retrieval-quality figure is published for any of these layers, and none is asserted here.**

### Threads, sessions, conversations and runs — four words, and they are not synonyms
This is the single most confusable area in the platform, and getting it wrong produces bugs that look like model failures.

The **classic** model — explicitly deprecated, with a stated retirement date of **31 March 2027** and a migration guide — has **threads** as conversation sessions storing messages and handling truncation automatically, **up to 100,000 messages per thread**; **messages**; and **runs**, which invoke the agent on a thread, append messages, and expose statuses including `queued` and `in_progress`. Threads persist until explicitly deleted, and the published guidance is to plan a retention strategy against storage cost and compliance policy.

The **current** model splits what "thread" used to conflate. A **session** is sandbox compute plus persisted filesystem, identified by `agent_session_id`, managed by the platform through a `/sessions` API, and used for file uploads and working state. A **conversation** is the history of messages, tool calls and responses, identified by `previous_response_id` or a `conversation` id, **stored in Foundry, persisting independently of compute state, and accessible from the playground, the API, Teams or any published channel.** The behaviour then forks by protocol, and this is the trap: under the **Responses** protocol, **continuity comes from the response or conversation id and not from the session id — reusing the same session id does not, on its own, replay prior messages to the model.** Under the **Invocations** protocol, **the platform stores no conversation history at all**; your container manages state.

Storage location depends on setup, and this is where the build-path note's basic-versus-standard distinction acquires teeth. **Basic setup stores agent state in Microsoft-managed resources. Standard setup stores threads, files and vector stores in your own Azure resources**, connected through capability hosts: **Azure Storage** for uploaded files, **Azure AI Search** for vector stores, **Azure Cosmos DB** for messages, conversation history and agent metadata. Standard setup provisions **five containers in a database named `enterprise_memory`, each requiring 1000 RU/s against an account total of at least 3000 RU/s** — `thread-message-store`, `system-thread-message-store` and `agent-entity-store` belonging to the classic runtime, and `agent-definitions-v1` and `run-state-v1` to the new one. **The documentation warns that the two runtimes use different containers.** The FAQ confirms the service is stateful and retains data.

**On retention: the documentation states a plan-your-own-strategy position for threads and gives no default period.** Threads persist until deleted. In standard setup the data is in your account and its lifecycle is yours. **That is a real answer, not an absence — but it is an answer that places the obligation on you, and a team that reads "managed" as "managed for me" will find no retention policy where it expected one.**

### Tracing and observability — the gap this note exists to close
**Foundry uses OpenTelemetry semantic conventions and stores traces in Azure Monitor Application Insights.** Tracing is **generally available for prompt and hosted agents; workflow and external agents are in preview.**

The recommended starting point is **server-side tracing**, which Foundry enables automatically once an Application Insights resource is connected to the project. **No code changes are required**, it works for any agent hosted in Foundry, and traces are available within minutes. Client-side instrumentation is layered on afterwards, when you need visibility into your own application code around the agent call, and exports to Azure Monitor, the console, or **any OTLP-compatible backend — Datadog, Grafana Tempo, Jaeger and Honeycomb are named.** A third path traces locally in VS Code against a local OTLP collector. Message content is **not** captured by default: `AZURE_TRACING_GEN_AI_CONTENT_RECORDING_ENABLED` must be set, and the documentation warns in the same breath that the content may contain personal data.

**What a trace captures**, stated at two levels of detail: **inputs, outputs, tool usage, retries, latencies and costs**; and more specifically **user inputs and agent outputs, tool calls and results, token consumption, and time signals such as duration and latency.** The framing of *why* is unusually good and is the part to teach: an agent run may have many steps; the sequence varies with input; inputs and outputs at each stage may be long; **and each step may nest — an agent invokes a tool, which uses another process, which invokes another tool — so when a top-level output is wrong it can be genuinely hard to determine where the error was introduced.** The stated purpose is to let you view the inputs and outputs of **each primitive** in the order invoked. Two questions are named as the ones tracing exists to answer: **"Where did this response come from?"** and **"Which step introduced an error or latency spike?"**

The vocabulary is standard OpenTelemetry — traces, spans, attributes, semantic conventions, exporters — and Foundry adds a multi-agent extension developed **in collaboration with Cisco Outshift**, built on OpenTelemetry and **W3C Trace Context**, and integrated into Foundry, Microsoft Agent Framework, LangChain, LangGraph and the OpenAI Agents SDK. The published conventions are worth having in full because they name what a multi-agent system is expected to expose: a span **`execute_task`** capturing task planning and event propagation; child spans under `invoke_agent` for **`agent_to_agent_interaction`**, **`agent.state.management`** (effective context, short- and long-term memory), **`agent_planning`** (internal planning steps) and **agent orchestration**; attributes **`tool_definitions`** and **`llm_spans`**; attributes **`tool.call.arguments`** and **`tool.call.results`** under `execute_tool`; and an **Evaluation event** carrying name, error type and label. **A trace is therefore expected to carry the agent's planning steps, its memory management and its arguments to and results from every tool — which is to say the trace is where the reasoning becomes inspectable, and also where the sensitive data goes.**

Alongside traces the portal exposes a **Conversation** view — conversation history, response information and tokens in a run, **ordered actions, run steps and tool calls**, and inputs and outputs between user and agent — searchable by response id or by a trace id that maps to the conversation. **This is the mechanism that makes after-the-fact reconstruction possible without re-running anything.**

External agents can be brought onto the same surface: instrument with OpenTelemetry, export to the project's Application Insights, and **set `gen_ai.agent.id` on every span** so Foundry can attribute it to the right registration — with the explicit note that if your framework does not set the attribute automatically you must set it yourself.

**On retention, the documentation gives a partial and slightly contradictory answer, and the precision matters.** The setup page states that once tracing is enabled **you have access to out-of-the-box traces for the past 90 days**, and that the portal lets you search, filter and sort ingested traces **from the last 90 days**. The same page's "Data retention and cost" section says only that traces are stored in your connected Application Insights resource and that **"Data retention and billing follow your Application Insights and Log Analytics configuration."** The concepts page agrees: **"Trace data retention and sampling follow your Application Insights configuration."** So: **there is a stated 90-day portal window; there is no Foundry-owned retention period at all; and retention is delegated to a resource you configure and pay for.** A team that wants traces for longer than the portal shows must go to Application Insights, and a team that has not thought about Log Analytics retention has not decided how long its agent's reasoning is kept.

Access is non-trivial and is a genuine handover item: **Log Analytics Reader** on the connected resource to query telemetry, plus **Privileged Monitoring Data Reader** if the underlying tables are protected. The published security guidance is short and correct — do not put secrets, credentials or tokens in prompts, tool arguments or span attributes; redact or minimise personal data before it reaches telemetry; **and treat trace data as production telemetry, applying the same access controls and retention policies you use for logs and metrics.** The published best practices add two more: **use consistent span attribute names and formats across all agents and tools**, and **correlate evaluation run ids with trace data** so quality and performance are analysable together. **Traces typically appear within two to five minutes; that figure is forbidden downstream.**

Separately from traces, hosted agents expose container logs — recent console output including stdout and stderr, continuous streaming, **system events for container lifecycle**, and filtering by session id — with a published table of common log patterns mapping symptoms to causes: a listening message meaning healthy start, an authentication error meaning the agent identity cannot authenticate, a model-not-found error meaning a deployment-name mismatch, container restart events meaning a crash loop. The readiness contract is concrete: **the container must answer `GET /readiness` on port 8088 with a 200**, and a protocol declared in configuration that the code does not implement causes requests to fail. **This is ordinary operations engineering, and it is a useful corrective to the idea that a managed agent platform removes it.**

### Evaluation — what is here that the evaluations note does not carry
[agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md) already carries the programming model, the local-versus-cloud tiering, the split strategies, the full nineteen-constant evaluator catalogue across agent behaviour, tool usage, quality and safety, expected outputs and tool calls, evaluation of pre-existing responses, repetitions, workflow evaluation, data mapping and thresholds. **None of that is repeated here.** What is new is the production side.

**Continuous evaluation** runs evaluators **on sampled agent responses** at a configurable sample rate, surfaces metrics in the monitoring dashboard, and — the important part — **connects evaluations to traces for root-cause analysis.** It is configured alongside three other preview features on the same settings panel: **scheduled evaluations** against a template on a schedule, **red team scans** running adversarial tests for risks such as data leakage or prohibited actions, and **alerts** on latency, token usage, evaluation scores or red-team findings. A published operational limit is worth carrying because it silently changes what your sample means: **evaluation runs are skipped when the hourly run limit is reached, and the default is 100 runs per hour**, adjustable via `max_hourly_runs`. **That figure is forbidden downstream, but the mechanism is not** — a rate limit on evaluation is a sampling decision made for you, and a team reporting a production quality number without knowing whether it hit that ceiling does not know what its number covers.

**Conversation-level evaluation (preview)** evaluates conversations pulled from Application Insights by agent name and version, with **tool definitions retrieved automatically from the traces or the agent registry.** Two filter strategies are published: **`random_sampling`**, the default, uniformly random up to a maximum; and **`smart_filtering`**, described as **"a service-managed heuristic that biases toward 'interesting' traces — conversations with potential problems, edge cases, or anomalies."** **The heuristic is not documented, and a biased sample scored and reported as a quality figure is a measurement whose denominator nobody can state.** The published lookback ceiling is **7 days (168 hours)**, with older traces reachable only through explicit time bounds inside your Application Insights retention.

The evaluator catalogue has grown beyond what the earlier note records, and the additions are structural rather than cosmetic. **Evaluation levels** are now explicit: every evaluator declares `supported_evaluation_levels`, either **`turn`** (the default, scoring individual responses) or **`conversation`** (scoring the whole multi-turn interaction), and **all evaluators in a run must support the level chosen — incompatible levels cannot be mixed.** **Rubric evaluators (preview)** score against custom weighted criteria, each dimension rated 1–5 by an LLM judge, the overall score being **the weighted average normalised to 0–1**; the published recommendation is to make rubrics your *primary* measure of agent quality because they express what "good" means for your case, and to pair them with built-in evaluators for safety, groundedness and harm. **Azure OpenAI graders** add Model Labeler, String Checker, Text Similarity and Model Scorer. And **human evaluation (preview)** now exists as a first-class feature: define question templates, have reviewers answer them per response in a browser-based preview app, and download the results.

**That last feature makes the platform's central silence sharper rather than softer.** The platform now ships an instrument for collecting human judgements about agent responses. **It publishes no agreement rate, no correlation and no calibration between any built-in evaluator and those human judgements.** A dedicated search for such data returned the human-evaluation feature, the rubric documentation and the evaluator catalogue, and no agreement figure of any kind. **The absence is confirmed rather than assumed.** This repository already forbids asserting any such agreement, on the prohibition list at [11-Microsoft-AI-Platform-Map.md](/archive/bsc-programme/program/11-Microsoft-AI-Platform-Map.md); **that prohibition remains correct, and this note is the confirmation it was resting on.**

### Fine-tuning — where the brief was wrong, and how
The three techniques are published with clear "when to use" boundaries. **SFT** trains on input-output pairs and is the stated starting point for most projects — domain specialisation, task performance, style and tone, instruction following, language adaptation — and works best when there are finite ways to solve a problem. **DPO** adjusts weights from binary preference data, **needs no reward model**, is described as computationally lighter and faster than RLHF while being equally effective at alignment, and suits cases with no clear-cut correct answer where tone, style or content preference matter. Its dataset format is distinct: `input`, `preferred_output` and `non_preferred_output`, **exactly two completions**, assistant and tool roles only. **RFT** uses reward signals from **graders** — string check, text similarity, model-based, or a multi-grader — and suits objective domains with many possible routes to an answer; it forbids system messages, requires the final training message to be a reference answer rather than an assistant turn, adds `eval_samples`, `eval_interval`, `reasoning_effort` and `compute_multiplier` as hyperparameters, and supports pausing and resuming to inspect checkpoints. **Techniques stack: SFT first, then DPO on the result.** Training tiers are **Standard** (in-region, data residency), **Global** (lower cost, faster queue) and **Developer** (experimentation, preemptible). The published shape of the practice is one line long and correct: **start from a baseline, measure, refine.**

**Now the correction.** The brief for this note listed, among expected silences, "no published guidance on how much data fine-tuning requires to be worthwhile." **That is not the case, and recording it accurately matters more than confirming the expectation.** The documentation is explicit and repeated: **jobs will not proceed with fewer than 10 training examples**, and "such a small number isn't enough to noticeably influence model responses"; **start with 50 well-crafted examples**; **provide hundreds, if not thousands** for success; a separate page says **50–100 for initial testing, scaling to 500+ for production**; RFT should begin with **several dozen to a few hundred** examples before committing to more, with a **50,000-example ceiling** on training files; and files must be JSONL, UTF-8 with a byte-order mark, **under 512 MB.** There is even a shape claim: **"doubling the dataset size can lead to a linear increase in model quality"**, immediately qualified by the warning that low-quality examples hurt and that training on unpruned internal data can produce a model **worse** than expected.

**So the silence is not where it was expected. Guidance is published in quantity; evidence for it is published nowhere.** No study, no curve, no dataset, no source is cited for the floor of 10, the recommended 50, the 500-plus, or the linearity claim. **Every one of those numbers is forbidden downstream**, and the linearity claim in particular is an asserted magnitude relationship of exactly the kind [09-Durable-and-Perishable-Register.md](/wiki/program/09-Durable-and-Perishable-Register.md) exists to keep out of teaching. **The durable content is the ordering — that a floor exists, that quality dominates quantity, and that pruning beats accumulating.** The numbers are this quarter's.

### Multi-agent: three shapes, and one of them is a security boundary
**Foundry workflows (preview)** orchestrate multiple agents in a repeatable process with branching logic and variable handling without code, and with **human-in-the-loop steps for approvals or clarifying questions.** Three portal templates are published — **Human in the loop**, **Sequential** and **Group chat** — and the underlying framework offers five orchestration patterns: **Sequential, Concurrent, Handoff, Group Chat and Magentic.** A workflow can be **wrapped so that it looks like an ordinary agent**, callable as a tool or over A2A, with consumers unaware they are talking to a workflow.

**Connected agents** are the delegation pattern: separate agents with their own orchestration, tools and knowledge, where a parent delegates part of a request. The published governance guidance is unusually direct and belongs in the assurance strand rather than the build one. Treat the connected agent **as an agentic tool with a description**, from the parent's perspective. **Manage data handoff deliberately** — decide what context passes, because in at least one sibling product conversation history passes by default. And the security paragraph is the one to teach verbatim in substance: **the connected agent may have access to things the parent does not; ensure that calling it does not inadvertently bypass restrictions; if the parent may not delete records but the child may, the parent must not call the child where deletion might happen without approval.** **A delegation edge is a privilege boundary, and the platform will not notice if you have drawn it wrongly.**

The distinction between **handoff** and **agent-as-tool** is stated precisely and is worth carrying because it changes who owns the failure: under handoff, control passes entirely, the receiving agent takes **full ownership** of the task and has full context; under agent-as-tools, the primary agent retains overall responsibility, control returns after the subtask, and the primary decides what context the sub-agent sees. **Also recorded honestly: connected agents in the classic experience are documented as available only in a named preview API version, with the documentation itself recommending migration to workflows.**

Publishing carries a trap that belongs in every handover checklist. An **agent version** is an immutable snapshot created on every change. Publishing creates an addressable resource with a stable endpoint, its own Entra agent identity and its own RBAC scope — and the note says twice, in two places, that **permissions assigned to the project identity do not automatically transfer to the published agent**, so access must be reassigned after publishing. For connected agents, **each agent must be published separately**, children first. **RBAC on the published application is managed through Azure Resource Manager, not through the Entra agent identity** — the agent identity governs the agent's own outbound calls, and Azure RBAC governs who may invoke it. **And this whole model is itself labelled the legacy publishing experience, with a migration guide to a newer one that collapses application and deployment into the agent object.**

### Responsible AI controls — what is on, and the gap in the middle
Defaults exist and are real. Models are assigned the **Microsoft.DefaultV2** guardrail. The content filtering system is an **ensemble of multi-class classification models detecting four categories — violence, hate, sexual, self-harm — at four severity levels: safe, low, medium, high**, plus optional binary classifiers for jailbreak risk and for protected text and code. **The default configuration filters at the medium threshold for all four categories on both prompts and completions** for text models, and at low for image models. **Prompt shields and protected-material models are optional and on by default**, and can be turned off — with the caveat that some must stay on to retain coverage under the copyright commitment. Filtering is **synchronous** with generation and **billed separately.**

Agent guardrails are **preview**, and two published facts about them deserve to be read together, because together they are a security finding rather than a configuration note. First: **for agents, "annotate" alone is not available — only "annotate and block."** Second, and stated as an Important: **"Risks are detected in an agent based on the guardrail it's assigned, not the guardrail of its underlying model. The agentic guardrail fully overrides the model's guardrail."** The documentation's own worked example shows what that means. A model deployment filters violence at High; the agent using it filters violence at Low for input and output and **declares nothing for tool calls**. The published expected behaviour: user queries scanned at Low; **tool calls generated internally, including the content sent to the tool, not scanned at all**; **the tool's response not scanned at all**; final output scanned at Low. **Override is total, not additive. An agent guardrail that omits a stage leaves that stage unscanned, and the model's stricter setting does not fill the hole.**

Inheritance resolves in a stated order: a custom guardrail if assigned; otherwise the underlying model deployment's guardrail; **and DefaultV2 only if the model deployment has none.**

One further item is recorded with a health warning about its provenance. **A Microsoft Q&A answer — not documentation** — states that `Microsoft.Default` and `Microsoft.DefaultV2` are system-managed baseline policies, **not editable and not deletable**, visible through the REST API but not the portal, that **protections for indirect prompt injection cannot be added to them**, and that the supported approach is a separate custom policy applied alongside. **Treat that as an unverified community answer with a Microsoft respondent, not as published guidance**, and note that a security scanner flagging the defaults is the reported symptom rather than a demonstrated vulnerability. **What can be said from documentation alone is narrower and still useful: the defaults exist, they are the floor, and the documented path to stronger protection is a layered custom policy rather than a stricter default.**

Finally, the transparency note's shared-responsibility language is repeated across many pages and is the platform's own framing of the limit: you are responsible for reviewing and testing applications in the context of your specific use cases, for **implementing your own responsible AI mitigations — metaprompts, content filters, other safety systems** — and for reviewing third-party data practices where data leaves the boundary. **The controls are a floor the vendor supplies, not a ceiling the vendor guarantees.**

## Key concepts and practices
- **Hosted agent = container image or source zip → ACR → managed compute, dedicated Entra agent identity, dedicated endpoint.** Runs on Azure Container Apps in a **Micro VM** with its own subnet IP.
- **Scaling is per session, not per replica.** No replica count, no warm pool. **Idle timeout 15 minutes; maximum session lifetime 30 days; permanent deletion after 30 days inactive.**
- **Compute tiers 0.5/1, 1/2 and 2/4 vCPU-to-GiB; disk up to 20 GiB with ~20% reserved and invisible.**
- **CPU and memory describe one session; billing is across all active sessions, so oversizing multiplies cost by concurrency.**
- **Right-sizing is empirical:** run a representative workload, read Application Insights performance, compare peaks to allocation.
- **Ceilings:** 100 active and 1,000 total revisions per agent; ~200 hosted agents per instance; ~250 projects per instance.
- **AgentSchema:** AgentDefinition (`prompt` | `hosted` | `workflow`), AgentManifest (template + parameters + resources), ContainerAgent. **`{{ param }}` resolves at init; `${VAR}` resolves at deploy or run.**
- **Two protocols: `responses`** (platform-managed conversation history) and **`invocations`** (no built-in conversation management).
- **The schema has no skills field**, and tooling does not auto-download skills.
- **`agent.yaml` and `agent.manifest.yaml` are documented as deprecated, superseded by a single `azure.yaml`** — while three other first-party surfaces still describe them as current.
- **Nine deployment types** across standard/provisioned × global/data-zone/regional, plus batch variants and **Developer** (24-hour lifetime, no SLA, no residency guarantee). **Instant access (preview)** needs no deployment at all.
- **Data at rest stays in the Azure geography for every type; inference processing location is what the type actually selects.**
- **Provisioned is offered for low latency *variance*, not low latency.**
- **Tool catalogue entries: remote MCP, local MCP, and custom (Logic Apps connectors converted to remote MCP).** Private tool catalogue scopes to one organisation.
- **OpenAPI 3.0/3.1 tools with anonymous, API-key or managed-identity authentication.**
- **Toolbox = curated tools behind one MCP-compatible endpoint**, with central credentials, versioning, governance and observability, and **tool implementations updatable without changing agent code.**
- **The toolbox abstraction is not universal:** tool search, skills and reminder are toolbox-only; **function calling is direct-only because execution is client-side**; Bing grounding and computer use are direct-only.
- **Three grounding layers:** the AI Search tool with inline citations; knowledge sources and knowledge bases for agentic retrieval; **Foundry IQ**, which automates chunking, embedding and permission enforcement and **decomposes queries into parallel subqueries and reranks.**
- **Private VNet + AI Search tool requires Entra managed identity; key-based authentication is unsupported.**
- **Session ≠ conversation.** Session is sandbox compute and filesystem; conversation is message history stored in Foundry and reachable from any channel. **Under Responses, reusing a session id does not replay prior messages.**
- **Basic setup stores state in Microsoft-managed resources; standard setup stores threads, files and vector stores in your Storage, AI Search and Cosmos DB** — five containers, 1000 RU/s each, 3000 RU/s minimum, **different containers for the classic and new runtimes.**
- **Threads persist until deleted; no default retention period is published; the documentation tells you to plan one.**
- **Tracing is GA for prompt and hosted agents, preview for workflow and external agents.**
- **Server-side tracing needs no code change** once Application Insights is connected. Client-side and local-OTLP paths layer on top; **any OTLP backend is supported.**
- **Traces capture inputs, outputs, tool calls and results, retries, token consumption, latency and cost.** **Message content requires an explicit environment variable and is off by default.**
- **Multi-agent semantic conventions** (with Cisco Outshift, on OTel + W3C Trace Context): `execute_task`; child spans `agent_to_agent_interaction`, `agent.state.management`, `agent_planning`, agent orchestration; attributes `tool_definitions`, `llm_spans`, `tool.call.arguments`, `tool.call.results`; an Evaluation event.
- **The Conversation view exposes ordered actions, run steps and tool calls**, searchable by response or trace id — the reconstruct-without-re-running mechanism.
- **External agents join the same surface by setting `gen_ai.agent.id` on every span.**
- **Portal trace window is 90 days. Foundry states no retention period of its own: retention and sampling follow your Application Insights and Log Analytics configuration.**
- **Querying telemetry needs Log Analytics Reader, plus Privileged Monitoring Data Reader on protected tables.**
- **Published tracing practice: consistent span attribute names; correlate evaluation run ids with traces; redact before telemetry; treat traces as production data under the same controls and retention as logs.**
- **Continuous evaluation samples responses at a set rate, surfaces metrics on a dashboard, and links evaluations to traces.** Sibling previews: **scheduled evaluations, red team scans, alerts.**
- **Evaluation runs are skipped at an hourly ceiling — default 100 per hour.**
- **Conversation-level evaluation lookback is capped at 7 days (168 hours).**
- **Two sampling strategies: `random_sampling` (default) and `smart_filtering`, an undocumented service-managed heuristic biased toward "interesting" traces.**
- **Evaluation levels `turn` and `conversation` cannot be mixed in one run.**
- **Rubric evaluators score weighted 1–5 dimensions normalised to 0–1**, and are recommended as the *primary* quality measure, paired with built-ins for safety and groundedness.
- **Human evaluation exists as a product feature — and no agreement between any built-in evaluator and human judgement is published.**
- **SFT for most cases; DPO for preference and tone with exactly two completions per item and no reward model; RFT for objective domains with graders, no system messages, and a reference answer as the final message. Techniques stack.**
- **Fine-tuning data floor is 10 examples; recommended start 50; hundreds to thousands for production; RFT ceiling 50,000; files JSONL, UTF-8 with BOM, under 512 MB.** **All of these are unsourced.**
- **Workflow patterns: human-in-the-loop, sequential, group chat in the portal; sequential, concurrent, handoff, group chat and magentic in the framework. A workflow can be exposed as an agent.**
- **Handoff transfers ownership and full context; agent-as-tool retains ownership and controls what the sub-agent sees.**
- **A connected agent may hold privileges the parent lacks. The delegation edge is a privilege boundary.**
- **Publishing gives a stable endpoint and its own identity and RBAC scope — and project permissions do not transfer. Reassign after publishing.**
- **Content filtering: four harm categories × four severity levels, default medium for text and low for images, prompt shields and protected-material detection on by default, filtering synchronous and separately billed.**
- **Agent guardrails are preview, are block-only (no annotate-only mode), and fully override the model's guardrail. An omitted stage is an unscanned stage.**
- **Guardrail inheritance: custom → underlying model deployment's → DefaultV2 only if the deployment has none.**

## Method and evidence base
First-party product documentation with a definitional purpose, plus one community Q&A answer marked as such. **Definitional authority is not evidential authority**, and the separation is unusually stark here. The documentation is an accurate account of what the platform is configured to do; it is not evidence that doing so produces any outcome.

There is no adoption data, no failure-rate data, no comparative benchmark against any non-Microsoft platform, and no outcome study behind any recommendation. The numbers that do appear fall into two classes. **Engineering constants** — 15-minute idle timeout, 20 GiB disk, 3000 RU/s, 100 active revisions, port 8088, 90-day portal window, 168-hour lookback — are contractual facts about the product, true until the product changes, and useful only when pinned to a date. **Guidance heuristics** — start with 50 examples, doubling the dataset gives a linear quality increase, investigate below a stated success rate, latency above a stated threshold suggests throttling — are asserted without any source at all. **The second class is the dangerous one**, because it is written in the register of finding while carrying the warrant of opinion. Every number in this note, of either class, is **forbidden downstream**; the wiki asserts no magnitudes.

The documentation's most valuable evidential property is its candour about its own limits: the network-isolation warning on basic setup, the shared-responsibility language repeated on almost every page, the guardrail-override example that shows a hole rather than hiding it, the connected-agent security paragraph that names privilege escalation explicitly, and the fine-tuning warning that unpruned data can make a model worse. **A vendor that documents its own failure modes is giving you something usable. That is not the same as giving you evidence.**

## Vocabulary the sources introduce
- **Prompt agent** — declaratively defined, fully managed runtime, no agent compute.
- **Hosted agent** — your containerised code on managed compute, with its own identity and endpoint.
- **Micro VM** — the lightweight virtual machine running one hosted agent.
- **Session** — sandbox compute plus persisted filesystem (`$HOME`, `/files`), identified by `agent_session_id`.
- **Conversation** — durable message, tool-call and response history stored in Foundry, reachable across channels.
- **Version** — an immutable snapshot of an agent; only runtime-affecting changes create one.
- **Revision** — the deployment unit; versioned or non-versioned (metadata-only).
- **Responses protocol / Invocations protocol** — platform-managed conversation history versus none.
- **AgentSchema / AgentDefinition / AgentManifest / ContainerAgent** — the open definition specification and its three shapes.
- **Capability host** — the connection point through which standard setup binds your own Storage, Search and Cosmos DB.
- **Single-tenant data proxy** — the per-project networking component through which all tool calls route.
- **Toolbox** — a curated tool bundle exposed as one MCP-compatible endpoint.
- **Tool search** — runtime tool discovery that keeps a large toolbox out of the model's context.
- **Knowledge source / knowledge base** — the content pointer and the retrieval orchestrator above it.
- **Foundry IQ** — the managed knowledge layer with automated chunking, embedding, permissions and query decomposition.
- **Work IQ** — Microsoft 365 signal exposed through a CLI and an MCP server.
- **Span, attribute, semantic convention, exporter** — the OpenTelemetry vocabulary Foundry adopts wholesale.
- **`gen_ai.agent.id`** — the span attribute that attributes telemetry to a registered agent.
- **Server-side versus client-side tracing** — automatic platform capture versus instrumented application capture.
- **Content recording** — the off-by-default setting that puts message content into traces.
- **Continuous / scheduled evaluation, red team scan** — sampled production scoring, scheduled batch scoring, adversarial scanning.
- **`smart_filtering`** — the undocumented heuristic that biases trace sampling toward interesting conversations.
- **Evaluation level** — `turn` or `conversation`; not mixable within a run.
- **Rubric, dimension, weight** — the custom quality instrument and its parts.
- **Grader** — the RFT scoring function: string check, text similarity, model-based, or multi-grader.
- **Guardrail inheritance and override** — the resolution order, and the total-override rule.
- **Agent identity versus project managed identity** — the agent's runtime identity versus the platform's infrastructure identity.
- **Agent Application / deployment** — the legacy publishing objects, being collapsed into the agent object.

## What to remember
- **A hosted agent is a fleet of single-session sandboxes, not a service with replicas.** Everything about its cost and its lifecycle follows from that one sentence.
- **Sizing describes one session; cost is sizing times concurrency.** The most expensive mistake available here is generous defaults.
- **Session is not conversation.** Compute state and message history are separate objects with separate lifetimes, and under one protocol the platform keeps no history at all.
- **The deployment type does not change what inference does. It changes where the data is processed and how you pay.**
- **Provisioned buys predictability, not speed.**
- **A tool abstraction with exceptions is not an abstraction yet.** Find the exceptions before you design around it.
- **Managed retrieval removes your visibility of the failure modes, not the failure modes.**
- **Server-side tracing is free of code changes and off by default in content.** You will get the shape of every run and none of the words until you decide otherwise — and that default is correct.
- **A trace is where the reasoning becomes inspectable and where the sensitive data goes.** Both are true at once, and the second is why redaction is a design step rather than a cleanup.
- **The portal shows 90 days; Foundry owns no retention period.** How long an agent's reasoning is kept is a decision you make in Application Insights, or fail to make.
- **A sampled quality metric with an undocumented sampling heuristic and an hourly ceiling is not a rate.** Know your denominator before you report a number.
- **The platform gives you an instrument for collecting human judgements and publishes no agreement between its own judges and yours.** Measure it yourself or do not cite it.
- **Fine-tuning guidance is plentiful and unsourced.** Keep the ordering, discard the numbers.
- **A delegation edge is a privilege boundary.** A connected agent can do what its parent may not.
- **Guardrail override is total.** A stage you did not name in the agent's guardrail is a stage nobody scans, whatever the model's guardrail says.
- **Project permissions do not survive publishing.** The handover has a step that is easy to miss and silent when missed.
- **Four first-party surfaces disagreed about the agent definition file on one day.** Pin every platform claim to a host, a version and a date, or do not make it.

## How to teach it
- **Lecture:** teach session-scoped isolation as an architecture before naming the product. Ask what changes about cost, state and failure when the unit of scaling is a conversation rather than a server.
- **Lecture:** put the four disagreeing pages about the agent definition file on one slide, dated. Do not resolve the disagreement. Ask what a citation would have to contain to survive it.
- **Lecture:** teach the guardrail override rule with the documentation's own worked example, and ask which stage is unprotected before revealing the answer.
- **Lab, highest value in the topic:** take one real agent run, open the trace, and reconstruct what happened without re-invoking anything. Then change one input and reconstruct again. Students should arrive at the difference between a trace and a log unprompted.
- **Lab:** run the same agent with content recording off, then on. Compare what each trace can and cannot answer, and write the redaction rule that makes the second one shippable.
- **Lab:** hand-label thirty stored responses using the human-evaluation feature, run a built-in evaluator on the same thirty, and report the disagreement rate. **This is the validate-the-validator exercise from [agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md), now runnable entirely inside the platform, and the documentation's continued silence on agreement is exactly why it must be run.**
- **Lab:** configure continuous evaluation, then work out what proportion of traffic the reported score actually covers once the sample rate and the hourly ceiling are both accounted for. Report the coverage alongside the score, always.
- **Lab:** build the same small agent twice, once as a prompt agent and once as hosted, and compare time to first working version against control, testability and monthly cost at a stated concurrency.
- **Lab:** deliberately misconfigure an agent guardrail so tool calls are unscanned, then demonstrate the gap. Fix it and demonstrate the fix. This is a safety lesson taught by observation rather than assertion.
- **Assessment:** require every platform claim in a defended artefact to carry host, version, page and date. **Claims about the definition file that cite one page should be challenged in the defence**, because a correct-looking citation to a deprecated page is the failure this material exists to teach.
- **Assessment:** require any reported quality number to state its sampling strategy, its coverage, its evaluation level, its thresholds and its measured judge agreement. A number without those five is not a result.
- **Assessment:** ask orally what the trace retention period is. The correct answer is that Foundry does not have one, and that someone must own the Application Insights configuration. A student who answers "ninety days" has read the portal and not the platform.
- **Framing:** **the most perishable material in the research set, and it perished visibly while being read.** Assess the reasoning, the derivations and the pins. Assess no syntax and no number.

## Limits and cautions
- **Verification depth is uneven and is recorded per claim in the section below.** Four sources were read in full — three Learn pages and one local skill. Everything else came through search excerpts across roughly thirty pages, with tables frequently truncated. **Do not treat any list here as exhaustive.**
- **Several consulted pages are explicitly superseded and still render.** The threads-runs-messages page is the classic variant, with agents (classic) documented as **deprecated and retiring 31 March 2027**. The continuous-evaluation page is a classic variant pointing at a new-portal replacement. The agent-applications page is labelled the legacy publishing experience with a migration guide beside it. **The `agent.yaml` schema reference documents a model its own first paragraph calls deprecated.** A page that renders is not a page that is current.
- **Preview status is pervasive and load-bearing.** Agent guardrails, workflows, human evaluation, rubric evaluators, conversation-level evaluation, scheduled evaluations, red team scans, alerts, tool search, skills, A2A, client-side tracing, external-agent registration, and tracing for workflow and external agents are all marked preview. Preview features carry no SLA and are explicitly not recommended for production.
- **Portal names, RBAC role names and product names are actively churning.** The documentation itself notes that Foundry RBAC roles were recently renamed and that old names may still appear. Navigation instructions differ between classic and new portals on nearly every how-to page.
- **The `agent.yaml` contradiction is unresolved in this note and should not be resolved by guessing.** Four first-party surfaces disagree. **Verify against the specific tooling version you are running before writing a line of YAML.**
- **One item is a Microsoft Q&A answer, not documentation** — the claim that the default guardrail policies cannot be edited or deleted and carry no indirect-attack controls. It is recorded as community content with a Microsoft respondent and should not be cited as published guidance.
- **The locally installed skill is a workflow router, not a source.** It was read to see what workflows are recommended and where they diverge from documentation. **No platform fact in this note rests on it.**
- **Vendor documentation is commercially framed.** It compares Microsoft options with each other, never against alternatives, and its guidance is reasoned assertion rather than tested finding.
- **Cost figures, threshold heuristics and dataset-size recommendations appear throughout and are all unsourced.** Every number in this note is forbidden downstream.
- **This note covers the agent build and runtime surface only.** Capacity and provisioned throughput are at [provisioned-throughput-for-foundry-models.md](/research/06-microsoft-platform/provisioned-throughput-for-foundry-models.md); gateway concerns at [apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md); retrieval and access control at [azure-ai-search-and-acl-patterns.md](/research/06-microsoft-platform/azure-ai-search-and-acl-patterns.md); estate posture at [purview-dspm-for-ai-and-defender-ai-spm-docs.md](/research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md).
- **Teaching this risks producing graduates fluent in one vendor's console.** The mitigation is the same as elsewhere in this repository: extract the mechanism, discard the surface, and assess only the reasoning.

### The silences, stated explicitly
Each of the following was searched for deliberately. **An absence recorded here means a search was run and returned nothing, not that nothing was looked for.**

- **No agreement between any built-in evaluator and human judgement is published.** No correlation, no kappa, no calibration study, no threshold rationale. **Confirmed by a dedicated search**, which returned the human-evaluation feature, the rubric documentation and the evaluator catalogue, and no agreement figure. The platform now ships the instrument for collecting human labels and publishes no comparison of its own judges against them. **The existing prohibition on asserting such agreement is correct and should stand.**
- **No measure of tracing completeness exists.** The documentation says what tracing captures. It says nothing about what proportion of an agent's decisions appear in a trace, whether any step can go unrecorded, what sampling does to completeness, or how a reader would detect a missing span. **A trace is presented as a record and never as a sample, and no page states the difference.**
- **No Foundry-owned retention period for traces or conversations.** This is the most nuanced absence and must not be overstated. **There is a stated ninety-day portal window for out-of-the-box traces, and there is an explicit statement that retention and sampling follow your Application Insights and Log Analytics configuration.** For threads, the guidance is to plan your own strategy and no default is given. **So: a display window is published; a retention policy is not; the obligation is delegated to a resource you own.**
- **No evidence that continuous evaluation catches anything manual review would not.** No study, no comparison, no false-negative rate, no worked case. The stated benefit — identify and troubleshoot issues early — is a claim about what the feature is for, not a finding about what it does.
- **No documentation of the `smart_filtering` heuristic.** It is described as service-managed and as biased toward interesting traces. What it optimises, how it decides, and what it systematically misses are all unstated. **A sample drawn by an undocumented rule has no reportable coverage.**
- **No measure of how often an agent's self-correction loop converges.** Traces capture retries. Nothing published says how often retrying succeeds, how often a loop terminates without converging, or how often an agent reports completion on work that is wrong. **This confirms the documented silence already named in [S049](/wiki/seminars/S049.md)'s platform anchor.**
- **Fine-tuning data guidance exists in quantity and carries no evidence whatsoever.** The expectation that no guidance would be published is **wrong** — floors, starting points, production ranges and ceilings are all stated. **What is absent is any source, study or curve behind any of them, including the explicit claim that doubling the dataset produces a linear increase in model quality.** Guidance without warrant is a different problem from silence, and arguably a worse one.
- **No published effect of Toolbox, tool search or Foundry IQ on any outcome.** The arguments for them are architectural and plausible. No measurement of token cost, selection accuracy or retrieval quality accompanies them.
- **No detection rate, false-positive rate or bypass rate for any guardrail or content filter.** Categories, severities and defaults are documented. Efficacy is not, anywhere.
- **No published agreement between the monitoring dashboard's operational heuristics and any outcome.** The suggested investigation thresholds have no stated derivation.
- **No comparative data of any kind against non-Microsoft agent platforms**, and none should be inferred from the absence.
