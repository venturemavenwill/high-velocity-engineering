## At a glance
- GitHub Copilot launched **June 21, 2022**; the course frames it against a broader AI timeline (1956 term "artificial intelligence" coined → 1997 "machine learning" coined when IBM Deep Blue beat Garry Kasparov → 2012 "AlexNet" deep-learning breakthrough → 2017 "deep learning" coined → 2021 generative AI era).
- Copilot uses two OpenAI models: **GPT-3.5** for in-editor code completions (fast, cheap, ~**16,000 tokens**, trained to **September 2021**) and **GPT-4o ("Omni")** for Copilot Chat (~10x more powerful/accurate, ~**128,000 tokens**, trained to **October 2023**).
- Three (or four) commercial SKUs: **Individual** ($10/mo or $100/yr), **Business** ($19/mo/seat), **Enterprise** ($39/mo/seat), plus **Business for non‑GitHub Enterprise users** (custom pricing, lets you bring your own identity provider). Enterprise requires GitHub Enterprise Cloud.
- Every prompt/completion passes through a **proxy service** both outbound (toxic-language filter, relevance/intent classifier, PII scrubbing, prompt-injection defense) and inbound (code-quality/vulnerability check, PII scrubbing, public-code/IP filter). Prompts and completions are **never used to train future models** — they are discarded after use, though GitHub retains anonymized usage telemetry for about **two years**.
- Context comes from the **open editor tab plus "neighboring tabs"**; tokens are converted into embeddings and matched against a **three-dimensional vector database** to predict the most probable next tokens.
- **GitHub Copilot Workspace** (in beta at recording time, built by the GitHub vNext team) extends Copilot from single-file, single-suggestion completions to a full ideation → plan → multi-file implementation → validate → pull-request workflow, reasoning across an entire indexed repository using chain-of-thought planning.
- Prompt engineering is distilled into the **4S framework** (Single, Specific, Short, Surround) plus zero-shot, one-/few-shot, and "let's think step by step" (chain-of-thought) techniques.
- Six **Responsible AI** principles (Microsoft): fairness, reliability & safety, privacy & security, inclusiveness, transparency, accountability — explicitly called out as exam content.
- "Every Copilot needs a pilot" — the recurring exam-relevant theme: the developer is always accountable for reviewing, testing, and accepting AI-generated code; Copilot is an assistant, not an autonomous author.

### 1. Getting Started: GitHub Copilot
**What it covers** — The history of AI leading up to generative AI and Copilot; core AI vocabulary (LLM, tokens, embeddings, prompts, completions, semantic kernel); what Copilot is and isn't; system requirements and the three SKUs at a glance; the GPT-3.5 vs GPT-4o split; how a prompt flows through the proxy service to the LLM and back; GitHub's Trust Center pillars; Copilot agents (`@workspace`, `@azure`, `@github`, `@terminal`, `@vscode`, custom agents); slash commands (`/explain`, `/tests`, `/fix`, `/new`, `/help`); hashtag commands (`#file`, `#selection`, `#editor`, `#terminalSelection`, `#git`, `#codebase`); a long live demo ("flight demonstration") in a Wright Brothers-themed C# API.

**Key concepts**
- AI timeline: 1956 "artificial intelligence" coined → ~1990s "big data"/internet era → 1997 "machine learning" coined (IBM Deep Blue beats Garry Kasparov) → 2012 "AlexNet victory" (ImageNet challenge, first deep-learning breakthrough in vision) → 2017 "deep learning" coined → 2021 generative AI era → June 21, 2022 GitHub Copilot GA.
- Vocabulary: **Open AI** (Azure-hosted AI-as-a-service), **ChatGPT/GPT** (a transformer-based LLM), **prompts**, **prompt engineering**, **tokens**, **embeddings** (numerical word representations arranged in an array), **completions**, **fine-tuning**, **semantic kernel** (uses LangChain-style APIs to build word/embedding references), **LLM**.
- Three-dimensional vector database — how the LLM looks up tokens to predict the next most probable word/token (example: "a car drives" → "on the road").
- Copilot vs ChatGPT: ChatGPT is a separate browser experience requiring copy-paste with no persistent code context and token-limited; Copilot is built into the editor, trained on "tens of millions" of code + historical resources (e.g., Wikipedia), keeps you "heads down" in your code, and adapts to your coding style.
- Survey stats (GitHub developer surveys, quoted verbatim in the session): **96%** of developers say Copilot helps with repetitive/boilerplate tasks; **88%** say it helps them feel more productive / accelerates innovation; **74%** report being happier/more satisfied developers.
- Requirements: a GitHub account, a Copilot license, and a supported IDE (or the CLI). Visual Studio Professional/Enterprise: Copilot ships baked in. VS Code, JetBrains/IntelliJ, Neovim, Azure Data Studio: require installing **both** the GitHub Copilot extension and the GitHub Copilot Chat extension, kept current via auto-update.
- Licensing at a glance (as taught in Session 1): **Individual** $10/month — code completions, comments-to-code, Copilot in the CLI, mobile, github.com, PR summaries. **Business** $19/month — adds org policies (e.g., **Public Code Filter**, allow/disallow copyrighted matches >150 characters). **Enterprise** — adds **Copilot Knowledge Base search** (query internal repos/markdown behind your firewall) and the ability to **fine-tune/privately train the LLM** behind your firewall.
- GPT-3.5 (completions engine): ~16,000 tokens, fast/cheap, trained to Sept 2021. GPT-4o "Omni" (chat engine): ~128,000 tokens, ~10x more powerful/accurate, slower but more thorough, trained to Oct 2023.
- How Copilot works: context = open tab + neighboring tabs → prompt assembled → sent through the **proxy service** (toxic-language filter, relevance test — "is this about code?", PII stripping — credit cards/phones/emails, prompt-injection/hacking protection) → LLM in a regional Azure data center → completion returned through the proxy again (code-quality/security check for SQL injection/XSS, toxic-language filter, PII strip, **Public Code Filter** for matches >150 characters) → ghost text appears in the editor.
- GitHub Trust Center four pillars: (1) code/customer data is never saved or used for future training; (2) secure development — prompts/completions filtered at the proxy for security issues/PII; (3) personal data collection — GitHub retains ~2 years of anonymized usage data (IDE used, number of prompts, number of suggestions, acceptance rate) tied to product improvement, not to individuals; (4) intellectual property protection — the >150-character public-code filter, controlled by the org's GitHub admin.
- Agents (VS Code, invoked with `@`): `@workspace` (traverses your local file structure/repo for context — supports multiple open workspaces), `@azure` (preview; assists with Azure deployment, resource groups, App Service, Kubernetes), `@github` (assists with GitHub account data — PRs, issues), `@terminal` (helps with shell/PowerShell/bash commands), `@vscode` (VS Code product help), and custom agents (buildable to enforce your own team's guidelines).
- Slash commands: `/explain`, `/tests`, `/fix` (also `@workspace /fix` for bigger fixes), `/new` (scaffold a brand-new project from a natural-language description), `/help`.
- Hashtag commands: `#file` (point Copilot at a specific file), `#selection` (laser-focus on highlighted code), `#editor` (whatever is visibly on screen), `#terminalSelection` (focus on terminal output), `#git`, `#codebase` (entire project context).
- Multi-suggestion cycling: `Ctrl+Enter` in VS Code opens the "GitHub Copilot Suggestions" pane showing all completions returned by the LLM so you can pick the best one.
- New/recent feature demoed: **"Fix Test Failure"** — `@workspace fix test failure` analyzes a failing test, inspects the related workspace files, proposes a fix, and lets you apply-and-rerun.
- Use cases highlighted: boilerplate/scaffolding code, mobile dev, documentation generation, unit-test/data generation, basic functions (Python/JSON/API wiring), PowerShell scripts, Docker/devcontainer/Kubernetes configs, CI/CD pipeline generation (GitHub Actions or Azure DevOps, with Bicep or Terraform IaC), performance troubleshooting, and refactoring (extracting methods, reducing cyclomatic complexity).

### 3. GitHub SKUs
**What it covers** — A complete walkthrough of GitHub Copilot's commercial plans (Individual, Business, Enterprise, and Business for non-GitHub Enterprise users), pricing, free-tier eligibility, billing setup (personal, organization, and enterprise level, including Azure metered billing), and a full feature-by-feature comparison building up from Individual → Business → Enterprise, plus a live demo of Individual-tier features (inline completion, inline chat, chat in the IDE, Copilot in the CLI, chat on github.com, PR summaries, GitHub Models).

**Key concepts**
- Four plans: **Individual** ($10/month or $100/year, sometimes free), **Business** (€/$19/month/seat, centrally managed), **Enterprise** ($39/month/seat, requires GitHub Enterprise Cloud), **Business for non-GitHub Enterprise users** (custom pricing; lets you bring your own identity provider).
- Individual and Business use personal GitHub accounts; Enterprise can use an **EMU (Enterprise Managed User)** account.
- Free Individual-license eligibility: verified students (must be enrolled at a school/university/college, 13+, verifiable email or documentation), verified teachers/faculty/researchers (documentation from the institution), and maintainers of popular open-source repositories (discoverable via the Copilot entry in your github.com profile menu).
- Billing setup: Individual — 30-day free trial requiring payment info (credit card or PayPal) up front; cancel within 30 days for no charge. Organization (Business) — set up billing at org settings level, then assign seats individually or via a GitHub team, or let members self-request access for owner approval; upgrading an existing Individual subscriber to Business cancels the remainder of their personal plan with a pro-rated refund. Enterprise — billing configured at the enterprise level, Copilot enabled per organization; **metered billing via Azure** is also possible (links your GitHub org/enterprise to an Azure subscription for consolidated billing), available for GitHub Free (org) and up, but **not** for personal accounts.
- Individual-tier feature set (all subsequently inherited by Business and Enterprise): supported across Visual Studio, JetBrains, Vim/Neovim, Azure Data Studio regardless of license; **code completion**; **Inline chat** (triggered by a keybinding, e.g. Ctrl+I, lets you type natural-language intent for larger changes than autocomplete alone); **Chat in the IDE** (most interactive, full back-and-forth conversation); **Copilot in the CLI** (via `gh` extension `github/gh-copilot`; explains/suggests across general shell commands, GitHub CLI commands, and Git commands); **Chat in the GitHub mobile app** (iOS and Android, via the GitHub app, not a separate Copilot app); **Public Code Filter** (blocks/allows suggestions matching ≥150 characters of public code — this moved from Business-only to Individual by the time of recording); **Copilot on github.com** chat (also moved down to Individual); **PR summaries**; **GitHub Models** (a marketplace for experimenting with available AI models, e.g., a GPT-4o mini playground, before committing to an API/paid model in your own app).
- Business-tier additions: **IP indemnification** from GitHub for unmodified suggestions when the public-code filtering feature is enabled (this shifts copyright responsibility from customer to GitHub); ability to **exclude specific files/paths** (e.g. `/secrets/*`) from being used as Copilot context, set at the organization level; **organization-wide policy management** covering feedback collection, preview-feature access, chat-in-IDE toggle, chat-in-mobile toggle, Copilot-in-CLI toggle, Copilot Extensions toggle, public-code-detection allow/block, and Copilot access to Bing (lets Copilot answer with information outside the LLM's training data, e.g. distance between two cities); **Audit Logs** (two event types: settings/policy changes, and seat assignment/cancellation changes — each with timestamp and actor; filterable specifically to "Copilot activity"); **usage reporting** via organization settings → Copilot → Access Management (per-user last-used date, exportable to CSV with login, status, last usage date, last editor used); a **REST API** (Business/Enterprise only) for user-management (assign/cancel seats, list seat holders) and usage metrics; **increased GitHub Models rate limits** (an example "low" tier shown: Individual 15 requests/min, Business 15 requests/min but higher requests/day, Enterprise 20 requests/min — see the full table under "SKU comparison" below, reconciled with Session 5's slightly different published numbers).
- Enterprise-tier additions: **Knowledge Base** (index one or more repositories so Copilot Chat on github.com can answer questions scoped to that knowledge base); file-exclusion configured at the **Enterprise** level (instead of organization level, same underlying mechanism); **custom models** (fine-tune on top of the base Copilot LLM using your own codebase — most useful for less-publicly-represented programming languages, custom/internal frameworks or libraries, or company-specific coding standards; works better with larger codebases since a small custom dataset has little influence); **Copilot Code Review Assistant** (a reviewer can ask Copilot to explain a PR description and suggest a review, surfacing issues a human reviewer might miss).
- FAQ addressed explicitly: **Is GitHub Enterprise Server (self-hosted/offline) supported for Copilot?** No direct ingestion of the full LLM is possible offline; two workarounds: (1) give every employee a personal GitHub.com account and assign them a cloud Business or Enterprise Copilot license (an empty cloud organization is enough just for licensing), or (2) use "Copilot for non-GitHub Enterprise Cloud users," which requires contacting GitHub directly.

### 4. GitHub Copilot Agent Mode
**What it covers** — An extended, mostly live, two-presenter demo of **GitHub Copilot Workspace** (branded in this course as "GitHub Copilot Agent Mode" but referred to throughout the transcript by its actual product name, GitHub Copilot Workspace), built by the GitHub vNext team and in beta/waitlist at recording time. Demonstrated end-to-end against a deliberately messy JavaScript "Battleship" game repository: starting from a natural-language description or an existing GitHub issue, generating and revising a step-by-step plan, implementing multi-file code changes, opening the result in Codespaces or local VS Code, running tests, iterating via a "brainstorming" chat tab, and creating/updating a pull request — including generating a GitHub Actions CI/CD workflow and a GitHub Pages deployment from scratch.

**Key concepts**
- **GitHub Copilot Workspace** — accessed at `copilotworkspace.githubnext.com` or via a "Open in Workspace" button in a repo/issue; can start from an existing repository, from an existing **issue**, or completely from scratch (bootstrap an entirely new app from a text description).
- **GitHub vNext team** — the internal "special" GitHub team that experiments with future modalities of software development; some vNext experiments graduate into shipping product features (e.g., Copilot Voice became a plain VS Code extension), others are retired ("we tried, didn't work").
- **Plan** — Workspace analyzes your prompt/issue, searches the **indexed repository**, decides which files are relevant, and produces a functional (not yet code-level) step-by-step plan you can edit: add/remove files, add/remove/indent plan items (indenting creates a **parent/child relationship** so both are evaluated together — flat/sibling items are evaluated independently), and add acceptance criteria or test-case requirements before generating code.
- **Chain-of-thought reasoning** — explicitly named as the underlying technique Workspace uses (reasons across the whole indexed repo in multiple LLM calls rather than a single limited-context prompt, unlike a normal `@workspace` chat call which is bounded by context size).
- **Implement/update files** — once you approve the plan, Workspace generates code changes across every affected file simultaneously (a diff view per file), rather than the file-by-file way a developer normally works.
- **Brainstorming tab** — a chat-style conversation scoped to the current plan; you can ask questions, propose revisions, and "add to task" to push a discussion point into the actual plan.
- Multi-modal / bidirectional sync: you can move between the browser Workspace session, a **Codespace**, and **local VS Code** (via the Copilot Workspace VS Code extension) and changes sync across all of them; you can also run a **Commands** tab (an embedded terminal backed by a hidden Codespace) to install dependencies and run build/test/lint scripts directly from Workspace.
- **Pull request generation** — Workspace can open a PR directly, auto-generate a title and description "translated" from the plan, and a reviewer can open the same PR's Workspace session to continue iterating on the plan and push updates as new commits.
- Refactoring-by-intent — expressing *why* you want a change (e.g., "make this easier to test" or "make it easier for multiple people to work on separate files") rather than only *how* (e.g., "implement the repository pattern"), which the presenters argue produces similar/better outcomes and is a more sustainable prompting habit.
- Safer big-refactor pattern demonstrated: extract the existing logic into a new class untouched (V1), implement a second class with a new domain model (V2) against the same interface, run the same test suite against both, then swap the implementation via configuration/DI, and finally delete V1 — broken into separate reviewable commits/PR updates rather than one giant change.
- Explicit exam-relevant callout: Workspace can also scaffold **CI/CD** (GitHub Actions workflows, replacing an existing Azure Pipelines YAML), **Dependabot** configuration, and **GitHub Pages** deployment — all generated the same plan → implement → iterate way, and all subject to the same **model training cutoff date** limitation (the model used in the demo was noted to be about a year old, so it defaulted to an older `actions/checkout`/`actions/upload-artifact` version until told to update).
- Limitations/caveats stressed repeatedly: this is still LLM-generated code requiring human review; large or vague single-shot refactors ("refactor everything") can produce big, hard-to-review diffs; the tool doesn't (yet) automatically feed failing test results back into the next iteration; it cannot read repository *settings* (e.g., it enabled a GitHub Pages workflow but the human still had to actually turn on Pages in repo settings); indentation/hierarchy in the plan materially changes how Copilot evaluates related requirements together.

**Detailed notes** — Rob Bos (DevOps Consultant, Azure & GitHub Trainer) and Jesse Houwing (Chief Trainer, Xebia) co-present. They recap Sessions 1–3 before introducing GitHub vNext's `githubnext.com` site and the Copilot Workspace waitlist. They open the "BattleJSip" (Battleship in JavaScript) sample — deliberately bad code used in their own Scrum/dev classes, where "it takes four humans about six hours" to get a working version, largely because everything lives in one file with poor naming. Starting from a blank prompt ("the game doesn't finish... it looks like it doesn't check whether all ships have sunk... let's fix that"), they show Workspace searching the indexed repo, deciding a new "all ships sunk" check function is needed, proposing where to wire it in (including the underlying test file), and letting the user add/remove/edit plan items (including adding an acceptance-criteria child item for a related edge case) before clicking "update files" to generate the diff across every affected file at once. They discuss reviewing before merging — "you can, yeah, pray" — versus opening the branch in a Codespace or local VS Code to actually run tests first, then creating a PR with an auto-generated description built from the plan. ## Prompt engineering reference
1. **Be Single** — focus each prompt on one well-defined task or question at a time.
2. **Be Specific** — give explicit, detailed instructions; vague asks (e.g., "return bad request if it exists" without saying "by name" vs "by ID") get Copilot guessing.
3. **Be Short** — stay concise once you're specific; don't bury the model in irrelevant extra detail.
4. **Surround with context** — use descriptive file/variable/function names, and keep only the relevant files/tabs/selections open — Copilot uses the open tab plus neighboring tabs as context.
5. **Provide clarity** — write concrete, single-focused prompts (e.g., "write a Python function to filter and return numbers from a given list").
6. **Provide context with details** — give clear instructions plus examples, expected inputs/outputs, and technical or business requirements.
7. **Provide examples for learning** (few-shot) — show sample input/output pairs so Copilot understands the pattern you want.
8. **Assert and iterate** — don't expect a perfect result on the first try; refine the prompt or continue the conversation in chat until you get what you need.
9. **Manage neighboring tabs deliberately** — open only what's relevant to your current goal; close unrelated files so they don't pollute the context.
10. **Zero-shot learning** — give a direct instruction or descriptive comment about exactly what the next line(s)/method should do, with no examples provided.
11. **One-shot / few-shot learning** — supplement your ask with concrete examples, input/output samples, or explicit technical/business requirements.
12. **Chain-of-thought ("let's think step by step")** — explicitly (or, per some presenters, implicitly by default) prompt the model to reason through sub-steps before producing a final answer; this is the same mechanism GitHub Copilot Workspace uses internally to plan multi-file changes.
13. **Use `#file` / `#selection` / `#editor` / `#codebase` / `#terminalSelection`** to laser-focus Copilot's context onto exactly the code or output you mean, rather than letting it guess from whatever happens to be visible.
14. **Model after an existing example** — point Copilot at an existing file (e.g., `#file PlanesControllerTests.cs`) and explicitly ask it to mirror that file's style/framework when generating a new one, rather than letting it invent its own conventions.
15. **Prefer intent over instruction for big changes** — state *why* you want a change ("make this easier to test," "make it easier for multiple people to work on separate files") rather than only prescribing the mechanical *how*; this was shown to produce comparable or better results and is more forward-compatible as the model reasons about the best implementation.
16. **Break large asks into safer incremental steps** — for big refactors, explicitly instruct the model to preserve old behavior in place, add new behavior alongside it, test both against the same suite, and only then remove the old path — rather than requesting one giant all-at-once change.
17. **Use custom Copilot instructions** (VS Code settings) to bake in standing preferences — e.g., "always use library version X" — so you don't have to repeat them every prompt.
18. **Iterate in the chat, not just the prompt box** — highlight a Copilot-generated result and ask a follow-up ("is this what I meant? Is there a better way?") rather than starting over from scratch.
