# WP-003 — Representation and the Leaking Abstraction

**Seminar day:** [S003](wiki/seminars/S003.md) · **Module:** [M01](wiki/modules/M01.md) · **Quarter:** [Q1](wiki/quarters/Q1.md)
**Strands:** CF · MS · SY · **Complexity class:** 1
**Platform anchor:** GitHub Copilot agent mode; custom instructions as executable specification · **MCP servers:** Microsoft Learn MCP Server

## Abstract

This paper defends teaching numeric precision, text encoding and time representation together, as three instances of one idea, rather than separately as three topics. The argument rests on the conditions for abstraction: a principle stated once and instantiated once is learned as a fact about that instance, whereas the same principle instantiated across surfaces that share no surface features is available for transfer. The day's target is not knowledge of any encoding but a durable interrogative habit — ask what the representation discarded — which is the same move later required of an embedding at S057, a benchmark score at S059 and a monitoring signal at S079. The paper further defends requiring students to state what their own proposed fix discards, on the grounds that this is the only step that distinguishes understanding the thesis from memorising a defect catalogue. **It adds a fourth instantiation the original design did not have: a specification, which discards, and which fails in exactly the way the day predicts when the thing it discarded was the checkable condition.** That instantiation is executed rather than argued, and it is the day on which the programme's claim that an instructions file is a specification stops being an analogy. The paper concedes that the day carries the highest perishability exposure in Q1, and that its central transfer claim rests on a mechanism whose scope conditions the design cannot verify.

## 1. The instructional problem this day must solve

Students hold representations as identities. A floating-point value *is* a number; a string *is* text; a timestamp *is* a moment. Each identification is false, and each is false silently: the representation behaves as expected across the overwhelming majority of inputs and diverges only in cases the student has no reason to construct.

This produces a characteristic professional failure. The engineer is not ignorant — asked directly, most will acknowledge that floating point is imprecise — but the knowledge is inert. It is not attached to the moment of use, so it does not fire when a comparison is written or a duration computed. The deficit is one of *triggering conditions*, not of content, and content-delivery instruction does not fix it.

The day's second problem is larger and is the reason it appears in week three rather than in a later systems course. The interrogative habit it installs is the programme's most widely reused single move. An embedding discards; a benchmark score discards; a monitoring aggregate discards; an evaluation rubric discards; a handover document discards. Every one of those is S003's question in a different costume. If the habit is installed here, on cheap and unambiguous instances where the discarded property can be exhibited exactly, then the later days have something to retrieve. If it is not installed here, each later day must build it from nothing against much more expensive material.

Third, this is the day that closes the S001 phase 2 loop, and that placement is not incidental. The programme's founding demonstration is resolved on a day whose content is *what a representation conceals* — and the concealment in question is students' own confidence about their own learning. The parallel is stated to the cohort.

## 2. Entry state and prior knowledge assumptions

- **Two days of programme norms.** Prediction before attempt, public error, retrieval without marks.
- **A complete execution model from S002,** which matters more than it appears: a student who has traced memory accesses by hand has somewhere to put the claim that a value occupies a fixed number of bits.
- **Universal practical exposure, near-universal conceptual absence.** Every student has used all three representations. Very few can state what any of them discards.
- **Widely varying encounter with the failures.** Some students have been burned by a floating-point comparison; a few by a zone transition; almost none by normalisation. The phase 7 protocol exploits this variance rather than trying to level it.
- **An outstanding sealed prediction** from S001 phase 2, and an unresolved dispute from S002 phase 3, both of which this day is scheduled to close or explicitly defer.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Moderate and unevenly distributed.** Each individual fact — that decimal fractions have no exact binary representation, that a grapheme cluster may span several code points, that a civil-time difference is not a duration — has *low* element interactivity and can be stated in a sentence. The interactivity lives entirely in the relation between them, which is the day's actual content.

This produces an unusual and favourable design position. The day can afford three domains where a higher-interactivity day could afford one, because the marginal load of the second and third domain is small once the first is understood. That affordance is what makes the abstraction available at all: one domain would teach a fact, three teach a structure.

Load management is nonetheless active in three places. Phase 3's three representations are presented with a **single shared dataset and a single shared computation set**, so that all variation is in the representation and none is in the task. Phase 5's three defects are sequenced with fading rather than presented together. And the perishable library specifics are marked and explicitly excluded from what must be retained, which removes a substantial quantity of material from the retention burden without removing it from the illustration.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Interleaving across the three domains.* Phase 5's defects run numeric, textual, temporal in sequence rather than blocked by domain. This is the day's principal desirable difficulty and the mechanism by which the shared structure becomes discriminable.
- *Prediction before locating,* in phase 5 step 1, which converts debugging from search into hypothesis testing.
- *Naming the new loss,* in phase 5 step 4. Substantially harder than proposing a fix and the step most students would skip if permitted.
- *Free-recall retrieval in phase 2* including the S001 passage, at a six-day gap.
- *The one-minute silence* after the phase 2 reveal, which forces students to interpret the result unaided.

**Deliberately not selected.**

- *Withholding the common-structure sentence.* Phase 4 point 5 states the abstraction plainly. Requiring students to generate it would be productive-failure theatre: they have the instances from phase 3 and the abstraction is a single sentence whose value is precision, not discovery.
- *Exhaustive coverage.* The day does not attempt every representation pitfall. Three domains, a handful of failures each. Coverage would convert a structural day into a catalogue, which is exactly the shape being argued against.
- *Adversarial input construction.* Students are given failing cases; they do not construct them. Construction requires the schema the day is building and belongs at S009 and S035.
- *Any assessment stake on the perishable layer.* Explicitly prohibited by the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md).
- *Asking students to judge whether the vague instruction "worked".* Phase 5 step 6 requires three runs and all three reported. It does not require a verdict. A verdict from three runs is a sample size the day is not entitled to and would model the exact behaviour [S029](wiki/seminars/S029.md) exists to correct.

**The scope statement for the platform instance, in strong form.** The day teaches a simplification that students will carry directly into work nobody supervises: **that a rule an executor cannot check is not a rule, and that a checkable rule changes behaviour.**

That simplification is **safe** for writing an instruction whose conformance can be inspected in an output, for diagnosing why a stated rule produced non-conforming work, and for distinguishing a rule that was ignored from one that was never delivered. It is **unsafe** in four conditions and the day states all four.

- **As a guarantee.** A checkable instruction changed the output in the room's runs. Nothing in the documentation states an adherence rate, and none is published. **The claim the day is entitled to is that a vague rule reliably fails and a checkable rule can succeed** — which is an asymmetry, not a guarantee, and step 6's three runs are what stop it being taught as one.
- **Beyond one run.** Case B's failure is visible over three runs and invisible in one. A student who carries the simplification into a single-run test has an instrument that cannot detect the failure mode the simplification is about.
- **Where delivery is not verified.** Case D produced case A's output while conforming to nothing, because nothing was injected. **Absence of effect is not evidence of non-conformance.** The payload inspection is the only thing that separates the two and it is required in the specification.
- **On any version other than the one in front of the student.** The path, the front-matter key, the glob semantics, the injection behaviour, the output channel and — in one editor — the setting that must be switched on before multiple instructions files do anything at all are all one release's facts. The instructions-file path changed once during this design's own drafting, and that is the example the day uses.

The artefact element that makes the boundary checkable is specification item 3: **all three runs of the vague instruction are reported, including any that succeeded.** A student who reports only the failures has left the safe range and fails.

### 3.3 Engagement and motivational mechanism

The day's engagement mechanism is **personal implication**, and it is unusually strong here.

Phase 1 is a sequence of six items that look trivial, that students answer confidently, and that they get wrong. This is a surprise with a specific quality: it is not a surprise about an unfamiliar domain but about something the student uses daily and believed they understood. Situational interest triggered this way is more durable than novelty-triggered interest because it attaches to existing practice.

Phase 7 converts that into something stronger. The partner's task is to find a case *in the student's own recent work* where the discarded property mattered. They usually find one. The resulting list — *what we discovered we had been assuming* — stays on the wall for the quarter, which is a deliberate reminder of a personally-owned discovery rather than a taught fact.

The competence threat is real and is managed rather than eliminated. Six confident wrong answers in twenty-five minutes could read as humiliation. Three things prevent that: the items are constructed so that *everyone* gets most of them wrong, which is stated afterwards with the distribution shown; the instructor's phase 6 disclosure is a costly professional error of exactly this class; and the framing throughout is that the representation misled the student rather than that the student was careless.

Autonomy enters at phase 8's commitment, which is to check a representation in the student's own current work — chosen by them, not assigned.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Six items spanning all three domains, deliberately unblocked so that the shared structure is present from the first minutes without being named. Item 6's self-prediction is the calibration instrument. The items are chosen for confident-wrongness rather than difficulty: an item students find hard produces caution, and caution is not the target state.

**Phase 2 (20 min).** Two functions in one phase. The retrieval items maintain the expanding schedule on S001 and S002. The S001 passage item resolves the founding demonstration. The one-minute silence before discussion is the design's acknowledgement that an instructor-supplied interpretation of a result the students could reach themselves wastes the strongest interpretive moment available. If the demonstration fails — see §9 — it is discussed at the same length and with the same silence.

**Phase 3 (45 min).** One dataset, three representations, five shared computations, results that disagree. All variation is in the representation. Groups commit a ranking in writing, which is the productive-failure component: ranking demands a criterion and no group possesses one, so the ranking is made on grounds the group cannot defend and knows it cannot. That felt inadequacy is the preparation phase 4 point 5 resolves.

**The four executions hold the request, the dataset and the model constant and vary only the specification governing them.** That is the configuration under which the specification's effect is attributable, and it is the same matched-cases logic the representation half of the phase already uses — which is why the two halves belong in one phase rather than in two. Case D exists to make the mechanism visible rather than magical: without a non-matching glob in the set, students learn that instructions files sometimes work, which is a superstition. **The design's decision to make the B-versus-C gap the payload rather than the A-versus-C gap is deliberate.** A-versus-C shows that instructions do something, which nobody disbelieves. B-versus-C shows that *wording* does something, which is the day's actual claim and the one that transfers to every specification the student will ever write.

**Phase 4 (50 min).** Thesis, three instantiations, then the common structure. The ordering matters: the abstraction arrives fifth, after all three domains, because an abstraction stated before its instances is a definition rather than a generalisation. Point 5 is the day's single retrievable sentence and is written on the board and left there. **Points 6 and 7 are two further instantiations placed deliberately after the abstraction rather than among the three domains.** The three domains are matched on being unambiguously representational; a specification and a truncated search result are not, and putting them before point 5 would make the abstraction harder to reach rather than easier. Placed after, they are applications, and the load they carry is recognition rather than induction.

**Phase 5 (90 min).** Real data from the substrate, three defects, interleaved by domain, faded across the three. Step 1's committed prediction and step 4's new-loss statement are the two steps that carry the design; steps 2 and 3 are the ordinary debugging work between them. The choice of substrate data rather than synthetic data is deliberate — it is the day's only contact with the live system in Q1 apart from S001 and S009, and it makes the failure class concrete rather than academic.

**Steps 5 and 6 transpose the thesis into the specification register and are performed once, on the third defect only.** Doing them on all three would triple the phase's most expensive component for no additional variability, since the specification lesson does not vary by domain. Step 6 is the harder of the two and is the day's second-most-failed element by design: a student told that vague instructions fail will write one that fails and stop, and the requirement to report a run that *succeeded* is what prevents the exercise from confirming what the student was told. **The design is aware that this makes step 6 a compliance trap for the incurious**, and accepts it, because the alternative — asking for a verdict — would teach a worse habit.

**Phase 6 (40 min).** Instructor first, with a real substrate defect, and specifically with the observation that *the code looked correct*. That detail is the phase's content: this class of error is not caught by review, which is why the interrogative habit has to be internal. **The agent case is chosen so that the error is in the inference and not in the output**, which is a harder case than S002's and is placed here because the room has now had one week of practice at examining outputs and none at examining inferences. The unanswerable question it raises — how many runs would be enough — is left unanswered and named as [S029](wiki/seminars/S029.md)'s.

**Phase 7 (30 min).** The strongest phase of the day and the one that makes the habit personal. The partner-as-investigator structure means the discovery is made *about* the student rather than *by* them, which is more uncomfortable and more memorable. The persistent wall list extends the effect past the day.

**Phase 8 (20 min).** Item 6 resolved. P2 explicitly *not* resolved, and the deferral named, so that students see a commitment being kept rather than a loose end. Personal commitment recorded and revisited at S006.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student who has been burned by floating point will find the numeric strand familiar and may generalise their familiarity to the whole day. The predicted failure is disengagement in phase 3 and a shallow phase 5, followed by a genuine surprise in the textual domain that arrives too late to re-engage them. Countermeasure: phase 1's items are ordered so that item 2, the grapheme-cluster item, comes early and is the one nearly everyone fails, including the numerically experienced. The design deliberately leads with the least-known domain rather than the best-known one.

**Students with less relevant prior knowledge.** A student who has not encountered any of these failures may experience the day as a list of arbitrary pitfalls with no organising idea, and will retain it as trivia. Countermeasure: phase 3's single shared dataset makes the structure visible without requiring prior encounter, and phase 5's fading provides the worked instance. Residual risk: phase 7 depends on the student having recent work of their own to interrogate, and the least experienced students have the least. Their partners are asked to interrogate a supplied code sample instead, which is weaker and is a known inequity in the phase.

**Phase 3 is too easy.** A group may explain all five disagreements quickly. This is not a serious risk for the ordering case, which is designed to require noticing that a value difference crossed a comparison boundary — an inference groups reliably miss. If a group does get it, the fallback is to ask them to *construct* a fourth computation on which the ranking reverses, which is a genuinely harder task and previews S009.

**Affective failure.** The day's characteristic affective risk is **cynicism** rather than distress: a student concludes that nothing can be trusted, that all abstractions leak, and that careful reasoning is therefore futile. This is a real and observed response to leaky-abstraction teaching. Countermeasures: phase 5 step 4's insistence that every fix has its own loss reframes the situation as choice under trade-off rather than as universal unreliability; and phase 4's thesis is stated as *chosen for a purpose*, which locates the failure in a mismatch rather than in the representation's inadequacy. The instructor is briefed to name cynicism explicitly if it appears, because the unspoken version is the damaging one.

## 6. Retention architecture

Retrieved by S011 (what a representation makes cheap — the same question with cost as the object), S015 (choosing a representation for a known caller), S027 (error has structure — the numeric strand becomes measurement error), S051 (from vectors to meaning), S057 (dense retrieval, where the embedding is the representation and the discarded property is the failure mode) and S059 (the benchmark trap).

The S057 retrieval at a gap of roughly five quarters is the day's principal long-range target. The claim tested there is that a student asked *what does this embedding discard* recognises the question as one they have answered before, rather than as a new and difficult problem.

Phase 4 point 5 is the single retrievable sentence and is deliberately short, because the retrieval schedule can maintain a sentence over three years and cannot maintain a taxonomy.

The day's own expanding schedule: next morning, day 3, week 2, week 6. The week-6 repetition is co-located with S011.

## 7. Assessment and evidence generated

No entrustment evidence.

One specification item in CF101, in six binary elements. Item 1 — the three-defect artefact, requiring for each defect a committed prior prediction, the located failure, a statement of the discarded property and the purpose mismatch, and a fix with its own loss named — is the original specification, unchanged. Items 2 to 6 are new: the checkable instruction with its two outputs, the vague instruction with all three runs, the prompt record, the intervention record and the frontier statement.

The new-loss statement remains the item most often failed on first submission, which is expected and is what the token-funded resubmission exists for. **Item 3 is expected to become the second**, and for a different reason: it is failed by omission rather than by inadequacy, because the run that succeeded is the one a student sees no reason to report.

Programme instrumentation: phase 1's confident-wrong rate per item is the calibration baseline for the cohort; the phase 6 disclosure count continues the psychological-safety series; the phase 2 condition comparison is the S001 demonstration's outcome, recorded whichever way it falls; **and the phase 1 item 7 responses — whether students predicted the agent's prose or its code to be better — are the third point on the frontier map.** Instrumentation rule 9: the map's reader is next year's cohort.

## 8. Objections and rebuttals

**Objection 1: this material belongs distributed across the courses that own it, not concentrated in one day.**

At its strongest: numeric precision belongs in numerical methods, text encoding in a systems or software-engineering course, time representation wherever dates are first handled. Teaching them together on day three means teaching them before students have any need for them, which violates the ordinary principle that content should arrive at the point of application. Concentrated delivery also means the material is met once and then abandoned, whereas distributed delivery would repeat it naturally.

The rebuttal is that distributed delivery reliably produces exactly the inert knowledge the day exists to prevent. Taught in the course that owns it, each representation failure is learned as a fact about that domain — a numerical-methods fact, a text-handling fact — and the shared structure is never noticed, because noticing a shared structure requires the instances to be adjacent. The transfer literature's position is that surface-dissimilar instances of a common structure must be *co-presented* for the structure to become available; separated by months and framed by different courses, they will not be.

The objection's point about need is nonetheless partly conceded. Students on day three have no immediate application, and the day compensates artificially with substrate data. That is weaker than genuine need, and it is a real cost of the placement.

**Objection 2: the transfer claim to embeddings and benchmarks is a rhetorical analogy, not a mechanism.**

At its strongest: saying that an embedding discards, that a benchmark discards and that a floating-point number discards uses one verb for three unrelated phenomena. Floating point discards in a precisely characterisable way, with a known error bound. An embedding's losses are not characterisable in that sense. A benchmark's losses are a question about construct validity, which is a social and definitional matter, not a representational one. Training students to see these as the same thing may produce a facile pattern-match that substitutes for the actual analysis each case requires.

This objection the design does not fully answer. The similarity being claimed is at the level of the *interrogative move* — ask what was discarded, and for what purpose the representation was chosen — and not at the level of the analytical technique, which genuinely differs in all three cases. But the design has no evidence that a habit installed on precisely-characterisable losses transfers to loosely-characterisable ones, and there is a reasonable prior that it does not, since the far-transfer literature is generally discouraging about exactly this kind of surface-dissimilar generalisation. The honest position is that the day's near-transfer targets, S011 and S015, are well supported by its structure, and its far-transfer targets, S057 and S059, are hopes with an instrument attached. See §9 prediction 4.

**The two new instantiations at phase 4 points 6 and 7 make the objection worse and the design says so.** A specification's losses and a truncated search result's losses are, if anything, *further* from floating point's than an embedding's are. The design added them anyway, on the ground that they are the two instances a student will meet within the week rather than within two years, and that near-in-time instances of a claimed structure are worth more than distant ones even when the structural claim is weaker. **That is a defensible trade and it is a trade**: the day now spans five instantiations of a structure whose commonality is argued and not demonstrated, and if the structure is a facile pattern-match, the day is now more of one than it was.

**Objection 3: a day that teaches instructions-file wording is teaching a vendor's prompt syntax, and prompt syntax is the most perishable thing in computing.**

At its strongest: nothing about `applyTo`, front matter, glob semantics or injection behaviour will survive the student's degree. A day that spends twenty minutes of phase 3 and thirty of phase 5 on it has spent a fifth of a seminar day on material the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) itself classifies as perishable — configuration schemas and SDK surfaces are named there explicitly — and the register forbids assessing perishable content. The day appears to be doing exactly that.

The rebuttal is that the register's rule is *perishable content may be used as an instance of durable content, but may never be the thing assessed*, and the specification is written to honour it precisely. **What is assessed is that a checkable rule was written and its effect demonstrated, and that a vague rule was written and its unreliability demonstrated over three runs.** Neither element requires the assessor to know the syntax, and a student who wrote both in a different agent's format would pass. The syntax is the vehicle.

What the objection gets right is that **the day cannot run without the vehicle**, which is a stronger dependency than the register anticipated. A day teaching floating point can be run with any language; a day teaching that specifications must be checkable, by demonstration, requires *some* executor that will conform or not, and there is currently one in the room. The register's uncomfortable-consequence section accepts that students will occasionally learn a concept through an instance already stale. This day accepts it more than most.

**Objection 4: the day teaches students to make their tool conform and never to write the code themselves, and the gap it identifies — knowing the general fact and not applying it — is exactly the gap it now cultivates.**

At its strongest, and this is the sharpest version of the dependency risk available in the module: §1 argues that the professional failure here is *inert knowledge* — the engineer who can state that floating point is imprecise and does not fire on it when writing a comparison. Phase 5 steps 5 and 6 respond to that by teaching the student to write a rule that makes something else fire on it. **The student's own trigger is not exercised at all.** Over three years, a student trained this way holds the general fact, holds a repertoire of rules that encode it, and has never once been the thing that noticed.

**This objection is conceded and the fix is cheap.** Steps 1 to 4 already exercise the student's own trigger — predict the failure before running, locate it, name the discarded property — and they are performed on all three defects, unaided, before any instruction is written. The fix is to make that ordering *load-bearing rather than incidental*: **the specification requires that step 1's committed prediction precedes any agent invocation on that defect, and a prediction written after an agent has been asked about the defect fails.** It costs one sentence, it is checkable from the artefact's own ordering only weakly, and it is the same procedural-and-defeatable countermeasure [M01](wiki/modules/M01.md) records for the whole module. It is added. The residual concern — that a rule which fires is more useful than a person who notices, and students will reasonably prefer the rule — is not addressed by anything in this design and is left standing.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** Phase 1 item 2, the grapheme-cluster item, will have the highest confident-wrong rate of the six, and its rate will not differ materially between students with and without prior numeric-precision experience. *Instrument:* per-item response and confidence, split by a background survey administered at admission.

**Prediction 2.** On first submission, phase 5 step 4 — naming the new loss — will be the most-failed specification element, by a wide margin over steps 1 to 3. *Instrument:* specification failure counts by element.

**Prediction 3.** Students will retrieve the phase 4 point 5 sentence at S011 at a substantially higher rate than they retrieve any specific domain fact from phase 4. *Instrument:* an S011 free-recall probe covering both the abstraction and three domain facts.

**Prediction 4.** At S057, students will spontaneously ask what an embedding discards — without prompting — at a higher rate than a comparison cohort not taught S003 in this form. *Instrument:* an S057 discussion protocol coded for unprompted representational questioning. **This is the day's far-transfer claim and it cannot be tested until a variant delivery exists. It is currently unsupported and is the objection in §8 stated as an empirical matter.**

**Prediction 5.** In phase 5 step 6, at least one of the three runs of the vague instruction will produce conforming output for the substantial majority of students, and the students for whom all three fail will report the exercise as confirming what they were told. *Instrument:* step 6 run outcomes, tabulated, against a one-line student note on what the three runs showed. **If the vague instruction fails all three times for nearly everyone, the day is teaching that vague instructions never work, which is a stronger and false claim**, and the instruction wording must be re-selected. The result branches to the following offering's case B wording.

**Prediction 6.** Students will predict, at phase 1 item 7, that the agent's code will be better than its prose, and the prediction will be wrong for the substantial majority. *Instrument:* item 7 responses coded for direction, against the phase 3 case A output. **This is the module's second consecutive prediction that the cohort expects mechanical tasks to be performed mechanically**, after [WP-002](wiki/whitepapers/WP-002.md) §9 prediction 6, and if it holds twice the finding is reported to the cohort at S010 as a named cohort-level miscalibration rather than as a per-day result.

## Evidence status

**Verified in this repository.** The durable-versus-perishable handling of library specifics follows the register derived from [research/06-microsoft-platform/collected-materials.md](research/06-microsoft-platform/collected-materials.md). The *defaults are opinions and thresholds are policy* position that phase 4 point 7 instantiates is that folder's own synthesis and is not vendor doctrine; the folder records it as such. The construct-validity framing that phase 4 point 5 seeds is grounded in [research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md). Complexity-class positioning follows [research/01-course-structure/10-gap-analysis-and-course-architecture.md](research/01-course-structure/10-gap-analysis-and-course-architecture.md).

**Cited from general knowledge, not verified here.** Contrasting cases and the conditions for abstraction, interleaving and contextual interference, variability of practice, the generation effect, retrieval practice, situational interest development, and the general difficulty of far transfer are canonical results cited for **direction and mechanism only**. No effect size is asserted for any of them. The far-transfer literature's discouraging general finding is invoked in §8 as a directional prior, not as a quantified result.

**Grounded in vendor documentation, with its version and its silence recorded.**

*What the documentation says, and where.* Custom instructions live at `.github/instructions/<name>.instructions.md`; the `applyTo` front-matter key scopes each file to a glob; **GitHub Copilot injects matching instructions into every request automatically, with no slash command required**; and the instructions apply across every surface whose glob matches, including ask mode, edit mode, agent mode and inline completions. The documentation supplies a worked before-and-after in which the *same model, same prompt, same Copilot* produces differently-conforming output with and without an instructions file, and enumerates what the tool does without one — PascalCase identifiers, `INT` primary keys, omitted header and `SET` statements, unqualified schema names, auto-named constraints — with the sentence **"None of these defaults are wrong. They just aren't yours."** Conformance is verified by inspecting the request payload in the editor's Copilot Chat output channel, which the documentation calls **the source of truth**. ([learn.microsoft.com/sql/tools/visual-studio-code-extensions/github-copilot/custom-instructions](https://learn.microsoft.com/sql/tools/visual-studio-code-extensions/github-copilot/custom-instructions?view=sql-server-ver17), [learn.microsoft.com/visualstudio/ide/copilot-chat-context](https://learn.microsoft.com/visualstudio/ide/copilot-chat-context?view=visualstudio).) In Visual Studio the multiple-instructions-file behaviour must be enabled in options before it takes effect. The Learn MCP Server's `maxTokenBudget` query parameter caps the token count in search responses by truncating content in results, and **affects search only — fetch always returns the full page** ([learn.microsoft.com/training/support/mcp-best-practices](https://learn.microsoft.com/training/support/mcp-best-practices)).

*Version and date.* Read **26 July 2026**. The vendor's own default enumeration is a T-SQL example and is used here as **an instance of a documented default set, not as a claim about defaults in any other language** — the day's phase 3 runs are on the room's own floating-point request and the enumeration is cited only for the sentence that follows it. The path and key are the elements most likely to move; the design records that the instructions-file path changed once during its own drafting and uses that as the perishability example.

*What the documentation does not report that a reader would need.* Four silences, and the first two are the ones the day's whole phase 3 rests on. **No instruction-adherence rate is published.** The documentation states that instructions are injected; it does not state how often the model follows an injected instruction, for any instruction class, and it therefore cannot distinguish the case B failure from bad luck. **No precedence rule is published for two instructions files whose globs both match** the same file — which a student with three rules and two files will hit within a fortnight. Third, **the `maxTokenBudget` documentation does not state what truncation removes**: whether content is dropped from the end of each result or results are dropped entirely, which is the difference between a shortened answer and a missing one, and is exactly the discarded-property question phase 4 point 7 is about.
