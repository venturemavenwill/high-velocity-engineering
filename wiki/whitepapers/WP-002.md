# WP-002 — What a Machine Actually Does

**Seminar day:** [S002](/wiki/seminars/S002.md) · **Module:** [M01](/wiki/modules/M01.md) · **Quarter:** [Q1](/wiki/quarters/Q1.md)
**Strands:** SY · CF · MS · **Complexity class:** 1
**Platform anchor:** GitHub Copilot agent mode · Azure MCP Server read-only inspection, demonstrated not operated · **MCP servers:** Microsoft Learn MCP Server (operated); Azure MCP Server (staff tenant)

## Abstract

This paper defends spending an entire seminar day on hand-execution of a machine that does not exist, in a programme whose distinctive claim concerns production judgement about large-scale intelligent systems. The argument is that the programme's later performance and cost reasoning — memory hierarchy, queueing, serving economics, inference capacity — is not a set of separate topics but repeated application of one competence: predicting resource consumption from a mechanical model of execution. That competence cannot be built at the level of abstraction where students currently operate, because at that level the resources are invisible. The day therefore installs a complete, small, fully inspectable execution model, and uses hand-tracing to convert it from a description into a procedure the student can run. **The paper further argues that the hand trace has acquired a second function the original design did not anticipate: it is the only independently produced oracle the programme will possess for three years, and the day now spends thirty-five minutes using it to characterise the agent that will do the student's tracing thereafter.** The paper argues that hand-execution's much-criticised tedium is the mechanism rather than a cost, defends the deliberate refusal to answer the day's central question, and concedes that the transfer claim from a toy machine to production reasoning is the design's weakest link and is not established by any evidence available here.

## 1. The instructional problem this day must solve

Almost every student arrives having programmed at a level of abstraction where the machine is absent. Objects are allocated without a store, iteration proceeds without a program counter, and cost is whatever the profiler says it is after the fact. This is a reasonable working position for a practitioner and an untenable one for a student who will be asked, at S064, whether a system's capacity commitment is adequate, and at S020, to argue for a resource allocation before observing it.

The specific deficit is not ignorance of architecture. It is the absence of an **executable mental model**. Students can often state that a processor fetches and executes instructions; very few can be handed an unfamiliar instruction sequence and a machine state and produce the resulting state without running it. The difference between those two conditions is the difference between a description and a procedure, and only the procedure supports prediction.

The day must also do something subtler. The programme's whole measurement strand rests on the claim that a quantity is meaningless until you know what question it answers. The cheapest possible demonstration of that claim is available here, at the very bottom of the stack: ask which of two machines does more work, and watch three defensible metrics produce three different rankings. Delivering this at week two, before students have any investment in a particular metric, is far cheaper than delivering it at S026 when they do.

## 2. Entry state and prior knowledge assumptions

- **One day of shared programme experience**, from S001, which supplies the norms — public error is safe, prediction precedes attempt, retrieval is a learning event — but no technical content.
- **Wide variance in architecture exposure.** A minority have written assembly. A majority have not and will not have seen a register. The reference card in phase 1 exists to neutralise this, converting a knowledge gap into a lookup task.
- **No shared programming language.** The day is deliberately conducted below the level at which language differences matter, which is a secondary reason for its placement: it is the last point at which the cohort's heterogeneity is irrelevant.
- **Universal experience of a program behaving differently on two runs**, which phase 7 depends on and which every student has.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Very high element interactivity.** A single state transition requires holding the current register contents, the memory contents, the program counter, the instruction semantics, and the flags — and each element's correct handling depends on the others simultaneously. This is close to the canonical high-interactivity case, and the students' schema base is close to zero.

The design's response is uncompromising load reduction in every dimension that is not the target:

- **One integrated representation.** The machine diagram is annotated in place. There is no separate legend, no colour key on another page, and no reference sheet requiring cross-consultation during phase 5 — split attention is the single most damaging avoidable cost in a tracing task.
- **A machine deliberately smaller than any real one.** Four registers, a flat store, a dozen instructions. Realism is sacrificed without hesitation, because interactivity scales with element count and realism buys nothing here.
- **Complete guidance fading in phase 5.** Worked, then completion, then independent. Independent practice at full interactivity from a zero schema base is the standard way to produce a student who copies form without acquiring structure.
- **No time pressure in phase 5.** Ninety minutes for a trace that takes a competent tracer fifteen.

The phase 3 generation task is the day's one high-load-by-design element, and it is placed before consolidation precisely because its function is not to succeed.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Free-recall retrieval in phase 2 with no notes.* The first live retrieval phase in the programme; deliberately harder than a cued format, and deliberately including one item most students will fail.
- *Generation before instruction in phase 3,* with the source program withheld so that reconstruction is a genuine inference.
- *The pre-statement in phase 5,* which forces a commitment that the trace may falsify. Predicting before observing is the day's transferable move.
- *Peer divergence-finding in phase 6* rather than instructor-supplied correct traces. Locating the first divergence is substantially harder than checking against an answer key and produces the error classification the phase needs.

**Deliberately not selected.**

- *Interleaving machine models within phase 5.* Phase 3 contrasts two machines; phase 5 uses one. Interleaving the models during independent tracing would exceed capacity, and the contrast has already done its work.
- *Withholding the fetch-decode-execute structure.* This is given directly in phase 4. There is no productive-failure value in students inventing a cycle that has one correct form and no interesting alternatives.
- *Speed.* No component of the day is timed against a standard. Fluency is not a Q1 objective and pursuing it here would trade accuracy of model for automaticity of a procedure that will never be performed in anger.
- *Assessment stakes.* The trace is a specification item, pass/fail, resubmittable.
- *Building the simulator by hand.* The student directs it. Writing an interpreter unaided is a genuine and worthwhile exercise and belongs on a decomposition day rather than an execution-model day; here it would consume the phase and produce a second artefact with the same provenance as the first, which is the one thing the comparison cannot tolerate. See §8 objection 4 for the commitment this creates.
- *Operating the Azure MCP Server.* Refused on availability grounds and not on pedagogical ones. See the scope statement below.

**The scope statement for the platform instance, in strong form.** The day teaches a simplification, and it is the sharpest one in the module: **that an independently produced account makes another account checkable.** The hand trace adjudicates the simulator.

That simplification is **safe** wherever the two accounts have genuinely independent provenance and the property in dispute is one both accounts express. It is **unsafe** in three conditions, and the day states all three because a student who carries the unsafe version forward will trust agreement.

- **When both accounts derive from the same source.** Student and agent are both reading the same one-page reference card. A misreading of the card produces agreement, and agreement produced that way is worth nothing. The phase 5 specification requires the student to say so where the traces agree, which is the artefact element that makes the boundary checkable rather than merely stated.
- **When the property in dispute is not expressed by both accounts.** The trace and the simulator both express state transitions; neither expresses energy, cache behaviour or elapsed time, and a student who concludes from their agreement that the program is *efficient* has left the safe range entirely.
- **On any version other than the one in front of the student.** The agent's behaviour on this task, the model that produced it, the confirmation boundary and the file-visibility rule are properties of one release. The documentation's own statement that the file restriction does not bound terminal commands is the day's example of a boundary that a reader would have guessed wrongly, and it is precisely the kind of statement that is true until a release note says otherwise.

**The Azure MCP Server demonstration is bounded by the same rule from the other direction.** It is shown and not operated because operating it requires a subscription and a directory role the programme does not give first-year students, and the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md) requires that a capability which cannot be put in every student's hands is demonstrated rather than operated **and not assessed.** Nothing about it appears in the specification. The five-minute cap is enforced for a second reason: the mechanism behind every number on the screen belongs to Q4, and a longer treatment would teach quota, sizing and billing to a cohort with no way to check any of it — which is the exact failure mode this module exists to prevent.

### 3.3 Engagement and motivational mechanism

Hand-tracing is widely disliked and the day does not pretend otherwise. Three moves carry the motivational load.

**Competence, achieved rather than asserted.** The trace terminates. The student produced it. It is either right or has a locatable first divergence. Very little else in the programme offers this quality of unambiguous closure, and a week-two success of this shape is disproportionately valuable to self-efficacy — it is a mastery experience in the strict sense, on a task the student initially judged tedious rather than impossible.

**A genuine puzzle in phase 3.** The reconstruct-the-source task is a real inference with a real answer, and groups typically find it absorbing in a way the phase 5 tracing is not. Placing the interesting task before the laborious one is deliberate: situational interest triggered in phase 3 is what carries phase 5.

**Relevance made specific, not gestured at.** Phase 4 names the three later days that retrieve this material. The claim is not "this will be useful"; it is "at S061 you will be asked where the time goes in a serving system, and the answer will be in these units."

**The refusal itself is engaging.** Ending phase 3 with a question the instructor declines to resolve — which machine does more work — is an open loop, and it is closed at S026 rather than today.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** The reference card converts the pretest from a knowledge test into a procedure test, which is what makes pretesting appropriate for a cohort with high background variance. Item 2 turns on a flag that the card mentions once, so that the near-universal error is an inattention error rather than an ignorance error. Item 4's meta-prediction is the calibration instrument and is resolved same-day because the S001 apparatus already carries the long-delay calibration load.

**Phase 2 (20 min).** Free recall rather than recognition, no notes, at the first expanding interval. Pair-checking before the answer reveal adds a second retrieval attempt at near-zero cost. Marks are explicitly not recorded, which is the standing condition that keeps retrieval a learning event rather than an assessment.

**Phase 3 (45 min).** The two traces are of the same computation, complete and correct, with the source withheld. Surface variation with invariant deep structure is the contrasting-cases configuration that makes the invariant noticeable. The written commitment before presentation prevents retrospective convergence on whatever is said first. The "more work" question is designed to be irresolvable and is left irresolvable.

**The four executions vary along one dimension only: whether the question posed has a determinate answer.** A, B and D do; C does not. The design's reason for making C the payload rather than a case where the agent traces incorrectly is that an incorrect trace is a *detected* failure and teaches nothing the students have not already been told. A confident answer to an underdetermined question is an **undetected** failure, and it is undetected precisely because it looks like the three correct answers around it. The room has just spent twenty-five minutes establishing that the question has no answer, which is the only condition under which a fluent answer to it is legible as a failure at all. **The controls are load-bearing:** a tool that had been wrong three times already would not be believed the fourth time, and the design needs it to be believed.

**Phase 4 (50 min).** Directly instructed, indexed to the board. The ordering places determinism fifth, after the state model is complete, because determinism is a claim about state and is vacuous before state has been enumerated. Point 5 is the day's measurement seed and is delivered as a resolution of the students' own disagreement, not as a new topic — and it now closes on phase 3 case C, which supplied a fourth ranking nobody asked for. Point 6 is the Azure demonstration, capped at five minutes and assessed nowhere. Point 7 is the day's default-the-platform-chose-for-you point and is placed after the demonstration because the demonstration is the first time the room has seen the tool touch something outside the editor.

**Phase 5 (90 min).** The program computes a running maximum: recognisable, small, and containing one instruction whose effect is routinely mis-executed on first pass. The pre-statement is written before completion and may not be amended, so that the falsification point is preserved as evidence. The three-part fading is the phase's structural commitment. **The hand trace is sealed before the agent is invoked**, which is the module's standing countermeasure against a hand artefact written to agree with a machine one; it is procedural, it is defeatable, and [M01](/wiki/modules/M01.md) says so rather than this paper repeating it five times. The three outcomes of the diff are specified in advance and all three pass, because a specification that rewarded disagreement would produce disagreement.

**Phase 6 (40 min).** First-divergence location rather than answer-key checking. The instructor's classification of causes without attribution is the mechanism that converts individual error into shared vocabulary, and the four classes recur throughout Q1.

**Phase 7 (30 min).** The counterexample-hunt has a guaranteed yield, and the resolution — the nondeterminism was unmodelled state — is a schema that S032 and S079 both retrieve. This is the day's only content deliberately planted for retrieval two years out.

**Phase 8 (20 min).** Same-day calibration resolution, plus a personal error-class commitment that is specific enough to act on. The commitment is revisited at S006.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** Students who have written assembly will find phase 5 trivial and may complete it in twenty minutes. Expertise reversal is a live risk: the fading structure that helps novices is redundant instruction for them and measurably unhelpful. Countermeasures: the phase 5 extension is a program with a genuine subtlety — self-modifying behaviour arising from the stored-program property — which is hard for anyone; and these students are assigned the divergence-adjudication role in phase 6, which is a genuine task rather than a holding pattern. The design accepts that phase 4 will be redundant for them and does not attempt to differentiate it, because splitting the consolidation would fracture the shared vocabulary the module depends on.

**Students with less relevant prior knowledge.** The greater risk. A student who cannot complete the first third of phase 5 with guidance will not complete the rest, and the failure is legible to their neighbours. Countermeasures: the worked first third is genuinely walked through, at pace, with the instructor executing on the board; the completion problems supply alternate transitions so that partial failure is bounded; and the phase 6 pairing is assigned rather than self-selected so that no student is left adjudicating with a partner who is equally lost. Residual risk remains and this is the day where the first genuine drop-out signal appears.

**Phase 3 is too easy.** A group may reconstruct the source quickly, particularly if any member has assembly experience. Countermeasure: the fallback is to press them on the "more work" question with a fourth metric — energy — which no group anticipates and which produces a fourth ranking. The failure mode is inexpensive because reconstruction speed does not shortcut the metric disagreement, which is the phase's actual product.

**Affective failure.** The day's characteristic failure is not distress but **disengaged compliance**: students produce a correct trace mechanically, without the model forming, because tracing can be performed as symbol-pushing. This is the one failure that the artefact does not reveal — a correct trace looks identical either way. Countermeasures: the pre-statement and its falsification point, which cannot be produced by symbol-pushing; and phase 7, which cannot be answered without the model. If a student's pre-statement is absent or was clearly written afterwards, that is the signal, and it is treated as a design problem rather than an integrity one.

## 6. Retention architecture

Retrieved by S003 (representation over the same store), S007 (decomposition, where the machine grounds the cost of a seam), S011 (representation cost), S016 (memory hierarchy), S017 (processes) and S061 (where the time goes).

The S016 and S061 retrievals are the ones the day exists for, at gaps of roughly one quarter and six quarters respectively. The claim being tested by those retrievals is not whether students remember the instruction set — they will not, and need not — but whether the *stance* survives: that resource consumption is derivable from an execution model rather than observable only after the fact.

Phase 7's unmodelled-state schema is retrieved at S032 and S079 at gaps of one year and two years, which is the longest deliberate retrieval span in the programme.

The day's own expanding schedule: next morning, day 3, week 2, week 5.

## 7. Assessment and evidence generated

No entrustment evidence.

One specification item in SY101, in eight binary elements. Items 1 to 3 — trace, pre-statement, falsification point — are the original specification and are unchanged. Items 4 to 8 — the simulator and its diff, the adjudication, the prompt record, the intervention record and the frontier statement — are new. Resubmittable at a cost of three tokens.

**Item 5 is the element that carries the day's new content and it is worth stating what it does not require.** Where the simulator was wrong, the student must say what in the agent's output would have made that detectable without the hand trace. **The answer "nothing would have" is a pass**, and it is the honest answer in most cases. The specification is written that way deliberately: an element that rewarded finding a detection signal would produce invented detection signals, which is the [Assessment Architecture](/wiki/program/03-Assessment-Architecture.md)'s specification rule 1 failure in a new costume.

Programme instrumentation: the phase 2 free-recall score distribution is the first data point in the retention series that runs for three years; the phase 6 divergence-cause distribution establishes the baseline error profile of the cohort; **and the phase 1 item 5 responses — how many students named a detection method and how many of those used it — are the second point on the frontier map opened at S001.** Instrumentation rule 9: the map's reader is next year's cohort.

## 8. Objections and rebuttals

**Objection 1: a fictional machine cannot support claims about real systems.**

At its strongest: the toy machine has no cache, no pipeline, no branch prediction, no memory controller and no operating system. Every one of those absences is precisely where real performance is determined. A student whose execution model is this machine holds a model that predicts real performance badly, and may hold it with more confidence than someone with no model at all — which is worse than the deficit the day set out to fix.

The rebuttal is that the day is not claiming predictive adequacy; it is claiming that a student who has never executed a complete model cannot reason about an incomplete one. The toy machine's value is that it is *complete* — the student can account for the entire state — and completeness is unavailable in any real machine at any level of study. S016 then explicitly breaks the model by introducing the memory hierarchy, and the breaking is instructive only because there was something to break.

The objection's strongest form is nonetheless partly correct: the overconfidence risk is real, and the mitigation — telling students the model is incomplete — is known to be a weak mitigation. The design's actual answer is structural rather than verbal: S016 is scheduled to falsify the model within one quarter, which is short enough that the confident wrong model does not have time to consolidate.

**Objection 2: hand-tracing is a discredited pedagogy.**

At its strongest: hand-tracing is tedious, error-prone, disliked, and produces a skill that is never exercised professionally, because in practice one uses a debugger. Its persistence in curricula is inertia. Time spent here is time not spent on anything students will actually do.

This objection the design does not fully answer. The rebuttal available is that the tedium *is* the mechanism — a debugger supplies the answer and therefore forecloses the prediction, and it is the prediction that builds the model — and that the target skill is not tracing but predicting, with tracing merely the only available forcing function at this stage. But the honest position is that no evidence in this repository establishes that hand-tracing produces the predictive competence claimed, or that it does so better than the obvious alternative of debugger-based stepping with predictions written down first. That alternative is cheaper and less aversive, and the design chose against it primarily because a debugger's step granularity conceals exactly the memory accesses phase 5 is counting. That is a reason, not a warrant. §9 prediction 3 is the instrument that would settle it, and until it reports, this day rests on a design judgement that could be wrong.

**The revised phase 5 changes the objection's economics without settling it, and the change deserves to be recorded because it is convenient for the design.** The hand trace now has a second, immediate and undeniable use: it is the only thing in the room that can adjudicate the simulator, and the student watches it do so within the same ninety minutes. That answers the *motivational* half of the objection — tedious work with a visible payoff is a different experience from tedious work with a payoff promised at S061 — and answers none of the *evidential* half. Hand-tracing may still be an inferior route to predictive competence. It is now, additionally, a route with a use, and a design should be suspicious of an argument that arrives exactly when it is needed. Prediction 3 remains the instrument and remains unrun.

**Objection 3: teaching on one vendor's agent produces familiarity with that agent, and the day is now half a product tutorial.**

At its strongest: thirty-five of phase 5's ninety minutes go to an agent-directed build. Five of phase 4's fifty go to a resource inspector the students may never use. A day defended on the ground that students need an execution model has given a third of its practical time to a toolchain that will be renamed twice before they graduate, and the justification — that the hand trace needs something to adjudicate — is circular, because nothing needed adjudicating until the agent was introduced.

The rebuttal concedes the circularity and denies that it matters. The agent will be in the student's editor whether or not this day acknowledges it, and the choice is not between a day with an agent and a day without one; it is between a day that characterises the agent on a checkable problem and a day that leaves the student to characterise it on an uncheckable one in year two. **The day's durable claim — that an independently produced account is what makes another account checkable — is not about any product**, is assessed, and is the sentence a student would carry to a different agent, a different language or a different profession.

What the objection gets right is the Azure demonstration, and here the design is weaker. Five minutes of a resource inspector on a staff account is not a use, is not assessed, and is included because SY101's course anchor names it. **A course anchor is not by itself a reason to put something in a seminar day**, and if the demonstration turns out to be five minutes of watching someone else's screen, it should be cut and the anchor discharged in SY101's own coursework instead. That is recorded as an open item rather than resolved, because it cannot be decided until the day has run.

**Objection 4: a student who builds a simulator by directing an agent has not learned to build a simulator.**

At its strongest, and this is the module's version of the programme-wide dependency risk: the phase 5 build is exactly the kind of small, self-contained, well-specified program that a novice learns most from writing unaided. Handing it to an agent removes the one task in the day at which a first-year student could have succeeded by their own effort, and replaces it with a supervisory task. Over three years of days constructed this way, the student accumulates supervision experience and no construction experience.

**This objection is conceded and the fix is cheap.** The day does not need the simulator to be agent-built for its argument to work — it needs the simulator to be **independently produced from the hand trace**, and a simulator the student writes themselves fails that requirement worse than an agent-built one, because the student would be writing it from the same reading of the reference card that produced their trace. The cheap fix is therefore not to hand-build the simulator here but to **name the construction task and give it a home**: writing a small interpreter unaided is the correct exercise, it belongs on a decomposition day rather than an execution-model day, and [S007](/wiki/seminars/S007.md) is the nearest one. **S007 does not currently carry it**, and the commitment is recorded here as an incoming one that S007 must accept or refuse in its own whitepaper. Without a home, the objection stands and this day is where the erosion starts.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** The majority of students will produce a phase 5 pre-statement that is falsified during tracing, and the falsification will cluster at the single instruction the program was selected for. *Instrument:* falsification points collected from the trace artefacts and tabulated by instruction index. If falsifications are uniformly distributed, the program selection was arbitrary and the phase's design rationale is unsupported.

**Prediction 2.** Phase 2 free-recall performance on the S001 mechanisms will be substantially below what students would predict, continuing the S001 calibration gap. *Instrument:* an optional confidence rating collected before the recall attempt, compared with scored recall.

**Prediction 3.** At S016, students will predict cache-related performance differences more accurately than a comparison cohort taught the memory hierarchy without a prior complete-machine model. *Instrument:* an S016 prediction task, compared across cohorts once a variant delivery exists. **This is the prediction that tests the day's existence, and it cannot be run until at least two cohorts have been taught differently. Until then the day is unfalsified rather than supported.**

**Prediction 4.** Students will retrieve the phase 7 unmodelled-state schema at S032 at a higher rate than they retrieve the instruction set. *Instrument:* an S032 free-recall probe covering both.

**Prediction 5.** Where the hand trace and the simulator agree, a minority of students will state that the shared reference card makes the agreement uninformative; the majority will treat agreement as confirmation. *Instrument:* phase 5 item 5 responses in the agreement case, coded for whether common provenance is named. **If the majority names it, §3.2's scope statement is being reached without instruction and the artefact element that enforces it is redundant.** The result branches: a cohort scoring high moves to the harder S003 variant, in which two agreeing accounts are supplied and one is wrong.

**Prediction 6.** Groups running phase 3 case C will accept the agent's ranking without asking which metric it used, at a higher rate than they accepted any single metric from their own twenty-five-minute discussion. *Instrument:* group written responses to case C, coded for whether the metric question is raised unprompted, against the same group's own committed phase 3 answer. **This is the day's test of whether a fluent external answer suppresses a question the group had already generated**, and it is the mechanism the jagged-frontier material predicts. If the rates are equal, the day's phase 3 payload is not doing what it claims.

## What a student should take from this paper

**What the design is claiming.** That you cannot reason about an incomplete model of a machine until you have executed a complete one, and that hand-tracing's tedium is the mechanism rather than its price. The second claim is that your trace is the only independently produced account in the room, which is the whole reason it can adjudicate anything.

**What the evidence licenses.** The load, fading and worked-example apparatus behind phase 5 is **class 2** — direction and mechanism only, no magnitude, ever. The tool-failure decomposition used in phase 6 is **class 1** and is carried at the verification depth its note records: vocabulary, not a finding. The claim that hand-tracing builds predictive competence is **class 3** — design reasoning with no external warrant — and §9 prediction 3 cannot run until two cohorts have been taught differently. You may say a complete model can be executed and an incomplete one cannot. You may not say this day is known to work.

**What to do with it.**

- **Seal the trace before you invoke anything.** The protection is procedural and defeatable, and [M01](/wiki/modules/M01.md) says so rather than pretending otherwise.
- **When two accounts agree, ask where each came from.** You and the agent read the same reference card, and a shared misreading produces agreement worth nothing.
- **Write "nothing would have made this detectable" when it is true.** That is a pass. An element rewarding a detection signal would produce invented detection signals.
- **Classify what the run produced, using the five classes on the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md).** A simulator that ran and printed output is an observed result. **A control is not evidence**, and provenance is not correctness.

**The concession worth remembering.** The paper concedes that nothing in this repository establishes that hand-tracing produces the predictive competence it is defended for, or that it does so better than stepping through a debugger with predictions written down first — and that the design chose against the cheaper, less aversive route for a reason rather than a warrant. **Hold the day to that.** The paper also warns you that an argument arriving exactly when it is needed deserves suspicion, and the second use it found for the trace arrived exactly then.

## Evidence status

**Verified in this repository.** The complexity-class-1 positioning and the strand architecture are grounded in [research/01-course-structure/10-gap-analysis-and-course-architecture.md](/research/01-course-structure/10-gap-analysis-and-course-architecture.md). The error-management framing of phase 6 draws on notes in [research/04-professional-formation/keith-frese-error-management-training.md](/research/04-professional-formation/keith-frese-error-management-training.md) and [research/04-professional-formation/edmondson-psychological-safety.md](/research/04-professional-formation/edmondson-psychological-safety.md). The position that a tool can report success and be wrong — which phase 6's agent case rests on — is the tool-failure decomposition recorded in [research/06-microsoft-platform/collected-materials.md](/research/06-microsoft-platform/collected-materials.md) and [research/06-microsoft-platform/agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md), where **five** tool-usage evaluators decompose the failure and two of the modes they name — a call made with the wrong arguments, and a successful result ignored or misread — produce systems that report success and are wrong. That note records that the source page behind it was written from search-returned excerpts rather than a full page fetch, and **that verification depth is carried forward: the decomposition is used here as vocabulary, not as a finding.**

**Cited from general knowledge, not verified here.** Cognitive load theory's treatment of element interactivity, the split-attention and redundancy effects, the worked-example effect and its fading sequence, expertise reversal, retrieval practice, and mastery experience as a source of self-efficacy are canonical and are cited for **direction and mechanism only**. No effect size is asserted. Scope conditions are as summarised in [Learning Science Foundations](/wiki/program/02-Learning-Science-Foundations.md).

**Grounded in vendor documentation, with its version and its silence recorded.**

*What the documentation says, and where.* Agent mode requests confirmation before running a terminal command or using a tool that is not built in; it can manipulate only local files that are part of the solution or that sit in the open solution directory and its subdirectories, and cannot access files excluded from it; **for terminal commands it has the same permissions as the running editor process and is not limited by those restrictions**, and the documentation instructs the reader to review proposed terminal commands carefully. Cancelling a request stops all running tools and terminal commands. Reverting is by checkpoint restore, and stepwise undo and redo are not supported. Tools contributed by MCP servers are not enabled automatically. All from [learn.microsoft.com/visualstudio/ide/copilot-agent-mode](https://learn.microsoft.com/visualstudio/ide/copilot-agent-mode?view=visualstudio). The default `Auto` model selection chooses a model per step dynamically, and the documentation recommends selecting a specific model where predictable steps matter ([learn.microsoft.com/azure/developer/intro/quickstart-agent-assist](https://learn.microsoft.com/azure/developer/intro/quickstart-agent-assist)).

*Version and date.* Read **26 July 2026**, against articles documenting Visual Studio 2022 version 17.14 and later. **The file-visibility and terminal-permission asymmetry is the single most version-bound sentence on this day** and is the one re-verified first before each offering; it is a security-relevant behaviour and a change to it would change what phase 4 point 7 teaches. The Azure MCP Server material shown at phase 4 point 6 is not cited as a claim here because nothing is taught from it; the demonstration's content is refreshed each offering and assessed nowhere.

*What the documentation does not report that a reader would need.* Three silences and the first is the day's whole subject. **No measure is published of how often agent mode's iterate-until-resolved loop terminates on work that is wrong.** The documentation states that Copilot monitors outcomes such as build results and test failures and iterates — which is a statement about what it reacts to, not about what it achieves — and a student whose simulator ran, produced output, and was wrong has met exactly the case the documentation is silent about.
