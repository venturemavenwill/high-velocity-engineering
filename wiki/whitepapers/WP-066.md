# WP-066 — The Release Gate as an Evaluation Artefact

**Seminar day:** [S066](/wiki/seminars/S066.md) · **Module:** [M14](/wiki/modules/M14.md) · **Quarter:** [Q7](/wiki/quarters/Q7.md)
**Strands:** ME · SY · **Complexity class:** 5
**Platform anchor:** Foundry cloud evaluation run as a CI gate — the `microsoft/ai-agent-evals` GitHub Action (preview) and the Foundry evaluator catalogue · **MCP servers:** Foundry MCP Server (preview) · Azure MCP Server · Microsoft Learn MCP Server

## Abstract

This paper defends treating a release gate as an evaluation artefact carrying every property the programme has already taught about evaluations, and defends delivering that claim as a two-minute consequence of facts the cohort established a quarter earlier rather than as new content. Its central design argument concerns the two error rates: a gate that passes a change which should have been blocked leaves an incident with a name, and a gate that blocks a change which should have shipped leaves nothing anywhere, so a cohort will enumerate one and not the other unless the design measures the omission before naming it. The paper defends a phase 3 payload in which the least defensible gate — an unwritten human sign-off — outperforms three written ones, and defends the second finding inside it, that the comparison exists only because that gate was the one nobody trusted. **It defends the day's practical turn: three of the four gates are now operated rather than described, and phase 5 ships a Foundry evaluation into a pipeline whose judge has no published agreement with human judgement, whose pass threshold defaults to three, and whose conversation split defaults to the last turn — so that the day's founding claim is a documented property of the artefact in the student's hands rather than an argument they are asked to accept.** It supplies the third scope case the compliance register records as owed to this day, and discharges the category-3 obligation WP-050 §8 left outstanding. It concedes that the day's assessed error-rate instrument sits downstream of the instruction that supplies its answer — **the second instance of a pattern opened at WP-054 §8** — concedes that the day teaches gate validation while leaving the substrate's own gate unvalidated, **concedes that the gate the day first specified could not block and takes the one-clause fix while recording what the fix does not reach, and concedes that the day's transfer claim depends on a vendor that documents its defaults unusually well.**

## 1. The instructional problem this day must solve

The students have spent a quarter learning that a criterion is constructed, that it drifts, that its judge is biased, and that its interval has a dependency structure. They hold all of it. They will then walk into an organisation, look at a release gate, and not recognise it as any of those things.

The reason is structural rather than intellectual. **A gate is consulted, not read.** It returns a verdict at the moment of maximum consequence, when the question in the room is whether to proceed, and a verdict consumed under that pressure is received as a fact about the change rather than as a measurement with properties. Nobody in the room is being careless. The gate's whole purpose is to compress an unmanageable uncertainty into a decision, and it succeeds; the cost is that the compression is invisible to its consumers.

The specific difficulty this day must break is **the asymmetry in what the gate's two errors leave behind.**

A gate that passes a change which should have been blocked produces an incident. The incident has a date, a name, a review, a remediation and a line in the gate's own history. It is the most legible object in an engineering organisation.

A gate that blocks a change which should have shipped produces nothing. The change is not made. The engineer revises it, or abandons it, or reshapes it until the gate is satisfied, and none of that is recorded as a gate outcome because from inside it does not look like one. **The false-block rate of almost every release gate in existence is unknown, and it is unknown for a reason that has nothing to do with difficulty.**

This is [S027](/wiki/seminars/S027.md)'s condition D — the diagnostic evidence is absent by construction — arriving in a place where the students will make real decisions. It is also why the day's item 2 is administered before any framework is supplied: a cohort told there are two error rates will name two, and the design wants to know how many name two unprompted.

The second problem is consumption. [S042](/wiki/seminars/S042.md) taught a three-set discipline in which an evaluation set is used once. A release gate is consulted at every release for years. [WP-042](/wiki/whitepapers/WP-042.md) §8 conceded that its scope boundary was drawn between project and research and that the long-lived engineering case fell outside both, and named this day as the home for the missing case. **Point 5 supplies it.**

The third problem is the one the day cannot fully solve and returns to at [S069](/wiki/seminars/S069.md): the threshold is a decision about which error you prefer, and it is made by people who have not been told there are two.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Low technical, high structural.** Nothing computed on this day is difficult. The load is in holding five properties of one artefact simultaneously — construct, criterion, judge, threshold, error structure — while the artefact in question is one the student has always treated as a single object with a binary output.

The interactivity is between steps 2, 3 and 4. The construct determines what counts as an error, the error definitions determine what a validation must detect, and step 4's threshold is meaningless without step 3. A student who writes step 4 before step 3 produces a validation with no failure condition, which is [S047](/wiki/seminars/S047.md)'s named fail state.

Management:

- **The substrate's gate and its complete consultation record are supplied**, so no time is spent constructing an artefact to examine.
- **All four phase 3 gates come with their outcome records already assembled**, and the three that are operated come with their datasets and credentials.
- **Step 4's validation forms are retrieved rather than introduced**, and the release-history harness is supplied.
- **The pipeline skeleton and its authentication are supplied**, because standing up a workflow is not this day's content and would consume the phase.
- **The change the student carries through the module is chosen once, at step 1, and not revisited.**
- **Step 6 requires no new work**; the category-3 list is returned to the student.

**The build adds load and the design pays for it deliberately.** Phase 5 now contains a construction task where it previously contained only analysis, and the three forced decisions at step 5 are three more elements held simultaneously. The compensation is that **two of the three decisions are made by reading one documentation page**, which is what the Learn MCP Server is for and which the cohort has done since Q1; and that the construction is the part Copilot does well, which is why the intervention record rather than the pipeline is what the specification examines.

**Step 3 is unsupported**, and §8 objection 1 argues that it has been contaminated anyway.

Expertise reversal would begin to apply for a student who has operated a release process professionally. For that student points 1 to 4 are review, and the day's remaining content is points 5 and 6 — consumption and validation — which are the two an experienced practitioner is least likely to have met.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Enumerating a gate's failure modes with no framework supplied,* item 2.
- *Reading a fourteen-month clean record,* item 3, where both obvious answers are wrong.
- *Ranking four gates before the outcome records arrive,* phase 3.
- *Stating both error rates with evidence rather than assertion,* step 3.
- *Committing a validation threshold before running the validation,* step 4.
- *A dual defeat requiring both the gate and its validation to fail,* phase 7.

**Deliberately not selected.**

- *Release mechanics.* Canary, blue-green, progressive rollout and flag management are SY301's, and the day treats the release mechanism as given.
- *Statistical machinery for the validation.* [S049](/wiki/seminars/S049.md)'s, applied here without re-teaching.
- *Who owns the threshold.* Named at point 7 in one sentence and given entirely to [S069](/wiki/seminars/S069.md), because a governance answer supplied here would be received as a procedural detail of a technical day.
- *Security review as a gate.* SG301's, and the day states that its argument applies to it without developing the case.

**Scope, per the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md), strong form.** Point 5's three consumption remedies — rotation, a held-back slice never consulted at release, and a stated consumption budget — are **safe as a discipline for an evaluation artefact the student's organisation owns and can rebuild**, which is the ordinary case for an internal regression suite or metric threshold. They are **unsafe wherever the gate is externally imposed**: a certification suite, a contractual acceptance test, a regulator's criterion. In those cases the consumption is just as real, none of the three remedies is available, and applying them is not merely useless but a breach. The correct move there is the one [S050](/wiki/seminars/S050.md) supplies — state plainly what the gate no longer discriminates, to the party relying on it — and the day says so.

This is the third scope case the compliance register's [WP-042](/wiki/whitepapers/WP-042.md) §8 entry records as owed here. **The operative distinction is not project-versus-research but single-deliverable versus long-lived, and the long-lived case divides again into owned and imposed.** The register entry should be updated accordingly; that amendment is argued in §8 and is outside this paper's authority to make.

**The platform instance, scoped in the strong form.** The day teaches the Foundry evaluation gate as an instance of the general claim, and the simplification has to carry its safe and unsafe conditions because students will otherwise carry it into work this day does not supervise.

*Safe.* Reasoning about any gate the student is handed: what construct does it stand for, who set the cut point, which of the two errors is it tuned against, what does its verdict license, and would anybody notice if it stopped running. On this platform each of those has a documented answer, which is what makes the instance a good teaching object; off it, each is still the right question.

*Unsafe.* Three conditions, all stated to students at point 11. **Unsafe for reasoning about what this service will do next term** — the threshold, the split default, the evaluator-set behaviour and the action's own version tag are product decisions and can change in a release note. **Unsafe as evidence for the durable claim** — a student who argues that release gates go unvalidated *because* a named vendor publishes no agreement figure has mistaken an instance for a proof; the argument is [S029](/wiki/seminars/S029.md)'s and the vendor is an illustration of it. And **unsafe as a model of gates that are not evaluation runs at all** — a certification suite, a legal review, a hardware sign-off. Those have the same five properties and none of the same mechanics, and a student who has only met the platform form will look for a threshold parameter where there is a person.

The boundary is delivered at point 11 rather than left in this paper, per the widening recorded on the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md), and **step 5's requirement that each setting carry the reason it was decided is where a student applying the simplification outside its range would fail** — a reason of the form "it is the default" is not a reason and does not pass the element.

### 3.3 Engagement and motivational mechanism

The day runs on **G4**.

Four gates are ranked. Three are written, auditable and reproducible. The fourth is a person's judgement with no criterion at all, and every group in the room ranks it last, correctly, for reasons the programme itself has spent two years installing. Then the outcome records arrive and G4 has the lowest false-pass rate by a wide margin.

That alone would be a cheap reversal, and the design does not rely on it. **The second finding is the one that carries the day: the comparison is only possible for G4, because G4 is the only gate anybody distrusted enough to measure.** G1, G2 and G3 have no false-block figures, not because the figures are hard to obtain but because nothing ever prompted anyone to obtain them. A room that has just been surprised by G4's numbers then discovers that the three gates it trusted have no numbers at all, and the surprise converts into the day's actual lesson rather than into a preference for human judgement.

The second mechanism is item 3. A gate that has blocked nothing in fourteen months admits three readings — the changes were good, the gate is broken, or the record is a fact about the gate and not about the changes — and only the third is useful. Students reach the first two immediately and the third rarely, and phase 8 reports the fraction, which is the day's cheapest and most quoted result.

Autonomy is supported by step 1: the student chooses the component and the change, once, and owns it for five days. Competence is supported by the fact that the day's method is within reach — validating a gate against known outcomes is not sophisticated, and the finding that almost nobody does it is what makes it worth doing. Relatedness is supported by phase 6, in which the staff member responsible for the substrate's gate presents its failure.

The competence risk is at step 3's false-block figure, which most students will be unable to produce from evidence because the evidence does not exist. **The instructor states before phase 5 that "this rate is not recorded anywhere and here is what I would need to measure it" is a complete and passing answer to step 3, and that an invented figure is not.** This is the day's most likely site of manufactured confidence and it is pre-empted explicitly.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Five sealed items on the substrate's real gate with its real record. Item 2 is the day's headline instrument and is placed before phase 4 for that reason; item 3's three readings are the cheapest measurement in the day. **Item 5 is the sealed Copilot prediction**, administered here and not later per instrumentation rule 8, and constructed so that both halves are scoreable — predicting an error is easy, and predicting that the agent's failure will be an accepted decision rather than a defect is the measure.

**Phase 2 (20 min).** Three retrievals and the bridge. The bridge asks what has been happening to a criterion every change is designed to pass, and the room answers from S047 and S059 in under two minutes.

**Phase 3 (45 min).** Four gates, ranking committed, three of them operated, outcome records revealed, and a task-after that produces the day's operative sentence. G4 is the record payload and carries two findings rather than one. **The G3 split comparison is the executed payload** and is the cheaper of the two: the same judge, the same data, two documented split strategies, and a verdict that may or may not survive the change — the day reports what happened rather than asserting what will. **G4 is demonstrated rather than operated**, for the reason that it is a person, and nothing depending on running it is assessed.

**Phase 4 (50 min).** Eleven points. Point 2 is the retained content. Point 5 carries the strong-form scope statement for consumption and the third scope case. Point 6 is the assessed method. **Points 9 and 10 are the platform points the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md) requires — five named defaults, and the documentation silence that makes point 6 non-negotiable — and point 11 delivers the perishability boundary to students.**

**Phase 5 (90 min).** Eight steps on the artefact the student carries to S070, **now building the gate rather than describing it.** Step 4 before step 5 makes the threshold a pre-commitment. **Step 5's three forced decisions and its failure-condition requirement are what convert point 9 from a remark into an assessed object.** **Step 6 is the WP-050 §8 discharge** and is deliberately excluded from quality assessment. **Step 8 is the day's link to S068**: a gate that is skipped and a gate that passes are indistinguishable downstream, and the platform supplies a documented instance at a rate limit. The artefact carries the prompt record, the intervention record and the frontier statement.

**Phase 6 (40 min).** A correctly implemented gate, a clean eighteen-month record cited as the reason not to examine it, and a validation that found most of the incident-causing changes had passed. **Then the agent case: a pipeline that was correct, green and incapable of failing** — the same lesson from the students' own morning.

**Phase 7 (30 min).** Dual defeat against the gate and its validation, reusing S029's structure contingently under rule 5 as amended at [WP-054](/wiki/whitepapers/WP-054.md) §8.

**Phase 8 (20 min).** Item 2's pooled enumerations; item 3's three readings as a fraction; the cohort's step 3 distribution; **item 5's frontier hit rate; and the three step 5 default-decision rates against the number who could name any default at phase 1.**

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student who has operated a release process will name both error rates at item 2, will rank G4 correctly, and will find phase 3 confirmatory. Predicted failure: they treat step 4 as documentation of something they already know and produce a validation with a threshold no result could reach. Countermeasure: phase 7's partner is required to defeat the validation specifically, and a validation written as documentation is trivially defeated by a partner who is not required to be kind about it. The lesson arrives from a peer rather than an assessor, which is the module's standing arrangement for students ahead of the cohort.

**Students with less relevant prior knowledge.** The risk is step 3's evidence requirement, which most of the cohort cannot satisfy for the false-block rate. Countermeasures: the instructor's pre-statement that an honest "this is not recorded and here is what would be needed" passes; the four supplied gates, one of which has the figure and three of which do not, which models both answers; and the release-history harness, which makes the false-pass side computable so that the asymmetry between the two is experienced rather than described.

**Phase 3 is too easy.** A group that ranks G4 first for the right reason has anticipated the payload. This is plausible for a cohort that has just done [S048](/wiki/seminars/S048.md), which establishes that a documented judge is not therefore a good one. Fallback: ask the group which of the four gates they would adopt for the substrate **next quarter**, given that G4's accountable staff member is leaving. The question forces the trade the ranking conceals — G4's performance is not transferable, and its unwritten criterion is exactly why — and it has no supplied answer.

**Affective failure.** The characteristic risk is **contempt for process**. A day whose payload is that the unwritten human gate beat three written ones, taught to a cohort with a strong technical identity, invites the conclusion that gates are theatre and judgement is what matters. That conclusion would be actively dangerous at [S069](/wiki/seminars/S069.md) and at [S070](/wiki/seminars/S070.md), and the day creates the conditions for it.

Countermeasures: G4's advantage is presented as measured rather than as demonstrated, and the point that it is measurable only because it was distrusted is made before the ranking is discussed rather than after; the fallback question above is used with the whole room if the mood appears, since G4 does not survive the departure of the person who is the gate; point 6 gives a constructive procedure that applies to all four; and the instructor states once that the day's argument is that gates should be validated, not that they should be abandoned.

**The build's own failure mode, new with the practical turn.** The construction at step 5 is the easiest part of the day and it will absorb the phase if nothing stops it. A student can spend ninety minutes making a pipeline work, produce a green run, and answer steps 2, 3 and 8 in four sentences on the way out — which inverts the day, because the pipeline is the vehicle and the three unsupported statements are the content. Countermeasures: **the skeleton and credentials are supplied**, so the only construction work is the part that requires a decision; **steps 3 and 8 are unsupported and both are checked elements**, and step 3 is the day's discriminator; **the instructor states before the phase that a working pipeline with a defaulted threshold and no stated error rates fails the specification, and a pipeline that never ran with all three statements complete does not** — which is stated in those words, because it inverts the incentive students arrive with. The residual risk is real and is that a cohort with strong engineering identity will optimise toward the artefact that looks like work.

## 6. Retention architecture

Retrieved by [S067](/wiki/seminars/S067.md) (where the gate's verdict meets the online outcome), [S068](/wiki/seminars/S068.md) (where what the gate cannot see becomes a detection requirement), [S069](/wiki/seminars/S069.md) (where the threshold acquires an owner), [S070](/wiki/seminars/S070.md) (where the gate is consulted on a decision the student is answerable for), [S075](/wiki/seminars/S075.md) (trajectory evaluation, where the gate's unit of judgement is an episode) and [S087](/wiki/seminars/S087.md) (the safety case, where a gate is a piece of evidence in an argument).

**S070 at roughly four weeks is the consequential target**, and the relationship is direct: the gate designed here is the one the student's own ship decision will rest on, and the two error rates are what the defence's perturbation questions attack.

**S068 at two weeks is the structural target.** Point 8 — a gate that has never blocked anything is evidence about the gate — becomes, at S068, the observation that a monitor which has never fired is evidence about the monitor. The correspondence is drawn there explicitly.

S087's retrieval is the longest and the most demanding: a safety case that cites a release gate as evidence has cited an evaluation artefact whose error structure was never characterised, and this day is where that becomes a defect the student can name.

Retained content: the gate as evaluation artefact; the two error rates and the asymmetry in what they leave behind; passing as weak evidence at release; optimisation against the gate; the long-lived consumption problem with its owned-versus-imposed division; and validating the gate. Six items.

Own schedule: next morning, day 3, week 2, week 4.

## 7. Assessment and evidence generated

No entrustment judgement. The module's is at [S070](/wiki/seminars/S070.md).

One specification item in ME301 with SY301. Per rule 1, the checked elements are the release decision and its accountable party, the gate's construct and what it actually measures, both error rates with evidence and which is counted, the validation design with its pre-committed threshold, **the built gate with its three decided settings and its failure condition**, the validation result, the category-3 comparison with a statement of what changed, the consumption position, **the not-consulted conditions**, **the prompt record, the intervention record and the frontier statement**, and the phase 7 outcome. **Nothing else is assessed.**

Four hard requirements: **a gate whose two error rates are not both stated fails**; **a validation whose stated threshold could not have been reached fails**; **a pipeline with no failure condition fails**; and **a setting accepted at its default with no stated reason fails that element.** The last two are new with the practical turn and are argued at §8 objection 3. **An intervention record with no entries fails**, unless the gate's own design demonstrates it could have detected an intervention-worthy error — the escape clause is the sensitivity discipline [S052](/wiki/seminars/S052.md) established and [WP-048](/wiki/whitepapers/WP-048.md) §8 corrected, and here a threshold assertion or a split check is the obvious qualifying artefact.

**Nothing that depends on operating G4 is assessed**, per the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md)'s rule for capabilities the programme cannot operate. The reason in this case is not a licence but a person, which the day states to the room rather than smoothing over.

**Step 6 is not assessed for the size of the category-3 list.** [WP-050](/wiki/whitepapers/WP-050.md) §7 argued that an assessed prediction check is a strategy rather than a prediction, and that argument is correct and is preserved: what is checked here is that the student consulted their own result and stated what they changed, which is precisely the form WP-050 §8 proposed.

**Rule-6 discharge, as required by [WP-050](/wiki/whitepapers/WP-050.md) §8.** WP-050 conceded that its category-3 prediction check — failures that occurred on a student's deployed model and were not stated in advance — was measured, reported and dropped, with no later occasion consuming it, and proposed carrying it forward to S066 or S070 with a requirement that the student say what they have changed. **The element exists and is a checked artefact element: phase 5 step 6 returns each student's category-3 list, requires a per-item statement of whether the gate they have designed would catch it, and requires a statement of what has changed in how they enumerate failure modes.** It is not a prompt and not a reflection question; its absence fails the specification. The obligation is discharged here and is confirmed again at [S070](/wiki/seminars/S070.md) phase 5, which reports the cohort recatch rate.

**Instrumentation under rule 6.** The item 2 and step 3 error-rate results respond at [S069](/wiki/seminars/S069.md) phase 3, whose four governance arrangements are selected against whichever error the cohort proved blind to and whose task-after names the cost-bearer of each; the step 6 recatch rate responds at [S070](/wiki/seminars/S070.md) phase 5. **WP-069 §7 and WP-070 §7 must report whether those elements exist**, per the commitment [WP-051](/wiki/whitepapers/WP-051.md) §8 established.

Programme instrumentation: the item 2 unprompted false-block naming rate is the cohort's baseline for the module's central blind spot; item 3's three-reading distribution is the cheapest measure of whether a null result is read as evidence about the instrument. **Item 5's sealed prediction accuracy and the three step 5 default-decision rates are this module's first frontier-calibration data**, and per instrumentation rule 9 their reader is named: the following year's cohort, through the [Durable and Perishable Register](/wiki/program/09-Durable-and-Perishable-Register.md), which carries the re-verification of every default named at point 9 before each offering. **Per instrumentation rule 3 the frontier data are a sample and the day says so to the students**: one cohort, one substrate, one Foundry project, one model family, on a task staff selected because a known failure was available in it. A frontier map assembled from them describes this day's task and not the agent.

ABET and CS2023 contribution: PO2 and PO7, via the artefact that S070's entrustment occasion consumes. Dispositions: **integrity**, at step 3, where an invented false-block figure is the available shortcut and is named as a fail condition.

## 8. Objections and rebuttals

**Objection 1: the day's assessed instrument is administered after its answer has been taught.**

At its strongest: the design's headline claim is that a cohort will name one error rate and not the other. It measures this at item 2, before phase 4, which is correct. But **the assessed element is step 3**, in phase 5, fifty minutes after point 2 has stated that a gate has two error rates, that only the false-pass rate is counted, and why. A student writing "we count only the false pass" at step 3 has recalled point 2. The specification cannot distinguish that student from one who examined their organisation's practice and found the same thing, and the artefact — which is what the assessor reads under rater discipline rule 7 — contains only the conclusion.

The partial rebuttal is that item 2 exists and is the uncontaminated version, and that step 3 requires *evidence* rather than a claim, which point 2 cannot supply. A student who asserts the counting practice without evidence fails the element on its own terms.

**The rest is conceded.** Requiring evidence raises the cost of recall without distinguishing it from analysis, because the evidence for "only the false pass is counted" is the same evidence for everybody in the room and is one query against the incident tracker. The available fix is one clause: **require step 3 to name one way the gate can be wrong that is on neither side of the two-rate framing** — a gate that is right for the wrong reason, a gate whose verdict arrives too late to matter, a gate that is not consulted at all for a class of change. That clause cannot be answered from point 2, forces the student back to their own artefact, and costs a sentence. It is not in the design.

**This is the second instance of the pattern [WP-054](/wiki/whitepapers/WP-054.md) §8 opened at one instance: this design places its phase 5 instruments downstream of its own instruction.** The mechanism is the same one WP-054 identified — the pretest structure exists to prevent this and is used correctly, and the failure appears at phase 5 elements which are written as parts of a learning task and are not thought of as measurements until §7 claims them as ones. The observation is now at two instances and is recorded, not elevated. The rule it would become is already stated at WP-054 §8: **an instrument administered after its answer has been taught measures recall.**

**Objection 2: the day teaches gate validation and leaves the substrate's own gate unvalidated.**

At its strongest: point 6 asserts that any gate can be validated against changes whose outcomes are known, and that almost none is. Phase 5 requires each student to run exactly that validation. **The substrate's gate — the one in phase 1, the one every student's release will actually pass through, the one the programme itself relies on — is not validated by this day.** Phase 6 supplies a case in which a substrate gate *was* eventually validated and failed, which is a historical account, not this gate.

So the programme runs a release gate on a live service with real users, teaches that such a gate is an unvalidated evaluation artefact with an uncounted error rate, and does not validate its own. The self-refutation is exact and it has the same shape as the one the [Substrate and Infrastructure](/wiki/program/10-Substrate-and-Infrastructure.md) page records about user disclosure, which was found by [WP-035](/wiki/whitepapers/WP-035.md) §8 and repaired.

The rebuttal is weak and is stated as such. Phase 5 produces thirty-odd validations of student-chosen gates on student-chosen components, some of which will be the substrate's gate, and the harness that makes those runs possible is the same one that would validate the substrate's. So the capability is present and the act is not specified.

**The fix is cheap and the design declines it for a reason that is worth stating.** Requiring the day to validate the substrate's own gate and publish the result would cost one phase 8 line and one staff afternoon. It is declined because **the result would then be known to every subsequent cohort before phase 3 runs**, and the day's payload depends on the room not knowing what the records say. That is a real trade rather than an oversight, and it is a bad trade: the day could publish the validation to the cohort at phase 8, after phase 3 has run, and refresh the validation annually so that no cohort inherits the previous one's answer. **The design should take that and does not.** It is recorded here rather than fixed because the choice interacts with the substrate's operating schedule, which this paper does not control, and because the [Substrate and Infrastructure](/wiki/program/10-Substrate-and-Infrastructure.md) page is where the commitment would have to live.

**Objection 3: the gate the day first specified could not block, so the day demonstrated its central claim on an artefact that satisfied it trivially.**

This is the objection that bites hardest on the practical turn, and it is conceded outright.

At its strongest: the day's culminating claim is point 8 — a gate that has never blocked anything is evidence about the gate. The day then had students build a Foundry evaluation run in a pipeline as their gate. **The documented input set for that action is a project endpoint, a deployment name, a data path and one or more agent identifiers, and its documented output is a summary report with scores, confidence intervals and, across versions, a pairwise statistical comparison. Nothing in the documented parameters states a failure condition.** So the artefact the student built could not block, would never block, and would sit green forever — and the day would have pointed at it and said *look, this is what a gate that never blocks looks like*, having built one that structurally cannot. That is not a demonstration of the claim. It is a demonstration of a different and weaker claim, that some tools produce reports, and a student could leave believing the problem is a product gap rather than a discipline gap.

**The fix is one clause and it is made.** Step 5 now requires the pipeline to be capable of failing — a step that compares a result to the student's threshold and stops the job — and **a pipeline with no failure condition is a named fail condition of the specification.** The clause costs a sentence and it converts the artefact from a report into a gate whose not-blocking is a decision the student made and can be asked about.

**What the fix does not reach is recorded rather than repaired.** A pipeline that can now block still blocks against a threshold whose judge has no published agreement with human judgement. The student has built something that can refuse, and they still cannot say how often its refusals would be right. **That residual is the day's actual subject and it is not fixable by any clause**, which is the argument for point 6 rather than an argument against the build. It is stated here so that a reader does not mistake the repaired specification for a solved problem.

**Objection 4: the day's transfer claim rests on a vendor that documents its defaults unusually well.**

At its strongest: point 9 names five defaults and point 11 tells students to carry the question rather than the numbers. **The question is only askable because this vendor writes its defaults down.** The pass threshold is stated, the split default is stated, the automatic evaluator addition is stated, the sampling default is stated, the comparison's significance bands are stated. A student trained here learns to look for a documented default — and the next platform they meet may have the same five decisions and publish none of them, at which point the trained behaviour returns nothing and the student concludes there were no defaults.

The rebuttal is partial and is worth having. The behaviour the day installs is not *find the documentation*; it is *name what was decided for you*, and the correct response to an undocumented default is to establish it empirically, which is what phase 3's G3 split comparison actually models — the room does not read that the split matters, it runs both and looks. So the day does teach the transferable move, once, in the phase where the room reasons.

**It teaches it once and asserts it everywhere else, and that is conceded.** Points 9 and 11 are documentation-derived and the day does not require a student to establish a single default by measurement in their own artefact. **The cheap fix is available and is declined: step 5 could require one of the three decided settings to be established empirically rather than read** — run the gate at two thresholds and state where the verdict flips — which costs perhaps ten minutes and produces the only piece of evidence in the day that survives the vendor. It is declined because phase 5 is already carrying a construction task new to this day, and because the same move is made at [S067](/wiki/seminars/S067.md) step 7, one day later, where the student reconciles rows requested against rows scored. **That is a real reason and it is not a good one**: a countermeasure available at ten minutes' cost, on the day whose whole subject is that nobody checks, was declined because the following day checks something else. It is recorded rather than fixed, and it is the day's most likely candidate for the first amendment after the design runs.

**A third finding is recorded without argument.** The compliance register's [WP-042](/wiki/whitepapers/WP-042.md) §8 entry — *scope boundary drawn at project-versus-research, leaving the long-lived case outside both* — is marked **Recorded** with the reason *requires a third scope case whose correct home is S066*. Point 5 supplies that case and divides it further into owned and imposed. The entry's status should move, and the reason should record that the third case exists at S066 point 5. This paper cannot make that amendment.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** At item 2, fewer than a quarter of students will name the false-block error unprompted, and those who do will be disproportionately students with professional release experience. *Instrument:* item 2 enumerations coded for both error classes, split by the admission background survey. **This is the day's founding claim and the prediction it most needs to survive**; if half the cohort names it, point 2 is not the day's content and phase 4's weighting is wrong.

**Prediction 2.** At item 3, more than half of students will read the fourteen-month clean record as evidence about the changes rather than about the gate, and fewer than one in five will reach the third reading. *Instrument:* item 3 responses coded into the three readings.

**Prediction 3.** Groups will rank G4 last, and the ranking will be near-unanimous. *Instrument:* phase 3 committed rankings. **If a majority ranks G4 first, the payload has been anticipated** and the fallback question in §5 becomes the phase's content rather than its reserve.

**Prediction 4.** More than half of step 3 submissions will state the false-block rate as unmeasured and describe what would be needed, rather than inventing a figure — and the proportion that invent one will be higher among students who ranked G4 last most confidently. *Instrument:* step 3 submissions coded for invented, honestly-absent, or evidenced, cross-tabulated against phase 3 rankings. **The cross-tabulation is the claim**: confidence in a written gate and willingness to invent its error rate should not be related, and the design predicts they are.

**Prediction 5.** At item 5, a large majority will predict that the agent's pipeline contains an error, and fewer than one in five will predict that its failure will be an accepted default or an absent failure condition rather than a defect. *Instrument:* item 5 responses coded into defect-predicted and decision-predicted, against what each student's agent actually produced. **The gap between the two rates is this day's frontier-calibration measure.** If the decision-predicted rate is high, the cohort already holds the day's central distinction and points 9 and 10 are consolidation rather than content; if both rates are low, students are not yet predicting agent behaviour at all and the sealed item is measuring nothing.

**Prediction 6.** Across the three forced decisions at step 5, the threshold will be changed most often and the conversation split least often, and the split will be changed by fewer than a third of students even though phase 3 ran the comparison in front of them. *Instrument:* step 5 decision records coded by setting and by whether the recorded reason cites the phase 3 result. **This is the day's test of whether an executed contrasting case transfers into an artefact decision forty minutes later.** If the split rate is high, phase 3's executed payload is doing the work the design claims; if it is low while the threshold rate is high, students are changing the setting they were told about rather than the one they measured.

*What it says.* The GitHub Action `microsoft/ai-agent-evals` performs offline evaluation of Foundry agents in a CI/CD pipeline; its documented inputs are a project endpoint, a deployment name, a data path, one or more agent identifiers in `name:version` form, and an optional baseline agent; its output is a workflow summary report carrying scores, confidence intervals and, across multiple agents, a pairwise statistical comparison; the article is marked preview and its sample workflow pins the action to a beta tag; and the page advises against running evaluation on every commit, on cost grounds. An Azure DevOps task is documented with the same capability set, also preview. The general-purpose evaluators return a one-to-five Likert score with a **default pass threshold of three**, passing at or above it; the risk and safety evaluators return a zero-to-seven severity score with a **default threshold of three**, passing at or below it; and the cloud-evaluation result schema is label, score, threshold, reason and optional details, with the documentation stating that any non-binary score is binarised against a default threshold the user can override. The Agent Framework's evaluation documentation states that **how you split a conversation determines what you are evaluating**, lists last turn as the default alongside full and per-turn, and states that its Foundry evaluator set runs relevance, coherence and task adherence by default and **adds tool-call accuracy automatically when items carry tool definitions**. The portal's run comparison is documented as using statistical t-testing with bands at p ≤ 0.001 and p ≤ 0.05, an *inconclusive* result for too few examples or p ≥ 0.05, and a comparison view that is not saved. Continuous evaluation is documented as preview, as scoring sampled agent responses at a rate the operator sets, and — in the Agent Monitoring Dashboard's troubleshooting table — as **skipping evaluation runs once an hourly run limit is reached, with a documented default of one hundred runs per hour** and a remedy of raising the limit or waiting.

*What version it says it at.* The Learn articles are dated by content rather than by a version number. Four of the capabilities used or named on this day — the GitHub Action, the Azure DevOps task, continuous evaluation and the Agent Monitoring Dashboard — carry a preview notice stating that they are provided without a service-level agreement and are not recommended for production workloads. The day is expected to be re-anchored and its numbers are marked perishable at point 11 for that reason.

*What it does not report.* Three silences, and **the first is load-bearing for this entire module.** **No agreement with human judgement is published for any evaluator in this catalogue** — not a correlation, not an inter-rater figure, not a validation set. The documentation is precise about scales, thresholds, default cut points, regions, rate limits and token costs, and states no accuracy anywhere; this is consistent with the folder-wide asymmetry recorded in [research/06-microsoft-platform/](/research/06-microsoft-platform/collected-materials.md), where every source states a latency or a sampling bound and none states an accuracy. **The day therefore describes every judged score in this stack as uncalibrated and no claim to the contrary is made here.** Second, **the documented parameter set for the CI action states no failure condition**; the day does not conclude that the action cannot fail a build, only that the documentation in front of the student does not say it does, and §8 objection 3 turns on exactly that distinction. Third, **the documentation does not state that a skipped evaluation run emits any signal**; the skip appears only as a troubleshooting symptom, which means the documented route to discovering it is noticing that results are absent.
