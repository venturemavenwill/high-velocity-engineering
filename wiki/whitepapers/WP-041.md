## In plain terms

**What this paper argues, before the formal version.**

For four quarters you have been able to work out what something does by looking at how it was built. An invariant holds because somebody established it. A contract is satisfied because the implementation was written against it. **None of that survives contact with a learned component.** You can read the training code, the architecture and every setting and still not know what the thing does on an input you have not tried. The only way in is measurement.

That would be fine if measurement were simple. It is not, and the reason is one you already hold: a number from an evaluation is an estimate **for the population the evaluation set was drawn from**. Not for your users. The two are almost never the same, and the gap is not a defect anybody introduced.

Everybody already knows to hold data back. Everybody still produces optimistic figures, because holding data back addresses one of several ways information gets from the evaluation into the model. Preprocessing fitted across everything. The same underlying event turning up twice under different records. Time running the wrong way. None of those is visible in the training code and none of them breaks the rule as you hold it.

And then the part that is hardest to accept: **removing every leak does not close the gap.** A correct, careful, honestly executed split still estimates performance on a population the model will not meet, because the world moved. That is not a fault to fix. It is a condition to estimate, with a direction and a reason, and confusing the two is expensive in both directions — chase a shift and you waste months, accept a leak and you ship a lie.

The last piece is about honesty in the artefact. You can claim your pipeline is clean, for free, and nobody can check. So the audit has to show what was looked at in each class, and an audit that shows nothing does not distinguish a clean pipeline from an audit nobody ran.

**What this paper concedes, and it is the sharpest concession in the module.** The day makes its case by running real evaluations, and a real evaluation on this platform arrives in the most persuasive shape the industry has produced: a bounded scale, a stated threshold, a pass label, and a written reason explaining the score. **Every one of those raises your confidence and none of them raises the accuracy.** The design has therefore increased the rhetorical force of the thing it is arguing against, more than it increased the argument. Its answer is to make you write, in the same sentence as every judged number, that nobody has published how well that judge agrees with a person. **Requiring a sentence does not produce a belief.** You can write it four times, believe the number completely, and pass — because nothing in this day makes any decision depend on it.

## Abstract

This paper defends introducing machine learning through the question of what a held-out estimate estimates, rather than through learning algorithms, and defends failing a leak audit that reports no findings. The first argument is that a learned component's behaviour is accessible only by measurement, that every measurement of it is an estimate for a population determined by how the evaluation set was constructed, and that the deployment population is almost never that one — so a student equipped with algorithms and without this framing will produce confident figures about the wrong thing. The second argument is that an audit reporting nothing is indistinguishable from an audit not performed, and that requiring the checks to be shown converts an assertion into evidence. The paper additionally defends constructing the day's contrasting cases so that the *correct* protocol is also optimistic, and defends running them as four real cloud evaluations against one deployed model rather than supplying four figures on a handout. It defends one further requirement introduced here and binding for the rest of the programme: **every judged score carries a sentence stating that it is uncalibrated**, because no agreement-with-human data is published for any evaluator on this platform. It concedes that the day's leak taxonomy is bounded in a way its own scope statement admits is dangerous, that its central specification clause rests on an empirical assumption the design has not tested, and that executing the evaluations may increase students' trust in a judged number by exactly the mechanism the day exists to warn them about.

## 1. The instructional problem this day must solve

Four quarters have taught that behaviour follows from structure. An invariant holds because it was established and preserved. A contract is satisfied because the implementation was specified against it. A paradigm applies because its structural hypothesis was checked.

None of this transfers. A learned component's behaviour is not derivable from its construction — you can read the training code, the architecture and every hyperparameter and still not know what the model does on an input you have not tried. The only access is measurement, and this is a genuinely new epistemic situation for these students rather than a harder version of a familiar one.

That would be manageable if measurement were straightforward, and it is not, for a reason the students are unusually well prepared to understand: **an evaluation figure is an estimate for the population the evaluation set was drawn from**, which is S028's entire content with a model as the instrument. Phase 2's bridge asks them to make this identification themselves.

The day's second problem is that students already know the rule. Everyone knows you evaluate on held-out data, and everyone will still produce optimistic figures, because the rule addresses one of at least four ways evaluation information reaches the model. Preprocessing fitted on all the data, the same underlying event appearing in both halves under different records, and temporal ordering are all invisible in the training code and none violates the rule as students hold it. Phase 3 supplies all four.

Phase 3's most important construction is that **protocol A — the correctly executed random split — is also optimistic** when tested against a genuinely later period. That is the day's central point and it cannot be reached by fixing leaks: the correct protocol still estimates performance on a population the model will not encounter. Point 4 separates this from leakage explicitly, because a student who treats shift as a fault will chase it and a student who treats leakage as a condition will accept it.

The third problem is auditability. A student can assert that their pipeline has no leaks, and the assertion is unfalsifiable and free. Step 4's audit requires, for each of four classes, a statement of what was checked and what was found — and **the specification fails an audit reporting nothing in all four**, which is the day's sharpest and most contestable clause.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**High, and concentrated in a relation rather than in a technique.** The day's difficulty is holding the evaluation population, the deployment population, and the four mechanisms by which they can differ, simultaneously — because a leak and a shift produce the same symptom and are distinguished only by their cause.

Management:

- **No algorithm content.** IS201 supplies it. The day trains and evaluates using supplied code.
- **One dataset and one task across the module.**
- **Four protocols supplied at phase 3** with a real out-of-time comparison, so groups reason rather than construct.
- **The audit form supplied** at step 4, listing the four classes.
- **Step 2 worked with the room,** because designing an evaluation whose population resembles a deployment population is the day's hardest single step.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Identifying the population an estimate is for,* item 3, before any instruction.
- *Protocol A's optimism,* phase 3's payload.
- *The four-class audit with findings required,* step 4.
- *Estimating the shift and its direction,* step 6.
- *The partner's adversarial audit on the design alone,* phase 7.

**Deliberately not selected.**

- *Model architecture or training.* Supplied.
- *Cross-validation protocol design.* S042's material, and deliberately withheld so that this day's estimate is a single held-out figure whose meaning can be examined without a resampling apparatus in the way.
- *Hyperparameter tuning.* Named at the scope statement and deferred to S042.
- *Feature leakage from future state.* Named and deferred to IS201, which is a genuine gap discussed in §8.
- *Formal generalisation bounds.* Not taught anywhere; the programme's position is that they do not inform practice at this level.

**Scope, per the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md), strong form.** Point 2's four leaks omit leakage through repeated hyperparameter selection and leakage through a feature computed from a future state. **Safe** as an audit for a single evaluation of a single model, which is this day's task. **Unsafe** as a complete leak taxonomy for a pipeline, because the two omitted classes are among the most common in practice and a student running this audit on a production pipeline will pass it while leaking. The first omission is S042's subject; **the second is assigned to IS201 and the seminar strand never checks that it landed**, which is a real gap.

**The platform instance, scoped in the strong form.** The day now runs its contrasting cases as four cloud evaluations against one deployed model, and reads the catalogue's published benchmarks as an evaluation set. Both simplifications must carry their conditions, because students will otherwise carry them into work this day does not supervise.

*Safe.* Reasoning about what a score is a score of; about why the same model returns different figures under four evaluation datasets; about why a published benchmark does not license a claim about your users; about why a run whose status is Partial is not a run whose scores can be averaged; and about why a pass label is a policy rather than a finding. In every one of those, executing the evaluation supplies exactly the evidence the reasoning needs and nothing more.

*Unsafe* in three specific directions, and the day names all three. **First, as a quality measurement.** A judged evaluator's score has no published agreement with human judgement; it is a number produced by a model rating another model's output, and treating it as a measurement is the error the whole measurement strand exists to prevent. **Second, as a comparison across models.** The catalogue's leaderboard is a normalised index over datasets and metrics the reader did not choose, displayed as an average by default, and it is in preview — three reasons a rank order there does not transfer to a rank order on your task. **Third, as a stable interface.** The Foundry MCP Server is in public preview and the evaluator set, the scale and the thresholds are all subject to change without the durable claim changing at all.

The boundary is delivered to students at points 8, 9 and 10 rather than left to this paper, per the widening recorded on the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md). **The artefact element under which a student applying it outside its safe range would fail is the uncalibrated clause**, which is required in the same sentence as any judged score and whose absence fails the specification.

### 3.3 Engagement and motivational mechanism

The day runs on **the right answer still being wrong**.

Phase 3's protocols B, C and D are leaks, and identifying them is satisfying in the ordinary way. Protocol A is correct — a properly executed random split, no leakage, nothing to find — and its figure is also optimistic against the real later period. Groups who have just spent twenty minutes finding faults have no fault to find here, which is precisely the state in which point 4's distinction lands.

Item 4 supplies the day's opening asymmetry. Most students predict correctly that live performance will be lower, and almost none can say why. Predicting a direction without a mechanism is a familiar state by Q5 and the design uses it deliberately: the prediction is right, the reasoning is absent, and the day supplies the reasoning.

Phase 7's construction — hand over the design and withhold the results — is the day's best single mechanism. A partner who cannot see the number cannot reason backwards from it and must actually read the design, which is what makes the audit adversarial rather than confirmatory.

The competence risk is that step 4's audit produces findings in the student's own work and feels like failure. Countermeasure: the specification fails an *empty* audit, which inverts the incentive, and this is stated before step 4 begins.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** A real model, a real figure, and the evaluation's construction disclosed at item 2. Most students do not identify the leak even when shown the construction, which is the pretest's finding and is the argument for a structured audit rather than an inspection. **Item 5 is the sealed Copilot prediction**, administered here and not later per instrumentation rule 8, and its prompt is deliberately the prompt a student would actually write — *evaluate this model and tell me whether it is good enough to ship* — which contains a question about a decision inside a request about a measurement.

**Phase 2 (20 min).** Four items importing M06 wholesale. The final item — which error source is a leaked evaluation set — has the answer *selection effect*, which establishes that no amount of additional evaluation data corrects it. That is the frame for the whole module.

**Phase 3 (45 min).** Four protocols, one dataset, adjudicated by a genuinely later period, **executed as four cloud evaluation runs against one deployed model rather than supplied as four figures**. Protocol A's inclusion is the phase's critical design decision and the phase collapses without it: three leaks and their corrections would teach that a correct protocol yields a correct estimate, which is false. Executing rather than reading buys two things a handout could not. The runs cost real time and real tokens, so the number of evaluations a group can afford becomes a live constraint one day before S042 makes it the subject. And the scores arrive with a pass label attached to a threshold nobody in the room set, so the threshold question is raised by the platform rather than by the instructor — which is a materially different reception, because a student can dismiss an instructor's provocation and cannot dismiss a number that has already been labelled.

**Phase 4 (50 min).** Eleven points. Point 1 is the retained sentence. Point 2 carries the scope statement. Point 3's observation — the obvious leak is the least dangerous because it is detectable — is the argument for the other three. Point 4 separates fault from condition. **Point 8 reads the catalogue's benchmark as an evaluation set** and is the day's strongest single moment, because the vendor's own troubleshooting text states the day's thesis in one line. **Point 9 names four defaults the platform chose**, per the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md). **Point 10 introduces the uncalibrated clause**, which binds every artefact from here to S090 and is the standing prohibition on the [Microsoft AI Platform Map](/wiki/program/11-Microsoft-AI-Platform-Map.md) converted from a rule staff enforce into a sentence students write.

**Phase 5 (90 min).** Seven steps at class 3, **shipping a working evaluation pipeline** rather than describing one. Step 1's deployment population comes first, before any evaluation is designed, which is S029's decision-first sequence applied to modelling. Step 4 is the discriminator. Step 7 is the production observable. The day's sharpest platform trap sits at step 3: a field mapping is a specification, a mapping that names a field the file does not contain does not fail loudly, and a run can return **Partial** — some evaluators completed, others did not — with a results page that reports what it has. A pipeline that reads scores without reading status will average over whichever evaluators happened to succeed.

**Phase 6 (40 min).** A leak that survived review, then an agent failure. The review detail matters for the same reason it did at S028: these failures are not caught by inspection, which is why the audit is structured. **The agent case is a correct pipeline that answered the wrong question** — it polled, read, compared against the threshold and reported readiness, having treated any terminal state as success and having answered a shipping question with a threshold comparison. It is chosen because there is no coding error in it at all; the failure is a category error the code executes faithfully, which is the failure a code review cannot find.

**Phase 7 (30 min).** Design without results. Recorded in the artefact per rule 3, which this module applies from its first day.

**Phase 8 (20 min).** The item 3 rate, the item 4 direction predictions against the phase 3 reality, the most-missed leak class across the cohort, and **item 5's sealed prediction opened** — the cohort's first frontier-calibration datum in Q5, read by the following year's cohort through the [Durable and Perishable Register](/wiki/program/09-Durable-and-Perishable-Register.md) per instrumentation rule 9.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student with machine-learning coursework will execute the split correctly and report a figure. Predicted failure: they treat the day as revision, produce a clean audit with no findings, and are surprised when it fails. Countermeasure: the failing clause is stated in advance and their phase 7 partner is reading the design rather than the code — where the population mismatch at step 2 is visible regardless of pipeline hygiene.

**Students with less relevant prior knowledge.** The day requires no modelling skill, which makes it unusually equitable. The demanding step is 2, and it is worked. Residual risk: their shift estimate at step 6 may be a guess, and the specification requires a direction and a reason rather than a magnitude, which is reachable.

**Phase 3 is too easy.** Protocols B and C are identified by most groups. Protocol D is harder. Protocol A is the phase's difficulty and no group is expected to anticipate its optimism. Fallback if a group does: ask them to estimate how much of protocol A's gap is shift and how much is a fifth leak they have not named — which is genuinely open and is the honest state of most real evaluations.

**Affective failure.** The characteristic risk is **the day read as an argument that evaluation is impossible**. Four leaks, a correct protocol that is still optimistic, and a shift that cannot be eliminated is a lot of subtraction, and the module's fatalism risk arrives on its first day rather than accumulating.

Countermeasures: point 4's framing of shift as a condition rather than a fault, which makes it something to estimate rather than to defeat; step 6's requirement to estimate it with a direction, which is a constructive output; and step 7's production observable, which converts an unresolvable uncertainty into a monitoring commitment. The design's position is that this day's negativity is front-loaded deliberately and that S042 through S044 are progressively more constructive — a claim which, per the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md)'s fourth register, requires a named verification: **S045's phase 1 asks students what they are willing to claim about their model, and a cohort that will claim nothing indicates this failed.**

## 7. Assessment and evidence generated

No entrustment judgement — the module's is at S045.

One specification item, jointly in IS201 and ME201. Per rule 1, the checked elements are: a stated deployment population, an evaluation design with its stated divergence, a completed four-class audit with its evidence, a three-part licensing sentence, **the uncalibrated clause on any judged score**, a shift estimate with direction, a production observable, the phase 7 outcome, **and the prompt record, the intervention record and the frontier statement**. **Nothing else is assessed, including the model's accuracy.**

**An audit that does not evidence what was checked in each of the four classes fails.** The clause is defended in §8.

**A judged score reported without the uncalibrated clause fails.** The clause must travel in the same sentence as the number, per specification rule 2 — a qualification must travel with the quantity it qualifies, in the same field — because a detached disclaimer is a disclaimer nobody reads.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error. An assertion on the run status before the scores are read, or a check that every mapped field resolved, are the accepted forms and are the two errors the day's own agent case turns on.

Programme instrumentation: the item 3 population-identification rate is the cohort's baseline and is the S022 deferred test's instrument; the most-missed leak class is tracked across cohorts and fed into IS201's coordination; **the phase 7 optimism-found rate is the design-audit measure** carried to S059 and S067; **item 5's sealed prediction accuracy is the quarter's first frontier-calibration datum**, read by the following year's cohort through the [Durable and Perishable Register](/wiki/program/09-Durable-and-Perishable-Register.md) per instrumentation rule 9.

The frontier statements are a sample and the day says so, per instrumentation rule 3: one cohort, one substrate, one task, one model, on a build staff constructed to contain a known trap. A frontier map assembled from them describes this task and not the agent.

Dispositions: **integrity**, at step 4, where reporting a leak in one's own pipeline is unattractive and undetectable if omitted.

## 8. Objections and rebuttals

**Objection 1: failing an audit that reports nothing punishes a clean pipeline.**

At its strongest: a student who designs a careful evaluation, fits preprocessing inside the fold, de-duplicates by underlying event, respects temporal order and samples the evaluation set to match deployment has done everything right — and fails, because their audit has no findings. The clause conflates *found nothing* with *did not look*, and the remedy for that conflation is to require evidence of the checks, which the specification already does at "what you checked". Adding a findings requirement on top is punishing the outcome rather than the process.

The rebuttal is that the clause is not about the outcome and the seminar page says so: an audit that found nothing has not distinguished a clean pipeline from an unperformed one, and the artefact must show the checks. A student with a genuinely clean pipeline records four checks with their evidence and no findings, and passes.

The concession is that **the seminar page's wording does not say that**. It states the failing condition as "reporting no findings", and a student reading it will believe findings are required. The design's actual position — checks must be evidenced, findings are not required — is stated in the clause's justification and contradicted by its operative sentence. That is a specification-wording defect of exactly the kind the [Assessment Architecture](/wiki/program/03-Assessment-Architecture.md)'s rule 1 was added to prevent, appearing in the first module written after the rule was introduced. The correct wording is that an audit failing to evidence what was checked in each class fails, and it is not what the page says.

**Objection 2: the day assigns its most common leak class to another course and never verifies it landed.**

At its strongest: §3.2 concedes that leakage through a feature computed from a future state is common and is assigned to IS201. That is the leak most likely to appear in a student's own work — a feature derived from an outcome, an aggregate computed over a window including the target period — and it is the one this day's four-class audit will not catch. A student passes the seminar's audit, believes their pipeline is clean, and has not checked the class most likely to be broken. The seminar strand and the course strand are both present in the same quarter and nothing connects them on this point.

This objection the design does not fully answer. The division is real: the seminar teaches the audit stance and IS201 teaches the feature-engineering material, and neither is the wrong home for its half.

What is missing is the join. **The audit form has four classes and could have five, with the fifth marked as covered in IS201 and requiring the student to state which IS201 material they applied.** That would cost nothing, would surface whether the coordination worked, and would give the seminar's audit the coverage its own scope statement says it lacks.

Its absence is the second instance in two quarters of this design deferring content to a concurrent course with no verification that the deferral was honoured — after [WP-039](/wiki/whitepapers/WP-039.md) §8's constraint-kind deferral to S082, which at least names a seminar day the design controls. Deferring to a course the seminar strand does not own is weaker still, and the design has no mechanism for checking any such deferral.

**Objection 3: executing the evaluations increases students' trust in a judged number by exactly the mechanism the day exists to warn them about.**

This is the objection that bites on the practical turn and it is the strongest of the three.

At its strongest: the day's argument is that a number is an estimate for a population and that a judged number has a judge whose agreement with people is unpublished. It then puts that number in front of students in the most persuasive form the industry has yet devised. **The score arrives on a bounded scale, against a stated threshold, with a pass label, accompanied by a written reason explaining why the score was given.** Every one of those features increases confidence and none of them increases accuracy. The reason field is the worst: an explanation makes a judgement feel accountable, and [S052](/wiki/seminars/S052.md)'s finding is precisely that a model's stated reasoning is a routing record and not a cause. The handout version of this day produced four numbers and a lesson about numbers. The executed version produces four numbers, four labels, four thresholds and four explanations — and a lesson about numbers delivered afterwards, by an instructor, against an artefact that has already made its case. **The design has increased the rhetorical force of the thing it is arguing against, and increased it more than it increased the argument.**

The objection is conceded. The rebuttal available — that seeing the persuasive form is the only way to learn to resist it — is true and is not sufficient, because the same reasoning would justify any amount of exposure and the design has no way to say how much is right.

**The cheap fix is one specification element and it is made.** The uncalibrated clause is now required in the same sentence as any judged score, per specification rule 2, so it cannot be detached from the number it qualifies; a report that states a score without it fails. That converts the day's scepticism from an instructor's assertion into something the student has to write in the position where it does work — next to the figure, in the artefact a later reader will actually read.

**What remains unfixed is larger than the fix and is recorded rather than repaired.** Requiring a sentence does not produce a belief. Nothing in this day makes a student *act* differently because a score is uncalibrated — no decision branches on it, no threshold moves, no second instrument is required. A student can write the clause four times, believe the number completely, and pass. The repair would be an artefact element requiring the student to name a decision they would make differently if the judge's agreement were published and low, which would cost one line and is not in the design. It is not made because the day already carries seven required elements and the design is not confident it can carry an eighth without the audit losing weight — which is a resourcing argument, not a principled one, and is recorded as such. **The correct home for the repair is [S048](/wiki/seminars/S048.md), whose entire subject is the judge**, and this is a deferral with a named day and a named artefact element, per the deferral rule.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** Fewer than a third of students will name a population at item 3, and a large majority will predict the correct direction at item 4. *Instrument:* items 3 and 4 coded separately. **The gap between them is the day's premise: direction is intuited, mechanism is not.**

**Prediction 2.** No group will anticipate protocol A's optimism before the out-of-time comparison. *Instrument:* phase 3 committed rankings. **If a group does, the temporal gap in the comparison is too obvious and the phase needs reconstruction.**

**Prediction 3.** The most-missed leak class will be duplicated events rather than temporal ordering. *Instrument:* step 4 audit findings by class against a staff audit of the same pipelines.

**Prediction 4.** In phase 7, partners will find a source of optimism in a majority of designs, and the rate will not be lower for students with prior machine-learning coursework. *Instrument:* phase 7 outcomes split by the admission background survey.

**Prediction 5.** A large majority of item 5 sealed predictions will say the agent will produce an evaluation and a number, and a small minority will name the specific failure — that it will answer the shipping question anyway. *Instrument:* item 5 responses coded for generic-versus-specific failure identification, against what each student's agent actually produced. **The gap between the two rates is the day's frontier-calibration measure. If the specific rate is high, the cohort already holds the distinction between a threshold comparison and a decision, and phase 6's agent case is redundant; if the generic rate is also low, students are not yet predicting agent failure at all and the sealed item is measuring nothing.**

**Prediction 6.** In the first cohort, a majority of students will report a judged score without the uncalibrated clause on first attempt, and the rate will fall below a quarter by S048. *Instrument:* specification submissions coded for the clause's presence and for its placement in the same sentence as the figure. **A high rate that does not fall indicates the clause is being treated as boilerplate, which §8's objection 3 predicts and which the design has no further remedy for at this day.**

## What a student should take from this paper

**What the design is claiming.** That you cannot read a learned component's behaviour off its construction — measurement is the only access — and that every measurement is an estimate for the population the evaluation set was drawn from, which is almost never the population the model will meet. The uncomfortable half is that a correctly executed split is still optimistic, so removing leaks does not close the gap.

**What the evidence licenses.** Generalisation, evaluation-set construction and distribution shift are **class 1**, grounded in [research/02-technical-foundations/thakur-beir.md](/research/02-technical-foundations/thakur-beir.md) and [research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md). **The four leak classes you will be audited against are class 3** — no note in this repository holds a leakage taxonomy, and the paper says so in its own evidence status. The platform is **class 4**, read on 26 July 2026: a judged score arrives on a five-point scale with a label, a reason, a threshold and a default pass value of three, and **no agreement with human judgement is published for any evaluator**, which is why every judged score you report must carry the uncalibrated clause.

**What to do with it.**

- Name the deployment population before you design the evaluation, not after.
- Keep leakage and shift apart. A leak is a fault to remove; shift is a condition to estimate, with a direction and a reason.
- **A control is not evidence**, per the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md). An audit reporting nothing does not distinguish a clean pipeline from an audit nobody ran, so show what you checked in each class.
- Read the run status before you read the scores. A Partial run still has scores, and averaging over whichever evaluators happened to succeed is a number about nothing.

**The concession worth remembering.** The paper concedes that running the evaluations increases the persuasive force of a judged score more than it increases the argument against it — the bounded scale, the pass label and the written reason all raise confidence and none raises accuracy. Requiring a sentence does not produce a belief. You can write the uncalibrated clause four times, believe the number completely, and pass, because nothing in this day makes any decision branch on it.
