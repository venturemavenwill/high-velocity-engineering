# WP-061 — Observability That Answers a Question

## In plain terms

Telemetry accumulates. Nothing removes it, because removing it feels like losing something and keeping it costs nobody anything they can see.

The session's move is to insert a column that most estates have never had: **for every signal, the question it answers and the person who asks it.** The column is written before any tool is opened, because a question written after looking at a signal is a description of the signal.

The frame the session works inside comes from the production machine-learning literature, which imports observability from control theory and states the governing asymmetry directly — **you can only control a system to the extent that you can observe it** — then operationalises it as **alertability**, thresholds that make a failure unambiguous, and **actionability**, enough signal to find the cause. Those two together define waste: **a stream you can neither alert on nor act from is cost, not observability.**

Two rules do most of the operational work and both come from an openly published engineering handbook.

**The first is that observability configuration belongs in source control, and the reason given is peer review** rather than reproducibility. That is the stronger argument because it names a mechanism: a dashboard held as code is a thing somebody else reads before it takes effect, can diff, can revert and can attribute. A dashboard built in a console is none of those.

**The second is a standing review rule: any data collected but not aggregated or alerted on must be reviewed to establish whether it is still required.** Almost no estate passes it. The session requires the learner to run it on their own and to produce a deletion list that is not empty.

The rest of the session is hygiene with teeth. The correlation identifier goes as early as the system can put it, and any segment before it is named as a blind segment rather than omitted. Personal and customer-sensitive data stays out of logs, and sensitive values stay out of URLs, because request URLs are logged by infrastructure the team does not control. An exception is logged once. A metric label is not a unique string. And the choice between a log, a metric and a trace is defended on **what each costs to keep**, which is the framing the bill uses and which the same handbook states plainly.

The platform half is where the abstract becomes configuration, and it carries the session's sharpest single lesson. The gateway can attach **custom dimensions** to the token metrics it emits. **Total token consumption tells you the bill; token consumption per interface per consumer tells you who to talk to.** The second is answerable only if somebody decided, before any traffic existed, that consumer identity was worth carrying — and nothing recovers it afterwards. **Attribution is a design property of the telemetry, not a property of the data.**

One gap that earlier revisions of this paper stated rather than filled is now closed, and **the closure is worth reading more carefully than the gap ever was.** The anchor names tracing in the vendor's agent platform, and this repository formerly held no research note covering that surface. A note now exists. The session teaches the surface, keeps the derivation first, and keeps the pin on every product observation — and it inherits two absences that were invisible while the first one was in the way. **No measure of tracing completeness is published**, so a trace is offered as a record and never as a sample. **No retention period is owned by the platform**, only a portal display window and a delegation to a workspace somebody on the delivery side configures and pays for. Both were confirmed by dedicated search. **A display window is not a retention policy, and a record is not a sample.**

## Abstract

This paper defends opening an operations module by specifying observability from the questions it must answer rather than from the signals a platform offers. The argument runs in four steps. **First**, telemetry accumulates monotonically because addition is cheap and removal is politically expensive, so an estate drifts from instrument to archive without anybody deciding that it should. **Second**, the production-monitoring literature supplies a definition of waste that is operational rather than rhetorical — alertability and actionability — and a signal satisfying neither is a bill, a retention row and a privacy surface producing nothing. **Third**, holding observability configuration as code converts it from an unreviewed artefact into a reviewed one, which is a mechanism rather than a preference, and mechanisms constrain behaviour whether or not anybody is enthusiastic about them. **Fourth**, attribution is decided before traffic exists: the gateway's metric dimensions are the concrete instance, and a dimension not emitted is a question permanently unanswerable.

The session installs a signal register with question and asker columns written before any tool is opened, a non-empty deletion list naming what will now be missed, a dated review list with a named owner for signals retained without an asker, a correlation statement that names its own blind segment, a privacy line the documentation never asks for, and the configuration itself in source control.

The paper concedes that no source behind it supplies comparative evidence of any kind; that the handbook it borrows two rules from has the most rotted observability section on its own site, recommending archived and deprecated tools on pages that still render; that the deletion requirement asks learners to accept a loss of visibility whose cost the design cannot estimate; and that the gap it formerly declared — **no research note covering the tracing surface the anchor names** — **is now closed, and closing it produced two sharper absences the design has kept rather than smoothed away**: no published measure of tracing completeness, so that a trace is a record and never a stated sample, and no platform-owned retention period at all. §9's instrument is re-pointed accordingly, from a citation gap to a completeness assumption.

## 1. The problem this session must solve

An observability estate has one direction of travel.

Every incident adds a signal. Every new component brings defaults. Every platform upgrade offers more. **Nothing in the ordinary operation of a delivery team ever removes one**, because addition is a minute's work and removal requires somebody to argue that a thing nobody is watching should stop being available in case somebody watches it.

The result is not merely expensive. It is that **the estate stops being an instrument and becomes an archive**, and the difference is that an instrument answers a question. A dashboard nobody reads is not a smaller version of a dashboard somebody reads; it is a different kind of object, and it will be present at the next incident, occupying the screen, while the thing that broke goes unrepresented.

There is a second problem underneath. **Almost all of this configuration lives where nothing else in the engineering estate is allowed to live** — in a console, changed by whoever had the tab open, undiffable and unattributable. A team that would refuse a code change without review will accept an alert threshold changed silently by a person who has since left.

The session's response is a specification with a question column, a deletion list, and the configuration in the repository.

## 2. Entry state and prior knowledge

**Entry state: this-programme-only.** The session operates on a running system produced by [Stage 5](/wiki/quarters/Q5.md) and assured by [Stage 6](/wiki/quarters/Q6.md), and it presumes the system model from [S051](/wiki/seminars/S051.md), because a signal is emitted by a component and belongs to a flow.

It assumes [S023](/wiki/seminars/S023.md), where a non-functional requirement acquired a measurement and a verification method; **the observability specification is that discipline applied to what the system emits rather than to what it must achieve.** It assumes [S043](/wiki/seminars/S043.md), because a learner who has written tests as a specification has already met the idea that an artefact's value is what it lets somebody else establish. And it assumes [S058](/wiki/seminars/S058.md), where a requirement asserted everywhere and instrumented nowhere was diagnosed; **this session is the same diagnosis pointed at telemetry.**

**The prior it works against is that more observability is better observability.** Learners arrive holding it, it is professionally rewarded, and nothing in their prior experience has ever charged them for it.

## 3. Theoretical basis

**3.1 Load profile.** Intrinsic load is low; the concepts are few and each is independently comprehensible. The surplus is spent on the deletion pass, which is affective work rather than cognitive: the learner has to accept a specific loss of visibility and write down what it is.

**3.2 Why observability rather than monitoring is the frame.**

The production machine-learning literature imports the idea from control theory and states the governing asymmetry directly: **you can only control a system to the extent that you can observe it** ([research/02-technical-foundations/crowe-machine-learning-production-systems.md](/research/02-technical-foundations/crowe-machine-learning-production-systems.md)). The slogan is quoted widely and is not by itself a design constraint. What makes it one is the same source's operationalisation into two properties — **alertability**, meaning thresholds that make a failure unambiguous, and **actionability**, meaning enough signal to support finding a cause — because those two are testable against a specific signal in a way that "observability" is not. **A stream that supports neither is cost rather than observability**, and the same source's standing rule follows directly: collect what you need rather than what you can.

Two further ideas from that source shape the session even though it does not teach them at length. **Functional monitoring** watches predictive behaviour and the distribution of what arrives; **non-functional monitoring** watches failures, latency and resource use; and the second matters regardless of the first, because a system that is down serves nothing. And two named sensitivities — **entanglement**, where changing one thing changes everything, and **configuration**, where a small error in versions or parameters produces radically different behaviour that ordinary software tests will not catch — explain why the cause of an anomaly is so often not where the anomaly appeared. **Those two are the reason the register carries a correlation statement rather than only a signal list**, since a search whose target may be anywhere depends entirely on being able to follow one request across the whole system.

**That source's limits are heavy and travel with every use of it here.** Practitioner guidance from a commercial publisher, not research: no study design, no comparison group, no measurement that its practices outperform alternatives. Three of its four authors worked at one large vendor, so its default toolchain is that vendor's. Some of its foundational claims rest on **anonymous practitioner testimony** that cannot be checked. And **every quantity in it is a property of a particular system after a particular training run**; mechanism and direction transfer, magnitudes do not, and **no figure from it appears in this paper or in the session.**

**3.3 Why the question column precedes the tool.** A question generated while looking at a signal will be a question the signal happens to answer. **Ordering the work so that the question exists first makes the signal answerable to it**, and the reverse ordering is not a weaker version of the same exercise — it is a different exercise that always succeeds. This is design reasoning and carries no external warrant; §9's prediction 4 is the instrument attached to it.

**3.4 Why peer review is the right argument for observability as code.** Reproducibility is a benefit and benefits are easy to defer. **Review is a mechanism, and mechanisms constrain behaviour whether or not anybody is enthusiastic about them.** A dashboard that must arrive as a change acquires a reader; the reader is the whole of the improvement. The rule itself — that configuration and management of observability assets must be managed as code — is quoted from a page of the openly published handbook ([research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), pages read 2026-07-30); **the elevation of review over reproducibility as the reason is this design's, not the source's.**

**3.5 Why cost is the honest basis for the log, metric and trace distinction.** The semantic account — logs are events, metrics are aggregates, traces are causal paths — is true and decides nothing, because most facts can be represented in more than one of them. The handbook draws the distinction instead **by data volume and processing cost rather than by semantics**, which answers what each instrument costs to keep rather than what each one means. That is the framing that survives contact with a finance conversation, and it is why opening item 4 asks which instrument the learner would drop if the bill doubled.

**3.6 Why tracing is not an incident instrument.** The same source frames tracing as an optimisation instrument and states that **"Its purpose isn't reactive, but is instead focused on optimization."** A learner who expects a trace to explain an outage will be looking at the wrong thing at the worst time, **and the expectation is common precisely because tracing is the most impressive of the three to demonstrate.** The complementary definition comes from the evaluation-practice literature: **a trace is a logical grouping of log records**, and for a conversational system the trace is the conversation, with searching, filtering and reading named as the essential tooling features ([research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md](/research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md)). **That source is one practitioner's case study with no control condition, no measured improvement and no released dataset, and its tooling references are dated.**

**3.7 Why the specification carries percentiles and a correlation statement rather than averages and a diagram.**

The engineering-practice literature makes tracing a design requirement rather than an add-on and states the test in a form a specification can be checked against: **"Ideally, you should be able to trace each query's transformation step-by-step through the system. If a query fails, you should be able to pinpoint the exact step where it went wrong"** ([research/03-measurement-evaluation/huyen-ai-engineering.md](/research/03-measurement-evaluation/huyen-ai-engineering.md)). The same source supplies the reporting correction the session adopts — **"Because latency is a distribution, the average can be misleading"** — and names *goodput*, the requests per second satisfying the service objective, as the quantity that matters operationally. It also disposes of the most common vanity signal in this domain with one sentence: **"A higher utilization rate means nothing if the cost and latency both increase."** **Its limits:** a commercial practitioner book in its first edition; where it reports figures it is almost always reporting somebody else's work, and **none is reproduced here.**

**3.8 Why attribution is treated as a design decision rather than an analysis task.**

This is the platform half of the session's argument and it is the part that could not be taught without an anchor. The gateway's observability capabilities include logging prompts and completions, per-consumer token metrics, a built-in dashboard and cross-application quota management, and the mechanism that carries the lesson is a policy attaching **custom dimensions** — client address, interface identifier, a consumer identifier — to the emitted token metric ([research/06-microsoft-platform/apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md)). **Dimensions are what make a metric answerable**, and a dimension that was not emitted cannot be recovered by any later analysis. That asymmetry is the strongest available argument for the session's whole ordering: the design decision precedes the traffic, and the question therefore has to precede the design decision.

Two further facts from the same documentation are load-bearing for the artefact. It states that logging serves **"billing and auditing"**, which is the point at which observability acquires a retention obligation rather than an operational convenience. And it **does not discuss the privacy implications of logging prompts and completions at all**, despite recommending the logging — which is why the session requires a privacy line that no documentation prompted the learner to write. **Its limits:** first-party product documentation with a commercial frame, fetched and read in full but perishable in its policy names, attributes and tier boundaries; capability availability varies by service tier; parts are preview; and it offers **no performance or cost-saving data of any kind**, so its stated benefits are plausible mechanisms rather than measured outcomes.

**3.9 A gap in the anchor that the design declared, and has now closed — without closing the silences it was standing beside.**

Earlier revisions of this paper recorded, correctly, that the anchor named tracing and observability in the vendor's agent platform and that **this repository held no research note covering that surface.** The session accordingly taught the derivation and refused the syntax. **That absence is now closed** by [research/06-microsoft-platform/foundry-agent-build-and-runtime.md](/research/06-microsoft-platform/foundry-agent-build-and-runtime.md), and the design's response is to teach the surface and keep the derivation first.

What the note supplies is a default rather than a vocabulary, and the default is the teachable object. **Server-side tracing requires no code change** once an Application Insights resource is connected, and it captures inputs, outputs, tool calls and results, retries, token consumption and time signals. **Message content is not among them**: an environment variable switches content recording on, and the documentation warns in the same sentence that the content may contain personal data. **That is the session's own collect-what-you-need rule, shipped as a product default by somebody who was not thinking about this session** — which makes it a better illustration than any example the design could have invented, because it is a real decision with a real owner and a real consequence.

**The design's judgement is that closing this gap changed the session's material and not its argument.** The question column still precedes the tool. The deletion list is still non-empty. The privacy line is still required and no documentation still asks for it. What changed is that the privacy line now has a concrete population to enumerate: the governance note records that connecting the telemetry resource requires a senior role on the account, and that **anyone holding a common monitoring reader role on the connected workspace can afterwards read prompts and completions** ([research/06-microsoft-platform/foundry-control-plane-and-governance.md](/research/06-microsoft-platform/foundry-control-plane-and-governance.md)). **The set that can enable collection and the set that can read the result are different sizes, and the gap between them is what the privacy line was always for.**

**And the silences beside the gap are confirmed rather than repaired, which is a stronger result than the one this paper previously recorded.** The note reports, from dedicated search rather than from non-encounter, that **no measure of tracing completeness exists** — nothing states what proportion of an agent's decisions appears in a trace, whether a step can go unrecorded, what sampling does to completeness, or how a reader would detect a missing span, so **a trace is presented as a record and never as a sample, and no page states the difference.** And **no Foundry-owned retention period exists for traces or conversations**: there is a stated portal display window for out-of-the-box traces, and an explicit statement that retention and sampling follow the customer's own Application Insights and Log Analytics configuration. **A display window is not a retention policy**, and the obligation is delegated to a resource the delivery team must own. §9's prediction 6 is re-pointed accordingly — it now instruments the completeness assumption rather than the citation gap.

**The note's limits are the heaviest attached to any source in this paper.** It is **the most perishable material in this repository and it perished visibly while being read**: four pages read in full, roughly thirty reached only through search excerpts with tables frequently truncated, several consulted pages explicitly superseded and still rendering, preview status pervasive and load-bearing. **It is definitional and not evidential** — an accurate account of what the platform is configured to do, and no evidence that doing so produces any outcome. **Every number in it is a dated platform parameter and none is reproduced in this paper or in the session.**

**3.10 Why a published standard is used as a specimen as well as a source.** The handbook supplies the two rules this session most depends on, and simultaneously supplies the sharpest available demonstration of why a standard is cited by page and by date. **Its observability section is the most rotted part of its own site**: the tracing page defines neither a span nor propagation, a roadmap years out of date is still quoted on a standards page, and several tools it recommends are archived or deprecated — on pages that all render perfectly. It contradicts itself in at least a dozen places without noticing, and asserts four unsupported magnitude claims that **this repository records as specimens and reproduces nowhere.** **A section about observing systems that has not itself been observed for years is a better lesson than any of its content**, and it is the concrete origin of the session's requirement that the specification carry a review date rather than a completion date.

**3.11 Why the register's coverage boundary is now a written artefact rather than an attitude.**

The estate-governance surface publishes named tables holding agent inventory and agent activity, queryable in the hunting language the rest of the security estate already uses ([research/06-microsoft-platform/agent-365-and-agent-identity.md](/research/06-microsoft-platform/agent-365-and-agent-identity.md)). The design takes one thing from that and it is not the schema. **A question in the register can now be answered by a query the learner wrote, held in the repository beside the register entry it serves** — which brings the platform half of the session under the same review mechanism as everything else in it, and closes a small inconsistency the earlier design carried: the register was code and the thing that answered it was a panel.

The assessable half is the comment block rather than the query. The documentation supplies coverage boundaries in its own voice — agents emitting no observability data are simply absent; agents off the sanctioned tool path fall outside the protection layer's claimed coverage; drafts are visible from one named build surface only — and **the design requires those to be written into the query file rather than known by the author.** The reasoning is the same one that produced the asker column. A boundary held in somebody's head is not transferred by handing over the query, and **a joined result across two tables carries an authority a single panel does not, which is precisely what makes an unstated boundary dangerous rather than merely incomplete.**

**The claim the design will not let the learner make is the coverage claim.** **No published figure states what proportion of the agents actually present in a tenant the inventory discovers**, and no detection rate or false-positive rate is published for any signal in that material. So the query returns the population that emits; whether that is the estate is unmeasured. **This is the same shape as §3.9's completeness silence one layer up, and the repetition is the finding**: at the trace level and at the estate level, the platform supplies a record and declines to characterise it as a sample. **Its limits:** newer than anything else in this research set and extremely perishable, substantially preview, with three announced capabilities carrying a future date and unverified, an announcement page that arrived fragmented with capability tables reduced to headers, and several central pages — including the inventory table's own schema — not read at all.

## 4. Session design and its warrant

The eight movements run situation, artefact, material, workflow, standard, failure modes, exercises, limits.

**Opening item 2 — what are you collecting that nobody aggregates and nobody alerts on — is the instrument.** It is asked before instruction and most learners cannot answer it, because the information required to answer it is exactly the information the estate does not maintain. **The inability is the finding**, and it arrives before anybody has been told what the session is about.

**4.1 The opening items are a generation phase and are deliberately unscaffolded.** The design is Productive Failure: learners generate answers to a problem they have not been taught, fail, and are then taught ([research/04-professional-formation/sinha-kapur-productive-failure.md](/research/04-professional-formation/sinha-kapur-productive-failure.md)). The mechanism relied on is the **failed generation effect** — attempting an answer before instruction improves later learning even when the attempt is wrong — and the binding condition is that the generation phase must not be helped, because guidance that reduces the failure rate reduces the learning. This is why the release rule gates §§4, 5 and 9 rather than merely recommending an order. **The source's limits are recorded and material: it is a trade book resting on school, university and laboratory evidence, and no adult-professional study appears in its reference list.**

**4.2 Why exercise 3 is a comparison and not a rewrite.** The same research tested exactly this: presenting a correct answer beside a learner's wrong one produced no benefit, and only the condition *instructed to compare them* learned more. Exercise 3 therefore forbids rewriting the item-2 answer until the learner has written one sentence naming the difference between it and the criterion. **A design that cited this mechanism and then simply showed learners the right answer would be violating the thing it was resting on**, which is a defect this repository has caught in itself before and expects to catch again.

**4.3 The workflow is ordered deliberately and the order is the design.** Question column, then deletion, then repository, then dimension, then register, then correlation, then the query with its coverage boundary, then the content-recording decision, then attack. Any other order produces a defensible artefact for the wrong reason: putting the configuration in the repository first preserves the estate you already had, in a better place. **Emitting the dimension before writing the register would be worse still**, because it teaches that attribution is something you switch on rather than something you decide. **The content-recording decision is placed last of the constructive steps for the same reason** — a learner who switches content capture on before writing the register will have collected the words before establishing which question needed them, which is the session's whole failure mode expressed in one setting.

**4.4 Why the agent is used to attack the register rather than to build it.** Enumeration and citation are what the tooling is good at; deciding what matters is what it is not. The session gives it the harder half deliberately — arguing that each retained question is a caption invented to justify an existing panel — and requires the rejected objections to be recorded. This is the same instrument [S001](/wiki/seminars/S001.md) installed and the same standing commitment: **an agent that agreed with you was not used as an instrument.**

**4.5 Why the closing exercise asks the second question rather than the first.** Naming the decision a panel changes is easy and most learners can do it for at least one panel. **Asking what would be lost if a kept signal stopped is the discriminating question**, because the honest answer is usually "we might want it", which relocates the signal to the review list. The exercise also requires the learner to notice *who* says that sentence, because if it comes from the author rather than the stranger the artefact has not yet been separated from its author.

## 5. Predicted failure modes and countermeasures

**The retrofitted question.** The likeliest failure: the learner writes questions that the existing signals happen to answer. *Countermeasure:* the ordering of the workflow, stated in the session as the thing being done rather than as advice, plus the closing exercise's second question, which a retrofitted table cannot survive. **§9's prediction 4 predicts this countermeasure failing.**

**The empty deletion list.** *Countermeasure:* the standard names a non-empty deletion list as a checkable property, and requires each entry to name what will now be missed — which is harder to fabricate than a deletion.

**The preserved estate in a better place.** The learner puts everything into source control unchanged and reports success. *Countermeasure:* the deletion pass precedes the repository pass, and the closing exercise asks about a kept signal rather than a deleted one.

**Tracing as an incident tool.** *Countermeasure:* named in the failure list with its warning sign, because it is a belief rather than an oversight and beliefs are not corrected by procedure. The material states the source's own framing — that the purpose is not reactive — rather than asserting it in the design's own voice.

**The undeclared privacy surface.** The learner logs prompts and completions because the gateway documentation recommends logging, and writes nothing about who may read them. *Countermeasure:* the privacy line is a required part of the artefact, and the material states explicitly that **the documentation recommends the logging and discusses none of its implications**, so the learner is told in advance that no tool will prompt them.

**The specification that does not match the running configuration.** *Countermeasure:* opening item 5, and the requirement that the configuration be deployed from the repository rather than described by it.

**The unpinned platform claim.** The learner observes the vendor's tracing surface and reports what they saw as though it were a property of the product rather than of one host, one version and one date. *Countermeasure:* the workflow requires a pin, and the material now states the note's own instruction to re-verify any syntax against the version actually running. **§9's prediction 6 is attached to this one**, re-pointed from the citation gap to the failure the closed gap makes more likely rather than less: **a learner who can now walk a documented trace is more likely, not less, to treat it as complete.**

**The coverage claim nobody measured.** The learner writes a query across the agent inventory, gets a clean joined result, and reports it as the estate. *Countermeasure:* the coverage sentences are a required part of the query file rather than a note in the commentary, the workflow puts them in the same artefact, and the exercise is scored on the comment block rather than on the query. **The material states in the design's own voice that the result is the population that emits and that no published figure says how far that is from the population that exists.**

## 8. Objections and rebuttals

**Objection 1: requiring a named asker for every signal will delete the telemetry you need for the incident you have not had yet, and incidents are exactly the situation where you cannot know in advance what question you will want to ask.**

At its strongest: the value of observability is optionality. The signal that resolves an outage is usually one nobody thought to specify, because if anybody had thought of it the failure mode would have been designed out. **A specification that keeps only what somebody currently asks about optimises for the incidents you have already had**, which are the ones least likely to recur. The rule therefore removes exactly the surplus that makes an estate useful, and it does so with an argument about cost that sounds disciplined and is short-sighted.

**Conceded in substantial part.** The rebuttal narrows the requirement rather than defending the strong form: the session does not require deletion of everything without an asker, it requires **a decision, recorded, with a date** — and the review list exists precisely so that a signal can be retained deliberately as cheap optionality rather than by default. That distinction is the whole of the design's answer, and it is thinner than the objection. **The declined fix is a coverage element requiring a minimum breadth of retained signal.** It is declined because nothing available to this programme could set the threshold, and a threshold set by the marker would be an opinion in a specification's clothing — the same reason [WP-060](/wiki/whitepapers/WP-060.md) §8 declines an accuracy element. **The residual risk is real: a learner following this session will delete something they later want, and the session cannot tell them which.**

**Objection 2: an estate held as code is slower to change during an incident, and incidents are when observability changes matter most.**

At its strongest: an engineer three hours into an outage who needs a new panel does not want a pull request. The console exists because it is fast, and the review argument optimises for the calm case at the expense of the case that hurts.

**Not conceded, and the rebuttal is specific.** The requirement is that the estate is *deployed* from the repository, not that no human may ever touch a console. **The failure the session targets is the change that was made in an emergency and never came back** — the panel added at three in the morning, the threshold raised to stop the paging, both of which then persist unreviewed and unattributed for years. Holding the estate as code does not prevent the emergency change; it makes the emergency change visibly divergent, which is the property that gets it reconciled. **The declined fix is an exemption for changes made during an active incident.** Declined because an exemption keyed to a state the team declares is a self-granted exemption, which is structurally the pattern [S054](/wiki/seminars/S054.md) traces end to end. **The cost is that reconciliation is real work and this session does not schedule it**; [S063](/wiki/seminars/S063.md) picks up the alert half of the problem and nothing picks up the dashboard half.

**Objection 3: the session's platform half teaches a vendor policy syntax that will be obsolete before the cohort graduates, and dresses a configuration exercise as a design lesson.**

At its strongest: the policy element names, their attributes and their tier availability are documented as perishable by the very note the session cites. A learner who spends part of a session attaching dimensions to an emitted metric has learned a product surface, and the session's claim that they have learned something about design is the standard justification every vendor course gives for teaching its own configuration. **And the objection is now broader rather than narrower**, because the session has since added a span vocabulary, an environment variable, two table names and a join — which is to say the perishable half grew.

**Partly conceded, and the growth conceded outright while the argument is not.** On the first half: the durable claim is not the policy but the asymmetry — **a dimension that was not emitted cannot be recovered by any later analysis** — and that claim is not a fact about a product, it is a fact about telemetry. The session is designed so that the learner meets the asymmetry by experiencing a question becoming answerable when nothing about the traffic changed, and a description of that experience does not produce it. The perishable half is quarantined in the perishability table and in the requirement to record the date the names were verified.

On the growth: **conceded, and the mitigation is that every added element is assessed for the decision it forces rather than for the string it uses.** Content recording is assessed as a privacy decision with a named owner and an enumerated reader set, not as an environment variable. The query is assessed on its comment block — the coverage boundary — and not on its syntax; the exercise says so explicitly and asks for the comment block to be submitted rather than the query. **The declined fix was to drop the tracing half of the anchor and teach only the gateway.** It was declined before the note existed, because the two halves answer different questions — the gateway sees traffic and the tracing surface sees a conversation — and a session that taught only the half with a note would leave learners believing that per-consumer token metrics are what observability of an agent means. **It stays declined now for a different and better reason: the note exists, the surface is teachable with warrant, and the thing that made the refusal necessary has gone.** What remains is that **a cohort will still observe a product surface whose completeness this repository cannot check them against**, and §9's prediction 6 exists to detect what that costs.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** Most learners will be unable to answer opening item 2 before instruction. *Instrument:* the submitted opening answers, coded *specific signals named* / *general acknowledgement* / *absent* by a second reader.

**Prediction 2.** Deletion lists will be shorter than review lists. *Instrument:* a count of entries on each, per learner, recorded without comparison to any target.

**Prediction 3.** Learners will name the decision a panel changes more readily than they will name what would be lost if a kept signal stopped. *Instrument:* the closing exercise, recorded as *answered* / *not answered* for each of the two questions.

**Prediction 4.** Most question columns will have been written against signals that already existed rather than derived independently. *Instrument:* a second reader comparing the question set with the pre-session signal inventory, coded *derived* / *retrofitted* / *cannot tell*. **This predicts the failure of the session's principal countermeasure** — the ordering of the workflow — and if retrofitting dominates, the session should require the question table to be submitted before the estate is examined at all.

**Prediction 5.** Privacy lines will be the most frequently omitted or thinnest part of the submitted specification, and thinner than the correlation statement. *Instrument:* the submitted artefacts, with each of the six required parts coded *complete* / *present but generic* / *absent*. **This is the design's own test of whether stating a documentation silence is enough to make learners act on it**, and a confirmation means the silence must be converted into a required prompt rather than a warning.

**Prediction 6.** Learners will treat a trace as a complete record of what the agent did, and will report a coverage claim — for a trace or for a query across the agent inventory — that no published figure supports, in at least one platform claim in the [S065](/wiki/seminars/S065.md) defence. *Instrument:* the defence transcript, coded for coverage claims made, qualified or absent, and separately for pinned versus unpinned platform claims. **This prediction was re-pointed when §3.9's gap closed.** It formerly instrumented the citation gap; it now instruments the completeness assumption, which is the failure the closed gap makes *more* likely rather than less — a learner who can walk a documented span tree has every reason to believe it is exhaustive, and nothing in the documentation tells them it is not. **A confirmation means the completeness silence must be converted into a required field on the register rather than a warning in the material.**

**Prediction 7.** Learners who ran the agent against their own register will delete or relocate more signals than those who used it to enumerate. *Instrument:* the recorded rejections against the deletion and review list lengths, per learner. **If this fails, the session's use of the agent as an adversary rather than an assistant has no support at this scale**, and the step should be rewritten as an assertion rather than presented as a demonstration.

## What a learner should take from this paper

**What the design claims.** That a signal with no named asker will never be deleted and never be defended; that peer review is the reason to hold observability as code; that the cost of keeping a thing is a more decidable basis than what the thing means; and that **attribution is a design property of the telemetry rather than a property of the data.**

**What the evidence licenses.** Nothing about outcomes. The observability rules are class 1 — verified from a complete reading of a public document — and **that document supplies no comparative evidence for any of them.** The control-theory framing and its operationalisation into alertability and actionability are also class 1, from a complete reading, but the source is practitioner guidance rather than research and states no measurement that its practices outperform anything. The platform mechanism is class 4 — grounded in vendor documentation read in full, which publishes **no performance or cost data of any kind.** The claim that a question written first is different from a question written second is class 3.

**Where the design is thinnest.** §3.9, still — but for a different reason than before. The anchor formerly named a surface this repository held no note for; that is closed. What replaced it is worse for the learner and better for the design: **the platform publishes no measure of how complete a trace is, and none of how complete an agent inventory is.** The design cannot repair either, so it names both and instruments the assumption at prediction 6.

**The concession worth remembering.** This session will make you delete something you later want. It has no way to tell you which one, and its only honest answer is that the decision was recorded and dated so that you can find out what you gave up.

## Evidence status

**Verified in this repository.** That observability configuration must be held in source control and deployed by infrastructure as code, with peer review named among the reasons; that data collected but not aggregated or alerted on must be reviewed to establish whether it is still required, and that teams should collect and measure what they need rather than what they can; that a raised exception should be logged only once; that personally identifiable and customer-sensitive information must never be logged and that sensitive data should be kept out of URLs because request URLs are typically logged by proxies and web servers; that a unique or high-cardinality string must not be used as the value of a metric label; that a correlation identifier must be assigned as early as possible; that the distinction between logs, metrics and traces is drawn by data volume and processing cost rather than by semantics; and that tracing is framed as an optimisation instrument whose purpose is not reactive.
