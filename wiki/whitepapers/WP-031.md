# WP-031 — Concurrency Is a Specification Problem

**Seminar day:** [S031](wiki/seminars/S031.md) · **Module:** [M07](wiki/modules/M07.md) · **Quarter:** [Q4](wiki/quarters/Q4.md)
**Strands:** SY · CF · MS · **Complexity class:** 3
**Platform anchor:** Azure API Management AI gateway — the `llm-token-limit` policy as a shared counter · **MCP servers:** Azure MCP Server (write) · Microsoft Learn MCP Server

## Abstract

This paper defends opening the concurrency module with a day on which no application code is written and no defect is fixed, and defends supplying an execution that no group could have constructed. The first argument is that concurrency's characteristic student failure is treating it as sequential programming with an elusive bug, that this framing makes debugging the natural response, and that debugging cannot answer a question about which correctness property should hold — so the framing must be displaced before any implementation work occurs. The second argument is that the space of executions is not the space a student can imagine, that this is an epistemic fact rather than a skill deficit, and that demonstrating it with an execution the room provably did not construct is the only way to establish it without inviting students to try harder. The paper additionally defends assessing the cost of properties *not* chosen, and defends re-anchoring the day on a metered gateway whose documented rate limit is approximate — so that the unconstructable execution is a published property of a billed service rather than a constructed teaching case. It concedes that a day withholding implementation may not survive contact with students' expectations, that the four-property ordering is a simplification whose boundary the day names and does not police, and that the day now hands students write access to real infrastructure on the strength of an argument it has not tested.

## 1. The instructional problem this day must solve

Students arrive holding correctness as a binary property of program text. A concurrent program that misbehaves is, on this model, a program containing a bug, and the response is to find it.

The model fails for a reason that is structural rather than difficulty-related. A concurrent program does not have *a* correctness property. It may be linearizable, or sequentially consistent, or causally consistent, or eventually consistent, and each is a distinct promise with a distinct cost. The question "is this correct?" has no answer until someone says which promise is being made — which is why phase 1 item 1 is unanswerable as asked, and why most students answer it anyway.

Displacing the model is the day's whole purpose, and it must happen before implementation work begins. A student who spends the module debugging will emerge able to fix races and unable to say what a component guarantees, which is precisely the engineer the module exists to prevent. Hence the day's most conspicuous decision: **no application code is written and nothing is fixed**, and the assessed artefact contains no implementation.

The day's second problem is epistemic and is harder. Students who accept that interleavings matter will attempt to enumerate them, and will believe that careful thought covers the space. It does not. The number of interleavings is large, the ones that matter are not the ones that are easy to imagine, and the scheduler's choices are neither adversarial nor random but shaped by factors outside the program.

Establishing this by argument invites students to try harder. Establishing it by demonstration — supplying, after groups have committed, an execution that no group constructed and that violates a property they judged satisfied — establishes it as a fact about the situation rather than about their diligence. Phase 3's design turns on this and the execution must genuinely be one that requires a pattern nobody would try.

**Re-anchoring the phase on a real gateway improved this argument in a way the design did not anticipate.** The previous construction supplied an unusual thread schedule, and its force depended on the students believing that the schedule was reachable. The gateway's version supplies a burst of concurrent requests against a token limit, the overshoot is measured in tokens the students are billed for, and **the vendor's own documentation states in advance that it will happen** — concurrent or near-concurrent requests can temporarily exceed the configured limit, because consumption is not known until the backend responds. A group that missed it did not fail to imagine a clever schedule. It failed to read the specification of the thing it was relying on, which is a different and more useful lesson and is the one the module is about.

The third problem is a specification defect so common it is nearly universal: student specifications are entirely safety properties, and a program that does nothing satisfies them. Point 6 addresses it and step 5 requires a liveness property, and the specification item fails artefacts without one. The platform sharpens this too: a gateway policy that rejects every request satisfies the strongest safety reading of "limited to 500 tokens per minute."

## 2. Entry state and prior knowledge assumptions

- **S006's invariant vocabulary,** twenty-five weeks old, retrieved regularly, and about to be generalised to interleaved execution.
- **S017's scheduling material,** which established that execution order is decided by a policy the programmer did not choose.
- **S023's acceptance of proved impossibility,** without which S034's trade-off will be read as a temporary limitation. [WP-023](wiki/whitepapers/WP-023.md) §9 predicted this dependency.
- **M06's construct discipline,** which point 7's specify-before-implement extends from measurement to correctness.
- **Class-3 mode, new.** This is the first day on which the success criterion is the student's.
- **A strong debugging reflex,** universal, and the day's principal obstacle.
- **Copilot in agent mode since Q1, and the Azure MCP Server in read configuration since Q2.** **Write access is new today** and no student has created or deleted an Azure resource. The design assumes none can predict what an agent will produce from an underspecified infrastructure request, which is what item 5 measures.
- **No experience of a rate limit.** The design assumes students hold "limit" as an exact bound, which is the misconception phase 3 exists to break.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**The module's peak, and the programme's highest to date.** This is a deliberate departure from the design's usual practice of placing the hardest day at a module's midpoint.

The reason is that concurrency does not admit incremental approach. A student who has not accepted that executions are the object of reasoning will treat S032, S033 and S034 as debugging days, and no amount of later scaffolding recovers the framing. The module therefore front-loads its hardest idea and accepts the consequences.

Management, which is aggressive:

- **No implementation.** The day's entire capacity goes to specification.
- **One program throughout,** small, and read once at phase 1.
- **Four properties supplied precisely,** so no capacity goes to formulating them.
- **Six executions supplied at phase 1** and further ones at phase 3, so students judge rather than generate — except at step 6, which is the single generative demand.
- **The precise-statement form supplied** at step 3.
- **The same gateway instance across the module.**
- **All policy syntax supplied or agent-authored.** This is the load decision the practical turn required. Adding a real service to the programme's highest-load day would be indefensible if students had to author configuration; **the difficulty is entirely in predicting and explaining behaviour**, and every artefact needed to produce that behaviour is given or generated.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *An unanswerable pretest item,* which most students answer.
- *The unconstructed execution,* phase 3's payload.
- *Stating the cost of the properties you did not choose,* step 6 — the day's discriminator.
- *Requiring a liveness property,* step 5.
- *The consumer's expectation elicitation,* phase 7.
- *Naming the gap between what you specified and what the configuration currently guarantees,* step 7, which is left unresolved for four days.
- *The sealed Copilot prediction,* item 5, which requires a student to predict correct output and name what it will not tell them — a harder discrimination than predicting an error.

**Deliberately not selected.**

- *Any implementation or debugging.* Refused entirely, and defended in §8.
- *Formal verification or model checking.* Named at point 2 as the systematic alternative to testing and not taught; SY201's material.
- *Memory models.* Genuinely important, entirely omitted, and the day says so.
- *Constructing the correctness properties.* Supplied precisely, because imprecise student-generated properties would make phase 3 unadjudicable.
- *Authoring policy from a blank file.* Refused, per §3.1.
- *Measuring the overshoot's magnitude.* The documentation publishes no bound and the day does not invite students to estimate one from a single session, which would be a sample of one condition presented as a property.

**Scope, per the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md).** Point 3's four properties are a selection ordered by strength. They omit serializability and its transactional variants — which belong with SY103's database material and are named as such — and the several intermediate properties that matter only at large scale. The selection criterion is that these four are the ones a caller can *distinguish behaviourally*, which is the day's operative test since step 4 requires the cost to be stated in the caller's terms. The day names the omission and does not police it: a student who specifies serializability is not corrected, and this is a deliberate looseness rather than an oversight.

**The platform instance, scoped in the strong form.** The day teaches a rate limit as a correctness property, and the simplification must carry its safe and unsafe conditions because students will otherwise carry it into work this day does not supervise.

*Safe.* Deciding what to promise a consumer about their allowance; explaining a charge a consumer disputes; reasoning about why an exact limit would require coordination and what that coordination would cost; and recognising that a configuration satisfying a safety property may serve nobody. In each of those the identification of a limit with a correctness property is sufficient and correct.

*Unsafe.* **Claiming that the gateway holds any particular bound.** The documentation states that enforcement is approximate, that counters are not aggregated across gateway instances, regions or workspaces, and that concurrent requests can exceed the configured value — and it publishes no bound on any of it. A student who has watched their own overshoot and infers a magnitude has generalised from one condition on one tier. It is equally unsafe as an argument about any other product's limits by analogy, and unsafe as a model of instruction-level concurrency: **there is no memory model here, no interleaving of instructions, and the shared state is a counter in a distributed cache.** The structural correspondence is between *a shared resource updated by concurrent parties whose updates are not instantaneous* and the same, which is real; the mechanisms are not the same and the day says so at point 9.

Step 7's current-versus-specified gap is where a student applying it outside that range would fail, and the seminar page carries the statement so that the boundary reaches students rather than only this paper.

### 3.3 Engagement and motivational mechanism

The day runs on **a question that turns out to be malformed**.

Item 1 asks whether a program is correct. Students answer. The answer is not wrong — it is not the kind of thing that can be wrong — and discovering that a question they answered confidently had no content is a more disorienting experience than being contradicted. Item 3's reframing, that the disagreement about execution 4 is a disagreement about the criterion rather than about the program, is where the day's content becomes visible.

Phase 3's unconstructed execution supplies the second and stronger mechanism. Groups commit judgements, are shown a pattern they did not think of, and it violates a property they had cleared. The design's insistence that this be genuinely unconstructable by the room is what makes it evidence rather than a trick — and on the platform it is better than unconstructable, because it is *published*, so the demonstration ends in a documentation page rather than in an instructor's cleverness.

Withholding implementation is itself a motivational decision with a cost. Students expect to fix something and do not, and some will experience the day as incomplete. Two things answer this now that did not before. Step 7's explicit gap converts frustration into an open loop. And **the day ships something** — a deployed policy on a real gateway, measured — so the absence of implementation is no longer an absence of building.

The competence risk is low in one sense and high in another. No student fails to produce a specification; many produce one that phase 7's partner reads as promising more than it says, which is the day's characteristic and expected outcome.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Five items on a small program and on the gateway about to be deployed. Item 1's unanswerability and the room's willingness to answer it constitute the day's opening finding. Item 4 predicts the disagreement, which turns out to be about the criterion — the design's standard construction for making a distinction the students' own discovery. **Item 5 is the sealed Copilot prediction** and is administered here rather than later, per instrumentation rule 8. It is deliberately not a prediction that the agent will fail: the agent's policy is correct, and the item asks what a correct policy will not tell you, which is the same discrimination the whole day is about.

**Phase 2 (20 min).** A twenty-five-week bridge asking what an invariant must establish and preserve when two threads run it. The answer generalises S006 to interleaved execution and is point 8's content delivered as retrieval.

**Phase 3 (45 min).** One configuration, four properties, committed judgements, then the supplied burst — **executed against a metered deployment rather than argued about.** The phase's critical dependency is unchanged: the supplied pattern must be one students would not attempt. What changed is the adjudicator. Groups now send traffic and read what was charged, so the properties are settled by measurement, and the closing task asks what the student would require *as the consumer paying for it*, which introduces the caller frame the module uses throughout and attaches a price to it.

**Phase 4 (50 min).** Ten points. Point 1 is the day's retained sentence. Point 2 distinguishes this from S009 explicitly, because students will otherwise apply S009's falsification discipline and find it inadequate without knowing why. Point 3 carries the scope statement. Point 6 addresses the safety-only defect. Point 8 closes the S006 generalisation. **Point 9 works the overshoot completely and marks every number in it perishable; point 10 names three defaults, of which the most instructive is that streaming overrides an explicit `estimate-prompt-tokens` setting — a default that defeats a decision rather than filling a gap; and point 11 records the documented silence, that no bound on the overshoot is published anywhere.**

**Phase 5 (90 min).** Seven steps at class 3, **deploying a policy and specifying what it guarantees** rather than describing a component. Step 6 is the discriminator and is modelled once because exhibiting a violating execution is genuinely hard. Step 7's gap is the module's driving problem and is deliberately left open — and is now measurable rather than argued, which is a material improvement: a student can compare what they specified against what they charged. The three Copilot Practice Standard elements attach here.

**Phase 6 (40 min).** A component with no specification that behaved correctly and then did not, then the agent case. The instructor disclosure's attention to whether anyone could say what it was supposed to guarantee is the phase's content: there was no mistake, which is why the failure is hard to disclose and hard to prevent. **The agent case is chosen so that every artefact in the chain is individually defensible** — the request, the policy, the review, the deployment — and the failure is located at the boundary between a requirement and a mechanism, which is where this module says failures live. It is deliberately not a case of the agent producing bad output, because a cohort taught that agent failures look like bad output will not recognise the ones that matter.

**Phase 7 (30 min).** Consumer expectation elicited from the specification alone. Structurally identical to S028's sentences-only protocol and deliberately so — a specification and a licensing sentence fail the same way, by being read as promising more than they say. **Per [WP-034](wiki/whitepapers/WP-034.md) §8 this protocol's rate is no longer compared across days**, and §7 below records the retraction.

**Phase 8 (20 min).** The item 1 answer rate, the execution 4 disagreement's true subject, the coverage question, and the sealed item 5 predictions opened against what the agent produced.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student with concurrent programming experience will recognise the properties and may find phase 3 straightforward. Predicted failure: they specify what the component *does* rather than what the caller *needs*, because practitioner experience is dominated by working within existing guarantees rather than choosing them. Countermeasure: step 1 requires the consumers first and step 7 requires the gap between specified and current to be named — a student who has specified the current behaviour will produce a gap of zero, which is visible and is the diagnostic.

**Students with less relevant prior knowledge.** The day's load is the programme's highest and arrives with no implementation to anchor it. Countermeasures: no application code, one small program, supplied properties, supplied executions, a supplied statement form, and agent-authored configuration. Residual risk: step 6's execution construction may be unreachable, and the fallback is to select a violating execution from those run at phase 3 and explain the consumer's indifference, which preserves the reasoning and loses the construction.

**Phase 3 is too easy.** The two satisfied and two violated properties are usually judged correctly. The phase's difficulty is entirely in the supplied burst, which no group is expected to have anticipated. Fallback if a group does anticipate it: ask them to predict whether the overshoot grows, shrinks or stays constant as concurrency rises, and to say what evidence would settle it — which is a genuine question the documentation does not answer and which previews S032.

**The platform fails on the day.** New, and it is a real operational risk that the previous design did not carry. A gateway that will not deploy, a quota that will not grant, or a model deployment that is throttled removes phase 3's adjudicator and phase 5's build on the module's most load-bearing day. Countermeasures: the gateway is deployed and verified by staff before the room arrives rather than by students at phase 3; a recorded set of measured results from a prior cohort is held so that phase 3 can be adjudicated from data if the live service is unavailable; and where that fallback is used **the day states that the cases were demonstrated rather than operated and the phase 5 build is not assessed**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

**Affective failure.** Two.

The first is **frustration at the withheld implementation**. Countermeasure: step 7's open gap, an explicit statement that the module ships a change at S035, and the fact that the day now deploys something.

The second and more serious is **learned helplessness about coverage**. A student shown that the execution space cannot be enumerated may conclude that concurrent correctness is unknowable and that specification is therefore pointless — which is the exact opposite of the day's argument, since the specification exists precisely because enumeration is impossible. Countermeasure: point 1's framing, that the set of executions is the object, is stated as an enabling move rather than as a limitation, and point 2 names model checking as the systematic response without teaching it. The design's position is that naming a tool it does not teach is better than leaving the impression that no tool exists, and this is the module's version of the fatalism risk M06 met four times.

## 6. Retention architecture

Retrieved by S032 (errors you cannot reproduce, where the unenumerable space becomes an evidential problem), S033 (partial failure), S034 (consistency models as a contract, which is this day's step 4 at full length), S035 (breaking a system that appears to work), S072 (orchestration patterns as control flow — agent orchestration is concurrency with a language model as one of the threads) and S074 (tool failure has four shapes).

S072 at roughly four quarters is the principal long-range target, and the correspondence is one the programme relies on: an agent invoking tools concurrently is a distributed system, and students who hold executions-as-the-object recognise it as one. **What transfers is the framing and not the gateway**, and the day's perishability register says so explicitly, because a student who has learned "token limits are approximate" and not "a shared resource updated by concurrent parties has no exact bound without coordination" has learned the wrong half and will not recognise the agent case.

Retained content: executions-not-text, the four properties with their costs, safety versus liveness, and specify-before-implement. Four items, no numbers.

Own schedule: next morning, day 3, week 2, week 6.

One specification item in SY201, containing no application code. **A specification containing only safety properties fails.** This is the module's first specification clause and targets the near-universal defect directly.

**Per the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md)'s rule 1 the checked elements are now stated on the seminar page and the item closes with *nothing else is assessed*.** This discharges, for this day, the repair [WP-028](wiki/whitepapers/WP-028.md) §8 specified and [WP-032](wiki/whitepapers/WP-032.md) §8 recorded as having been made in neither place. It is recorded here as discharged at S031 and S032 and not retrospectively at S028, per the standard's non-retroactivity boundary.

The artefact additionally carries the **prompt record, intervention record and frontier statement**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md). **An intervention record with no entries fails** unless the artefact demonstrates that the design could have detected an intervention-worthy error; the accepted form here is a stated expected charge checked against a measured one before the configuration was accepted, which is the sensitivity escape [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected.

Programme instrumentation: the phase 1 item 1 answer rate is the cohort's malformed-question baseline; the phase 3 coverage-belief figure is the enumeration-illusion measure, re-probed at S035; **item 5's sealed prediction accuracy is this day's frontier-calibration datum**, recorded as two rates — predicting the policy, and naming what it would not tell you — and read by next year's cohort through the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md), per instrumentation rule 9.

**The phase 7 over-expectation rate is no longer compared with S028's.** [WP-034](wiki/whitepapers/WP-034.md) §8 established that the document-only protocol's first questions index familiarity with the instrument by their third administration, and retracted the pairing this section previously drew. The rate remains recorded as a within-day observation and no trend is claimed from it. **This also removes prediction 4 from §9 as originally stated**, and it is restated below in a form the retraction permits.

The frontier statements are a sample and the day says so, per instrumentation rule 3: one cohort, one gateway instance, one tier, one model deployment, on a task chosen by staff to have a known documented surprise available. A frontier map assembled from them describes this task and not the agent.

Dispositions: **humility**, at step 7, where naming a large gap between one's specification and the configuration's actual guarantee is the honest and less comfortable output.

## 8. Objections and rebuttals

**Objection 1: a concurrency day with no implementation will not survive contact with students.**

At its strongest: students come to a concurrency day expecting to encounter races, to see something go wrong, and to fix it. Withholding all three for six hours means the day's most vivid available experiences are all absent, and the specification work — which is abstract, textual and unresolved by design — has to carry the whole session. The likely outcome is not that students reject the argument but that they disengage from it, and a disengaged student produces a specification that satisfies the form.

The rebuttal is that the vivid experiences are precisely what installs the wrong framing. A student who has spent a day chasing a race has learned that concurrency is about races, and the module's four remaining days will be read through that lens regardless of what they say. The design's judgement is that the framing is worth more than the engagement, and that the engagement is recovered at S032 and S035.

**The practical turn weakens this objection without answering it.** The day now deploys a real policy and measures a real overshoot, so the absence of implementation is no longer an absence of anything happening. What is still withheld is *fixing*, and the objection's core — that students want to repair something — stands.

The concession is that the judgement remains untested and the design has no fallback. If phase 8's coverage-belief figure shows that students left believing they can enumerate executions, or if the phase 7 over-expectation rate is very high, the day has failed and the module's remaining four days will be miscalibrated. The mechanism for detecting this before S032 begins — absent when this paper was first written — is now [S032](wiki/seminars/S032.md)'s phase 0, which was added in response to this concession and whose result is reported at S032's phase 8.

**Objection 2: the day teaches four properties and declines to police their boundary.**

At its strongest: §3.2 states that a student specifying serializability is not corrected, on the grounds that the omission is named. But serializability is a transactional property with different guarantees and different costs, and a student who specifies it for a non-transactional component has made a category error that the day will not catch — the specification item's only structural clause concerns liveness. The scope statement discharges the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md)'s requirement in letter and leaves the student able to make an uncorrected error.

This objection the design does not fully answer. The looseness is deliberate — the day's purpose is to establish that a property must be chosen and defended, and correcting a student's choice of property risks re-establishing the sense that there is a right answer, which is the framing the day is displacing.

But the objection identifies a real gap between the scope rule's purpose and its effect. The rule was introduced so that students would know a taught list is incomplete; here it also functions as a licence for the day not to engage with what lies outside the list. **A scope statement that names an omission and then declines responsibility for it is a weaker artefact than the rule intended**, and this is the first case where that weakness is visible. The question it raised for the standard has since been answered elsewhere: the scope rule was widened to its strong form, and then widened again so that a day must carry an artefact element under which a student applying a simplification outside its safe range would fail. **This day's platform scope statement complies with the widened rule** — step 7's current-versus-specified gap is the artefact element — and its four-property scope statement does not. The asymmetry is recorded rather than repaired, because the widening applies from [S090](wiki/seminars/S090.md) forward and this day is not retrospectively amended.

**Objection 3: the day hands second-year students write access to real infrastructure, and its defence of that is an assertion.**

This is the objection that bites on the practical turn and it is the strongest in this paper.

At its strongest: today a student who has never created a cloud resource directs an agent to create several, on the module's highest-load day, while their attention is fully consumed by a genuinely difficult conceptual argument about correctness properties. The design's protections are that the environment is disposable and that the artefact carries an intervention record. Neither is a control. **A disposable subscription still bills, still consumes a real quota, and still permits the agent to create resources nobody notices** — the deletion of the resource group is not verified until S033. The intervention record is a self-report written after the fact by the person whose diligence it is evidence of, which is an instrument the programme's own measurement strand would reject in any other setting. And the deepest version of the objection is not about accidents at all: **a student who produces a working gateway configuration from three prompts has produced something they could not have written, and the day assesses their specification rather than their configuration precisely because the design knows this.** The assessment's silence about the configuration is not neutrality. It is an admission.

The objection is conceded in part and the concession has a shape.

What is defensible: the day's *assessed* competence is stating what a system guarantees, and that competence is not delegable to an agent — item 5 asks what a correct policy will not tell you, and no agent supplies that on the student's behalf, because it requires knowing what the consumer will do with the answer. The design's position, stated on the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), is that this is the whole of the programme's defence and it is applied here without softening.

What is conceded: **the day has no measure of whether a student could have produced the configuration themselves, and it makes no attempt to acquire one.** The programme's structural response to dependency — unassisted work at S010, S045 and S090 — does not touch infrastructure at all, and whether three occasions is enough is already recorded as unknown. This day makes the gap larger and does not widen the response.

**One cheap fix is available and it is made.** The seminar page's assessment now states its checked elements and closes with *nothing else is assessed*, and **the elegance of the policy, the number of prompts used and whether the agent's first attempt was correct are named as outside the specification.** That does not measure independence, and it does something adjacent and honest: it stops the day from rewarding fluent agent use, so a student who prompted well and specified badly fails, and a student who prompted badly and specified well does not. **The cheap fix that is not made** is requiring a student to state, in one sentence, what they would have had to look up to write the configuration unaided. It costs a line, it would supply the first datum the programme has on infrastructure dependency, and it is not in the design because the design is not confident the answer would be honest and has no way to check it. That is a reason and not a justification, and it is recorded as such.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** A large majority will supply a definite answer to phase 1 item 1, and fewer than a quarter will note that the question is underdetermined. *Instrument:* item 1 responses coded for definiteness and for underdetermination flags.

**Prediction 2.** No group will anticipate the phase 3 concurrency overshoot before it is run. *Instrument:* group property judgements recorded before the supplied burst, coded for whether any group's reasoning cited unresolved concurrent consumption. **If a group does anticipate it, the phase's epistemic claim is not established for that cohort and the fallback in §5 applies.**

**Prediction 3.** Students with prior concurrent programming experience will produce a smaller step 7 gap than those without. *Instrument:* gap size, blind-rated, against the admission background survey. **This is the specify-the-current-behaviour failure stated as a prediction.**

**Prediction 4.** Within this day, the phase 7 over-expectation rate will exceed the rate at which students' own step 3 specifications contain the missing guarantee. *Instrument:* phase 7 partner responses against the specifications they read, paired. **This replaces the cross-day comparison with S028 that [WP-034](wiki/whitepapers/WP-034.md) §8 retracted, and it is answerable within one administration, so it is not affected by the cohort learning the protocol.**

**Prediction 5.** A large majority of item 5 sealed predictions will correctly anticipate the policy the agent produces, and a small minority will name a specific thing it does not tell them — the overshoot, the non-aggregation of counters, or the streaming override. *Instrument:* item 5 responses coded for correct-policy prediction and for specific-omission naming, against what each student's agent actually produced. **The gap between the two rates is the day's frontier-calibration measure. If the specific rate is high, the cohort already holds the model phase 3 exists to install and the day's ordering is wrong; if the correct-policy rate is low, students are not yet able to predict competent agent output at all, which is a different and more serious finding about Q1 to Q3.**
