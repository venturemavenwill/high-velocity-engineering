# WP-006 — The Invariant You Did Not Write Down

**Seminar day:** [S006](wiki/seminars/S006.md) · **Module:** [M02](wiki/modules/M02.md) · **Quarter:** [Q1](wiki/quarters/Q1.md)
**Strands:** CF · MS · PE · **Complexity class:** 1
**Platform anchor:** GitHub Copilot agent mode; `*.instructions.md` custom instructions files · **MCP servers:** Microsoft Learn MCP Server

## Abstract

This paper defends placing a near-transfer test at the shortest gap the timetable permits, two days after the technique it tests was taught, and defends treating its outcome as a measurement of the design rather than of the students. The argument is that a technique which fails to survive a two-day gap and a change of setting was encoded situationally, and that discovering this in week six is worth more than any content the day could otherwise deliver. The paper further defends the requirement that every surfaced invariant be accompanied by a concrete breaking caller, on the grounds that this is the only available discriminator between an invariant and a plausible-sounding property, and that the same discriminator recurs at S009, S035 and S087 in progressively more expensive forms. It then defends the day's second and larger claim, which is the programme's anchor for it: **a specification and a repository custom instructions file are the same object in two registers, and the executable register reports its own defects immediately.** That claim is not argued but staged, by running one prompt against four configurations of which one is correct, saved, in the right folder and not in force. The paper concedes that the day's use of real substrate code introduces comprehension load the design cannot fully control, that its central transfer probe is confounded in a way that makes a negative result interpretable and a positive one much less so, and that the executed half licenses far less about specification quality than students will take from it.

## 1. The instructional problem this day must solve

S005 taught invariant reasoning in mathematics, on a machine the cohort had traced, with the property supplied. Every one of those conditions is absent in professional practice. Code arrives unfamiliar, the properties are not supplied, and nobody frames the situation as an invariant problem. The competence S005 built is worth nothing unless it fires under those conditions, and there is a substantial literature-supported expectation that it will not: techniques encoded in one setting frequently remain bound to it.

This is the module's sequencing bet, and it is testable. If a cohort that proved a loop invariant on Tuesday cannot recognise one in code on Thursday, the encoding was situational and the programme's entire assumption that mathematical technique transfers to engineering practice is in question — in week six, when it is still cheap to act on.

The day's second problem is the professional one. Unwritten invariants are the dominant failure mode in systems that have more than one caller and more than one author, and they have a property that makes them pedagogically awkward: **the failure has no author.** Nobody wrote a bug. A function that was correct for its caller became incorrect when a second caller appeared, and neither party did anything wrong. Students whose model of defects is "somebody made a mistake" have no category for this, and the category is required by S033's partial failure, S068's detectability and S079's drift.

The third problem is one of stance. Phase 5 step 2 — write the caller that breaks it — installs a discipline that the programme relies on for three years: **a claim you cannot construct a violation of is not a claim you have understood.** That discipline reappears as the falsifying test at S009, the deliberate break at S035, the adversarial input at S076 and the residual-risk statement at S088.

The fourth problem is the one this day is the programme's anchor for, and it is not a problem about invariants. **Students arriving in week six believe a specification is a description of intent.** It is not an unreasonable belief: every specification they have ever written was read by a human who reconstructed the intent behind the words, and so the words never had to carry it. The belief survives ordinary specification instruction because ordinary specification instruction has no mechanism for refuting it — a marker who understood what you meant cannot show you that you did not say it.

A repository custom instructions file has that mechanism. It is a specification whose conformance is checked by execution rather than by reading, so a file that describes intent and does not constrain output produces non-conforming work in front of its author within a minute, and the file is the only thing that changed. **The register does not make the point better; it makes it attributable**, which is a different and larger property. This is why the equivalence is anchored here rather than in a technical-communication course: the day already requires students to state a property precisely enough to construct a violation of it, and the instructions file is the same demand with a machine supplying the violation.

The two failure modes the file exhibits map exactly onto the two the day already teaches. A precondition too weak does not protect; an instruction that asks for a quality judgement the agent cannot make will get one, and it will not be yours — **specification rule 1**. A precondition detached from what it qualifies does not travel; an instruction that says *cite sources* without saying *in the same sentence as the claim* produces detached citations — **specification rule 2**. Neither rule is new. What is new is that the day can now demonstrate both in four minutes rather than assert them.

## 2. Entry state and prior knowledge assumptions

- **A two-day-old invariant technique** with three named obligations, proved once on a known loop.
- **The S004 reader question**, used at phase 4 point 5 without re-explanation. This day treats two prior days' protocols as available infrastructure.
- **The S003 cost habit,** now expected at step 5 rather than prompted.
- **Substantial variation in code-reading experience,** larger than the variation in proof experience and less well managed. This is the day's principal equity problem and is addressed by scale rather than by scaffolding: the phase 1 sample is forty lines.
- **No experience of specifying an interface.** Almost no student has written a precondition deliberately.
- **No experience of configuring an agent.** Students have used Copilot in chat since S001; none has written a file that changes what it does. The `applyTo` syntax and the folder convention are therefore supplied in writing at the moment of use, and are not assumed.
- **An outstanding S005 commitment** — the module-closure paragraph — which is not revisited here.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**High, and higher than S005 in one respect the design cannot fully mitigate.** S005's subject program was known to every student; S006's is not. Comprehension load is therefore added on top of interactivity that is already high, because invariant strength is an interaction between the property, the body and the caller — none of which can be considered alone.

Mitigations, in order of importance:

- **Scale.** Forty lines in phase 1, two hundred in phase 5. Both are far below what a professional would call a module and both are chosen so that comprehension is achievable within the phase.
- **Phase 3 removes comprehension entirely.** One body, seen three times, so that after the first reading all attention is on the specification. This is the day's most important load decision: the strength trade-off, which is the hardest idea, is met under the lowest comprehension load available.
- **The caller is supplied in phase 3 and constructed in phase 5.** Constructing a breaking caller is much harder than recognising one, and the two appear in that order.
- **Fading in phase 5** across steps 1 and 2, with steps 3 to 5 independent.
- **Perishable mechanism detail is marked and excluded** from what must be retained, which removes a real quantity of language-specific material from the retention burden without removing it from the work.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *The concrete breaking caller,* phase 5 step 2. The day's defining difficulty and its discriminator.
- *Writing preconditions that are sufficient and usable,* phase 3's generation demand, where the too-strong first attempt is the intended outcome.
- *Case D,* whose defect is in a property of the file nobody was asked to look at. This is a difficulty of attention rather than of reasoning and it is deliberate: the design wants the room to have been fooled once, cheaply, by something the documentation states plainly.
- *The partner's legitimate-caller attack,* phase 7, which reproduces phase 3's error in the student's own work.
- *A cross-day bridging retrieval,* phase 2's final item, which requires applying S005's vocabulary to a case S005 did not cover and which almost nobody answers.
- *A two-day gap with a setting change,* which is the day's structural difficulty and its measurement.
- *The sealed frontier prediction at phase 1 item 5,* whose second half — where will it be wrong — is much harder than its first and is expected to be answered badly.

**Deliberately not selected.**

- *Unfamiliar language.* The substrate code is in the teaching language. Changing the language would move the difficulty into syntax.
- *Withholding the three locations.* Phase 4 point 2 names them. Vocabulary, not insight.
- *Discovering the strength trade-off unaided.* Phase 3 produces the felt difficulty; phase 4 point 3 resolves it explicitly. Leaving it unresolved would leave students with an experience and no handle.
- *Realistic scale.* Explicitly refused. Two hundred lines is not a realistic module and is not meant to be.
- *Withholding the `applyTo` syntax.* Refused. It is a convention, and a convention discovered by trial is a difficulty in the wrong place.
- *Any model comparison.* Refused. Comparing what two models do with the same file is a real and interesting question, it is [S029](wiki/seminars/S029.md)'s question, and running it here would replace the day's subject with a measurement problem the cohort cannot yet frame.
- *Assessment stakes on the same day.* The CF101 item is submitted afterwards.

**The strong-form scope statement, and where it binds.** The day teaches a simplification: that an instructions file and a specification are the same object. **That is safe for reasoning about how a requirement should be worded, how it should be scoped, and how its defects are found — which is everything the day assesses. It is unsafe in one direction: an instructions file is evidence about what the agent was given and never about what it did.** A student who carries the simplification into the belief that a conforming run demonstrates a correct file has adopted the confirmatory habit [S009](wiki/seminars/S009.md) exists to displace, two days early. The boundary is stated at phase 4 point 10 and is bound to the artefact: step 7 requires an attack, three runs of it, and a report of the variation, and **an artefact whose only evidence for its file is that the output looked right fails the specification.** That binding is the widened form of the scope rule recorded in the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md), applied here rather than deferred, because this is the day that introduces the simplification.

### 3.3 Engagement and motivational mechanism

The day runs on **recognition of the familiar made strange**, and it is the first day where the substrate does real motivational work.

Phase 1's code works. It has been running. Students are told this, and then asked to list what it depends on and does not check. The list is longer than anyone predicts, and it is a list about code that is currently serving real users. That combination — this is fine, and here are eleven ways it is not — is the day's hook, and it does not require any contrivance.

Phase 6's instructor disclosure is chosen for the same reason and for one more: the failure has no author. That removes blame from the frame entirely, which is what makes the disclosure safe to make and safe to imitate. A student who has just heard that an eighteen-month-correct function became incorrect without being edited has a category for their own equivalent experience.

The competence risk is real. Phase 1 will show most students found few of the invariants, and phase 7 will show most students' preconditions were too strong. Two visible shortfalls in one day. Countermeasures: the phase 1 reference list is presented as what a careful reader finds *with the technique*, not as what a competent programmer should have seen; and phase 7's high success rate is announced in advance, which converts it from a personal failure into an expected result.

Autonomy sits at phase 8's commitment, which is an invariant in the student's own work, chosen by them.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Four items on working substrate code. Item 3 is the transfer probe and the day's most important instrument. Item 2 — what happens if it stops holding — is the item that converts a list into an understanding, and is where students discover that most of their listed properties have no consequence and therefore were not invariants.

**Phase 2 (20 min).** Free recall with a bridging final item. The final item's near-universal failure is expected and is itself informative: S005's vocabulary is retrievable, and its application to a new case is not, which is the day's thesis stated as a retrieval result.

**Phase 3 (45 min).** One body, three specifications, three callers, and then the same three specifications executed against one prompt with a fourth configuration added. The design's cleanest contrasting-cases construction, because the invariant deep structure is literally invariant — the same function, byte for byte, and then the same prompt, word for word. The too-strong tendency in the written half is the productive failure and is resolved at phase 4 point 3. **Case D is the executed half's payload and is chosen on a specific criterion: it is a failure with no wrong content.** Groups who reason perfectly about what the file says learn nothing about why it did not apply, which is exactly the discrimination the day is trying to install and the one no amount of reading produces. All four cases are operated rather than demonstrated; the only prerequisite is a Copilot subscription and a workspace folder, and nothing in the day requires a cloud subscription, a paid deployment or a tenant privilege.

**Phase 4 (50 min).** Ten points. Point 4 is delivered by asking the room to supply the mapping to S005's obligations rather than by stating it, which makes the consolidation itself a retrieval event. Point 6 is the no-author observation and is given weight because it is the point students have no existing category for. Points 7 and 8 are the anchor argument and are consolidations of case D rather than assertions, per instrumentation rule 7 — the room has met the failure before it is named. Point 9 is the day's perishable content and its named default, and it includes a contradiction between two Microsoft-published pages that the design has chosen to teach rather than resolve. Point 10 is the strong-form scope statement.

**Phase 5 (90 min).** Seven steps on genuinely used code. Step 2 carries the day. Step 5 is the S003 habit's third instance and is deliberately unprompted in the instructions beyond its one line — the design wants to know whether it has become a habit, and the specification failure rate on step 5 is the instrument. Steps 6 and 7 are the build. Step 7's three-run requirement exists because the system is non-deterministic and one run is not a characterisation, and it is the cheapest available correction to the objection at §8 objection 3.

**Phase 6 (40 min).** The authorless failure. The emphasis that nothing changed in the function is the phase's content, not its framing. The second instructor case is an agent failure that survived review, and it is chosen on the same criterion as the first: the defect had no author, and this time neither did the code.

**Phase 7 (30 min).** Adversarial construction against the student's own implementation. High success rate, announced in advance. The phase converts phase 3's illustrated trade-off into a personally experienced one, which is the difference between knowing about the trade-off and having made it badly.

**Phase 8 (20 min).** Item 4's calibration gap shown. **Item 3's transfer result reported honestly to the room, whichever way it fell, together with what the design will do about it.** That disclosure is a deliberate continuation of S001's commitment that the programme instruments itself in public, and it is the strongest available demonstration that the commitment is real. Item 5 is unsealed and scored in two halves, and the *where will it be wrong* rate is the cohort's first entry in the programme's frontier map. That map is assembled from one cohort's builds on one substrate at one model version and is labelled as that sample, per instrumentation rule 3; its reader is the following year's cohort, via the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md), per instrumentation rule 9.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student with professional code-review experience will surface invariants fluently in phase 1 and may find phase 3 obvious. The predicted failure is that they treat the day as revision and skip the strength reasoning, which is the part their experience least likely covers — practitioners surface invariants far more readily than they specify them at the right strength. Countermeasure: phase 7 targets exactly this, and their partner's legitimate-caller attack usually succeeds against experienced students at the same rate as against inexperienced ones. If it does not, they are given the role of constructing attacks against three other students' implementations.

**Students with less relevant prior knowledge.** A student with limited code-reading experience faces comprehension load plus high interactivity plus unfamiliar substrate. This is the module's worst-placed student and the design's mitigations are partial. Countermeasures: forty-line and two-hundred-line scales; phase 3's zero-comprehension construction; phase 5's fading; and a supplied invariant for step 1 if requested. Residual risk: step 2's caller construction may be unreachable, in which case the student recognises a supplied breaking caller instead. That is a genuinely weaker experience and it is the day's known inequity.

**Phase 3 is too easy.** Groups may identify the caller-version mismatches quickly. This is expected; the difficulty is entirely in the generation step, where the too-strong tendency is robust. Fallback if a group produces well-calibrated preconditions: hand them a fourth caller, legitimate and rejected, and ask them to weaken without losing sufficiency.

**Affective failure.** The characteristic risk is **defensiveness on behalf of the code's authors**, which sounds like engagement and is not. Students who have been taught that criticising working code is arrogant will produce short phase 1 lists and hedged phase 5 statements. Countermeasure: the instructor states in advance that the substrate code was written by the teaching staff, that the invariants were not written down because writing them down is genuinely expensive, and that the exercise is not an audit. The secondary risk is the opposite — contempt for the code — which is countered by phase 5 step 5's cost statement, since every proposed fix turns out to cost something.

**The executed half does not run.** A network failure, an expired subscription or a client update that moves the References panel removes the day's payload. Countermeasure: the four configurations are recorded once, on video, with the References panel visible, and the recording is held by the instructor. If the recording is used, **the day states that case D was demonstrated rather than operated and the specification does not assess elements 6 and 7**, which fall back to a written instructions file with its scope argued rather than checked. This is a materially weaker day and the design says so rather than pretending the fallback is equivalent.

## 6. Retention architecture

Retrieved by S007 (a bad seam is an interface whose invariants cannot be stated cleanly), S009 (the falsifying test is step 2's breaking caller in a new costume), S015 (choosing a representation for a caller you have met — the same caller reasoning with representation as the object), S031 (concurrency, where invariants must hold under interleaving and the breaking caller becomes the breaking schedule), S034 (consistency models as a contract with the caller) and S073 (protocols, tools and the boundary of trust).

The S073 retrieval at roughly six quarters is the long-range target: a tool boundary is an interface whose preconditions cannot be enforced because the caller is a language model.

The day's retained content is deliberately small: three locations, the strength trade-off, and the no-author observation. The mechanism catalogue at phase 4 point 5 is explicitly not retained.

Own schedule: next morning, day 3, week 2, week 6.

## 7. Assessment and evidence generated

No entrustment evidence.

One specification item in **CF101 rather than MS101**. The placement is a deliberate structural statement: a student who believes invariant reasoning is a mathematics activity has not learned what the module intended, and grading it as programming work is a cheaper way of saying so than any amount of instruction. Ten elements are checked, each binary, and the day's specification ends with the sentence *nothing else is assessed*.

That sentence requires a note, because the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) records that its three specification-writing rules bind from [S041](wiki/seminars/S041.md) forward and that S001 to S040 are deliberately left unamended so that the defect remains legible. **Elements 6 to 10 are added under the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), which post-dates that decision and binds every day in the programme**, and a checked list that carried the sentence for half its elements and not the other half would be unreadable. So the whole list carries it. The inconsistency with the S001–S040 treatment is real and is recorded here rather than repaired: the day whose subject is that a specification must state what it checks cannot ship a specification that does not, and the six elements that predate this revision are not retrospectively re-argued.

The three added artefact elements do different work and are not interchangeable. The **prompt record** makes the difference between a build directed in one prompt and one directed in fourteen legible. The **intervention record** is the only element that measures the student's attention rather than their output, and its no-entries fail condition inherits the sensitivity discipline [S052](wiki/seminars/S052.md) established: an empty record passes only where element 7 shows an attack that would have detected a violation had one occurred. The **frontier statement** is this day's contribution to the running frontier map and is the element that keeps the programme honest about its own primary tool.

Programme instrumentation: **phase 1 item 3 is the M01-to-M02 transfer measurement** and is the most consequential single instrument in Q1; the phase 5 step 5 specification failure rate measures whether the S003 cost habit has generalised; the phase 7 success rate is the strength-calibration baseline, repeated at S015 and S034; **the phase 1 item 5 second-half accuracy is the cohort's frontier-calibration baseline**, repeated at every subsequent day and read by the following year's cohort. Item 5's branch, per instrumentation rule 4, is at [S010](wiki/seminars/S010.md): a cohort whose frontier predictions are near chance across S006 to S009 has its S010 unassisted segment lengthened from twenty minutes to thirty and the additional time spent on the same element assisted, so that the comparison the student receives is longer and closer.

Dispositions: integrity is observable in phase 5 step 4 — whether the student ran the breaking caller and reported what actually happened — and in step 7, where reporting three runs that all held is less attractive than reporting one that did not.

## 8. Objections and rebuttals

**Objection 1: real substrate code introduces uncontrolled comprehension load and makes the day's difficulty accidental rather than designed.**

At its strongest: the day's intended difficulty is invariant reasoning. What students will actually spend their time on is understanding two hundred lines of unfamiliar code, and that difficulty varies enormously with prior experience, is unrelated to the day's objective, and will dominate the phase 5 outcome. A synthetic example of thirty lines would isolate the target skill precisely, and the only thing lost would be authenticity, which is a motivational property and not an instructional one.

The rebuttal is partly a concession. The comprehension load is real, it is uncontrolled, and it is the day's known inequity, stated in §5. What the design claims in exchange is specific: the phenomenon being taught — invariants that were never written down because the original author had no reason to write them — **does not exist in synthetic code**. A thirty-line constructed example has the invariants the designer chose to omit, which is a different thing entirely and which students detect. The no-author failure at phase 6 cannot be illustrated with authored code. And phase 3, which carries the day's hardest idea, is deliberately synthetic and comprehension-free for exactly the reason the objection gives. The design therefore uses synthetic material where isolation matters and real material where authenticity is the content, rather than choosing one throughout.

**Objection 2: the transfer probe at phase 1 item 3 is confounded and cannot support the inference the design wants from it.**

At its strongest: the design intends to read item 3 as a measure of whether S005's technique transferred. But a student may fail item 3 because the technique did not transfer, or because they could not comprehend the code, or because they did not recognise the situation as one calling for the technique, or because "loop invariant in the S005 sense" is an ambiguous instruction two days after a single exposure. These are four different findings with four different remedies, and the instrument cannot distinguish them. Worse, the design has publicly committed to reporting the result to the cohort at phase 8, which means an uninterpretable number will be reported as though it meant something.

This objection the design does not fully answer, and the asymmetry is worth stating plainly. A **negative** result is weakly interpretable at best, for exactly the reasons given. A **positive** result — students reliably identifying the loop invariants in unfamiliar code two days after one exposure — is barely interpretable at all, since it is equally consistent with the technique having transferred and with the code's loop invariants being obvious to anyone who reads carefully. The honest position is that item 3 is a **trigger for investigation, not a measurement**: a low rate prompts a follow-up probe at S008 under controlled comprehension, and a high rate prompts nothing. Phase 8's public report is therefore framed as an observation with its confounds named, which is a weaker commitment than the design originally intended and is the correct one. Prediction 2 in §9 is the partial disambiguation.

**Objection 3: the executed half teaches students to accept a passing run as evidence, on the day before the module tells them not to.**

This is the objection that bites on the practical turn, and it is the strongest available against it. A specification is a claim about *all* conforming work. An instructions file produces one sample of work per prompt. The day's step 7 asks the student to attack their file, run the attack, and — if the file holds — write a sentence about why the attack was genuine. That is a green test suite with a paragraph attached. Worse, it is a green test suite in a register where the student has just been shown, at case D, that the *interesting* defects are the ones the output does not display. So the day demonstrates that output is a poor instrument and then assesses the file on its output, forty minutes later, in the same session. And because the executed half is new, engaging and mechanical, it will dominate what students remember: they will leave believing that a file which produced good code is a good file, which is the confirmatory habit [S009](wiki/seminars/S009.md) exists to displace, installed two days early by the day that should have inoculated against it.

**The design concedes this, and the cheap fix is named and is now in the specification.** A single run is not a characterisation of a non-deterministic system, and the platform's own evaluation documentation reaches the same conclusion by a different route, running repetitions specifically to detect non-deterministic behaviour. **Step 7 therefore requires three runs of the same attack and a report of the variation between them, and the assessment checks the variation rather than the outcome.** Three prompts instead of one is a trivial cost, it makes the non-determinism visible rather than hypothetical, and it is what a student would have to do anyway before believing anything about a file.

What the fix does not do is close the objection, and the residue should be stated at its full size. **Three runs of one attack is still one attack.** The day licenses exactly this and nothing more: *this named attack, run three times, did not defeat this file.* Phase 4 point 10 says so, the scope statement in §3.2 binds it to the artefact, and an artefact whose only evidence is that the output looked right fails. The claim the design cannot make, and does not, is that any student leaves the day with a characterised specification. They leave with a specification that survived one attack and a sentence explaining why the attack was genuine — and whether that sentence is a judgement or a formality is Prediction 5 in §9, which the design cannot currently answer.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** Students will substantially overestimate the number of unchecked dependencies they found, and the overestimate will be larger than the equivalent calibration gap at S003. *Instrument:* phase 1 item 4 prediction against found count, compared with the S003 phase 1 item 6 gap.

**Prediction 2.** Phase 1 item 3 performance will correlate more strongly with code-reading experience than with S005 phase 5 outcomes. *Instrument:* item 3 scored against both the admission background survey and S005 specification results. **If this holds, the probe is measuring comprehension rather than transfer and §8 objection 2 is confirmed. If S005 outcomes dominate, the probe is doing what the design hoped.**

**Prediction 3.** In phase 3, a large majority of groups will produce preconditions that are sufficient and too strong, rather than insufficient. *Instrument:* committed phase 3 preconditions coded against the reference sufficiency and usability boundaries. This is the productive-failure design assumption and the phase is mis-constructed if groups fail in the weak direction instead.

**Prediction 4.** Phase 5 step 5 — the cost statement — will have a lower specification failure rate than the equivalent step at S003, without any additional instruction. *Instrument:* step 5 failure rates across S003 and S006. This is the habit-generalisation claim; a flat rate means the S003 step was learned as an S003 requirement.

**Prediction 5.** Among students whose step 7 attack did not defeat their file, the written justification for why the attack was genuine will be rated *less* specific than the equivalent justification at [S009](wiki/seminars/S009.md) step 5, by the same blind rubric. *Instrument:* blind-rated specificity of survival justifications at S006 and S009. **This is the §8 objection 3 test.** If the two are equally specific, the day is producing a judgement rather than a formality and the objection's residue is smaller than stated. If S006's is markedly weaker, the executed half is being read as a demonstration rather than as evidence, and the correct response is to move step 7 out of S006 entirely and run it at S009 on the same file, where the asymmetry has been taught.

**Prediction 6.** Phase 1 item 5's first half — what will the agent produce — will be answered well, and its second half — where will it be wrong — near chance. *Instrument:* item 5 scored in two halves at S006, S007, S008 and S009, with the second-half rate tracked across the module. **A second-half rate that does not improve across four days is evidence that frontier calibration is not developing from build experience alone**, which is the assumption the whole Copilot practice rests on, and its named response is the S010 branch in §7.

## Evidence status

**Verified in this repository.** The unwritten-interface-assumption failure class and the multi-caller degradation pattern are grounded in the engagement material in [research/05-fde-craft/](research/05-fde-craft/collected-materials.md). The disclosure norms governing phase 6 and the authorless-failure framing draw on [research/04-professional-formation/](research/04-professional-formation/collected-materials.md). Complexity-class positioning and the module's transfer bet follow [research/01-course-structure/10-gap-analysis-and-course-architecture.md](research/01-course-structure/10-gap-analysis-and-course-architecture.md).

**Cited from general knowledge, not verified here.** Transfer-appropriate processing and the situational binding of encoded technique, contrasting cases, the generation effect, worked-example and completion-problem fading, element interactivity and comprehension load in program reading, retrieval practice at expanding intervals, and error management training are cited for **direction and mechanism only**. No effect size is asserted for any of them. The jagged-frontier finding behind phase 1 item 5 is taken from [research/04-professional-formation/dellacqua-jagged-technological-frontier.md](research/04-professional-formation/dellacqua-jagged-technological-frontier.md) for **direction and mechanism only** — that capability is uneven in ways not predictable from human-perceived task difficulty — and **no effect size from that source is asserted anywhere in this paper or on this day.**

**Grounded in vendor documentation, with its version and its silence recorded.** Four mechanisms are taught from vendor documentation and each is bounded here.

*What the documentation says.* Custom instructions files use the `.instructions.md` extension and are discovered in `.github/instructions` by default; the optional YAML frontmatter carries `name`, `description` and `applyTo`; **where `applyTo` is not specified the instructions are not applied automatically**, which is case D's entire mechanism. Where several instruction files apply they are combined and **no specific order is guaranteed**; across types, personal instructions take precedence over repository instructions, which take precedence over organization instructions. The chat response's References section and the chat customization diagnostics view report which files were actually used. The Learn MCP Server is a remote server at `https://learn.microsoft.com/api/mcp` requiring no authentication and carrying no charge, exposing `microsoft_docs_search`, `microsoft_docs_fetch` and `microsoft_code_sample_search`, serving published documentation only, and refreshing incrementally on content update with a full refresh once a day.

*Version.* The agent-customization pages carry a page-edit date of 15 July 2026 and are cited as at that date. The Learn MCP Server overview and getting-started articles are cited as consulted for this day. **No page consulted carries a product version number**, only an edit date, so a reader cannot tell from the documentation which client build a statement describes.

*What it does not report that a reader would need.* No measure of any kind is published for how reliably a conforming instructions file produces conforming output — no rate, no benchmark, no interval — and the day therefore supplies none.
