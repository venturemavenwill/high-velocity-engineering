# WP-038 — Domain Modelling and Ubiquitous Language

**Seminar day:** [S038](wiki/seminars/S038.md) · **Module:** [M08](wiki/modules/M08.md) · **Quarter:** [Q4](wiki/quarters/Q4.md)
**Strands:** PE · CF · SY · **Complexity class:** 3
**Platform anchor:** Bicep resource naming generated from a repository custom instructions file · Azure Monitor and API Management metric vocabulary · **MCP servers:** Azure MCP Server (write, disposable resource group) · Microsoft Learn MCP Server

## Abstract

This paper defends treating a name as a modelling commitment rather than a label, and defends validating a domain model by having the domain expert narrate their own work in its terms while the student records every stumble. The first argument is that vocabulary divergence between engineers and domain experts is invisible to both parties, persists for years, and degrades every conversation between them without producing a detectable failure; making the vocabulary's provenance checkable — each term either appears in an observation record or was explicitly invented — converts an invisible drift into a verifiable property. The second argument is that a model's adequacy cannot be assessed by review, since a reviewer reads what they expect, and can be assessed by use: an expert who stumbles while narrating has encountered a distinction the model does not support. The paper additionally defends permitting invention under a stated condition rather than prohibiting it, and defends the day's practical turn — that the vocabulary is written as a repository instructions file and executed, generating infrastructure the expert then reads — on the ground that a vocabulary's gaps are not neutral once something generates from it, which is a property no paper exercise exhibits. It concedes that the vocabulary-provenance rule is mechanically checkable and semantically empty, that the day's validation instrument is exercised for six minutes per student, and that adding an execution step to a day whose scarcest resource is one person's attention buys a finding at a cost the design cannot fully account for.

## 1. The instructional problem this day must solve

S037 produced a record of one person's work: long, specific, and unusable by anyone who was not present. A model is what makes it transmissible, and students can build models — S014 taught entities, relationships and structural questions, and CF201 supplies the type apparatus.

What they cannot do is name things. Asked to name an entity, a student produces an engineering word — record, item, job, task — because that vocabulary is available, general and comfortable. The domain expert calls the same thing a case, or a claim, or a run. Both parties then proceed believing they share a model, and every subsequent conversation is partly failing.

The failure has a property that makes it uniquely hard to correct: **it produces no error**. Conversations continue, work proceeds, and the mismatch surfaces only when a distinction the two vocabularies handle differently becomes load-bearing — which may be years later, at which point the model, the code and the documentation all embed the engineers' version. Phase 6's first disclosure is exactly this, and its emphasis is duration.

The intervention is provenance. Point 3 establishes that vocabulary is *observed in use* rather than asked for, step 1 extracts it from yesterday's said column with counts, and the specification requires every term in the model to trace to that extraction or to an explicit invention. That makes a property which is normally invisible into one that can be checked mechanically — which is also the basis of this day's principal objection.

The second problem is that prohibiting invention is wrong. Domains routinely lack a word for a distinction an engineer needs, and a modeller who refuses to introduce one produces a model that cannot express what it must. Model D in phase 3 is the case where invention was correct, and point 5 states the condition: introduce the term explicitly and check that the expert adopts it. The rule is not *never invent* but *never invent silently*.

The third problem is validation. A model reviewed by a domain expert is approved, because reading a diagram is a low-effort recognition task and experts recognise their domain in almost any representation of it. Point 7 replaces review with use: the expert narrates their own work in the model's terms, and where they stumble, the model is missing something. Stumbles are the day's data.

**The fourth problem is new and it changes what a gap in the vocabulary costs.** Until an agent is generating from your model, an unnamed distinction is simply unnamed — a hole, visible to anyone who looks. Once an instructions file is the specification and an agent is the implementer, **the hole is filled**, instantly, consistently, and from the vocabulary the agent has most of: the platform's. The result is infrastructure whose domain terms are the expert's and whose remaining terms are a vendor's, in one file, with no marker separating them. Nothing in a code review looks for this, because as infrastructure it is correct.

That is silent invention — point 4's third failure mode — performed at scale by something that is not in the room and cannot be asked. It is the strongest possible argument for the day's own discipline and it is not available without executing.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Moderate.** Model construction is familiar from S014 and the day's novelty is confined to the vocabulary discipline, which is conceptually simple.

The interactivity is at step 3: identifying a distinction you need that the vocabulary does not make requires holding the model's requirements and the vocabulary's coverage simultaneously and finding the gap between them. That is genuinely hard and is where most students stall.

The generation step at step 7 is deliberately the cheapest build in the module. The student writes the specification; the agent does everything else; and **the output is never assessed as infrastructure**, only as naming. That containment is what allows a class-3 modelling day to carry a deployment without becoming a platform day.

Other management:

- **The observation record is the student's own** and is one day old.
- **Step 1's extraction is worked with the room,** since counting term usage in a free-text record is unfamiliar.
- **The model form is supplied,** so no capacity goes to notation. **The instructions-file form is not**, because students have written specifications since S006 and supplying a template would remove the day's sharpest lesson about under-specification.
- **Four models supplied at phase 3** with their generated outputs and their subsequent conversations, so groups judge rather than construct.
- **Six minutes of expert time per student,** which bounds phase 5's step 8 and is the day's binding resource constraint.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Checking each name's provenance against yesterday's record,* item 3 — checkable and usually unflattering.
- *Model D's condition,* which requires the rule to be stated rather than applied.
- *Identifying a needed distinction the vocabulary lacks,* step 3.
- *Writing a specification that has to survive execution,* step 6, where an under-specified rule produces conforming and wrong output within the hour.
- *Read-back validation,* step 8, where the expert uses the model rather than reviewing it.
- *Recording every stumble,* step 9, including one's own model's failures in front of its author.
- *Resolving one stumble and stating its cost,* step 9.
- *Predicting which of your own terms an agent will drop,* item 5.

**Deliberately not selected.**

- *Formal modelling notation.* A supplied form, deliberately plain. Notation would let students hide vocabulary problems inside structure.
- *Aggregate or boundary decomposition.* Genuinely part of domain modelling and omitted; the day is about vocabulary.
- *Infrastructure review.* The generated Bicep is read for its names and for nothing else. Reviewing it as infrastructure is SY301's material and would consume the day.
- *Multi-expert reconciliation.* Named at point 4's scope statement and deferred to S082.
- *Prohibiting invention.*

**Scope on the enumeration, per the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md), strong form.** Point 4's four vocabulary failure modes assume a single expert community. They omit the case where two groups of domain experts each believe they speak the domain's language and use terms differently. **Safe** when modelling a domain with one expert community, which is this day's situation. **Unsafe** when two departments are involved, because the correct response there is to record both usages and their boundary rather than to choose one — and a student applying this day's rule will choose, will pick the vocabulary of whoever they observed, and will produce a model one department cannot read. That case is S082's and the day says so.

**Scope on the platform instance, strong form.** The day uses a vendor's own vocabulary as its demonstration of the fourth failure mode, and uses generated infrastructure as its demonstration that gaps get filled.

*Safe.* Auditing a model's vocabulary for provenance; expecting a term to mean different things to different components of a system and checking rather than assuming; and treating a specification that governs generation as a specification, subject to the rules the programme already teaches. All three transfer to any stack and to any generator.

*Unsafe* in two directions. **It is unsafe as a criticism of the vendor.** Four senses of the word *limit* is what happens when four teams each name their own thing correctly, and a student who leaves thinking the documentation is careless has drawn the opposite of the intended conclusion — the whole point is that this failure is produced by competence, not by sloppiness, which is why it is undetectable inside any one team. **And it is unsafe as a reason to adopt platform vocabulary.** The agent's fluency in the vendor's terms is a fact about its training data and not evidence that those terms are good names for your domain. A student who concludes that using the platform's words will make generation easier is correct and has traded the day's entire subject for a convenience. Step 9's stumble record is where a student who has done this fails, because the expert cannot narrate their work in a vendor's vocabulary.

### 3.3 Engagement and motivational mechanism

The day runs on **a number the student cannot argue with**.

Item 4 asks what fraction of their names came from the user. Students predict optimistically. Item 3 makes the actual fraction checkable against a record they wrote themselves the previous day, so the gap is not an instructor's claim and not a sample of somebody else's work. It is usually below half.

Item 5 supplies a second number of the same kind, and its resolution at phase 8 is the day's most surprising. Students predict which of their terms an agent will fail to carry, and most predict that terms will be dropped. Terms are rarely dropped; **gaps are filled**, and what fills them is the platform. The distribution is shown before it is explained.

Step 8 supplies the day's most exposed moment and its strongest engagement. The domain expert reads the student's model and narrates their own work in its terms, in front of them, for six minutes, and then reads the generated resource names. Stumbles are audible. Students describe this as uncomfortable and as the most informative six minutes in the module, and the discomfort is functional: a stumble is unarguable in a way that a reviewer's comment is not.

Phase 8's closing question — the expert says which model they would rather work with and why — is the day's second external judgement and is deliberately not an instructor's. The expert's reasons are usually about vocabulary rather than about structure, which is the day's thesis delivered by the person it concerns.

The competence risk is at step 3 and is managed by accepting a partial answer: a student who cannot find a missing distinction may state that the vocabulary appears sufficient and say what would change their view, which passes.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Five items on the student's own record. Item 2's one-word constraint forces commitment. Item 3's checkability is what makes item 4's prediction consequential. **Item 5 is the sealed Copilot prediction**, administered here per instrumentation rule 8, and its resolution is the day's second unarguable number.

**Phase 2 (20 min).** The bridge asks which S011 question choosing a name answers, and what a name discards. Establishing a name as a representation choice before any modelling occurs is what makes the rest of the day a continuation rather than a new topic.

**Phase 3 (45 min).** Four vocabularies over one structure, **generated and then adjudicated by the subsequent conversations**. Model D is the payload and its inclusion is what prevents the phase from teaching a prohibition. The generation step supplies the finding the phase could not previously produce: model A — the one everyone chooses — comes back with the platform's vocabulary filling every gap the model did not cover, which is the fourth problem in §1 arriving as a result rather than as a claim. The closing tasks ask for the condition rather than the verdict, and for what happens to an unmade distinction, which are the two generalisations.

**Phase 4 (50 min).** Eleven points. Point 1 is the day's retained claim. Point 4 carries the enumeration scope statement, and its fourth failure mode — one word for two things — is the subtlest and the one students never detect unaided. Point 7 specifies validation as use rather than review. **Point 9 exhibits the fourth failure mode in a document the room can open**, which is what instrumentation rule 7 requires of a phase 4 point the design's own entry state predicts students will find over-subtle: the four senses of *limit* are not asserted, they are looked up. Point 10 names a default and satisfies the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md) requirement. Point 11 carries the platform scope statement in its strong form.

**Phase 5 (90 min).** Nine steps at class 3, with the expert present for the last thirty minutes. Step 1's counts matter: a term used once by the user is weaker evidence than one used forty times, and students who extract without counting lose that. **Step 6 is the day's practical hinge** — an instructions file is a specification whose conformance is checked by execution, and an under-specified one produces conforming, wrong output inside the hour, which is a lesson the programme has taught on paper since S006 and never before demonstrated. Step 9's stumble record is the discriminator and its resolution requirement is discussed in §8.

**Phase 6 (35 min).** A two-year vocabulary divergence and the conversation where it surfaced, then the agent case. The duration is the first disclosure's content. The agent case is the day's own step 6 failing — a specification silent on the case that mattered, producing infrastructure two engineers correctly approved — and it is chosen because **there was no test that could have failed**, which is the property that makes vocabulary drift different from every other defect the programme teaches.

**Phase 7 (25 min).** Model-only reconstruction. Per the [Seminar Day Design Pattern](wiki/program/04-Seminar-Day-Design-Pattern.md)'s instrumentation rule 2, this is the fourth document-only elicitation in the programme and **is explicitly not compared with the earlier three**. It functions here as an intervention and the seminar page says so.

**Phase 8 (20 min).** The provenance gap, the stumble distribution, **item 5 opened in two parts**, and the expert's own preference stated in the room.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student with domain-driven design exposure will know the ubiquitous-language principle and will assert it fluently. Predicted failure: they build a model in what they *believe* is the domain's language, drawn from the domain generally rather than from this user's observed usage, and their step 1 counts will not support half their terms. Countermeasure: the specification's provenance clause is mechanical and is indifferent to whether a term is plausible domain vocabulary — it either appears in the record or was invented explicitly.

**Students with less relevant prior knowledge.** Step 3's missing-distinction identification is the hardest demand. Countermeasures: the model form is supplied, step 1 is worked, and a stated claim that the vocabulary appears sufficient, with what would change that view, is an acceptable answer. Residual risk: their model may be a restatement of the observation record with no abstraction, which the specification does not catch and phase 7's reconstruction test does.

**Students who write the instructions file for the agent rather than for the expert.** New, and the practical turn's characteristic failure. A student optimising for generation will use terms the agent handles well, which are the platform's, and will produce a file that works beautifully and a model the expert cannot read. Countermeasure: step 8's second reading puts the generated names in front of the expert, so the optimisation is detected by the person it disadvantages rather than by an instructor. This is the strongest countermeasure the day has and it is available only because the day executes.

**Phase 3 is too easy.** Models B and C are rejected quickly. The difficulty is in model D and in stating the invention condition, which groups typically produce as a permission to invent rather than as an explicit-introduction-plus-adoption rule. **Model A's generated output is the phase's new difficulty** and groups do not anticipate it. Fallback if a group states the condition correctly and predicts model A's result: ask what would have happened if model D's team had introduced the term in the model and not in the conversation, which is the failure the condition prevents.

**Affective failure.** The characteristic risk is at step 8 and is **the expert's politeness**. A domain expert reading a student's model in front of them will smooth over stumbles, supply the intended meaning, and say it is fine — which destroys the instrument. Countermeasures: the expert is briefed to narrate rather than to evaluate, and to say when they cannot proceed rather than to work around it; and the student records stumbles rather than asking for feedback, which removes the evaluative frame the expert would otherwise respond to. **This countermeasure is the day's principal export.** It is retrieved at S081, S082, S084 and S086, wherever a day asks an external party to judge a student's work in the student's presence, and per instrumentation rule 5 it is part of the design's repertoire rather than a local fix. **The re-anchoring extends it**: the second reading, of generated resource names, is more exposed than the first, because a name is shorter than a narration and there is nowhere to be tactful. The expert's brief now covers both readings explicitly.

The secondary risk is the student's — **hearing a stumble as a personal failure**. The design's response is the specification: stumbles are recorded, not penalised, and a model producing none is treated as suspicious rather than as good.

## 7. Assessment and evidence generated

No entrustment judgement.

One specification item, jointly in PE201 and CF201. Per the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md)'s rule 1, the checked elements are: an extracted vocabulary with counts; a model whose every term traces to that vocabulary or to an explicit step 4 invention; at least one identified missing distinction or a stated sufficiency claim with its falsifier; one explicitly invented term with its adoption outcome; a discard statement; **the instructions file**; a stumble record from both readings; **one resolved stumble with the cost of the change**; **and the prompt record, intervention record and frontier statement required by the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)**. **Nothing else is assessed** — not the model's structure, not its elegance, not the number of stumbles, and not whether the generated infrastructure is any good.

**A model containing an untraceable term fails.**

**An artefact whose deployment changed the substrate's user-facing behaviour fails.** The module's build rule.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design would have caught an intervention-worthy error. An instructions file carrying an explicit rule for what to do where the vocabulary is silent satisfies it, and is precisely the check that prevents the phase 3 model A result — which makes the escape clause here a reward for having solved the day's hardest problem rather than a loophole.

Programme instrumentation: the item 4 provenance gap is the cohort's vocabulary-source baseline, re-probed at S046; the stumble distribution is the model-adequacy measure; **the expert's phase 8 preference and stated reason is recorded verbatim across cohorts** and is the day's only external quality signal; the step 4 adoption rate measures whether explicit invention works; **item 5's two-part accuracy is the day's frontier-calibration datum**, read by the following year's cohort through the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) per instrumentation rule 9.

Dispositions: **humility**, at step 9, where recording a stumble accurately is less comfortable than recording that the reading went well.

## 8. Objections and rebuttals

**Objection 1: the provenance rule is mechanically checkable and semantically empty.**

At its strongest: the specification requires every term to appear in the extracted vocabulary or to be explicitly invented. That is a string-matching condition. A student can satisfy it by building an engineering model and renaming its parts with words the user happened to say, producing a model whose vocabulary is the domain's and whose *distinctions* are entirely the engineer's — which is the failure the day exists to prevent, wearing the day's own compliance as camouflage. Worse, this model will pass phase 7's reconstruction test, because a partner reading domain words will reconstruct domain work.

The rebuttal is that step 8 catches it. An expert narrating their work in a model whose distinctions are wrong will stumble, regardless of how familiar the words are — arguably more, because familiar words carrying unfamiliar distinctions are worse than unfamiliar words. The stumble record is the semantic check that the provenance rule is not.

The concession as previously written was that the stumble record was required and never used. **The fix this paper named is now made.** Step 9 requires one stumble to be resolved and the resolution's cost to be stated, and the specification checks for it, so the day's semantic check now produces data that goes somewhere. That closes what this paper recorded as the third instance in M08 of a discrimination performed and then discarded before assessment, after [WP-035](wiki/whitepapers/WP-035.md) §8 and [WP-036](wiki/whitepapers/WP-036.md) §8. **The pattern finding stands**: three instances in one module was a design habit rather than three oversights, and the fact that all three have since been repaired individually does not retire the habit, because nothing in the design detects the fourth instance before a whitepaper is written about it.

**Objection 2: six minutes per student is not a validation.**

At its strongest: step 8 is the day's semantic instrument and each student gets six minutes of expert time — now split across two readings, which makes each shorter. A domain expert can narrate perhaps two or three operations in six minutes, from a model that may describe fifteen. The stumbles observed are therefore a small and non-random sample — non-random because the expert will narrate what comes to mind first, which is the common case, which is the case any model handles. The distinctions that matter are in the uncommon operations and will not be reached.

This objection the design does not fully answer. Six minutes is what the expert's availability permits and the constraint is real: this is one person, giving a further thirty minutes after having already given ninety the previous day, and the [Substrate and Infrastructure](wiki/program/10-Substrate-and-Infrastructure.md) page's duty-of-care position limits how much can be asked.

Two mitigations are available and one and a half are now taken. The taken one is that students may choose which operations to have narrated — and the day now **tells them to choose the ones they suspect are weak**, which is the omission this paper previously recorded and is a one-sentence repair. The half is that the second reading, of generated names, samples differently from the first: it is not narration-ordered, so it reaches parts of the model the narration would not have.

The untaken one is unchanged: **the expert could narrate one student's model rather than each student narrating their own**, with the room observing, producing thirty minutes of evidence about one model instead of six about each. That trades individual assessment evidence for collective learning, and the design chose individual evidence — which is defensible given the specification's requirements but was not weighed openly anywhere. It is also the sampling problem [WP-037](wiki/whitepapers/WP-037.md) §8 identified in a different form: **whose model gets read, and which operations get narrated, determines what is found, and M08 has now produced three separate instances of this design not attending to how its own evidence is sampled.**

**Objection 3: the execution step buys one finding at a cost the day cannot account for, and the day's scarcest resource is not time.**

This is the objection that bites on the practical turn.

At its strongest: the day's binding constraint is one person's attention for thirty minutes, and the practical turn spends part of it. Step 8 now asks the expert to do two things where it previously asked one, so each is shorter — and the first, the narration, is the one the day's entire assessed apparatus rests on. Meanwhile the generation step's payoff is a single finding: that gaps get filled from the platform. That finding is real and it is one finding, and it could have been delivered as a worked example in phase 4 at a cost of four minutes and nobody's expert time. **The design has spent its scarcest resource to convert a demonstrable claim into a demonstrated one**, on a day where the scarce resource was already the reason for its principal conceded weakness.

There is a second edge to it. A student who has generated infrastructure has an artefact that looks substantial, and the model — which is three boxes and a list of words — does not. The day's assessed object is the small thing and its most impressive output is the large one, which is the crowding-out risk [WP-036](wiki/whitepapers/WP-036.md) §8 named, arriving in the form this day is worst equipped to resist.

The rebuttal is that the finding is not a finding about the platform, and could not have been delivered as a worked example. **What the student learns at step 7 is that their own specification was under-specified**, in a way they did not predict at item 5, with consequences they can read in a file they caused to exist. A worked example about somebody else's model teaches that gaps get filled. Generating from your own teaches that yours had gaps, which is a different proposition and is the one that transfers.

**The objection is conceded on the resource question and the fix is named and made.** The expert's thirty minutes were being spent on one instrument, and are now spent on two, and the design cannot claim that the first is undamaged. What it has done is make the split explicit in the expert's brief and in the specification — the narration is the assessed validation and the name-reading is an additional record — so that a student who runs out of time has lost the second rather than the first. **The fix that is named and not made** is the obvious one: ask the expert for forty minutes instead of thirty. It is not made because the duty-of-care position limits what may be asked of a substrate user, and because the design has no evidence that ten more minutes would be spent well. That is a reason and it is not a strong one, and it is recorded as the weakest argument in this paper.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** The actual fraction of names traceable to the user's usage will be below half for a majority, and item 4 predictions will exceed it. *Instrument:* paired predictions and record-checked provenance.

**Prediction 2.** Groups will state the phase 3 invention condition as a permission rather than as an explicit-introduction-plus-adoption rule, on first attempt, for a majority. *Instrument:* phase 3 closing statements coded.

**Prediction 3.** Students with domain-driven design exposure will produce provenance fractions no higher than students without. *Instrument:* provenance fractions split by the admission background survey. **A higher fraction would indicate the principle transfers from exposure and the day's mechanical rule is less necessary than claimed.**

**Prediction 4.** Models producing zero stumbles in the narration will be rated lower on phase 7's reconstruction test than models producing two to four. *Instrument:* stumble counts against blind-rated reconstruction accuracy. **Zero stumbles indicates a reading that did not probe, which this predicts is detectable elsewhere.**

**Prediction 5.** A majority of item 5 predictions will name a term the agent will drop, and the agent will drop few or none; the substitutions will be platform vocabulary in a large majority of generated files. *Instrument:* item 5 responses coded against the generated Bicep, with substituted terms classified by source. **This is the module's third frontier-calibration datum and it shares a shape with [WP-036](wiki/whitepapers/WP-036.md) §9 prediction 5 and [WP-037](wiki/whitepapers/WP-037.md) §9 prediction 5: in all three the cohort is predicted to expect an error of omission where the actual behaviour is confident completion. If all three hold, the cohort's model of an agent is wrong in one consistent direction, which is a more useful finding than three separate ones and is what the frontier map should carry.**

**Prediction 6.** Stumbles recorded during the second reading, of generated names, will exceed stumbles recorded during the narration, for a majority of students. *Instrument:* stumble counts split by reading. **A higher narration count would indicate the generated names are not reaching parts of the model the narration misses, which would remove objection 2's half-mitigation and make the resource cost in objection 3 harder to defend.**

## Evidence status

**Verified in this repository.** Ubiquitous language, domain vocabulary provenance, model validation by use rather than review, and the vocabulary-divergence failure at phase 6 are grounded in [research/04-professional-formation/](research/04-professional-formation/collected-materials.md) and [research/05-fde-craft/](research/05-fde-craft/collected-materials.md). The entity-relationship apparatus follows [research/02-technical-foundations/](research/02-technical-foundations/collected-materials.md).

**Grounded in vendor documentation, with its version and its silence recorded.** The vocabulary used at point 9 and point 10 is taken from three Microsoft Learn pages, all read 2026-07-26. From the quota page for Azure OpenAI in Foundry Models: quota is assigned per subscription, per region, per model and per deployment type in tokens per minute, and **Quota Tokens-Per-Minute allocation is stated not to be related to the maximum input token limit of a model**, which is the fourth failure mode in the vendor's own words. From the `llm-token-limit` policy reference for Azure API Management: `tokens-per-minute` is a rate and `token-quota` over a `token-quota-period` is a separate cap, enforced by the same policy and returning different status codes. From the `llm-emit-token-metric` policy reference: the metric namespace defaults to API Management, and eight default dimension names may be used without a value — API ID, Operation ID, Product ID, User ID, Subscription ID, Location, Gateway ID and Backend ID. The instruction that ten legacy metrics on the same resource, including one named Blocked Calls, are not to be used for this service is taken from the Azure Monitor reference for Azure OpenAI in Foundry Models, read the same day. That Copilot agent mode authors Bicep is taken from the agent-mode deployment quickstart, read the same day.

**Two silences are recorded and one is taught.** The documentation states that the ten legacy metrics are not to be used for this service and **does not state what happens if they are** — whether the values are empty, partial or misleading — which is the silence point 10 names to students, and which matters because a team using one would receive numbers rather than an error. And the four senses of *limit* are each documented correctly on their own page and **nowhere disambiguated against each other**; the one explicit disambiguation the day cites exists because a note was added to a single page, not because the vocabulary is governed. Consistent with the folder-wide asymmetry recorded in [research/06-microsoft-platform/](research/06-microsoft-platform/collected-materials.md), **all four pages state limits, defaults and definitions and none states an accuracy**; nothing in them licenses a claim about how often the ambiguity causes a fault, and none is made here. All are dated by content rather than by version number; the quota page additionally identifies itself as the classic portal version and points to a successor, which is a supersession in progress and is exactly the perishability point 11 marks.
