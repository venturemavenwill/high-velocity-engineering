# WP-033 — Partial Failure and the Unreliable Network

**Seminar day:** [S033](/wiki/seminars/S033.md) · **Module:** [M07](/wiki/modules/M07.md) · **Quarter:** [Q4](/wiki/quarters/Q4.md)
**Strands:** SY · MS · CF · **Complexity class:** 3
**Platform anchor:** API Management backend pools and circuit breaker · Azure MCP Server tool idempotence annotations · Bicep · **MCP servers:** Azure MCP Server (write) · Microsoft Learn MCP Server

## Abstract

This paper defends teaching distributed failure as a permanent epistemic condition of the caller rather than as a class of engineering problems to be handled, and defends requiring an unhandled failure to carry a probability estimate before it counts as a decision. The first argument is that the third outcome — the caller does not know what happened — is not a transient state that better engineering resolves, that students treat it as one, and that the resulting default behaviour is to retry without deciding to; the reframing makes the timeout a caller-side choice and the retry a design decision with four named consequences. The second argument is that a failure declared out of scope without a probability is an omission rather than a judgement, and that requiring the estimate converts a shrug into an accountable position. The paper additionally defends opening with a quantitative pretest whose near-universal error is directional, and defends making this the quarter's deploy-and-destroy day: students build a real multi-backend gateway with a circuit breaker, break a backend, and discover that priority-based routing is not failover unless a breaker has tripped. It concedes that the day's probability estimates rest on a history the substrate may be too young to supply, that its central discipline may produce false precision, and that the day now permits an agent to deploy resilience configuration whose most consequential property is the absence of something nobody asked for.

## 1. The instructional problem this day must solve

Within a process, a call has two outcomes: it returns, or the process dies. Across a network there is a third and it is the common one. The caller times out and does not know whether the request arrived, whether it was processed, whether the response was lost, or whether processing is still underway. These are indistinguishable from the caller's position and no engineering removes the indistinguishability — it is a property of the situation.

Students meet this and treat it as an inconvenience with an obvious remedy. Retry. And the retry is frequently correct, which is what makes it dangerous: a default that is usually right is not examined, and its four consequences — duplication, amplification, latency inflation, and masking a failure until it is worse — arrive without anyone having chosen them.

Amplification is the least intuitive and the most damaging. A dependency that is slow rather than failed will receive retries, the retries add load, the added load makes it slower, and the caller has converted a degradation into an outage without any component having failed. Phase 6's disclosure is exactly this case and its emphasis — the dependency never failed — is what makes it instructive, because there is nothing to blame.

The day's second problem is that failure handling is unbounded work. Every failure could be handled; handling costs code, latency and complexity; and the question of *which* to handle has no answer that is not a judgement about probability and consequence. That judgement is complexity class 3's demand, and students make it implicitly and badly — they handle the failures they thought of and ignore the ones they did not, with the boundary determined by imagination rather than by estimate.

Step 5's requirement is the intervention: name the failures you are not handling, with their probability and consequence. **"Unlikely" is not an estimate**, and the specification says so. A failure declared out of scope with a number attached is a decision somebody can dispute; the same failure declared unlikely is an omission with a word in front of it.

**The day's third problem is new and belongs to the practical turn.** Students who accept all of the above will still believe that a resilience feature, once configured, is operating. It is the same error one level up: not *I retried without deciding to*, but *I configured failover and therefore have failover*. The platform supplies an unusually clean demonstration, because the documentation states that lower-priority backends are used **only when higher-priority backends are unavailable because circuit-breaker rules are tripped** — so a priority pool with no breaker is an ordering rather than a fallback, it deploys without error, it reads correctly, and it does nothing. There is no test that fails. This is why the day ends by breaking a backend rather than by describing what would happen if one broke.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Moderate to high, and the module's most tractable so far.** The individual ideas are simple — three outcomes, four retry consequences, multiplication of availabilities — and the interactivity is in step 4's criterion, where probability, consequence and handling cost must be traded against one another.

Management:

- **Arithmetic limited to multiplication.** No distributions, no dependence structure, no correlated failures beyond a named caveat.
- **Phase 3 supplies the four scenarios and the intervention,** so groups reason about one design decision applied across a fixed set.
- **Step 2's estimation from history is worked with the room,** because deriving a probability from an incident log is a skill nobody has — **and both the observed and the zero-observation cases are worked**, which repairs the gap §8 objection 1 identified.
- **Step 3's arithmetic is supplied as a form.**
- **The same gateway instance across the module,** now on its third day.
- **Bicep is read, not authored.** The file is agent-produced and the student's task is review. This is the load decision that makes a deploy-and-destroy day possible at all: infrastructure syntax on a day already carrying probability estimation would be indefensible.
- **The priority-breaker dependency is taught at point 8 before it is met at step 7**, deliberately. A student who discovers it by having their own failover fail has learned it well; a student who discovers it while their gateway is the only route to a running service has learned it expensively, and the module has no appetite for the second.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Enumerating the outcome space,* item 1, where lists are consistently incomplete.
- *The availability arithmetic,* item 3, where the error is near-universal and directional.
- *Applying idempotence across all four scenarios,* phase 3, including the one it does not help.
- *Predicting which platform operations are annotated idempotent,* phase 3's executed payload, where the room's prediction inverts the documented answer.
- *Naming unhandled failures with probabilities and confidences,* step 5 — the day's discriminator.
- *The caller's observable in each unhandled case,* step 8.
- *Narrating the worst-moment arrival,* phase 7.
- *Destroying what you built,* step 9.

**Deliberately not selected.**

- *Consensus protocols and the impossibility results around them.* Genuinely central to distributed systems and entirely omitted; SY201's material.
- *Correlated failure and dependence structure.* Named as a caveat at point 5 and not modelled, which is a real simplification since dependencies fail together far more often than independently.
- *Retry policy design at system scale.* Deferred to S062, and the scope statement says the day's four-consequence list is unsafe as a basis for it.
- *Distributed tracing tooling.*
- *Authoring Bicep from a blank file.* Refused, per §3.1.
- *Measuring the failover delay as a property.* Students record what they observe at step 7 and are not invited to generalise from one run on one tier, which would be a sample of one presented as a characteristic.

**Scope, per the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md), strong form.** Point 3's four retry consequences are those visible at a single call site. They omit retry's interaction with backpressure and with client-side queueing. The statement is given in the strong form the standard now requires: **safe** for deciding whether to retry a particular call, **unsafe** as a basis for designing a system-wide retry policy, which this day does not do and S062 does. The independence assumption in point 5's arithmetic is a second and more serious simplification: it is safe for establishing that availability multiplies and unsafe for any actual availability estimate, since correlated failure dominates in practice. That second statement is in the seminar page and is the more important of the two.

**The platform instance, scoped in the strong form.** The day treats a gateway backend pool as an instance of partial failure.

*Safe.* Reasoning about the outcome space; about what a retry does to each member of it; about idempotence as a property that makes a repeat harmless and about which operations have it; and about what a caller can and cannot distinguish. In each of those the pool is a faithful instance.

*Unsafe.* **As a complete account of the failures the arrangement produces.** A gateway that trips a breaker returns 503 to a caller no backend failed for, so the mediator introduces a failure mode of its own that the day's four scenarios do not contain — the seminar page names it at point 8 and step 8 requires the student to record it. It is unsafe as a basis for a system-wide retry policy, which is S062's. And it is unsafe to treat the documented tool annotations as guarantees: **the documentation calls them hints**, and nothing in it obliges any client to honour them, so an operation annotated idempotent is a claim by its publisher rather than a property you have verified.

Step 8's caller-observable is where a student applying it outside that range would fail, and the seminar page carries the statement.

### 3.3 Engagement and motivational mechanism

The day runs on **an arithmetic error everyone makes in the same direction**.

Item 3 asks for the availability of a component depending on four services at 99.9 per cent each. The arithmetic is a multiplication and the answer is materially lower than almost anyone predicts. Item 4 asks students to guess the direction of their own error, and most guess wrongly.

This is an unusual pretest for this programme — quantitative, with a definite answer, and failed by nearly everyone — and it is used because the failure mode it exposes is quantitative. Students do not merely lack a concept; they hold a wrong number, and holding a wrong number is corrected by seeing the right one in a way that a wrong concept is not.

Phase 3's second run supplies the day's structural pleasure. The same four scenarios, one intervention, and three of four answers change — which makes idempotence's value precise rather than general, and makes scenario D's resistance to it legible. **The annotation prediction supplies a third and sharper moment**: the room predicts that creating a resource is the safe retry and deleting one is the dangerous retry, and the platform's own table says the reverse. Students hold *destructive* and *unsafe to repeat* as one idea, and watching them come apart in a published table is more persuasive than any definition.

Phase 7's worst-moment narration is the day's most engaging phase by observation, and it is engaging for an uncomfortable reason: students enjoy constructing the sequence in which someone else's unhandled failure ruins a user's day, and the enjoyment survives the reversal of roles.

Step 9's teardown adds a small and reliable satisfaction the design did not anticipate needing. **Destroying a resource group you built an hour earlier is the first moment in the programme at which a student's relationship with cloud infrastructure is symmetrical**, and the design's observation is that it materially reduces the caution that otherwise suppresses experimentation on the following days.

The competence risk is at step 2. A student who cannot estimate a probability from the substrate's history will produce a number they do not believe, and the specification requires numbers. Countermeasure: step 2 requires a *stated confidence and provenance* alongside the estimate, so a poorly-supported number that says so is acceptable and a confident invention is not.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Five items. Item 1's enumeration is consistently incomplete and the incompleteness is systematic — students omit the processed-but-response-lost case, which is the one idempotence exists for. Item 3's directional error is the day's hook. **Item 5 is the sealed Copilot prediction** and is administered here per instrumentation rule 8; it asks the student to name the part of a resilience configuration that will not do what its name says, which is answerable only by holding the priority-breaker dependency and is therefore expected to have a low hit rate.

**Phase 2 (20 min).** The bridge asks which S019 phenomenon a retry storm produces. The answer is saturation, and stating it before point 3 means amplification arrives as an instance of a known curve rather than as a new hazard.

**Phase 3 (45 min).** Four scenarios, one symptom, then one intervention applied across all four — **now produced against real backends the groups can fail, hang or silence.** The design's decision to re-run rather than to introduce a fifth scenario is what isolates idempotence's contribution: the comparison is within-scenario rather than across. The executed payload is the annotation prediction, and it is placed after the idempotence re-run rather than before, so that the room has just finished forming a working account of idempotence when the platform's table contradicts the account's most confident application.

**Phase 4 (50 min).** Twelve points. Point 1 states the third outcome as permanent, which is the day's reframing. Point 2 relocates the timeout from the callee to the caller, which is the move that makes it a decision. Point 3 carries the strong-form scope statement. Point 4 works the annotation result completely. Point 5 works the arithmetic completely and names the independence caveat. Point 6 is the class-3 demand. **Points 8 to 11 are the platform content: the priority-breaker dependency and the 503 the gateway invents; four defaults including a one-hour interval nobody chose and a single permitted rule; the documented statement that both load balancing and breaker tripping are approximate because gateway instances do not synchronise; and the silence that no bound on that approximation is published.** Point 10's second sentence is the day's most important transfer: this is S031's approximate counter in a second register, and naming the identity is what stops the two being learned as separate facts.

**Phase 5 (90 min).** Nine steps at class 3, **deploying and destroying a real gateway.** Step 5 is the discriminator and its specification clause is the day's sharpest. Step 7's break is what converts a design document into a measurement. Step 8 continues the module's caller demand: everything decided here is invisible to the caller unless stated, which S034 makes the whole subject. **Step 9's teardown is assessed** — not as administration, but because a student who cannot destroy what they built does not know what they built, and an agent-created resource that survives the teardown is the clearest possible evidence of an unreviewed action.

**Phase 6 (40 min).** Amplification with no failed component, then the agent case. The instructor disclosure is chosen because it has no villain and no faulty part, which is the third consecutive module disclosure with that property — S031's unspecified component, S032's correct-but-wrong change, and now this — and the accumulation is deliberate. **The agent case is the module's clearest instance of the write-access failure class: a complete, correct, well-reviewed answer to an incomplete question, deployed.** It is chosen over a case of bad agent output because a cohort taught that agent failures look like errors will not recognise the ones that pass review.

**Phase 7 (30 min).** Worst-moment construction plus user experience. The two halves matter: constructing the sequence is analytical, narrating the user's experience is not, and the second is what makes step 6's degradation specification feel inadequate when it is.

**Phase 8 (20 min).** Item 1 completeness against the reference, item 3's error direction, the cohort's computed availabilities against the substrate's measured figure — which is usually lower, for reasons point 5's independence caveat predicts — the annotation prediction rate, and the sealed item 5 opened as two rates.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student with distributed systems experience will know the third outcome and will handle phase 3. Predicted failure: their step 4 criterion will be inherited practice — retry idempotent calls, circuit-break on repeated failure — applied without estimates, because operational convention supplies defaults that work. Countermeasure: step 5's probability requirement is not served by convention, and their phase 7 partner constructs the case their inherited default handles worst. **A second countermeasure is now available and is stronger: the experienced student is the most likely to configure a priority pool and assume failover**, because the convention they inherited is correct on other platforms, and step 7 tests it.

**Students with less relevant prior knowledge.** Step 2's estimation from history is the day's hardest demand for them. Countermeasures: it is worked with the room in both the observed and zero-observation cases; the arithmetic form is supplied; stated low confidence is acceptable; and the Bicep is read rather than written. Residual risk: their availability computation may be built on estimates they cannot defend, and step 2's provenance requirement is the only check.

**Phase 3 is too easy.** Scenarios A to C are handled by most groups on the first pass. The re-run with idempotence and scenario D's resistance are where the phase bites. Fallback if a group resolves D: ask what machinery would resolve it and what that machinery costs, which is a transactional answer and previews SY103's material without teaching it.

**The platform fails on the day, or the tier does not carry the feature.** The circuit breaker is not available in every API Management tier. Countermeasure: the tier is confirmed before each offering; where it does not support the breaker, **the seminar page states that the breaker cases are demonstrated rather than operated, step 7 and the breaker element of the specification are not assessed**, and the priority-breaker dependency is taught from the documentation. This is the module's only planned instance of the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md)'s demonstrated-rather-than-operated provision, and it is named at [M07](/wiki/modules/M07.md) so that the exception is visible at module level rather than buried in a day.

**Affective failure.** The characteristic risk is **the day producing a sense that distributed systems cannot be built**. Three outcomes, four retry consequences, multiplying availabilities and an unhandled-failure list is an accumulation of bad news, and it lands on the module's third consecutive day of things being harder than they appeared.

Countermeasures: point 7's degradation-as-choice is the day's constructive output and is stated as a design decision rather than as damage control; the phase 8 comparison shows that the substrate's measured availability, while lower than computed, is adequate for its users, which is evidence that these systems do work; step 4's criterion is the student's, which converts an unbounded problem into a bounded decision; **and the day now builds something that works before it breaks it**, which the previous design could not offer. The design's position is that this day is where the module's negativity peaks and that S034's contract framing is the resolution — which is a deferral, and per the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md)'s fourth register it must name its verification: **S034's phase 8 asks students to state what they can now promise a caller, and a cohort that cannot answer indicates this deferral failed.**

## 6. Retention architecture

Retrieved by S034 (the contract, one day later, which is what step 8's caller observable becomes), S035 (breaking a system that appears to work), S062 (batching and the latency you promised, which supplies the system-wide retry policy this day's scope statement excludes), S068 (designing for detectability), S073 (protocols, tools and the boundary of trust) and S074 (tool failure has four shapes — which is this day's outcome space with a language model as the callee).

S074 at roughly four quarters is the principal target. A tool call that times out has exactly this day's three outcomes, plus a fourth the day does not have: it may have returned something plausible and wrong. The design's claim is that students who hold the three-outcome frame receive the fourth as an extension. **The seminar page states explicitly that what transfers is the frame and the boundary argument, not the gateway**, because a student who has learned "circuit breakers are approximate" and not "a failure detector distributed across independent observers has no consistent view of failure" will not recognise the agent case when it arrives.

Retained content: the third outcome, timeout-as-caller-decision, retry's four consequences, idempotence and its limit, availability multiplication, and degradation-as-choice. Six items, no numbers.

Own schedule: next morning, day 3, week 2, week 6.

## 7. Assessment and evidence generated

No entrustment judgement.

One specification item in SY201. **An unhandled failure named without a probability estimate fails, and "unlikely" is not an estimate.** This is the day's central clause and is the class-3 demand made checkable.

**A second clause is added: an unhandled failure carrying a probability without its confidence also fails.** This is the repair §8 objection 2 specified and previously recorded as unmade — the day required provenance at step 2 and stripped it from step 5, which is the only output another person reads. The seminar page now states its checked elements and closes with *nothing else is assessed*, and the artefact additionally carries the **prompt record, intervention record, frontier statement and confirmation of teardown**.

Programme instrumentation: item 1's enumeration completeness is the cohort's outcome-space baseline, re-probed at S074; item 3's error direction and magnitude is the availability-intuition measure; the step 2 confidence-and-provenance quality is the estimation-honesty measure carried to S049 and S064; the gap between cohort-computed and substrate-measured availability is the independence-assumption illustration and is used at S049; **the phase 3 annotation prediction rate is the destructive-versus-idempotent conflation measure and is new**; and **item 5's two rates — generic omission and the named priority-breaker dependency — are this day's frontier datum**, read by next year's cohort through the [Durable and Perishable Register](/wiki/program/09-Durable-and-Perishable-Register.md) per instrumentation rule 9.

The frontier statements are a sample and the day says so, per instrumentation rule 3: one cohort, one tier, two backends, one deployment shape chosen by staff because it contains a documented dependency the agent is not asked about.

Dispositions: **integrity**, at step 2, where a confident invented number is easier to produce and more impressive than a hedged supported one.

## 8. Objections and rebuttals

**Objection 1: the substrate may not have enough history to support the estimates the day requires.**

At its strongest: step 2 asks students to estimate failure probabilities from the substrate's actual history. A teaching system a few years old, with a modest user base, will have observed few dependency failures — possibly none for some dependencies. Estimating a probability from zero observations is not an estimation problem, it is a prior-selection problem, and the day supplies no apparatus for it. Students will produce numbers by a procedure the day did not teach, and the specification will accept them because they are numbers.

The rebuttal is that the situation the objection describes is the professional one. Engineers routinely estimate failure probabilities for events they have not observed, and the honest output is a bounded estimate with its provenance stated — which is exactly what step 2 requires. A student who writes "no observed failures in eighteen months; upper bound therefore roughly one in a thousand requests at our volume; low confidence" has done the right thing.

**The concession is discharged.** When this paper was first written the day's worked example used a dependency with observed failures, which is the easy case, and the zero-observation case — the common one — was modelled nowhere. **Step 2 now works both**, and the seminar page states that a zero-observation case must produce a bounded estimate rather than an omission. The gap is closed at this day; it is recorded here rather than deleted so that the original diagnosis remains legible.

**Objection 2: requiring numbers may produce false precision that is worse than the vagueness it replaces.**

At its strongest: "unlikely" is vague and it is honestly vague — the person reading it knows they are receiving a judgement. "One in ten thousand" is precise and, on the evidence available, invented. A downstream reader cannot tell an estimate grounded in eighteen months of data from one produced to satisfy a specification, and will treat both as measurements. The day's clause therefore replaces a signal that reads as uncertain with one that reads as certain, and the programme's own S026 material establishes that numbers acquire authority they have not earned.

This objection has considerable force and the design's answer is structural rather than argumentative. Step 2 requires the estimate, the confidence and the provenance *together*, and the specification assesses all three — an estimate without provenance fails on the same clause. So the artefact the day produces is not a number but a number with its basis attached, which is precisely the reporting obligation S026 point 6 established.

**The concession is discharged and its diagnosis stands.** The original concession was that the protection lived inside the artefact and did not survive it: step 5's unhandled-failure list, the part anyone else reads, carried probability and consequence and **not** confidence or provenance, so the day's own output propagated exactly the false precision the objection describes, through a form the design specified. **Step 5 now carries the confidence, and the specification fails a bare probability.** The finding it produced is not withdrawn: this was the third instance in this design of a limitation recorded in one place and not travelling with the number it qualifies, after [S026](/wiki/seminars/S026.md) phase 6's metric attrition and the [S029](/wiki/seminars/S029.md) instrument-adoption failure. **Three instances of one failure mode, two of them in the design's own artefact specifications, is a pattern rather than a coincidence**, and the repair made here is local. The general conclusion — that the programme should require every reported quantity to carry its qualification structurally rather than by convention — is not implemented anywhere and remains recorded, because it belongs to the [Whitepaper Standard](/wiki/program/05-Whitepaper-Standard.md) rather than to this day.

**Objection 3: a day that hands students write access and a deletion command has traded a real hazard for a pedagogical convenience, and its safety argument is the environment rather than the practice.**

This is the objection that bites on the practical turn.

At its strongest: students direct an agent to create a multi-resource gateway and then to destroy a resource group, on their third day of write access, having never deleted anything. The design's protection is that the subscription is disposable. **That protection is doing all the work, and it is exactly the protection that will not exist in eleven months.** A student who learns that `delete` is safe because the environment was disposable has learned something false, and the day teaches the annotation table — which says delete is idempotent — immediately beforehand, which makes the false lesson easier rather than harder to reach. The objection's second half is worse: **the day's agent case is about a resource property that was absent, and the day's own teardown step is the moment at which an absent-property failure is most likely to occur unnoticed**, because a resource the agent created outside the resource group survives the deletion and nobody is looking for it.

The objection is conceded in part.

What is defensible: the disposable environment is not the safety argument, it is the sequencing argument. The module's position, stated at [Q4](/wiki/quarters/Q4.md), is that disposable environments teach the write *discipline* and the substrate teaches the write *consequence*, and that reversing the order would be indefensible. Step 9 exists because the discipline includes reversibility, and a student who has never destroyed anything holds an asymmetric and dangerous model of what they are doing.

What is conceded: **the day does not tell students that the disposable environment is the reason the teardown is safe, and it should.** Idempotent deletion of a disk is a property of the operation; safe deletion of a resource group containing an hour's work is a property of the environment; and the day teaches the first immediately before performing the second without distinguishing them. **The cheap fix is one sentence at point 4 and it is made** — the seminar page's point 4 states that destructive and non-idempotent are independent properties and that the platform's annotation table is the demonstration, and the perishability register records that a hint is not a guarantee.

**The fix that is not made** is requiring the student to confirm, after step 9, that nothing they created survives outside the deleted group. It would take one query, it would catch precisely the failure the day's own agent case is about, and it is not in the design because step 9 already runs against the end of a ninety-minute phase and the design judged the addition unaffordable. **That is the same phase-budget reason [WP-032](/wiki/whitepapers/WP-032.md) §8 recorded twice**, which makes this the third such omission in three consecutive days and a finding about the module's scheduling rather than about any one measurement.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** A large majority of item 1 enumerations will omit the processed-but-response-lost case. *Instrument:* item 1 responses coded against the four-case reference.

**Prediction 2.** A large majority of item 3 answers will be too high, and item 4 predictions of the error direction will be wrong for a majority. *Instrument:* paired item 3 and item 4 responses.

**Prediction 3.** Students with distributed systems experience will produce step 4 criteria rated more conventional and step 5 lists rated shorter than students without. *Instrument:* blind ratings against the admission background survey. **Shorter unhandled lists from experienced students is the inherited-default failure stated as a prediction.**

**Prediction 4.** Cohort-computed availabilities at step 3 will exceed the substrate's measured availability for a large majority. *Instrument:* computed against measured. **This is the independence assumption's cost, and the gap's size is the material for S049.**

**Prediction 5.** In phase 3, a large majority will predict that resource creation is annotated idempotent and deletion is not, and the rate of that inversion will not differ between students with and without cloud experience. *Instrument:* annotation predictions coded, split by the admission background survey. **If experienced students invert less often, the conflation is a knowledge gap rather than a conceptual one and the phase's placement after the idempotence re-run is unnecessary.**

**Prediction 6.** A majority of item 5 sealed predictions will name a generic omission, and fewer than a fifth will name the priority-breaker dependency. *Instrument:* item 5 responses coded for generic-versus-specific, against what each student's agent produced. **This is expected to be among the module's lowest specific rates, because it requires a fact the day supplies at point 8. If the specific rate is high, the cohort held the dependency beforehand and point 8's placement before phase 5 is over-cautious.**

## Evidence status

**Verified in this repository.** Partial failure, the indistinguishability of network outcomes, retry amplification, idempotence, availability composition and the phase 6 amplification incident are grounded in [research/02-technical-foundations/](/research/02-technical-foundations/collected-materials.md) and [research/05-fde-craft/palantir-fde-practitioner-writing.md](/research/05-fde-craft/palantir-fde-practitioner-writing.md). The estimation and reporting obligations at step 2 follow [research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md). The characterisation of circuit breaking as failure isolation, and of priority routing as the operational consequence of paid-for dedicated capacity, is recorded in [research/06-microsoft-platform/apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md).

**Grounded in vendor documentation, with its version and its silence recorded.** The backend behaviour used at phases 3 to 5 is taken from Microsoft Learn's backends page for Azure API Management, the AI gateway overview, and the Azure MCP Server tools documentation, all read 2026-07-26: backend pools supporting round-robin, weighted, priority-based and session-aware distribution, with **up to thirty backends in a pool**; the statement that **backend load balancing is approximate because different gateway instances do not synchronise and each balances on its own information**; the statement that **the service uses backends in lower priority groups only when all backends in higher priority groups are unavailable because circuit-breaker rules are tripped**; circuit-breaker rules defined by a count or percentage of failures over an interval across a status-code range, with the gateway **returning 503 Service Unavailable to the client** while tripped and resuming after the trip duration; the statements that the breaker is **not supported in the Consumption tier**, that **only one rule may be configured per backend**, and that **breaker tripping rules are likewise approximate because instances do not synchronise**; an `acceptRetryAfter` flag under which the breaker waits for a `Retry-After` value supplied by the backend instead of its configured trip duration; portal defaults of a one-hour failure interval and a one-hour trip duration; and configuration through Bicep or ARM. The tool annotations used at phase 3 are taken from the Azure MCP Server tools index and its compute page, read the same day: **the annotations are documented as *hints***, the set comprises Destructive, Idempotent, Open World, Read Only, Secret and Local Required, **managed-disk delete is annotated destructive and idempotent and returns success whether the disk was removed or did not exist, while managed-disk create and virtual-machine create are annotated destructive and not idempotent**, and at least one delete tool exposes a `force` parameter documented as bypassing confirmation prompts.

**Two silences are recorded and one is taught.** The documentation calls both load balancing and breaker tripping approximate and **publishes no bound on either approximation** — no figure for how much traffic reaches a failed backend after a trip condition is met, at any instance count — which is the silence point 11 names to students and the reason step 2's estimates must come from the operator's own history. And the annotations are hints: **nothing in the documentation states that any client is obliged to honour them**, so an operation's idempotence is a publisher's claim rather than a verified property, which the seminar page records in its perishability register and does not develop.
