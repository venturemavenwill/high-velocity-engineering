# WP-072 — Orchestration Patterns as Control Flow

**Seminar day:** [S072](wiki/seminars/S072.md) · **Module:** [M15](wiki/modules/M15.md) · **Quarter:** [Q8](wiki/quarters/Q8.md)
**Strands:** IS · SY · ME · **Complexity class:** 5
**Platform anchor:** Microsoft Agent Framework — the five built-in workflow orchestrations · **MCP servers:** Foundry MCP Server · Microsoft Learn MCP Server

## Abstract

This paper defends teaching agent orchestration as control flow — five constructs the cohort learned in year one, with the branch conditions computed by a component that has no obligation to be consistent — and defends that framing on durability grounds rather than on elegance ones. It defends making path-set cardinality the day's assessed object, on the argument that a system whose path set is unbounded has no enumerable failure modes and that every subsequent day in the module marks up the drawing this one produces. It defends retrieving [S017](wiki/seminars/S017.md) at six quarters so that the orchestrator's victim is derived by the room rather than asserted, and defends a phase 3 in which four orchestrations are built, run twice and read from their own traces, whose simplest pattern wins on one task and loses on a second. **Section 8 records that the second task was absent from the first draft, that [S017](wiki/seminars/S017.md) had supplied the remedy six quarters earlier, and that this is the second consecutive day of this module on which a remedy in the design's own repertoire went uncarried and was found only by writing the objections section.** It concedes separately that the day has no instrument for a bound that is too loose, and that the day's platform layer supplies a mnemonic for exactly the perishable vocabulary its own point 8 tells students not to retain.

## 1. The instructional problem this day must solve

The vocabulary for this material is changing while the students are in the room, and it is changing in a way that is hostile to teaching.

Patterns acquire names. Names acquire frameworks. Frameworks acquire diagrams, and the diagrams are good — they are legible, they are memorable, and they are the thing a student will reproduce in an interview two years from now, by which point the framework will have been replaced twice. The [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) records agent orchestration patterns as semi-durable and re-verified annually, and protocol-mediated interoperability as re-verified per delivery. **A day organised around the vocabulary would be a day whose entire content the register forbids assessing.**

So the day needs a framing that is cheaper than the vocabulary and outlives it, and the framing has to do real work rather than merely being safe. The one this design uses is that **orchestration is control flow**: sequence, branch, loop, fan-out and join, recursion. It is deliberately unglamorous. It is also, in the design's view, correct, and it earns its place by delivering three things the vocabulary does not.

**It makes the path set computable.** Once a student names the construct, the arithmetic follows — one, k, the product, or unbounded — and [S031](wiki/seminars/S031.md) established four quarters ago that the object of reasoning is the set of executions. **A student who cannot bound the path set cannot enumerate the failure modes**, and every artefact in the rest of the module is an enumeration over that set: the crossings at [S073](wiki/seminars/S073.md), the failure shapes at [S074](wiki/seminars/S074.md), the unit of judgement at [S075](wiki/seminars/S075.md).

**It locates what is actually new.** Exactly one thing about this material has no precedent in the cohort's first year, and it is not the pattern catalogue: it is that **the branch condition is computed by a component with no obligation to be consistent between two runs on the same input.** In an ordinary program the same input takes the same path. Here it does not, and no defect is present. Naming that as the single novelty is what stops students treating the whole area as unfamiliar.

**It carries [S017](wiki/seminars/S017.md) across.** An orchestrator decides which component runs next, on whose request, under what budget. That is a scheduling policy, and [S017](wiki/seminars/S017.md) established at class 2 that no scheduling policy is neutral and that the thing deprioritised is somebody's work. Getting a room to take the victim question seriously about orchestration is otherwise difficult; here the room derives it from a day they sat six quarters ago, in phase 2, in under two minutes.

The specific difficulties the day must beat are three.

**The path count written as a number.** Item 4's error. A student counts the branches they drew and stops, because a loop with a model-computed continuation condition does not look like an unbounded construct — it looks like a step that repeats a few times. The cap is the only bound and it lives in a configuration file next to a timeout.

**The simplest-pattern conclusion.** Phase 3's first task is constructed so that the least autonomous pattern wins, which is the finding the room needs. It is also, on one record, a conclusion that is wrong, and §8 records what the first draft of this design did about that.

**Framework fluency mistaken for analysis.** A student who can name six patterns and cannot state the path set of any of them has acquired the perishable layer exactly.

## 3. Theoretical basis for the design

### 3.1 Load profile and element interactivity

**Moderate and unusually well-shaped, because the day's hardest object is a drawing.**

A control-flow diagram is an external representation that holds the path set for the student rather than requiring them to hold it. That is the day's principal load management and it is not incidental: the alternative — reasoning about an agent's possible behaviours in prose — requires holding a branching structure in working memory while also holding the model's inconsistency, and that combination is where students stall.

The interactivity is between steps 1, 2 and 3. The drawing determines the path set; the path set is unbounded exactly where a construct makes it so; and step 3's divergence statement is what turns a drawn branch into a set of paths that a second run might take. A student who draws without marking model-computed conditions produces a diagram that looks like a program's and licenses conclusions a program's would license, which is the specific wrong artefact the day is preventing.

Management:

- **The notation is worked with the room** at step 1 and is five box types.
- **Phase 3's four patterns, two tasks and all records are supplied**, pre-run and readable.
- **The capability is the one already chosen**, so nothing is scoped on the day.
- **Step 7 is a harness.**
- **The path arithmetic is four rules and is written up rather than spoken**, because a student reasoning with it cannot re-inspect a spoken sentence.

**Step 6 is unsupported.** Expertise reversal begins to apply at point 1 for a student who has implemented an orchestrator professionally; the design's answer is that such a student is not being asked to learn the constructs but to bound their own system's paths, and phase 7's partner will attack the bound.

### 3.2 Desirable difficulties selected, and those deliberately not

**Selected.**

- *Drawing a real system's control flow before any vocabulary exists,* item 1.
- *Committing a path count before the loop is named as unbounded,* item 4.
- *Ranking four patterns before the records arrive,* phase 3.
- *A second task on which the ranking reverses,* phase 3.
- *Stating what a second run on the same input might do differently, per branch,* step 3.
- *Naming the request class your own pattern deprioritises and who submits it,* step 4.
- *Predicting a path not on your own drawing,* step 6.
- *A partner who must construct one,* phase 7.

**Deliberately not selected.**

- *Implementing the patterns.* IS302's. A student debugging an orchestrator is not analysing one.
- *Concurrency between branches.* [S031](wiki/seminars/S031.md) to [S035](wiki/seminars/S035.md) own it and point 1's scope statement names it as excluded. Shared mutable state across fan-out branches is a real and common construction and it is a module's worth of material, not a point's.
- *Cost modelling of the patterns.* [M13](wiki/modules/M13.md)'s, five weeks behind. Phase 3 reports cost per completed request as an adjudicator and does not ask students to derive it.
- *Multi-agent delegation as an orchestration topic.* [S073](wiki/seminars/S073.md) point 6 treats it as a trust question, which is where the design believes it belongs, and putting it here would make it a topology question.

**Scope, per the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md), strong form.** Point 1's five constructs are **safe** as a vocabulary for describing and bounding a single orchestrated capability whose configuration you can read. They are **unsafe** in two named conditions. Where a component can be resumed from outside on a signal — an interrupt, an event subscription, a webhook — the flow has an entry point the drawing does not contain, and the path set computed from the five is a lower bound that will be read as a total. Where branches share mutable state, the constructs still describe the topology and no longer describe the behaviour, because the interleaving is now part of the path and [S031](wiki/seminars/S031.md)'s executions are back. **A student who bounds a path set for a system with either property has produced a number that is confidently wrong**, and the day's own artefact is one of them if the capability has an event entry — which the specification does not currently check, and which §8 objection 2 does not fix either.

**The platform instance carries its own scope statement, at point 9.** The mapping from the framework's five built-in orchestrations onto the five constructs is **safe** for describing what an orchestration you can read the configuration of does, and for absorbing a new orchestration name by asking which composition it is. It is **unsafe** in three directions. It is not a claim that the framework's five are a complete set — the documentation itself lists further patterns as in development, and the day quotes that rather than asserting completeness. It is not a claim that any other framework's names map the same way, since the mapping is a property of these implementations and not of the constructs. And it is **unsafe as a claim that the mapping is evidence for the five constructs**: a catalogue agreeing with a decomposition establishes nothing about either, and a student who cites the framework as warrant has made the error §8 objection 3 examines. Step 1's *name a composition your framework has no name for* clause is the artefact element under which a student applying the mapping outside its range would fail.

### 3.3 Engagement and motivational mechanism

The day runs on **phase 3's reversal.**

Groups rank four patterns, confidently, and the room's ranking is defeated: the least autonomous pattern wins on the substrate's own record. That is satisfying and it is a trap, and the design springs it in the same phase. The second task arrives, the ranking inverts, and the students who have just concluded that simplicity wins discover they have learned a fact about one workload. **What survives is the method — bound the paths, characterise the task, price the match — which is the only thing the day wanted them to leave with.**

The second mechanism is item 4 against phase 8. A student writes a number. The number is wrong for a structural reason they can state themselves once the loop is named, and phase 8 reports the fraction of the room that did it. Nobody is corrected individually and the finding is the room's.

The third is step 4. Naming the class of request your own pattern deprioritises, and the people who submit it, is [S017](wiki/seminars/S017.md)'s demand at class 5 with real requesters attached, and the cohort's pooled victim list at phase 8 is the phase's content: **the overlaps are the interesting part, because a class deprioritised by most of the cohort's patterns is a class the substrate is about to systematically underserve.**

Autonomy is complete at steps 1 to 4 and constrained only by the construct vocabulary. Competence is supported by the drawing, which makes a hard analysis into a legible artefact. Relatedness is supplied by the named requesters at step 4 and by the partner at phase 7.

The competence risk is at step 2 for a student whose capability turns out to be unbounded in three places. The instructor states before phase 5 that an unbounded path set is a finding rather than a defect, that the correct output is the construct and its practical bound, and that [S074](wiki/seminars/S074.md) will use the unbounded region as its material.

## 4. Phase-by-phase design and its warrant

**Phase 1 (25 min).** Five sealed items on a real system with its trace log. Item 2 administers the day's central distinction before it is named; item 4 is the discriminator; **item 5 is the sealed Copilot prediction**, required by the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md) and administered before phase 4 per instrumentation rule 8.

**Phase 2 (20 min).** Four retrievals, one scaffolded at six quarters, and a bridge whose answer is *a scheduling policy, and therefore it has a victim.*

**Phase 3 (45 min).** Four orchestrations, **built and run twice**, two tasks, three findings — the ranking, the reversal, the join. Selection disclosed per instrumentation rule 3. The second task's provenance is described in §8. The running is what makes the divergence at P3 and the silent join at P4 observations rather than assertions.

**Phase 4 (50 min).** Ten points. Point 1 carries the strong-form scope statement. Point 3 is the assessed object. Point 4 is the reversal named. Point 6 is [S017](wiki/seminars/S017.md) point 7 at class 5. Point 8 is the perishability defence stated as a competence. **Points 9 and 10 are the platform layer**, placed after point 8 so the framework catalogue arrives as an application of the constructs rather than as their source — an ordering §8 objection 3 argues is necessary and insufficient.

**Phase 5 (90 min).** Seven steps producing the drawing the rest of the module marks up **and the running orchestration it describes**. **Step 7's second clause is the first empirical test of an [S071](wiki/seminars/S071.md) boundary. Step 6 is unsupported.** The artefact gains the prompt record, the intervention record and the frontier statement.

**Phase 6 (40 min).** A cap raised correctly, for the right people, with a review, and an outage eleven weeks later caused by a system nobody had connected to it — then an agent case in which a correct retry multiplied a path set nobody was looking at.

**Phase 7 (30 min).** A path off the drawing, and a construct priced against a capability. Both reuses contingent under rule 5 as amended.

**Phase 8 (20 min).** Item 1 against the trace log; item 2 by direction; item 4's number-for-a-loop fraction; **item 5 read against item 4**; the reversal against the cohort's own task characterisations; step 6 against step 7; the [S071](wiki/seminars/S071.md) breach count; the pooled victim list.

## 5. Predicted failure modes and countermeasures

**Students with more relevant prior knowledge.** A student who has built an orchestrator will draw quickly and correctly and will bound the path set by inspection of the code. Predicted failure: **they bound it accurately and never notice that the model-computed conditions make the bound a different kind of object** — their drawing is a program's drawing and their number is a program's number. Countermeasure: step 3 requires a divergence statement per model-computed condition, in writing, before step 7; and phase 7's partner is instructed to construct an input rather than to critique the diagram, which is a demand a code reading does not answer. §8 objection 2 concedes that a related error — the bound that is too loose — has no countermeasure at all.

**Students with less relevant prior knowledge.** The risk is not the constructs; it is that a student who has not read an agent configuration cannot find the branch conditions in it. Countermeasures: item 1 supplies a system whose configuration is annotated; the notation is worked with the room; the capability at step 1 is the student's own and is as small as they made it; and a fallback drawing of the substrate's own capability is available and its use is recorded in the assessor note rather than concealed.

**Phase 3 succeeds too easily.** P1 winning on the first task is not hard to see once the incident records are read, and a quick group will have it in ten minutes. **The difficulty is the reversal**, and the design's expectation is that no group predicts it — the room has just been rewarded for concluding that fewer paths are better, and the second task punishes exactly that conclusion. A group that predicts the reversal has done the day's work in phase 3. **Fallback:** ask which pattern they would deploy on the substrate for the *combined* traffic of both tasks, which admits no clean answer and forces either a routing construct or an explicit statement of who is being underserved.

**Affective failure.** The characteristic risk is **deflation.** The day's argument is that the interesting new area reduces to five constructs from year one and a scheduling lesson from year one, and a student can hear that as *there is nothing here.* That reading is more likely in this cohort than in most, because they have spent seven quarters being told that things they thought were new were old, and the move has by now a slightly deflating familiarity.

Countermeasures: point 2 is stated as the one genuine novelty rather than as a footnote, and it is a real one — a branch condition with no obligation to be consistent has no analogue anywhere else in the programme. Phase 3's reversal is not predictable from the constructs and demonstrates that the framing generates findings rather than merely organising them. Point 8 is framed as a competence students will have that their colleagues will not: describing a system in terms that survive its framework. And the instructor states once, at point 8, that reducing a moving vocabulary to a stable one is the whole of what makes an engineer's knowledge worth anything after five years.

## 6. Retention architecture

Retrieved by [S073](wiki/seminars/S073.md) at one week (where the drawing is the surface every trust crossing is marked on), [S074](wiki/seminars/S074.md) at two weeks (where the unbounded region supplies the failure cases), [S075](wiki/seminars/S075.md) at three weeks (where the unit of judgement is chosen over this path set), [S077](wiki/seminars/S077.md) (resource exhaustion, where an adversary moves the operating point of a loop), [S079](wiki/seminars/S079.md) (drift, where a path distribution shifts without any change to the system) and [S087](wiki/seminars/S087.md) (the safety case, where the bound is a claim the case rests on).

**[S073](wiki/seminars/S073.md) at one week is the primary target** and the dependency is total: a crossing is a point on a path, and a student without a drawing has nothing to mark.

**[S079](wiki/seminars/S079.md) at seven weeks is the most interesting retrieval.** A path distribution that shifts while the configuration is unchanged is drift in a form the programme has not previously taught — the system's own branch conditions have moved — and it is only observable against a baseline distribution, which is what step 7 produces. This day should record its distribution for that purpose and the design does not currently say who keeps it; that is a gap and it is named here rather than in §8 because it is an omission rather than an argument.

Retained content: the five constructs, the model-computed branch condition, the path arithmetic, the task-shape rule, the step cap as a loop bound, and the orchestrator's victim. Six items.

No constituent skill is scheduled for blocked practice. The path arithmetic is exercised four times in phase 3 and once in phase 5, then interleaved into the between-day sets alongside [S033](wiki/seminars/S033.md)'s availability arithmetic and [S063](wiki/seminars/S063.md)'s concurrency ceilings, which are the two computations it is most confusable with.

Own schedule: next morning, day 3, week 2, week 3.

## 7. Assessment and evidence generated

**No entrustment judgement**, per [Q8](wiki/quarters/Q8.md).

One specification item in IS302 with ME302. Per rule 1, the checked elements are the drawing in the five constructs with branch conditions marked by origin, **together with one composition the framework has no built-in name for**; the path bound or the unbounding construct with its practical bound, who set it, **and the configuration field it sits in**; the step 3 divergence statements; the deprioritised request class with magnitude and submitter; the task-shape characterisation and the mix change that would invalidate it; a join-distinguishability statement for every join including an explicit cannot; the step 6 prediction; **the deployed orchestration and its realised path distribution with [S071](wiki/seminars/S071.md) breaches marked**; both phase 7 outcomes; **the prompt record**; **the intervention record**; and **the frontier statement**. **Nothing else is assessed.**

Three hard requirements: **a path count stated as a number for a system containing a loop fails**; **a drawing with no named victim fails**; and **a framework's pattern name used in place of a construct fails**, including any of the five the framework supplies at point 9. A fourth, imported from the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md): **an intervention record with no entries fails** unless the artefact demonstrates that the design could have detected an intervention-worthy error, and a deliberately set and defended step cap is the qualifying demonstration on this day.

Reliability is observed within the activity, evidenced by whether the step 2 bound is one the student's own configuration enforces.

**Older forward links discharged.** [WP-031](wiki/whitepapers/WP-031.md) §6 named this day as its principal long-range target; **that is phase 2's bridge and point 3**, and it is answered by the room rather than asserted. [WP-017](wiki/whitepapers/WP-017.md) §6 named this day; **that is point 6 and step 4**, with the *who submits it* clause carried unchanged. [WP-021](wiki/whitepapers/WP-021.md) §6 named this day; **that is point 1**, whose scope statement names the two conditions under which the structural hypothesis fails.

**Instrumentation under rule 6.** Two instruments with named response occasions, both inside this module. **The step 2 path-bound error** responds at [S074](wiki/seminars/S074.md) phase 3, whose four tool-failure cases are drawn from the paths this cohort did not bound, with the selection rule disclosed to students per instrumentation rule 3. **The count of realised paths touching an [S071](wiki/seminars/S071.md)-prohibited action** responds at [S073](wiki/seminars/S073.md) phase 5 step 5, where every breach path must acquire an enforcement point at a named boundary or the prohibition must be re-declared as accepted. **[WP-073](wiki/whitepapers/WP-073.md) §7 and [WP-074](wiki/whitepapers/WP-074.md) §7 must report whether those elements exist.**

Programme instrumentation: the item 1 construct-omission rate; the item 2 attribution error by direction; the item 4 number-for-a-loop fraction; the step 6 unlisted-path hit rate; and the cohort's pooled victim list, whose overlaps are the substrate-level finding.

ABET and CS2023 contribution: PO1 and PO2.

**What this day does not license anyone to conclude.** A student's bound is evidence that they can name the constructs in their own capability and compute a path count from them. **It is not evidence that the bound is correct**, since step 7 exhibits paths and cannot falsify a bound — §8 objection 2. It is not evidence about systems with event-driven entry or shared state across branches, which point 1's scope statement excludes and which the specification does not check for. And **phase 3's ranking licenses nothing about which pattern to use**, which is the point of the second task and is stated to the room in those words.

## 8. Objections and rebuttals

**Objection 1: the day taught a general lesson from a single record, and the remedy for that was already in the design's repertoire, from the day this one retrieves.**

At its strongest, as it applied to this design's first draft: phase 3 ran four patterns against **one** substrate task and reported that the simplest won. That is one system, one task, one traffic profile and one three-month period. The programme has spent [S041](wiki/seminars/S041.md), [S042](wiki/seminars/S042.md), [S049](wiki/seminars/S049.md) and [S059](wiki/seminars/S059.md) teaching students to distrust exactly that inference, and the day would have been running it in front of them while asking them to generalise from it. Worse, the case set was staff-selected, which instrumentation rule 3 requires be disclosed, and a disclosed selection does not repair a single-record generalisation.

**And [S017](wiki/seminars/S017.md) — the day this one retrieves in phase 2 — had already solved it.** Its phase 3 runs four scheduling policies against one workload, then against a second workload with a different shape, and the ranking reverses; [WP-017](wiki/whitepapers/WP-017.md) states in as many words that the second workload is what prevents the phase teaching "shortest-first is best." The identical construction, for the identical reason, was six quarters behind this day and was cited in this day's own phase 2.

**The day is fixed rather than recorded**, per the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md)'s criterion: instrumentation rule 5 is a written rule, the remedy was validated as far as any remedy in this design can be, and no design judgement was in contest. Phase 3 now runs both tasks, the ranking reverses, point 4 states the rule the reversal establishes, step 4 carries a task characterisation, and phase 8 checks each student's pattern choice against the mix change they themselves named. The correction is annotated in the day at the point of change and **a compliance-register entry is required**, stated verbatim in §9.

**What this makes visible is worse than the instance and is conceded.** This is the **second consecutive day of this module** on which a remedy already in the design's repertoire was not carried across, and the second found by the same method: writing the objections section. [WP-071](wiki/whitepapers/WP-071.md) §8 found [S068](wiki/seminars/S068.md) step 5's external-observer form uncarried at [S071](wiki/seminars/S071.md) phase 7. This paper finds [S017](wiki/seminars/S017.md) phase 3's second-workload form uncarried here. Both are rule 5 failures; both were cheap; both were in days the failing day explicitly cites.

**The design's own diagnosis is that rule 5 has no trigger.** Rules 1, 3, 4 and 6 are checkable against a single day's material — is there a self-report, is the sampling disclosed, does the instrument name a response, is the response occasion named. Rule 5 requires the author to recall every remedy in the repertoire and test the current day against all of them, and nothing in the writing order prompts it. **The natural fix is a rule-5 checklist maintained alongside the compliance register**, listing each validated-or-proposed remedy with the failure it addresses, consulted at §5 of every whitepaper. That is a change to a shared page and this paper cannot make it; it is argued for in §9 and reported rather than enacted. Two instances in two days is not proof that the checklist is worth its cost, and it is enough that a third should not be argued from scratch.

**Objection 2: the day has no instrument for a bound that is too loose, and a too-loose bound is the safe-looking error.**

At its strongest: the day's assessed object is a bound on the path set, and the only evidence the day generates about a bound is step 7's shadow run, which **exhibits paths.** A run can show that a student's drawing missed a path — under-drawing — and phase 8 reports exactly that. **No run can show that a bound was too loose.** A student who states that their capability has forty distinct paths and observes six has not been contradicted, and neither has a student who states four hundred.

That matters more than it sounds, because **the loose bound is the error a specification like this one creates.** The day fails a number stated for a system containing a loop; it does not fail a number that is enormous. A student who writes a bound of ten thousand has satisfied every checked element, cannot be shown wrong, and has produced an enumeration that is useless for the purpose the rest of the module needs it for — [S073](wiki/seminars/S073.md) marks crossings on paths, and ten thousand paths cannot be marked. The failure will not surface until [S074](wiki/seminars/S074.md), where the student will be unable to classify, and it will look there like a failure of the classification.

**The fix is one clause and it is named.** Require step 2 to state both the bound and **the tightest bound the student can defend**, with the argument; and give phase 7's partner a third obligation — attack the tightness rather than the coverage. It costs a sentence in the specification.

**It is declined and the reason is not a good one.** Phase 7 already carries two obligations, and this design holds to two because a three-part peer protocol in thirty minutes degrades into one partner talking. That is a real constraint and it is the reason the fix is not taken, and it is a scheduling reason rather than an argument that the objection is wrong. **The objection stands and the day ships with a known asymmetric instrument**: it detects the error that looks careless and not the error that looks careful, which is the wrong way round and is a shape this programme has criticised elsewhere in other people's work.

**Objection 3: the day's platform layer supplies a mnemonic for exactly the vocabulary its own point 8 tells students not to retain.**

This is the objection that bites on the practical turn, and it bites because the fix for the day's first problem creates its second.

At its strongest: point 8 is the day's defence against its own perishability. It says **name the construct, not the framework**, and the specification fails a pattern name used in place of a construct. Point 9 then supplies a clean one-to-one mapping from five branded orchestration names onto the five constructs. **A one-to-one mapping is a mnemonic.** It is the most memorable object in the day, it will be reproduced in an interview two years from now, and it is composed entirely of the semi-durable vocabulary the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) forbids assessing. The day has not merely tolerated the perishable layer; **it has made the perishable layer easier to acquire by putting it next to the durable one in a table.**

The specification's countermeasure is real and it is one-directional. It fails a student who writes a pattern name where a construct belongs. **It does not test whether the student can go the other way** — whether they can describe a composition the catalogue has not named — and that is the direction in which the mapping actually fails, because a mapping is a lookup and a lookup has no entry for a case its table does not contain.

**This is an internal contradiction rather than a judgement between defensible options**, so the day is fixed rather than recorded, per the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md)'s criterion. **Step 1 now requires the student to name one composition of the five constructs their framework has no built-in name for, and to say whether their capability needs it.** It costs one clause, no phase time, and it has material available from the framework's own documentation, which lists further patterns as in development. A student who can produce such a composition has the constructs; a student who cannot has the table.

**What remains is conceded and is not small.** The fix tests production of an unnamed composition and it does not prevent retention of the named five, which are memorable whether or not anything assesses them. The design's honest position is that **the mapping's teaching value — a student can absorb a sixth orchestration in a sentence — is worth its retention cost**, and that this is a bet rather than a demonstration. §9 prediction 5 is written to lose it if it is wrong.

## 9. Falsifiable predictions and instrumentation

**Prediction 1.** At item 4, more than half of the cohort will write a number for a system whose loop makes its path set unbounded, and the numbers written will cluster near the count of drawn branches rather than near the cap. *Instrument:* item 4 responses coded number / unbounded, with numeric answers compared against both the drawn-branch count and the cap. **The clustering is the claim**: if the numbers cluster near the cap instead, students are treating the loop as a construct and mis-computing it, which is a different and much smaller problem.

**Prediction 2.** No group will predict the phase 3 reversal, and after it, more than half of step 4 task characterisations will name a mix change that would invalidate their own pattern choice. *Instrument:* group rankings on task 2 recorded before the records are supplied; step 4 characterisations coded for whether the named invalidating change is one their pattern would actually fail on. **If groups predict the reversal, the first task's construction is not defeating expectation and P1's win is being read as a demonstration rather than as a finding.**

**Prediction 3.** The number of realised paths touching an [S071](wiki/seminars/S071.md)-prohibited action will be greater than zero for a majority of students, and the breaches will concentrate on prohibitions whose enforcement field was blank. *Instrument:* step 7 breach counts joined to the [S071](wiki/seminars/S071.md) step 4 enforcement records. **If breaches concentrate on prohibitions that had a named enforcement, the enforcement points students named do not exist**, which is a finding about [S071](wiki/seminars/S071.md)'s step 4 rather than about this day and would be the strongest available evidence for [WP-071](wiki/whitepapers/WP-071.md) §5's fluency failure.

**Prediction 4.** Step 6's *one path not on your drawing* will be answered correctly by fewer students than step 6's *least frequent path*, and the gap will be large. *Instrument:* step 6 and step 7 pairs coded separately for the two clauses. **The gap is the claim**: predicting the frequency of a path you drew is interpolation, and predicting a path you did not draw requires knowing what your own representation omits, which is the competence [S073](wiki/seminars/S073.md) needs and which this design believes the cohort does not yet have.

**Prediction 5.** At step 1's added clause, more than half of first submissions will name a composition that **is** one of the framework's five under a different description, and the modal error will be a fan-out with a model-selected aggregator offered as unnamed. *Instrument:* step 1 compositions coded against the framework's catalogue at delivery. **This is §8 objection 3's test and it is written to lose the design's bet**: if students cannot produce a composition outside the catalogue, the mapping has replaced the constructs rather than illustrating them, and point 9 should be moved out of phase 4 into a handout that is not taught.

**Prediction 6.** At item 5, the modal sealed prediction will be that the agent produces a *correct drawing with a wrong bound*, and the agent's stated bound will cluster with the room's at item 4 rather than with the cap. *Instrument:* item 5 responses coded against the agent's actual output per student, with agent bounds compared to drawn-branch counts and to the cap on the same axis as item 4. **The clustering is the claim.** If the agent bounds correctly while the room does not, the day has an unusually clean frontier datum in the opposite direction from the one the design expects, and the phase 6 agent case is the wrong case.

**Instrumentation note, for the compliance register.** The entry §8 objection 1 requires, stated so that it can be transcribed without re-derivation: *[WP-072](wiki/whitepapers/WP-072.md) §8 — [S072](wiki/seminars/S072.md) phase 3 generalised from a single task record and did not carry [S017](wiki/seminars/S017.md) phase 3's second-workload remedy across. Rule: instrumentation rule 5. Status: **Fixed**. Reason: violation of a written rule with the remedy already in the repertoire and cited in the same day's phase 2; no design judgement was in contest.* The paper additionally argues, without enacting, for **a rule-5 checklist maintained alongside the compliance register**, listing each remedy in the repertoire with the failure it addresses, to be consulted at §5 of every whitepaper — on the ground that rule 5 is the only instrumentation rule with no checkable trigger and has now failed twice in two consecutive days.
