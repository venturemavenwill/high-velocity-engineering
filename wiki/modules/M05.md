# M05 · Algorithmic Thinking Under Constraint

**Quarter:** [Q3](wiki/quarters/Q3.md) · **Seminar days:** [S021](wiki/seminars/S021.md)–[S025](wiki/seminars/S025.md) · **Complexity class:** 2
**Strands:** CF · MS · SY
**Platform anchor:** Azure AI Search — one index, five days · **MCP servers:** Microsoft Learn MCP Server · Azure MCP Server (read)

---

## The central difficulty

Students believe that a sufficiently clever person can solve any problem efficiently, and that failing to find an efficient algorithm is a failure of effort or ingenuity. This belief is flattering, common, and expensive: it produces engineers who spend weeks on problems that are provably hard, who cannot tell a colleague that a request is unreasonable, and who ship heuristics without saying they are heuristics.

The module installs the opposite stance. **Some problems are hard in a way that is a property of the problem, not of you. Recognising this is a technical skill, saying it is a professional obligation, and what you do afterwards — approximate, restrict, or refuse — is a decision with stated consequences.**

This is the programme's first sustained encounter with a limit that cannot be engineered around, and it is deliberately placed before M06 teaches the analogous limit on evidence.

**The module now has a second difficulty and it arrived with the tooling.** A student prompting GitHub Copilot to solve a hard problem will get an answer. The agent does not decline, it does not hedge, and its output on an intractable request is indistinguishable in tone from its output on a routine one. Every belief the module exists to correct is reinforced by an instrument the students use every day. **That is the module's practical turn: the duty to say so is now first a duty owed about a machine that will not say it for you.**

## The module's platform instance

All five days run against **one Azure AI Search index**, built by the cohort on day one over the substrate corpus and kept for the module. The load argument is the one the module already makes for its single problem domain: comprehension is paid once and the variation is entirely in the analysis. The service is chosen because it instantiates the module's five subjects without adaptation.

| Day | What the index supplies |
|---|---|
| S021 | Four retrieval methods over one corpus, each asserting a different structural property, and one of them exact |
| S022 | Four filter modes whose guarantees differ in form — one guarantees a count, two do not, and the documentation says which |
| S023 | An asymmetry that is literally a reduction's direction: an approximate index answers an exact query and an exact index cannot answer an approximate one |
| S024 | A schema whose existing fields cannot be modified, and a reranker that cannot see past its candidate window |
| S025 | An exhaustive scan that generates the ground truth against which an approximation's promise is measured |

S025 additionally reaches into **Foundry's `document_retrieval` evaluator**, which is the quarter's second anchor and M06's first, because its metrics are the measured-distribution promise made mechanical — including one metric whose only job is to count the documents your ground truth does not cover.

**Every day produces a build.** The whole-task phase ships a configuration, a measurement harness or a reply against the real index, authored principally by prompting Copilot in agent mode through the Azure MCP Server in read configuration and the Learn MCP Server for grounding. Each artefact carries a **prompt record**, an **intervention record** and a **frontier statement**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

**Where a capability cannot be operated it is demonstrated and not assessed.** Two fall in that class for this module: `strictPostFilter` and the vector-query `threshold` parameter are preview features, and the module shows them rather than requiring them.

## Why this module sits here

**It requires M03 and M04's cost vocabulary.** An argument that a problem is intractable is meaningless to a student who cannot reason about cost in the first place.

**It must precede M06.** The two modules teach the same competence — knowing and stating a boundary — and the computational version is cleaner, because intractability can be proved and construct validity cannot. Students meet the tractable form first.

**It must precede M07.** Distributed systems are full of impossibility results, and a student who has not accepted that some things cannot be done will read a consistency trade-off as a temporary engineering limitation.

**And it must be the first module with a service in front of it.** M04 measured a machine. This module argues with one, which requires a system that will answer a question it cannot answer well and report success.

## Task-class variability plan

The module varies **what makes the problem hard**, so that hardness is recognised as a family rather than as a property of particular problems.

- **S021** varies the structure the problem has — optimal substructure, overlapping subproblems, greedy-choice property — and which paradigm each supports.
- **S022** varies the guarantee's form: worst case, amortised, expected, high probability.
- **S023** varies the reduction's direction, which is the day's central and most-confused distinction.
- **S024** varies the requester, because the same intractability must be communicated differently to a colleague, a manager and a user.
- **S025** varies the guarantee that can be offered: approximation ratio, restricted input class, anytime behaviour, or nothing but measured performance.

## Load profile

High at S023 and S025, moderate elsewhere.

S023 is the module's peak: reduction direction is the single most reliably confused idea in undergraduate complexity, and getting it wrong inverts every conclusion. It is given the module's most heavily faded task.

S025's load is different in kind — the difficulty is not analytical but decisional, since the student must choose what to promise under acknowledged uncertainty and defend it to a person who wanted a guarantee.

The module's standing load reduction is that **all five days use problems from one domain** — the substrate's scheduling, routing and matching problems — so that the problem statements are familiar by S022 and the variation is entirely in the analysis.

## Module-level predicted failure modes

**Intractability learned as a vocabulary.** Students acquire the terminology and apply it as a label rather than as an argument. Countermeasure: S024's artefact requires the reduction, not the classification, and a claim of hardness with no reduction fails.

**Reduction direction inverted.** The module's most likely technical failure. Countermeasure: S023's phase 3 supplies four reductions of which two are backwards and both directions produce plausible-sounding conclusions.

**The duty to say so becomes a refusal reflex.** Students who learn that some problems are hard may start declining problems that are merely difficult. Countermeasure: S024's phase 3 includes two problems that look intractable and are not, and the day's specification requires the student to state what they checked before concluding.

**Heuristics shipped without guarantees.** The module's target professional failure, reproduced by its own students. Countermeasure: S025's specification fails any recommendation whose promise is not stated in terms a non-specialist requester can check.

**The agent's confidence adopted as the student's.** New with the platform anchor and predicted to be the module's most common failure. An agent asked for a hard thing produces a fluent answer, and a student who has not formed their own view first will adopt it. Countermeasure: **the sealed phase 1 Copilot prediction, which is written before the agent is run on every one of the five days** and opened at phase 8, and which by design cannot migrate into phase 5 — instrumentation rule 8. A student who has committed a prediction in writing has a position to defend against the output.

**An intervention record with no entries.** The module's own instrumentation failure. A student who accepted everything the agent produced has either had a trivial task or was not reading. Countermeasure: every specification in the module fails an empty intervention record **unless the artefact demonstrates that the design could have detected an intervention-worthy error** — the sensitivity escape [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected. In this module the escape is usually a check the student built: an assertion that the approximate result set matches the exhaustive one, or a schema pre-flight that reads the existing index before proposing an update.

## Assessment contribution

**No entrustment judgement in this module** — the quarter's is at S030.

Specification items:

- **S021** — a problem's structure characterised, with the paradigm it supports and one it defeats.
- **S022** — a guarantee stated in its correct form, with the caller for whom it is adequate.
- **S023** — a reduction in the correct direction, with the conclusion it licenses and the one it does not.
- **S024** — a hardness argument about a real substrate problem, with the reduction and the communication to a named requester.
- **S025** — a recommendation with a stated guarantee, checkable by the requester, and what happens when it is not met.

**Every one of the five gains the same three artefact elements** — the prompt record, the intervention record and the frontier statement — and every one of the five ends its checked-element list with *Nothing else is assessed*.

Dispositions observed: **integrity** at S025, in whether the promise made matches the guarantee available.

## Durable and perishable

The module's argument is durable and its instance is not. The separation is stated on each day's own page and summarised here.

| Durable claim, assessed | Platform instance, perishable |
|---|---|
| A method asserts a structural property that can be checked | HNSW, exhaustive KNN, BM25 and rank fusion as four assertions over one corpus |
| A guarantee has a form, and the form decides who is served | The filter modes, and which of them guarantees a result count |
| A reduction has a direction and three requirements | Which index kind can answer which query kind, and which cannot |
| Some requests cannot be satisfied and are owed to the requester | Field immutability and the reranker's candidate window |
| A promise must be checkable by its recipient | Recall against an exhaustive ground truth, and a judged score with no published calibration |

Parameter names, defaults, ranges, score ranges, window sizes, preview boundaries and every measured number are **perishable**. Where a service is renamed or its behaviour changes, the module is re-anchored and the five durable claims are unchanged; if a re-anchoring required one of them to change, that would be a finding about the claim and is recorded as such.
