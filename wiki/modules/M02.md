# M02 · Constructing Correct Programs

**Quarter:** [Q1](wiki/quarters/Q1.md) · **Seminar days:** [S006](wiki/seminars/S006.md)–[S010](wiki/seminars/S010.md) · **Complexity class:** 1
**Strands:** CF · MS · PE
**Platform anchor:** GitHub Copilot agent mode; custom instructions as executable specification · **MCP servers:** Microsoft Learn MCP Server

---

## The central difficulty

Students believe correctness is something you check for. They write a program, run it, observe that it produces the expected output, and treat that observation as evidence of correctness. The belief is not stupid — it is what the tooling encourages, what most instruction rewards, and what usually works.

It is also the belief that makes the rest of this programme impossible. A student who thinks correctness is checked after the fact cannot design an evaluation at S029, cannot argue for a release at S066, and cannot construct a safety case at S087, because all three require stating in advance what would have to be true. The stance the module installs is that **correctness is constructed into a program and then evidenced, not discovered by running it**.

M01 gave the technique. M02 makes it a working habit under the conditions where students actually write code, and then — at S010 — makes being wrong in public a normal event rather than an exceptional one.

## The idea this module owns

**A specification and a repository custom instructions file are the same object in two registers, and one of them tells you immediately when it is defective.**

Both state what must be true of work that does not yet exist. Both are defective when the work they produce does not conform. The difference is the feedback interval and where the blame lands. A specification defect surfaces when a human reads the artefact, weeks later, and is normally attributed to the reader's carelessness. An instructions file defect surfaces on the next prompt, and is attributable to the file — because the file is the only thing that changed.

This is why the module is the right place for it. Students arriving in week six believe a specification is a description of intent. The instructions file register refuses that reading, because an instructions file that describes intent and does not constrain output produces non-conforming work in front of the student who wrote it, within a minute. **A student who can write a specification and cannot write an instructions file that produces conforming work has not understood what a specification is for.** The equivalence is established at [S006](wiki/seminars/S006.md), and both specification rules 1 and 2 in the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) are applied to instructions files from that day onward.

The module's four technical days are the four things a specification has to be able to say — an invariant ([S006](wiki/seminars/S006.md)), a boundary ([S007](wiki/seminars/S007.md)), a termination argument ([S008](wiki/seminars/S008.md)) and a falsifiable claim ([S009](wiki/seminars/S009.md)) — and each is written twice, once for a human reader and once for an agent that will act on it.

## Why this module sits here

Three reasons.

**It must immediately follow M01, at the shortest possible gap.** S006 sits two days after S005 and re-uses the invariant technique in a programming rather than mathematical setting. That is a near-transfer test at the shortest distance the timetable permits, and it is deliberate: if the technique does not survive a change of setting after two days, it will not survive one after two years, and the design would rather discover that in week six.

**It must complete before Q2 begins.** M03 asks students to choose representations for a known caller, which presupposes that they can say what a chosen representation must guarantee. That is an invariant claim.

**S010 must be the first assessment-bearing day, and it must be an error clinic.** The programme's assessment architecture depends on students disclosing failure honestly for three years, under a firewall that keeps error-clinic content out of assessment entirely. Establishing that firewall on the first assessment-bearing day — and demonstrating that it holds — is worth more than anything the day could assess about programming.

## The platform this module runs on

Every day is executed in GitHub Copilot agent mode against the workspace's own customization surface, with the Microsoft Learn MCP Server supplying documentation grounding. Nothing in the module requires a cloud subscription, a tenant privilege or a paid deployment, which is deliberate: this is week six, and the programme's first build must not be blocked on procurement.

The surface the module operates is the repository itself. Verified against the Visual Studio Code documentation for agent customization, current at 15 July 2026:

| Object | Where it lives | What the module uses it for |
|---|---|---|
| Always-on instructions | `.github/copilot-instructions.md`, or an `AGENTS.md` file | A specification with no scope statement |
| File-scoped instructions | `.github/instructions/*.instructions.md`, with an `applyTo` glob | A specification whose scope is stated and checkable |
| Prompt files | `.github/prompts/*.prompt.md`, invoked as a slash command | A procedure |
| Custom agents | `.github/agents/*.agent.md`, with a declared tool list | A boundary drawn around what may be done |

The Learn MCP Server is a remote server at `https://learn.microsoft.com/api/mcp`, requiring no authentication and carrying no charge, exposing `microsoft_docs_search`, `microsoft_docs_fetch` and `microsoft_code_sample_search`. Its documented limits are used as content rather than hidden: it serves published documentation only, and its knowledge service refreshes incrementally on content update with a full refresh once a day. **The documentation states that cadence and states no retrieval accuracy for the search tool** — which is the asymmetry [research/06-microsoft-platform/](research/06-microsoft-platform/collected-materials.md) records across every source in that folder, met here on the module's first day.

## Task-class variability plan

The module stays at complexity class 1 — the task is specified and the method is given — so all variability is surface variability. The plan is deliberate about which surface each day varies, because four days varying the same surface would produce four instances of one case.

- **S006 varies setting.** One technique, two contexts: the mathematical loop from S005 and a piece of substrate code. Nothing else changes.
- **S007 varies seam placement.** One problem, three decompositions, and a change request that is cheap under one and expensive under the others.
- **S008 varies recursive structure.** One argument shape over three inductive structures, which supplies the variability WP-005 conceded was thin within S005 itself.
- **S009 varies the claim.** One program, several hypotheses about it, and tests designed to discriminate between them rather than to confirm any.
- **S010 varies nothing.** It is an assessment occasion and a norms occasion.

Each of S006 to S009 ships a build. The builds are small — a few files in a repository — and they run, which is the property that matters. A day that produced a described design and not a working configuration would leave the module's central claim untested, because an instructions file that has never been executed is indistinguishable from a specification that has never been read.

## Load profile

The module's interactivity is high at S006 and S008 — both are invariant reasoning under interaction — and moderate at S007 and S009, where the individual elements are simple and the difficulty is in the choice between them.

The module's dominant load risk is **not intrinsic**. It is that students are, for the first time, writing code that is looked at by other people and assessed against a specification with no partial credit. That is an evaluative-threat load, and it is managed by the token economy, by the error-clinic firewall stated explicitly and repeatedly, and by keeping the programs small enough that failure is legible rather than diffuse.

Fading across the module: S006 supplies the invariant and asks for the argument; S007 supplies the decompositions and asks for the judgement; S008 supplies the structure and asks for both; S009 supplies neither and asks the student to state the claim first.

## Module-level predicted failure modes

**The technique does not transfer from S005 to S006.** The most consequential possible outcome in Q1, and the one S006's design is built to detect within its first phase. If students who proved a loop invariant on Tuesday cannot state one for code on Thursday, the M01 encoding was situational and the module's sequencing assumption is wrong. Countermeasure: S006 phase 1 is a direct probe, and the result is treated as a design finding rather than a student finding.

**Decomposition is learned as an aesthetic.** S007's risk is that students conclude some seams are "cleaner" without being able to say what a seam costs. Countermeasure: the change request is what adjudicates, and it is not revealed until after the decompositions are committed.

**Testing becomes a coverage ritual under a new name.** S009's risk is the largest in the module, because the ritual it replaces is deeply installed and superficially similar. Countermeasure: the day's artefact requires the claim to be written before any test exists, and a test that cannot fail is a specification failure.

**S010's firewall is not believed.** Students may treat the assessment-bearing error clinic as a trap regardless of what is stated. Countermeasure: the firewall is stated at S001, restated at every error clinic, and demonstrated at S010 by the assessor being physically absent from the clinic portion of the day. Belief is expected to lag the demonstration and is instrumented across the quarter.

**The agent does the reasoning the module exists to install.** The module's demand is that a claim is stated before the result arrives. An agent will produce a plausible claim on request, at any point, including after the code. The risk is not that students cheat; it is that the ordering the module cares about becomes unobservable, and a narrated claim is indistinguishable from a derived one in the artefact. Countermeasures are three and none is sufficient alone: the intervention record, which asks where the student corrected the agent rather than what the agent produced; the frontier statement, which requires a specific thing the agent did badly on this build; and the [S010](wiki/seminars/S010.md) unassisted segment, which is the only place in the module where the student's unaided reasoning is observed directly. The design's position is that these make the ordering *arguable* rather than verifiable, and [WP-008](wiki/whitepapers/WP-008.md) §8 already concedes that the discipline is unenforced.

**The frontier is assumed rather than located.** Students will form a view in week six about what Copilot is good at and hold it for three years. The countermeasure is structural: every day carries a sealed phase 1 prediction about what the agent will do and where it will be wrong, checked at phase 8, and the cohort's accuracy is the programme's running measure of frontier calibration. The mechanism, taken from [research/04-professional-formation/dellacqua-jagged-technological-frontier.md](research/04-professional-formation/dellacqua-jagged-technological-frontier.md), is that capability is uneven in ways not predictable from how hard a task looks to a person — so the frontier has to be probed, not inferred. **No effect size from that source is asserted anywhere in this module.**

## Assessment contribution

**One entrustment-relevant occasion, and it is not an entrustment judgement.** S010 is assessment-bearing but produces no supervision-level rating. It generates a specification decision on the module's cumulative artefact and a dispositions observation on disclosure conduct. The programme's position, per the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md), is that no entrustment judgement is made in Q1 at all.

Specification items:

- **S006** — an invariant stated for substrate code, with the argument, graded in CF101 rather than MS101 so that the stance is enforced where students do not expect it.
- **S007** — three decompositions with a committed cost prediction and the post-hoc reconciliation.
- **S008** — a recursive procedure with its induction hypothesis stated as the specification, jointly in CF101 and MS101.
- **S009** — a claim, a test designed to falsify it, and a statement of what the test's passing does not establish.
- **S010** — the module's cumulative artefact, assessed against specification, with tokens available.

Every specification item from S006 to S009 additionally carries the three artefact elements the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md) requires of any phase 5 build: **the prompt record** — what you asked for, in order, including what you abandoned; **the intervention record** — every point at which you corrected the agent and what the correction was, where an intervention record with no entries fails unless the artefact demonstrates that the design could have detected an intervention-worthy error; and **the frontier statement** — one thing the agent did faster than you could have, and one thing it did badly that you caught, both specific to this build.

**The unassisted-work provision falls in this module.** [S010](wiki/seminars/S010.md) is the first of the programme's three occasions — with [S045](wiki/seminars/S045.md) and [S090](wiki/seminars/S090.md) — at which a bounded portion of the assessed work is performed without agent assistance. The assisted and unassisted work are compared, the comparison is reported to the student and in aggregate to the programme, and **it contributes to no level and to no specification decision.** Its purpose is to make a trajectory visible while there is time to act on it, and the design records at [WP-010](wiki/whitepapers/WP-010.md) §7 and §8 that three occasions may not be enough and that the provision introduces a category the day otherwise denies exists.

Dispositions observed across the module: **integrity** (does the student report what their program actually does), **humility** (does the student's phase 8 calibration move toward accuracy), **reliability** (are commitments from prior days closed).

## Perishability

The durable claims are the module's assessed content: that correctness is constructed and then evidenced; that a specification and an instructions file are the same object; that an unstated invariant is not an invariant; that a boundary costs what crosses it; that a loop needs a well-founded measure; and that passing is weak evidence.

The platform instance is the vehicle and is expected to move. File extensions, folder locations, frontmatter keys, setting names and the location of the diagnostics view are perishable and are marked as such on every day. The module already carries one worked example of the distinction: **the object now called a custom agent and defined in a `.agent.md` file was called a custom chat mode and defined in a `.chatmode.md` file, and the documentation's own migration instruction is to rename the file.** The name changed; the object did not; nothing the module assesses moved. That is what re-anchoring is supposed to look like, and it is shown to students rather than absorbed silently.
