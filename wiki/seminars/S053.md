# S053 · The Transformer, Assembled

**Module:** [M11](wiki/modules/M11.md) · **Quarter:** [Q6](wiki/quarters/Q6.md) · **Complexity class:** 4
**Strands:** IS · ME
**Whitepaper:** [WP-053](wiki/whitepapers/WP-053.md)
**Retrieves from:** S007, S043, S051, S052
**Platform anchor:** Azure AI Search retrieval pipeline — HNSW against exhaustive KNN, semantic ranker, hybrid arms · Foundry reasoning deployments — `reasoning_effort` · **MCP servers:** Azure MCP Server · Foundry MCP Server · Microsoft Learn MCP Server

---

## What this day is for

Two operations, alternating. Mix information across positions — which is [S052](wiki/seminars/S052.md)'s lookup. Then compute at each position independently. Repeat.

Everything else in the architecture is there to make a deep stack of those two operations trainable, and [S007](wiki/seminars/S007.md) already supplied the frame: **residual connections and normalisation are seams.** They are what lets you add a layer without redesigning the rest, and they are the reason the thing scales at all.

The assembly is not the difficulty. The difficulty is that students hold a confident and wrong account of what the parts do — a pipeline in which early layers handle syntax and late layers handle meaning, in which every component contributes proportionally to its size, and in which removing something important produces damage proportional to its importance.

**All three claims are false, and the day breaks them by ablation rather than by assertion.**

The target: **which component is load-bearing is a question about a trained, configured system and a class of inputs, not about an architecture — and it is answered by removing things and measuring, with the measurement's sensitivity stated first.**

## What can be removed, and what cannot

This day has a constraint and states it at the front rather than in a footnote.

**The weight-level ablations that motivate the day cannot be operated here.** Serverless deployments host model weights on Microsoft-managed infrastructure and expose an inference API; there is no supported route by which a student removes a residual path from a deployed model. Managed compute does place weights on virtual machines you control, and a surgical architectural ablation on one is a research project rather than a ninety-minute phase. **Phase 3 arm A is therefore demonstrated rather than operated, and it is not assessed.**

What the platform does permit is a different and, for this programme, better class of ablation: **components you can remove at query time from a system that is serving real requests.** A retrieval pipeline has an approximate-nearest-neighbour graph, a lexical arm, a fusion step and a reranker, and every one of them can be switched off in a single request parameter against the same index. An inference deployment has a per-request computation dial. Those are real components with real costs and real failure classes, and the day's argument — that load-bearing is a property of a configured system on a class of inputs — is not weakened by being made about them. It is strengthened, because the students are answerable for the configuration.

## Phase 1 · Pretest and prediction (25 min)

A diagram of the assembly is supplied with five component types named. Five items, **sealed and opened at phase 8.**

1. **Rank the five components** by how much removing one would damage the output.
2. **What does the first layer do that the last layer does not?**
3. **Predict the output change from removing all positional information.**
4. **Predict the output change from removing one feed-forward block in the middle of the stack.**
5. **Copilot prediction, sealed.** You will shortly ask the agent to design an ablation study over the substrate's retrieval pipeline. Write down what it will produce, and **name the one thing it will get wrong.** Sealed with items 1 to 4 and opened at phase 8.

Items 3 and 4 are the two the folk model gets confidently wrong, in opposite directions.

**Warrant.** Pretesting with two items constructed to be wrong in opposite directions — item 3 over-predicts collapse, item 4 under-predicts redundancy. A pretest whose errors all run one way teaches students that they were miscalibrated in a direction; a pretest whose errors run both ways teaches them that they had no model at all, which is the honest finding. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8; the design's expectation is that the agent will produce a competent study with no sensitivity statement and only aggregate reporting, which is precisely the two things this day fails.

## Phase 3 · Contrasting cases and generation (45 min)

Two arms, and the split is disclosed to students at the start of the phase, per instrumentation rule 3.

**Arm A — architectural ablations, demonstrated rather than operated.** Groups receive **the same trained model with four ablations already run**, and predict each outcome before seeing it. The model is a small open-weight one on local hardware; the ablations were run by staff; **arm A is not assessed.**

- **A** — residual paths removed.
- **B** — normalisation removed.
- **C** — all positional information removed.
- **D** — one feed-forward block removed from the middle of the stack.

Predictions are committed. Then **aggregate metrics are supplied.** Then, separately, **per-class breakdowns.**

Ablation C's aggregate damage is far smaller than the room predicts, and its per-class damage on one small class of inputs is catastrophic. Ablation D's aggregate damage is almost nil, and stays nil per class.

**Arm B — pipeline ablations, operated.** Groups then run four ablations themselves, against the substrate's own Azure AI Search index and its reasoning deployment, over a fixed set of queries from the real query log. Each is one request parameter. Each removes a real component from a system that is serving real requests.

| Ablation | What is removed | How |
|---|---|---|
| **P** | The approximate-search graph | Set the vector query to run exhaustively, which invokes exhaustive nearest-neighbour search at query time **even though the field is indexed for HNSW**. Same index, same vectors, different navigation. |
| **Q** | The reranker | Turn the semantic ranker off, leaving the fusion ranking that fed it. |
| **R** | The lexical arm | Reduce the text recall window until the fusion step has almost nothing from the keyword side to fuse. |
| **S** | Half the inference computation | Drop `reasoning_effort` one level on the deployment that answers from the retrieved passages. |

Predictions are committed first, then aggregates are supplied, then per-class breakdowns by query type.

The phase's payload is in the gap between the two reveals, and arm B reproduces both shapes of it.

**Ablation Q is arm B's C.** Removing the reranker costs little in aggregate and is severe on one small class of queries — the ones whose answer depends on which of several near-identical passages is returned first. **Ablation P is arm B's D.** Exhaustive search returns the exact nearest neighbours rather than approximate ones, and on this corpus at this size it changes the answers barely at all while changing the latency and the resource profile substantially. The documentation says as much about the technique's purpose: exhaustive search is what you run to build the ground-truth neighbour set against which an approximate algorithm's recall is measured. **Students who predicted that the exact algorithm would be better have discovered that they predicted the direction correctly and the magnitude uselessly**, which is item 4's lesson in a system they own.

Task after: **for each of the eight ablations, state what you would have concluded from the aggregate alone.**

**Warrant.** Contrasting cases across ablations with a deliberately staged two-part reveal. Supplying the aggregates and the per-class breakdown together would let students see the discrepancy without first committing to a wrong conclusion from the aggregate — which is the conclusion the whole industry publishes. **Arm B exists because the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md) requires the four contrasting cases to be run wherever the subject permits, and because the substitution is not a concession**: a query-time component ablation on a live index is a closer analogue of the engineering decision the students will actually face than a residual-path removal they will never perform. Arm A is retained and demonstrated because the architectural facts it establishes — particularly permutation-equivariance at C — have no operable equivalent and are the mechanism points 2 and 3 rest on. The two arms are matched in shape so that phase 4 can index to either.

## Phase 4 · Consolidating instruction (50 min)

1. **The assembly is two alternating operations.** Mix across positions, then compute per position. Everything else exists to make a deep stack of those two trainable.

2. **Residuals and normalisation are the seam,** in [S007](wiki/seminars/S007.md)'s exact sense. They are not refinements; they are what makes depth composable, and their removal is not a degradation but a structural failure.

3. **Positional information is injected, not inherent.** The lookup is permutation-equivariant — it has no notion of order unless order is supplied. This is the day's most surprising mechanical fact and it is the reason item 3 is a good pretest question.

4. **Layers are not stages.** There is no pipeline in which layer *k* performs one identifiable job. This is the folk model's most confident claim and neither ablation nor probing supports it.

5. **Redundancy is real, uneven, and a property of the trained network.** Some components can be removed with almost no aggregate effect. That fact is about this model after this training run. It does not transfer, and [S051](wiki/seminars/S051.md) point 8 applies.

6. **Aggregate ablation metrics hide class-specific catastrophe.** A one-percent aggregate drop can be a very large drop on a small class of inputs, and that class is usually one somebody cares about. [S026](wiki/seminars/S026.md) and [S049](wiki/seminars/S049.md) both apply, and this is the direct precursor of [S059](wiki/seminars/S059.md)'s benchmark material.

7. **An ablation must state its sensitivity before it runs.** What size of change could this measurement have detected, on what class, at what n? An ablation reporting no effect without that statement has reported nothing.

8. **Parameter count is not capacity for your task.** [S043](wiki/seminars/S043.md)'s account applies unchanged: capacity is relative to the function class the job requires.

9. **The same argument holds one level out, where you can actually operate it.** A retrieval-and-inference pipeline is an assembly with seams too, and its components have the same uneven, class-specific, non-transferable load-bearing structure. Arm B is the demonstration and the platform's own documentation supplies the mechanism for each part. The two vector algorithms differ in kind: the approximate one builds a navigation graph and requires all data points to reside in memory, which consumes the index's vector storage quota; the exhaustive one scans and does not. **The reranker is a second ranking applied over an already-ranked set**, using models the documentation describes as multilingual deep-learning models adapted from Microsoft Bing — so removing it removes a stage rather than a signal. And the fusion step ranks by rank rather than by score, which is why **its scores are on a different scale from the similarity scores that fed it, by design**, and why a low fused score can still be a strong match.

10. **Perishable, and marked as such.** Every parameter name in arm B, the reranker's provenance, the two algorithm names, the recall window's default and maximum, and the effort levels are all this vendor's, at this date. Two of the parameters the day uses are available only in preview API versions. **None of it is what the specification assesses**, and all of it will need re-verifying before this day is next taught.

11. **Defaults are opinions, and this pipeline has four.** The default vector similarity distance function is cosine, so [S051](wiki/seminars/S051.md) point 2's geometry question was settled before you arrived. A vector query's weight defaults to one, and **the text side of a hybrid query carries an implicit neutral weight of one that you cannot set directly** — you change its influence by changing how many keyword results reach the fusion step, which is a different kind of control wearing the same name. The recall window itself defaults to a thousand documents out of a maximum of ten thousand. And **the default counting mode reports every document matching the text query, including documents that fell outside that window and were never retrieved for ranking** — so the count on your dashboard describes a superset of what the system could have returned. **That last default is point 6 built into a product.** An engineer who cannot state what was chosen for them does not understand their own system.

**Warrant.** Consolidation indexed to phase 3, now to both arms. Point 4 is the folk-model break. Point 6 is the retained content and the forward link. **Point 7 is this day's discharge of the obligation [S052](wiki/seminars/S052.md) placed on it under instrumentation rule 6**, and it is stated as a rule rather than as advice for that reason. Point 9 carries the day's platform mechanism and is what makes arm B interpretable rather than merely runnable. **Point 10 is the required perishable platform point and point 11 the required naming of defaults**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md); point 11's fourth default is the strongest teaching artefact on the day, because it is a shipped, documented, defaulted-on instance of the exact aggregate-hides-class failure the day exists to teach, and no student who has met it will believe again that a count is a count.

## Phase 5 · Whole-task learning task (90 min)

**Class 4. The behaviour, the ablation and the sensitivity are the student's. This phase produces a build.**

Students use Copilot in agent mode, through the Azure MCP Server and the Foundry MCP Server, to ship a working ablation harness over the substrate's retrieval pipeline. They:

1. **State a behaviour** on the substrate you care about, and **the class of inputs it lives on.**
2. **Choose a component to ablate,** and say what you expect. **It must be a component you can actually remove.**
3. **State the sensitivity of your measurement before running it:** what size of change it could detect, on what class, at what n.
4. **Run the ablation** against the live index or deployment, over queries drawn from the real log.
5. **Report aggregate and per-class.**
6. **State which component is load-bearing for your behaviour,** and how confident you are.
7. **State what you would have concluded from the aggregate alone.**

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned.
- **Intervention record.** Every point at which you corrected it. **An intervention record with no entries fails**, unless the artefact demonstrates that the harness's own checks would have caught an intervention-worthy error — a harness that refuses to report a per-class result when that class's n falls below the sensitivity the student stated at step 3 is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch.

**Fading:** step 3 is worked with the room, since sensitivity statement is new and technical. **Step 2 is unsupported.**

**Warrant.** Whole-task at class 4, now ablating a running system rather than reading supplied tables. **Step 3 is the artefact element S052 named under instrumentation rule 6**, and it is placed before step 4 so the sensitivity is a pre-commitment rather than a post-hoc rationalisation. Step 2's added constraint is the day's platform honesty made assessable: a student who proposes a weight-level ablation has proposed something arm A already showed them and the day's opening already told them they cannot do. Step 7 is the day's discriminator and is the sentence [S059](wiki/seminars/S059.md) will retrieve.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate model change justified by an aggregate ablation study. The removed component was load-bearing for one class of query. The class was two percent of traffic and was the class the substrate's most dependent users relied on. Attention is directed at the study — **it was correctly run, correctly reported, and correctly interpreted at the aggregate level.**

Then the agent case, from this day's own build. A student asked Copilot to measure whether the reranker was earning its latency. **The agent produced a clean, well-documented harness that ran both configurations over the query log, computed the aggregate ranking metric for each, and reported no meaningful difference.** It was right about every number it printed.

Two things were wrong and neither was visible in the output. It reported only the aggregate, because that is what the request implied and nothing objected. And it never set a result count, so **both configurations were compared at the response default of fifty results while the production interface shows ten** — which is the regime where a reranker does most of its work, and the one the comparison never entered.

Attention goes to why review did not catch it: the code was readable, the metric was the right metric, the statistical statement was correctly hedged, and **the defaulted parameter did not appear in the code at all**, because a default is precisely the thing nobody writes down. This is point 11 failing in the register where it is invisible.

Then students, in threes: a change you made because the overall number improved, or a place today where you accepted a default the agent had not mentioned.

**Warrant.** Error management targeting points 6 and 11. The instructor case contains no methodological error at all, which is what makes it a lesson about the unit of reporting rather than about rigour. **The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen so that the defect is an absence** — an unset parameter and an unrequested breakdown — because absences are what review does not see, and because the intervention record exists to catch exactly this class.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents **their step 6 load-bearing claim and their step 3 sensitivity statement.**

The partner's task: **construct an input class on which the claim is false, and show that the sensitivity statement would not have detected it.**

Both are required. A construction that defeats the claim but that the measurement would have caught is not a defeat.

Per rule 3, the outcome is recorded in the artefact. Per rule 5, this reuses [S029](wiki/seminars/S029.md)'s dual-defeat structure — **a validated remedy**, having run at S029, S047 and S048.

**Warrant.** Interactive-tier articulation with a dual demand. The pairing of claim and sensitivity is what makes the phase a test of the measurement rather than of the model, and it is the reason step 3 is assessed rather than merely required.

## Phase 8 · Calibration and commitment (20 min)

- Sealed items opened. **The cohort's item 1 ranking against the arm A ablation results.**
- **Item 3 and item 4 error magnitudes, reported separately and in opposite directions,** which is the day's most quoted result.
- Item 2's layer-stage answers read aloud anonymously, against point 4.
- **Item 5 opened.** The sealed Copilot predictions are read against the study the agent actually designed, coded for whether it carried a sensitivity statement and whether it reported per class. The cohort's hit rate is recorded.
- Step 7's aggregate-only conclusions against step 6's actual conclusions: how many students would have concluded something different.

## Assessment

**One specification item**, in IS202. Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 1, the checked elements are: the behaviour and its input class; the chosen ablation with an expectation; **the pre-run sensitivity statement**; the ablation result; aggregate and per-class reporting; the load-bearing claim with a confidence; the aggregate-only counterfactual; the phase 7 outcome; **the prompt record; the intervention record; and the frontier statement.** **Nothing else is assessed.**

**Phase 3 arm A is not assessed.** The architectural ablations are demonstrated rather than operated, because serverless deployments do not expose model weights and no supported route exists by which a student removes a residual path from a deployed model. The specification does not require a student to run one, reproduce one, or reason from one.

**An ablation reported without a pre-run sensitivity statement fails.** This is the day's single hard requirement.

**A result reported only in aggregate fails.** Per-class reporting is not optional on this day.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error.

No entrustment judgement. The quarter's is at [S060](wiki/seminars/S060.md).

**Instrumentation under rule 6.** Two instruments with named response occasions:

- **The item 3 and item 4 error magnitudes** measure the folk model's shape — whether the cohort over-predicts fragility or under-predicts redundancy, and by how much. **Response occasion: [S055](wiki/seminars/S055.md), phase 3, whose four demonstrations are selected against whichever direction the cohort got worse.**
- **The step 7 aggregate-only counterfactual rate** — how many students would have reached a different conclusion from the aggregate — is the cohort's baseline for benchmark scepticism. **Response occasion: [S059](wiki/seminars/S059.md), phase 1, where the same measurement is retaken on published results rather than on the student's own.**

Item 5's hit rate joins the running frontier map, per instrumentation rule 9, and is read by the following year's cohort through the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md).

## Perishable content in this day

**This module's platform layer is the most perishable in the programme**, and this day depends on two preview parameters.

| Durable claim | Platform instance, perishable |
|---|---|
| The assembly is two alternating operations | The arm A model and every magnitude in it |
| Residuals and normalisation are the seam | Nothing; this claim has no operable instance and arm A demonstrates it |
| Positional information is injected | Ablation C, demonstrated rather than operated |
| Layers are not stages | Ablation D and the depth profile it does not supply |
| Redundancy is real and does not transfer | Ablation P: exhaustive search against the approximate graph |
| Aggregate hides class | Ablation Q, and the default counting mode at point 11 |
| Sensitivity is stated before the ablation runs | The harness that refuses to report below its stated n |

- **Durable:** the two-operation assembly; the seam argument; positional information as injected; layers-are-not-stages; aggregate hides class; the sensitivity-before-ablation rule.
- **Perishable:** every magnitude in both arms, the redundancy of any specific component, the class on which ablation C fails, every parameter name in arm B, and every default at point 11. All are properties of one trained network or one product version.
- **Local:** the substrate model, its index, its query log, its input classes, and the phase 6 change.
