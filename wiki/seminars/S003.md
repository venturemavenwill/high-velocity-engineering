# S003 · Representation and the Leaking Abstraction

**Module:** [M01](wiki/modules/M01.md) · **Quarter:** [Q1](wiki/quarters/Q1.md) · **Complexity class:** 1
**Strands:** CF · MS · SY
**Platform anchor:** GitHub Copilot agent mode; custom instructions as executable specification · **MCP servers:** Microsoft Learn MCP Server
**Whitepaper:** [WP-003](wiki/whitepapers/WP-003.md)
**Depends on:** S001
**Re-tests:** S002

---

## What this day is for

A representation is a decision to preserve some properties of a thing and discard others. Students have been taught representations as facts — a floating-point number *is* a real number, a string *is* text, a timestamp *is* a moment. Each of those is false in a way that will eventually cost them, and the cost arrives without warning because the abstraction is silent until it is not.

The day's target is a habit, not a fact list: **before trusting a representation, ask what it discarded.**

It is also the day that closes the S001 phase 2 loop.

**And it is the day the instructions file stops being a configuration step and becomes a specification.** The deficit this day names — knowledge that is present when asked and absent at the moment of use — is a deficit the agent has too, and in a form the room can demonstrate in ten minutes. Ask it what floating-point comparison discards and it answers well. Ask it to write the comparison and it writes the naive one. The gap between what a tool can state and what it does is the same gap the day is about, and this is where students learn that closing it requires a rule that is *checkable*, not an exhortation to be careful.

## Phase 1 · Pretest and prediction (25 min)

Six short items, each of which looks trivial and is not.

1. Does adding a sequence of decimal values in a different order give the same result?
2. How many characters are in a short string containing one composed accented letter?
3. Is the duration between two timestamps in a fixed local zone always what the clock difference says?
4. Does sorting these strings put them in the order a reader would expect?
5. Are these two values equal? (They are equal under one representation and not another.)
6. Predict: how many of items 1–5 did you get right?

**The Copilot prediction, sealed.** A seventh item:

7. The agent will be asked items 1 to 5 as questions, and then asked to *write the code* that each item is about. **Will its answers and its code agree — and if they diverge, on which item, and in which direction?**

The direction clause is the item. Most students who consider the question at all predict that the code will be better than the prose, because code is the thing the tool is for.

**Warrant.** Every item is a case where the intuitive answer is confidently wrong. The prediction in item 6 makes the overconfidence measurable rather than merely asserted. Item 7 extends the same instrument to the tool and is sealed at phase 1 per instrumentation rule 8.

## Phase 2 · Cumulative retrieval set (20 min)

**The S001 reveal happens here.**

First, retrieval, no notes:

- The machine's complete state consists of what?
- What were the four error classes from S002 phase 6?
- Why did the two machine traces disagree about which did more work?
- Reproduce the passage content from S001 phase 2.

The final item is scored **by condition**. The re-read group and the free-recall group are compared, and the S001 confidence ratings are laid alongside.

The result is displayed without commentary for one minute before it is discussed.

**Warrant.** Retrieval practice, and the delayed resolution of the programme's founding demonstration. The one-minute silence is deliberate: the students should reach the interpretation before the instructor supplies it.

## Phase 3 · Contrasting cases and generation (45 min)

*First, 25 minutes, unchanged.* Groups receive the **same dataset represented three ways** — as text, as fixed-point decimal, and as binary floating point — together with the results of the same five computations performed on each.

The results disagree. Not catastrophically; subtly, in the last places, and in one case in a way that changes an ordering.

Task: **explain every disagreement**, and rank the three representations for this dataset. Commit in writing.

Groups will explain some disagreements and not others. The ordering-change case is the one that typically defeats them, because it requires seeing that a small value difference crossed a comparison boundary.

*Then, 20 minutes: four instruction configurations, run.* Every group issues the **same request** — *write a function that returns whether these two computed totals are the same* — against the same dataset, in agent mode, under one of four configurations:

- **Case A.** No instructions file. The agent writes a direct equality comparison.
- **Case B.** An instructions file whose rule is a **quality judgement**: `Compare floating-point values carefully.`
- **Case C.** An instructions file whose rule is **checkable**: `Never compare floating-point values with equality. Compare the absolute difference against a tolerance supplied by the caller.`
- **Case D.** Case C's rule, but placed in an instructions file whose `applyTo` glob does not match the file being written.

**The payload is case B against case C, and the room does not predict the gap.** A rule stating a checkable condition changes the output every time. A rule implying a quality judgement the tool cannot make changes it unreliably, and — worse — produces output that *looks* as though the instruction was honoured, because the agent will add a comment saying the comparison is careful. **Specification rule 1, executed rather than asserted, in week three.**

Case D is the control that makes the mechanism visible rather than magical. Instructions are injected into a request when their `applyTo` glob matches; when it does not, nothing is injected and the output is case A. Groups confirm this by opening the GitHub Copilot Chat output channel and reading the request payload, which the documentation calls the source of truth. **A specification that was never delivered has not failed. It was not present.**

**Warrant.** Contrasting cases with invariant deep structure: three surfaces, one underlying question about what each representation preserves. The ranking demand forces a criterion, which no group has, which is the productive failure. The four executions hold the request, the dataset and the model constant and vary only the specification governing them, which is the configuration under which the specification's effect becomes attributable.

## Phase 4 · Consolidating instruction (50 min)

1. **A representation is a map, and the map discards.** Stated as the day's thesis, then applied.
2. **Numbers.** Finite precision, the spacing of representable values, why associativity fails, why equality comparison is a design decision rather than an operation.
3. **Text.** Bytes, code points, grapheme clusters, normalisation, collation. Why "length" has at least three answers and why sorting is locale-dependent.
4. **Time.** Instants, civil time, zones, offsets, the discontinuities. Why a duration and a clock difference are different quantities.
5. **The common structure.** In all three cases the representation is a *lossy encoding chosen for a purpose*, and the failure occurs when a value is used for a purpose the encoding was not chosen for. This sentence is the retrievable item.
6. **An instructions file is a specification, and it obeys the specification rules.** Indexed to phase 3 cases B, C and D.
   - **Rule 1 — a specification must state what is actually checked.** Case B implied a quality judgement and produced a comment instead of a behaviour. Case C stated a condition and produced the behaviour.
   - **Rule 2 — a qualification must travel with the quantity it qualifies, in the same field.** An instruction saying "cite sources" and not saying "in the same sentence as the claim" produces detached citations. This is the same defect as case B in a different register, and it is the one students will meet at [S001](wiki/seminars/S001.md)'s case C if they go back and read it.
   - **Delivery is not conformance.** Case D failed to change anything and was not violated; it was never in the request. A specification's effect is not evidence that it exists, and its absence of effect is not evidence that it was ignored. The payload inspection is what separates the two.
   - *Perishable, marked as such:* the `.github/instructions/` path, the `applyTo` front-matter key, glob semantics, the fact that matching instructions are injected into every request with no command required, the location of the output channel that shows the payload, and — in one editor — the fact that multiple instructions files must be switched on in options before any of this happens at all. *Durable:* that a rule an executor cannot check is not a rule.
7. **A default the platform chose for you, and it is a silence.** The Learn MCP Server accepts a `maxTokenBudget` parameter that caps the token count in **search** responses by truncating content in the results; the same parameter does not affect fetch, which always returns the full page. Left unset, the budget is whatever the tool decided. **A student who searched, read a truncated result and concluded the documentation did not mention something has been given a representation of the documentation that discarded exactly the part they needed** — which is point 5, arriving from the citation strand rather than the numeric one. *Perishable: the parameter, its name and its default. Durable: that your evidence arrived through a lossy channel and the channel did not tell you what it dropped.*
8. Resolution of the phase 3 ordering case, and the pretest.

**Warrant.** Consolidation indexed to generated accounts. The common-structure move at point 5 is the abstraction; the three domains are the varied instances that make it available. Points 6 and 7 are two further instances of point 5 in registers students do not expect — a specification and a search result are both lossy encodings chosen for a purpose — and they are placed after it so that they land as applications rather than as new topics. Scope rule, strong form: point 6's account of instructions files is safe for reasoning about what a specification must contain and unsafe as a description of any version other than the one installed, which is stated in those words.

## Phase 5 · Whole-task learning task (90 min)

**The build: an instruction that prevents the defect, and one that does not.**

Students receive a small program that produces a **plausible and wrong** result on a real dataset drawn from the substrate's logs.

Task, in order:

1. Predict, before running, where the representation failure is. Commit in writing.
2. Locate it.
3. State what the representation discarded, and what purpose it was being used for that it was not chosen for.
4. Propose a fix, **and state what the fix now discards.**
5. **Write an instruction that would have prevented the defect from being generated in the first place, and demonstrate that it does.** Add the rule to the repository's instructions file with an `applyTo` glob that matches. Delete the defective function. Ask the agent to write it again. Show the two outputs side by side.
6. **Write a second instruction, for the same defect, phrased as a quality judgement, and demonstrate that it does not reliably work.** Run it three times. Report all three outputs, including any that happened to be correct.

Step 4 is the day's conceptual objective. **Step 6 is its assessment objective**, and it is the harder of the two, because a student who has been told that vague instructions fail will produce a vague instruction that fails and stop. Reporting the run that happened to succeed is the required part: an instruction that works sometimes is worse than one that never works, because the sometimes is what makes it survive review.

Every fix trades one loss for another, and a student who proposes a fix without naming the new loss has not yet understood the thesis.

**Faded guidance:** the first of three defects is worked with the instructor; the second is a completion problem; the third is independent. Steps 5 and 6 are performed once, on the third defect only.

The three additional deliverables:

- **The prompt record**, including the instruction wordings tried and abandoned. This day generates more abandoned wordings than any other in the module, and they are the most informative part of the record.
- **The intervention record.** An empty record fails unless step 6's three runs are present — they are the demonstration that the design could have detected an intervention-worthy error.
- **The frontier statement.**

**Warrant.** Whole-task at class 1 — the method is given, the task is specified. Variability of practice across the three defects: numeric, textual and temporal, deep structure constant. Steps 5 and 6 are the day's transposition of the thesis into the specification register, and they are placed after step 4 so that the student has already named a loss before being asked to encode a rule about it.

## Phase 6 · Error clinic (40 min)

Opened by the instructor with a representation error from the substrate's own history: what it was, how long it went unnoticed, what it cost, and — specifically — why the code looked correct.

Then students, voluntarily: a case where they trusted a representation and were wrong. Every student who has programmed for any length of time has one.

The instructor collects them by **which property was discarded**, not by which student made them.

**The agent case.** A phase 5 step 6 run from the room in which the vague instruction produced code that was correct, and the student recorded the instruction as working. This is the day's designed instance of confident wrongness that review does not catch, and it is subtler than S002's: **the output was correct.** Nothing about it was detectable by inspection, and the student's conclusion — that the instruction works — was reached from a true observation by a valid-looking inference. The review did not fail; it succeeded on the wrong question. The question it should have asked is not *did this output conform* but *would this instruction produce a non-conforming output*, and that question requires more than one run.

The class is asked how many runs would be enough. There is no answer today. The question is [S029](wiki/seminars/S029.md)'s and it is named as such: **a prompt that has never failed has never been tested.**

**Warrant.** Error management. The classification-by-mechanism move continues from S002 and is now applied to a class of error with real professional consequence. The agent case is chosen so that the error is in the *inference from the observation* rather than in the output, because that is the class the day's own subject predicts and the class an artefact cannot expose.

---

## Phase 7 · Peer articulation (30 min)

Pairs. One student names a representation they use daily and states what it discards. The partner's task: **find a use of that representation, in the student's own recent work, where the discarded property mattered.**

Roles then swap.

Reports to the room are collected as a running list titled *what we discovered we had been assuming*, which stays visible for the rest of Q1.

**Warrant.** Interactive-tier articulation applied to the student's own practice, which is the condition under which the habit — ask what it discarded — becomes personal rather than academic.

---

## Phase 8 · Calibration and commitment (20 min)

- Item 6 prediction resolved against actual pretest performance. The gap is typically large.
- **Item 7 resolved.** The cohort's predictions about whether the agent's prose and its code would agree are compared against the phase 3 runs. Most students predicted the code would be the better of the two. It is the worse of the two, and reliably so — the tool states the general property correctly when asked and writes the naive comparison when not. **The same inert knowledge, in the same shape, in the instrument.** Recorded on the frontier map.
- The S001 P2 prediction is **not** resolved today; students are reminded it remains sealed until S011.
- Each student commits to one representation in their current work that they will check before S006.
- Each student adds one rule to their repository's instructions file, in the checkable form, and states what it would prevent.
- Retrieval schedule: next morning, day 3, week 2, week 6.

## Assessment

One specification item in CF101. Binary. Resubmittable. No entrustment evidence.

Checked:

1. For each of the three defects: a committed prior prediction, the located failure, a statement of the discarded property and the purpose mismatch, and a fix with its own loss named.
2. The checkable instruction from step 5, in the repository, with an `applyTo` glob that matches, and the two outputs side by side.
3. The quality-judgement instruction from step 6, with **all three** runs reported, including any that succeeded.
4. **The prompt record**, including abandoned instruction wordings.
5. **The intervention record.** An empty record fails unless item 3 is present.
6. **The frontier statement**, both halves, specific to this build.

**Nothing else is assessed.** The elegance of the fix is not assessed. Whether the checkable instruction is the *best* rule for the defect is not assessed. Whether the quality-judgement instruction happened to work is not assessed — only whether all three runs were reported.

The new-loss statement at item 1 is the element most often failed on first submission, which is expected and is what the token-funded resubmission exists for. Item 3 is expected to become the second.

*Annotation at the point of change.* Item 1 is the original specification, unchanged, and the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md)'s S001–S040 non-retroactivity boundary holds over it. Items 2 to 6 are new element classes and are stated in the closed form the rule requires.

## Perishability register

**Durable — assessed.** That a representation is a lossy encoding chosen for a purpose, and that failure occurs on a purpose mismatch. That every fix discards something new. That a rule an executor cannot check is not a rule. That a specification's absence of effect and its absence of delivery are different findings.

**Platform instance — not assessed.** The specific library behaviours used as instances — how a particular language's string-length function counts, how a particular date library handles a zone transition — remain perishable and are marked as such in the materials; the underlying properties of the encodings are durable, and students are told which is which explicitly in phase 4. Newly perishable: the `.github/instructions/` path and `applyTo` key, the injection behaviour, the output channel that displays the request payload, the editor setting that must be enabled before multiple instructions files take effect, and the Learn MCP Server's `maxTokenBudget` parameter and its search-only scope. **This day carries the highest perishability exposure in the module and is re-verified in full before each offering.**
