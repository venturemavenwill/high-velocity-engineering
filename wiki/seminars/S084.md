# S084 · Each Iteration Leaves It Better

**Module:** [M17](/wiki/modules/M17.md) · **Quarter:** [Q9](/wiki/quarters/Q9.md) · **Complexity class:** 6
**Strands:** PE · ME
**Platform anchor:** none
**Whitepaper:** [WP-084](/wiki/whitepapers/WP-084.md)
**Retrieves from:** S055, S062, S081, S083
**Entry state:** this-programme-only

---

## The situation

The closure re-run has been executed against the estate as it now stands. Some items closed, because the evidence for them is now discoverable where the procedure looks. Some regenerated.

Two of the regenerated items are real fixes, made in a portal, in a place the re-run cannot see. One is a genuine gap that has been open since the security work and has regenerated on every re-run since.

Answer these in writing before the session opens.

1. What does a regenerated item mean? Give three meanings, not one.
2. For the item that has regenerated every time: what is the correct action, and is it the same as the action you would have taken the first time?
3. Nobody scheduled this re-run. Who should, on what trigger, and what happens if the trigger is a person remembering?
4. If you closed everything on this list, what would you have demonstrated?
5. What is the smallest change to the criterion that would let it see a fix made outside the repository — and what does that change cost?

**Item 4 is the session's subject.** The instruction that governs this whole idea, in the one place it is written down well, is that perfect compliance is not the goal and that pursuing it is itself a failure mode. What is asked instead is that each iteration leave the system better than the last. **A learner who cannot say why the first is a failure mode has not understood the second.**

## What you must produce

A **re-run finding** that classifies every regenerated item into exactly one of three states, with the evidence for the classification.

- **A real gap** — the thing is not done. The item is correct and the work exists.
- **An invisible fix** — the thing is done, somewhere the criterion cannot look. **The defect is in the criterion, and the item names it.**
- **A criterion that cannot ever see it** — the fix is real, it will always live outside the procedure's reach, and no reasonable extension of the procedure will find it. This is a permanent exception and must be recorded as one, with an owner, or it will regenerate forever and train everybody to ignore the list.

Plus one further section: **the items you are deliberately not raising this iteration**, and why.

## What good looks like

- Evidence for a closure is a location, not an assertion. **A file and a place in it, or a resource and its configuration — never a statement that something is secure.**
- The classification is defended per item and the defence names what was inspected.
- **The permanent exception is written as a defect in the instrument**, not as an excuse for the estate. An exception that reads as a complaint about the customer has been misclassified.
- The long tail is withheld on purpose and the withholding is recorded. Handing somebody every finding at once is a reliable way to have none of them fixed, and pretending otherwise is not rigour.
- The re-run has a trigger that is a state change rather than an intention — the same shape as the withdrawal trigger at [S074](/wiki/seminars/S074.md), and for the same reason.
- Where the acceptance criterion for an item was written by the same process that wrote the item, that is stated. **A generated check on a generated recommendation is one party marking its own work twice.**

## How it goes wrong

Five failure modes, each with the warning sign that precedes it.

- **Compliance pursued** — the goal becomes an empty list, and items are closed to empty it. *Warning sign:* an item was closed and nobody can say what changed.
- **The regenerated item ignored** — the same entry appears on every run, everybody knows it is not real, and nobody classifies it. *Warning sign:* somebody in the room refers to an item as noise.
- **False closure** — an item is marked done on a plausible-sounding basis, because that is quicker than establishing it. *Warning sign:* your closure evidence is somebody's recollection. **Claiming that something is implemented when it is not is strictly worse than failing to notice that it is.**
- **The re-run that nobody runs** — the procedure exists, the estate drifts, and nothing fires. *Warning sign:* the last run was performed because somebody was preparing for this session.
- **The improvement without a direction** — the list is different from last time and nobody can say whether it is better. *Warning sign:* you cannot name one thing that is now true which was not true before.

## Do it

Work from the supplied situation in [Q9](/wiki/quarters/Q9.md). Take the re-run output and classify.

Then do the harder half. **Write the criterion change that would make one invisible fix visible**, and cost it — in whose time, against what other work, and with what likelihood of being kept current. A criterion extended to reach one portal setting, and then never maintained, is worse than one that honestly cannot see it, because it will report a stale answer confidently.

Then decide the exception. One item, permanently outside reach, with a named owner and a review that is triggered rather than remembered.

## Show it

Report one item per class, in one minute each, and then the sentence that matters: **what is now true that was not true before this iteration.**

If the honest answer is *nothing, but the list is more accurate*, say that. **A more accurate list is an improvement and it is worth claiming as one** — provided you do not claim it as an improvement to the system.

## What this does not establish

**That any of this makes anything safer, better or more mature.** The design this session borrows from has no outcome evidence whatever. Nothing published or internal establishes that a plan produced this way leads to more fixed problems than a plan produced any other way — no comparison against a human-authored equivalent, no escape rate, no coverage against a known set.

**The scar tissue is real and unciteable.** The procedures behind this idea contain instructions that were plainly written after something went wrong — resume a half-written file, re-read the file rather than trusting what you already hold, refuse to run while an item is unevaluated. Those instructions imply observed failures. **The observations themselves are nowhere recorded, so the strongest evidence that the design works cannot be cited.**

And the self-checking is self-report. A numbered verification list at the end of a step is a configured instruction that a system may follow, partly follow, or silently not follow. **It is not a control, and where it is rendered into the delivered artefact with its own ticks against it, a configured instruction has been given the visual language of an audit trail.** Distinguishing the two is the durable skill in this session; everything else in it is a recipe.
