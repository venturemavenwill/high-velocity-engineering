# S084 · Each Iteration Leaves It Better

**Module:** [M17](/wiki/modules/M17.md) · **Quarter:** [Q9](/wiki/quarters/Q9.md) · **Complexity class:** 6
**Strands:** PE · ME
**Platform anchor:** An agent configuration corpus improved across pinned commits — improvement visible because each state is citable
**Whitepaper:** [WP-084](/wiki/whitepapers/WP-084.md)
**Retrieves from:** S055, S062, S081, S083
**Entry state:** this-programme-only

---

## The situation

The closure re-run has been executed against the estate as it now stands. Some items closed, because the evidence for them is now discoverable where the procedure looks. Some regenerated.

Two of the regenerated items are real fixes, made in a portal, in a place the re-run cannot see. One is a genuine gap that has been open since the security work and has regenerated on every re-run since.

Answer these in writing before the session opens.

1. What does a regenerated item mean? Give three meanings, not one.
2. For the item that has regenerated every time: what is the correct action, and is it the same as the action you would have taken the first time?
3. Nobody scheduled this re-run. Who should, on what trigger, and what happens if the trigger is a person remembering?
4. If you closed everything on this list, what would you have demonstrated?
5. What is the smallest change to the criterion that would let it see a fix made outside the repository — and what does that change cost?

**Item 4 is the session's subject.** The instruction that governs this whole idea, in the one place it is written down well, is that perfect compliance is not the goal and that pursuing it is itself a failure mode. What is asked instead is that each iteration leave the system better than the last. **A learner who cannot say why the first is a failure mode has not understood the second.**

## What you must produce

A **re-run finding** that classifies every regenerated item into exactly one of three states, with the evidence for the classification.

- **A real gap** — the thing is not done. The item is correct and the work exists.
- **An invisible fix** — the thing is done, somewhere the criterion cannot look. **The defect is in the criterion, and the item names it.**
- **A criterion that cannot ever see it** — the fix is real, it will always live outside the procedure's reach, and no reasonable extension of the procedure will find it. This is a permanent exception and must be recorded as one, with an owner, or it will regenerate forever and train everybody to ignore the list.

Plus one further section: **the items you are deliberately not raising this iteration**, and why.

Plus the section this module turns on: **the improvement statement.** One sentence naming what is now true that was not true before, and beside it the two pinned states — the revision the previous run was taken at, and the revision this one was — because **a claim of improvement with only one citable state is a claim about a memory.**

## The material

### Improvement is only visible where each state is citable

This is the durable claim and it is smaller than it sounds, which is why it works.

To say a thing improved you need two states and a comparison. Almost every improvement claim in delivery work has one state — the present — and a recollection standing in for the other. **A recollection is not a state.** It cannot be re-read, it drifts toward the flattering, and it belongs to one person who will leave.

The repair is not more careful memory. It is **pinning**: recording the exact revision each observation was made at, so that the earlier state can be fetched and re-inspected by somebody who was not there. A pin is cheap, it is a string, and it converts *we got better* into *at this revision the list contained these items and at this one it contains these*, which is a claim a hostile stranger can check.

**The programme has already stated this property in its other direction, and the two are the same sentence.** Pinning does not slow decay; **it makes decay visible.** A documentation page cited without a version is cited at whatever it says today and nobody can tell. A repository cited without a commit has the same defect, and the commit makes it visible. **The identical mechanism makes improvement visible**, and that symmetry is the whole reason this session's anchor is a pinned corpus rather than a delivery estate.

### The worked instance: a corpus that can be cited at two moments

The specimen is an openly published agent configuration corpus, read at a pinned commit, and it is a good teaching object because **nothing about it is careless** ([research/06-microsoft-platform/hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md)).

Its organising claim is that a coding agent's behaviour is an engineering artefact, and that if it is an artefact it should be authored, versioned, reviewed, packaged and distributed like any other. Four artefact kinds are held in distinct trees; collection manifests declare what ships together; a generated plugin tree is built from them and is **explicitly not canonical**. The unglamorous consequence is the one that matters here: **maturity and retirement are expressed through collection membership and metadata rather than inferred from a file's age.** A state, not a vibe.

The phases are joined by **durable state on disk** under stable identifiers, so that a run interrupted resumes from files and a decision made in one phase can be found in another by identifier. The corpus's own documentation is candid about what that buys: **provenance and restartability, and nothing about whether the decisions recorded were correct.** Separately, execution completion and acceptance outcome are declared to be different results — **a phase that ran to completion has not thereby been accepted** — and an agent may not record a human's approval, because human review is a stop condition rather than a checkbox the workflow can satisfy for itself.

Its assurance layer is where the session's third class of finding comes from. The repository states, in its own documentation, that its behavioural checks are regex-graded and **test output shape and not correctness**; that behaviour conformance is **advisory by default** and lacks established calibration; that baseline equivalence covers a narrow contract with unresolved work; and that **a check can be advisory at one tier while the nightly run treats the same check as authoritative.** That last is the single most misread property in the whole artefact, because a green mark looks the same either way.

**And the finding that keeps this session honest.** At the pinned revision there is **no committed controlled study, no calibrated baseline, no outcome dataset and no result corpus** — the storage location for results is an empty placeholder — while the corpus's own prose uses the vocabulary of demonstrated benefit. **The machinery is real and it is not a result**, which is [S068](/wiki/seminars/S068.md)'s finding and remains true here.

One more detail belongs in the teaching because it is exactly the kind of thing a summary erases. **The revision this programme pins is not all-green.** Of the checks reported, most were skipped, many succeeded, and one failed. **That is part of the evidence rather than a blemish on it**, and finding it takes deliberate looking — which is the same act this session's re-run classification requires.

**Its limits are extreme and travel with every use.** Perishability is total on paths, counts, plugin names and package versions, all of which moved while the note was being written. **Host and model dependence is absolute** — every artefact is inert without a host that loads it, and a result observed on one client and one model is not a result about the corpus. Scale will overwhelm a small team. **And a single vendor's opinion about agent configuration is not the field.**

### An iteration's result is immutable, and that is what makes the next one comparable

The openly published engineering handbook this programme uses elsewhere contributes one line that is exactly right and one habit that is exactly wrong, and both are useful.

The line is from its iterative performance-test template: **"The results of any iteration is immutable regardless whether the goal was achieved or not"** ([research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), pages read 2026-07-30). Read past the grammar. **A result that can be edited after the fact is not a state**, and a sequence of editable results cannot support a comparison. Immutability is not ceremony; it is the precondition for the next iteration meaning anything.

The habit is the one this repository records as a specimen. **The handbook asserts four unsupported magnitude claims** — figures with no method, no baseline and no citation — and carries a catalogue of non-functional threshold values with **no citation of any kind**, which a reader who does not notice will absorb as a normal range. **This repository reproduces none of the four, here or anywhere**, because naming the pattern is the teaching and repeating the figures would install the hazard.

**Cite it by page and by the date that page was read, never as a whole.** Its own footers span years, it contradicts itself in at least a dozen places without noticing, and several tools it recommends are archived or deprecated.

### A criterion cannot see outside its own scope, and that is a property rather than a fault

The second class of regenerated item — the fix that is real and lives where the procedure cannot look — has an exact analogue in governance tooling, and meeting it there makes the classification concrete.

Posture assessment for AI **samples the estate rather than covering it**: a bounded, usage-ranked subset of sites, a periodic cadence, a reporting delay measured in days, item-level scanning capped and one major store excluded entirely ([research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md](/research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md)). **A remediation applied outside that scan scope is invisible to the instrument no matter how real it is.**

That is not a defect. It is the resolution of the instrument, and it produces exactly the shape this session asks learners to classify: an item regenerating on every run because the fix exists somewhere the procedure was never designed to reach. **The defect is in the criterion and the item names it** — and where no reasonable extension of the procedure would ever reach it, the honest move is a recorded permanent exception with an owner rather than a criterion stretched until it lies.

**Its limits.** The Purview page consulted describes itself as the classic version and states it has been replaced; the Defender material was read through search excerpts with its structure reconstructed; agent-level capabilities move to a separate licence in 2026; and **no detection or false-positive rate is published for either product, and none is asserted here or anywhere in this wiki.**

### A difference smaller than the instrument's noise is not an improvement

The last piece is the one that stops a re-run finding becoming a trend.

Results are conventionally reported with a **"highest number is best" mentality**, in which a leading figure is highlighted "but not necessarily to test that result for any kind of statistical significance" ([research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md)). Two consequences land on a re-run comparison. **A comparison on a small set frequently cannot distinguish the two states at all**, and the correct response is to decide in advance what difference the instrument could have detected. And **where items arrive in related groups rather than independently, an uncorrected interval is too narrow** — which is the normal condition of estate findings, since they cluster by repository, by template and by team.

**Two runs are two observations.** A shorter list this time is not a trend, and a learner who reports one has done at the estate level exactly what [S067](/wiki/seminars/S067.md) forbids at the measurement level.

**Its limits:** analytical rather than empirical; illustrative magnitudes rest on stylised assumptions; and **statistical validity says nothing about construct validity — a tight interval around a meaningless item count is still meaningless.** No figure from it is reproduced.

### The corpus behind this programme has never exhibited an iteration

For completeness, and because it changes how much weight this session can carry: the internal practice material asserts an iterative posture and **reports no post-deployment record for anything it describes** ([research/05-fde-craft/microsoft-accelerated-delivery-practice.md](/research/05-fde-craft/microsoft-accelerated-delivery-practice.md)). Whether any delivered system survived, was maintained by the customer, or was still running months later is not reported once. **There is no worked instance anywhere in it of a second iteration against the same estate.**

**So the session's central instruction — that each iteration leave the system better than the last — is carried by an instruction rather than by a demonstration**, and it is class 3: design reasoning with no external warrant.

**Its limits:** access-controlled and unverifiable by any public reader; paraphrased and never quoted; contradicts itself in at least a dozen places; no cost side, no quality evidence and no sustainment evidence appears anywhere in it.

## The workflow

**Pin two states of a corpus, diff them, and say what improved — with both revisions citable.**

You will use the openly published agent configuration corpus as the worked object, because it is public, versioned, and can be fetched at any revision by anybody who wants to check you.

**Step 1 — pin the earlier state.** Take the revision recorded in this repository's research note: commit, package version, and the date it was read. **Record the host and the model too.** Every artefact in that tree is inert without a host that loads it, and a result observed on one client with one model is not a result about the corpus.

**Step 2 — pin the current state.** Fetch the same repository at `main`, record today's commit and package version, and record your own host and model. **Two pins, two dates, four environment facts.** That is the entire apparatus.

**Step 3 — run the same enumeration against both.** Count the artefact kinds and their entry points, list the collections, list the evaluation lanes, and — with equal effort — search both trees for a committed result corpus, a calibrated baseline, an outcome dataset or a human-rated sample. **Record where you looked, not only what you found.** An absence is evidence only if the search was competent.

**Step 4 — find the failing check at each revision.** Neither is likely to be all-green. **Locate the failing job in the record rather than on this page**, and notice how much looking it took. The lesson is not that a build failed; it is that **a mostly-green summary conceals a specific fact**, and that concealment is the normal condition of every dashboard a supplier will ever show you.

**Step 5 — write the iteration record.** One file, and it is the assessed artefact.

```yaml
# iteration-record.yaml  — SHAPE, NOT SCHEMA.
# Every path, count, plugin name and package version below is a fact about ONE
# revision on ONE host with ONE model. Re-derive it; never copy it forward.

states:                       # TWO of them, or there is no claim
  before:
    commit: "<full sha>"
    package_version: "<version>"
    host: "<client + version>"     # artefacts are inert without a host
    model: "<model + version>"     # a result on one model is not a result about the corpus
    read_on: "<YYYY-MM-DD>"
    all_green: false               # record the failing job by name
  after:
    commit: "<full sha>"
    package_version: "<version>"
    host: "<client + version>"
    model: "<model + version>"
    read_on: "<YYYY-MM-DD>"
    all_green: false

enumeration:                  # the SAME procedure run against both states
  artefact_kinds: { before: "<list>", after: "<list>" }
  evaluation_lanes: { before: "<list>", after: "<list>" }
  committed_results: { before: null, after: null }   # searched with EQUAL effort
  search_performed:
    looked_for: ["controlled study", "calibrated baseline", "outcome dataset",
                 "human-rated sample", "stored result corpus"]
    outcome: "<what the search returned at each revision>"
    caveat: "Absence at one commit is not proof of absence in the project."

regenerated_items:            # EXACTLY one class each
  - item: "<name>"
    class: "real-gap"          # the thing is not done; the work exists
    inspected: "<what I opened>"
  - item: "<name>"
    class: "invisible-fix"     # done, somewhere the criterion cannot look.
    inspected: "<what I opened>"
    defect_is_in: "the criterion"      # NOT in the estate
    criterion_change: "<the smallest extension that would see it>"
    criterion_change_cost: "<whose time, against what, and who keeps it current>"
  - item: "<name>"
    class: "permanently-unreachable"   # no reasonable extension will ever see it
    owner: "<named person>"            # an exception without an owner regenerates forever
    review_trigger: "<a STATE CHANGE, not a person remembering>"

withheld_this_iteration:      # the long tail, on purpose, recorded
  - item: "<name>"
    reason: "<why not now>"

improvement_statement:
  now_true_that_was_not: "<one sentence, or the honest 'nothing'>"
  evidenced_by: "the diff between the two pinned states above"
  is_this_a_trend: false       # TWO observations are two observations
  detectable_difference_decided_in_advance: "<what would have counted>"

attribution:
  who_establishes_causation: "<named person>"   # never 'the team'
```

**Step 6 — classify every regenerated item into exactly one of the three states, and defend each by naming what you inspected.** Expect the second class to be the largest and the hardest, because an invisible fix looks identical to a real gap from inside the procedure. **The distinguishing move is always to go and look at the place the procedure cannot reach.**

**Step 7 — cost the criterion change before you propose it.** Whose time, against what other work, and with what likelihood of being kept current. **A criterion extended to reach one setting and then never maintained is worse than one that honestly cannot see it**, because it will report a stale answer confidently.

**Step 8 — use the agent to attack your own improvement statement, not to strengthen it.** One prompt: *argue that nothing improved between these two pinned states, that my regenerated-item classifications are wrong in at least one case, and that my improvement statement describes a more accurate list rather than a better system.* Read it for the last clause. Keep what is better than your own reasoning, record what you rejected, and **record that the instrument shares a model family with the corpus under examination and is therefore not independent of it.**

**What this makes observable that prose cannot.** The difference between a claim you can hand somebody and a claim you can only tell them.

The two pins sit at the top of the file. Anybody, anywhere, can fetch both revisions and run your enumeration. **They do not have to believe you and they do not have to have been present**, and the moment a learner watches somebody else reproduce their diff, the argument for pinning stops being an argument. There is a second-order finding too: **the diff is usually smaller than the recollection.** A learner who expected the corpus to have moved substantially and finds two named changes has learned something about improvement claims in general that no amount of caution about them delivers.

## What good looks like

- Evidence for a closure is a location, not an assertion. **A file and a place in it, or a resource and its configuration — never a statement that something is secure.**
- The classification is defended per item and the defence names what was inspected.
- **The permanent exception is written as a defect in the instrument**, not as an excuse for the estate. An exception that reads as a complaint about the customer has been misclassified.
- The long tail is withheld on purpose and the withholding is recorded. Handing somebody every finding at once is a reliable way to have none of them fixed, and pretending otherwise is not rigour.
- The re-run has a trigger that is a state change rather than an intention — the same shape as the withdrawal trigger at [S074](/wiki/seminars/S074.md), and for the same reason.
- Where the acceptance criterion for an item was written by the same process that wrote the item, that is stated. **A generated check on a generated recommendation is one party marking its own work twice.**
- **Both states are pinned.** Commit, package version, host, model and date, for each. A claim of improvement with one citable state is a claim about a memory.
- The improvement statement is one sentence, and it says whether what improved is the system or the list. **Both are legitimate; conflating them is not.**
- Two runs are treated as two observations. **A shorter list this time is not a trend**, and the document says what difference would have been detectable before reporting the difference observed.

## How it goes wrong

- **Compliance pursued** — the goal becomes an empty list, and items are closed to empty it. *Warning sign:* an item was closed and nobody can say what changed.
- **The unpinned before-state** — the comparison rests on how the estate is remembered. *Warning sign:* your earlier state has a description and no revision.
- **The regenerated item ignored** — the same entry appears on every run, everybody knows it is not real, and nobody classifies it. *Warning sign:* somebody in the room refers to an item as noise.
- **False closure** — an item is marked done on a plausible-sounding basis, because that is quicker than establishing it. *Warning sign:* your closure evidence is somebody's recollection. **Claiming that something is implemented when it is not is strictly worse than failing to notice that it is.**
- **The invisible fix blamed on the estate** — a real remediation lives outside the criterion's reach and the item is written as the customer's failure. *Warning sign:* your entry reads as a complaint.
- **The criterion stretched until it lies** — the procedure is extended to reach one setting and then never maintained. *Warning sign:* nobody was named as keeping the extension current.
- **The re-run that nobody runs** — the procedure exists, the estate drifts, and nothing fires. *Warning sign:* the last run was performed because somebody was preparing for this session.
- **The improvement without a direction** — the list is different from last time and nobody can say whether it is better. *Warning sign:* you cannot name one thing that is now true which was not true before.
- **Two observations reported as a trend** — the list is shorter, therefore the estate is improving. *Warning sign:* your document contains a direction and no statement of what difference was detectable.
- **The green summary accepted** — a mostly-passing run is read as passing. *Warning sign:* you did not go looking for the failing job, and you cannot name it.

## Exercises

**None of these is assessed.** The re-run finding, the iteration record and the permanent exception are carried to [S085](/wiki/seminars/S085.md), where the improvement statement either survives an independent re-derivation or does not.

**1 · Sort six statements into state, comparison and recollection.** For each, say what it licenses.

- *The corpus is much better organised than it used to be.* · *At this commit the tree held these evaluation lanes; at this one it holds these.* · *We fixed most of the findings from last time.* · *Three items regenerated on both runs and one of them has never closed.* · *The results directory was an empty placeholder at both revisions.* · *Things are moving in the right direction.*

> **Model answers.** The second, fourth and fifth are **comparisons resting on two citable states**, and each is checkable by somebody who was not present. The first, third and sixth are **recollections**: no revision is named, so the earlier state cannot be fetched and the claim cannot be wrong. **The general rule: a claim of improvement needs two states and a stated comparison, and any claim missing one of the three is a claim about the claimant's memory.** Notice that the fifth is a comparison that found *no change* — and that it is more useful than any of the recollections, because it forecloses an inference somebody was about to make.

**2 · Pin two states and run the same enumeration against both.** Using the workflow, fetch the corpus at the revision recorded in this repository's research note and at today's `main`, and run one procedure against each.

> **What you should find.** That the diff is smaller than you expected, and that at least one thing you were sure had changed had not. **Record the surprise**, because it generalises: a corpus that is actively developed still moves less between two arbitrary dates than a person's sense of it suggests. Record also that you searched both trees for a committed result corpus with the same effort you spent enumerating the machinery, and what that search returned. **If you find committed results at the later revision, that is a real finding and this session's opening needs revising** — record it, with the pin.

**3 · Go back to your own item 4, then break it.** Find what you wrote for opening item 4 — what you would have demonstrated by closing everything on the list. **Do not rewrite it yet.** Put it beside the criterion below and write one sentence naming the difference. Then write the honest version.

> **Criterion.** A pass says that closing everything would have demonstrated **that the criterion could be satisfied**, and names at least one route by which it could be satisfied without the estate changing — a scope narrowed, an item reclassified, an exception granted, a criterion relaxed. **A pass is available only by naming a route.** *"That we did the work"* fails, because it assumes the conclusion. *"Perfect compliance is not the goal"* fails as an answer even though it is the correct instruction, because reciting the instruction is not the same as saying why it is one.
>
> **Why the comparison step is mandatory rather than encouraged.** The research this session's structure rests on tested exactly this: showing learners a correct answer next to their own wrong one produced no benefit, and only the group *instructed to compare them* learned more ([research/04-professional-formation/sinha-kapur-productive-failure.md](/research/04-professional-formation/sinha-kapur-productive-failure.md)). Reading the criterion is not the exercise. Naming the difference between it and what you wrote is.

**4 · Find the failing check.** At each pinned revision, locate the one job that failed and name it.

> **What to notice.** How long it took, and that neither revision was all-green. **A mostly-green summary conceals a specific fact**, and the concealment is not anybody's doing — it is what a summary is for. Note also that this repository's own research note records the failing job rather than rounding it up, and ask yourself whether you would have.

**5 · Cost one criterion change.** Take one invisible fix and write the smallest extension that would make it visible, with the cost: whose time, against what other work, and who keeps it current.

> **Scoring criterion.** A pass names a person for the maintenance. A fail proposes the extension and leaves maintenance implicit. **A criterion extended to reach one setting and then never maintained is worse than one that honestly cannot see it**, because it will report a stale answer confidently — and confident staleness is the single hardest defect to detect from outside.

**6 · Turn the instrument on this programme.** This repository is a corpus with pinned states of its own. Take any two revisions of it and write an improvement statement using the same record.

> **What you should find.** That the statement is easy to write and impossible to warrant as an improvement to anything but the text — because **not one of this repository's hundreds of falsifiable predictions has been measured.** The apparatus is complete: predictions written, instruments named, coding schemes specified. **That is machinery, and it is not a result.** A learner who writes *the wiki improved* has done here exactly what the corpus's own benefit vocabulary does, on the material teaching them not to.

## What this does not establish

**That any of this makes anything safer, better or more mature.** The design this session borrows from has no outcome evidence whatever. Nothing published or internal establishes that a plan produced this way leads to more fixed problems than a plan produced any other way — no comparison against a human-authored equivalent, no escape rate, no coverage against a known set.

**That pinning improves anything.** Pinning makes a state citable. It does not make the state good, it does not make the comparison meaningful, and **it does not slow decay — it makes decay visible**, which is the same property that makes improvement visible and is the only claim this session makes for it. A learner who leaves believing that a pinned corpus is a better corpus has inverted the argument.

**The scar tissue is real and unciteable.** The procedures behind this idea contain instructions that were plainly written after something went wrong — resume a half-written file, re-read the file rather than trusting what you already hold, refuse to run while an item is unevaluated. Those instructions imply observed failures. **The observations themselves are nowhere recorded, so the strongest evidence that the design works cannot be cited.**

**And the self-checking is self-report.** A numbered verification list at the end of a step is a configured instruction that a system may follow, partly follow, or silently not follow. **It is not a control, and where it is rendered into the delivered artefact with its own ticks against it, a configured instruction has been given the visual language of an audit trail.** Distinguishing the two is the durable skill in this session; everything else in it is a recipe.

**Everything observed through the pinned corpus is bound to one host, one model and one revision.** Perishability is total on paths, counts, plugin names and package versions. **A result seen on one client with one model is not a result about the corpus**, and the corpus's own transparency statement says so. Its absence of committed results is an absence at one commit and is not proof of absence in the project.

**The comparison literature cited here is analytical rather than empirical**, its illustrative magnitudes rest on stylised assumptions, and it is explicit that a tight interval around a meaningless item count is still meaningless. **No figure from it is reproduced**, and no figure from the openly published handbook's four unsupported claims is reproduced either — both omissions deliberate, because demonstrating the hazard by repeating it installs it.

**No detection or false-positive rate for the governance tooling is published, and none is asserted.** Its sampling, cadence and latency bound every finding drawn from it, and a fix outside its scan scope is invisible to it however real it is.

**And the practice corpus has never exhibited a second iteration against the same estate.** The instruction that each iteration should leave the system better than the last is carried by an instruction rather than by a demonstration. **This session is class 3 throughout.**
