# S036 · The Question You Should Not Have Asked

**Module:** [M08](/wiki/modules/M08.md) · **Quarter:** [Q4](/wiki/quarters/Q4.md) · **Complexity class:** 3
**Strands:** PE · CF
**Whitepaper:** [WP-036](/wiki/whitepapers/WP-036.md)
**Depends on:** S026
**Re-tests:** S001
**Platform anchor:** Azure API Management `llm-token-limit` policy, deployed with Bicep · **MCP servers:** Azure MCP Server (write, disposable resource group) · Microsoft Learn MCP Server

---

## What this day is for

A request arrives. It is specific, it is reasonable, and somebody with authority wrote it.

It is also the output of an analysis you did not see, performed by someone with less information than you will have, under time pressure, and frequently by working backwards from a solution they had already thought of. The request tells you what they concluded. It does not tell you what they wanted, and the gap between those is where the work is.

The target: **construct the problem from evidence, treating the request as one piece of evidence among several rather than as the specification.** This is S026's construct-instrument distinction moved from measurement to requirements — the request is an instrument, the need is the construct, and the gap opens the same way.

**Today the agent builds the request while you are still reading it.** Given a substrate user's sentence, Copilot in agent mode will author the gateway policy, author the Bicep, deploy it through the Azure MCP Server and report success — competently, in minutes, with nothing a reviewer would object to. It will not ask what the request was for, because that is not a question it is positioned to ask. **This is not a failure of the agent and the day does not treat it as one.** It is the reason the day exists: the only thing that used to protect an engineer from building the wrong thing well was that building it took long enough to think during.

So you will build it. Into a disposable resource group, from the request as written, and then you will find out what you have.

## The delivery standard on this day

This day carries **principle 6 of the [FDE Delivery Standard](/wiki/program/14-FDE-Delivery-Standard.md): let AI accelerate the work, and require a human to decide** — that page's wording rather than a quotation, for the reason it gives there. Phase 4 point 8 is that principle stated as an engineering fact rather than as a value — the agent removes the delay in which you used to think, and the one decision it cannot make is whether the request should have been built at all, because that requires knowing what the requester will do with the result.

**What the principle costs here is the whole of phase 5's ordering.** Steps 2 and 3 are closed before the agent is given anything, which puts the analysis at the point where it is slowest, least rewarding and usually unnecessary — because the request is usually right. A principle that is expensive precisely in the cases where it changes nothing is a principle people stop applying, and the day says so rather than pretending the cost is small.

**Principle 5 lands here too, and it lands as this day's own question. Added 2026-07-30.** The standard treats security and responsible AI as **first-commit obligations rather than pre-launch gates**, and the playbook implements that as an assessment that is mandatory before any project involving a model — whose **standing first question is whether the problem can be solved without AI at all, and whether simpler technology would suffice.** That is this day's subject in its purest form, arriving from an unexpected direction: **the question you should not have asked is *how do we build this with AI* when the answer is that you do not need it**, and an assessment opening on it is a request-need gap check with a governance label on it. It costs exactly what point 8 costs — the question must be asked at the moment the agent could already have built the thing, and it is most expensive in the cases where the answer is *yes, build it*, which are most cases. **Neither source reports any outcome for the practice**, and asking the question first is not evidence that anybody's answer improved.

**The playbook artefact already running here is the engineering feasibility spike.** Step 4's disposable build is a time-boxed investigation, and step 2's belief enumeration is the spike's pre-mortem asked forwards: *imagine the project has failed, what caused it* becomes *what would have to be true for building this to be right.* The rule that travels with the form is the module's build rule arriving from a second source — **the code written for a spike is not the solution's code** — which is why step 4 goes nowhere near the substrate's production path. **Neither source reports any outcome for the practice**, and [WP-036](/wiki/whitepapers/WP-036.md)'s evidence status says so.

## Phase 1 · Pretest and prediction (25 min)

Five items. A real request from the substrate's history is supplied, verbatim.

1. What is being asked for?
2. What do you think they want?
3. What would you need to know to be confident about item 2?
4. Predict: how different are items 1 and 2 for the room?
5. **Copilot prediction, sealed.** You will shortly hand the agent this request and ask it to implement it against a disposable gateway. Write down what it will produce, and **name the one thing it will get wrong**. Sealed with items 1 to 4 and opened at phase 8.

Item 2 is answerable and most students answer it by restating item 1 in different words. Item 3 is the day's move.

Item 5 has a failure mode the day watches for and does not correct: most students will predict a defect — a syntax error, a missing parameter, a wrong scope. The agent will not produce one. **Predicting that the agent will build it badly is the wrong prediction, and finding that out is worth more than getting it right.**

**Warrant.** Pretesting on the request-need gap before it is named. The near-identity of items 1 and 2 across the room is the day's opening finding. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8: an instrument administered after its answer has been taught measures recall.

## Phase 3 · Contrasting cases and generation (45 min)

### The reading pass, run while the environments provision (added 2026-07-30)

Four disposable environments take real minutes to provision, during which nobody can run anything. **This is what fills them, and it is not filler.**

Each group receives **one whole section of the engineering playbook the strand runs on** — every page in it, in the order the site lists them, with no selection by staff — and classifies each page as **substantive practice**, **recipe bound to a named tool at a named version**, **worked example instance**, or **stub or link list**. Then they defend the classification.

**The defence is what is discussed, not the verdict.** Two groups may classify the same page differently and both be defensible; a group that cannot say what in the page produced its verdict has not done the exercise. It is not assessed.

Three findings arrive reliably and none is announced first.

- **The navigation does not signal which is which, and section size does not predict substance.** One of the site's longest sections is largely stubs and redirects; one of its shortest is substantive throughout. A reader who assigns work by menu entry assigns badly.
- **The register is uniform and the warrant is not.** Every page is written in the same flat declarative voice. Some cite the standard literature of their field; some cite only the documentation of the tool they configure; one cites a handful of social-media posts; and one asserts a catalogue of numeric thresholds and cites nothing at all. **Nothing on the page tells you which you are reading, and only the bibliography differs.**
- **The pages carry their own dates and the site carries none.** The footers span years. A page that renders is not a page that is current, and a recipe naming a tool version is dated whether or not anyone updated its footer.

Task after: **name the page in your section you would not rely on, and say what in it told you.** Then: **name the page you would rely on hardest, and say the same.** Then one more, added 2026-07-30 and the one that reaches furthest: **name at least one place where a page in your section disagrees with another page of this document**, and say which of the two you would follow — the disagreements are real and unmarked, nobody has adjudicated any of them, and what happens when a document in that condition is handed to somebody who was not there is [S089](/wiki/seminars/S089.md)'s subject.

The document is real, it is sincere, and its authors publish it for use — which is why it teaches this better than a constructed exercise could. **Every student in this room will meet a document like it in their first job, usually an internal one, usually with no bibliography at all.**

### The four requests

**Executed, not read.** Each group has a disposable resource group containing an API Management instance in front of a Foundry deployment, and four real requests from the substrate's history. Every request concerns the same object — the token limit users are meeting — and each was written by a different person.

Groups first classify all four, before running anything, on the question: would building this as asked serve them?

Then they hand each request to Copilot in agent mode, one at a time, and let it implement. The agent authors an `llm-token-limit` policy change and its Bicep, and deploys through the Azure MCP Server. Groups then drive traffic through the gateway and measure what the requester would actually experience.

| Case | The request | What building it as asked produces |
|---|---|---|
| A | Raise the per-minute token allowance | Solves it. The refusals stop. |
| B | Raise the per-minute token allowance, from a caller whose traffic is bursty inside the minute | Deployed, correct, and the refusals continue |
| C | Add a monthly token quota so we can predict spend | Works, and solves a different problem the requester had not mentioned — they wanted their own consumption *visible*, and the remaining-quota header gave them that |
| D | Give each team its own limit so one team cannot exhaust the others | Deployed, correct, and creates a new problem the requester will report as a complaint |

Case D is the payload. The policy is right, the Bicep is right, the deployment succeeds, and two properties the request never mentioned decide the outcome: **API Management uses one counter per `counter-key` across every scope at which the policy is configured**, so a key chosen without thought merges the teams it was meant to separate; and **the policy tracks usage independently at each gateway and does not aggregate across the instance**, so a limit stated once is enforced once per gateway. Neither is a defect. Both are documented. Neither is in the request.

Groups predict the ranking, commit, then run.

Task after: **for the cases you got wrong, state what in the request should have told you.** For most groups the answer is that nothing in the request could have told them, which is the phase's point.

**Sampling, disclosed to the room.** These four were chosen by staff from the substrate's history to span the outcome space. They are not a random draw, and the base rate of requests that are simply right is much higher than one in four. What the phase supports is a claim about the request's informational content, not about how often requests fail. Per instrumentation rule 3, a day that selects its own cases says so in the terms it would demand of a student.

**Demonstrated rather than operated.** The counter's behaviour across gateways is shown from documentation and a staff-run trace, not operated: it requires a multi-region deployment the programme does not hold. It is not assessed. The same applies to the difference between the v2 tiers' token-bucket rate limiting and the classic tiers' sliding window, which requires two tiers.

**Warrant.** Contrasting cases along one controlled dimension — the relationship between a request and the need behind it — with a measured adjudicator, now run against a metered service rather than read from a handout. Case D is the phase's payload because its wrongness is invisible in the diff: a reviewer reading the pull request sees a correct policy, and the failure lives in a property of the counter that the request did not raise and the review had no reason to check. **The reading pass is the same discipline one level up and is placed first deliberately.** Phase 4 point 6 asks students to treat a request as evidence with a provenance licensing a limited conclusion; the reading pass asks it of the document the strand itself rests on, page by page, before the day asks it of anybody else's sentence. It also decides something practical: which pages of the playbook the module may lean on for the next four days is a question the students answer rather than one staff answer for them.

## Phase 4 · Consolidating instruction (50 min)

1. **A request is the output of an analysis.** Somebody already decided something; you are receiving their conclusion, not their reasoning.
2. **Four things that shape a request** before it reaches you: the requester's model of what is possible, what they think you will agree to, what they have already tried, and who else they have had to persuade. **This list omits organisational incentives that reward requesting one thing rather than another, and it omits the case where the request is a compromise between several people with different needs — both are common and both are taken up at S082. Safe as a set of questions to ask about a request from an individual; unsafe as an account of how requests are produced in organisations, which is S081 and S082's material.**

   **A third omission, added 2026-07-30 on a full reading of a source this day's whitepaper already cited.** The list assumes a request describes something the requester wants. **Some requests exist to create urgency.** The best-known text on organisational change advises exactly this: "Real leaders often **create these sorts of artificial crises** rather than waiting for something to happen", with approving worked examples including deliberately permitting a large loss. A requester who has read that advice, or absorbed it second-hand, may be asking for something in order to make a problem visible rather than in order to have it built — and none of the four shaping forces above will surface that, because all four assume good-faith description. **The day does not equip you to detect it and does not claim to.** What it gives you is the behavioural question at point 5: *what would you do if this never existed* separates a person who needs a thing from a person who needs a conversation to happen. **This is recorded as a boundary rather than taught as a technique**, and the source it comes from cites no evidence for any of its advice, which the day states rather than smooths over.
3. **The request-need gap** as S026's construct-instrument gap. The request is the instrument; the need is the construct.
4. **Why asking "what do you really want" does not work.** People answer with another solution, because a request is what they have practised producing.
5. **What does work:** what happened last time, what you did instead, what would change if this existed, and what would you do if it never existed. Four questions about behaviour rather than about preference.
6. **The request as evidence,** not as specification: one observation, with a provenance, licensing a limited conclusion — S028's licensing discipline applied to a sentence somebody wrote.
7. **When the request is right.** Frequently. The point is not to override requesters but to know why you are agreeing.
8. **What an agent changes, and what it does not.** It removes the delay in which you used to think. It does not remove the analysis, and it cannot perform it, because the analysis requires knowing what the requester will do with the result — which is the one input the agent does not have and cannot obtain. **The correct response is not to build more slowly.** It is to spend the time you saved on the question the speed was previously hiding.
9. **Defaults are opinions, and today four were chosen for you.** The Azure MCP Server's read-only start parameter **defaults to false**, so the agent had write access because nobody turned it off. Exceeding a rate limit returns **429** and exceeding a quota returns **403** — two codes for two different scarcities, and a client that retries on 429 will hammer a 403 forever. A quota period's start is **the UTC timestamp truncated to the unit**, so a "monthly" quota resets on a boundary that is nobody's billing month. And `estimate-prompt-tokens` has **no default at all**: the policy requires you to state it, which is the platform declining to choose on your behalf and is the most honest of the four. **An engineer who cannot state what was chosen for them does not understand their own system**, and this generalises far beyond this vendor.
10. **Perishable and durable, separated.** Every status code, parameter name, counter behaviour and default in point 9 is **perishable** and several will move within the programme's own three years. What is durable is that a platform makes choices for you, that those choices are decisions nobody in your team made, and that a request written in ignorance of them will be implemented in ignorance of them. **Safe** for reasoning about this gateway, this quarter, at the version in front of you. **Unsafe** as a description of API Management generally, of any other gateway, or of the same gateway after an upgrade — and the correct move on encountering the next one is a documentation lookup, which is what the Learn MCP Server is for.

**Warrant.** Consolidation indexed to phase 3. Point 2 carries the strong-form scope statement on the enumeration. Point 7 exists to prevent the day producing engineers who second-guess everything, which is the module's characteristic overreach, and it is deliberately placed before point 8 so that the agent material cannot be read as a reason for suspicion. Point 9 is the day's platform-specific content and satisfies the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md)'s requirement that each day name a default the platform chose. Point 10 carries the perishability boundary in its strong form.

## Phase 5 · Whole-task learning task (85 min)

**Class 3. The problem is the student's to construct. This phase produces a build, and the build is an instrument rather than a remedy.**

Students take **the module's running need** — a real, unaddressed request from a substrate user, not yet analysed — and:

1. **State what is being asked for,** verbatim.
2. **List what you would have to believe** for building it as asked to be the right move.
3. **Identify which of those beliefs you can check** and which you cannot.

**Steps 2 and 3 are submitted before step 4 begins.** The agent is given nothing until the enumeration is closed, so that the build follows the analysis rather than shaping it.

4. **Build the request, literally, as written.** Copilot in agent mode, Azure MCP Server in write configuration, into your own disposable resource group. Deploy it. Drive traffic through it. **It goes nowhere near the substrate's production path** — per the module's build rule, an artefact that changes what the substrate does for its users fails this specification.
5. **Check the checkable beliefs** — against the substrate's data and history, and now against your own deployment, which has just answered several of them.
6. **State the problem as you now understand it,** and how confident you are.
7. **State what your build did not establish.** It demonstrated that the request is implementable and what implementing it produces. It established nothing about whether the requester is better off.
8. **State what evidence would change your characterisation,** and how you would get it.
9. **Write the question you will ask the user** at S037 — one question, behavioural, per point 5.

**No solution is proposed.** The module's standing rule begins here, and step 4 is not an exception to it: you have built the requester's conclusion in order to examine it, and the artefact says so.

**The artefact carries three further elements**, per the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript. If you gave one instruction and got a working deployment, record that — it is the day's most informative possible result.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that your own checks would have caught an intervention-worthy error — a `what-if` run whose output you reconciled against the deployed state, or a traffic test that would have exposed a wrong `counter-key`, are both accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 2 is worked with the room; step 9's question forms are supplied as examples. Steps 4, 6, 7 and 8 are unsupported.

**Warrant.** Whole-task at class 3, now shipping rather than describing. Step 2's belief enumeration is the day's discriminator — it converts an unexamined acceptance into a set of checkable propositions — and step 9 makes the day's output an input to the next. **Step 7 is the countermeasure to the module's newest failure mode**: a student who has deployed something feels finished, and requiring them to state what the deployment did not establish is the cheapest available way of withholding that feeling. It is unvalidated and [WP-036](/wiki/whitepapers/WP-036.md) §8 says so.

## Phase 6 · Error clinic (40 min)

Instructor first: something built exactly as requested on the substrate that was never used, with attention to **what the requester said when asked why**.

Then the agent case: a Copilot-authored gateway change that was **confidently wrong and passed review**. The agent produced the policy, produced the Bicep, and ran `what-if` before deploying — and the reviewer approved a preview in which the change did not appear. What-if had **short-circuited**: it could not evaluate part of the deployment, and when that happens to a module, every resource inside it is excluded from the results. The reviewer read a clean preview and concluded that nothing surprising would happen.

Attention goes to why review did not catch it. The preview was not wrong; it was incomplete, and it did not say so, because **on the CLI version the team was running, the diagnostic that reports short-circuiting is not displayed** — the condition still occurs and it occurs silently. A reviewer checking that the preview matched the intent had no way to know that the preview was not of the whole deployment.

Then students: something you built because someone asked for it, or a place today where you accepted agent output you had not checked.

**Warrant.** Error management. The requester's own explanation is the phase's first content: it is almost never "I asked for the wrong thing" and almost always a description of a circumstance the engineer never knew about. The agent case is the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen so that the failure is invisible to the review the students would actually have performed — the reviewer did everything the process asked, and the instrument they were reading was silently partial.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents their step 6 problem statement, and the partner's task is to **state what solution it implies** — and then to check whether the student had that solution in mind before writing it.

Where the implied solution matches the student's prior intent, the characterisation has been written backwards from a conclusion.

The partner then does one more thing: they read the student's step 8 statement of what evidence would change the characterisation, and **judge whether it is plausible for the problem as stated**. A characterisation written backwards from a solution has no evidence that would change it, and the answers to step 8 are where that shows.

**Warrant.** Interactive-tier articulation with a reverse-inference test. Writing the problem to fit a solution you already hold is the module's most common and least visible failure, and this is the cheapest available detector. The step 8 addition is the repair [WP-036](/wiki/whitepapers/WP-036.md) §8 identified as costless and did not originally make; it moves one of the day's two convergence detectors inside a phase whose outcome the artefact records.

## Assessment

Specification item in PE201. Checked elements: the verbatim request; the belief enumeration; the checkable-versus-uncheckable split; the deployed build and its measurements; the checks performed; the problem statement with confidence; **the statement of what the build did not establish**; the evidence that would change the characterisation; the behavioural question; **the prompt record; the intervention record; the frontier statement.**

**An artefact containing a proposed solution fails the specification.** The module's standing rule.

**An artefact whose build changed the substrate's user-facing behaviour fails the specification.** The module's build rule.

**An intervention record with no entries fails**, unless the artefact demonstrates that the student's own checks would have caught an intervention-worthy error.

Nothing else is assessed.

The substrate's specific requests and their outcomes are **perishable**, as are all policy attribute names, status codes, counter semantics, defaults and tool versions. **The playbook section handed out at the reading pass is perishable in the same sense and for a sharper reason** — a page classified as substantive this year may be a stub next year and the reverse, the section boundaries move, and the classification a cohort produces is a record of one reading rather than a fact about the site. What is durable is the move: classify before relying, and check the footer, the bibliography and the tool version before the prose. The request-as-analysis-output framing, the four shaping forces, the request-need gap, the four behavioural questions and the request-as-evidence discipline are durable and are what the specification assesses. **Amended 2026-07-30:** the four shaping forces are unchanged and now carry a third stated omission at point 2 — the request written to manufacture urgency rather than to describe a need. The enumeration was not rewritten and the specification is unaltered; what changed is that the day now names a case it does not cover instead of implying it covers everything. **The reading pass was added on the same date and adds nothing to the specification**; it occupies provisioning time that was previously dead.

## What to take from this day

**The claim to hold.** A request is the output of an analysis you did not see. **The request is the instrument and the need is the construct**, and nothing in a request tells you whether building it will help.

**What the sources license, and what they do not.** The request-need distinction, contextual inquiry's rationale and behavioural rather than preference questioning are grounded in [research/05-fde-craft/fitzpatrick-the-mom-test.md](/research/05-fde-craft/fitzpatrick-the-mom-test.md) and [research/05-fde-craft/beyer-holtzblatt-contextual-design.md](/research/05-fde-craft/beyer-holtzblatt-contextual-design.md), with the professional-formation material held at folder level. **Added 2026-07-30:** point 2's third omission is taken from [research/05-fde-craft/kotter-leading-change.md](/research/05-fde-craft/kotter-leading-change.md), read in full on that date, and **the citation carries three hard bounds.** Its author states in his own preface that he drew neither examples nor major ideas from any published source but his own and did not try to cite evidence from other sources, so **the book cites nothing**. **No change-failure rate appears in it**, so the percentage widely attributed to it is not its own and is not repeated here. And its stage sequence is described as usual rather than strict, with **running several stages at once being the author's own position rather than a criticism of him**. What it supports here is the existence of the manufactured-urgency case and nothing about how often it occurs. The unevenness of agent capability is grounded in a note written from an abstract, [research/04-professional-formation/dellacqua-jagged-technological-frontier.md](/research/04-professional-formation/dellacqua-jagged-technological-frontier.md), and supports **direction and mechanism only; no magnitude from it is asserted anywhere in this wiki.**

**Guidance for your own work.**

- **Ask what happened last time and what they did instead.** Behaviour, not preference — people answer *what do you really want* with another solution.
- **Enumerate what you would have to believe** for building it as asked to be right, and close the list before the agent starts.
- **Say what the build did not establish.** It shows the request is implementable and what implementing it costs; it establishes nothing about whether the requester is better off.
- **Put the deployment in its class** per the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md). A successful deploy is an *observed result* about the configuration; concluding that the person is now served is *unsupported inference*.

**Where this is easy to get wrong.** Predicting that the agent will build it badly. It will not. The wrongness is invisible in the diff, because it lives in a property of the system the request never raised and the review had no reason to check.
