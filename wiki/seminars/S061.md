# S061 · Where the Time and Memory Actually Go

**Module:** [M13](wiki/modules/M13.md) · **Quarter:** [Q7](wiki/quarters/Q7.md) · **Complexity class:** 5
**Strands:** IS · SY · ME
**Whitepaper:** [WP-061](wiki/whitepapers/WP-061.md)
**Depends on:** S016, S053
**Re-tests:** S007
**Platform anchor:** The PTU sizing model for Foundry Models — request shape, output-to-input ratio, cache rate · **MCP servers:** Azure MCP Server (read) · Foundry MCP Server · Microsoft Learn MCP Server

---

## What this day is for

[S053](wiki/seminars/S053.md) assembled the thing. Today it becomes a cost model.

The move is short and the students already hold both halves. [S016](wiki/seminars/S016.md) established that performance is a property of an access pattern rather than of an operation count, because moving data is the expensive act. S053 established that the assembly is two alternating operations over a stack of weights. Put those together and the answer falls out: **producing one token of output requires reading every weight, once, to do a small amount of arithmetic.** The cost of that step is bytes moved. Doubling the arithmetic available does almost nothing.

Processing an input is the opposite. Every position is available at once, the work is parallel, and the machine is busy doing arithmetic.

**So inference is not one workload. It is at least two, with opposite bottlenecks, and a system tuned for one is mis-tuned for the other.**

The day's target: **which resource binds is a property of the request shape, not of the model — and cost per request is therefore a function, not a number.** A student who reports one cost per request has reported a statement about a traffic mix, and the mix moves.

**The platform states this in its own arithmetic, and the students read it there.** To size dedicated capacity for a Foundry model you supply three things and only three: the request shape, an output-to-input ratio, and a cache rate. The documentation says why each is there — output tokens require more processing capacity than input tokens, and cached input tokens consume no capacity at all. The three combine into one normalised throughput figure, which is divided by a per-model divisor to give a quantity of machine. **That is this day's claim written down by somebody who has to bill for it**, and it is the reason the day teaches the ratio rather than a number.

This day also closes a promise. [S016](wiki/seminars/S016.md) point 7 said its two-property model of the hierarchy would be superseded, and named this day. It is superseded at phase 4 point 2, announced as such. S016 also taught the prompt cache; today that cache reappears as a term in a capacity formula, which is a different thing from a latency optimisation.

## Phase 1 · Pretest and prediction (25 min)

Five items on the substrate's own serving path, **sealed and opened at phase 8.**

1. Two requests carry the same total token count. **A** has a long input and a short output; **B** has a short input and a long output. **Predict the ratio of their serving cost.**
2. **For each of A and B, which resource binds** — arithmetic throughput, memory bandwidth, or memory capacity?
3. You double the arithmetic throughput of the hardware and change nothing else. **Predict the effect on A and on B, separately.**
4. Predict your item 1 ratio's accuracy: within a factor of two, five, or worse.
5. **Copilot prediction, sealed.** You will shortly ask the agent, through the Foundry MCP Server, to size a dedicated deployment for the substrate's current traffic and to say what it will cost per month. Write down what it will produce, and **name the one thing it will get wrong**. Sealed with items 1 to 4 and opened at phase 8.

Item 1's real ratio is far larger than almost anyone predicts. Item 3's answer is that one of the two barely moves, and most of the room does not predict which. Item 5's expected distribution is that a majority predict the agent will get a number wrong and a minority predict that **it will produce a confident figure for a quantity that is not its to state** — a monthly cost requires a rate the agent has not retrieved and a decision nobody has made.

**Warrant.** Pretesting with a quantitative extrapolation on a system the cohort has operated for a quarter without ever costing. **Item 2 is the day's first instrument and is deliberately sited here, before any instruction**, so that what it measures is the entering model rather than the morning's teaching. Items 1 and 3 are the same fact approached from opposite directions, so a student who is wrong on both cannot conclude that they were merely cautious. Item 5 is the module's first frontier-calibration datum and is sealed at phase 1 rather than at phase 5, per instrumentation rule 8.

## Phase 2 · Cumulative retrieval set (20 min)

Free recall, no notes.

- [S016](wiki/seminars/S016.md): the two hierarchy properties, and what an access pattern is a property of.
- [S007](wiki/seminars/S007.md): what a bad seam costs, and when you pay it.
- [S053](wiki/seminars/S053.md): the two alternating operations, in two sentences.
- [S052](wiki/seminars/S052.md): point 7 — the cost that is quadratic in sequence length, and the property that makes the architecture worth having anyway.
- **Bridge:** S016 said performance is a property of the access pattern, not the operation count. S053 said the assembly is a stack of weights with two operations run over it. **What is the access pattern of producing one token of output?**

The room answers: every weight is read once, to produce one token. The cost is bytes moved, and arithmetic is not the scarce thing.

**Warrant.** Expanding-interval retrieval reaching back five quarters, with a bridge that delivers the day's central mechanical claim as a consequence of two facts the room already holds. The claim is therefore a retrieval item rather than an exposition, which is the strongest position available to it, and it costs about ninety seconds.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups have a standard chat deployment on the substrate's serving path and an access token. They issue **four request shapes at matched total token volume** and read, from each response, the reported prompt tokens, completion tokens and cached tokens, together with the observed latency.

| Case | Shape |
|---|---|
| **R1** | Long input, short output. A document reduced to three lines. |
| **R2** | Short input, long output. A question answered at length. |
| **R3** | Short input, short output. A classification. |
| **R4** | Long input, long output. The substrate's retrieval-augmented path: retrieved context plus a full answer. |

Groups rank the four by **cost per request** and by **cost per unit of useful output**, and commit. Then they send the requests and compute, for each shape, the **normalised throughput figure the platform's own sizing method produces** — the documented combination of request shape, the model's output-to-input ratio, and the observed cache rate. The ratio and the per-model divisor are **retrieved by each group through the Learn MCP Server and recorded with the retrieval date**; neither is supplied and neither is assessed.

The payload is **R2**. It carries the fewest tokens of the three long shapes, it is what the substrate's users send most often, it looks like the cheap one, and it is the most expensive per unit of output by a wide margin. The room has spent a quarter counting tokens and the token count is not the cost — and the vendor's own sizing arithmetic says so, because it does not treat a token as a token.

Tasks after: **for each shape, name the resource that binds and state what buying more of the other one would achieve.** Then: **R3 is the cheapest per request and one of the three others is cheaper per unit of useful output than R3 is. Which, and why?** Then, third and shortest: **of the three inputs to the sizing method, say which are facts about inference and which is a fact about this vendor's price list.** Two are properties of the machine and one is a published ratio that could be changed in a release note, and a group that cannot tell them apart has learned a formula rather than a mechanism.

**Demonstrated rather than operated.** The sizing arithmetic produces a quantity of dedicated capacity, and the cohort cannot deploy it. What the room can do is compute the number, check it against the portal's capacity calculator, and query the model-capacities read API to see whether that much capacity currently exists in the region. **What happens when you ask for it is [S064](wiki/seminars/S064.md)'s**, and nothing about provisioned deployment is assessed today.

**Warrant.** Contrasting cases along one controlled dimension — the ratio of input length to output length — with a measured adjudicator and the model, deployment and traffic held fixed. The cases are now executed against a metered service rather than supplied as data, and the measurement the students take is the same measurement the vendor's capacity model takes, which is what makes the day's claim checkable rather than assertable. R2 is the payload because it defeats the room's expectation using the room's own established habit rather than an unfamiliar fact. The closing tasks are what make the phase generative: naming a binding resource is a hypothesis, and stating what the other resource would buy is the test of it.

## Phase 4 · Consolidating instruction (50 min)

1. **Two phases, opposite bottlenecks.** Processing the input is parallel across positions and bounded by arithmetic. Generating output is sequential and bounded by the rate at which weights can be moved. Everything else on this day is a consequence.

2. **Arithmetic intensity is the test.** Bytes moved per operation performed decides which resource binds. **This supersedes [S016](wiki/seminars/S016.md)'s two-property model, and S016 said it would.** The two properties — each level faster and smaller, data moving in fixed blocks — were true and incomplete. The missing property is that movement has a finite rate, and a generation step spends its whole budget there.

3. **Memory has three terms.** The weights, fixed. The transient working state, bounded by how many requests are processed together. And the **retained per-request state, which grows with sequence length and with the number of requests in flight.** Only the third is under run-time control, and it is [S063](wiki/seminars/S063.md)'s entire subject.

4. **Two cost terms, different growth.** The attention term is quadratic in sequence length; the weight-movement term is linear in output length and independent of it. Which dominates depends on the lengths and the model, so **the crossover is measured, not assumed.** [S012](wiki/seminars/S012.md) point 6 and [S052](wiki/seminars/S052.md) point 7 are the same argument.

5. **Efficient attention variants and architectural alternatives are attempts to move that crossover**, and each buys a change in which resource binds at a stated cost in quality, generality or memory. This is the deferral [WP-052](wiki/whitepapers/WP-052.md) and [WP-053](wiki/whitepapers/WP-053.md) placed on this day, and it is discharged as a class of moves rather than as a catalogue. **The durable content is that the crossover exists, is measurable, and is what the variants target. Which variants are current is perishable and is marked so.**

6. **Cost per request is a function of shape, not a number.** An aggregate cost per request is a claim about a traffic mix. This is [S053](wiki/seminars/S053.md) point 6 with money as the metric: **an aggregate hides a class-specific catastrophe in exactly the way an aggregate ablation does**, and here the class is a group of users rather than a taxonomy of inputs.

7. **The platform's capacity model is the same claim, priced.** Sizing dedicated throughput for a Foundry model takes exactly three inputs: the request shape, an **output-to-input ratio** expressing how many input tokens one output token is worth for capacity purposes, and a **cache rate**, because cached input tokens consume no capacity. The three produce a normalised throughput figure which is divided by a per-model divisor to yield a quantity of machine. **Read that formula backwards and it is phase 3.** Three consequences are worth stating and none is obvious. A capacity estimate is only as good as the traffic description it was built from. Improving your cache rate reduces the machine you need, so a prompt-layout decision from [S016](wiki/seminars/S016.md) is now a procurement decision. And **the divisor is per model, so changing model changes how much machine the same traffic needs** — which is why a model swap is a capacity event.

   **Everything numeric in this point is perishable and is dated.** The ratio, the divisor, the minimum deployment size and every price are retrieved on the day, recorded with their retrieval date, and **none of them appears in any assessment item.** They were verified for this offering on **2026-07-26** and the design's expectation is that at least one of them will have moved before the next.

8. **Defaults are opinions, and four were chosen for you before you woke up.** *The billing unit.* A standard deployment bills per token and has **no latency service level agreement**; a dedicated one bills per unit of capacity per hour and carries a defined latency target. Nobody asked you which you wanted; you got the first because it is what a new deployment is. *The routing.* Where your request is processed — globally, within a data zone, or in one region — is a deployment-type decision that trades data residency against availability, and the default was made by whoever created the resource. *The cache.* Whether your prompt tokens are discounted depends on a caching behaviour you did not configure. *And the ratio.* Output tokens are worth more than input tokens by a factor the vendor set, published per model, that you cannot change and that silently reprices every feature you have ever shipped. **An engineer who cannot state what was chosen for them does not understand their own system**, and this generalises far beyond this vendor.

9. **A cost model is an instrument.** [S029](wiki/seminars/S029.md)'s six-step sequence applies unchanged — decision, question, construct, instrument, error budget, sampling scheme, licensing sentence — and its point 8 applies hardest: **state what the model cannot detect, in the honest form.** A cost model is also subject to the substrate's adoption conditions, so its limitation statement travels with every figure it emits.

10. **Scope of everything above, in the strong form.** The two-phase decomposition and the three memory terms are **safe** for reasoning about where a serving system's time and memory go, for deciding which resource to buy, and for predicting the direction of a change. They are **unsafe** as a complete account of a serving system's cost: they omit the cost of the retrieval and pre-processing stages in front of the model, the cost of moving requests and results across a network, the cost of holding a model resident while idle, and every fixed cost that does not vary with traffic. A student who prices a service using only these terms will under-price it, and the omission is largest for exactly the low-traffic services where the fixed terms dominate. **The platform makes the omission concrete: a dedicated deployment's meter runs from creation to deletion whether or not a single request arrives, and the documentation states that such a deployment cannot be paused.** The idle-residency term is not a footnote on this platform; it is the whole bill for an unused deployment.

**Warrant.** Consolidation indexed to phase 3's four shapes. Point 2 is the day's mechanical content and discharges a commitment made five quarters ago. Point 6 is the retained content and the forward link. **Point 7 is the day's perishable platform-specific point and point 8 is the day's defaults point**, both required by the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md); point 7 is indexed to the arithmetic the groups performed at phase 3 rather than asserted, per instrumentation rule 7. Point 10 is required by the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md)'s scope rule in its strong form, and it is stated as a place where students will be wrong rather than as a list of exclusions.

## Phase 5 · Whole-task learning task (90 min)

**Class 5. The service, the classes, the model and its expiry are the student's, and it will be billed. This phase produces a build.**

Students work with Copilot in agent mode, through the Azure MCP Server in read configuration and the Foundry MCP Server, and **ship a running cost model** — not a spreadsheet. It reads the substrate's own telemetry, classifies traffic, and emits a figure per class with its qualification attached.

1. **Choose one service on the substrate.** State the decision your cost model will inform and who makes it. [S029](wiki/seminars/S029.md) point 1, unchanged.
2. **Define the request classes** the model will report on, and say how you chose them.
3. **Predict which resource binds for each class,** before measuring.
4. **Measure** cost per request and cost per unit of useful output, per class, on real traffic. The rate you convert tokens into currency with is **retrieved on the day and carries its retrieval date**; it is not supplied.
5. **Build the model.** One figure per class, **each carrying its confidence, its provenance and the retrieval date of every rate it depends on in the same field**, per specification rule 2.
6. **State what the model cannot detect**, in [S029](wiki/seminars/S029.md) point 8's honest form: what you checked for and could not detect, not what it misses.
7. **State the date at which the model becomes checkable and the divergence that would show it was wrong.** This is committed, not estimated — [S065](wiki/seminars/S065.md) reports the realised bill against it.

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the model's own checks would have caught an intervention-worthy error — an assertion that every rate in the model carries a retrieval date, or that the reported token counts reconcile against the platform's, is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 4's measurement harness is supplied and step 5's per-class arithmetic is worked with the room. **Step 3 is unsupported.**

**Warrant.** Whole-task at class 5, in which the deliverable is a running commitment with a date rather than an analysis. Step 5 enforces specification rule 2 at the point where the failure it was written for is most likely — a cost figure is the most travelled number in any organisation and the one most often separated from its qualification, and on this platform it additionally depends on a published rate that changes without notice, which is why the retrieval date joins the confidence and the provenance in the same field. Step 7 is what makes the day class 5 rather than class 4: the student cannot find out today whether they were right, and they must say in advance what being wrong would look like. The intervention record's escape clause follows the sensitivity discipline [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate optimisation that reduced the arithmetic cost of a serving path substantially, was correctly measured, was correctly reported, shipped, and did not change the bill. The path was bandwidth-bound. Attention is directed at the beginning rather than the end — **nobody asked which resource bound before the work started**, and the six weeks were spent well against the wrong constraint.

Then the agent case, and it is the one this module will keep returning to. A capacity estimate produced by Copilot in agent mode, in response to a plain request to size a dedicated deployment for a described workload. **It was confidently wrong and it passed review.** It applied the documented sizing method correctly, used the correct per-model divisor, produced a defensible number of capacity units and a monthly figure to two decimal places — and it assumed a cache rate nobody had measured, priced the result at a rate it had not retrieved, and said nothing about whether that capacity existed in the region or whether anyone had agreed to pay for it. Attention goes to why review did not catch it: **the arithmetic was right, the method was the published one, and every error was in a premise the request had not mentioned.**

Then students, in threes: a time you optimised something and the number you cared about did not move, or a place today where you accepted a figure the agent produced without asking where its inputs came from.

**Warrant.** Error management targeting points 1, 2 and 7. The instructor case contains no measurement error and no implementation error, which is what makes it a lesson about the question asked first rather than about rigour. The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen because **the review a student knows how to perform is a review of the arithmetic**, and the arithmetic was correct. It is also the module's opening instance of its characteristic agent failure: confident arithmetic about somebody else's decision.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents **their step 3 predictions and their step 5 per-class figures.**

The partner's task: **construct a request class on which one of those figures is wrong by more than its stated confidence, and show that the step 6 limits statement did not name it.**

Both are required. A class that defeats the figure but that step 6 already anticipated is not a defeat.

Per rule 3, the outcome is recorded in the artefact. Per rule 5, this reuses the dual-defeat structure introduced at [S029](wiki/seminars/S029.md) and used since at S047, S048 and S053; per the amendment at [WP-054](wiki/whitepapers/WP-054.md) §8, **its reuse here is recorded as contingent on S029's reported outcome.**

**Warrant.** Interactive-tier articulation with a dual demand, which makes the phase a test of the limits statement rather than of the model. This is the pairing that converts step 6 from a required paragraph into an assessed claim.

## Phase 8 · Calibration and commitment (20 min)

- Sealed items opened. **Item 1's predicted ratio against the measured ratio**, reported as a ratio of ratios.
- **Item 2's binding-resource error rate, broken out by request shape.** This is the day's first instrument and the cohort's entering baseline.
- **Item 3's doubled-arithmetic predictions against measurement**, shown beside item 1 so that both errors are visible at once.
- **Item 5 opened.** The sealed Copilot predictions are read against what each student's agent actually produced, and the cohort's hit rate is recorded. **Both halves count:** predicting that the agent would err is easy, and naming the error is the measure. The design's specific interest is how many students named a *premise* failure rather than an arithmetic one.
- The room's phase 3 rankings against the measured cost per unit of output, with R2's position marked.
- Each student names **one service they depend on whose binding resource they do not know.**
- Retrieval schedule: next morning, day 2, week 2, week 4.

## Assessment

**One specification item**, in IS301 with ME301. Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 1, the checked elements are: the service and the decision the model informs; the request classes and how they were chosen; the pre-measurement binding-resource predictions; the measured cost per request and per unit of output, per class; each figure carrying its confidence, its provenance and the retrieval date of every rate it depends on in the same field; the limits statement in the honest form; the committed check date and divergence; the phase 7 outcome; **the prompt record; the intervention record; and the frontier statement.** **Nothing else is assessed.**

**A cost figure reported only in aggregate fails.** Per-class reporting is not optional in this module.

**A figure whose confidence and provenance are recorded anywhere other than the same field fails.** This is specification rule 2 applied at the site it was written for.

**A commercial rate used without its retrieval date fails.** Every published price, ratio and divisor on this platform is perishable, and a figure derived from an undated rate is not checkable at the date the model claims to become checkable.

**An intervention record with no entries fails**, unless the artefact demonstrates that the model's own checks could have detected an intervention-worthy error.

**No provisioned-throughput capability is assessed.** The sizing arithmetic is performed and the capacity read APIs are queried, but creating a dedicated deployment is **demonstrated rather than operated** on this day and on every day in this module, per the [Microsoft AI Platform Map](wiki/program/11-Microsoft-AI-Platform-Map.md)'s open question on lab feasibility.

No entrustment judgement. The module's is at [S065](wiki/seminars/S065.md).

**Discharges.** Two obligations placed on this day by earlier work are discharged here. [S016](wiki/seminars/S016.md) point 7 committed that its two-property model would be superseded and announced as such; **phase 4 point 2 is that announcement.** [WP-052](wiki/whitepapers/WP-052.md) §3.2 and [WP-053](wiki/whitepapers/WP-053.md) §3.2 both deferred efficient attention variants and architectural alternatives to this day; **phase 4 point 5 discharges the deferral as a class of moves against a measurable crossover**, and marks the catalogue perishable.

**Deferral declared.** [S065](wiki/seminars/S065.md) phase 5 reports the realised serving cost of weeks 61 to 65 against every model built today, in three categories. **That report is not assessed, and it is stated here rather than only at S065 so that the decoupling is a written commitment before the model is written.** A student whose unmodelled costs are large is not marked down; if the check were assessed, step 6's limits statements would become strategic and the considered statement the module wants would stop being produced.

**Instrumentation under rule 6.** Two instruments with named response occasions:

- **The item 2 binding-resource error rate**, by request shape, measures the cohort's entering model of where cost lives. **Response occasion: [S063](wiki/seminars/S063.md), phase 5 step 1, where the student must state the binding resource for their admission decision and show the arithmetic that establishes it — a required artefact element, constructed around whichever resource this cohort most often mis-identified.**
- **The step 4-against-step 5 divergence** — how far each student's per-class figure sits from its own stated confidence band on re-measurement — measures whether the cohort's cost models are calibrated or merely produced. **Response occasion: [S064](wiki/seminars/S064.md), phase 5 step 3, where the model is carried forward and its measured divergence must be stated as an uncertainty band on the capacity claim rather than discarded.**

## Perishable content in this day

**Serving-technology detail is the most perishable material in the programme, and this day contains a great deal of it.** Everything durable here is written as a measurement obligation rather than as a fact about a named system.

| Durable claim | Platform instance, perishable |
|---|---|
| Inference is at least two workloads with opposite bottlenecks | Input processing against output generation on a Foundry chat deployment |
| Arithmetic intensity is the test for which resource binds | The output-to-input ratio, published per model, retrieved with a date |
| Cost per request is a function of shape, not a number | Normalised throughput over a per-model divisor |
| A cached input costs less than an uncached one | Cached tokens consume no dedicated capacity at all |
| Movement has a finite rate and a generation step spends its budget there | The per-model throughput divisor, which is where that rate is priced |
| Fixed costs dominate a low-traffic service | An hourly meter that runs from creation to deletion on a deployment that cannot be paused |
| Changing the model changes the machine the same traffic needs | The divisor is per model, so a model swap is a capacity event |

- **Durable:** the two-phase decomposition and its opposite bottlenecks; arithmetic intensity as the test for which resource binds; the three memory terms; the quadratic-versus-linear crossover as a thing to be measured; cost per request as a function of shape; a cost model as an instrument; aggregate-hides-class applied to money; and the observation that a capacity estimate inherits every simplification in the traffic description it was built from.
- **Perishable:** every ratio measured in phase 3; every published output-to-input ratio, throughput divisor and minimum deployment size; the current set of efficient attention variants and which crossover each moves; per-token prices; the names of the deployment categories and routing variants; and the substrate's own cost per class. **The whole of point 5's catalogue and every number in point 7 is perishable and only their shape is not.** All were verified for this offering on **2026-07-26**.
- **Local:** the substrate's serving path, its traffic mix, the four request shapes as instantiated, the phase 6 optimisation, and the phase 6 agent transcript.

**Demonstrated rather than operated:** creating a dedicated deployment, and everything downstream of holding one. The cohort computes the sizing, reads the capacity, and stops.
