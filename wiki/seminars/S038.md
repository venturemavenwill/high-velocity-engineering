# S038 · Domain Modelling and Ubiquitous Language

**Module:** [M08](wiki/modules/M08.md) · **Quarter:** [Q4](wiki/quarters/Q4.md) · **Complexity class:** 3
**Strands:** PE · CF · SY
**Whitepaper:** [WP-038](wiki/whitepapers/WP-038.md)
**Depends on:** S011, S037
**Re-tests:** S014
**Platform anchor:** Bicep resource naming, generated from a repository custom instructions file · Azure Monitor and API Management metric vocabulary · **MCP servers:** Azure MCP Server (write, disposable resource group) · Microsoft Learn MCP Server

---

## What this day is for

Yesterday produced a record of what one person actually does. It is long, specific, and useless to anyone who was not there.

A model is what makes it transmissible. And the model's most important property is not its structure but its **vocabulary**: the words used to name the things in the domain. If the engineers say "record" and the domain expert says "case," two models exist, both parties believe there is one, and every conversation between them is partly failing without either noticing.

The target: **build a model in the domain expert's language, and validate it by having them read it back.** A term the expert does not use is a term the engineers invented, and it will cost something later.

This is S014's entity-and-relationship work with a person in the room and the naming as the object.

**There are two new parties to the vocabulary this quarter and both of them are loud.** The first is the platform, which arrives with a complete vocabulary of its own — and it is not the domain's, and it is not internally consistent either. The word *limit* names at least four different quantities in the stack the substrate runs on, and the documentation states outright that two of them are unrelated to each other. The second is the agent, which will adopt whatever vocabulary you give it and generate infrastructure named in it. **An instructions file is a vocabulary with an executor attached**, and today is where students find out what that means: a term the expert does not use becomes a resource name nobody in the room can trace, in an hour, at scale.

## Phase 1 · Pretest and prediction (25 min)

Five items on yesterday's observation record.

1. List the things in this domain — the entities.
2. Name each one. Use one word.
3. For each name, say whether the user used that word yesterday.
4. Predict: what fraction of your names came from the user?
5. **Copilot prediction, sealed.** You will shortly give the agent your vocabulary as a repository instructions file and ask it to generate the gateway's Bicep from it. Write down **which of your terms it will fail to carry into the generated names, and what it will substitute instead.** Sealed with items 1 to 4 and opened at phase 8.

Item 3 is checkable against the record. Item 4's answers are optimistic; the actual fraction is usually below half.

**Warrant.** Pretesting on naming provenance, checkable against a record the student made themselves the previous day. The gap between predicted and actual is the day's opening finding and cannot be disputed. Item 5 is sealed at phase 1 per instrumentation rule 8, and it is the day's second checkable prediction — the agent's substitutions are observable, and they are almost always the platform's vocabulary rather than the engineer's, which is a finding students do not expect.

## Phase 2 · Cumulative retrieval set (20 min)

Free recall, no notes.

- The S037 said/done/inferred separation.
- The S011 pair: what a representation discards and what it buys.
- The S014 five question types.
- Which S011 question does choosing a name answer, and what does a name discard?

**Warrant.** Expanding-interval retrieval with a bridge making a name a representation choice — which is the day's central claim and is delivered as retrieval.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups receive **the same domain modelled four ways** by four teams who all worked from the same observations. The models are structurally similar and lexically different. One entity is called four things.

- **Model A** uses the domain expert's vocabulary throughout.
- **Model B** uses implementation vocabulary — records, rows, jobs.
- **Model C** uses a vocabulary borrowed from a different domain the team knew well.
- **Model D** uses the expert's vocabulary for most things and one invented term for the concept the expert has no word for.

Groups judge which they would rather inherit, and commit.

Then each model is **run**. Its vocabulary is supplied to Copilot as a repository instructions file, and the agent is asked to generate the same gateway change from each — the same policy, the same resources, four times. Groups read the four generated Bicep files side by side and answer: **which of these could the domain expert read?**

The results are not what the room predicts. Model B's output is fluent and unreadable to the expert, which everyone expects. Model C's output is worse and for a reason nobody predicts: **borrowed vocabulary generates names that are plausible, consistent and about a different domain**, so the file reads as competent work and is wrong throughout. And model A — the one everyone chose — produces a file in which the expert's words appear only where the model had a word; everywhere else the agent has silently filled the gap with **the platform's vocabulary**, because that is what is in the documentation it was trained on and the instructions file said nothing.

Then **a transcript is supplied** of each team's next conversation with the domain expert. Three go badly, in different ways, and model D's goes well — because the invented term was introduced explicitly and the expert adopted it.

Task after: **state the condition under which inventing a term is correct.** Then: **state what happens to a distinction your vocabulary does not make, when an agent generates from it.**

**Warrant.** Contrasting cases across vocabularies with a fixed structure, now generated rather than described. Model D remains the payload: the rule is not "never invent" but "invent explicitly, and get it adopted." **The generation step adds the finding the day could not previously produce — that a vocabulary's gaps are not neutral.** A human modeller leaves a gap; an agent fills it, from the platform, consistently and invisibly, which converts a missing term into a term nobody chose.

## Phase 4 · Consolidating instruction (50 min)

1. **A name is a model.** Choosing a word commits you to a set of distinctions and forecloses others — S011's pair, applied to vocabulary.
2. **Ubiquitous language:** one vocabulary, used by everyone, in conversation and in code. Its value is that a mismatch becomes visible.
3. **Where the vocabulary comes from:** the domain expert, observed in use, not asked for.
4. **The four failure modes,** from phase 3: implementation vocabulary, borrowed vocabulary, silent invention, and — the subtlest — the same word used for two things. **This list omits vocabulary that differs between two groups of domain experts who both believe they are speaking the domain's language, which is common in any organisation of size and is S082's material. Safe when modelling a domain with one expert community; unsafe when two departments are involved, where the model must record both usages rather than choose one.**
5. **When to invent,** from model D: when the expert has no word for a distinction that matters, introduce one explicitly and check that they adopt it.
6. **The model itself** — entities, relationships, and the operations the domain actually performs. S014's apparatus, with the naming now load-bearing.
7. **Validation by reading back.** The expert reads the model aloud and narrates their work in its terms. Where they stumble, the model is wrong.
8. **What the model discards** and why that is acceptable — every model does, and the question is whether it discarded something the work depends on.
9. **The fourth failure mode, in the vendor's own vocabulary.** *Limit* names at least four distinct quantities in the stack the substrate runs on: the gateway's per-minute token rate; the gateway's token quota over a fixed period; the model deployment's tokens-per-minute quota, allocated per region and per model; and the model's own maximum input token length. They are enforced by different components, they fail with different status codes, and **the documentation states explicitly that the deployment's token-per-minute allocation is not related to the model's maximum input token limit.** A requester who says "raise the limit" has named one of four things and does not know which. **This is not a criticism of the vendor.** It is the ordinary result of four teams naming their own thing correctly, which is exactly how the failure arises in a domain, and it is the day's best available demonstration that the fourth mode is not a beginner's error.
10. **A vocabulary the platform supplies, and a default it chose for you.** The gateway's metric policy ships with eight dimension names you may use without defining them — including one called **User ID**. It is not the domain's user; it is the caller identity the gateway happens to hold. A model that adopts it has imported an entity from the platform's domain into yours without noticing, and the platform's own metric namespace defaults to **"API Management"** for the same reason: **an unnamed thing gets the vendor's name.** Elsewhere on the same resource, ten metrics carry the instruction *do not use for Azure OpenAI service* — including the one named **Blocked Calls**, which is the exact phrase a requester complaining about refusals will use. **The word you want and the metric you must not use have the same name.**
11. **Perishable and durable, separated.** Every metric name, dimension name, policy attribute and default above is **perishable**, and the four senses of *limit* will be four different senses in two years. Durable: a name is a model; vocabularies collide where teams name correctly and independently; an unnamed distinction gets named by whoever generates from your model. **Safe** for reasoning about the vocabulary in front of you and for auditing your own model's provenance. **Unsafe** as a claim about how any particular vendor names things, and unsafe as a reason to prefer the platform's vocabulary because it is the one the tooling already knows — which is the day's most tempting wrong conclusion.

**Warrant.** Consolidation indexed to phase 3's four models. Point 4 carries the strong-form scope statement. Point 7 is the day's assessed validation and is a behaviour rather than a review. **Point 9 is the day's platform-specific content and exists because the fourth failure mode is the one students never detect unaided** — it is stated in phase 4 in the general case and it is now also *exhibited*, in a document the students can open, which satisfies instrumentation rule 7 for a point the day's own entry state predicts students will find over-subtle. Point 10 satisfies the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s default requirement.

## Phase 5 · Whole-task learning task (90 min)

**Class 3. The model and its vocabulary are the student's. This phase produces a build, and the build is an instrument rather than a remedy.**

Students take yesterday's observation record and:

1. **Extract the vocabulary the user actually used,** with counts, from the said column.
2. **Build the model** — entities, relationships, operations — using only those terms.
3. **Identify the distinctions you need that the vocabulary does not make.**
4. **Invent a term for one of them,** explicitly, per point 5.
5. **State what the model discards** from the observation record, and why it is acceptable.
6. **Write the instructions file.** A repository custom instructions file that states your vocabulary, the terms that must be used, the terms that must not, and what to do where the model is silent. This is a specification whose conformance is checked by execution, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), and specification rules 1 and 2 apply to it exactly as they apply to prose.
7. **Generate and deploy.** Ask the agent, governed by your instructions file, to author the gateway change as Bicep and deploy it to your disposable resource group. It changes nothing the substrate's users experience.
8. **Validate twice.** The domain expert returns for the last thirty minutes, reads the model, and narrates their work in its terms. Then they read **the generated resource names** and say which they recognise.
9. **Record every stumble** — in the narration and in the reading — and what caused it. **Resolve one of them**: state what you changed and what the change cost.

**The expert is present for step 8.** Each student gets six minutes. Students choose which operations to have narrated, and the day tells them to choose the ones they suspect are weak rather than the ones they are confident about.

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** What you asked for at step 7, including anything you abandoned. If your instructions file was doing the work, the prompt should be short — and a long prompt is evidence that the specification was not carrying its own weight.
- **Intervention record.** Every point at which you corrected the agent. **An intervention record with no entries fails**, unless the artefact demonstrates that the design would have caught an intervention-worthy error — an instructions file with an explicit rule for what to do where the vocabulary is silent is the obvious example and is accepted, because it is the check that prevents the phase 3 model A failure.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch.

**Fading:** step 1's extraction is worked with the room; step 2's model form is supplied; step 6's instructions-file form is not — students have written specifications since S006 and this is one.

**Warrant.** Whole-task at class 3 with in-session validation. Step 9's stumble record is the day's discriminator — a model that produced no stumbles was probably not read carefully, and a model that produced many is a finding rather than a failure. **The resolution requirement at step 9 is the repair [WP-038](wiki/whitepapers/WP-038.md) §8 identified and did not make**, and it is now made: the day's semantic check previously produced data that went nowhere. Step 8's second reading is the executable half of the same validation and is what makes the instructions file a specification rather than a note.

## Phase 6 · Error clinic (35 min)

Instructor first: a substrate model whose vocabulary diverged from the users' over two years, and the specific conversation where the divergence surfaced — with attention to **how long both parties had been talking past each other**.

Then the agent case: a Copilot-generated infrastructure change that was **confidently wrong and passed review**. The team's instructions file said to use the domain's vocabulary. It did not say what to do where the domain had no word, and the gateway configuration needed several things the domain has no word for. The agent named them from the platform, consistently and plausibly, and the resulting file was reviewed by two engineers who both read it as correct — which it was, as infrastructure. Six months later the domain expert could not follow a conversation about their own service, because half its parts were called things nobody had ever said to them.

Attention goes to why review did not catch it: **the reviewers were checking whether the file was right, and the file was right.** Nobody was checking whether it was *theirs*, because that is not a property a code review looks for and there was no test that could fail.

Then students: a word you use that the people you build for do not — or a name in your step 7 output that you cannot trace to anybody.

**Warrant.** Error management. The duration detail is the first disclosure's content: vocabulary divergence is never discovered when it happens. The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and it is the day's own step 6 failing — an under-specified specification producing conforming, wrong work, which is the register in which the programme has assessed specifications since S006.

## Phase 7 · Peer articulation (25 min)

Pairs. Each student hands their partner **the model alone**, and the partner must describe the user's work from it.

The original student says nothing until the description is complete, then states what was wrong.

**Warrant.** Interactive-tier articulation with a reconstruction test. Per the [Seminar Day Design Pattern](wiki/program/04-Seminar-Day-Design-Pattern.md)'s instrumentation rule 2, this is the fourth document-only elicitation in the programme and **is not compared against the earlier three** — it is an intervention here, not a measurement.

---

## Phase 8 · Calibration and commitment (20 min)

- Items 3 and 4 resolved: predicted against actual vocabulary provenance.
- The room's step 9 stumble counts shown as a distribution; the most common stumble cause is named.
- **Item 5 opened.** The sealed predictions about which terms the agent would fail to carry are read against the generated Bicep, and the cohort's hit rate is recorded — separately for identifying a dropped term and for naming what was substituted. The design's expectation is that the substitution is the platform's vocabulary far more often than the room predicts.
- **The domain expert is asked, in the room, which model they would rather work with and why.**
- Each student names one term in their own current work that they cannot trace to a user.
- Retrieval schedule: next morning, day 3, week 2, week 6.

## Assessment

Specification item in PE201 and CF201 jointly. Checked elements: the extracted vocabulary with counts; the model built from it; the identified missing distinctions; one explicitly invented term with its adoption outcome; the discard statement; **the instructions file**; the stumble record from both readings; **one resolved stumble with its cost**; **the prompt record; the intervention record; the frontier statement.**

**A model containing a term that does not appear in the step 1 vocabulary and was not explicitly invented at step 4 fails the specification.**

**An artefact whose deployment changed the substrate's user-facing behaviour fails the specification.** The module's build rule.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design would have caught an intervention-worthy error.

Nothing else is assessed — not the model's structure, not its elegance, not the number of stumbles, and not whether the generated Bicep is good infrastructure.

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| A name is a modelling commitment | The four senses of *limit* in this stack |
| The same word used for two things is the subtlest failure mode | A deployment's TPM quota and a model's maximum input tokens, documented as unrelated |
| An unnamed thing gets named by whoever writes it down | The metric namespace defaulting to "API Management" |
| A vocabulary imported from elsewhere brings its domain with it | "User ID" as a supplied dimension name |
| A vocabulary's gaps are filled by whatever generates from it | The agent substituting platform terms where the instructions file is silent |
| A specification that produces non-conforming work is defective | An instructions file with no rule for the silent case |

The substrate's domain, the specific vocabulary, and every metric name, dimension name, policy attribute and default above are **perishable**. Name-as-model, ubiquitous language, the four vocabulary failure modes, the invention condition, read-back validation, and the treatment of an instructions file as a specification are durable and are what the specification assesses.
