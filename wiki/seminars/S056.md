# S056 · The Lexical Baseline You Must Beat

**Module:** [M12](wiki/modules/M12.md) · **Quarter:** [Q6](wiki/quarters/Q6.md) · **Complexity class:** 4
**Strands:** IS · ME
**Whitepaper:** [WP-056](wiki/whitepapers/WP-056.md)
**Depends on:** S013, S051
**Re-tests:** S041
**Platform anchor:** Azure AI Search full-text keyword retrieval — BM25 scoring, analysers, the shard · **MCP servers:** Azure MCP Server (Search) · Microsoft Learn MCP Server

---

## What this day is for

Every student in the room believes term matching is what retrieval used to be.

It is not. A weighted term-matching ranker is a strong, cheap, inspectable system that has outlived several generations of the things built to replace it, and on a large fraction of real query traffic it is still the best available answer. **A student who cannot beat it does not have a retrieval system; they have a preference.**

Today it is not a diagram. **Each student ships a real keyword index over the substrate corpus and runs the substrate's real queries against it**, built by prompting Copilot in agent mode through the Azure MCP Server. The ranker is the one the service gives them, with the two weighting parameters somebody else chose, and by the end of the day they will know which of their own users it serves better than anything they are about to build.

The day's harder half is underneath that. To say anything about whether one ranker beats another, somebody has to decide which documents were the right ones. That decision is a criterion in [S046](wiki/seminars/S046.md)'s exact sense — constructed, by named people, for a purpose — and in retrieval it is almost never written down. When it is written down and two people apply it, they disagree. **That disagreement is the ceiling on every number this module will produce**, and most published retrieval improvements are smaller than it.

The target: **relevance is a judgement made by a person against a criterion, the lexical baseline is a real result rather than a straw man, and which ranker wins is a fact about your query distribution before it is a fact about either ranker.**

## Phase 1 · Pretest and prediction (25 min)

Twelve queries from the substrate's log are supplied with the top five results from an unnamed ranker.

1. **Mark which results are relevant.** Write down the rule you used, in one sentence, *after* marking.
2. **Rank the twelve queries** by how well the system did.
3. Here are **the same twelve queries against a second unnamed ranker.** Which system is better?
4. Predict: **on how many of the twelve will the two systems disagree about the top result?**
5. **Copilot prediction, sealed.** You will shortly ask the agent to create a search index over the substrate corpus and load it, using nothing but a description of the corpus. Write down what it will produce — the field attributes, the analyser, the scoring configuration — and **name the one thing it will get wrong.** Sealed with items 1 to 4 and opened at phase 8.

Item 1's ordering is deliberate — mark first, articulate second — because the rule students write is a reconstruction and the day needs them to see that.

Item 5 is the day's contribution to the running frontier map. The design's expectation is that most students will predict the agent gets a *parameter* wrong and few will predict that it gets a *field attribute* wrong — and the field attributes are what determine whether anything is scored at all, because **only fields marked searchable participate in scoring and only fields marked retrievable come back.**

**Construction rule.** The twelve queries are **selected against [S051](wiki/seminars/S051.md)'s item 1 grouping distribution**, which measured whether the cohort's unaided notion of similarity is behavioural or semantic. If the cohort's groupings clustered on E3, the set is weighted toward queries whose clicked result is not the correct one and whose correct answer is found by exact rare-term match. If they clustered on E2, the set is weighted toward queries where paraphrase similarity retrieves a fluent wrong document and the rare term retrieves the right one. **In both branches the majority intuition is the one the set defeats**, and which branch runs is decided from the S051 data before the day is delivered.

**Warrant.** Pretesting on a task students can perform, with the articulation deliberately placed after the performance. The construction rule is this day's discharge of the obligation [S051](wiki/seminars/S051.md) placed on it under instrumentation rule 6: the response to that measurement is a change in what phase 1 contains, not a mention of it. **Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8: an instrument administered after its answer has been taught measures recall.**

## Phase 2 · Cumulative retrieval set (20 min)

Free recall, no notes.

- [S013](wiki/seminars/S013.md): the four claim types — worst case, amortised, expected, observed distribution — and which reader each is for.
- [S041](wiki/seminars/S041.md): what a held-out estimate estimates, and the four leak classes.
- [S051](wiki/seminars/S051.md): *similar to what*, and the freezing point.
- **Bridge:** [S013](wiki/seminars/S013.md) said an observed distribution is a claim about a sample from a population. **A retrieval score is an observed distribution over queries. Which population?**

The room answers: the query population you sampled, which is almost never the one the system will serve.

**Warrant.** Expanding-interval retrieval reaching back four quarters to S013 and importing its claim taxonomy intact. The bridge delivers the day's second-hardest idea as a consequence of a fact the cohort has held since week thirteen, and it costs one minute.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups have **one loaded search index over one corpus, a keyword ranker and a nearest-neighbour ranker over [S051](wiki/seminars/S051.md)'s E2 embedding as two fields on that same index, and four query sets** of forty queries each. They issue every query against the live service and read the returned ordering and each match's score. Relevance judgements for every returned result are supplied.

- **Q1** — queries containing identifiers: error codes, product names, version strings, ticket numbers.
- **Q2** — queries phrased in vocabulary the documents do not use.
- **Q3** — natural-language questions whose answering document never contains the question's words.
- **Q4** — **an unfiltered sample from the substrate's real query log.**

Groups characterise what determines the winner on each set and commit **before issuing anything.** Then the queries run. **Then the four sets' construction is disclosed**, including how Q4 was sampled and over what period.

The payload is **Q4**. On Q1, Q2 and Q3 the result is the expected one and the embedding ranker wins two of three. On Q4 the keyword ranker wins, and it wins because the real log is dominated by short identifier-bearing navigational queries — the Q1 shape — which nobody in the room chose to weight because nobody in the room has looked at a query log.

**A second finding arrives unbidden and is not skipped.** The two rankers' scores are on the same field of the same response and are not the same kind of number. The keyword score is unbounded; the vector score for a cosine metric is reported in a range that is **not the cosine range**. Groups are asked to notice this before it is explained, because a student who compares the two numerically has made the error [S051](wiki/seminars/S051.md) point 2 warned about, on a service that invites it by naming both `@search.score`.

Task after: **for each of the four sets, state what would have to be true of a deployment for that set to be the right one to evaluate on.**

**Warrant.** Contrasting cases across query populations with the corpus and both rankers held fixed, so that every difference is attributable to the queries. **The cases are issued against a real service rather than supplied as a table**, which changes what a wrong prediction costs: a group that predicted Q4 wrongly watched it happen. The construction disclosure is required by [instrumentation rule 3](wiki/program/04-Seminar-Day-Design-Pattern.md): a day that supplies four sets and teaches students to disclose their sampling must disclose its own. The final task prevents the phase resolving into "use the real log", which is right for the substrate and wrong as a rule.

## Phase 4 · Consolidating instruction (50 min)

1. **Retrieval is ranking, not matching.** The output is an ordering over the whole corpus, and every decision in the system is a decision about order. Matching is a special case that discards the information the caller uses.

2. **Term weighting is a claim about informativeness.** A term occurring in few documents discriminates more than one occurring in many; a long document matches more terms by construction and must be normalised for. Both are modelling decisions with visible parameters, which is the baseline's underrated property: **you can read it and say why it returned what it returned.**

3. **What the baseline discards** — [S011](wiki/seminars/S011.md)'s pair. Word order, morphology, synonymy, negation, and any relation not expressible as shared vocabulary. **The failure is not noise; it is the definition working correctly**, exactly as [S051](wiki/seminars/S051.md) point 4 said.

4. **Vocabulary mismatch is the baseline's single failure mode**, and it is [S038](wiki/seminars/S038.md)'s ubiquitous-language problem with nobody in the room to notice it. Where the query language and the document language are the same — identifiers, jargon, code, names — the mismatch does not arise and there is nothing for a semantic method to fix.

5. **Relevance is a judgement, not a property.** Somebody decides, against a criterion, for a purpose. The criterion has all of [S046](wiki/seminars/S046.md)'s parts and is usually unrecorded, which makes a relevance-judged evaluation a criterion-construction act performed by whoever had the afternoon free.

6. **Two people applying the same written criterion disagree, and the rate is not small.** That rate is the ceiling on every comparison built from those judgements. A reported improvement smaller than the disagreement between your own judges is not a result, and this is [S049](wiki/seminars/S049.md)'s dependency argument with the annotator as the cluster.

7. **Which ranker wins is determined by the query distribution.** The corpus fixes what can be found; the query population fixes what is asked for; the criterion fixes what counts. The method is the smallest of the four terms and is the only one anybody reports.

8. **The platform instance, and what it will cost you when it changes. Marked perishable.** The ranker you used this morning is BM25, and the service exposes exactly two of its parameters: `k1`, which controls how fast repeated occurrences of a term stop adding score, and `b`, which controls how much a document's length discounts it. Both are the parameters [research/02-technical-foundations/](research/02-technical-foundations/robertson-zaragoza-bm25-and-beyond.md) derives from stated modelling assumptions, exposed by a vendor at their derived meaning. **The correspondence between the monograph and the configuration file is the strongest single piece of evidence in this module that the durable material is durable.** The numbers are not: the defaults, the ranges, the score bounds and which algorithm a service even offers are all version-dependent and service-age-dependent, and one of them turns on **when the search service was created** rather than on anything the student controls.

9. **Defaults are opinions and thresholds are policy — and four of them shaped every number you produced this morning.** None was announced.

    - **`k1` is 1.2 and `b` is 0.75.** Nobody in this room chose either, and changing them requires taking the index offline, which is why almost nobody does.
    - **The score is computed per shard, not per index.** The service divides an index into a fixed number of shards and computes the ranking statistics within each; two identical documents in different shards can score differently. Computing the statistics across the whole index is one query parameter away and is documented as carrying a performance penalty.
    - **Full-text retrieval stops looking after a fixed number of matches.** There is a documented cap, it is a default you can raise, and past it the engine stops searching. Your recall figure is bounded by a number nobody in your team has read.
    - **`@search.score` equal to 1 for every row does not mean a perfect match — it means nothing was scored at all.** Wildcard, fuzzy, regex and empty queries return an unranked set with a uniform score, and it reads exactly like a strong result.

    **An engineer who cannot state what was chosen for them does not understand their own system.** Three of those four are decisions this day's argument depends on, and none of them appears in a single line of the code the agent wrote you.

10. **Scope, in the strong form.** Points 3 and 4 name the baseline's failure as vocabulary mismatch, and that is **safe** as a diagnosis when your queries and documents are the same kind of language and you are deciding whether a semantic method has anything to add. It is **unsafe** as a complete account of when term matching fails: it omits failures of aggregation across long documents, failures on queries whose intent is not lexical at all, and failures where the corpus itself is the problem. **A student who concludes from this day that lexical retrieval fails only on vocabulary mismatch will ship a baseline into a case it cannot serve and will not know where to look.** The scope statement extends to the platform instance without softening: points 8 and 9 are **safe** for reasoning about your own index on the version in front of you, and **unsafe** for any other search service by analogy, for any other version of this one, and — the case that will actually catch somebody — for reasoning about *why* a default sits where it does. A parameter's derivation is in the monograph; a parameter's default is a product decision and can only be looked up.

**Warrant.** Consolidation indexed to phase 3. Points 5 and 6 are the retained pair and are the module's foundation. Point 7 is the day's most portable sentence. Point 9 is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required naming of platform defaults, and it is placed here rather than earlier because each of the four is only legible after the room has produced a number that depended on it. Point 10 is written in the strong form because the enumeration at point 3 is exactly the kind of tractable list this design has repeatedly presented as complete.

## Phase 5 · Whole-task learning task (90 min)

**Class 4. The information need, the criterion and the query set are the student's. This phase produces a build.**

Each student ships **a working keyword index over the substrate corpus**, using Copilot in agent mode through the Azure MCP Server, and evaluates it against their own judgements.

1. **State the information need** the retrieval is for, and **who decides whether it was met.**
2. **Write the relevance criterion.** A document is relevant to a query when — one paragraph, applicable by someone who is not you.
3. **Sample a query set** of at least sixty from the substrate's log, and **state how you sampled it and over what period.**
4. **Predict** which ranker wins, on which query class, and by how much. Commit in writing.
5. **Build and load the index.** Decide, and state, which fields are searchable, which are retrievable, which analyser applies, and whether you changed `k1` or `b`. **Accepting a default is a decision and must be recorded as one.**
6. **Judge relevance on your own set. Then have a peer group judge twenty of your query-result pairs under your written criterion, and measure the disagreement.**
7. **Run both rankers and report by query class**, never in aggregate.
8. **State the query class on which the keyword baseline wins**, and **what property of your corpus or your query population makes that true.**

Step 5 is where the day bites and the bite is cheap to miss. A field that is retrievable and not searchable is returned and never scored; a field that is searchable and not retrievable is scored and never seen. **Both configurations run, both return results, and neither raises an error** — which is the reason this step is a build rather than a diagram.

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript — a record of what you asked for and why.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that your own design would have caught an intervention-worthy error — a check that every field named in your criterion is in fact searchable is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 2 is worked with the room, since criterion-writing is new and is where most students stall. Step 5's schema is produced by the agent and read by the student rather than authored. **Step 4 is unsupported.**

**Warrant.** Whole-task at class 4 in which the student performs every construction the day critiques, **and ships the system the critique is about.** **Step 3's sampling disclosure is [instrumentation rule 3](wiki/program/04-Seminar-Day-Design-Pattern.md) applied to the student.** Step 6 is this day's discharge of the obligation [S054](wiki/seminars/S054.md) placed on it under instrumentation rule 6: the same disagreement S054 measured on preference pairs is measured here on relevance judgements, by an external observer per instrumentation rule 1, and the two rates are reported together at phase 8. Step 8 is the discriminator — a student who reports that the baseline never wins has either an unusual corpus or an unexamined query set, and the assessors check which. The intervention record's fail condition carries the sensitivity escape [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate change in which keyword search was replaced by a semantic ranker on the strength of a published comparison and an internal evaluation. Both were correctly run. Support-ticket resolution time rose for eleven weeks. The evaluation's query set had been written by the team; the users search by error code, and error codes are the one input for which semantic similarity has nothing to contribute and something to lose. Attention is directed at the fact that **nobody on the team had read the query log**, and that reading it would have taken an hour.

Then the agent case, and it is from this material. A student asked Copilot to create a search index over a document set and load it. The agent produced a schema that was correct in every respect a reviewer would check: keys typed properly, an analyser named, a sensible field per column, no errors on creation, no errors on load, and results returned on the first query. **It had marked the body field retrievable and not searchable.** Every query returned the same documents in an order that looked plausible, because the only searchable field left was the title. The student's review consisted of running a query and reading the results, which is what a review of a search index looks like, and the results were not empty. Attention goes to why review did not catch it: **the failure produced output, the output was ranked, and the ranking was wrong in a way that requires knowing what should have come back.**

Then students, in threes: a time you evaluated something on inputs you chose yourself, or a place today where you accepted a schema you had not read.

**Warrant.** Error management targeting point 7. The instructor case contains no methodological error and no carelessness — the comparison was real, the evaluation was clean, and the query set was the ordinary thing to do — which is what makes it transferable rather than a story about a bad team. The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen because **the review that would have caught it is not the review a student knows to perform**: an index that returns nothing is diagnosed in a minute, and an index that returns the wrong thing confidently is not diagnosed at all without a judgement to check it against.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents **their step 2 relevance criterion and their step 8 baseline-wins class.**

The partner's task, in two parts, both required:

- **Construct a query-document pair on which the criterion, applied literally, gives an answer the student would reject.** Not a hard case — a case where the written criterion and the author's intent come apart.
- **Then say which of the two should change**, the criterion or the intent.

Per rule 3, both the constructed pair and the student's answer to the second part are recorded in the artefact.

Per rule 5 as amended at [WP-054](wiki/whitepapers/WP-054.md) §8, the second part is a **new structure, proposed and not validated**, and its reuse anywhere later is contingent on this day's reported outcome.

**Warrant.** Interactive-tier articulation with bilateral production: the partner constructs and the author adjudicates, so neither can pass by agreeing. The second part is the phase's point — a criterion the author immediately amends whenever it is inconvenient is not a criterion, and forcing the choice out loud is the only way this design has found to surface that.

## Phase 8 · Calibration and commitment (20 min)

- Item 4's predicted disagreement between the two rankers against the measured rate.
- Step 4's predictions against step 7's results, **split by query class.**
- **Item 5 opened.** The sealed Copilot predictions are read against what each student's agent in fact produced, and the cohort's hit rate is recorded. **Both halves count:** predicting that the agent would err is easy, and naming the error is the measure. The tally separates parameter predictions from field-attribute predictions, because the second is the one that silently changes what was measured.
- **The cohort's step 6 relevance disagreement rates, shown as a distribution and placed beside [S054](wiki/seminars/S054.md)'s preference-annotation disagreement distribution.** The two are the same measurement on two tasks and the comparison is the day's most quoted result.
- The cohort's step 8 baseline-wins classes, tallied.
- Each student names **one evaluation they have seen whose query set they cannot account for**, and **one default in their own index they did not choose.**
- Retrieval schedule: next morning, day 3, week 2, week 5.

## Assessment

**One specification item**, in IS203 with ME202. Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 1, the checked elements are: the information need and its decider; the written relevance criterion; the query set with its sampling and period disclosed; the pre-committed prediction; **the shipped index with its field attributes, analyser and scoring configuration recorded as decisions**; the measured peer disagreement; per-class results for both rankers; the baseline-wins class with the corpus or query property that explains it; the phase 7 outcome including the student's adjudication; **the prompt record; the intervention record; and the frontier statement.** **Nothing else is assessed.**

**A query set whose sampling is not stated fails.** This is the day's single hard requirement and it is the same rule the day applies to itself at phase 3.

**A result reported only in aggregate fails.** [S053](wiki/seminars/S053.md)'s standard carries forward unchanged.

**An accepted default recorded as an absence rather than as a decision fails.** Point 9's four defaults are the reference list; a student who did not change `k1` states that they did not and why.

**An intervention record with no entries fails**, unless the artefact demonstrates that its own design could have detected an intervention-worthy error.

No entrustment judgement. The quarter's is at [S060](wiki/seminars/S060.md).

**Rule-6 discharges.** Two obligations were placed on this day and both are built.

- [S051](wiki/seminars/S051.md) named this day's **phase 1 construction** as the response occasion for its item 1 grouping distribution. **The element exists: the twelve queries are selected by a stated two-branch rule against that distribution, so that the cohort's own majority intuition is the one the phase defeats.** The obligation is discharged.
- [S054](wiki/seminars/S054.md) named this day's **phase 5** as the response occasion for its step 4 peer-disagreement distribution. **The element exists and is assessed: step 6 collects relevance judgements from a peer group under the student's written criterion and measures the same disagreement on a retrieval task, and phase 8 shows the two distributions together.** The obligation is discharged.

**Instrumentation under rule 6.** Two instruments with named response occasions:

- **The step 6 relevance-judgement disagreement distribution** is the ceiling on every comparison this module will make. **Response occasion: [S059](wiki/seminars/S059.md), phase 5, where each student must state the agreement ceiling their own judgements imply and compare it against the size of the difference they are claiming.**
- **The step 4 prediction accuracy by query class** measures which query populations the cohort cannot reason about. **Response occasion: [S057](wiki/seminars/S057.md), phase 3, whose four dense configurations are evaluated on whichever query class the cohort mis-predicted worst here.**

**Frontier instrumentation.** Item 5's sealed prediction accuracy is this module's first frontier-calibration datum and is read by the following year's cohort through the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md), per instrumentation rule 9. Per instrumentation rule 3 the day states its sample: one cohort, one substrate corpus, one search service, one agent version, on a task staff chose because a known silent failure was available in it. **A frontier map assembled from these predictions describes this task, not the agent.**

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| Retrieval is ranking, not matching | The returned ordering and `@search.score` on one service |
| Term weighting is a claim about informativeness | `k1` at 1.2 and `b` at 0.75, and their exposed ranges |
| What the baseline discards | Which analyser the index was created with |
| Vocabulary mismatch is the baseline's failure | The two rankers' relative standing on any named set |
| Relevance is a judgement, not a property | This cohort's judgements on this corpus |
| The disagreement ceiling | This cohort's measured rate |
| Point 7's ordering of the four terms | The composition of the substrate's query log |

**Also perishable and marked as such at points 8 and 9:** the per-shard scoring behaviour and the shard count, the full-text match cap and its default, the meaning of a uniform score of 1, which scoring algorithm a service offers as a function of its creation date, and every score in phase 3.

**Local:** the substrate corpus, its query log and sampling period, the four query sets, the phase 6 change and the phase 6 agent case.
