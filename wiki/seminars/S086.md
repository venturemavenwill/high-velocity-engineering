# S086 · Reusable Starting Points

**Platform anchor:** An agent configuration corpus read at a pinned commit, treated as a starting point that must be re-verified rather than inherited
**Whitepaper:** [WP-086](/wiki/whitepapers/WP-086.md)
**Retrieves from:** S024, S031, S073, S075
**Entry state:** this-programme-only

## The situation

A starter repository was assembled during the engagement. It is now being proposed for a different customer, in a different sector, whose scoping has already begun. Somebody has described it in a mail as *proven*.

Inside it are the two review-routing thresholds that an engineer set late in a working week, with no recorded provenance. Inside it is the evaluation-set selection rule that was never written down — the set exists, the rule that produced it does not. Inside it are field names that somebody at the operator believes a regulator imposed, and nobody has checked.

**Answer these in writing before reading further.** They are not rhetorical, and item 3 is the one this session is actually about.

1. For each item you propose to carry: what does it rest on, and how would the next team find that out without you?
2. Which items are about the problem, and which are about the customer you built them for? Those are different things, and only one of them may travel.
3. What in this repository would let somebody skip a step rather than do it better?
4. How will the next team know this is out of date? Name the signal, not the intention.
5. What are you retiring, and what does retiring it cost the next engagement?

Most people answer 1, 2 and 5 readily. Item 4 produces the word *annually*, and item 3 produces nothing at all, because the question sounds like an accusation and is not. **A reusable starting point is precisely the instrument that makes step-skipping look like acceleration**, and the practice corpus behind this programme demonstrates that in its own documents: the rule holding the whole method together is stated as a headline — use the tooling to make each step better, not to skip steps — while its proudest anecdote is a prototype produced on the first day from a template, with no discovery activity described anywhere in it. Neither document notices. You are about to build the thing that produced that contradiction.

## What you must produce

**A reuse ledger and a retirement list.** The ledger has one row per carried item, with four fields and no others.

1. **What it is**, at a granularity somebody could act on. Not *the repository*.
2. **What it rests on** — the decision record, the observation, the constraint, the customer fact. **A name is not a provenance.** *Written by a senior engineer* records who to blame, not what to check.
3. **What must be re-established before use**, by whom, on the receiving engagement.
4. **Its staleness signal** — the observable event that will tell somebody this is no longer current, and who would see it.

Plus a **retirement list** with at least one entry, and the cost of each retirement stated. And a **pin block** for anything inherited from outside the engagement: revision, package version, host, model, date read.

## The material

### A pinned artefact tells you what was true and when, and that is the whole of its safety

The clearest available specimen of a reusable starting point is an openly published agent configuration corpus, read at a pinned commit and recorded at [research/06-microsoft-platform/hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md). It is a good teaching object because nothing about it is careless.

Its organising claim is that a coding agent's behaviour is an engineering artefact, and that if it is an artefact it should be authored, versioned, reviewed, packaged and distributed like any other. It separates four artefact kinds — instructions, prompts, agents and skills — into distinct trees with distinct application rules. It separates authoring source, packaging manifest and generated output, and **declares the generated tree non-canonical**. It expresses maturity and retirement through collection membership and metadata rather than leaving them to be inferred from a file's age. That last mechanism is the most transferable idea in the corpus for this session, because it is the only one that treats retirement as a first-class state rather than as neglect.

**Now the part that matters more than the architecture.** The note records the revision it was read at, the package version, the file counts, the date, and the build state at that commit — which was not all-green. It records that file counts, paths, plugin names and collection membership **all changed during the period the note describes**. It records that host and model dependence is total: every artefact is inert without a host that loads it, and a result observed on one client and one model is not a result about the corpus.

That is what a pin buys you. **It does not slow the decay. It makes the decay visible.** An unpinned starting point cannot be stale, because there is nothing to compare it against; a pinned one announces its own age every time somebody reads the date. **Reuse without re-verification imports somebody else's expired assumptions, and the pin is the only thing that tells you whose, and when.**

The note is blunt about the limit that follows: **only the mechanism layer is quotable without a date.** Phase separation with return paths, decisions addressable by identifier, review with normalised severity, untrusted input treated as data, human approval as a stop condition — those survive the disappearance of every file path in the tree. The paths do not.

### The two things a starting point is made of, and only one of them travels

Every artefact you are considering carrying is a mixture of two things, and they decay at different rates.

The first is **a claim about the problem**. A threshold is required at this point in the flow. A review step must exist between draft and record. An evaluation set must contain cases where the correct answer is refusal. These are statements about the shape of the difficulty, and they survive a change of customer.

The second is **a claim about the customer you built it for**. This threshold's value. This field structure. This site's volumes. These are inheritances — and the practice corpus this programme rests on is unusually good on exactly this instinct in a neighbouring context: reusing an environment after a project closes is named there as a policy violation rather than an inefficiency, explicitly because the asset is bound to a project identity.

**That instinct is correct, and it is applied to infrastructure and not to artefacts.** A repository carries a customer's thresholds, schemas and assumptions exactly as an environment carries their data, and it travels far more easily, because nobody has to raise a ticket to copy a folder.

**The corpus's limits travel with every use of it.** It is internal material, paraphrased here and never quoted or named. It contains no worked failure, no exclusion criteria and no outcome data of any kind — see [research/05-fde-craft/microsoft-accelerated-delivery-practice.md](/research/05-fde-craft/microsoft-accelerated-delivery-practice.md), whose limits section is the honest place to start. It contradicts itself in at least a dozen places and nothing reconciles them. **Its own prerequisites are stated and then immediately waived**, which means they are not prerequisites — and that is directly relevant here, because a starting point supplied with conditions the supplier is willing to drop is a starting point with no conditions.

### An unprovenanced constant is the most durable defect you can ship

The two thresholds are the session's hardest case, and they are hard for a reason worth naming.

A threshold that works is invisible. Nobody questions it, because the system behaves. It survives every review, gets copied into the next repository, and acquires authority purely by persistence. Ask where it came from and the answer is a person's name and a week.

The openly published engineering handbook this programme draws on supplies the mechanism by which this happens at scale. It carries a catalogue of non-functional threshold values with **no citation of any kind**, sitting inside a page that reads as guidance ([research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md)). A reader who does not notice the absence of sourcing absorbs those values as a normal range. **Specimen values become benchmarks whether or not anybody intends it**, and the reader who absorbed them will later describe a real customer's figure as high or low without being able to say against what.

**That handbook must be cited by page and by that page's own footer date, never as a whole.** Its pages carry individual dates spanning years; its navigation gives no signal distinguishing a maintained page from an abandoned one; and it contradicts itself in at least a dozen places without noticing — two pages disagreeing about branch naming, a worked example that does not follow its own template, a recipe recommending the approach its sibling comparison advises against. **The unevenness is invisible in the navigation**, which is exactly the failure mode a starter repository reproduces.

### Freshness is a cadence, not a latency, and the difference is your staleness signal

Item 4 in the opening is where almost everybody writes *review annually*, and the platform documentation supplies a better vocabulary for why that fails.

The Learn MCP Server's documentation states its freshness as cadence: the underlying knowledge service **"refreshes incrementally after content updates and performs a full refresh once a day"** ([research/06-microsoft-platform/learn-mcp-server-docs.md](/research/06-microsoft-platform/learn-mcp-server-docs.md)). Read that carefully. It bounds nothing about the interval between a page being corrected and that correction becoming retrievable. **"Incrementally after content updates" is compatible with seconds and compatible with hours**, and the note records that no indexing lag is published anywhere.

The same source records a second behaviour that any reuse ledger should steal outright. When content is deprecated without replacement, the vendor will **"redirect to the next best appropriate content, which may be a slightly modified scope, or to a landing page"**. So a fetch of a known-good address can silently return something other than what was there. **A citation to a page is a citation to a redirect target, not to a document** — which is why the note's own instruction is to cite the page *and the date you read it*, never the address alone.

**That is the shape of every good staleness signal: an observable event, with a named observer, that fires without anybody remembering to look.** *Annually* has no observer. *This breaks when the platform's default changes, and the pipeline fails on the day it does* has one, and the observer is whoever gets the alert.

**The documentation's limits are severe and stated.** It is first-party, definitional throughout and evidential nowhere. It is extremely perishable — the note records dated changes across nine months, including two that added tools which did not previously exist, against a developer reference that reserves the right to change the tool list without notice. Its own repository's marketing claims are unwarranted and must not enter teaching material in any form.

### The counterweight: reuse is not the same as improvement

One caution belongs here, because the session is otherwise a straight argument for carrying things forward carefully.

Accumulated practice explains far less about professional performance than the popular account claims, and it explains least in exactly the domains that look like this one — unstable conditions, delayed feedback, contested criteria ([research/04-professional-formation/macnamara-deliberate-practice-limits.md](/research/04-professional-formation/macnamara-deliberate-practice-limits.md)). **No magnitude from that paper is reproduced here.** The transferable point is directional: the domains where repetition compounds are the ones with stable rules and fast, unambiguous feedback, and forward-deployed engagement work is not one of them.

**Its limits are real.** It is a meta-analysis of correlational studies, read here from the official abstract; its underlying samples are range-restricted in a way that attenuates the effect it measures, and its professions estimate is the least stable of the set. A 2018 corrigendum exists and changed nothing substantive. Take the direction and the domain ordering, and take nothing else.

The consequence for the ledger: **an item that was right last time is evidence about last time.** The re-establishment column is not bureaucracy. It is the only place in the artefact where that fact is written down.

## The workflow

**Pin the corpus, then audit one item in it as though you were about to inherit it.**

You will use the agent configuration corpus as your specimen rather than your own repository, because you have no loyalty to it and because it is pinned, public and inspectable.

**Step 1 — pin it before you read a line.** Record the commit or release tag, the published package version, the host and its version, the model and its version, the enabled configuration, and the date. **Never audit a moving target.** Every count you take is a count at a revision, and a later reader who cannot reproduce your revision cannot check your audit.

**Step 2 — pick one artefact and find what it rests on.** Choose a single instructions file, prompt or skill. Read it, then go looking for the thing that justifies it: a decision record, a documented constraint, a stated rationale. Record what you find and — more usefully — record where you looked and found nothing.

**Step 3 — separate the two kinds of content inside it, line by line.** For each line write *problem* or *this-context*. Do not summarise. The value of the step is that it is tedious and produces a ratio you did not expect.

**Step 4 — find the retirement mechanism.** The corpus expresses maturity and retirement through collection membership and metadata rather than through file age. Find where your artefact's membership is declared. **If you cannot find it, that is the finding**, and it is the same finding you will make about your own starter repository.

**Step 5 — write the row.** Four fields, and the staleness signal must name an observable event and an observer.

```yaml
# reuse-ledger.yaml   <- SHAPE, NOT SCHEMA. Every pin value is a fact about ONE
#                        revision on ONE host with ONE model. Re-derive, never copy.
pin:
  source: "<public repo or internal path>"
  revision: "<full sha or release tag>"
  package_version: "<version as published>"
  host: "<client + version>"        # artefacts are inert without a host that loads them
  model: "<model + version>"        # a result on one model is not a result about the corpus
  read_on: "<YYYY-MM-DD>"
  build_state_at_revision: "<not necessarily all-green; record it either way>"

items:
  - what: "review-routing threshold, draft-to-record step"
    rests_on:
      kind: none-found        # decision-record | observation | constraint | customer-fact | none-found
      searched: ["decision records", "commit messages", "eval specs", "issue history"]
      note: "A name is not a provenance. Author recorded separately, below."
      author_only: "<name>"   # who to ask. NOT what to check.
    content_split:
      problem: "a threshold is required at this point in the flow"
      this_context: "the value itself; the volumes it was tuned against"
    re_establish_before_use:
      what: "observe the receiving site's volumes; re-derive the value"
      who: "receiving engagement's measurement owner"
      blocking: true          # true = may not be used until done
    staleness_signal:
      event: "upstream default changes; the pipeline fails on that day"
      observer: "whoever holds the pipeline alert"
      not_a_signal: "review annually"   # no observer, no event

retired:
  - what: "<the item whose retirement you will most resent>"
    cost: "<what the next engagement loses, stated plainly>"

must_not_travel:
  - "<named content that is this customer's and stays here>"
```

**Step 6 — turn the instrument on the corpus's own prose.** Search it for benefit vocabulary — words asserting that something is faster, prevented, measurable or proven. Beside each, write what would have to exist in the tree for the word to be warranted. **Do not editorialise.** The word in one column, the missing evidence in the next.

**Step 7 — attack your own ledger rather than extend it.** One prompt to the agent: *for each row where I recorded that provenance was found, argue that what I found is an author rather than a warrant — then find the row where I have wrongly marked re-establishment as non-blocking.* Read it for the misplacement you made. Keep what is better than your own reasoning and record what you rejected. **Record separately that this instrument shares a model family with the corpus being audited and is therefore not independent of it**, and that an agent which endorsed your ledger was not used as an instrument.

**What this makes observable that prose cannot.** The physical distance between an artefact and its warrant. Step 2 takes half an hour and usually ends at a person's name; step 5 then forces you to type that name into a field explicitly labelled as *not* provenance. **No amount of arguing produces the moment where you write a colleague's name in a box marked "who to ask, not what to check."**

## What good looks like

- **Every row has a pin, and the pin includes host and model.** An artefact recorded without the thing that loads it is a file, not a starting point.
- Provenance is a fact about the item, never about its author. A threshold's provenance is the observation it was tuned against; if there is none, the row says so and the item does not travel without a blocking re-establishment step.
- **Customer-specific content is separated from problem-specific content, and the separation is defended item by item.** A field structure that somebody believes a regulator imposed is one organisation's inheritance until somebody checks.
- Every staleness signal names an event and an observer. *Review annually* fails both tests.
- **At least one item is retired, and the retirement costs something.** A ledger with no retirements has not been read.
- Anything deliberately disposable stays disposable. Spike code was discarded at [S031](/wiki/seminars/S031.md) for a reason that has not changed because the code is now convenient.
- The ledger states what it does not contain — the parts of this engagement that must not travel, named.

## How it goes wrong

- **Carrying by default** — everything goes in, because nothing in it is obviously wrong. *Warning sign:* your ledger and your repository have the same contents.
- **Residue** — one customer's data, identifiers, thresholds or assumptions travel inside something described as generic. *Warning sign:* you would not show the item to the receiving customer in the state it is in.
- **The unprovenanced constant** — a value that works, whose origin nobody can state, now reused as a default. *Warning sign:* somebody defends a number by saying it has always been that.
- **The starting point that skips the step** — the next engagement generates something on day one and books the discovery it did not do as time saved. *Warning sign:* the item's value is described in units of elapsed time.
- **The invisible catalogue** — the reused asset carries no version, no age and no coverage statement, so a stale one produces confident, well-formed, out-of-date output with nothing marking that it happened. *Warning sign:* nothing in the item records when it was last true.
- **The pin nobody can reproduce** — a revision was recorded and the host and model were not, so the observed behaviour cannot be reproduced by anybody. *Warning sign:* your pin block has one line in it.
- **Inherited prose absorbed along with the artefact** — the corpus's benefit vocabulary arrives with its files, and you start saying *proven*. *Warning sign:* a verb in your handover summary is doing work no artefact in your ledger supports.

## Exercises

**None of these is assessed.** The reuse ledger is carried to [S089](/wiki/seminars/S089.md), where the departure it records becomes a candidate amendment, and to [S090](/wiki/seminars/S090.md) as evidence.

**1 · Sort six statements about a corpus into problem, context and neither.**

- *A threshold is required between draft and record.* · *The threshold is set at the value in this file.* · *This corpus ships no model and no safety classifier.* · *The field names match the operator's compliance form.* · *Fetched pages are data, never authority.* · *This approach is proven.*

> **Model answers.** The first, third and fifth are **problem** claims — they are about the shape of the difficulty and they travel. The second and fourth are **this-context**: an inheritance from one customer, carriable only as *a value is needed here*, never as the value. The sixth is **neither** — it is an outcome claim, and nothing in a configuration corpus establishes one. **The general rule: a statement travels if it would still be true for a customer you have not met.**

**2 · Pin something, then break the pin deliberately.** Using the workflow, pin the agent configuration corpus. Then take one fact you recorded — a path, a count, a plugin name — and check it against the current head of the same repository.

> **What you should find.** That at least one of them has moved, and that nothing anywhere announced it. The note this session rests on records that paths, counts, plugin names and package versions all changed *while the note was being written*. **The exercise is not to catch the repository out.** It is to feel the difference between a fact you can date and a fact you cannot, which is the only difference that makes reuse safe.

**3 · Go back to your own item 3, then break it.** Find what you wrote for opening item 3 — what in the repository would let somebody skip a step. **Do not rewrite it yet.** Put it beside the criterion below and write one sentence naming the difference. Then write the honest version.

> **Criterion.** A pass names a specific artefact, the specific step it makes skippable, and the observation that would have been made if the step had been done. *"The template could reduce discovery"* fails: it names no step and no lost observation. *"The generated schema lets the build meeting open with a field list, so nobody asks who fills the form in — and that question is where the review step came from last time"* passes.
>
> **Why the comparison step is mandatory rather than encouraged.** The research this session's structure rests on tested exactly this: showing learners a correct answer next to their own wrong one produced no benefit, and only the group *instructed to compare them* learned more ([research/04-professional-formation/sinha-kapur-productive-failure.md](/research/04-professional-formation/sinha-kapur-productive-failure.md)). Reading the criterion is not the exercise. Naming the difference between it and what you wrote is.

**4 · Write three staleness signals and have somebody try to defeat them.** Take three rows. For each, write the signal. Then hand them to another learner whose only job is to describe a plausible way the item goes stale without the signal firing.

> **What to notice.** That the defeat is usually easy, and that it usually works by changing something adjacent — the host, the model, an upstream default, the corpus behind a fetched page. This is the redirect behaviour from the platform note in another costume: **the thing you cited moved, and the citation still resolves.**

**5 · Retire the item you will most resent retiring.** Name it, name what the next engagement loses, and name who would object.

> **Scoring criterion.** A pass states a real cost. *"We would have to re-derive the thresholds"* is a real cost. *"Nothing, it was out of date anyway"* is not a retirement; it is tidying, and a ledger whose only retirements are tidying has not been read. **Retirement must be expressed as a decision with a price**, because a mechanism that only ever adds is a mechanism that accumulates.

**6 · Find one default you already trust and cannot source.** Write down a threshold, timeout, batch size or ratio you expect to see, and try to trace it to an observation.

> **What to expect.** For most people the trace stops at a document with no citation, or at a colleague. Both endings are the same ending. **The specimen-becomes-benchmark mechanism is documented in the handbook this programme uses** — an uncited catalogue of threshold values presented as guidance — and the point of the exercise is that you have already been through it once without noticing.

## What this does not establish

**That carrying anything forward helps.** Reusable starting points are named in the practice corpus as one of the things that must hold together for accelerated delivery to produce value rather than activity. **That is the whole of the treatment.** Nothing describes how one is built, what provenance it must carry, how it is versioned, who owns it, when it is retired, or whether reuse ever produced a better outcome than starting again. It is a pillar with nothing underneath it, and this session is written into that gap. **That makes it class 3 — design reasoning with no external warrant.**

**The nearest thing to evidence points the other way.** The corpus's one honest note about working on a mature codebase records that the assistant could not be asked to add a feature end to end, because the generated code reused outdated patterns and ignored the architecture's constraints; the workaround was to make failing tests the specification. **That is a report of reuse producing the wrong thing**, and it sits in speaker notes while the headline claims sit on slides.

**The risk this session is most worried about is documented as a pattern, not a finding.** Where a single knowledge source drives a generated process, that source's blind spots become the process's blind spots, and no step records the source's version, age or coverage anywhere in any output. **A stale input produces a confident, well-formatted, out-of-date result containing no signal that this happened.** That is a description of one design. Whether it generalises to a starter repository is this session's argument and nobody's evidence.

**The pinned corpus establishes architecture and nothing about outcomes.** The note is explicit: no committed controlled study, no calibrated baseline, no defect-rate comparison, no outcome dataset, no learner study. Its own prose nonetheless uses benefit vocabulary. **Absence at one commit is not proof of absence in the project**, and this session's use of it should be re-run against a later revision before any stronger statement is made in either direction.

**And nothing here is measured.** No claim in this session about what happens when a ledger is kept, or is not kept, rests on an observation of anybody keeping one.
