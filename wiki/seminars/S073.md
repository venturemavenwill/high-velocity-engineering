# S073 · Protocols, Tools and the Boundary of Trust

**Module:** [M15](wiki/modules/M15.md) · **Quarter:** [Q8](wiki/quarters/Q8.md) · **Complexity class:** 5
**Strands:** IS · SG · SY
**Whitepaper:** [WP-073](wiki/whitepapers/WP-073.md)
**Retrieves from:** S034, S039, S044, S072
**Platform anchor:** MCP — tool annotations as hints, `require_approval`, `allowed_tools` · **MCP servers:** Azure MCP Server · Foundry MCP Server · Microsoft Learn MCP Server

---

## What this day is for

[S034](wiki/seminars/S034.md) established that a consistency model is a contract, that its anomaly catalogue is the operative half, and that **a caller who knows only the model's name cannot handle what they will see.** [S034](wiki/seminars/S034.md)'s phase 6 case was a caller who assumed a stronger guarantee than the service provided, built correctly on that assumption, and failed rarely — with neither team wrong, because the contract had never been written down.

Today the caller is a language model. It will not read the contract if you write it. It will read the tool's **name**, take the strongest available interpretation of it, and call.

That is not a defect and it is not fixed by better documentation. [WP-006](wiki/whitepapers/WP-006.md) §6 named this day sixteen months in advance and stated the shape: **a tool boundary is an interface whose preconditions cannot be enforced, because the caller cannot be made to read them.** What survives is the part the boundary itself does something about — the schema it validates, the permission it holds, the precondition the callee checks, the rate it limits. Everything else in the contract is a suggestion addressed to something that does not take suggestions.

And then there is the direction nobody draws. A tool call goes out and **a value comes back**, and that value was authored by somebody who is not you: a document body, a page, a ticket comment, another team's error message, another agent's reply. At some specific point on some specific path, that value stops being data the system is examining and becomes input to a decision the system will act on.

**That point is the boundary of trust.** It is a place in a path, not a policy in a document, and most systems have more of them than their authors can name.

The target: **a tool boundary is [S034](wiki/seminars/S034.md)'s contract with a caller who will not read it; only four things in it are enforceable; the boundary of trust is the point at which a value the system did not author becomes input to a decision it acts on; and a tool that wraps an agent is not a tool.**

## Phase 1 · Pretest and prediction (25 min)

Five items on one substrate tool, **sealed and opened at phase 8.**

1. The tool's written specification is supplied together with the tool. **Name two things the specification promises that the tool does not do, and two things the tool does that the specification does not mention.** Both directions are required.
2. A model-written call to that tool is supplied, and it is wrong. **What did the caller assume, and where in the tool's surface did it get that idea?**
3. A trace is supplied in which the tool returned a well-formed, successful result whose text contained an instruction. The system followed it. **Mark the line at which the returned text stopped being data and became an instruction.**
4. Predict: **in this system, how many distinct places does content the system did not author become input to a decision the system acts on?** Write a number.
5. **Copilot prediction, sealed.** You will shortly ask the agent to add a tool to your capability and to make sure it cannot be used for one named purpose. **Write down what it will produce, and name the one thing it will get wrong.** Sealed with items 1 to 4 and opened at phase 8.

Item 1 is the two-directional documentation gap [WP-034](wiki/whitepapers/WP-034.md) §9 carried forward as the cohort's contract-reading baseline, re-probed here at four quarters; the S034 rate is the baseline this one is read against and both are reported together at phase 8. Item 4 is the day's discriminator, and the room's numbers are low. **Item 5 is the day's contribution to the running frontier map**, and the design's expectation is that most students predict the prohibition will be expressed in the tool's description — which is where a helpful assistant would put it, and which is the one place in the surface that constrains nothing.

**Warrant.** Pretesting on a real tool with its real specification, so that item 1 measures a capability rather than a memory and can be compared against the same student's [S034](wiki/seminars/S034.md) result. Item 2's *where did it get that idea* clause is what turns a diagnosis into the day's mechanism: the answer is almost always the tool's name. Item 3 requires a student to locate a transition they have no vocabulary for, which is what makes the phase 4 definition land as a name for something they have already found. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8; it is the same shape as [S071](wiki/seminars/S071.md) item 5 one construct further out, and the movement between the two is reported at phase 8.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups receive **four tool boundaries over one substrate capability**, all four registered as MCP tools on a running agent, each with three months of its call log, its incident record, and the permission it was granted.

- **T1** — a narrow typed schema, a permission scoped to a single record, no free-text field anywhere in the surface, annotated read-only.
- **T2** — a broad schema with excellent documentation: complete, accurate, and explicit about what the tool must not be used for.
- **T3** — a tool whose returned value contains content authored by a third party — a document body, a ticket comment, a page fetched from elsewhere.
- **T4** — a tool that wraps another agent.

Groups rank the four by **how much of what the tool must not do is actually prevented**, and commit before the records arrive.

Then they call them — including, deliberately, the calls the documentation forbids.

The payload is **T4.** Every group treats it as a tool, because its interface is a tool's: a name, a schema, a return value. It is a **caller.** Its behaviour is a trajectory rather than a function, it is non-deterministic in the way [S072](wiki/seminars/S072.md) point 2 established, and — the finding nobody predicts — **it holds its own permissions, which are not the ones its caller was granted.** The calling system's boundary of trust is somewhere inside a component it cannot see, and the permission the eventual action used belongs to a party nobody in the calling system has named.

**T2 is the day's second finding**, and it is the one the room expects to be safe. Its documentation is correct, complete and unread; **the forbidden call is made in the room and it succeeds**, and the incident record shows the same prohibited use occurring in the second week of the log, repeatedly, by a caller that never had access to the sentence forbidding it.

Task after: **for each boundary, mark the exact point at which content the system did not author becomes something it acts on — then name who is accountable for the permission the resulting action used.** For T4 the second answer is not available from anything in the calling system, and groups are required to write that rather than to nominate the tool's owner.

**Demonstrated rather than operated, and not assessed:** private MCP connectivity is documented as available only with the standard agent setup and a customer-supplied virtual network, with one hosting configuration described as the tested one and others as not internally validated. This programme's tenant holds neither. The configuration is shown from the documentation and from a recorded session, and **nothing in the specification depends on it.**

**Warrant.** Contrasting cases across boundary constructions with real call logs as adjudicator, holding the capability fixed so that variation is attributable to the boundary alone. **The four are called rather than described**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), and the operation is what makes T2 land: a room told that documentation does not bind will agree and continue writing documentation, and a room that has just watched a forbidden call return a successful result has met the finding rather than the claim. T4 defeats the room's expectation that a tool interface implies a tool. The accountability clause in the task-after is what makes T4's finding a professional one rather than an architectural curiosity.

## Phase 4 · Consolidating instruction (50 min)

1. **A tool boundary is [S034](wiki/seminars/S034.md)'s contract with a caller who will not read it.** [WP-006](wiki/whitepapers/WP-006.md) §6 named this sixteen months ago: an interface whose preconditions cannot be enforced, because the caller cannot be made to read them. **The tool's name and its schema are the specification. Everything else is commentary** — accurate, valuable to humans, and not part of what constrains the call.

2. **Four things are enforceable at a boundary:** the schema it validates, the permission it holds, the precondition the callee checks and rejects on, and the rate it limits. **This enumeration is not complete.** It omits **the content filter or classifier applied to a value in transit**, which is a real fifth mechanism, is genuinely load-bearing in deployed systems, and is excluded here because it is probabilistic — it belongs with the things you measure rather than with the things you rely on, and [S076](wiki/seminars/S076.md) treats it as such. It also omits **enforcement that lives downstream of the tool entirely**, in the system the tool acts on: a database constraint, an approval workflow, an immutable log. Those are frequently the strongest enforcement present and they are invisible from the boundary. The four are **safe** as a checklist for deciding what a tool boundary you control actually prevents, and as the answer to *what other than the sentence stops this* from [S071](wiki/seminars/S071.md) point 5. They are **unsafe** as an inventory of a system's total enforcement, because a student who audits only the boundary will report a system as unprotected when its real protection is two layers down, and will report one as protected when the boundary's four are present and the downstream system accepts anything.

3. **The boundary of trust is a place.** It is the point at which a value the system did not author becomes input to a decision the system will act on. **It is not a policy, not a setting and not a disposition.** It is a specific point on a specific path, and [S072](wiki/seminars/S072.md)'s drawing is the surface you mark it on. A team that cannot point at theirs does not have one.

4. **Every returned value crosses it, and there are more crossings than authors can name.** Item 4. Tool output, retrieved document, error message, file name, another agent's reply, a field the system logged last week and read back today. **Anything the system did not author is external content**, including content the system authored under a different request.

5. **The strongest reading.** [S034](wiki/seminars/S034.md)'s phase 6 caller assumed a stronger guarantee than the service provided and was not being careless — it was reading the name. A model caller does this systematically and cannot be argued out of it. **The design response is to make the strongest reading of the name true**, by narrowing the tool until its name is an accurate description of everything it can do.

6. **A tool that wraps an agent is not a tool.** T4. It is non-deterministic; its contract describes a function and its behaviour is a trajectory; and **it holds its own permissions, which are not the ones you were granted.** Composing agents is delegating authority, and the authority delegated is the callee's. **The professional consequence is accountability:** when the action lands, the permission it used belonged to somebody, and in a composed system that somebody is frequently not in any document either party holds.

7. **The protocol is not the boundary.** Interoperability protocols standardise how a tool is described, discovered and invoked. They do not decide what it may do. **The interoperability problem is durable; every specific protocol in this room is semi-durable at best**, and the [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) records it as re-verified per delivery. The durable content is therefore a measurement obligation rather than a fact: **for any protocol, state which of point 2's four enforceable things it carries and which it leaves to the implementer.** A student who can answer that for a protocol they have never seen has the day's transferable competence.

8. **[S039](wiki/seminars/S039.md) point 5, at the boundary.** A trade must be evaluable by the other party or agreement is not consent. A tool's permission is granted by a person who is being asked to accept an action set, and **a grant made without an enumerable action set is not consent.** This is [S044](wiki/seminars/S044.md)'s accept list and [S071](wiki/seminars/S071.md)'s allow list arriving at a person who has to sign for them, and it is why step 4's schema reduction is a professional act and not a technical one: **narrowing the schema is what makes the action set enumerable, which is what makes the grant something a person can actually give.**

9. **The protocol's own word for what a tool says about itself is *hint*.** *Perishable, and marked — and it is the day's sharpest concrete instance.* The Model Context Protocol defines annotations a server may attach to a tool: **destructive**, **idempotent**, **open world**, **read only**, with two Microsoft-proprietary additions on the Azure MCP Server — **secret**, meaning the response might contain material requiring sanitisation, and **local required**. The documentation calls them **hints that provide additional information about the characteristics of each tool**, and that word is exact. **An annotation is a declaration a server makes about itself. No client is obliged to honour it, and honouring it is a property of the client rather than of the boundary.**

   Two documented facts make the point in opposite directions on the same day. Microsoft Security Copilot **declines to import any MCP tool whose destructive hint is true** — a client that honours a hint, which shows that honouring is possible and that it is a decision somebody made in a product. And Foundry's toolbox documentation states, of the approval setting a tool can carry, that **`require_approval` is agent-enforced: the proxy executes `tools/call` regardless of the setting, and the agent runtime is responsible for gating the call.** A tool marked as requiring approval will run if the caller does not stop it.

   **That is point 1 in one sentence, from the vendor.** The declaration is addressed to a party that is not obliged to read it, and what constrains the call is what the caller does about it. It is also point 3: **the boundary of trust is not where the annotation is written, it is where the calling runtime decides.** Every name, field and value in this point is documented today and will move, and none of it is assessed.

10. **Defaults are opinions, and three of them widen your action set before you write anything.** *First, the allow list's default is everything.* An MCP tool configuration accepts `allowed_tools`, and it is optional; **omit it and every tool the server exposes is callable.** That is [S044](wiki/seminars/S044.md)'s accept list with an implicit *all* in it. *Second, the trust decision is documented as yours.* Microsoft's own guidance on third-party MCP servers states that **Microsoft has not tested or verified them**, recommends relying on servers hosted by the service provider rather than on proxies, and recommends logging everything shared with them for auditing. That is a vendor writing down that it is not the enforcing party — which is the correct thing to write and is not what most readers assume they are being told. *Third, a duration was chosen for you:* a non-streaming MCP tool call is documented as timing out at **one hundred seconds**, which is a rate limit in the sense of point 2 that nobody in this room set and that will silently define what kinds of tool your capability can have. **An engineer who cannot state what was chosen for them does not understand their own system.**

**Warrant.** Consolidation indexed to phase 3, with each of the four boundaries named at the point its lesson is defined. Point 2 carries the strong-form scope statement on the enumeration the room produced at the bridge, which is where it is most needed — a list students generated themselves is the one they are least likely to bound. Point 3 is the day's definition and is stated as a location because every wrong version of it is stated as a policy. Point 6 is the phase 3 payload named. Point 7 is the day's defence against its own perishability. Point 8 is the professional content and is placed so it lands on an established technical base. **Points 9 and 10 are the platform layer**, required by the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), and point 9 is placed after point 7 deliberately: point 7 tells students that for any protocol the assessed question is which of the four enforceable things it carries, and point 9 is that question answered once, out loud, on the protocol in front of them — **the answer being that annotations carry none of the four, because a hint is not an enforcement.** A student who can reproduce that reasoning on a protocol invented after they graduate has the day's transferable competence; a student who has memorised the six annotation names has the perishable layer exactly.

## Phase 5 · Whole-task learning task (90 min)

**Class 5. This phase produces a build. The crossings, the contract, the reduction and the enforcement are the student's.**

Students use **the control-flow drawing they produced at [S072](wiki/seminars/S072.md)** and the deployed capability behind it, working in Copilot agent mode through the Azure and Foundry MCP servers.

1. **Mark every crossing on the drawing** — every point at which a value your system did not author becomes input to a decision it acts on.
2. **For each crossing, state who authored the value**, and whether that party can be identified at all from inside your system.
3. **For your highest-consequence tool, write the contract in [S034](wiki/seminars/S034.md)'s three parts** — what the caller may assume, what it will observe, what it must do about it — **and then mark each clause as enforced or prose**, naming which of point 2's four enforces it. **An annotation is prose**, per point 9, and a clause defended by one is marked accordingly.
4. **Reduce the schema, and ship the reduction.** Produce the narrowest schema that still serves the capability, **deploy it**, and **state what the reduction cost**: which real request it no longer serves, and whether a substrate user makes that request.
5. **Take your [S071](wiki/seminars/S071.md) prohibited-action list — including every line you left blank — and your [S072](wiki/seminars/S072.md) breach paths, and give each one an enforcement point at a named boundary on your drawing** — or **re-declare it as accepted**, with [S044](wiki/seminars/S044.md)'s discipline: probability, consequence, and **your confidence and its provenance in the same field**, per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) specification rule 2. **State which SY301 material you used to identify each enforcement point.** An entry with neither an enforcement point nor an accepted re-declaration fails.

   *(The SY301 clause was added after [WP-073](wiki/whitepapers/WP-073.md) §8 found this day relying on a prior course it does not control, with no artefact element joining it back — the same failure [WP-044](wiki/whitepapers/WP-044.md) §8 recorded for a concurrent course, in a direction the [Whitepaper Standard](wiki/program/05-Whitepaper-Standard.md)'s deferral rule does not currently cover.)*
6. **Predict which crossing your own review missed.** One, named by position on the drawing, committed before step 7.
7. **Run the substrate's boundary inventory** — an enumeration of the actual crossings on the paths you drew — and report it against your markings and against step 6. **State which unmarked crossings your step 5 enforcement already covers by accident**, and which it does not. **Then attempt one call your boundary prohibits, against your own deployed tool, and report what happened.** One call. If it was refused, name the mechanism that refused it and say whether it is the one you wrote at step 5. If it succeeded, that is the more valuable result and it is not a deficiency.

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent to produce the reduced schema and the enforcement placements, in order, including the ones you abandoned.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error — and today the qualifying demonstration is a schema whose narrowing makes the intervention-worthy call unexpressible, which is the strongest form the escape can take on this day and is accepted without argument.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 3's three-part contract form is supplied, since it is [S034](wiki/seminars/S034.md)'s and re-deriving it costs time the day needs elsewhere; step 5's enforcement-point placement is worked with the room, because locating enforcement on a drawing is a new operation and the [M15](wiki/modules/M15.md) course allocation gives the platform mechanics no other home. **Step 6 is unsupported.**

**Warrant.** Whole-task at class 5 whose input is the previous day's artefact and whose output is what [S074](wiki/seminars/S074.md) classifies. **Step 5 is the receiving element for both instruments named on this day** — [S071](wiki/seminars/S071.md)'s unenforced-boundary count and [S072](wiki/seminars/S072.md)'s breach paths — and it is deliberately a fail condition rather than a prompt, because a boundary that acquires neither enforcement nor an honest acceptance is the exact artefact [S071](wiki/seminars/S071.md) point 5 named as a routing aid with a firmer tone. Step 3's annotation clause is point 9 as an assessed decision: a student who marks an annotated clause *enforced* has made the day's central error in one word, where it is visible. Step 4 is point 8 made concrete and is now **shipped rather than proposed**, which is what makes its cost real — the cost clause is what stops the reduction being free, and the *does a user make that request* clause is what stops it being theoretical. Step 7's inventory is the adjudicator, and [WP-073](wiki/whitepapers/WP-073.md) §8 concedes what an inventory cannot see.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate tool whose documentation was, by common agreement, the best in the codebase. It was complete, it was accurate, it named three uses the tool was not for, and it was reviewed annually. Its schema had one free-text field, added for a legitimate reason, with a legitimate default.

Over two years that field carried instructions the tool's authors never imagined. No security event was recorded, no incident was raised, nothing broke. **The tool simply became a different tool**, one nobody had specified, whose behaviour was defined by whatever callers had discovered they could put in the field.

Attention is directed at one fact: **the documentation was correct the whole time, and nobody read it — including the humans.** The three prohibited uses were prohibited in a sentence, in a file, that the callers did not open and the reviewers did not compare against the call log.

Then the agent case: a student asked Copilot in agent mode to **add a tool that lets the agent look up a customer record, and make sure it can only read.** It produced good work. The tool reads and does not write. It carries `readOnlyHint` set true, which is accurate. It has one parameter, a free-text `query` field, because that is the shape that serves the most requests. The review passed, and the review was right about everything it checked: **the tool is read-only and the annotation is true.**

Attention goes to two things the review had no reason to look at. **The annotation is a hint about the tool and says nothing about the system**, per point 9 — a read-only tool whose returned value the system then acts on is a crossing, and read-only is a property of the wrong side of it. And **the free-text field is the crossing**, added for the same good reason the instructor case's field was added, three seconds after being asked for the safest possible tool.

Then students, in threes: **a field you added because somebody had a good reason.**

**Warrant.** Error management targeting points 1 and 5, constructed like the module's other clinics so that the case contains no error of care at any step: the documentation was good, the field was justified, the review happened. The two years and the absence of any incident are the phase's content — this is the failure mode with no event to point at, which is why diligence does not prevent it and why the countermeasure has to be a narrowing rather than a warning. **The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition** and is chosen because it compresses the instructor case into one prompt, because the agent's output is defensible at every line, and because the room is about to produce the same artefact in phase 5 step 4.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents **their step 1 crossings and their step 4 reduced schema.**

The partner has two obligations and both are required.

- **Find one crossing they did not mark**, and say what could be authored there and by whom.
- **Name the capability the reduced schema no longer serves**, and state whether a real substrate user makes that request — **from the substrate's own request log, which is available in the room, rather than from judgement.**

Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 3, both outcomes are recorded in the artefact.

Per instrumentation rule 5 as amended at [WP-054](wiki/whitepapers/WP-054.md) §8, the dual-defeat construction reuses [S068](wiki/seminars/S068.md) phase 7's and **its use here is contingent** on S068's reported outcome; a reported failure there retracts it here along with every other contingent reuse.

**Warrant.** Interactive-tier articulation with a dual demand, attacking the enumeration and the reduction separately because they fail in opposite directions — an unmarked crossing is under-caution and an over-reduced schema is over-caution, and a student who is defeated on both has learned where the trade sits. **The second obligation is answered from the request log rather than from the partner's opinion**, per instrumentation rule 1: the record of what users actually ask for is present in the room for other reasons and the judgement is its to make, not a peer's.

## Assessment

**One specification item**, in IS302 with SG302. Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 1, the checked elements are: every crossing marked on the [S072](wiki/seminars/S072.md) drawing with its author and whether that author is identifiable; the three-part contract for the highest-consequence tool with each clause marked enforced or prose and the enforcing mechanism named; **the deployed reduced schema** with its cost stated as a real request and whether a user makes it; **an enforcement point at a named boundary or an accepted re-declaration with probability, consequence, confidence and provenance in the same field, for every [S071](wiki/seminars/S071.md) prohibition and every [S072](wiki/seminars/S072.md) breach path, each enforcement point carrying the SY301 material used to identify it**; the pre-committed step 6 prediction; the boundary inventory against the student's markings with the accidentally-covered crossings identified; **the attempted prohibited call with its outcome and, where refused, the mechanism that refused it**; both phase 7 outcomes; **the prompt record**; **the intervention record**; and **the frontier statement**. **Nothing else is assessed.**

**An [S071](wiki/seminars/S071.md) prohibition or an [S072](wiki/seminars/S072.md) breach path with neither an enforcement point nor an accepted re-declaration fails.** This is the day's single hard requirement and it is the element two prior days' instruments were named for.

**An enforcement point that cannot be located on the drawing fails.** Naming a mechanism is not placing one, and this is the condition [WP-071](wiki/whitepapers/WP-071.md) §5 predicted experienced students would fail.

**A contract clause marked enforced without naming which of the four enforces it fails.** **A clause whose named enforcement is an annotation fails**, per point 9: a hint is a declaration and not one of the four, and marking it enforced is the day's central error committed in a single field.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error; a schema narrow enough that the error is unexpressible qualifies.

No entrustment judgement. The quarter's is at [S080](wiki/seminars/S080.md), and [M15](wiki/modules/M15.md) carries none for the reason published on [Q8](wiki/quarters/Q8.md).

**Disposition observed:** integrity, evidenced by whether the enforcement points named at step 5 exist and by whether an honest accepted re-declaration was chosen over an invented mechanism. Recorded in narrative within the activity, never scored as one.

**Rule-6 discharge.** Two obligations land on this day and **both elements exist.**

- **[S071](wiki/seminars/S071.md) named this day's phase 5 step 5** as the response occasion for its step 4 unenforced-boundary count, specifying that every blank acquire an enforcement point at a named boundary or be re-declared as accepted with probability, consequence and confidence in the same field. **The element exists as step 5, it is a checked element, it is the day's single hard requirement, and the cohort's three-way split — enforced, accepted, neither — is reported at phase 8.** The obligation is discharged.
- **[S072](wiki/seminars/S072.md) named this day's phase 5 step 5** as the response occasion for its count of realised paths touching a prohibited action. **The element exists as the second clause of step 5: the breach paths are carried in by name and each must be closed the same way, and they are reported at phase 8 under the same split.** The obligation is discharged. The two obligations land on one element deliberately — a prohibition and a path that crosses it are the same problem from two directions, and closing them separately would produce two documents that disagree.

**An older forward link discharged.** [WP-006](wiki/whitepapers/WP-006.md) §6 named this day, at roughly six quarters, on the claim that a tool boundary is an interface whose preconditions cannot be enforced because the caller is a language model. **That is point 1, and it is the day's opening rather than a mention.** [WP-034](wiki/whitepapers/WP-034.md) §9 carried its item 4 two-directional documentation gap here as the cohort's contract-reading baseline; **that is phase 1 item 1, and both rates are reported together at phase 8** rather than the new one alone.

**Instrumentation under rule 6.** Two instruments with named response occasions:

- **The step 1 crossing-count error** — marked crossings against the substrate's boundary inventory, per student, with the misses grouped by what authors the content there. **Response occasion: [S074](wiki/seminars/S074.md), phase 5 step 1**, where every crossing the student failed to mark must be classified by the failure shape it could produce, so that the decomposition is exercised on the enumeration's own blind spot.
- **The step 4 schema-reduction cost** — what capability each student gave up, and how many gave up nothing. **Response occasion: [S076](wiki/seminars/S076.md), phase 3**, whose injection cases must include one that the cohort's narrowest schema still admits, selected against the reduction this cohort was least willing to make.

**[WP-074](wiki/whitepapers/WP-074.md) §7 and [WP-076](wiki/whitepapers/WP-076.md) §7 must report whether those elements exist**, per the commitment [WP-051](wiki/whitepapers/WP-051.md) §8 established.

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| A tool boundary is a contract with a caller who will not read it | The tool description field, and where an agent writes a prohibition |
| Four things are enforceable, with two named omissions | Schema validation, scoped permissions, callee preconditions, the 100-second call timeout |
| The boundary of trust is a place | The point in a runtime at which an approval decision is or is not taken |
| A declaration is not an enforcement | Tool annotations, called *hints* by the documentation that defines them |
| A tool that wraps an agent is not a tool | Agent-to-agent delegation, and the identity the delegate holds |
| For any protocol, state which of the four it carries | MCP, whose annotations carry none of them |
| Consent requires an enumerable action set | `allowed_tools`, and its default of everything |

- **Perishable in full:** every protocol version, annotation name, configuration field, schema language and timeout value used today, including all six annotations at point 9 and all three defaults at point 10; the four boundaries of phase 3 and all their figures; and the substrate's current permission model. **Point 7 is written so that the protocol layer can be replaced entirely without changing what is assessed**, and the material states this to students rather than only to the reader of this page.
- **Local:** the substrate's tool specifications and call logs, its boundary inventory, its request log used at phase 7, the phase 6 free-text-field case, the phase 6 agent case, and the four boundaries as configured this term.
- **Assessed:** the left-hand column only. **A student is never assessed on which annotations exist**; they are assessed on being able to say that an annotation is a declaration and to name what would have enforced the same thing.
