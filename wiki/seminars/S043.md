# S043 · Tests as the Specification

**Module:** [M09](/wiki/modules/M09.md) · **Quarter:** [Q5](/wiki/quarters/Q5.md) · **Complexity class:** 3
**Strands:** PE · ME
**Platform anchor:** An executable specification for conversation behaviour — the Microsoft 365 Agents Playground's headless conversation driver, deterministic and model-free in CI, beside the evaluator catalogue it neither reaches nor mentions
**Whitepaper:** [WP-043](/wiki/whitepapers/WP-043.md)

**Entry state:** either

## The situation

The open playbook states two rules about tests that are unusual for their bluntness. Code is **incomplete** if it is not accompanied by tests. Tests are committed in the **same change** as the code they cover, and *I will add tests next* is recorded on that page as not acceptable.

Both are ordinary engineering hygiene and neither is why this session exists.

This session exists because of a single piece of practitioner testimony held in the internal corpus, in speaker notes, contradicting the collection's own headline. On a mature production codebase, the assistant **could not** be asked to add a feature end to end: the generated code reused outdated patterns and ignored architectural constraints. The workaround was to **make failing tests the specification and spend most of the human effort there.**

The same collection's customer-facing material describes end-to-end feature delivery as the model's signature achievement. **Neither document notices the other.**

Answer these before instruction.

1. Write down what *done* means for one behaviour in your slice, in a form something other than you could check.
2. Which of your architectural constraints could a test catch, and which could only a person catch?
3. Hand the implementation to somebody who has never seen this codebase. What do they get wrong first?
4. What does a test suite that passes on wrong code look like?
5. If the implementation becomes cheap, where does the human effort go?

**Item 5 is the session's centre of gravity.** The testimony's answer is *into the specification*, and that is a redistribution of effort rather than a saving. Nothing in the collection prices the redistribution, and neither does this session.

## What you must produce

**A failing specification** for one behaviour in your slice, written before the implementation exists.

- The behaviour, expressed as checks that currently fail for the right reason.
- **The untestable residue** — every constraint from item 2 that no check can express, each with the review lens that would catch it instead, and who would have to hold that lens.
- A statement of what the specification does **not** constrain, so that a reader knows what an implementation is free to do.
- One deliberate wrong implementation that passes your specification, and the check you added because of it.

## The material

### The test set is the requirement, and the prose is commentary

The openly published playbook states two testing norms in the first person plural, as commitments the organisation binds itself to rather than as advice: **"We consider code to be incomplete if it is not accompanied by tests"** and **"We write our tests early and block any further code merging if tests fail."** The reviewer page closes the usual loophole outright: **"Tests should always be committed in the same PR as the code itself ('I'll add tests next' is not acceptable)."** ([research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), pages read 2026-07-30.)

That is ordinary engineering hygiene and it is not why this session exists.

This session exists because of what happens when the implementation stops being the expensive part. **When generating a plausible implementation costs less than writing down what the implementation must do, the specification becomes the artefact under time pressure**, and prose specifications do not survive that pressure because nothing checks them. A written requirement can be satisfied by an implementation that does something else, and nobody finds out until somebody reads both carefully, which is the thing nobody has time for.

The practitioner literature's response is a decomposition rather than an exhortation. Break the system's scope into **features** — what it can do — and **scenarios** — the situations each feature must handle — and turn each scenario into an assertion ([research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md](/research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md)). The decomposition is what makes the suite diagnostic rather than merely red or green: a failing scenario names the situation that broke, and a suite organised any other way names only that something did.

That source also breaks with software-testing convention in a way this session adopts. **"Unlike traditional unit tests, you don't necessarily need a 100% pass rate. Your pass rate is a product decision."** Copying the everything-green habit into this setting is a category error: the question is not whether every check passes but whether the failures you are shipping are the ones you chose. **Limits:** a practitioner essay resting on a single company's case study, with no control condition, no measured improvement and no released dataset; its tooling recommendations are dated and will drift; and one figure it uses is explicitly the author's rhetorical estimate rather than a measurement.

The same author supplies the discipline that makes any of this trustworthy. An automated judge is itself a measurement instrument requiring its own evaluation against human labels, run in small batches with paired human and model critiques — and reported carefully, because **"using raw agreement is generally not recommended and can be misleading when classes are imbalanced. Instead, you should typically measure precision and recall separately."**

### Criteria drift: you cannot write the specification before you have seen the outputs

This is the finding that stops *specification first* from being a slogan, and it is uncomfortable in exactly the right way.

The research naming it puts the circularity plainly: **"users need criteria to grade outputs, but grading outputs helps users define criteria"** ([research/03-measurement-evaluation/shankar-evalgen.md](/research/03-measurement-evaluation/shankar-evalgen.md)). It is not a symptom of a disorganised team. It is structural. And the sharper half of the finding is that some criteria appear to be **dependent on the specific outputs observed** rather than independently definable in advance, which the authors say "raises serious questions for approaches that assume the independence of evaluation from observation of model outputs."

Take that seriously and two things follow for your artefact. **First, a specification whose criteria never moved was not examined.** A rubric authored in week one and applied unchanged is not evidence of discipline; it is evidence that nobody looked at outputs. **Second, the revision must be versioned rather than silent**, because if criteria are revised after seeing outputs, those same outputs can no longer serve as a clean held-out set — a cost the source itself does not resolve, and one your specification has to handle by freezing a version and holding out fresh cases before any claim that matters.

The same work supplies the question this whole session inherits: **who validates the validators?** Using a generated instrument to check generated output does not solve the trust problem. It relocates it.

**Limits:** the evidence for criteria drift is qualitative, from a small interface study; the paper establishes that the phenomenon is real and consequential and does not quantify how often or how much; and the tool it describes is a research prototype from 2024.

### The split strategy decides what your number means, silently

Here is the platform's most transferable idea, and it is one line of configuration that most teams never choose deliberately.

An evaluation of a multi-turn interaction has to cut the conversation into a query half and a response half before anything can be scored, and the documentation states the consequence without hedging: **"Multi-turn conversations must be split into query and response halves for evaluation. How you split determines *what you're evaluating*."** Three strategies are published. **Last turn**, the default, splits at the last user message and suits "response quality at a specific point". **Full** treats the first user message as the query and everything after as the response, and suits "task completion and overall trajectory". **Per-turn** scores each exchange independently with cumulative context ([research/06-microsoft-platform/agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md)).

**An agent that recovers well from a bad first attempt scores well under Full and badly under Per-turn. Neither score is wrong. They answer different questions**, and a team that never chose is reporting an answer to a question it did not ask. The generalisation is the thing to carry out of the session and out of the decade: **the unit of analysis is a choice, and it silently determines what the number means.** Your specification must name its split and defend it, because a reader who does not know the split cannot interpret the result.

The framework's other structural idea is a cost gradient expressed directly in the API. A **local evaluator** "runs checks locally without API calls — ideal for inner-loop development, CI smoke tests, and fast iteration"; a cloud evaluator runs judged evaluation and returns dashboards; **the two can be mixed in a single run.** That is the same ladder the measurement literature argues for in the abstract — cheap deterministic checks constantly, expensive judged checks periodically — and having it in the type system means the architecture carries the discipline rather than a policy document.

Defaults are opinions. The cloud evaluator defaults to relevance, coherence and task adherence, and **"when items contain tool definitions, it automatically adds tool call accuracy"** — which says that an agent with tools has acquired an obligation an agent without them does not have.

### Four ways a tool call fails, two of which report success

The catalogue decomposes tool usage into five evaluators, and the decomposition is a debugging vocabulary worth more than the evaluators. `tool_selection` catches choosing the wrong tool. `tool_input_accuracy` catches calling the right tool with the wrong arguments. `tool_call_success` catches the call failing technically. `tool_output_utilization` catches ignoring or misreading a successful result. `tool_call_accuracy` covers "the overall quality of tool calls including selection, parameter correctness, and efficiency".

**Two of those — wrong arguments and ignored output — produce a system that reports success and is wrong**, which is the failure class hardest to detect in production and the one your specification is most likely to miss. A single *did the tool work* check conflates all five.

One evaluator in the catalogue is worth naming separately because it is the only deterministic one. `task_navigation_efficiency` takes `actions` and `expected_actions` and **requires no model parameter**, so its result does not depend on a judge. Everything else in the agent-behaviour group does.

The output format carries a design decision the session leans on. Results come back as pass or fail with a `reason` string, plus a numeric `score` for the evaluators that use a scale before thresholding. **The threshold is a policy choice separable from the measurement, and moving it changes the pass rate without changing the system** — so a threshold must be justified rather than inherited. The `reason` field is what makes a judgement auditable rather than merely numeric.

**The limits here are the heaviest in this session and the most consequential.** The documentation was read through search excerpts rather than full page fetches; many evaluators are marked **preview**; one consulted page is a superseded **classic** variant; API surfaces differ across languages and examples are not interchangeable; cloud evaluation requires a project with a model deployment and costs money. And the decisive one: **no agreement rates with human judgement are published for any evaluator, no calibration data, and no account of where the default thresholds came from.** Treat the documentation as an accurate description of what the tooling computes and as no evidence at all that what it computes is right. **Assert no evaluator's agreement with human judgement anywhere**; none is published, and inventing one is the exact failure this programme exists to prevent.

### A specification that runs in CI with no model in the loop, and the seam nobody marks

Everything above is judged evaluation, and judged evaluation is expensive, slow and stochastic. **Before any of it there is a cheaper layer, and it is the one that actually behaves like a specification**, because it is deterministic, it is fast, and its result does not depend on anybody's opinion.

The vendor's toolchain ships a local sandbox that removes three dependencies from the inner loop — **a licensed tenant, a tunnelling service and an application registration** — by emulating the client and the connector service with mock data ([research/06-microsoft-platform/agents-toolkit-and-sdk-family.md](/research/06-microsoft-platform/agents-toolkit-and-sdk-family.md)). Alongside it, and documented not on the vendor's public pages but inside a shipped editor extension, is the part that matters here: a **headless conversation driver**. It exposes a test client that drives multi-turn conversations against the agent's endpoint, an operation to start a fresh conversation so each case is isolated, and a response object carrying **text, attachments, suggested actions and a type**. A companion HTTP facade lets a runner in any language post a scenario of turns and read back a per-turn status of **completed, timed out, errored or skipped**.

**That is an executable specification for conversation behaviour, and it is the only deterministic, fast, model-free assertion layer the toolchain has.** It runs on every commit. It costs nothing per run. It does not need a judge, a threshold or a repetition count, because it is not measuring anything — it is asserting. **Which is exactly why it belongs in this session and exactly what makes it dangerous.**

**A conversation driver is not an evaluator. It scores nothing, and nothing in the toolchain does.** The validation command checks a manifest against schema and rules; the driver drives conversations and asserts on what comes back. **Nothing anywhere in that toolchain scores agent quality, nothing connects to the evaluator catalogue this session's earlier material describes, and — the part to sit with — no page acknowledges the gap or tells a developer where to go next.** The seam between *my agent is valid* and *my agent is any good* is unbridged and unmarked.

**The unmarked seam is the teaching point, not a complaint.** A toolchain that stated the gap would be handing you the boundary of its own claim, which is what good documentation does elsewhere in the same family. This one does not, so a team that gets its conversation tests green has satisfied every quality signal the toolchain offers and has measured nothing. **That is this session's thesis arriving as a product decision:** a passing specification establishes that the agent behaves as specified, and nothing whatever about whether the specification was right.

The sandbox is better behaved about its own limits than about that one, and the contrast is instructive. **It publishes what it cannot emulate** — manifest-driven features are not processed at all; only one card type is supported and four of that card type's features are excluded by name; mobile and meeting experiences are unsupported; and a comparison table lists typing indicators, tabs, message extensions, dialogs and single sign-on as unavailable. **A sandbox that publishes its own limitations is worth more than one that does not**, because you can write down what your green run did *not* cover. Two further facts belong beside it. **The default channel differs by launch route** — the convenient path emulates a less faithful channel than the manual one, silently, and the documentation states the fact without stating the cost. And the mock configuration **requires exactly five users, with no rationale published anywhere.**

**The limits, and one of them is the reason this whole subsection carries a health warning.** The driver interface is documented **inside an editor extension rather than on any published page** — it has no public URL, no currency guarantee, and is cited only by extension version. **Six pages of the surrounding family were fetched and read in full; roughly thirty more were reached only through search excerpts**, so no list here is exhaustive. **Every principal name in this area has changed at least once and one package twice**, and two package names for the sandbox appear simultaneously on live pages, so a course that picks one will be wrong for some readers. And the decisive silence: **no evidence is published that the sandbox predicts deployed behaviour.** A *capability* difference table exists and is valuable. A *fidelity* claim does not exist anywhere — nothing states how often an agent that passes locally behaves differently in a real tenant, and the quieter default channel makes that question sharper rather than softer.

### A gate that fires on a difference smaller than its own noise is theatre

A specification that is executable is a measurement, and it inherits every limit of one.

An evaluation is an experiment. A reported score needs a standard error and a count, and where cases arrive in related groups it needs a clustered one ([research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md)). Three of that source's disciplines bear directly on a specification you intend to gate on.

**Power analysis before the run** turns *we tested and found nothing* into a statement about the system rather than about the test. **Paired comparison** on the same cases removes the variation two versions share and costs nothing, because they agree about which cases are hard. And **"Don't touch the thermostat!"** — suppressing variance by lowering a sampling temperature whose purpose is something else shifts what is being measured rather than measuring it better, and can move variance into the component you cannot reduce.

The platform supplies the corresponding mechanism and names its purpose exactly: **repetitions run each query multiple times "to detect non-deterministic behavior"**, which is the acknowledgement that one sample from a stochastic system is not a measurement.

**Limits:** that measurement source is analytical rather than empirical; its illustrative magnitudes rest on stylised assumptions; and it addresses comparing scores rather than choosing what to score, so a tight interval around a badly chosen criterion is still meaningless. **No number from it appears here.**

### Error framing works when the task gives readable feedback, and this one does not always

The session's third movement asks you to build a wrong implementation on purpose, and the design's warrant for that is the error-management literature rather than intuition.

That literature's method has two elements: minimal guidance, so learners work independently on difficult tasks and make many errors, and explicit instructions that errors are informative rather than shameful, delivered while **no further assistance is given when an error occurs** ([research/04-professional-formation/keith-frese-error-management-training.md](/research/04-professional-formation/keith-frese-error-management-training.md)). The meta-analysis supports the approach for transfer to genuinely novel tasks and finds no advantage on performance measured during training itself.

**The moderator that matters most here is the one people skip.** Because the method withholds guidance, the task must supply clearly interpretable feedback of its own; where feedback cannot be readily interpreted, the method may be worse than instruction. **The authors' own verdict is that this hypothesis "received only limited support"** and that it cannot be concluded the method works only when task feedback is clear — the moderator test did not reach significance and its coding had low interrater reliability.

Carry it as a design caution rather than as a finding. **A failing check is clear feedback. A judged score with no `reason` field is not.** That is the operational reason this session insists your specification's judged components carry their reasons, and the reason the wrong-implementation exercise is built around checks that go green rather than around scores that go up.

**Further limits:** every study in that pool compared one training method against another, never against no training, so all effects are relative; **no study measured on-the-job performance**; almost all taught software skills in a laboratory; and the overall pool was not statistically heterogeneous, so the moderators were theory-driven partitions rather than partitions the data demanded. **No effect size from it appears here.**

## The workflow

**Write the specification as a dataset, run it against nothing, then run it against something wrong.**

**Step 1 — decompose before you assert.** Write the features and scenarios grid for one behaviour in your slice from [S041](/wiki/seminars/S041.md), on paper, before you open an editor. A suite that is not organised by scenario cannot tell you what broke.

**Step 2 — write the dataset. This is the specification.** Test data is JSONL; simple string fields suffice for straightforward cases, and conversation arrays in the published schema are required where tool calls are involved.

```jsonl
{"id":"S1-one-match","query":"Straightforward case, single applicable rule.","expected_tool_calls":[{"name":"case_file_read","args":{"case_id":"A-1"}}],"ground_truth":"Recommends award, cites the single applicable paragraph."}
{"id":"S2-no-match","query":"No rule applies.","expected_tool_calls":[{"name":"case_file_read","args":{"case_id":"A-2"}}],"ground_truth":"Declines to recommend and says which paragraph it checked."}
{"id":"S3-ambiguous","query":"Two rules apply and conflict.","expected_tool_calls":[],"ground_truth":"Escalates. Does not choose."}
{"id":"S4-tool-down","query":"Case file unavailable.","expected_tool_calls":[{"name":"case_file_read","args":{"case_id":"A-4"}}],"ground_truth":"Reports that it could not read the file. Does NOT recommend from memory."}
```

```yaml
# evals/first-slice.eval.yaml  -- the specification's own configuration is part of the specification
split_strategy: full          # last_turn | full | per_turn -- CHOOSE, then defend below
split_rationale: >
  We are specifying task completion, not turn-level quality. An agent that recovers
  from a bad first attempt should pass. Under per_turn it would not. Stating this
  is mandatory: the split silently determines what the score means.
repetitions: 5                # one sample from a stochastic system is not a measurement
local_checks:                 # deterministic, no API calls, runs on every commit
  - name: no_recommendation_without_citation
    assert: "every recommendation contains at least one paragraph reference"
  - name: never_recommends_when_tool_failed
    assert: "if tool_call_success is false, output contains no recommendation"
judged_evaluators:            # expensive; runs on a cadence, not on every commit
  - tool_call_success
  - tool_input_accuracy       # right tool, wrong arguments -- reports success, is wrong
  - tool_output_utilization   # read the result and ignored it -- reports success, is wrong
  - task_adherence
thresholds:
  tool_input_accuracy:
    value: 3
    justification: "NOT inherited. Set after hand-labelling 30 traces; see docs/threshold.md."
untestable_residue:           # no check expresses these. Each needs a person.
  - constraint: "Recommendations must not restate the applicant's protected characteristics."
    lens: "Adjudication policy review"
    holder: "Head of adjudication policy"
  - constraint: "Escalation wording must not imply a decision has been taken."
    lens: "Communications review"
    holder: "Named case officer"
```

**Step 3 — run it and watch it fail for the right reason.** A check that fails because nothing compiles has specified nothing. **A specification you have not seen fail is a hypothesis about a specification.**

**Step 4 — build the wrong implementation on purpose.** Satisfy the specification badly: the least defensible thing that goes green. You are looking for the gap between *passes* and *correct*, and the gap is where the untestable residue lives. **This is the session's most productive twenty minutes and the one learners skip**, because building something you intend to throw away feels like waste when the checks are already green.

**Step 5 — add the check the wrong implementation forced, and record which criterion you had not been able to state until you saw an output.** That entry is criteria drift, caught and dated, and it is the honest version of specification-first work.

**Step 6 — delegate it and record what came back wrong.** Give the specification and nothing else to an executor that has not seen your codebase. Record what they got wrong. **That record is your specification's only available quality measurement.**

**Step 7 — turn the instrument on the specification rather than on the code.** Give the agent your dataset and the untestable residue, and instruct it to write an implementation that passes every check and violates the residue, then to name the check it would have had to break. Then instruct it to argue that three of your scenarios are the same scenario. Keep what is better than your own reasoning; record what you rejected. **An agent that produced a correct implementation was given a specification that was already doing the work, which is the outcome you wanted and the one that teaches you least.**

**Step 8 — write the half of the specification that needs no model, and make it run on every commit.** Everything above this step costs money, takes minutes and returns a different answer each time. **The conversation-behaviour half costs nothing, takes seconds and returns the same answer**, so it belongs in the pipeline rather than on a cadence — and writing it is where you discover which of your requirements were about behaviour and which were about quality.

```javascript
// tests/conversation.spec.js   <- SHAPE, NOT SCHEMA. The driver is documented inside an
// editor extension rather than on any published page: no public URL, no currency
// guarantee. Verify the interface against the extension version you have, and record it.
// EXTENSION VERSION CHECKED: <fill this in, or the test below is a claim about nothing>

const client = newTestClient({ endpoint: 'http://localhost:<port>/api/messages' });

test('S4 — tool down: reports the failure and does NOT recommend from memory', async () => {
  await client.newConversation();                 // isolate the case, always
  const r = await client.send('Draft a recommendation for case A-4.');
  expect(r.text).toMatch(/could not read/i);
  expect(r.text).not.toMatch(/recommend/i);       // the assertion that carries the risk
});

test('S3 — conflict: escalates and does not choose', async () => {
  await client.newConversation();
  const r = await client.send('Two rules apply and they conflict.');
  expect(r.text).toMatch(/escalat/i);
});

/* WHAT A GREEN RUN HERE ESTABLISHES ------------------------------------------
   That the agent behaves as specified, on this endpoint, in this emulated
   channel, for these turns. Nothing else.

   WHAT IT DOES NOT ESTABLISH -------------------------------------------------
   - That the specification was right. Nothing here scores quality, nothing in
     this toolchain does, and no page in it says so.
   - That it behaves this way in a real tenant. A capability difference table is
     published; a FIDELITY claim is not published anywhere.
   - Anything about the channel this run did not emulate. The convenient launch
     route emulates a less faithful channel than the manual one, by default.
   NOT COVERED BY THIS RUN, copied from the published limitations table:
     <list them here. This list is the deliverable, not the green tick.> */
```

**The comment block is the assessed artefact and the tests are the easy part.** Copy the sandbox's published limitations into it verbatim, because that table is the only honest account available of what your green run did not touch — and because it is a rehearsal for every simulator, emulator and staging environment you will meet for the rest of your career, most of which publish no such table at all.

**What this makes observable that prose cannot.** That the difference between a requirement and a wish is whether something other than a person can tell they have been met — and that the difference shows up in minutes, in a run, rather than in a fortnight, in a disagreement. **You will also see the split strategy change your result without changing your system**, which is the single most useful hour available on this topic.

## What good looks like

- **The checks fail before the implementation and fail for the stated reason.** A check that fails because the code does not compile has not specified anything yet.
- **At least one architectural constraint is expressed as an executable check**, not merely named.
- **The untestable residue is non-empty and each entry has an owner.** A specification with nothing outside it has not been examined.
- **The wrong implementation is genuinely wrong and genuinely passes.** Producing it is the assessed thinking, not a formality.
- **The specification is legible to somebody who has not seen the codebase**, and this is checked rather than asserted.
- **Nothing in the specification depends on who reads it.** A specification that only works when a human reads it is not a specification.
- **The split strategy is named and defended in the artefact**, not left at its default, because a reader who does not know the split cannot interpret the result.
- **Every threshold carries a justification that is not "the default".** A threshold is policy; moving it changes the pass rate without changing the system.
- **At least one criterion is recorded as having been unstatable until an output was seen**, with the date. A specification whose criteria never moved was not examined.

## How it goes wrong

- **The retrofitted test** — written after the implementation, shaped by it, incapable of failing on it. *Warning sign:* you have never seen it red.
- **The tautological check** — it asserts what the code does rather than what the behaviour requires. *Warning sign:* changing the requirement would not change the check.
- **The shape check** — it asserts that output has the right form and says nothing about whether it is right. *Warning sign:* your check would pass on a plausible-looking wrong answer.
- **The declared-absent constraint** — an architectural rule that cannot be expressed as a check is quietly dropped rather than moved to the residue. *Warning sign:* your residue is empty.
- **The specification only its author can read** — it encodes context nobody else has. *Warning sign:* explaining it takes longer than reading it.
- **The effort that vanished** — the implementation got cheap, the specification did not get more effort, and nobody noticed where the work went. *Warning sign:* the specification took less time than the implementation.
- **The unchosen unit** — the conversation was split at the default and the number is reported as though the split were a fact about the system. *Warning sign:* you cannot say what would happen to your score under a different split.
- **The inherited threshold** — a pass line arrived with the tooling and was never justified, so the gate's strictness is somebody else's opinion. *Warning sign:* your threshold is a round number you did not choose.
- **The unvalidated judge** — a generated instrument checks generated output and nobody has compared it against a human label. *Warning sign:* you can report a score and not a disagreement rate.

## Exercises

**None of these is assessed.** The specification, including its untestable residue and its holders, is carried into [S045](/wiki/seminars/S045.md), where the pack is checked for whether the holder actually looked.

**1 · Score one trace under all three split strategies and reconcile the results.** Take one multi-turn interaction from your slice, run it under last-turn, full and per-turn, and write the sentence that explains the difference.

> **What you should find.** That an agent which recovers from a bad first attempt does well under full and badly under per-turn, and that neither score is wrong. **They answer different questions.** The documented statement is exact — how you split determines what you are evaluating — and the generalisation is the part worth keeping when the product name changes: **the unit of analysis is a choice, and it silently determines what the number means.** If you reported one score without naming its split, you reported an answer to a question you did not ask.

**2 · Build a wrong implementation that passes, then say which check you had to add.** The least defensible code that goes green.

> **Scoring criterion.** It passes if the wrong implementation is genuinely wrong and genuinely passes, and if the check you added afterwards would catch it without also catching correct implementations. **A wrong implementation that fails your suite proves nothing except that you already had the check.** Note where the gap lived: most learners find it in outputs whose *shape* was constrained and whose *content* was not, which is the shape check named in this session's failure list.

**3 · Go back to your own item 5, then break it.** Find what you wrote for opening item 5 — where the human effort goes if the implementation becomes cheap. **Do not rewrite it yet.** Put it beside the criterion below and write one sentence naming the difference.

> **Criterion.** The answer this session teaches is that the effort moves **into the specification and into the residue that no specification can express**, and that this is a redistribution rather than a saving. Nothing in the sources prices the redistribution and neither does this session. **If you wrote that the effort goes into review, you named the next session and not this one** — review is where the residue is discharged, and [S044](/wiki/seminars/S044.md) will ask you what that costs. If you wrote that the effort disappears, notice that you have made the strongest available claim on no evidence, which is the failure the whole programme is organised against.
>
> **Why the comparison step is mandatory rather than encouraged.** The research this session's structure rests on tested exactly this: showing learners a correct answer next to their own wrong one produced no benefit, and only the group *instructed to compare them* learned more ([research/04-professional-formation/sinha-kapur-productive-failure.md](/research/04-professional-formation/sinha-kapur-productive-failure.md)). Reading the criterion is not the exercise. Naming the difference between it and what you wrote is. **School, university and laboratory evidence; no adult-professional study in its reference list.**

**4 · Validate one validator.** Hand-label a set of traces yourself, run one judged evaluator over the same traces, and report the disagreement.

> **Scoring criterion.** It passes if you report the disagreement rather than the agreement, and if you report it in a form that survives class imbalance — **raw agreement is misleading when one class dominates, and precision and recall separately are the recommended form.** The exercise exists because the platform documentation **publishes no agreement rates with human judgement for any evaluator, no calibration data and no account of where its default thresholds came from.** That silence is not a reason to distrust the tooling. It is a reason to do this yourself, and to assert nothing about the tool's agreement that you have not measured.

**5 · Justify one threshold out loud.** Pick the threshold that most affects your gate and defend it to one colleague, who has one job: to ask what would change if you moved it by one.

> **What you should find.** That the pass rate moves and the system does not, which is the whole point: **the threshold is policy and the score is measurement, and they are separable.** A defence that appeals to the default has not defended anything. A defence that names the cases which sit either side of the line, and says which of those you are willing to ship, has. Add the repetitions question while you are there — **if a single run decides a gate, the gate is deciding partly on sampling noise**, which is why the platform's repetitions mechanism exists and says so in its own documentation.

**6 · Find the criterion you could not have written down.** Read a set of your own outputs and write the criterion that only became statable after you saw them. Date it.

> **What to notice.** That you have just reproduced the finding this session's specification discipline rests on — **users need criteria to grade outputs, but grading outputs helps users define criteria** — and that the circularity is structural rather than a symptom of poor planning. **The cost is real and the source does not resolve it:** those outputs can no longer serve as a clean held-out set for the criterion they produced. The discipline is to version the specification, record why each revision happened, and hold out fresh cases before any claim that matters. **The evidence for criteria drift is qualitative and from a small study; it establishes that the phenomenon is real and consequential, not how common it is.**

**7 · Get the conversation tests green, then write one paragraph on what green does not establish.** Run workflow step 8. Hand in the paragraph, not the tests.

> **Scoring criterion.** A pass names at least three separate things a green run leaves open: **that nothing in the toolchain scored quality** and no page in it admits the gap; that **no fidelity claim is published anywhere**, so passing locally licenses nothing about a real tenant; and that the emulated channel was a default somebody chose, and it is the less faithful one when the convenient launch route is used. **A fail is a paragraph about coverage percentages or about how the tests could be more thorough**, which answers a question about the suite rather than about the seam. The distinction this exercise installs is the one the whole session turns on: **a passing conversation test establishes that the agent behaves as specified, and nothing about whether the specification was right.**

**8 · Find the boundary between assertion and measurement, and put each of your requirements on one side of it.** Take your features-and-scenarios grid and mark each scenario *assertable* or *only judgeable*.

> **What you should find.** That the assertable ones are about **behaviour under a condition** — it escalated, it did not recommend, it cited a paragraph — and the judgeable ones are about **quality** — the recommendation was well reasoned, the tone was appropriate, the citation was the right one. **The first set can run on every commit with no model in the loop and no threshold to defend. The second set cannot, ever**, and every discipline in this session about splits, thresholds, repetitions and judge validation exists because of it. **The valuable discovery is usually that more of your specification is assertable than you assumed**, and that you had been reaching for a judge out of habit for things a deterministic check settles. **The dangerous discovery is the opposite**: a team whose whole grid is assertable has specified the shape of its outputs and not their content, which is the shape check in this session's failure list.

## What this does not establish

Nothing here shows that specification-first work produces better software, faster delivery or fewer defects.

The playbook states its testing norms as commitments and **supplies no comparative evidence**, and one of its pages reaches for a cost multiple attributed to an old study through a link that cannot be followed in any current browser. **That figure is not repeated here and is not a warrant for anything.**

**The practitioner testimony this session is built on is a single account.** It is the best-evidenced thing in its collection because it names a codebase property, a failure mechanism and a workaround that cost something — and it is still one engineer's experience, in speaker notes, with no measurement attached. It is treated here as a hypothesis worth teaching, not as a finding.

**What the session actually establishes is a conditional:** if you cannot state what *done* means in a form something other than you could check, you cannot delegate the behaviour and know whether you got it. That is close to a definition of delegation, and it is the strongest claim available.

The wrong-implementation exercise, the untestable-residue register and the requirement that residue entries carry an owner are **design reasoning with no external warrant.** So is the requirement that a specification record the date on which a criterion first became statable.

**The platform documentation is definitional and its silence on validation is the most important thing about it.** It was read through search excerpts rather than full page fetches; many evaluators are **preview** and one consulted page is a superseded **classic** variant; API surfaces differ across languages; and **no agreement rates with human judgement are published for any evaluator, no calibration data, and no account of where the default thresholds came from.** Treat it as an accurate description of what the tooling computes and as no evidence that what it computes is right. **No evaluator's agreement with human judgement is asserted anywhere in this wiki, because none is published.**

**The measurement source is analytical rather than empirical.** Its illustrative magnitudes rest on stylised assumptions, and it addresses comparing scores rather than choosing what to score, so a tight interval around a badly chosen criterion is still meaningless.

**The error-management evidence is relative and laboratory-bound.** Every study in the pool compared one training method against another rather than against no training; **no study measured on-the-job performance**; almost all taught software skills to students or recruited employees in a laboratory; and the moderator this session leans on hardest — that the task must give interpretable feedback — received, in the authors' own words, only limited support. **No effect size from it appears here.**
