# S016 · The Memory Hierarchy Is the Performance Model

**Module:** [M04](wiki/modules/M04.md) · **Quarter:** [Q2](wiki/quarters/Q2.md) · **Complexity class:** 2
**Strands:** SY · CF
**Whitepaper:** [WP-016](wiki/whitepapers/WP-016.md)
**Retrieves from:** S002, S003, S011
**Platform anchor:** Foundry embeddings (`text-embedding-3`) and Azure OpenAI prompt caching · **MCP servers:** Azure MCP Server (read) · Microsoft Learn MCP Server

---

## What this day is for

Four times in M03 the programme said that constant factors have physical causes and promised an explanation. This is it.

The cause is that **a memory access is not one operation**. It is one of several operations of wildly different cost, selected by where the data happens to be, and where the data happens to be is determined by what was accessed recently and how things are laid out. A program's performance is therefore a property of its **access pattern**, not of its operation count — and the access pattern is something the programmer controls and almost never thinks about.

S002 gave students a machine model with uniform-cost memory. That model was a deliberate simplification and today it is falsified, in front of them, on the machine they have been measuring all quarter.

And then it is falsified a second time, on a machine they are not standing next to. **A Foundry deployment has a memory hierarchy too**, it is documented, it is metered, and it obeys the same two properties. A prompt whose leading tokens are identical to a recent one is served from a cache of processed token computations; a prompt whose first character differs is not. The saving is reported back in the response body and it is charged for at a different rate. The hierarchy is not an analogy here. It is the bill.

## Phase 1 · Pretest and prediction (25 min)

Five items on the module's substrate component and its Foundry deployment.

1. Two loops perform the same number of operations on the same data in different orders. Predict the ratio of their running times.
2. A structure is changed from an array of records to a set of parallel arrays. Same data, same operations. Predict the effect.
3. Which of the S012 three terms does each of items 1 and 2 change?
4. Predict your item 1 ratio's accuracy: within a factor of two, ten, or worse.
5. **Copilot prediction, sealed.** You will shortly ask the agent to write a batching routine that embeds a large document set through a Foundry deployment as cheaply as possible. Write down what it will produce, and **name the one thing it will get wrong**. Sealed with items 1 to 4 and opened at phase 8.

Item 1's real ratio is far larger than almost anyone predicts. Item 5 is the day's contribution to the running frontier map, and the design's expectation is that a majority will predict the agent will get the limits wrong and a minority will predict *which* limit.

**Warrant.** Pretesting with a quantitative prediction on a phenomenon the students have measured the effects of for four days without being able to explain. Item 3 connects the day to S012 before any instruction. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8: an instrument administered after its answer has been taught measures recall.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups have a real Foundry chat deployment and an access token. They send four request layouts carrying **the same instructional content and asking the same question**, and they read `cached_tokens` under `prompt_tokens_details` in each response, together with the observed latency.

| Case | Layout |
|---|---|
| A | Stable content first — instructions and examples at the top, the variable question last |
| B | One changing token in the leading region — a timestamp at the very top, everything else identical to A |
| C | As A, but the identical leading region is extended by roughly eighty tokens of additional shared content |
| D | As A, issued after a gap longer than the cache retention window |

They predict the ranking and the cached-token counts, and commit.

Then the requests are sent — twice. Once with the group working alone against its own deployment, and once with the whole room issuing the same prefix at the same time, so that both the values and their stability are visible.

Task after: **explain case C's result**, which is neither the best nor the worst, and which returns exactly the same cached-token count as case A despite carrying more identical content.

**Warrant.** Contrasting cases along one controlled dimension with a measured adjudicator, now run against a metered service rather than read from a handout. Case C is the phase's payload — it cannot be explained without a block-transfer property, so a correct explanation of it is a correct model of the hierarchy. Case B is the day's cheapest surprise and case D introduces temporal locality as an observed eviction rather than a definition. The dual condition is the module's standing defence against benchmark reasoning, and here the loaded condition is produced by the room rather than supplied, which makes the contention its own.

## Phase 4 · Consolidating instruction (50 min)

1. **The hierarchy**, described by the only two properties that matter for reasoning: each level is faster and smaller than the one below, and data moves between levels in fixed-size blocks. Everything else is detail.
2. **Locality**, temporal and spatial, defined as properties of an access pattern rather than of a program.
3. **Why case C came out where it did,** from phase 3, worked completely. This is the day's central explanation. The documentation states that after the first 1,024 tokens, cache hits occur for every 128 additional identical tokens — which is property 2, in a vendor's own words, on a service that bills for it. Eighty extra identical tokens buy nothing; a hundred and thirty buy a block.
4. **The S012 movement term, resolved.** It was never a separate cost; it is the hierarchy's cost, and it is why comparison-count analysis fails.
5. **Layout as a decision.** Array-of-records against parallel arrays, indirection against inlining, padding against packing — each is a choice with an access pattern it serves and one it punishes. On the platform the same decision appears as where in the prompt you put the content that does not change, and as the vector width you ask an embedding model for.
6. **What the S002 model bought and what it discarded,** stated explicitly as the answer to phase 2's final item. Simplification is a representation choice and this one was made deliberately by the programme.
7. **Defaults are opinions.** Four were chosen for you today and none of them was announced. Prompt caching is **on by default** for supported models. The embeddings API returns `float` unless you ask for `base64`. Which retention policy applies depends on which model you deployed, not on anything you set. And requests are routed to a cache by a hash of the prompt's leading tokens — **typically the first 256, though the documentation says the exact length varies by model and does not say by how much.** An engineer who cannot state what was chosen for them does not understand their own system, and this generalises far beyond this vendor.
8. **Why measured numbers here are perishable and the reasoning is not.** Cache sizes change; the 1,024-token minimum and the 128-token block will change; the block-transfer structure does not. **And the two blocks do not have the same kind of cause.** A hardware cache line is a fixed width because a memory bus transfers a fixed width; a 128-token hit increment is a fixed width because somebody at a vendor decided so. The structure is the same and the reason is not, which is precisely why the structure is assessed and the number is not — and why this correspondence is safe for reasoning about where to put your stable content and unsafe for reasoning about why the boundary sits where it does, or about any other service by analogy.

**Warrant.** Consolidation indexed to phase 3's case C. Point 1 is deliberately minimal — two properties — because a hierarchy taught as a table of sizes is memorised, and one taught as two properties is reasoned with. Point 7 is the day's platform-specific content and satisfies the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s requirement that each day name a default the platform chose. Its final clause is also the day's first encounter with a documentation silence, and the silence is pointed out rather than papered over.

## Phase 5 · Whole-task learning task (90 min)

**Class 2. The layout is not given. This phase produces a build.**

Students use Copilot in agent mode, through the Azure MCP Server in read configuration, to ship a working embedding pipeline over a substrate corpus. They:

1. **Characterise the access pattern** in the terms of point 2 — for the corpus, and for the request shape the pipeline will issue.
2. **Choose a layout.** The vector width from the `dimensions` parameter, the wire format from `encoding_format`, and the batch shape. Any, including one not covered.
3. **Predict the effect** on each of S012's three terms, with numbers.
4. **Predict what the layout punishes** — the access pattern for which it is worse.
5. **Build and measure,** with the pipeline running alone and again while the room is running theirs.
6. **Reconcile,** naming the mis-modelled term if the prediction failed.
7. **State the condition** under which you would revisit the layout.

The batch shape is where the day bites. A single embeddings request accepts an array of up to 2,048 inputs, each input is capped at the model's 8,192-token limit, and **the request additionally fails with HTTP 400 if the sum across all inputs exceeds 300,000 tokens** — a limit that is satisfied by every individual input and violated by the batch. A pipeline that respects the per-item limit and not the aggregate one works on small corpora and fails on large ones.

**The artefact carries three further elements**, per the Copilot Practice Standard.

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the pipeline's own checks would have caught an intervention-worthy error — a batch-size assertion against the aggregate limit is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 1's characterisation is worked with the room; step 3's prediction template is supplied. Steps 2, 4 and 7 are unsupported, per the module's position.

**Warrant.** Whole-task at class 2, now shipping rather than describing. Step 4 is the day's discriminator — a layout choice without a named punished pattern is a preference. Step 5's dual measurement is the module's standing defence against idle-machine reasoning. The intervention record is the element that distinguishes a student who directed the build from one who accepted it, and its fail condition is written with the sensitivity escape [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate change that improved a benchmark by a large factor and production by nothing — with attention to the difference between the benchmark's working set and production's.

Then the agent case: a Copilot-generated batching routine that was **confidently wrong and passed review**. It chunked correctly, respected the per-input token limit, handled retries, and read as competent work — and it batched by item count alone, so it succeeded on every test corpus and failed on the first real one. Attention goes to why review did not catch it: the reviewer checked the limit they knew about, the code cited a limit, and the two were not the same limit.

Then students: a performance measurement you took that did not predict anything, or a place today where you accepted agent output you had not checked.

**Warrant.** Error management. The instructor disclosure targets the module's standing error rather than the day's specific content, deliberately, because the standing error is what the module exists to prevent. The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen so that the failure is invisible to the review the students would actually have performed.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student states their step 4 punished pattern, and the partner's task is to **find that pattern in the substrate** — in an existing caller, a scheduled job, a plausible feature, or a request shape the pipeline will meet next term.

If they find it, the pair decides whether the layout choice still stands.

**Warrant.** Interactive-tier articulation with a realism demand, now the module's third instance and expected to require no framing.

## Phase 8 · Calibration and commitment (20 min)

- Items 1 and 4 resolved: predicted ratios against measured, and the distribution of accuracy bands.
- Step 3's numeric predictions against measured, as ratios.
- **Item 5 opened.** The sealed Copilot predictions are read against what the agent actually did, and the cohort's hit rate is recorded. Both halves count: predicting that the agent would err is easy, and naming the error is the measure.
- Each student names one structure in their own current work whose layout they chose without considering access.

## Assessment

Specification item in SY102. Checked elements: the characterised access pattern; the layout choice; three-term numeric predictions; the named punished pattern; dual measurements; the reconciliation; the revisit condition; the prompt record; the intervention record; the frontier statement.

**A layout choice with no named punished pattern fails the specification.** **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error.

Nothing else is assessed.

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| Each level is faster and smaller than the one below | The prompt cache as a tier above model recomputation |
| Data moves between levels in fixed-size blocks | The 1,024-token minimum and the 128-token hit increment |
| Locality is a property of an access pattern | Prefix stability, and the cache retention window |
| Layout is a decision with a punished pattern | `dimensions`, `encoding_format`, and batch shape |
| The movement term is the hierarchy's cost | Cached tokens billed at a different rate from uncached |

All cache sizes, block sizes, level counts, token limits and measured latencies are **perishable** and are marked at point 8 explicitly. The two hierarchy properties, locality, layout as a decision, and the resolution of the movement term are durable and are what the specification assesses.
