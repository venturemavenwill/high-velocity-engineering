# S041 · Generalisation Is the Only Thing That Matters

**Module:** [M09](wiki/modules/M09.md) · **Quarter:** [Q5](wiki/quarters/Q5.md) · **Complexity class:** 3
**Strands:** IS · ME · MS
**Whitepaper:** [WP-041](wiki/whitepapers/WP-041.md)
**Retrieves from:** S009, S026, S028
**Platform anchor:** Foundry model catalogue benchmarks and Foundry cloud evaluation · **MCP servers:** Foundry MCP Server (preview, first use) · Microsoft Learn MCP Server

---

## What this day is for

A model's training performance is not evidence. A model's held-out performance is evidence about something — and the question of *what* is the day's whole content.

Students know that you evaluate on held-out data. They will still produce optimistic estimates, because the obvious leak — training on the test set — is one of at least four ways information from the evaluation set reaches the model, and the other three are invisible in the code.

The target: **an accuracy figure is an estimate of performance on a specific population under specific conditions, and stating which is part of reporting it.** This is S028's licensing sentence with a model as the instrument, and the day says so.

And it is said again, at the end of the day, by a vendor. The Foundry model catalogue publishes benchmark scores for selected models, and its own troubleshooting page explains a score that disagrees with yours in one line: *public benchmarks use standardised datasets and might not reflect performance on your specific data.* **That is this day's entire content, written by the party with the least incentive to write it**, sitting in a help table where nobody reads it.

## Phase 1 · Pretest and prediction (25 min)

Five items. A trained model and its evaluation are supplied, on the module's substrate task.

1. What does the reported figure of 0.87 tell you?
2. Here is how the evaluation set was constructed. Does that change your answer?
3. What population is this an estimate for?
4. Predict: will this model's live performance be higher, lower, or the same?
5. **Copilot prediction, sealed.** You will shortly ask the agent, through the Foundry MCP Server, to *evaluate this model and tell me whether it is good enough to ship*. Write down what it will produce, and **name the one thing it will get wrong**. Sealed with items 1 to 4 and opened at phase 8.

Item 3 is the day's move. Item 4's answer is lower, and predicting it is not the same as being able to say why.

Item 5's prompt is deliberately the prompt a student would actually write, and it contains a question the agent cannot answer — *good enough* is a property of a decision, not of a model. The design's expectation is that a majority predict the agent will produce an evaluation run and a number, and that a minority predict it will **answer the shipping question anyway**, which is the failure that matters.

**Warrant.** Pretesting on a real evaluation whose construction is disclosed at item 2. The construction contains a leak that most students do not identify even when shown it. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8: an instrument administered after its answer has been taught measures recall.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups have one model deployed on Foundry and four evaluation datasets built from the same substrate corpus. They run four cloud evaluations — four calls to create an evaluation and start a run against a versioned dataset — and read four scores back from the same deployment.

| Case | Protocol |
|---|---|
| A | A random split, correctly held out |
| B | A random split, where preprocessing was fitted on all the data |
| C | A random split, where the same underlying event appears in both halves under different records |
| D | A temporal split, where the evaluation period precedes the deployment period |

Groups rank the four figures for trustworthiness and commit **before submitting the runs**.

Then each protocol's model is evaluated against **a genuinely later, genuinely unseen period**, and the four figures are compared against reality.

**Protocol A's figure is optimistic too, and the reason is item 3's.** This is the payload. Three groups will have found three faults and will have nothing to find in A, which is the state in which point 4's distinction lands.

Two things are observed on the way and are not explained until phase 4. The evaluation run reports a status, and one of the available statuses is **Partial** — some evaluators completed and others failed — which produces a result page that looks complete and is not. And the scores come back on a one-to-five scale with a pass label attached, against a threshold **nobody in the room set**.

**Warrant.** Contrasting cases across evaluation protocols with a real out-of-time adjudicator, now run against a metered service rather than supplied as data. Protocol A's optimism is the phase's payload: the correct protocol still estimates the wrong population. Executing rather than reading buys two things the handout version could not — the runs take real time and cost real tokens, so the number of evaluations a group can afford becomes a live constraint two days before S042 makes it the subject; and the pass label arrives attached to the score, so the threshold question is asked by the platform rather than by the instructor.

## Phase 4 · Consolidating instruction (50 min)

1. **What a held-out estimate estimates:** performance on data drawn as the evaluation set was drawn. Not on the deployment distribution, unless those are the same.
2. **Four leaks,** from phase 3: fitted preprocessing, duplicated events, temporal ordering, and selection of the evaluation set itself. **This list omits leakage through hyperparameter tuning across many experiments, which is S042's subject, and leakage through a feature computed from a future state, which is common and is covered in IS201 rather than here. Safe as an audit for a single evaluation; unsafe as a complete leak taxonomy for a pipeline.**
3. **Why the obvious leak is the least dangerous** — it is detectable, and the others are not.
4. **Distribution shift** as the residual gap after all leaks are closed. The deployment population is not the training population, and this is not a defect.
5. **The licensing sentence for a model,** S028's three parts: the estimate, its interval, and the population it is about.
6. **The leak audit** as an artefact: for each leak class, what you checked and what you found.
7. **What "it works" means** and does not. The day's connection to S050.
8. **The catalogue's benchmark, read as an evaluation set.** The Foundry model catalogue publishes benchmark scores for selected models across quality, safety, estimated cost and throughput, with a leaderboard and trade-off charts. It is the most useful model-selection instrument most of these students will ever have, and **three of its properties are the four leaks in public form**. The benchmarks are standardised datasets, so the population is not yours — the documentation says exactly this, in a troubleshooting table, and the sentence is read aloud. Benchmark data is not available for all models, so absence of a Benchmarks tab is absence of publication and not absence of risk. And **the leaderboard is in preview**, which is a statement about the instrument's own stability.
9. **Defaults are opinions and thresholds are policy.** Four were chosen for you today and none was announced. The evaluation portal **preselects recommended evaluators** for you based on the target and scope you picked, so the question of what to measure was answered before you asked it. Judged evaluators return a score from one to five with a **default pass threshold of three**, and a pass label — a threshold nobody in this room set, on a scale nobody in this room defined. Groundedness Pro does not return a number at all; it returns a boolean, so it cannot be thresholded and cannot be averaged with the others. And the catalogue **displays an average index across various metrics and datasets by default**, which is a single number composed from a weighting you did not choose and cannot see. An engineer who cannot state what was chosen for them does not understand their own system, and this generalises far beyond this vendor.
10. **Every judged score in this stack is uncalibrated, and you say so.** No agreement-with-human-judgement data is published for any Foundry evaluator. That is not a criticism of the evaluators; it is a statement about what is known. A score of 4.2 on relevance is a number produced by a model asked to rate another model's output, and **nobody has published how often it agrees with a person**. The licensing sentence at point 5 therefore acquires a fourth clause whenever the figure came from a judge: *and this score is uncalibrated.* This is the day's most portable sentence and it is required in every artefact from here to S090.
11. **Why today's numbers are perishable and the reasoning is not.** Evaluator names change, scales change, thresholds change, the preview label moves. What does not change is that a score has a population, that a judged score has a judge, and that a threshold is a policy someone set.

**Warrant.** Consolidation indexed to phase 3. Point 2 carries the strong-form scope statement. Point 4 separates leakage, which is a fault, from shift, which is a condition. Points 8 and 9 are the day's platform-specific content and satisfy the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s requirement that each day name a perishable point and a default the platform chose. Point 10 is the standing prohibition on the [Microsoft AI Platform Map](wiki/program/11-Microsoft-AI-Platform-Map.md) converted into a sentence a student writes rather than a rule staff enforce.

## Phase 5 · Whole-task learning task (90 min)

**Class 3. The evaluation protocol is the student's. This phase produces a build.**

Students use Copilot in agent mode, through the Foundry MCP Server, to ship a working evaluation pipeline over the module's substrate task. They:

1. **State the deployment population** — who and what the model will see in use.
2. **Design the evaluation** so that its population resembles it, and state where it does not.
3. **Train and evaluate,** running the evaluation in the cloud against a versioned dataset so the run is on file and re-readable.
4. **Conduct the leak audit,** per point 6: four classes, what you checked, what you found.
5. **State the figure with its licensing sentence,** plus the uncalibrated clause for any judged component.
6. **Estimate the shift** between your evaluation population and the deployment population, and its direction.
7. **State what you would observe in production** that would tell you your estimate was wrong.

The day bites at step 3, in a place students do not expect. **The evaluation's field mapping is a specification.** Cloud evaluation connects your data's fields to each evaluator's parameters explicitly, and your field names must match what is actually in the file — a dataset with a `question` column and a mapping that says `query` does not fail loudly. A run can also come back **Partial**, meaning some evaluators completed and others did not, and a partial result page reports the scores it has without announcing what is missing. A pipeline that reads the scores and not the status will report an average over whichever evaluators happened to succeed.

**The artefact carries three further elements**, per the Copilot Practice Standard.

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the pipeline's own checks would have caught an intervention-worthy error — an assertion on the run status before reading scores, or a check that every mapped field resolved, are the obvious examples and are accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 2 is worked with the room; step 4's audit form is supplied.

**Warrant.** Whole-task at class 3, now shipping an evaluation rather than describing one. Step 4 is the day's discriminator — an audit reporting no findings across all four classes is treated as an incomplete audit rather than a clean one. Step 7 is S029's validation criterion applied to a model. The intervention record is the element that distinguishes a student who directed the build from one who accepted it, and its fail condition carries the sensitivity escape [S052](wiki/seminars/S052.md) established and [WP-048](wiki/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate model whose offline figure was excellent and whose live performance was materially worse, with attention to **which leak it was and how long it took to find**.

Then the agent case: a Copilot-generated evaluation pipeline that was **confidently wrong and passed review**. Asked to evaluate a model and report whether it was good enough to ship, the agent produced a clean pipeline — it uploaded a versioned dataset, created the evaluation, started the run, polled to completion, read the scores, compared them against the threshold and reported *passes on all criteria, ready to ship*. Every step was correct. Two things were wrong and neither is visible in the code. The run came back **Partial**, and the polling loop treated any terminal state as done, so two evaluators had failed and their absence was reported as a pass. And **the shipping question was answered at all** — by a threshold of three that the agent did not choose, on a scale it did not define, against a population nobody had named.

Attention goes to why review did not catch it: the reviewer checked that the code was right, and the code was right. What was wrong was that a threshold comparison had been presented as a decision.

Then students: a number you have reported that was optimistic, or a place today where you accepted agent output you had not checked.

**Warrant.** Error management. The disclosure targets a leak that survived review, because the module's whole claim is that these are not caught by inspection. The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen so that the failure is invisible to the review a student would actually perform — it is not a coding error, it is a category error the code executes faithfully.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student hands their partner **the evaluation design from step 2 only** — not the results — and the partner must find a way the reported figure could be optimistic.

Per the [Assessment Architecture](wiki/program/03-Assessment-Architecture.md)'s rule 3, the outcome is recorded in the artefact.

**Warrant.** Interactive-tier articulation with an adversarial audit. Withholding the results is what prevents the partner from reasoning backwards from the number.

## Phase 8 · Calibration and commitment (20 min)

- Items 1 to 4 resolved: the item 3 answer rate and the item 4 direction predictions against the phase 3 out-of-time results.
- **Item 5 opened.** The sealed Copilot predictions are read against what the agent actually did, and the cohort's hit rate is recorded. Both halves count: predicting that the agent would err is easy, and naming the error is the measure. This is the cohort's first frontier-calibration datum in Q5.
- The room's step 4 audit findings collected by leak class; the most-missed class is named.
- Each student names one figure they have quoted whose population they did not state.
- Retrieval schedule: next morning, day 3, week 2, week 6.

## Assessment

Specification item in IS201 and ME201 jointly. Per rule 1, the checked elements are: a stated deployment population, an evaluation design with its stated divergence, a completed four-class leak audit, a licensing sentence with all three parts, **the uncalibrated clause on any judged score**, a shift estimate with direction, a production observable, the phase 7 outcome, **the prompt record, the intervention record and the frontier statement**. **Nothing else is assessed**, including the figure itself.

**A leak audit that does not evidence what was checked in each of the four classes fails the specification.** A pipeline with no leaks passes — provided the four checks and their evidence are shown. What fails is an audit that asserts cleanliness without demonstrating the looking, because an unperformed audit and a clean pipeline produce the same claim and only one produces the evidence.

**A judged score reported without the uncalibrated clause fails**, on the same ground that an unqualified accuracy figure does.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error.

*(The leak-audit clause was corrected after [WP-041](wiki/whitepapers/WP-041.md) §8 found the original wording — "an audit reporting no findings fails" — contradicted the design's own position by making findings rather than evidence the requirement.)*

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| A held-out estimate estimates the population its set was drawn from | The catalogue leaderboard's normalised index, and its standardised-datasets caveat |
| Four leaks, of which the obvious one is least dangerous | Four evaluation datasets and four cloud evaluation runs |
| Shift is a condition, leakage is a fault | The out-of-time evaluation dataset built from a later substrate period |
| A threshold is a policy someone set | The one-to-five scale and the default pass threshold of three |
| A judged score is uncalibrated until its agreement is published | Every Foundry evaluator, on the date of reading |
| A result that looks complete may not be | The **Partial** run status |

The substrate task, the dataset, all figures, every evaluator name, the scale endpoints, the threshold and the preview label are **perishable**. The held-out estimate's meaning, the four leaks, leakage-versus-shift, the licensing sentence, the leak audit and the uncalibrated clause are durable and are what the specification assesses.
