## What this day is for

There is a vocabulary attached to this material and it is changing while the students are in the room. Patterns acquire names, names acquire frameworks, frameworks acquire diagrams, and a student who learns the diagrams has learned something that will be wrong before they graduate. The [Durable and Perishable Register](wiki/program/09-Durable-and-Perishable-Register.md) marks agent orchestration patterns semi-durable and re-verified annually, which is the register's polite way of saying that the vocabulary is not the content.

**The content is that orchestration is control flow.** Sequence, branch, loop, fan-out and join, recursion. Every pattern in the room is a composition of five constructs the cohort learned in their first year, and the only thing that is new is where the branch conditions come from: **they are computed by a component that has no obligation to be consistent between two runs on the same input.**

That is the cheapest framing available and it is the most durable, and it earns both by doing real work. Once a student can name the construct, they can state the path set. Once they can state the path set, they know the failure surface — because [S031](wiki/seminars/S031.md) established that the object of reasoning is the set of executions, and **you cannot enumerate the failure modes of a system whose path set you have not bounded.**

[S017](wiki/seminars/S017.md) supplies the other half. A scheduler is an allocation policy, every policy optimises something at another thing's expense, there is no neutral choice, and **the thing deprioritised is somebody's work.** An orchestrator chooses which component runs next, on whose request, with what budget. It is a scheduling policy and it has a victim.

The target: **an orchestration pattern is a control-flow construct with a model-computed branch condition; path-set cardinality is the failure surface; the step cap is a loop bound presented as a configuration value; and every orchestration policy deprioritises somebody.**

## Phase 1 · Pretest and prediction (25 min)

A working agent system is supplied with two weeks of its trace log. Five items, **sealed and opened at phase 8.**

1. **Draw its control flow** as you would draw a program's. Mark where it branches, where it loops, and where it fans out.
2. **For each branch you drew, say whether the condition is computed by code or by the model.**
3. Here are **two runs on the same input.** They took different paths. **Which construct produced the divergence, and could code have produced it?**
4. Predict: **how many distinct paths does this system have?** Write a number, or write why you cannot.
5. **Copilot prediction, sealed.** You will shortly ask the agent to draw the control flow of your own capability and to state its path bound. **Write down what it will produce, and name the one thing it will get wrong.** Sealed with items 1 to 4 and opened at phase 8.

Item 4 is the day's discriminator. The system contains a loop with a model-computed continuation condition and a cap of six; its path set is bounded only by the cap, and most of the room writes a number.

**Item 5 is the day's contribution to the running frontier map.** The design's expectation is that the agent produces a correct and legible drawing quickly — reading a configuration is exactly the shape of task it is good at — and then states a path count computed from the branches it drew, which is item 4's error produced by the instrument rather than by the student. **The prediction worth making is not that it will be wrong but that it will be wrong in the same place the room is.**

**Warrant.** Pretesting with a construction demand on a real system, before any vocabulary is supplied, so that phase 8 compares the student's own drawing against the substrate's trace log rather than against a corrected version of itself. Item 2 is the day's central distinction administered before it is named. Item 3 admits a plausible-and-wrong answer — non-determinism in the tool layer — that a cohort fresh from a concurrency module is disproportionately likely to give. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups receive **four orchestrations implemented over one substrate task on Microsoft Agent Framework**, pre-built and runnable, together with three months of each one's traces, its realised quality on the task, its cost per completed request, and its incident record.

- **P1** — a fixed sequence. Sequential orchestration; the control flow is code and the model fills slots.
- **P2** — a router. One model call selects among four branches by handoff, then a fixed sequence runs.
- **P3** — a loop. A single agent with tools decides at each step whether to continue, under a step cap.
- **P4** — fan-out. Concurrent orchestration to several workers and an aggregator that combines their returns.

Groups rank the four on **quality, cost, and how confidently you could say what the system will do**, and commit before the records arrive.

Then each group runs all four against a fixed request set, twice, and reads the emitted traces. **Two things are visible in the run that are not visible in a description.** P3 takes different paths on two identical inputs, which is item 3 happening in front of the group rather than being asserted. And P4's aggregator returns a result on a run in which one worker returned nothing — with nothing in the output distinguishing that run from one in which every worker contributed.

The payload is **P1.** It is the pattern every group ranks least capable, and it wins on the substrate's own record — on quality, on cost, and by a distance on the third question. The reason is available once anyone looks at the path counts: P1 has one path, P2 has four, P3 has as many as the cap allows, and P4 has the product of its workers' outcomes. **Every failure P1 had was attributable to a named step, and every remedy it received stayed fixed.** The three others accumulated remedies that worked on the path that had failed.

**Then the task changes.** The same four orchestrations are run against a second substrate task with a different shape — one whose requests genuinely fall into unlike classes requiring unlike work — and **the ranking reverses.** P1 is worst on it, and not marginally: a single path cannot serve four kinds of request, so P1's quality is the average of one good case and three bad ones, and its per-request cost is the highest of the four because it does every step for every request. P2 wins.

**Selection disclosed under instrumentation rule 3.** The two tasks and the four orchestrations were chosen by staff from the substrate's own workload, and students are told so at the start of the phase, together with what the selection was chosen to demonstrate.

Task after: **state what property of the task determined the ranking**, and then, **for each orchestration, state the number of distinct paths and name one failure that produces a successful-looking run.**

The second finding lands here rather than in the ranking. **P4's join cannot distinguish a worker that failed from a worker that had nothing to add** — both deliver nothing to the aggregator, and the aggregate is computed over whatever arrived. That is [S033](wiki/seminars/S033.md)'s third outcome, at a place the students did not expect to meet it, and the room has just watched it happen. It is the case [S074](wiki/seminars/S074.md) is built on.

**Warrant.** Contrasting cases across control-flow constructs with two real records as adjudicators, holding the pattern set fixed across two tasks so that the reversal is attributable to the task's shape. **The four are operated rather than described**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md), and the operation buys two things a handout cannot: the divergence at P3 is observed rather than claimed, and the join at P4 produces a clean-looking result in the room, which is worth more than any number of assertions that it would. P1 is constructed to defeat the expectation that autonomy is the axis of capability, and it defeats it on the substrate's own numbers rather than by argument. **The second task is [S017](wiki/seminars/S017.md) phase 3's second-workload construction, carried across because instrumentation rule 5 requires it**: without it the phase teaches *the simplest pattern wins*, which is the conclusion a single record supports and which is wrong. The correction was made after [WP-072](wiki/whitepapers/WP-072.md) §8 found the remedy sitting unused in the design's own repertoire. The task-after separates the reversal finding, the path-count finding and the join finding deliberately: a group that has just watched the ranking invert will accept *bound the paths, then price the match* as a method, and that is the frame the rest of the module runs on.

## Phase 4 · Consolidating instruction (50 min)

1. **Five constructs.** Sequence; branch; loop; fan-out and join; recursion, where a component invokes an instance of itself or of another orchestrator. Every orchestration pattern in current use is a composition of these. **This enumeration is not complete.** It omits interrupt and event-driven entry, where the flow is resumed from outside on a signal, which is SY301's material and is the construct most likely to be added by the next generation of platforms; and it omits **shared mutable state between concurrent branches**, which is not a construct at all but which changes the meaning of every construct it appears under, and which is [S031](wiki/seminars/S031.md)'s subject rather than this day's. It is **safe** as a vocabulary for describing and bounding a single orchestrated capability you can read the configuration of; it is **unsafe** as a description of a system whose components can be resumed from outside or that share state across branches, where the path set computed from these five is a lower bound and will read as a total.

2. **The branch condition is computed by a component with no obligation to be consistent.** In an ordinary program, `if (x > 3)` evaluates the same way on the same `x` twice. Here it does not. Item 3's two runs are the demonstration and there is nothing else to it: **the same input can take two paths, and no defect is present.**

3. **Path-set cardinality is the failure surface.** Sequence: one. Branch: the number of branches. Fan-out: the product over the workers' outcome sets. Loop: bounded only by the cap. **You cannot enumerate the failure modes of a system whose path set you have not bounded**, which is [S031](wiki/seminars/S031.md) point 1 with the executions now generated by the system rather than by a scheduler. This is the day's assessed object.

4. **The task's shape determines which pattern wins, and the path set is what you pay for the match.** Phase 3's reversal. A pattern whose path set is smaller than the task's real branching structure averages unlike cases together; a pattern whose path set is larger buys nothing and pays for it in everything below. **A pattern recommendation without a characterisation of the task is not a recommendation** — which is [S017](wiki/seminars/S017.md) point 5, unchanged, with requests in place of jobs.

5. **The step cap is a loop bound presented as a configuration value.** It is the only thing standing between a model-computed continuation condition and an unbounded path set, and it is almost always set by someone tuning latency. **Choosing it is deciding how much the system may do before anybody looks.** [S071](wiki/seminars/S071.md)'s decline point and this number are the same decision.

6. **[S017](wiki/seminars/S017.md) point 7, in an orchestrator.** Every orchestration policy prioritises something — latency, cost, coverage, recoverability — at something's expense. Fan-out buys latency with cost, and the cost falls on whoever is queued behind it. A cap buys predictability with completeness, and the incompleteness falls on the requests that needed the seventh step. **The thing deprioritised is somebody's request and you can name them.**

7. **Fan-out inherits the third outcome at the join.** A worker that failed and a worker that had nothing to contribute deliver the same thing to the aggregator: nothing. **Unless the join distinguishes them, the aggregate is computed over an unknown denominator** — and almost no join distinguishes them, including P4's, which is the substrate's own.

8. **Name the construct, not the framework.** A framework's pattern vocabulary is semi-durable at best and its diagrams are perishable. **A student who can say *this is a loop with a model-computed continuation condition, a cap of six, and a fan-out of three inside it* has described the system in terms that survive the framework's replacement, and has stated the path set in the same sentence.** Every named product, pattern name and protocol used today is an instance and is marked as such; the assessed content is the construct, the bound and the victim. Retry inside a loop — [S033](wiki/seminars/S033.md) point 3's four consequences, compounded once per iteration, with amplification the one that takes systems down — is the standing example, and it is worse here than at a single call site because the loop's continuation condition is computed from the responses the retries are producing.

9. **The framework's catalogue, mapped onto the five constructs.** *Perishable, and marked.* Microsoft Agent Framework documents five built-in workflow orchestrations — **sequential, concurrent, handoff, group chat and magentic** — and each is a composition of constructs the cohort already holds. Sequential is a sequence. Concurrent is fan-out and join. Handoff is a branch whose condition is model-computed. Group chat is a loop whose next speaker is chosen by the orchestrator. Magentic is a manager agent that coordinates specialists, which is a loop whose body is selected by a model at each iteration. **The mapping is the point and the names are not**, and the documentation itself supplies the evidence for that: a swarm pattern and a model-driven speaker selector are listed as in development, so the vendor states in its own pages that the set of five is not closed. **A student who learns five names has learned a list that its author says is growing. A student who learns the mapping can absorb the sixth in a sentence.**

   The same documentation supplies point 2 in its own words. It distinguishes an **agent**, whose steps are "dynamic and determined by the LLM based on the context", from a **workflow**, which is "a predefined sequence of operations" whose "flow is explicitly defined". That is the model-computed branch condition named by the party that built it, and it is the clearest available statement that **choosing an agent rather than a workflow is choosing an unbounded path set.**

10. **Defaults are opinions, and two of them decide your path set and your bill.** *In group chat orchestration, the agents do not share a session instance; the orchestrator broadcasts each response to every other agent before the next turn so that all of them hold the full conversation.* Nobody configures that — it is what the pattern is. Two consequences nobody drew: **every agent you add multiplies the context every other agent receives**, which is a cost curve with no line in any diagram; and the "shared conversation" is a construction of the orchestrator rather than a shared object, so a broadcast that does not happen is invisible from inside any participant. The second default is the one this day cares about most: **human-in-the-loop exists in these orchestrations through tools that require approval and pause the workflow, and it is off unless a tool is configured to require it.** That is [S071](wiki/seminars/S071.md) point 5's *what other than the sentence prevents it* reduced to a configuration field, with the default on the permissive side. **An engineer who cannot state what was chosen for them does not understand their own system.**

**Warrant.** Consolidation indexed to phase 3. Point 1 carries the strong-form scope statement and carries it on the enumeration the whole day depends on. Point 3 is the retained anchor and the assessed object. Point 4 is what phase 3's reversal established and is stated immediately after the arithmetic that explains it. Point 6 is the professional content and is placed where it lands on an established technical base, as [S017](wiki/seminars/S017.md) point 7 was. Point 8 is the day's defence against its own perishability and is stated as a competence rather than as a warning. **Points 9 and 10 are the platform layer**, required by the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md) and placed after point 8 deliberately: point 9 is the framework catalogue arriving *as an application of the constructs* rather than as their source, which is the only order in which it does not undo point 8, and point 10 names two defaults that change a path set and a cost without appearing in any drawing.

## Phase 5 · Whole-task learning task (90 min)

**Class 5. This phase produces a build. The pattern, the bound, the victim and the prediction are the student's.**

Students use **the capability they deployed at [S071](wiki/seminars/S071.md)** and the boundary they wrote for it, working in Copilot agent mode through the Foundry MCP Server.

1. **Draw the control flow** of the capability using only the five constructs. Mark every branch condition as model-computed or code-computed. **Then name one composition of the five constructs that your framework has no built-in name for**, and say whether your capability needs it. **This clause is point 8 made checkable**: a student who can only describe compositions the catalogue has named has the catalogue and not the constructs.
2. **Bound the path set.** State the number of distinct paths, **or** state which construct makes it unbounded, what bounds it in practice, and who set that bound — **by name, and by the configuration field the bound sits in.**
3. **For each model-computed branch condition, state what a second run on the same input might do differently**, and which of your drawn paths that opens. Committed in writing.
4. **Name the victim**, per [S017](wiki/seminars/S017.md) point 7: which class of request your pattern deprioritises, by how much, and **who submits it.** **State also the task-shape characterisation your pattern choice assumed**, per point 4, and what change in the request mix would invalidate it.
5. **For every join in your drawing, state how you distinguish a failed contributor from a silent one** — or state that you cannot, which is a permitted answer and is the more common one.
6. **Predict the path the system will take least often, and one path it will take that is not on your drawing.** Committed before step 7.
7. **Implement the orchestration you drew, deploy it, and run it on the substrate's shadow path.** Report the realised path distribution against step 6, **and against your [S071](wiki/seminars/S071.md) boundary: which realised paths touched a prohibited action.**

**The artefact carries three further elements**, per the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent to produce the drawing and the implementation, in order, including the ones you abandoned.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error — and today the qualifying demonstration is a step cap you set deliberately, with the number defended as a control-flow bound rather than inherited as a latency setting.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 1's construct notation is worked with the room, since drawing a model-computed branch is a new representational decision and the notation is the day's shared object; step 7's deployment procedure is worked with the room. **Step 6 is unsupported.**

**Warrant.** Whole-task at class 5 producing the drawing that [S073](wiki/seminars/S073.md), [S074](wiki/seminars/S074.md) and [S075](wiki/seminars/S075.md) all mark up — and, now, the running system those days interrogate. Step 2 is the day's discriminator and its second clause is what prevents a student writing a number for a system containing a loop; the *configuration field* clause is new and is point 5 made checkable, because a bound whose location cannot be named is a bound nobody set. Step 4 is [S017](wiki/seminars/S017.md) step 4 re-run at class 5, and the *who submits it* clause is unchanged because it was right the first time. **Step 7's second clause is the first empirical test of an [S071](wiki/seminars/S071.md) boundary** and it is deliberately the student's own boundary against the student's own pattern, so that a breach cannot be attributed to a supplied case. The intervention record's qualifying demonstration is chosen so that it coincides with the day's own assessed content rather than adding a requirement.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate orchestration whose step cap was raised from four to twelve for one class of request. The change was requested by the people whose requests were being truncated, was correct for them, was reviewed, and improved the outcome measurably. Cost rose acceptably. Latency rose acceptably. Nothing else changed for eleven weeks.

Then an unrelated dependency slowed by a factor of three, and the loop — which now had three times the iterations to retry inside — amplified the slowdown into an outage that took the whole capability down for both classes of request.

Attention is directed at one fact: **the cap was a control-flow bound and was changed as a tuning parameter.** Everybody involved was correct, the review was competent, and the number appeared in a configuration file next to a timeout and a batch size.

Then the agent case: a student asked Copilot in agent mode to **add a retry to the tool call in the loop.** It produced textbook work — bounded retries, exponential backoff, jitter, a clean error path — and the review passed, because the retry logic was correct and the reviewer was checking the retry logic. **The path set had been multiplied by the retry count once per iteration and the cap was untouched**, so the worst-case work went from six steps to six times four calls, against a continuation condition computed from the responses the retries were producing. The agent had been asked for a retry and it produced a retry; nothing in the request or the review located the change in the control flow.

Attention goes to why review did not catch it: **the change was correct at the site it was made and wrong at the scale it operated**, which is the same shape as the instructor case one level down, and the reviewer had no artefact in front of them that showed the path set at all.

Then students, in threes: **a limit you raised because the thing it was limiting was legitimate.**

**Warrant.** Error management targeting point 5, constructed like the module's other clinics so that the case contains no error of care. The dependency slowdown is what makes it point 8's retry amplification as well as point 5 — the cap's real function was invisible until an unrelated system moved — and the eleven weeks are the phase's content, because they are why nobody connected the change to the outcome. **The agent case is the [Copilot Practice Standard](wiki/program/12-Copilot-Practice-Standard.md)'s required addition** and is placed here because it is the same failure at a shorter timescale, produced by the instrument the students are about to use in phase 5, and because the drawing produced at step 1 is precisely the artefact that would have made it visible.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents **their step 1 drawing and their step 2 path bound.**

The partner has two obligations and both are required.

- **Construct an input that takes a path not on the drawing**, and say which construct the drawing got wrong.
- **Name the construct you would remove to halve the path set**, and state what capability the removal costs and which class of request loses it.

A construction the drawing misses but that the student's step 3 statement already anticipated is not a defeat.

Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 3, both outcomes are recorded in the artefact.

Per instrumentation rule 5 as amended at [WP-054](wiki/whitepapers/WP-054.md) §8, the dual-defeat construction reuses [S068](wiki/seminars/S068.md) phase 7's and **its use here is contingent** on S068's reported outcome; a reported failure there retracts it here along with every other contingent reuse.

**Warrant.** Interactive-tier articulation with a dual demand in which the second half attacks the design rather than the description. The removal question is the phase's real content: it forces the student to price their own path set against a capability, which is the trade point 5 names and which nobody makes voluntarily.

## Assessment

**One specification item**, in IS302 with ME302. Per [Assessment Architecture](wiki/program/03-Assessment-Architecture.md) rule 1, the checked elements are: the control-flow drawing in the five constructs with every branch marked model-computed or code-computed, **together with one named composition the framework has no built-in name for and a statement of whether the capability needs it**; the path bound, **or** the unbounding construct together with what bounds it in practice, who set that bound, and the configuration field it sits in; the step 3 divergence statement for each model-computed condition; the deprioritised request class with its magnitude and who submits it; **the task-shape characterisation the pattern choice assumed together with the request-mix change that would invalidate it**; a join-distinguishability statement for every join, including an explicit cannot; the pre-committed step 6 prediction; **the deployed orchestration and its realised path distribution, with the paths that touched an [S071](wiki/seminars/S071.md) prohibition marked**; both phase 7 outcomes; **the prompt record**; **the intervention record**; and **the frontier statement**. **Nothing else is assessed.**

**A path count stated as a number for a system containing a loop fails.** This is the day's single hard requirement and it is item 4's error written into the specification.

**A drawing with no named victim fails.** An orchestration policy that deprioritises nobody has not been analysed, and [S017](wiki/seminars/S017.md) established six quarters ago that no such policy exists.

**A framework's pattern name used in place of a construct fails.** Point 8, as a specification condition: the artefact is written in the five constructs, and a named pattern — including any of the five the framework supplies at point 9 — may appear only as an annotation to one.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error; a deliberately set and defended step cap qualifies.

No entrustment judgement. The quarter's is at [S080](wiki/seminars/S080.md), and [M15](wiki/modules/M15.md) carries none for the reason published on [Q8](wiki/quarters/Q8.md).

**Disposition observed:** reliability, evidenced by whether the step 2 bound is one the student's own configuration actually enforces. Recorded in narrative within the activity, never scored as one.
