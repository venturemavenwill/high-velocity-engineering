# S006 · The Invariant You Did Not Write Down

**Module:** [M02](/wiki/modules/M02.md) · **Quarter:** [Q1](/wiki/quarters/Q1.md) · **Complexity class:** 1
**Strands:** CF · MS · PE
**Platform anchor:** GitHub Copilot agent mode; `*.instructions.md` custom instructions files · **MCP servers:** Microsoft Learn MCP Server
**Whitepaper:** [WP-006](/wiki/whitepapers/WP-006.md)
**Depends on:** S005
**Re-tests:** S004

---

## What this day is for

Every working program is full of invariants. Almost none of them are written down. The list is sorted, the index is in range, the connection is open, the units are seconds — these hold, the code depends on them holding, and nothing in the program says so. They are invariants in exactly the S005 sense, and they have never been stated, established or preserved deliberately.

This day's target is the recognition that **the invariants you did not write down are the ones that break**, and the working habit of surfacing them. It is the near-transfer test of M01's technique at the shortest gap the timetable allows: two days after proving a loop invariant in mathematics, students are asked to do it to code they did not write.

It is also where the programme's second register opens. **A specification and a repository custom instructions file are the same object, and one of them tells you immediately when it is defective.** An unwritten invariant and an unwritten instruction fail for the same reason and are repaired in the same way; the difference is that the instructions file is executed, so the repair loop is a minute long instead of a fortnight. The argument is made here because this is the first day in the programme where students have an invariant worth writing down and an agent that will act on it, and it is load-bearing from here to [S090](/wiki/seminars/S090.md).

## Phase 1 · Pretest and prediction (25 min)

Students receive forty lines of real substrate code that works.

1. List every property this code depends on that it does not check.
2. For each, say what happens if it stops holding.
3. Which of these is a loop invariant in the S005 sense?
4. Predict how many you found compared with the room's median.
5. **Sealed Copilot prediction.** The same forty lines will be given to Copilot in agent mode, with the wording of item 1 as the prompt. Write down now, and seal it: what will the agent produce, and **where will it be wrong**? A prediction that says only "it will do well" or "it will miss things" does not count; name the property you think it will miss, or the kind of property it will invent.

Item 3 is the transfer probe and it is the day's most important measurement — not of the students, but of the design. Item 4 is calibration, and students overestimate. Item 5 is sealed with the rest and opened at phase 8; its cohort accuracy is this day's contribution to the programme's running frontier map, and the design expects the *where will it be wrong* half to be much weaker than the *what will it do* half.

**Warrant.** Pretesting with a generation demand on untaught material. Item 3 tests whether S005's technique survived a change of setting after two days; the result is recorded as a design finding. Item 5 is administered before phase 4 and may not migrate later, per instrumentation rule 8: a frontier prediction made after the frontier has been shown measures recall.

## Phase 2 · Cumulative retrieval set (20 min)

Free recall, no notes.

- The three obligations from S005 phase 4.
- The four argument-failure classes from S004.
- What did the S003 phase 5 fix discard, in your own case?
- Which S005 obligation does an unchecked precondition fail?

The final item is a bridging retrieval and is answered by nearly nobody in week six.

**Warrant.** Expanding-interval retrieval with a discrimination item that requires applying S005's vocabulary to a situation S005 did not cover.

## Phase 3 · Contrasting cases and generation (45 min)

Groups receive **the same function three times**, each with the same body and a different set of stated preconditions.

- **Version A** states nothing. It works on the supplied inputs.
- **Version B** states preconditions that are true but insufficient.
- **Version C** states preconditions that are sufficient but so strong that no realistic caller can satisfy them.

Each version is then handed a caller. All three callers are reasonable. One of them breaks a version.

Task: identify which caller breaks which version and why, and then — the generation demand — **write the preconditions the function actually needs**: strong enough to be sufficient, weak enough to be usable.

Groups commit in writing. Nearly every group's first attempt is too strong.

**Then the three specifications are executed.** Each version's preconditions are written into a `.github/instructions/contract.instructions.md` file with an `applyTo` glob matching the teaching language, and each group issues the identical prompt in agent mode: *write a caller for this function.* Four configurations are run against one prompt.

| Case | Configuration | What the room expects |
|---|---|---|
| A | Version A's file — no preconditions stated | A generic caller; several groups expect the agent to infer the constraints from the body |
| B | Version B's file — true, insufficient | A caller that honours everything written and still breaks the function |
| C | Version C's file — sufficient, too strong | A caller so constrained that it is not the caller anyone wanted |
| D | Version C's file with the `applyTo` line deleted | The same output as C |

**Case D is the payload and it defeats the room.** The file is present, correct, saved, and in the documented folder, and the agent behaves as though it were not there — because the documentation states that when `applyTo` is not specified, the instructions are not applied automatically. Nothing warns you. The only evidence is the **References** section of the chat response, which lists the instructions files actually used, or the chat customization diagnostics view.

Second generation demand, after all four have run: **state the difference between a precondition that is wrong and a precondition that is not in force.** Groups reliably have vocabulary for the first and none for the second.

All four cases are operated, not demonstrated. The only prerequisite is an active GitHub Copilot subscription and a workspace folder; nothing here requires a cloud subscription or a tenant privilege.

**Warrant.** Contrasting cases with invariant deep structure: one body, three specifications, and a trade-off that only becomes visible when a caller is introduced. The too-strong tendency in the written task is the productive failure the phase is built to produce. Case D supplies a second and sharper one — a specification can be defective in a way that has nothing to do with what it says, and the evidence sits in a panel nobody was told to open.

## Phase 4 · Consolidating instruction (50 min)

1. **The unwritten invariant.** Every dependency the code does not check is a claim about the caller, and an unstated claim cannot be preserved deliberately.
2. **Three places invariants live in code:** preconditions at an interface, loop invariants inside a computation, and data invariants that hold across an entire structure's lifetime.
3. **The strength trade-off,** resolved from phase 3. A precondition too weak does not protect; too strong does not permit. This is a design decision, not a discovery.
4. **Establishment, preservation and termination in code**, mapped directly onto S005's three obligations. Termination in code is the one students forget, and it is the same forgetting.
5. **Making an invariant visible**: an assertion, a type, a named constructor that cannot produce an invalid value, a comment. These differ in when they fail and in who they inform — which is the S004 reader question again.
6. **Why the unwritten ones break.** They survive as long as the original author is the only caller. The failure is triggered by a second caller, a refactor or a passage of time, none of which are events the code can observe.
7. **The second register, stated once and completely.** A repository custom instructions file is a specification whose conformance is checked by execution rather than by reading. It is not an analogy and it is not a productivity tip; it is the same object with a shorter feedback loop, and the programme treats it that way from here on. Three consequences, taught rather than implied:
   - **A specification that produces non-conforming work is a defective specification.** In this register you find out on the next prompt, and the file is the only thing that changed, so the attribution is unambiguous. That is the whole reason the equivalence is introduced in a programming course and not in a writing course.
   - **Specification rule 1 applies.** A specification must state what is actually checked. *Write idiomatic code* asks for a quality judgement the agent cannot make, so it will make one, and it will not be yours.
   - **Specification rule 2 applies.** A qualification must travel with the quantity it qualifies, in the same field. *Cite sources* without *in the same sentence as the claim* produces detached citations, reliably, on the first attempt.
8. **What the file does not say is where it fails.** The `applyTo` glob is a scope statement in executable form, and case D is what an unscoped specification looks like when it is run: present, correct, inert. The strength trade-off at point 3 has a scope twin — a glob too narrow does not protect, a glob too wide applies rules to files they were never written for, and `**` is not a safe default but the absence of a decision.
9. **Two defaults the platform chose for you, and one contradiction it has not resolved.** Perishable, marked as such, verified against the Visual Studio Code agent-customization documentation as it stood on 15 July 2026.
   - **When several instructions files apply, the documentation states that they are combined and that no specific order is guaranteed.** So you cannot write a general file, refine it with a specific one, and rely on the refinement winning. Across *types* a precedence is published — personal instructions outrank repository instructions, which outrank organization instructions — which means a file on one developer's machine can override the repository's specification, and nothing in the repository records that it happened.
   - **Custom instructions are not applied to inline suggestions as you type.** The Visual Studio Code documentation states this plainly. A Microsoft Learn quickstart for the same feature states that custom instructions apply across every surface matching the glob, "including ask mode, edit mode, agent mode, and inline completions." **Two vendor pages disagree**, neither carries a version stamp that reconciles them, and no coverage figure is published for either claim. The engineering response is the one this programme applies to any unverified claim: run it, read the References list, record what your version did, and date the record.
10. **Scope of all of the above.** Points 1 to 8 are safe for reasoning about interfaces, contracts and repository conventions, and for any code whose callers you can enumerate. They are unsafe in exactly one direction that matters this quarter: an instructions file is evidence about what the agent was *given*, never about what it *did*, and points 7 and 8 must not be carried into the belief that a conforming file produces conforming work. That claim is tested at [S009](/wiki/seminars/S009.md) and it does not survive.

**Warrant.** Consolidation indexed to phase 3's committed preconditions. Point 4 is an explicit retrieval of S005 rather than a restatement, and is delivered by asking rather than telling. Points 7 and 8 consolidate what case D produced rather than asserting a claim the room has not met, per instrumentation rule 7. Point 9 is perishable and is the day's stated instance of the durable rule that defaults are opinions.

## Phase 5 · Whole-task learning task (90 min)

Students take a second piece of substrate code — larger, roughly two hundred lines, genuinely in use — and:

1. **Surface three invariants** it depends on and does not state.
2. **For each, write the caller that breaks it.** Not a hypothetical: an actual call the code would accept.
3. **Choose a visibility mechanism** for each, from phase 4 point 5, and justify the choice by naming the reader it informs and the moment it fails.
4. **Implement one of them,** and run the breaking caller to confirm it now fails loudly.
5. **State what your change costs.** Every assertion is a runtime cost, every type is a constraint on future callers, every comment is a maintenance liability.
6. **Write the second register.** Take one of the three invariants you did *not* implement in code and state it in a `.github/instructions/<name>.instructions.md` file, with an `applyTo` glob that names its scope. Confirm from the chat References list that the file was actually applied — not that it exists.
7. **Attack it.** Write the prompt most likely to make the agent produce work that violates that invariant. **Run it three times**, because a system whose output varies between runs is not characterised by one of them. If the file held on all three, say why your attack was genuine. If it did not hold on any, **repair the file rather than the output**, and run the attack again. Report the variation, whatever it was.

Step 5 is the S003 habit applied to a third domain and is now expected rather than prompted. Steps 6 and 7 are the build, and they are what the day ships: a check in code, the same claim in the register the agent reads, and evidence that one of them was attacked. The instructor time-boxes step 4 hard, because a rushed step 7 loses the day.

**The artefact carries three additional elements**, per the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** What you asked for, in the order you asked, including the instructions you abandoned and why.
- **Intervention record.** Every point at which you corrected the agent, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error — for this day, that means a step 7 attack that would have caught a violation had one occurred.
- **Frontier statement.** One thing the agent did well that you could not have done as fast, and one thing it did badly that you had to catch. Both from this build, both specific.

**Faded guidance:** step 1 is worked with the room for one invariant; step 2 is a completion problem for the first; steps 3 to 7 are independent, with the `applyTo` syntax supplied in writing at the moment of use.

**Warrant.** Whole-task at class 1, method given. Step 2 is the day's discriminator — an invariant that cannot be broken by a concrete caller was probably not an invariant. Step 7 is the same discriminator moved into the second register, and it is the step that prevents the instructions file being graded as prose.

## Phase 6 · Error clinic (40 min)

Instructor first: an invariant in the substrate that was true for eighteen months and stopped being true when a second team began calling the code. Emphasis on the fact that **nothing changed in the function**.

Instructor second, an agent case: a prompt that produced a function satisfying every clause of the instructions file and violating the invariant the file existed to protect. The clause said *validate the inputs*; the invariant was a relation between two of them. The agent reported success and was confident. **Two people reviewed the diff and neither caught it**, and the clinic's attention is on why: a reviewer reading a diff against a specification checks the clauses, and the defect was in the space between two clauses that both passed. This is the same authorless failure as the first case, one level up — nobody wrote a bug, and this time nobody wrote the code either.

Then students: a property your own code depended on that you only noticed when it broke.

Classified by phase 4 point 2's three locations.

**Warrant.** Error management. The instructor's first case is chosen so that the failure has no author — nobody wrote a bug — which is the point about unwritten invariants that a single-author story cannot make. The agent case is chosen so that the failure survived review, because a case the reviewer caught teaches that review works.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student hands their partner **one of their step 4 implementations** and the partner's task is to write a caller that is *legitimate* and that the new check now rejects.

If they succeed, the precondition was too strong — phase 3's error, reproduced in the student's own work.

**Warrant.** Interactive-tier articulation with an adversarial construction demand. The success rate is high and the phase's function is to make the strength trade-off personal rather than illustrative.

## Phase 8 · Calibration and commitment (20 min)

- Item 4 resolved: found counts against the reference list, with the gap shown.
- Item 3's transfer result reported to the room honestly, whichever way it fell, and what the design will do about it.
- **Item 5 unsealed.** Predictions are scored in two parts — what the agent produced, and where it was wrong — and the two rates are shown separately, unattributed. The cohort's *where will it be wrong* rate is entered in the programme's frontier map, whose reader is next year's cohort via the [Durable and Perishable Register](/wiki/program/09-Durable-and-Perishable-Register.md). The map is assembled from one cohort's builds on one substrate, and is labelled as that sample.
- Each student names one invariant in their own current work to surface before S009.
- Retrieval schedule: next morning, day 3, week 2, week 6.

## Assessment

Specification item in **CF101, not MS101** — deliberately, so that the argument stance is enforced in the programming course where students do not expect it.

The following elements are checked, each as a binary decision:

1. Three surfaced invariants.
2. A concrete breaking caller for each. **An invariant with no concrete breaking caller fails.**
3. Three justified visibility choices, each naming the reader it informs and the moment it fails.
4. One implementation, with the breaking caller run against it and the observed result reported.
5. The cost statement.
6. **The instructions file from step 6,** with its `applyTo` glob, and the References-list evidence that it was applied. A file whose application was not checked fails, whatever it says.
7. **The step 7 attack, its three runs and their outcomes,** including the repair if the file did not hold and the variation across runs if there was any.
8. **The prompt record.**
9. **The intervention record.** An intervention record with no entries fails unless element 7 demonstrates an attack that would have detected a violation.
10. **The frontier statement,** both halves, specific to this build.

**Nothing else is assessed.** Elegance, file length, prose quality and the number of prompts used are not assessed and are not commented on.

Elements 6 to 10 are added under the [Copilot Practice Standard](/wiki/program/12-Copilot-Practice-Standard.md), which binds every day in the programme. The [Assessment Architecture](/wiki/program/03-Assessment-Architecture.md) records that its three specification-writing rules bind from [S041](/wiki/seminars/S041.md) forward and that S001 to S040 are not retrospectively amended; that decision stands for the elements that predate this revision, and the checked list above therefore carries the sentence over its whole length rather than over its new elements alone, which a list carrying it for half its elements and not the other half could not do. The inconsistency is real, it is visible, and it is the correct trade: the day whose subject is that a specification must state what it checks cannot ship a specification that does not.

**Durable — assessed.** The three locations invariants live. The strength trade-off. The mapping to S005's three obligations. The no-author failure. That an unstated dependency is not enforceable and an unscoped specification is not in force. That a specification and an instructions file are the same object, and that a specification producing non-conforming work is defective.

**Perishable — the vehicle, not assessed.** The assertion, type and contract mechanisms available in the teaching language. The `.instructions.md` extension, the `.github/instructions` folder, the `applyTo` frontmatter key and the behaviour when it is omitted, the location of the References list and the chat customization diagnostics view, the published precedence between personal, repository and organization instructions, and the statement that instructions do not reach inline suggestions. All of the above are as documented on 15 July 2026 and are re-verified before every offering.

**Silences recorded.** The documentation states where instructions files live and when they apply, and states no measure of how reliably a conforming instruction produces conforming output. There is no published accuracy, and this day does not supply one either; the cohort's step 7 results are a sample of one cohort on one substrate.

**The published corpus, shown and not adopted.** Students are shown a public repository in which this day's claim has been taken to its conclusion at scale — instructions, prompts, agents and skills authored as source, packaged by manifest, generated into versioned plugins, and checked by a conformance suite that tests **the specifications themselves** rather than the work they produce. It is displayed for ten minutes, at a pinned commit, for one purpose: **the equivalence this day argues in prose is that repository's entire architecture**, and a student who has seen it cannot afterwards treat an instructions file as a note to the agent.

**Two things are said about it in the same breath, and the second is the one that is assessed later.** Its conformance suite has no committed results, and its own prose describes benefits nothing in it measures. **A specification you can check is not a specification that helps**, and the difference is the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md)'s five classes of conclusion arriving on the first day they have anything to attach to. Nothing about the corpus is assessed here, and nothing about it may be quoted without its commit.

## What to take from this day

**The claim to hold.** **The invariants you did not write down are the ones that break.** An unstated dependency is not enforceable and an unscoped specification is not in force. A repository custom instructions file is a specification whose conformance is checked by execution, so **a specification that produces non-conforming work is defective** — and here you find that out on the next prompt.

**What the sources license, and what they do not.** The unwritten-interface failure class and the multi-caller degradation pattern are verified here, at [research/05-fde-craft/evans-domain-driven-design.md](/research/05-fde-craft/evans-domain-driven-design.md), and phase 6's disclosure norms at [research/04-professional-formation/edmondson-psychological-safety.md](/research/04-professional-formation/edmondson-psychological-safety.md). Transfer-appropriate processing, contrasting cases and error management training are cited for **direction and mechanism only** with no effect size asserted, and the jagged-frontier mechanism behind item 5 for direction alone. The corpus is recorded at [research/06-microsoft-platform/hve-core-repository.md](/research/06-microsoft-platform/hve-core-repository.md) at a pinned commit, and **it establishes an architecture and nothing about whether a conforming instruction produces conforming work.**

**Guidance for your own work.**

- **For every invariant, write the caller that breaks it.** An invariant with no concrete breaking caller was probably not one.
- **Check that your specification was applied, not that it exists.** The References list is the evidence; a file on disk is not.
- **Attack it more than once**, and repair the specification rather than the output when it fails.
- **A control is not evidence.** A conformance suite tests the *shape* of a specification and never whether the specification helps — which is the distinction the five classes on the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md) exist to keep open.

**Where this is easy to get wrong.** Treating a file that reads correctly as a rule in force. It shipped because it read correctly — and the defect that costs you sits in the space between two clauses that both passed.
