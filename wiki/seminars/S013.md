# S013 · Hashing and Amortised Reasoning

**Module:** [M03](/wiki/modules/M03.md) · **Quarter:** [Q2](/wiki/quarters/Q2.md) · **Complexity class:** 1
**Strands:** CF · MS
**Whitepaper:** [WP-013](/wiki/whitepapers/WP-013.md)
**Depends on:** S004
**Re-tests:** S011, S012

**Platform anchor:** Microsoft Foundry embedding deployment under its TPM and RPM quota — the 429, the reset boundary, and the two token counts
**MCP servers:** Microsoft Learn MCP Server (grounding) · Azure MCP Server, Read only = true

---

## What this day is for

A hash table is the structure students reach for by default, and the reason they give — constant-time lookup — is a claim about an average over a sequence, stated as though it were a property of an operation.

The distinction is the day's content. **A worst-case claim and an amortised claim are both true, about different things, and each is the relevant one for a different caller.** The user waiting on a single request cares about the worst case. The batch job processing a million records cares about the total. Neither is being pedantic and neither answer is the real one.

The day's second structure is a Foundry deployment under quota, and it is here because it is a resize spike with a bill attached. A deployment's rate limit is enforced against a **running token count that resets every minute**, so the same request succeeds at 12:00:59 and returns 429 at 12:00:58 — a bucket boundary producing a tail exactly as a doubling does. And the platform holds **two different true token counts for one request**: an estimate computed at admission, which decides whether you are throttled, and a count computed after processing, which decides what you are charged. The day's terminal demand is two true reports from one measurement. The platform gets there first.

This is the module's highest-load day and its only one where the same structure has two correct cost answers.

## Phase 1 · Pretest and prediction (25 min)

Four items.

1. A hash table's insert is described as constant time. A sequence of $n$ inserts is timed and one of them takes far longer than the others. Has the claim been violated?
2. Two systems are given: one with uniform 10ms responses, one averaging 4ms with occasional 900ms responses. Which is better?
3. For which caller is your item 2 answer wrong?
4. Predict: will the room agree on item 2?

Item 3 is the day's move and most students cannot answer it before instruction.

**Copilot prediction, sealed.** *In phase 5 you will ask Copilot to make an embedding workload "robust". Write down now: what will it do about the 429, will it distinguish a 429 from a 400, and what will it report to the caller while it is retrying?* Opened at phase 8.

**Warrant.** Pretesting with a perspective-shift demand. Item 2's disagreement is real and is the day's opening fact; item 3 converts a preference into a question about who is asking. The Copilot item targets the specific failure the day's phase 6 discloses — an agent that makes a system look healthier than it is — and is sealed before instruction, per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

Groups receive **one hash table implementation and four callers**, each with a documented requirement.

- **Caller A** processes a batch overnight. Total time matters; individual operations do not.
- **Caller B** serves interactive requests with a stated response-time limit.
- **Caller C** serves interactive requests and is behind a queue with a timeout.
- **Caller D** runs inside a real-time control loop where a single overrun is a failure.

Groups decide, for each, whether the amortised claim is adequate, and commit.

Then the operation-by-operation timing distribution is supplied — including the resize spikes.

**Then the same four callers are run against a real Foundry embedding deployment, and the cases are executed.**

| Case | What is run | What it exposes |
|---|---|---|
| A | The batch caller's workload as one array of inputs | Excellent total, one long wait, and a per-item mean that describes nobody |
| B | The same tokens as individual interactive calls | The same total, a different distribution, and a tail with a clock in it |
| C | Case B repeated until the deployment's per-minute counter is breached | The 429, and the reset boundary that makes an identical request succeed a second later |
| D | Case C behind the MCP client's default retry policy | A caller who sees no error at all, and waits |

**Case D is the payload.** Groups predict that the retry policy fixes case C. It does — for the operator, whose error rate falls to zero — and it converts caller C's problem into caller B's, because exponential backoff with three attempts is a decision about how long somebody waits before finding out. Nobody in the room made that decision. It shipped as a default.

Task after: **for the callers where the amortised claim is inadequate, state what claim would be adequate**, and whether the structure — or the deployment — can supply it.

Caller C is the case that defeats groups, because the queue makes an individual spike into a systemic effect. The platform version makes it visible in twenty minutes rather than deferring it entirely.

**Warrant.** Contrasting cases across callers rather than across structures — the module's first — with a distributional adjudicator. The four executed platform cases mirror the four analytic callers exactly, so the phase teaches one contrast twice rather than two contrasts once. Caller C plants queueing for S019; case D plants retry policy for S019 and S062.

## Phase 4 · Consolidating instruction (50 min)

1. **Hashing: what it buys and what it discards.** Order is discarded, and with it range queries and predecessor queries. S011's pair applied.
2. **Collisions and load factor**, briefly, as the mechanism behind the cost.
3. **The general phenomenon, then the instance.** Aggregate statistics conceal distributions. That is the durable idea, and it has many causes — collection pauses, contention, scheduling, network variance, rate-limit boundaries. **Amortised resizing is the one instance you can see all the way through today**, because you can count the copies and predict the spike exactly, and that is why the day is built on it. The general framing comes first deliberately, so that the technique is not mistaken for the idea.
4. **Amortised analysis** — the sequence as the unit. The aggregate argument for table doubling, worked completely.
5. **What amortised does not say.** It does not bound any individual operation, and no amount of averaging makes it do so.
6. **Worst case, amortised, expected, and observed distribution** as four different claims about the same structure, each with its own reader — S004, directly. **The list is four because four is what this day can work through, not because there are four.** Percentile bounds, service-level objectives and conditional claims are all omitted and arrive at S019, S028 and S062.
7. **Which caller needs which**, indexed to phase 3's four.
8. **Tail latency as the honest report**, named here and developed at S019 and S062. The mean is not the summary you owe an interactive caller.
9. **The platform holds two true token counts for one request, and this is documented.** The rate limit is enforced against an **estimate computed when the request is received** — derived in part from the character count of the request — and that estimate is explicitly *not* the count used for billing, which is computed after processing completes. So the answer to "how many tokens was that" is two numbers, both true, one of which decides whether you are throttled and the other of which decides what you pay. The response body reports the second. Nothing reports the first. This is phase 5 step 6 arriving from the platform rather than from the student, and it is the strongest available evidence that the day's demand is a real professional situation rather than a classroom device.
10. **What the platform chose for you, and what is perishable.** The counter resets each minute; that boundary is a policy, not a physical fact, and it manufactures a tail. The Azure MCP Server's default retry policy — exponential, three attempts, two-second base, ten-second cap, hundred-second network timeout — is a decision about your caller's worst case that arrived with the tool. **Dynamic quota, currently preview, lets a standard deployment opportunistically exceed its configured TPM when spare capacity exists, and the extra requests are billed at the regular rate**; a team that enables it has changed its latency distribution and its bill together, and only one of those is visible on a dashboard. **Safe** to reason with against this service at this documented behaviour; **unsafe** at any other version, and unsafe as a claim about any other service's throttle, because the shape recurs and the numbers, the boundary and the preview status do not.

**Warrant.** Consolidation indexed to phase 3's callers. Point 6 makes the day an argument day as much as a structures day and is the reason S004 is a retrieval source. Point 3 is the framing correction [WP-013](/wiki/whitepapers/WP-013.md) §8 conceded was missing: the general idea is stated before the narrow technique rather than after it. Point 9 is reachable from phase 3 cases C and D rather than asserted, per instrumentation rule 7.

## Phase 5 · Whole-task learning task (90 min)

**The output is a build.** Students take a substrate component that calls the embedding deployment under real load, and ship an instrumented version of it to a disposable environment, directed through Copilot agent mode.

1. **State both claims.** Worst case and amortised, with the reasoning for each.
2. **Name a caller for whom each is the relevant one.** Real callers from the substrate where possible.
3. **Predict the observed distribution's shape**, including where the tail sits and which mechanism puts it there. Commit in writing.
4. **Build and measure.** Direct the agent to instrument the component so that the per-request latency distribution, the response's reported token usage, and every non-200 with its status code are all recorded separately. Ground the status-code meanings with the Learn MCP Server, not with the agent's memory.
5. **Reconcile.** If the tail is worse than predicted, say which mechanism you omitted.
6. **State what you would report** to each of your two callers from step 2 — two different sentences, both true.

Step 6 is the day's payload: two true reports from one measurement.

**Artefact elements.** As at S011 and S012, and assessed.

- **Prompt record** — the instructions given, in order, including abandoned ones.
- **Intervention record** — every correction and what it was. **Empty fails**, unless the build demonstrates that an intervention-worthy error was detectable: here, that a 429 absorbed by a retry is still recorded and still visible in the instrumented output.
- **Frontier statement** — one thing the agent did faster than you could have, one thing it did badly that you caught.

**Faded guidance:** the amortised argument at step 1 is worked with the room; step 3's prediction template is supplied, and it requires a mechanism rather than a shape; the deployment and credential are supplied.

**Warrant.** Whole-task at class 1. Step 6 is the S004 reader question with a distribution as the subject, and is the first time a student produces two different true statements from one body of evidence. Step 4's separate recording of latency, usage and status is the instrumentation that makes step 6 possible; without it a student has one number and can only paraphrase.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate incident caused by a resize spike under load, where the structure's average performance was excellent throughout — with attention to what the monitoring reported and why it looked fine.

**Then the agent case.** Asked to make an embedding client "robust", Copilot produced a competent retry wrapper: exponential backoff, jitter, a sensible cap, clean logging of the final outcome. It caught every 429 and it also caught the 400 from an oversized batch and retried that too, three times, before giving up — turning an immediate permanent failure into a slow permanent failure and reporting a success rate that was unchanged because the eventual failure was logged the same way. Two students reviewed it. Both approved it, because **the code was defensive and defensiveness reads as correctness**, and because the dashboard the wrapper fed had never looked better. Attention on the review: the reviewers checked whether errors were handled and not whether they were *distinguished*, which is the shape of nearly every retry bug in production.

Then students: a claim you made about performance using an average.

**Warrant.** Error management, with a disclosure whose monitoring dimension seeds S068 and S079. The agent case is the required sixth element and pairs deliberately with the instructor's: both are systems that concealed a problem from the person who could have fixed it, one by averaging and one by retrying.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student reads out **one of their two step 6 reports**, without saying which caller it is for. The partner must identify the caller.

Then the harder half: the partner must state what the report **conceals** from the other caller, and whether concealing it is legitimate.

Then the same question, asked about a system neither of them built: **the embeddings response body reports the token count used for billing and does not report the estimate used to decide whether you were throttled. What does that conceal from you, and would you call it legitimate?** The pair answers as the party who was not told, which is a different and easier seat than the one they have just occupied.

**Warrant.** Interactive-tier articulation. The second half is the programme's first direct encounter with selective true reporting, and it is deliberately left unresolved — the question of when omission becomes misrepresentation is opened here and answered at S050 and S088. The third question moves the student from discloser to recipient without pre-empting either later day, and it is the design's answer to [WP-013](/wiki/whitepapers/WP-013.md) §8 objection 3.

## Assessment

Specification item in CF102. The checked elements are: both claims with reasoning; two named callers; the committed distribution prediction with its mechanism; the measurement from the instrumented build; the omitted-mechanism reconciliation; the two reports; **the prompt record**; **the intervention record**; and **the frontier statement**.

**Two reports that differ only in wording fail the specification.** They must differ in what they assert. An intervention record with no entries fails unless the build records a retried 429 rather than absorbing it.

**Nothing else is assessed.** The agent's output quality is not assessed, the phase 1 Copilot prediction is not assessed, and phase 3 cases C and D are instruction rather than evidence.

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| Aggregate statistics conceal distributions | Resize spikes, and a per-minute counter boundary |
| Amortised does not bound any individual operation | A 429 that an average throughput figure cannot show |
| A claim's adequacy is relative to a caller | Four callers, run |
| Two true numbers can describe one event | The admission estimate and the billed count |
| A default is a decision about somebody's worst case | Exponential, 3 attempts, 2s, 10s cap, 100s timeout |
| Tail latency is the honest report | The measured distribution, not the mean |

The left column is assessed. The right column is the vehicle and will change. The implementation's load factor, growth policy and measured spike magnitudes, every quota behaviour at point 9 and point 10, and dynamic quota's preview status are all **perishable** and are marked.

## What to take from this day

**The claim to hold.** **A worst-case claim and an amortised claim are both true, about different things, and each is the relevant one for a different caller.** Amortised analysis bounds a sequence and bounds no individual operation, and no averaging makes it do so. Aggregate statistics conceal distributions, so tail latency is the honest report to an interactive caller.

**What the sources license, and what they do not.** Tail latency as the honest report, and the monitoring failure mode phase 6 discloses, are verified here, at [research/02-technical-foundations/kwon-pagedattention-vllm.md](/research/02-technical-foundations/kwon-pagedattention-vllm.md) and [research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md). Contrasting cases, prediction before adjudication and error management training are cited for **direction and mechanism only**, with no effect size asserted. The two token counts and the reset boundary are documented behaviour at one version, and no rate of occurrence is published for any of it.

**Guidance for your own work.**

- **Ask who is asking before you answer how fast it is.** The batch job and the person waiting need different sentences, and both can be true.
- **Distinguish your errors, do not merely handle them.** A retry that swallows a permanent failure turns an immediate refusal into a slow one and leaves the dashboard looking better.
- **Record the status codes separately from the latencies.** A 429 absorbed by a retry still happened.
- **A clean log is not an outcome.** A retry wrapper is a configured control and its output is at best an observed result — the ladder on the [Agent Configuration Standard](/wiki/program/13-Agent-Configuration-Standard.md) exists so that you do not read either of those rows as the fourth one.

**Where this is easy to get wrong.** Approving defensiveness as correctness. The code caught everything, the logging was clean, the dashboard had never looked better, and the reviewers checked whether errors were handled rather than whether they were told apart.
