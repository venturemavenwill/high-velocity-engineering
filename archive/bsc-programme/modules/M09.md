# M09 · Learning From Data

**Quarter:** [Q5](/archive/bsc-programme/quarters/Q5.md) · **Seminar days:** [S041](/archive/bsc-programme/seminars/S041.md)–[S045](/archive/bsc-programme/seminars/S045.md) · **Complexity class:** 3
**Strands:** IS · MS · ME · SG
**Platform anchor:** Foundry model catalogue, deployment and cloud evaluation · Defender AI posture management at S044
**MCP servers:** Foundry MCP Server (preview) · Azure MCP Server · Microsoft Learn MCP Server

---

## The central difficulty

A learned component's behaviour is not derivable from its construction. You can read every line of the training code and every hyperparameter and still not know what the model will do on an input you have not tried.

This is a genuinely new epistemic situation for these students. Four quarters have taught that behaviour follows from structure — an invariant holds, a contract is specified, a paradigm's hypothesis is checked. None of that applies here. **The only access to a learned component's behaviour is measurement, and measurement of a distribution you did not choose.**

The module's stance: **generalisation is the only property that matters, every other number is a proxy for it, and the proxies fail in known ways.** A student who evaluates on data the model has seen has learned nothing and will not know it.

## The module's platform spine

One model runs through all five days, and it lives on Foundry from the first hour.

| Day | What the student operates | Through |
|---|---|---|
| S041 | The catalogue's own benchmark data, then a first cloud evaluation run | Foundry MCP Server · `model_benchmark_get` |
| S042 | A versioned evaluation dataset, consulted a counted number of times | Foundry cloud evaluation · `evals.create` and `evals.runs.create` |
| S043 | A fine-tuning method choice and the hyperparameters the service resolves for you | Foundry fine-tuning · `supervised`, `dpo`, `reinforcement` |
| S044 | Four infrastructure-as-code checks against the deployment template | Defender for Cloud AI security posture management |
| S045 | A live model deployment, and a feature flag in front of it | Foundry MCP Server · `model_deploy`, `model_deployment_get` |

**Every day produces a build.** Phase 5 is not a paper exercise anywhere in this module: the student ships something to the substrate or to a disposable environment, using Copilot agent mode against a named service through a named MCP server, and the artefact carries a prompt record, an intervention record and a frontier statement per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md).

**The Foundry MCP Server is in public preview** and every day in this module says so. A student operating a preview interface learns something the documentation cannot teach them: that the tool list is a moving target, that a prompt which worked last term may route to a tool that no longer exists, and that "it worked when I tried it" is a statement about a date.

## The claim this module discharges

The programme claims a graduate can architect and ship a working AI system principally by prompting Copilot, and can say what it does badly. **M09 is where the second half is assessed for the first time on something a real person will use.** The first half is comparatively easy to demonstrate and comparatively worthless on its own: an agent will produce a training script, a deployment and an evaluation run from three prompts. What it will not produce is the sentence naming who this model will fail, how often, and what you will do about it — because that sentence requires knowing what the user will do with the answer, and the agent does not know that.

## Why this module sits here

**It requires M06 entirely.** Construct validity, error structure, sampling and instrument design are all preconditions. A student without them will report accuracy figures and believe them.

**It requires M05's guarantee taxonomy.** S022's individual-versus-population sentence is the foundation of every claim a model makes, and [WP-022](/archive/bsc-programme/whitepapers/WP-022.md) §9 Prediction 4 named S041 as its deferred test.

**It requires M08's problem construction.** A model is trained toward an objective somebody chose, and a student who cannot ask where a request came from cannot ask where a loss function came from.

**It precedes M10 deliberately.** M09 evaluates against criteria that are supplied. M10 asks where they came from, which is the class-4 move.

## Task-class variability plan

The module varies **the way a generalisation estimate becomes optimistic**, because that is the single failure with the most forms.

- **S041** varies the leak: four ways information from the evaluation set reaches the model, none involving training on test data.
- **S042** varies the selection procedure: same data, four protocols, and the reported figure differs by more than the models do.
- **S043** varies capacity against data size, where the same regularisation is correct and incorrect either side of a threshold.
- **S044** varies the adversary: four actors with different access and different goals.
- **S045** varies nothing. It is the entrustment occasion.

## Load profile

High throughout, with S042 the peak.

S042 is the hardest because its content is a *protocol* rather than a technique — the discipline of deciding how you will choose before you choose — and because its failure mode is invisible in every artefact the student produces. It is placed second so that S043 and S044 can apply it rather than precede it.

The module's standing load reduction is that **one dataset and one task run through all five days**, drawn from the substrate, with a real deployment target at S045.

## Module-level predicted failure modes

**Accuracy reported as a property.** The module's defining failure. Countermeasure: every artefact requires the figure to be stated with its population, per S028's licensing sentence, and S041's specification fails an unqualified figure.

**Leakage undetected.** Students avoid the obvious leak and produce three subtler ones. Countermeasure: S041's phase 3 supplies four leaks of which one is obvious, and the artefact requires a leak audit rather than an assertion.

**Selection protocol written afterwards.** S042's risk, and the module's least visible. Countermeasure: the protocol is committed and timestamped before any model is trained, and a protocol matching the eventual selection exactly is treated as suspect rather than as good.

**The threat model becomes a list.** S044's risk. Countermeasure: each threat requires an actor with stated access and a stated goal, and threats with no actor fail.

**A judged score treated as a measurement.** New in this module and specific to the platform. Foundry's evaluators return a number between one and five with a threshold and a pass label, and the number looks exactly like a measurement. **No agreement-with-human data is published for any of them.** Countermeasure: every artefact carrying a judged score carries the sentence stating that it is uncalibrated, and a score reported without it fails the same way an unqualified accuracy figure does.

**The build accepted rather than directed.** The module's agent-specific failure. A student prompts, receives a training script and a deployment, and ships. Countermeasure: the intervention record, whose empty state fails unless the artefact demonstrates that the design could have detected an intervention-worthy error — a batch-size assertion, a threshold check, an evaluation gate. A student who built the detection has not been penalised for not having intervened.

## Assessment contribution

**One entrustment judgement, at S045.** The activity is *train, evaluate and deploy a learned component, and state what it will do badly* — a precursor to EA-1. Expected 2a–2b. Two assessors judge independently and form the level from the artefact before the defence, per rater discipline rule 7. **A defended decision not to deploy is a pass; a deployment with no stated failure modes is not.**

Specification items:

- **S041** — a generalisation estimate with its population, and a completed leak audit.
- **S042** — a selection protocol committed before training, with what it forbids.
- **S043** — a capacity choice with the assumption it makes about the data, and the point at which the assumption fails.
- **S044** — a threat model with actors, access, goals, and the threats deliberately accepted.
- **S045** — the deployed model, its evaluation, its stated failure modes, and the defence.

**Every one of the five also carries the prompt record, the intervention record and the frontier statement**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). These are cheap to produce, hard to fake, and are the elements that distinguish a student who directed the work from one who accepted it.

**S045 carries the module's unassisted-work provision.** Phase 3's decision hour is performed without agent assistance — one of the three such occasions in the programme, with S010 and S090. The assisted-versus-unassisted comparison is reported to the student and to the programme and is **not used to award a level.**

Dispositions observed: **integrity** at S041 and S042, where an unreported leak or a retrofitted protocol is undetectable; and at S045, where the stated failure modes are checkable against the student's own S041 and S043 evidence.

## Perishable content in this module

| Durable claim | Platform instance, perishable |
|---|---|
| A held-out estimate estimates the population its set was drawn from | The catalogue's normalised benchmark index and its own "might not reflect performance on your specific data" caveat |
| Selection is search; a maximum is not an estimate | Cloud evaluation runs against a versioned dataset, and their count |
| Capacity is a structural hypothesis about the data | `supervised` versus `dpo` versus `reinforcement`, and the `auto` hyperparameter resolution |
| A threat is an actor with access and a goal | The four Defender IaC check names and Defender CSPM's plan boundary |
| A deployment decision is not an evaluation decision | The Foundry deployment name, the feature flag, the withdrawal signal |
| A judged score is uncalibrated until its agreement is published | Every Foundry evaluator, the 1–5 scale, and the threshold of 3 |

All evaluator names, scale endpoints, thresholds, deployment-type SKU codes, tool names and check names are **perishable**. The five durable claims are what the specifications assess.
