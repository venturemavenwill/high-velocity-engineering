# M08 · Understanding the Problem Before the Solution

**Quarter:** [Q4](/archive/bsc-programme/quarters/Q4.md) · **Seminar days:** [S036](/archive/bsc-programme/seminars/S036.md)–[S040](/archive/bsc-programme/seminars/S040.md) · **Complexity class:** 3
**Strands:** PE · CF · SY
**Platform anchor:** Azure API Management AI gateway — the `llm-token-limit` policy and the quota behind it · Bicep · **MCP servers:** Azure MCP Server (write, except [S040](/archive/bsc-programme/seminars/S040.md)) · Microsoft Learn MCP Server

---

## The central difficulty

Students are good at solving problems and have almost no practice constructing them. Every problem they have been given arrived pre-formed: the specification was written by someone who knew the answer, the ambiguity had been removed, and the work was to satisfy it.

Professional work does not arrive that way. It arrives as a request, and **the request is not the problem**. Somebody has already performed an analysis — badly, under pressure, without the information you will have — and handed you its output. Accepting it is the most common and most expensive failure in engineering practice, and it is invisible, because the engineer who builds exactly what was asked has done nothing wrong by any standard the organisation applies.

The module's stance: **the problem is something you construct from evidence and are answerable for, and the request is one piece of that evidence.**

## Why an agent makes this module more necessary, not less

**Copilot is extremely good at building what you asked for.** That is not a criticism of it; it is what it is for, and on this module's material it is faster and cleaner than any student in the room. Given a substrate user's request, an agent in write configuration will author the gateway policy, author the Bicep, deploy it through the Azure MCP Server and report success — in minutes, with no defects a reviewer would catch.

Which is exactly why [S036](/archive/bsc-programme/seminars/S036.md)'s question matters more now than it did before agents existed. The only thing that ever protected an engineer from building the wrong thing well was that building it was slow enough to think during. That protection is gone. What is left is the discipline of asking what the request was for, and there is no tool that performs it, because it requires knowing what the requester will do with the answer.

So the module is built around a specific artefact: **an agent's fast, clean, confident implementation of the wrong thing.** Students produce it themselves at [S036](/archive/bsc-programme/seminars/S036.md), they instrument it at [S037](/archive/bsc-programme/seminars/S037.md), they find out at [S038](/archive/bsc-programme/seminars/S038.md) that it is named in a vocabulary nobody in the domain uses, they negotiate the constraint it was built against at [S039](/archive/bsc-programme/seminars/S039.md), and at [S040](/archive/bsc-programme/seminars/S040.md) they are handed one and asked why a working implementation is not an answer.

**The module's hardest design problem is that this is also its largest risk**, and it is stated here rather than left to the whitepapers: a module about restraint whose days now end in a deployment can teach the opposite of its subject. The response is the build rule below, and the honest position is that the rule is a constraint on the design rather than a guarantee about it. [WP-036](/archive/bsc-programme/whitepapers/WP-036.md) §8 argues it at length and concedes what it cannot establish.

## The build rule: every M08 build is an instrument, not a remedy

The [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md) requires every seminar day's phase 5 to produce a build. The module's standing rule is that **no artefact in M08 may contain a proposed solution.** Both hold, and they hold together because of a distinction the module makes explicit:

> **An M08 build produces evidence about the problem. It does not change what the substrate does for its users.**

S036 ships the request implemented literally, into a disposable resource group, in order to find out what building it as asked actually produces. S037 ships a telemetry policy that records the session. S038 ships an instructions file and the Bicep an agent generates from it. S039 ships an evidence pack. Not one of them is a fix, not one is deployed to the substrate's production path, and every one of them exists to make a characterisation checkable that would otherwise be an opinion.

**A build that changes the user-facing behaviour of the substrate fails the specification on the day that produced it.** This is the solution prohibition in its platform form, and it is the mechanism by which the module survives becoming build-centred.

## Why this module sits here

**It requires M07's specification stance.** A student who thinks correctness is received cannot understand that a problem is constructed. M07 taught the first on material where the costs are measurable; M08 applies it where they are not.

**It requires real users and the practice of talking to them.** S015 introduced a caller; S037 makes inquiry the object rather than the means, which is only possible once students have done it once badly.

**It requires write access to something real.** Q4 is where the Azure MCP Server moves from read to write, and this module is where a student first uses an agent to change infrastructure. That is deliberate: the request-need gap is an abstraction until the student has personally deployed a correct implementation of a request and watched it fail to help anybody.

**It must precede Q5.** Every day from S041 onward involves deciding what a system should do, and the answer is never in the request.

**It ends the quarter with an endurance exercise** rather than a production event, deliberately. M07 closed on execution; M08 closes on refusing to execute — and, now, on refusing to execute something an agent has already built for you.

## Task-class variability plan

The module varies **the source of the misdirection**, so that "the request is not the problem" is understood as a family rather than as a slogan.

- **S036** varies who framed the request and what they were optimising when they framed it.
- **S037** varies what people say against what they do — the same user, described and observed.
- **S038** varies the vocabulary: the same entity named four ways by four groups, each name carrying a different model.
- **S039** varies the constraint that is genuinely immovable, which is rarely the one stated as immovable.
- **S040** varies nothing. The problem is unsolved and stays unsolved for six hours.

## Load profile

Moderate throughout and unusual in shape: the module's difficulty is almost entirely **tolerance** rather than complexity.

S037 and S040 are the demanding days and neither is intellectually hard. S037 requires sitting with a person for an extended period without steering them; S040 requires holding an unresolved problem for six hours while every instinct pushes toward a solution. Both are affectively costly and both are the module's point.

The module's standing load reduction is that **one real unaddressed need runs through all five days**, supplied by the substrate's users and not yet analysed by anyone. Its platform reduction is the same shape: **one service, one policy, one constraint across all five days** — the substrate's AI gateway, its `llm-token-limit` policy, and the model-deployment quota behind it. Comprehension load on the platform is paid once for the module, and the days differ in what they ask of it rather than in what they are pointed at.

## The running need

The module's need is a real unaddressed request from a substrate user, and since the Q4 re-anchoring it concerns the gateway: **users are being refused, and somebody has written down what they think should be done about it.** The request is short, specific, reasonable, and implementable in an afternoon by an agent. Whether it is the problem is what the module is for.

The substrate supplies the rest: a real requester, a real capacity owner who can decline, real telemetry, and a real limit that somebody chose. Per the [Substrate and Infrastructure](/archive/bsc-programme/program/10-Substrate-and-Infrastructure.md) page, the monthly ceiling is enforced at the gateway rather than discovered on an invoice, which is why this constraint is one students can both observe and argue with.

## Module-level predicted failure modes

**Premature convergence.** The module's defining failure and the reason S040 exists. Countermeasure: every day's artefact is a characterisation rather than a proposal, and S040's specification fails any artefact containing a solution.

**The build crowds out the problem.** The module's new failure and the one introduced by its own practical turn. A day that ends in a working deployment supplies a completion the module is trying to withhold, and a student who has shipped something feels finished. Countermeasures: the build rule above, which makes every build an instrument rather than a remedy; the requirement at S036 and S039 that the artefact state what the build *did not* establish; and the placement of the module's only unshippable day last, where it cannot be redeemed by a deployment. **This countermeasure set is unvalidated.** It is argued in [WP-036](/archive/bsc-programme/whitepapers/WP-036.md) §8 and [WP-039](/archive/bsc-programme/whitepapers/WP-039.md) §8 and conceded in both.

**Inquiry as requirements-gathering.** Students conduct an interview to confirm a solution they already hold. Countermeasure: S037's artefact is an observation record with a stated separation between what was said, what was done and what the student inferred.

**The model becomes the engineer's.** S038's risk: a vocabulary the domain expert does not use. Countermeasure: the model is validated by the expert reading it back, and terms they do not use fail. The platform sharpens this rather than softening it — the gateway supplies a ready-made vocabulary of its own, and it is not the domain's.

**Negotiation becomes accommodation.** S039's risk: the student concedes every constraint. Countermeasure: the day's artefact requires a constraint the student successfully moved and the argument that moved it.

**The agent's output is treated as a finding.** New, and specific to this module's material. An agent that implements a request produces a working system, and a working system reads as evidence that the request was right. Countermeasure: every day's Copilot prediction is sealed at phase 1 and opened at phase 8, so the agent's behaviour is something students predicted rather than something they received.

## Assessment contribution

**One entrustment judgement, at S040.** The activity is *characterise a problem from evidence and defend the characterisation to someone who asked for something else* — a precursor to EA-3. Expected level 2a to 2b.

Specification items:

- **S036** — the request, the problem behind it, and the evidence separating them.
- **S037** — an observation record separating said, done and inferred, with one thing observed that contradicts what was said.
- **S038** — a model in the domain expert's vocabulary, validated by them reading it back.
- **S039** — a requirement both parties hold, with the constraint that moved and the argument that moved it.
- **S040** — the characterisation, defended, containing no solution.

**Every specification item in the module additionally carries the three elements the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md) requires** — a prompt record, an intervention record and a frontier statement. At S040 the intervention record is empty by construction, because correcting the agent would be proposing, and the specification's escape clause therefore becomes the day's sharpest assessed element rather than an addition to it.

Dispositions observed: **humility** at S037 and S038, **integrity** at S039 in whether the reported agreement is the actual one.

## Perishability

The module's durable claims are the request-need gap, say-do divergence, name-as-model, purpose-before-mobility and the stopping criterion. **The gateway, the policy, the status codes, the metric names, the quota mechanics and every number attached to them are perishable**, and each day carries its own register separating the two. Per the [Microsoft AI Platform Map](/archive/bsc-programme/program/11-Microsoft-AI-Platform-Map.md), a re-anchoring changes the vehicle and not the claim; if it turns out that a durable claim cannot survive re-anchoring, that is a finding about the claim and is recorded as one.
