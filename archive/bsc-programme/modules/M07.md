# M07 · Correctness at Scale

**Quarter:** [Q4](/archive/bsc-programme/quarters/Q4.md) · **Seminar days:** [S031](/archive/bsc-programme/seminars/S031.md)–[S035](/archive/bsc-programme/seminars/S035.md) · **Complexity class:** 3
**Strands:** SY · CF · MS
**Platform anchor:** Azure API Management AI gateway, one instance across all five days · **MCP servers:** Azure MCP Server (**write**) · Microsoft Learn MCP Server

---

## The central difficulty

Students hold correctness as a property a program either has or lacks. Under that model, a concurrent program is a sequential program with a bug in it, and the remedy is to find the bug.

The model does not survive contact with concurrency, and the reason is not that concurrent programs are harder. It is that **there is no single correctness property to have.** A concurrent system can be linearizable, or sequentially consistent, or eventually consistent, or something weaker still, and each is a different promise to the caller with a different cost. Choosing among them is the engineering act, and no amount of debugging substitutes for it.

The module's stance: **correctness at scale is a contract you select and defend, and the selection is made before the code exists.** This is complexity class 3 — the student chooses the method and the success criterion — and concurrency is the cleanest domain in which to install it, because the criterion is genuinely underdetermined and the consequences of choosing wrongly are observable.

## The module's component is a gateway

Every day of M07 runs against **one Azure API Management instance fronting one model deployment**, deployed on day one and torn down at the module's end. It is the module's substrate component in the sense the load profile requires — comprehension load paid once — and it is chosen because it is the smallest real system in which all five days' subjects are simultaneously present and measurable.

A gateway in front of a model endpoint is a distributed system with a shared finite resource, an approximate limit, a cache that answers questions it was not asked, backends that fail independently, and consumers who assume more than they were promised. **Every one of those is an M07 day**, and none of them is a metaphor.

The module makes one claim about this choice and it is bounded. The gateway is used because the platform's own documentation states, without qualification, the properties the module teaches: that a distributed limit is never exact, that a similarity threshold is a correctness knob, that circuit-breaker rules do not synchronise across gateway instances, and that a deployment preview omits what it cannot evaluate. **Those statements are evidence that the vendor knows this; they are not evidence that the module's claims are true.** The durable claims are grounded in [research/02-technical-foundations/](/research/02-technical-foundations/collected-materials.md); the gateway is where students meet them with a bill attached.

## Write access, and what the module does about it

This is the first module in which the agent creates and deletes real resources.

The risk is stated plainly because it cannot be exhorted away: **a student can now produce a working gateway configuration they could not have written and cannot review.** The module's response is three structural measures, not one attitude.

1. **Every phase 5 build is preceded by a stated expectation and followed by a measurement.** A student who cannot say what the configuration will do has not finished the design step, whoever typed it.
2. **Every build carries a prompt record, an intervention record and a frontier statement**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). The intervention record is the element that distinguishes direction from acceptance, and an empty one fails unless the artefact itself would have caught an intervention-worthy error.
3. **S035 characterises the review instrument.** `what-if` is treated as an instrument in [S029](/archive/bsc-programme/seminars/S029.md)'s sense, with its false positives and false negatives established from the vendor's own documentation before any student relies on it. This is the module's answer to the dependency risk and it is the only one that survives the objection, because it does not depend on students choosing to be careful.

What the module cannot do is detect a student who has become unable to build without the agent. That is the programme-level risk recorded on the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md), and M07 adds no instrument for it.

## Why this module sits here

**It requires M06's evidential discipline.** S035's central act is deciding what "working" means for a system nobody specified, and then falsifying it. Without S026's construct discipline and S029's instrument design, that day collapses into ad hoc testing.

**It requires M05's acceptance of proved impossibility.** A student who reads a consistency trade-off as a temporary engineering limitation cannot make S034's choice. [WP-023](/archive/bsc-programme/whitepapers/WP-023.md) §9 predicted exactly this dependency.

**It must precede M08.** Requirements work assumes a student who knows that a specification is a construction with costs, which is what this module demonstrates on material where the costs are measurable.

## What every day carries

Per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md), and without exception in this module:

- **A sealed Copilot prediction at phase 1** — what will the agent do, and where will it be wrong — opened at phase 8.
- **Four contrasting cases executed against the running gateway**, not read from a handout. The payload case is the one whose measured behaviour defeats the room's prediction.
- **At least one perishable platform-specific point at phase 4**, and at least one naming a default the platform chose. *Defaults are opinions and thresholds are policy.*
- **A build at phase 5**, with a prompt record, an intervention record and a frontier statement.
- **An agent failure in the error clinic** — a case where Copilot was confidently wrong and review did not catch it.
- **A perishability register** separating the durable claim from the platform instance.

One day's cases cannot be operated. **S033's circuit-breaker tier restriction is demonstrated rather than operated** where the programme's instance is not on a tier that supports it, and in that condition it is not assessed. Which condition applies is checked before each offering, per the [Durable and Perishable Register](/archive/bsc-programme/program/09-Durable-and-Perishable-Register.md).

## Task-class variability plan

At class 3 the criterion is the student's, so variability is in **what makes the criterion hard to choose**.

- **S031** varies the property: same program, four correctness properties, and it satisfies two.
- **S032** varies the evidence available: same defect, four investigative situations, and reproduction is possible in one.
- **S033** varies which component fails, and the same handling strategy is right in two cases and catastrophic in a third.
- **S034** varies the caller: same system, four callers, and each needs a different contract.
- **S035** varies nothing externally. The student supplies the criterion and then attacks it.

## Load profile

The module is the programme's highest-load stretch to date and S031 is its peak, not its gentlest entry — which is a departure from the design's usual shape and is deliberate. Concurrency's central difficulty is that it cannot be approached incrementally: a student who has not accepted that interleavings are the object of reasoning will treat every subsequent day as debugging.

Load management is structural. **The same gateway instance runs through all five days** — one API Management instance, one model deployment behind it, deployed at S031 and torn down after S035 — and the substrate component behind it is introduced at S031 and shipped against at S035.

Two further decisions manage the load the platform adds:

- **Every policy fragment students need is supplied.** No day requires a student to author policy XML from a blank file; the phase 3 cases are supplied as configurations to run and compare, and phase 5's build is authored with the agent. **The difficulty is in predicting and explaining behaviour, never in syntax.**
- **Bicep is introduced as a review artefact before it is introduced as an authoring skill.** Students read a deployment before they write one, at S033, which is the order that makes the agent useful rather than load-bearing.

Fading is retained around the reasoning apparatus and removed from the criterion selection, per the position established at [S015](/archive/bsc-programme/seminars/S015.md) and clarified in [WP-015](/archive/bsc-programme/whitepapers/WP-015.md) §8.

## Module-level predicted failure modes

**Concurrency treated as sequential-plus-bugs.** The module's defining failure. Countermeasure: S031's phase 3 supplies a program that is correct under every trace the students can construct and incorrect under one they cannot, which cannot be resolved by debugging — and its platform case is a token limit that is exceeded by concurrent requests the documentation says will exceed it.

**Correctness properties learned as a vocabulary.** Students name linearizability without being able to say what it costs. Countermeasure: every day's artefact requires the property's cost to the caller in the caller's own terms, and S034's specification fails a contract stated without one.

**Reproduction treated as a prerequisite for belief.** S032's risk: students refuse to act on a defect they cannot reproduce. Countermeasure: S032's phase 3 makes reproduction available in one of four situations, and the day's artefact is an evidence argument rather than a fix.

**S035's break becomes theatre.** The risk that breaking a production component is experienced as spectacle rather than as evidence. Countermeasure: the criterion is committed in writing before the window opens, and the assessed artefact is the falsification argument, not the break.

**The platform instance read as proof of the durable claim.** New in this module and the risk the practical turn introduces. A student who watches a real gateway exhibit exactly the behaviour the module predicted will trust the module further than the evidence supports, and will generalise to the next product by analogy rather than by checking. Countermeasure: each day's perishability register separates the claim from the instance, each day's scope statement is given in the strong form, and **the specification assesses the claim and never the instance**. This is the same correction [WP-016](/archive/bsc-programme/whitepapers/WP-016.md) §8 made for the prompt cache, carried forward under instrumentation rule 5 as a validated repertoire item.

**Agent output accepted because it deployed successfully.** The module's new failure mode and the one with real consequences. A configuration that applies without error is not a configuration that does what you wanted; three of the module's five days turn on a mechanism that fails silently. Countermeasure: the intervention record, the mandatory prediction before every build, and S035's characterisation of the review instrument.

## Assessment contribution

**No entrustment judgement in this module** — the quarter's is at S040.

Specification items:

- **S031** — a correctness property chosen and stated, with the interleaving that violates the properties not chosen.
- **S032** — an evidence argument for a defect that could not be reproduced, with what would falsify it.
- **S033** — a failure-handling decision with the failures deliberately not handled named and their probability estimated.
- **S034** — a contract with a named caller, its cost to them in their terms, and the anomaly they will observe.
- **S035** — a stated working criterion, the falsification attempt, the production result, and the repair.

**Every one of the five additionally requires the prompt record, the intervention record and the frontier statement**, and every one states its checked elements and closes with *nothing else is assessed*, per the [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md)'s rule 1.

Dispositions observed: **integrity** at S035, in whether the reported consequence of the break is the actual one — and at S033, in whether a probability estimate carries the provenance it claims.

## The deploy window and the production window

Two different things, deliberately separated.

**The deploy window** runs at S031 through S034, in disposable subscriptions the programme owns. The agent has write access through the Azure MCP Server. Everything created is destroyed the same day, and S033's phase 5 ends with the resource group removed. Nothing here touches the substrate.

**The production window** is S035 and is the first time student changes reach the live system. The conditions are stated in the [Substrate and Infrastructure](/archive/bsc-programme/program/10-Substrate-and-Infrastructure.md) page and summarised here: a bounded window, a staff-held rollback used only if a user is affected, and a requirement that the student's criterion be committed before the window opens. **The agent does not apply the substrate change.** It may author it, reason about it and draft the report; the application is a human act, for the reason given on the [Q4](/archive/bsc-programme/quarters/Q4.md) page.
