# M01 · The Machine and the Proof

**Quarter:** [Q1](/archive/bsc-programme/quarters/Q1.md) · **Days:** S001–S005 · **Complexity class:** 1
**Strands recruited:** CF · MS · SY · PE
**Courses drawn on:** CF101, MS101, SY101, PE101
**Platform anchor:** GitHub Copilot agent mode · **MCP servers:** Microsoft Learn MCP Server (operated); Azure MCP Server (demonstrated at S002, read-only, staff tenant)

## The module's central difficulty

Students arrive able to write programs that work and unable to say why. The gap is not knowledge; it is a *stance*. The prevailing stance is empirical: change something, run it, observe. The module's whole purpose is to install an alternative stance — that a program's behaviour is determined before it runs and can be argued about — and to make the empirical stance feel insufficient rather than forbidden.

This is harder than it looks, because the empirical stance works. It works for small programs, it produces fast feedback, and it feels productive. Telling students it is wrong is both false and unpersuasive. The module instead constructs situations where it *fails visibly and cheaply*, which is the only argument that lands.

**The agent makes the empirical stance cheaper, faster and more persuasive, which makes this module harder and more necessary at the same time.** A student who can obtain a plausible trace, a plausible proof and a plausible invariant in seconds has a stronger version of the stance the module is arguing against, and the version is stronger precisely because the output is fluent. The module's response is not to withhold the tool. It is to give the student, on every one of the five days, **something hand-produced to check the tool against** — a trace, a committed pre-statement, a reader's rejection, a broken loop — and to make the comparison the assessed artefact rather than the output.

## Why it opens the programme

Three reasons, in order of weight.

1. **Everything downstream is an argument about behaviour under conditions you cannot enumerate.** A capacity argument at S020, a consistency contract at S034, a safety case at S087 are all the same move: reason about what a system will do without running it in every case. If the move is not installed here it is never installed.
2. **The programme's own design must be defended before it is endured.** S001 exists so that students hold a model of why the timetable feels inefficient. Compliance with a deliberately effortful design requires the model; supplying it after the aversion has set is too late.
3. **Proof is a communication act.** S004 frames it that way deliberately, which is what makes MS101 continuous with PE101 rather than orthogonal to it.

A fourth reason now applies and is placed last because it is the newest and the least established. **The instrument must be characterised on material whose answers are independently available**, and this module is the last point in the programme at which that is true of everything taught. From [S011](/archive/bsc-programme/seminars/S011.md) the student's own check becomes progressively more expensive than the agent's output, and by year two there are days on which no hand check exists at all. The five days here are the programme's only free calibration data.

## The four contrasting cases are run

Every day in this module executes its phase 3 against a real service rather than reading it, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). The payload case is stated per day and in every instance it is the case where the agent's *actual* behaviour defeats what the room predicted at phase 1.

| Day | The four cases | Payload |
|---|---|---|
| S001 | One question about three timetables, asked in four agent configurations | Attaching the grounding server changes nothing, because the question is outside its corpus — and the answer's confidence is identical either way |
| S002 | Four tracing and counting prompts against the two machines | The agent answers *which machine does more work* decisively, when the question has no answer |
| S003 | Four instruction configurations over the same generation request | A checkable instruction changes the output; an instruction implying a quality judgement does not |
| S004 | The same theorem proved for four named readers | Four documents differing in register and identical in what they establish |
| S005 | Four loops and four candidate properties | The agent affirms loop 4's near-invariant — the same case that defeats the room |

**Two of the five payloads are cases where the agent fails exactly where the students fail.** That is not a defect in the case selection; it is the module's most uncomfortable finding and it is taught as one. A tool whose errors are correlated with yours does not give you a second opinion.

## Strand interlock

| Strand | What it contributes here |
|---|---|
| CF | The programs being reasoned about; the vocabulary of state and control; the instructions file as an executable specification |
| MS | Proof technique, induction, the counterexample as an object; the agent as an adversary that accepts too much |
| SY | The machine that makes "what happens" a determinate question; the machine you are billed for, shown once |
| PE | Evidence and warrant as professional obligations, not academic ones; grounding a claim in documentation you have actually fetched |

The interlock is what makes this a module rather than four parallel courses. S005 is simultaneously an induction day, a recursion day, a machine-execution day and a day about the standard of proof a colleague is owed.

## The five days

| Day | Title | What the student does | What the student builds |
|---|---|---|---|
| S001 | Why This Programme Feels Wrong | Predicts their own retention, then confronts the prediction | A configured repository: instructions file, `applyTo` glob, Learn MCP Server, injection verified |
| S002 | What a Machine Actually Does | Traces execution on a machine simple enough to hold entirely | A machine simulator, agent-built, checked against the hand trace |
| S003 | Representation and the Leaking Abstraction | Finds the case where a convenient representation misleads | An instruction that demonstrably prevents the defect, and one that demonstrably does not |
| S004 | Proof as an Act of Communication | Writes a proof for a specific reader and has it rejected | A reader-directed proof plus an adjudication of the agent's review of it |
| S005 | Induction and the Machine That Runs Forever | Proves a loop property, then breaks a plausible false one | A runnable invariant check, run against the sound loop and the broken one |

Every build carries the three artefact elements the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md) requires: a **prompt record**, an **intervention record** and a **frontier statement**.

## Task-class variability plan

All five days sit in complexity class 1: task specified, method given. Variability is introduced in **surface structure only**, which is the four-component design's prescription for early task classes.

- **S002** varies over machine models — the same trace performed on a register machine and a stack machine.
- **S003** varies over data domain — the same representation failure in numeric, textual and temporal data.
- **S004** varies over audience — the same claim proved for a peer, a sceptic and a future maintainer.
- **S005** varies over structure — induction over naturals, over lists and over a loop's iteration count.

Surface variation with constant deep structure is the condition under which students abstract the deep structure. Deep-structure variation at class 1 would exceed available capacity and produce memorisation of surface cues instead.

**The agent adds a fifth axis of variation that costs no additional capacity.** On each day the same task is performed twice — once by hand and once by direction — and the comparison is the artefact. This is variability in the *producer* rather than in the task, and it is affordable at class 1 precisely because the task itself does not change. It is also the module's cheapest source of the frontier data the programme will collect for three years.

## Load profile

**High element interactivity relative to schema base, and therefore heavily supported.** Every day in this module uses worked examples with completion problems before independent problems. The generation phase (phase 3) is deliberately *short* here — 45 minutes as specified, but with narrower contrasting cases than later modules use — because productive failure requires enough prior knowledge to fail productively, and in week one there is very little.

The module is the clearest instance in the programme of the reconciliation rule stated in [Learning Science Foundations](/archive/bsc-programme/program/02-Learning-Science-Foundations.md): difficulty is raised in retrieval and selection, and lowered in representation and attention. Materials here are aggressively de-cluttered, integrated rather than split, and free of decorative detail.

## Predicted failure modes for the module as a whole

- **The strong-background student is bored by S002 and concludes the programme is remedial.** Countermeasure: the S002 extension case is genuinely hard for them, and S001's calibration exercise usually humbles them before S002 begins.
- **The weak-background student cannot trace at all and hides it.** Countermeasure: phase 6 at S002 and the S010 error clinic; and the tracing artefact is a specification item, so failure surfaces within a fortnight rather than at the end of term.
- **The proof stance is adopted performatively and discarded outside MS101.** This is the module's most likely real failure. Countermeasure: S006's invariant work is graded in CF101, not MS101, so that the stance is enforced where students do not expect it.
- **The hand-produced work becomes a formality performed after the agent's output is in front of the student.** This is the module's newest and probably its most serious failure mode, and it is invisible in the artefact: a trace written to agree with a simulator looks exactly like a trace written before one existed. Countermeasure: on every day the hand-produced element is *committed* before the agent is invoked — S002's pre-statement, S003's prediction, S004's round-1 proof, S005's committed invariant — and the commitment is a separate specification element from the thing it predicts. **The countermeasure is procedural and therefore defeatable.** The design has no detector for a student who defeats it, and says so here rather than in a whitepaper, because it applies to all five days.
- **The intervention record is padded.** A student who understands that an empty intervention record fails will produce entries. Countermeasure: the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s exception — an empty record passes where the artefact demonstrates the design could have detected an intervention-worthy error — makes the honest empty record available, which removes the incentive to invent. It is first exercised at [S005](/archive/bsc-programme/seminars/S005.md), whose property check is exactly such a demonstration.

## Assessment contribution

No entrustment evidence. Three specification items: the traced execution artefact (S002), the rejected-and-repaired proof (S004), and the loop-property argument (S005).

**Each of the three now carries the prompt record, the intervention record and the frontier statement**, and S001 and S003 carry the same three against their own artefacts in PE101 and CF101 respectively. All pass/fail against specification, all resubmittable with tokens.

The three added elements are assessed for **presence and specificity**, never for the quality of the build the agent produced. A frontier statement naming a specific thing the agent did badly on this build passes; one saying that the agent was sometimes unreliable does not. This is the [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md)'s specification rule 1 applied to a new element class, and it is the reason the module's specification lists are stated in the closed form despite falling inside the S001–S040 non-retroactivity boundary. The boundary is otherwise unchanged: nothing else in these five specifications has been amended.

The dispositions record opens at the end of this module.
