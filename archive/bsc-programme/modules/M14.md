**Platform anchor:** Foundry cloud evaluation in CI — the `microsoft/ai-agent-evals` GitHub Action and the `AIAgentEvaluation` Azure DevOps task, both preview · trace evaluation and pre-existing response scoring · continuous evaluation and the Agent Monitoring Dashboard, both preview · **MCP servers:** Foundry MCP Server (preview) · Azure MCP Server · Microsoft Learn MCP Server

## The central difficulty

A release is a decision made under evidence that is always insufficient.

That sentence is not a complaint about industrial practice. It is a structural fact, and it is the module's subject. The evidence available before a release is offline; the thing being decided is online. The population the evidence was drawn from is not the population that will arrive. The criterion the evidence was scored against was chosen by someone solving a different problem. The interval around the number assumed a dependency structure the deployment does not have. Every one of those gaps has been taught already, in [M06](/archive/bsc-programme/modules/M06.md), [M09](/archive/bsc-programme/modules/M09.md) and [M10](/archive/bsc-programme/modules/M10.md), as a property of measurements. This module is where they arrive together as a property of a decision.

The students' defence against this is a gate. Every organisation they will work in has one — a regression suite, a metric threshold, a review board, a sign-off. The gate exists precisely so that nobody has to hold the whole uncertainty at once, and it works, and the module's stance is that it works for a reason nobody in the room can currently state.

**A release gate is itself an evaluation artefact, and it is subject to every rule this programme applies to evaluations.** It has a construct — is this change safe to release — and it measures something else. It has a criterion, chosen by named people for a purpose, which [S046](/archive/bsc-programme/seminars/S046.md) says must be traceable and which no gate in existence is. It has a judge, human or automated, with a systematic error component that [S048](/archive/bsc-programme/seminars/S048.md) established does not average out. It has a threshold, which is a decision about which of two errors you prefer, made almost always by someone who has not been told there are two. It has an error structure, and one half of it is never counted. And it is consulted at every release for years, which makes it the long-lived evaluation artefact [S042](/archive/bsc-programme/seminars/S042.md)'s three-set discipline has no version for.

**Nobody validates the gate.** [S047](/archive/bsc-programme/seminars/S047.md) required a check the criterion could fail, and the release gate is the criterion in the programme's whole span that is most consulted, most optimised against, and least examined.

The module's difficulty is not that this is hard to believe. It is that believing it changes nothing until the student has designed a gate, watched it disagree with reality, made a decision on it anyway, and been answerable for the result weeks later.

## The gate is a real thing they run

The argument above was, in this module's first draft, an argument. It is now an artefact the student stands up in a pipeline and watches behave.

A release gate in this module is **a Foundry evaluation run wired into continuous integration** — the `microsoft/ai-agent-evals` GitHub Action or the equivalent Azure DevOps task, both of which Microsoft labels preview. The student supplies a dataset of test queries and a list of evaluators from the Foundry evaluator catalogue; the run invokes the agent, scores the responses, and writes a summary report with confidence intervals and, across two agent versions, a pairwise statistical comparison. That is a real gate on a real service, and **every property the module claims about gates is a documented property of that one.**

- **Its judge is uncalibrated.** The quality evaluators are LLM-as-judge. **No agreement-with-human-judgement figure is published for any of them.** It is not that the number is poor; it is that the number does not exist, and a gate whose judge has never been characterised is [S029](/archive/bsc-programme/seminars/S029.md)'s unvalidated instrument at the moment of maximum consequence.
- **Its threshold is a default nobody in the room chose.** The general-purpose evaluators score on a one-to-five Likert scale with a documented default pass threshold of three; the risk and safety evaluators score zero to seven and pass at or below three. The documentation states that a non-binary score is binarised to pass or fail against a default threshold the user *can* override. Almost nobody does.
- **Its unit of judgement is a default too.** A multi-turn conversation must be split before it can be scored, the documentation says in its own words that *how you split determines what you're evaluating*, and the default split is the last turn — which measures the answer to the most recent question and not whether the task was completed.
- **Its scope is a default as well.** The Agent Framework's Foundry evaluator set runs relevance, coherence and task adherence by default, and **adds tool-call accuracy automatically when the items carry tool definitions.** A gate whose evaluator list changes when the input shape changes is a criterion that moves without anybody editing it.
- **And the online half of it stops running without saying so.** Continuous evaluation, which is preview, scores a *sample* of production responses at a rate the operator sets. The documentation records that evaluation runs are skipped once the hourly run limit is reached — the default is a hundred runs an hour — and it records this **in a troubleshooting table, under the symptom that results did not appear.** The remedy is to raise the limit or wait. Nothing in the documentation says a skipped run emits anything.

The last of those is the module's sharpest single fact and it belongs to [S068](/archive/bsc-programme/seminars/S068.md) as much as to [S066](/archive/bsc-programme/seminars/S066.md): **a monitoring path that stops evaluating and reports nothing is the third outcome, in a vendor's own troubleshooting table.** A student who has watched their own gate go quiet at the cap has learned something that no amount of instruction about liveness would have installed.

## Why this module sits here

**It requires the substrate to be real, and it is the first module that cannot degrade gracefully without it.** Every earlier module's activity survives as an exercise with reduced value. A ship decision does not: a student who decides not to ship in a simulation has decided nothing. The [Substrate and Infrastructure](/archive/bsc-programme/program/10-Substrate-and-Infrastructure.md) page's withdrawal commitment names [S068](/archive/bsc-programme/seminars/S068.md) explicitly, and the honesty of that commitment is tested here first.

**It requires [M13](/archive/bsc-programme/modules/M13.md) immediately before it.** A release decision under cost is the only kind there is. [S065](/archive/bsc-programme/seminars/S065.md)'s cost argument is the other half of what [S070](/archive/bsc-programme/seminars/S070.md) asks a student to hold, and the two entrustment occasions of Q7 are deliberately adjacent for that reason. The dependency is also instrumented: [S064](/archive/bsc-programme/seminars/S064.md) named [S070](/archive/bsc-programme/seminars/S070.md) as the response occasion for its commitment shape and break-even, so the capacity commitment a student made in week 64 against a forecast is defended in week 70 against the realised spend of the billing period that closes that week. **That is the module's only inbound rule-6 link and it is the mechanism by which a class-5 decision acquires a consequence the student cannot argue with.**

**It requires all of M10.** The gate is a criterion ([S046](/archive/bsc-programme/seminars/S046.md)), it drifts ([S047](/archive/bsc-programme/seminars/S047.md)), its judge is biased ([S048](/archive/bsc-programme/seminars/S048.md)), its interval has a dependency structure ([S049](/archive/bsc-programme/seminars/S049.md)), and what it licenses is narrower than what it will be read as licensing ([S050](/archive/bsc-programme/seminars/S050.md)). A student without that apparatus receives this module as operations training.

**It requires [M12](/archive/bsc-programme/modules/M12.md)'s shipping experience.** [S060](/archive/bsc-programme/seminars/S060.md) put a retrieval system into production. This module asks whether that was the right call and how anyone would have known.

**It is not placed later** because [M15](/archive/bsc-programme/modules/M15.md) and [M16](/archive/bsc-programme/modules/M16.md) both assume it: an agent's trajectory evaluation at [S075](/archive/bsc-programme/seminars/S075.md) is an offline-online problem, and [S079](/archive/bsc-programme/seminars/S079.md)'s drift and alerting material is [S068](/archive/bsc-programme/seminars/S068.md) at a longer horizon with an adversary present.

## Task-class variability plan

At class 5 the student decides **whether to proceed at all, under uncertainty and cost.** Variability across the five days is therefore in **what makes proceeding costly**, since holding the class constant while varying the cost structure is what prevents the decision procedure calcifying into one rehearsed move.

**All four contrasting-case sets are executed rather than read**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). Where a case cannot be operated — because it needs a tenant privilege or a licence the programme does not hold — the day states that it is demonstrated rather than operated and the specification does not assess it.

- **S066** varies the gate: four release gates over one change, differing in construct, judge and error structure, **one of which is an undocumented human judgement and outperforms the written ones.** Three of the four are run as real evaluation runs against a Foundry project.
- **S067** varies the cause of the gap: four offline-online pairs with the same sign of divergence and four different mechanisms behind it.
- **S068** varies the monitor: four detection designs for one component, differing in what they can see and in how long they take to see it, **one of which cannot detect its own failure.**
- **S069** varies the authority: four governance arrangements over one decision, differing in who bears the cost of being wrong. This is the module's one set that is discussed rather than executed, because an authority structure is not a service call.
- **S070** varies nothing supplied. The change, the evidence, the gate, the detection design and the arrangement are all the student's own, produced across the preceding four days, and the cost is the substrate's users.

## Load profile

**Low technical, extreme temporal.** Nothing in this module is difficult to compute. The gate is a threshold, the gap is a subtraction, the detection target is four sentences, and the governance arrangement is a paragraph. A student who finds this module hard is not finding the material hard.

The module's distinctive load is **answerability across time.** At class 5 the student owns a system across weeks and is answerable for decisions whose consequences arrive after the day that made them. That is a load the programme has not previously imposed: [S045](/archive/bsc-programme/seminars/S045.md)'s deployment was reported back at [S050](/archive/bsc-programme/seminars/S050.md), but nothing at S045 turned on holding the future in mind while deciding. Here it does, at every day, and the artefacts from S066, S067 and S068 are inputs to S070 rather than deliverables in themselves.

The standing load reduction is that **one change, on one substrate component, runs through all five days.** The student picks it at S066 and does not pick again. Every day adds an object to the same decision — a gate, a measured gap, a detection design, an owner — and S070 assembles them. Nothing is introduced except the next question.

The second reduction is that **S070 builds nothing.** The entrustment occasion is a decision and a defence, not a construction, for the reason [WP-050](/archive/bsc-programme/whitepapers/WP-050.md) §3.1 gives: a judgement about a decision under pressure is invalid if the student is simultaneously constructing the evidence. The four builds happen at S066 to S069 and their **prompt records, intervention records and frontier statements** arrive at S070 as inputs to the defence rather than as work to be done on the day.

The third reduction is that **the platform work is the same platform work every day.** One Foundry project, one agent, one evaluator catalogue, one Application Insights resource. The student pays the setup cost once, at S066, with Copilot in agent mode through the Foundry MCP Server, and thereafter the platform is furniture rather than content.

## Module-level predicted failure modes

**The gate is treated as the answer rather than as the artefact.** The module's defining failure and the hardest to see, because a student who says "the gate passed, so I shipped" has behaved exactly as their future employer wants. Countermeasure: every day's phase 1 asks what the supplied gate is measuring before the day names it, and **S066's specification fails a gate whose two error rates are not stated.**

**Offline-online divergence read as an offline failure.** Students will conclude that the offline measurement was wrong. Sometimes it was; usually both numbers are correct measurements of different things. Countermeasure: **S067's artefact requires the gap to be attributed to one of five named differences, with the evidence that distinguishes it from the other four**, and an attribution of "the offline set was bad" without that evidence fails.

**Detectability treated as an operations concern.** The commonest professional error in this area and the one with the largest consequence: monitoring is added after release, by whoever is on call, to the conditions that have already happened. Countermeasure: **S068 places the detection design before the release decision in the module's sequence and S070's decision artefact will not accept a ship without one.**

**Governance read as bureaucracy.** A student who concludes that S069's material is process overhead has learned the opposite of the day. Countermeasure: S069's payload arrangement is the slowest of the four and produced the best outcomes on the substrate's own record, and the mechanism is stated — it required the engineer to argue against their own change.

**Not shipping read as failure.** The module's affective risk and the one that distorts the entrustment judgement. Countermeasure: **a defended decision not to ship is a pass at S070, stated before phase 1**, and the cohort's split is shown at S070 phase 6 with what actually distinguished it.

**The platform's verdict read as the answer.** New with the practical turn and a sharper version of the first failure mode. A student who has built a real evaluation run in CI now has a green tick from a named vendor service, which is a more persuasive object than a threshold in a spreadsheet and is exactly as uncalibrated. Countermeasure: **every day's phase 4 names at least one default the platform chose**, and [S066](/archive/bsc-programme/seminars/S066.md)'s specification fails a gate whose two error rates are not stated — a requirement the platform's own report does not help with, because the report contains scores, confidence intervals and a pass rate, and no error rate at all.

**The agent's output accepted because it ran.** Copilot in agent mode will stand up a working evaluation pipeline quickly, and a pipeline that runs is not a pipeline that gates. Countermeasure: **every day's phase 6 error clinic carries a case where the agent was confidently wrong and review did not catch it**, and **every phase 5 artefact carries an intervention record whose emptiness fails** unless the build itself demonstrates it could have caught an intervention-worthy error.

## Assessment contribution

**One entrustment judgement, at [S070](/archive/bsc-programme/seminars/S070.md)** — the quarter's second, after [S065](/archive/bsc-programme/seminars/S065.md). Activity: *make and defend a ship / do-not-ship decision on a live system with real users.* Expected **2b–3a**. It is the first rehearsal of **EA-1** on a live system and it is not EA-1, which is assessed at ME390 across at least four occasions with at least three distinct assessors.

Specification items:

- **S066** — a release gate with its construct, its judge, its two error rates, and a validation the gate could fail with a pre-committed threshold.
- **S067** — a predicted gap, a measured gap, one user class constructed after the results from the residuals, an attribution with its distinguishing evidence, and the [S059](/archive/bsc-programme/seminars/S059.md) ceiling set against what survived contact with users.
- **S068** — a detection design with the four-part target, an explicit list of what the student has decided not to detect with the cost and provenance of each, a signal whose independence from the monitored pipeline is argued, and a detector for the [S060](/archive/bsc-programme/seminars/S060.md) failure class they did not anticipate.
- **S069** — a governance arrangement naming owner, authority, record and reversal path, with an owner assigned to every undetectable failure, negotiated live with the accountable staff member.
- **S070** — the decision, its cost position against the realised spend, its defence, and the carry-forward statement.

**S066 to S069 each additionally carry the three artefact elements the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md) requires of a build: the prompt record, the intervention record and the frontier statement.** An intervention record with no entries fails, unless the artefact demonstrates that the build's own design could have detected an intervention-worthy error. **S070 carries no build and therefore no new records**; it carries the four existing ones into the defence, and the published question set does not ask about them, because the entrustment judgement is on the decision and not on the tooling.

Dispositions observed: **integrity** at S066 and S070, in whether the stated error rates and failure modes match the student's own evidence; **humility** at S067 and S069; **reliability** at S068, in whether the detection commitment is one the student can keep.

## What this module may not assert

Binding on all five days, and restated here because this is the module where the temptation is greatest:

- **No evaluator's agreement with human judgement.** None is published. Every judged score produced by this stack is described to students as uncalibrated, and a module about release gates that softened this would be teaching the opposite of its subject.
- **No detection or false-positive rate for any governance or security service**, and no accuracy figure anywhere in the platform layer.
- **No magnitude for any gate's false-pass or false-block rate.** Every such figure in these five days is measured on the substrate's own records and is marked perishable.
