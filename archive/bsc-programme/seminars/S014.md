# S014 · Trees, Graphs and the Shape of a Problem

**Platform anchor:** the vector index as a proximity graph — an Azure AI Search HNSW configuration, read through the Azure MCP Server

## What this day is for

Trees and graphs are usually taught as structures with traversal algorithms attached. That framing gets the dependency backwards. The reason to represent something as a graph is that **the problem has a shape**, and recognising the shape is the skill; the traversals follow from it almost mechanically.

The day's target is the recognition move: given a problem stated in ordinary language about entities and relationships, identify whether it is a reachability question, an ordering question, a shortest-path question, a connectivity question or a cycle question — and then observe that the algorithm is nearly implied.

The day's platform instance is chosen because it is the case students will least expect to be a graph at all. An Azure AI Search vector index is a **layered proximity graph**: every vector is a node, the `m` parameter is how many bi-directional links each new node gets, and a query is a traversal that stops when a dynamic candidate list of size `efSearch` stops improving. The question the caller asked was a *distance* question. The mechanism that answers it is a *reachability* traversal, it is approximate, and **when it is wrong it is wrong because the traversal did not reach the answer, not because the distance was miscalculated.** Recognising that is the day's recognition move applied to the system students will spend three years querying.

It is also the day where S008's inductive correspondence stops being a technique and becomes the working method, at a four-week gap and without re-teaching.

1. For each, say what the entities are and what the relationships are.
2. For each, state the question being asked in one word: reachability, ordering, distance, connectivity, cycle.

Item 3 has an answer. The two problems share no surface features at all.

**Copilot prediction, sealed.** *In phase 5 you will ask Copilot to answer a real user's question about a relationship dataset. Write down now: what shape will it assume, will it state the shape before writing code, and will its answer be in the user's words or in yours?* Opened at phase 8.

**Warrant.** Pretesting on the recognition move rather than on structures. Item 3 is a transfer probe by construction: two problems with identical deep structure and no surface similarity. The Copilot item probes whether students expect the agent to perform the day's actual skill — shape identification — or only its mechanical consequence, and is sealed before instruction per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

Groups receive **one relationship dataset** from the substrate — real entities, real relationships — and **five questions** about it.

The questions are phrased in domain language, not graph language. For each, groups must state the graph question and the traversal that answers it, and commit.

Then a sixth question is supplied, which **looks like** one of the first five and is not — it is a shortest-path question phrased almost identically to a reachability question, and the two require different work.

Task after: **state what in the phrasing distinguishes them.**

**Then the same discrimination, on a running system.** Four cases over a vector index the students did not build. Two are operated by the room; two are demonstrated by staff, and the difference is stated out loud.

| Case | What happens | Operated or demonstrated |
|---|---|---|
| A | Read the index's `vectorSearch` configuration through the Azure MCP Server and name every graph parameter in it | **Operated.** Reading an index definition is a read. |
| B | Run the same vector query at several values of `k` and record which neighbours appear, disappear and change rank | **Operated.** |
| C | Raise and lower `efSearch` and observe the effect on results | **Demonstrated.** `efSearch` is a query-time parameter but changing it edits the index definition, which is a write this quarter does not perform. |
| D | Change `m` and rebuild | **Demonstrated.** Requires reindexing the corpus. |

**Case A is the payload.** Groups commit in writing, **before reading anything**, to what kind of structure they expect behind "find the most similar documents" and what they expect its parameters to control. Almost nobody says *graph*. The configuration says `"kind": "hnsw"` — Hierarchical Navigable Small World — and its parameters are graph parameters: `m` is an out-degree, `efConstruction` and `efSearch` are the sizes of a candidate list carried during a traversal, and `metric` is the edge weight. **The caller asked a distance question and the system answers it by walking a graph**, which is the day's near-miss discrimination arriving in production form: two question types that look identical from outside and are not.

Cases C and D are demonstrated rather than operated and **are not assessed**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). After each demonstration, groups state **which of their own case A predictions it falsified**, so that a phase performed by staff still produces a student artefact. What the demonstrations are for beyond that is the observation that the parameters students would most want to vary are the ones that cost a rebuild, which is [S011](/archive/bsc-programme/seminars/S011.md)'s irreversibility point in a second form.

**Warrant.** Contrasting cases with a near-miss adjudicator. The sixth question is the phase's payload for the language half: near-identical surface, different deep structure, which is the discrimination the recognition skill requires. Case A is the payload for the systems half and is the day's answer to instrumentation rule 7 — the claim that a similarity search is a graph traversal is one the room will not believe if it is asserted, and it is read out of a live configuration instead.

## Phase 4 · Consolidating instruction (50 min)

1. **The shape comes first.** Entities, relationships, and the question. The representation follows; the algorithm nearly follows from that.
2. **Five question types** and what each requires: reachability, ordering, distance, connectivity, cycle detection. Indexed to phase 3. **The list is five because five is what this day can carry, not because there are five.** Flow, matching, colouring, centrality and spanning structure are all absent, several of them are genuinely important, and each needs machinery this day cannot afford. Two of the five also overlap: connectivity is a reachability property, and cycle detection frequently falls out of ordering. **Safe** as a vocabulary for recognising the questions this programme's problem class actually raises; **unsafe** as a classification scheme — a problem that does not fit is evidence about the list, not about the problem.
3. **Traversal as structural recursion**, from S008 directly. Depth-first and breadth-first as two well-founded orderings over the same structure, not as two algorithms to memorise.
4. **What the graph representation discards** — S011's pair. Everything not expressible as a binary relation between entities, which is a great deal.
5. **Cost, in S012's terms.** Node and edge counts are the operation count; the probe cost is the adjacency representation; movement dominates for large sparse graphs.
6. **When the shape is wrong.** A problem forced into a graph that is not one, and the cost of the forcing. Two examples, one from the substrate.
7. **Trees as the special case that buys termination for free** — S008's structural recursion, and why cycles change the argument.
8. **The vector index is a graph, and its parameters are graph parameters.** From case A, in the configuration's own words. `kind` is `hnsw`; `m` is the number of bi-directional links created for each new element; `efConstruction` and `efSearch` are the sizes of the dynamic candidate list held during indexing and during search. The documentation states the trade in both directions: larger `m` gives denser graphs and better query performance at more memory and computation, and larger `efSearch` may improve results and slows queries. That is S012's crossover, in a vendor's parameter reference.
9. **An approximate answer fails as a traversal, not as an arithmetic.** When a nearest-neighbour search misses the true nearest neighbour, the distance function did not err — the walk did not get there. This is the single most useful sentence the day supplies to [S057](/archive/bsc-programme/seminars/S057.md) and [S058](/archive/bsc-programme/seminars/S058.md), and it is only available because the shape was identified first.
10. **What the platform chose for you, and what is perishable.** `m` defaults to 4 in a permitted range of 4 to 10. `efConstruction` defaults to 400 and `efSearch` to 500, both in a range of 100 to 1,000. `metric` defaults to `cosine`, with Euclidean and dot product available. Read that list again as a sentence about your own system: *somebody chose your graph's out-degree and how far your queries walk, and it was not you.* One machine-readable annotation makes a related shape claim — of the Azure MCP Server's AI Search read tools, only **Retrieve from knowledge base** is marked **Open World**, meaning its domain of interaction is not closed; the others are. **Safe** to reason with against this service at these documented defaults; **unsafe at any version other than the one in front of you**, and unsafe as a claim about any other vector store, because the parameter names, the defaults and the ranges are all this vendor's and this version's. *Defaults are opinions and thresholds are policy.*

**Warrant.** Consolidation with the recognition move first and the algorithms last, which inverts the conventional order deliberately. Point 3 makes S008 the method rather than a prerequisite. Point 2's completeness statement is the repair [WP-014](/archive/bsc-programme/whitepapers/WP-014.md) §8 conceded was owed. Points 8 to 10 are the platform layer; 8 and 9 are reachable from phase 3 case A, and 10 is the day's defaults point.

## Phase 5 · Whole-task learning task (90 min)

**The output is a build.** Students take **a real question asked by a real substrate user** — supplied verbatim, in the user's own words, not translated — and ship a working answer to a disposable environment, directed through Copilot agent mode.

1. **Identify the entities and relationships.** State what you are discarding.
2. **State the question type.**
3. **Write the induction hypothesis** for the procedure that answers it, before writing the procedure.
4. **Build.** Direct the agent to implement the procedure. Give it the hypothesis from step 3 as part of the instruction and note whether the code it returns is the one the hypothesis describes.
5. **State its cost** in S012's three terms, on the actual graph's size and density.
6. **Answer the user's question,** in the user's words, and state one thing your answer does not tell them.

Step 6 is the day's close and joins the module to PE102's contextual-inquiry material.

**Artefact elements.** As at S011 to S013, and assessed.

- **Prompt record** — the instructions given, in order, including abandoned ones. On this day the record is unusually informative, because the difference between a prompt that names the shape and one that does not is visible in one line.
- **Intervention record** — every correction and what it was. **Empty fails**, unless the build demonstrates that an intervention-worthy error was detectable: here, a graph small enough that the correct answer is known by hand and is compared against the procedure's.
- **Frontier statement** — one thing the agent did faster than you could have, one thing it did badly that you caught.

**Faded guidance:** steps 1 and 2 are worked with the room for a sixth question; step 3's hypothesis skeleton is supplied.

**Warrant.** Whole-task at class 1 on a genuine user question. Step 3 enforces S008's argument-before-code discipline in a setting where it is now the natural method rather than an imposition, and step 4 makes the hypothesis an *input to the agent* rather than a private artefact, which is the day's cheapest demonstration that a specification and a prompt are the same object. Step 6 is the first time a student answers a real person.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate feature built on a graph model where the real relationships were not binary — one entity related to several others jointly, not pairwise — and what the model's forcing cost.

**Then the agent case.** Asked to answer a question about which records could affect which other records, Copilot wrote a correct, tested, readable breadth-first search — and answered a reachability question that had been a *shortest-path* question, because the user's phrasing said "how" and the agent read it as "whether". The output was a set where the answer needed a path. It was reviewed by two students, who checked the traversal and found it correct, which it was. Attention on why: **the agent had produced the right answer to the wrong question, and every downstream artefact — tests, names, comments — was internally consistent with the wrong question**, so there was nothing for a reviewer to catch except the framing, and the framing was in the prompt.

Then students: a problem you modelled with the wrong shape.

**Warrant.** Error management, with a disclosure targeting point 6 rather than any algorithmic error, because shape errors are expensive and rarely disclosed. The agent case is the required sixth element and is the same failure class as the instructor's, which is the point — a shape error survives review whether a person or an agent made it, and for the same reason.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student presents their step 6 answer to their partner, who plays **the user who asked**, and whose task is to ask the follow-up question a real user would ask.

Then: does the student's model answer the follow-up, or does it require a different shape?

**Warrant.** Interactive-tier articulation with a role demand. The follow-up question is where a model's adequacy is actually tested, and this is the first time in the programme a student defends work to someone playing a non-technical reader.

## When it does not work

These are [WP-014](/archive/bsc-programme/whitepapers/WP-014.md) §5's predicted failure modes, restated as instruction to the person in the room. The whitepaper is the authority; where this section and §5 diverge, §5 is right.

**A strong algorithms student classifies phase 1 quickly, implements fluently at step 4, and treats steps 1, 2 and 6 as preamble.** That inverts the day's priorities exactly. No intervention is needed, and this is the rare case where prior knowledge makes the assessed element *harder*: the specification fails an answer written in graph vocabulary, and the more comfortable a student is with the technical framing, the harder step 6 becomes for them. Let the specification do the work.

**A student with little graph exposure is meeting recognition, modelling, recursion and costing in one day.** The question types are named rather than withheld, the hypothesis skeleton is supplied, traversals may be taken from a library, and steps 1 and 2 are worked with the room. *Residual risk the design accepts:* step 5's three-term cost on a real graph may be beyond them. The stated fallback is that they give the operation-count term and mark the other two as unmodelled, which is an honest artefact and passes.

**A group answers all five phase 3 questions correctly.** That is the design, not a problem — the near-miss requires a formed pattern to violate. If they also resolve the sixth immediately, set the construction task: a seventh question that is a near-miss for a different pair of types.

**A student whose model cannot answer the phase 7 follow-up explains why the follow-up is unreasonable.** This is the day's characteristic affective failure and it is the professional-formation strand's central concern arriving in its earliest and most correctable form. Two countermeasures, both before the phase rather than during it. Instruct the partner to stay in role and to decline engineering-side explanations. Name the pattern to the room in advance, framed as normal and worth noticing rather than as a fault. Say also that a model which cannot answer the follow-up is a normal outcome and is the phase's information rather than its failure — the follow-up is designed to be answerable by roughly half of models.

## Assessment

Specification item in CF102. The checked elements are: entities and relationships with the discard statement; question type; induction hypothesis written before the procedure; the built procedure; three-term cost; the user-facing answer with its limitation; **the prompt record**; **the intervention record**; and **the frontier statement**.

**An answer written in graph vocabulary fails the specification.** The user did not ask in graph vocabulary and is not owed an answer in it. An intervention record with no entries fails unless the build compares its output against a hand-computed answer on a small graph.

**Nothing else is assessed.** Phase 3 cases C and D are demonstrated rather than operated and carry no assessment; the phase 1 Copilot prediction is not assessed; and the agent's output quality is not assessed.

## What to take from this day

**The claim to hold.** **The shape comes first; the algorithm nearly follows.** Given a problem in ordinary language, identify the entities, the relationships and the question — reachability, ordering, distance, connectivity or cycle — and most of the work is done. Two questions can look identical and be different types, and **an approximate answer fails as a traversal rather than as an arithmetic.**

**What the sources license, and what they do not.** The problem-shape and entity-relationship material is verified here, at [research/05-fde-craft/evans-domain-driven-design.md](/research/05-fde-craft/evans-domain-driven-design.md), and the contextual-inquiry basis for step 6 at [research/04-professional-formation/](/research/04-professional-formation/collected-materials.md). **Narrowed and sharpened 2026-07-30**, when that source was read in full rather than carried as a synthesis. What it supplies precisely is the definition this day has been using loosely: an entity is "an object fundamentally defined not by its attributes, but by a thread of continuity and identity", against a value object that "describes some characteristic or attribute but carries no concept of identity". What it does **not** support is the weight this day placed on the tactical apparatus: the author nominates the chapters on language, model–implementation binding, implicit concepts and model integrity as the book's core, **and none of them is a building-block chapter.** He also states an applicability condition this day never carried — the approach "has limited applicability using languages such as C, because there is no modeling paradigm that corresponds to a purely procedural language" — so the shape-first claim is warranted here by the day's own reasoning wherever the implementation language supplies no modelling paradigm. **The book contains no measurement of any kind and licenses no magnitude.** The graph-based approximate-search material behind points 8 and 9 is grounded in [research/02-technical-foundations/malkov-yashunin-hnsw.md](/research/02-technical-foundations/malkov-yashunin-hnsw.md) and [research/02-technical-foundations/subramanya-diskann.md](/research/02-technical-foundations/subramanya-diskann.md); **the day asserts mechanism and direction from those notes and no experimental figure from either.** The five question types are a working vocabulary and not a classification scheme.

**Guidance for your own work.**

- **State the shape before anything is written**, and hand that statement to whoever writes the code — including the agent.
- **Answer in the questioner's words.** They did not ask in graph vocabulary and are not owed an answer in it.
- **Keep a case whose answer you know by hand.** On a small graph you can adjudicate; on a large one you cannot.
- **Pin what you read a configuration from** — revision, host and model, as the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md) requires — because parameter names, defaults and ranges belong to one vendor and one version.

**Where this is easy to get wrong.** Producing the right answer to the wrong question. When the shape is wrong the tests, the names and the comments are all consistent with it, so there is nothing for a reviewer to catch except the framing — and the framing was in the prompt.
