# S002 · What a Machine Actually Does

**Module:** [M01](/archive/bsc-programme/modules/M01.md) · **Quarter:** [Q1](/archive/bsc-programme/quarters/Q1.md) · **Complexity class:** 1
**Strands:** SY · CF · MS
**Platform anchor:** GitHub Copilot agent mode · Azure MCP Server read-only resource inspection, *demonstrated not operated* · **MCP servers:** Microsoft Learn MCP Server (operated); Azure MCP Server (staff tenant, read-only, shown once)
**Whitepaper:** [WP-002](/archive/bsc-programme/whitepapers/WP-002.md)
**Re-tests:** S001

---

## What this day is for

Students write programs against an abstraction so thick that the machine underneath has become invisible. That is mostly fine and occasionally catastrophic. Every performance question in this programme — the memory hierarchy at S016, queueing at S019, serving cost at S061 — reduces to a question about what the machine is physically doing, and a student who has never held a complete machine in their head cannot reason about a partial one.

So the day gives them a machine small enough to hold entirely, and makes them execute it by hand until the execution model is not a metaphor.

**The hand trace is also the day's oracle.** This is the only day in the programme on which a student can produce, unaided and in ninety minutes, a complete and independently correct account of what a program does. That makes it the one free opportunity to find out what an agent's account of the same program is worth, and the day takes it. From S011 the checking gets expensive; here it costs nothing beyond the tedium the day was already paying for.

**And the machine you are billed for is shown once.** SY101's platform anchor is read-only inspection of real resources through the Azure MCP Server. That requires a subscription and a directory role first-year students do not hold, so it is **demonstrated on a staff account and nothing about it is assessed.** The demonstration lasts five minutes inside phase 4 and exists to make one point: the four-register machine on the board has a real counterpart with a name, a region, a size and an hourly line on an invoice.

## Phase 1 · Pretest and prediction (25 min)

Four items on an instruction set the students have not seen, supplied with a one-page reference card.

1. Given three instructions and an initial register state, what is the final state?
2. Which of these two instruction sequences leaves the same state? (Neither does; the difference is a flag.)
3. How many memory accesses does this sequence perform?
4. Predict: will your answer to item 3 match the machine's count?

Item 4 is the calibration item. Students commit to a yes or no, and the reveal comes in phase 4.

**The Copilot prediction, sealed.** A fifth item, answered before phase 3:

5. The agent will be given the same reference card and asked to trace the same sequence. **Will its trace be correct — and if it is wrong, at which step, and how will you be able to tell?**

The third clause is the item. A student who answers "I'll check it against mine" has given the correct answer and has committed themselves to producing a trace worth checking against. A student who cannot say how they would tell has stated, accurately, that the agent's output would be unfalsifiable for them today.

**Warrant.** Pretesting with a reference card available: the retrieval attempt is genuine but the failure is not knowledge-gated, which is the correct configuration at complexity class 1 with no shared prior background. Item 5 is bound to phase 1 by instrumentation rule 8: asked after phase 3 it would measure recall of what phase 3 had already displayed.

## Phase 2 · Cumulative retrieval set (20 min)

First live retrieval phase of the programme. Free recall, no notes.

- Name and describe three mechanisms from S001 phase 4.
- State the reconciliation rule in your own words.
- What was your P1 prediction, and by how much were you wrong?
- One item from S001 phase 3: why did the third timetable defeat the contact-hours account?

Answers written, then a single round of pair-checking, then correct answers displayed. **No marks are recorded.**

**Warrant.** Retrieval practice at the first expanding interval. The final item is deliberately the hardest and most students will not recover it, which is the intended experience — retrieval difficulty is the mechanism.

## Phase 3 · Contrasting cases and generation (45 min)

*First, 25 minutes, unchanged.* Groups receive traces of the **same computation** executed on two machines: a register machine and a stack machine. The traces are complete and correct. The source program is not supplied.

Task: reconstruct the source program, and then answer — **which machine is doing more work, and what does "more work" mean here?**

The second question has no clean answer, which is the point. Groups will propose instruction count, memory accesses, or elapsed steps, and will discover that the three rankings disagree.

Groups commit their answer in writing before presenting.

*Then, 20 minutes: four prompts, run.* The reference card and the two traces are given to GitHub Copilot in agent mode, and each group runs one of:

- **Case A.** *Trace this sequence on the register machine and give the final state.* Checkable against the group's own reconstruction.
- **Case B.** *Trace this sequence on the stack machine and give the final state.* Same.
- **Case C.** *Which of these two machines does more work?*
- **Case D.** *How many memory accesses does the register-machine sequence perform?* A count, checkable exactly.

**The payload is case C.** The agent answers a question that has no answer, decisively, in a paragraph that reads like a resolution. It will pick a metric — usually instruction count, because instruction count is the metric most often discussed in the text the model was trained on — and it will not say that it picked one. The room has just spent twenty-five minutes discovering that three defensible metrics give three different rankings, and it is handed a confident single ranking within a minute of asking for one.

That is the day's central lesson arriving from an unexpected direction. **A quantity is meaningless until you know what question it answers, and a tool that supplies the quantity without the question has not answered you — it has chosen for you and not told you.** The connection to phase 4 point 5 is made there, not here.

Cases A, B and D are the control. They are usually right, and their being usually right is what makes case C dangerous: a tool that had been wrong three times already would not be believed the fourth time.

**Warrant.** Contrasting cases: the two traces differ in surface form and agree in outcome, which is the configuration that makes the invariant structure noticeable. Productive failure: the "more work" question is a preview of the whole measurement strand and is not resolvable today. The four executions are matched on subject and vary only in whether the question posed has a determinate answer, which is the dimension the day is about.

## Phase 4 · Consolidating instruction (50 min)

Indexed to the group answers left on the board.

1. **The stored-program idea.** Instructions and data occupy the same store. Why this is the source of both the machine's power and a great deal of its trouble.
2. **The fetch-decode-execute cycle**, walked through once at full detail on the register machine.
3. **State.** Registers, memory, program counter, flags. The complete state of the machine is a finite object, and "what happens next" is a function of it.
4. **Determinism.** Given the state, the next state is determined. This is the sentence the whole module is built on.
5. **Why "more work" was not answerable.** Instruction count, memory accesses and time are three different quantities, and choosing between them requires knowing what the caller cares about. Forward reference to S011, S019 and S026, made explicit. **Phase 3 case C is put on the board here**, and the class is asked which of the three quantities the agent chose. It did not say. It rarely does.
6. **The machine you are billed for**, five minutes, demonstrated. On a staff account, read-only resource inspection through the Azure MCP Server: a real compute resource, its size, its region, its state. The point is the correspondence — four registers and a flat store on the board; a name, a size code and an hourly rate on the screen — and that the second is billed whether or not anything is running on it. **Nothing here is assessed and no student operates it.** The mechanism behind every number shown is deferred to Q4 and SY102, per the cross-course deferral rule; the artefact element that discharges the deferral is carried at [S017](/archive/bsc-programme/seminars/S017.md), not here.
7. **A default the platform chose for you, in the room's own work.** Agent mode requests confirmation before running a terminal command or a tool that is not built in — so most of what happened in phase 3 was approved by someone. But the boundary is asymmetric and it is documented: agent mode can manipulate only files inside the open solution directory and its subdirectories and cannot reach excluded files, **while terminal commands it runs carry the same permissions as the editor process and are not bounded by that restriction at all.** Two boundaries, one of them much wider than the other, and the wider one is the one nobody pictures. *Perishable: this specific boundary and this specific approval behaviour. Durable: that a tool's stated restriction may bound one of its capabilities and not another, and that reading which is which is your job.*
8. Reveal of pretest item 3 and the item-4 calibration split.

**Warrant.** Worked example with full guidance. This is the module's lowest-extraneous-load phase: one integrated diagram of the machine, annotated in place, no separate legend. Point 6 is capped at five minutes deliberately — it is an instance, not a mechanism, and a longer treatment would import Q4 content into week two. Scope rule, strong form: point 7's boundary description is safe as a statement about the version in front of the student and unsafe as a statement about any other, including the next update.

## Phase 5 · Whole-task learning task (90 min)

**The build: a simulator, and the hand trace that adjudicates it.**

*First, 55 minutes, by hand and unassisted.* Students hand-execute a program on the register machine and produce a **complete trace**: every state transition, every memory access, until termination.

The program is chosen so that it does something recognisable — it computes a running maximum over a small array — and so that it contains one instruction whose effect students will get wrong on the first pass.

Deliverables from this part:

- The full trace.
- A one-sentence statement of what the program computes, written **before** the trace was completed and not amended afterwards.
- The point in the trace at which their pre-statement was falsified, if it was.

**Faded guidance structure.** First third: fully worked, executed with the instructor. Second third: completion problem, alternate transitions supplied. Final third: independent.

*Then, 35 minutes, directed.* The hand trace is sealed. Students then use GitHub Copilot in agent mode to build a small **simulator** for the register machine — a program that reads the reference card's instruction set, executes the same program, and emits a trace in the same format. It runs in a disposable environment; nothing is deployed anywhere.

Then they run it and **diff its trace against their own.**

Three outcomes, all of them informative and all of them assessable:

- **They agree.** The student states which of the two is the evidence and why. The correct answer is neither on its own; two agreeing accounts produced from the same reference card can share a misreading, and the reference card is the only common source.
- **They disagree, and the hand trace was wrong.** The student states what they got wrong and where, and this is the ordinary case for the selected instruction.
- **They disagree, and the simulator was wrong.** The student states what the agent got wrong, and — the required part — **what in the agent's output would have made this detectable without the hand trace.** The answer is usually nothing, and saying so is a pass.

The additional deliverables:

- **The prompt record.** What was asked, in order, with reasons, including abandoned instructions.
- **The intervention record.** Every correction. An empty record fails unless the diff itself demonstrates that the design could have detected an intervention-worthy error, which here it does.
- **The frontier statement.** One thing the agent did faster than the student could — writing a working simulator in a language the student may not know is the usual answer, and it is a true one — and one thing it did badly that the student caught.

**Warrant.** Worked-example to completion to independent problem is the standard fading sequence for high element interactivity with a low schema base. The pre-statement is the generation component and the falsification point is the day's most valuable artefact. The sealing of the hand trace before the agent is invoked is the module's standing countermeasure against a hand artefact written to agree with a machine one; it is procedural and therefore defeatable, and that is stated in [M01](/archive/bsc-programme/modules/M01.md) rather than repeated here.

## Phase 6 · Error clinic (40 min)

Traces are exchanged. Each student finds the **first** divergence between their trace and their partner's, and the pair establishes which is correct by re-executing from the last agreed state.

Then, to the room: three pairs describe a divergence and what caused it. The instructor collects the causes into classes on the board — misread instruction, assumed rather than tracked state, arithmetic slip, skipped step — without attributing any to a person.

**The agent case.** One simulator from the room is put up in which the agent produced a **running, terminating, plausible simulator that was wrong**, and whose output was accepted by its author. Two things are examined and only the second matters.

First, which of the four error classes the agent's error belongs to. Usually it is the same class as the humans': misread instruction. The classes were derived from human traces and they fit the machine's trace as well, which is a real finding and is stated as one.

Second, **why the review did not catch it.** The simulator ran. It produced no error. It emitted a well-formatted trace of the correct length. Every signal the student had available said the work was done, and none of those signals was about correctness. This is the shape the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md) names — a tool that reports success and is wrong — and it is met here in the cheapest possible instance, on a machine with four registers, where the correct answer is on the desk in the student's own handwriting.

**Warrant.** Error management: errors are treated as information about the process rather than about the person. The classification move is what converts an individual mistake into a shared diagnostic vocabulary. Applying the same classification to the agent's error is deliberate and is the first instance of the programme's standing position that the agent is characterised with the same instruments as everything else.

## Phase 7 · Peer articulation (30 min)

Pairs, roles assigned. One student explains **why the machine is deterministic**; the partner attempts to produce a counterexample from ordinary programming experience — a program that behaved differently on two runs.

Every pair will produce one, because every student has experienced this. The explanation must survive by locating the missing state: the clock, the input, the operating system, another process. It always resolves, and the resolution is the actual content of the phase.

**Warrant.** Interactive-tier articulation, and a first encounter with the idea that apparent nondeterminism is unmodelled state — which is retrieved at S032 for concurrency and at S079 for drift.

---

## Phase 8 · Calibration and commitment (20 min)

- Item-4 calibration resolved: who predicted their memory-access count would be right, and who was.
- **Item 5 resolved.** The cohort's predictions about the agent's trace are compared against what the phase 3 case A and case D runs actually produced, and — the part that counts — against the detection method each student named. Students who named a detection method and used it are separated from students who named one and did not. The distribution joins the frontier map opened at S001.
- Each student records the class of error from phase 6 they are most prone to, and one specific check that would catch it. **The same sentence is written for the agent**: one class of error it made today, and one check that would catch it.
- Retrieval schedule issued: S002 material next morning, day 3, week 2, week 5.

## When it does not work

The predicted failures and their countermeasures are argued in [WP-002](/archive/bsc-programme/whitepapers/WP-002.md) §5. Restated here as instruction to the person in the room. Nothing below is assessed.

| What you see | What to do | What the design accepts |
|---|---|---|
| A student who has written assembly finishes phase 5 in twenty minutes | Give them the extension program with the self-modifying behaviour, and assign them the divergence-adjudication role in phase 6 — a genuine task rather than a holding pattern | Phase 4 will be redundant for them and the design does not differentiate it, because splitting the consolidation fractures the shared vocabulary the module depends on |
| A student cannot complete the worked first third of phase 5, and their neighbours can see it | Walk the first third at pace, executing on the board yourself. Make sure the completion problems supply their alternate transitions so that partial failure is bounded. Assign the phase 6 pairing rather than letting it self-select | **This is where the module's first genuine drop-out signal appears.** The residual risk is real and §5 does not claim to remove it |
| A group reconstructs the source program quickly | Press them on the work question with the fourth metric, energy. It produces a fourth ranking and no group anticipates it | Inexpensive. Reconstruction speed does not shortcut the metric disagreement, which is what the phase is actually for |
| A correct trace arrives with no model behind it — symbol-pushing, and the artefact looks identical either way | The pre-statement and its falsification point are the only detector, because neither can be produced mechanically. Phase 7 is the other, since the counterexample cannot be resolved without the model | This is the day's characteristic failure and it is disengaged compliance rather than distress. If a pre-statement is absent or was clearly written afterwards, **treat it as a design problem and not an integrity one** |
| Both traces agree and the student concludes the program is correct | Hold them to specification item 5. Student and agent both read the same reference card, so a shared misreading produces agreement, and agreement produced that way is worth nothing | Named in [WP-002](/archive/bsc-programme/whitepapers/WP-002.md) §3.2 as the first of three conditions under which the day's simplification is unsafe |

## Assessment

One specification item in SY101. No entrustment evidence. Resubmittable with tokens.

Checked, in binary:

1. The trace: complete and correct.
2. The pre-statement, present and unamended.
3. The falsification point, or its stated absence.
4. The simulator, running, with the diff against the hand trace.
5. The adjudication: which account is the evidence, and — where the simulator was wrong — what in the agent's output would have made that detectable without the hand trace. "Nothing would have" is a pass.
6. **The prompt record.**
7. **The intervention record.** An empty record fails unless the diff at item 4 is present.
8. **The frontier statement**, both halves, specific to this build.

**Nothing else is assessed.** The simulator's code quality is not assessed. The number of prompts is not assessed. Whether the agent's trace was right is not assessed — only whether the student found out.

*Annotation at the point of change.* Items 1 to 3 are the original specification and are unchanged; the [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md)'s S001–S040 non-retroactivity boundary holds over them. Items 4 to 8 are new elements and are stated in the closed form the rule requires.

## What this day does not establish

The day demonstrates two things and both are cheap by design: that a sealed hand trace and an agent-built simulator can be diffed and the divergence adjudicated, and that on phase 3 case C the tool supplied a ranking without naming the metric it ranked by. **Both are observations about one room, one program and one model version, and the day claims nothing about how often either happens** — no rate is asserted here for the tool's accuracy, and none is published by the vendor.

What rests on a note: the error-management framing at phase 6, in [research/04-professional-formation/keith-frese-error-management-training.md](/research/04-professional-formation/keith-frese-error-management-training.md), for direction and mechanism only. And the Azure demonstration is declared demonstrated rather than operated, so it establishes nothing about the student and is assessed nowhere.

## What to take from this day

**The claim to hold.** **A tool that reports success has told you nothing about correctness.** A machine's next state is a function of its current state, so a complete account of a program's behaviour can be produced — and what makes any account checkable is a second one produced independently. Today you hold both, at no cost.

**What the sources license, and what they do not.** The error-management framing behind phase 6 is verified here, in [research/04-professional-formation/keith-frese-error-management-training.md](/research/04-professional-formation/keith-frese-error-management-training.md), and supports **direction and mechanism only**; no magnitude is asserted. The position that a tool can report success and be wrong rests on the decomposition at [research/06-microsoft-platform/agent-framework-and-evaluations-docs.md](/research/06-microsoft-platform/agent-framework-and-evaluations-docs.md) — **a note written from search-returned excerpts rather than a full page fetch**, so it is used as vocabulary rather than as a finding.

**Guidance for your own work.**

- **Seal your own account before you run the other one.** An account written after seeing a machine's is a memory of agreeing with it.
- **When a quantity arrives without its question, the question was answered for you.** Ask which of instruction count, memory accesses or time it is, and who chose.
- **Classify what a clean run establishes**, using the five classes on the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md). A simulator that runs is an executable check; that it emitted a well-formed trace is an observed result; that it is right is an unsupported inference until you diff it.
- **Read which capability a stated restriction bounds**, and then check whether the other one is bounded at all.

**Where this is easy to get wrong.** Accepting the artefact because every available signal said the work was done. It ran, it terminated, it raised no error and its trace was the correct length — and not one of those signals was about correctness.
