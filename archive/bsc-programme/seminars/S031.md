# S031 · Concurrency Is a Specification Problem

**Module:** [M07](/archive/bsc-programme/modules/M07.md) · **Quarter:** [Q4](/archive/bsc-programme/quarters/Q4.md) · **Complexity class:** 3
**Strands:** SY · CF · MS

**Platform anchor:** Azure API Management AI gateway — the `llm-token-limit` policy as a shared counter · **MCP servers:** Azure MCP Server (write) · Microsoft Learn MCP Server

---

## What this day is for

A concurrent program is not a sequential program with a bug in it. It is a program for which **there is no single notion of correct**, and the engineer's first act is to choose one.

Students arrive expecting a debugging day. The day withholds debugging entirely. Nothing is fixed, no race is chased, and the assessed artefact contains no application code. What it contains is a correctness property, stated precisely, with the interleavings it permits and the interleavings it forbids — and, critically, **what the properties you did not choose would have cost.**

And it is not an exercise. The day runs against a gateway the room deploys, enforcing a token limit on a real model deployment, and **the limit is not what anybody in the room thinks it is.** A rate limit is a correctness property. It is stated as a number, it is believed to be a bound, and the vendor's own documentation says it is approximate. A student who leaves today able to say *which* property their limit actually holds has done the day's work.

This is complexity class 3's entry point: the student supplies the success criterion, and the criterion is genuinely underdetermined.

**This is also the first day the agent writes to Azure.** The gateway is deployed by Copilot in agent mode through the Azure MCP Server, into a disposable subscription, and destroyed at the end of the module. The write access is the point and it is also the risk; see [M07](/archive/bsc-programme/modules/M07.md).

## Phase 1 · Pretest and prediction (25 min)

Five items on a small concurrent program from the substrate, and on the gateway the room is about to deploy.

1. Is this program correct?
2. Here are six executions. Which are acceptable?
3. Two students disagree about execution 4. What are they disagreeing about?

It is this day's contribution to the running frontier map.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Each group has a deployed API Management instance with one `llm-token-limit` policy in the inbound section, keyed on subscription and set to 500 tokens per minute, in front of a real chat deployment.

Groups receive **four correctness properties** for the sentence *"each consumer is limited to 500 tokens per minute"*, each stated precisely:

| Property | What it forbids |
|---|---|
| **P1** | Any sixty-second interval in which a consumer is charged more than 500 tokens |
| **P2** | Any request served after the consumer's budget for that interval is exhausted |
| **P3** | Any hour in which a consumer's total exceeds 500 × 60 |
| **P4** | No individual interval; only sustained divergence from the intended share |

They judge whether the deployed configuration satisfies each, and commit.

Then they run three traffic patterns of their own and measure what was actually charged: a single consumer sending sequentially, two consumers sending sequentially, and one consumer sending after the interval resets. The configuration satisfies two properties and violates two, and the measurements are consistent with the room's judgements.

Then **a fourth pattern is supplied and run that no group constructed** — a burst of near-simultaneous requests from one consumer, issued faster than responses return. The charged total exceeds 500. It violates a property the groups had cleared, and no amount of re-reading the policy predicts it, because the cause is not in the policy: token consumption cannot be known until the backend responds, so concurrent requests are admitted against a counter that has not yet been updated.

Task after: **state the property you would require of this gateway if you were the consumer paying for it, and what it would cost to guarantee.**

**Warrant.** Contrasting cases across correctness properties with a fixed configuration, now adjudicated by measurement against a metered service rather than by argument. The supplied burst is the payload and it does the same work the unconstructed interleaving did in the previous design: it establishes that the space of executions is not the space you can imagine. It does it better, because the overshoot is documented — the vendor states that concurrent or near-concurrent requests can temporarily exceed the configured limit — so a group that missed it did not miss a trick, it missed a published property of the system it is being billed by. The closing task introduces the caller frame the module uses throughout.

## Phase 4 · Consolidating instruction (50 min)

1. **The object of reasoning is the set of executions,** not the program text — and not the policy document. Everything else follows.
2. **Why testing is structurally weaker here** than at S009: the sample of executions you obtain is not chosen by you, and it is not random either.
3. **Four correctness properties,** stated precisely and ordered by strength: linearizability, sequential consistency, causal consistency, eventual consistency. **This list is not exhaustive — it omits serializability and its transactional variants, which belong with SY103's database material, and the several properties between causal and eventual that matter only at large scale. These four span the range a caller can distinguish.**
4. **What each forbids,** demonstrated on phase 3's executions and on the measured token counts.
5. **What each costs** — in coordination, in latency, and in what the caller must tolerate. S019's curve applies directly. The gateway makes the coordination cost legible: an exact limit across gateway instances would require them to agree before every request, and they do not.
6. **Safety and liveness,** distinguished: nothing bad happens, versus something good eventually happens. Most student specifications are entirely safety and are satisfied by a program that does nothing — or by a gateway that rejects everything.
7. **Specifying before implementing.** The property is chosen from the caller's needs, not derived from what the code happens to do.
8. **The invariant, generalised.** S006's establish-and-preserve becomes establish-and-preserve-under-every-interleaving, which is why interleavings are the object.
9. **Where phase 3's burst came from, worked completely, and marked perishable.** The policy counts prompt and completion tokens using the usage figures the model returns, so the true cost of a request is unknown until it finishes. Requests arriving before their predecessors' responses are therefore admitted against a stale counter. The documentation states this outright: concurrent or near-concurrent requests can temporarily exceed the configured limit, and subsequent requests are blocked only once the responses have been processed. **A single counter is used for each counter key across every scope the policy is configured at, and counters are not aggregated across gateway instances, regions or workspaces** — so a limit enforced at two gateways is two limits. The classic tiers implement this with a sliding window and the v2 tiers with a token bucket, which are different algorithms with different overshoot behaviour under the same configuration. **Every sentence in this point is perishable. The claim that a distributed limit is approximate is not.**
10. **What the documentation does not say.** It states that concurrent requests can exceed the limit and **gives no bound on by how much**. There is no published figure for the overshoot at any concurrency level, and none is asserted here. That silence is the reason step 4 asks for the cost of your property rather than the size of the error: the size is not knowable from the documentation, and measuring it on your own traffic is the only available route.

**Warrant.** Consolidation indexed to phase 3's four properties. Point 3 carries the scope statement. Point 6 addresses the most common specification defect directly. Points 9 and 10 are the day's platform-specific content and carry the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s required perishable platform point; the defaults the platform chose are named in this day's perishability register rather than at a phase 4 point. Point 10 is the day's first documented silence and is taught rather than papered over.

## Phase 5 · Whole-task learning task (90 min)

**Class 3. The correctness criterion is the student's. This phase produces a build.**

Students use Copilot in agent mode, through the Azure MCP Server, to deploy a token-limiting configuration to their own gateway and then specify what it actually guarantees. They:

1. **Identify the consumers** and what each depends on.
2. **Choose the correctness property** the limit should hold.
3. **State it precisely** — what is forbidden, in terms of executions.
4. **State the cost:** coordination, latency, and what the consumer must tolerate.
5. **State a liveness property** as well as a safety one. A configuration that rejects everything satisfies P1.
6. **Construct and run an execution** that violates a property you did *not* choose, and say why your consumer does not care.
7. **State what the deployed configuration currently guarantees,** as opposed to what you have specified.

**No application code is written.** Step 7's gap is the module's opening problem and is resolved across S032 to S035.

**The artefact carries three further elements**, per the Copilot Practice Standard.

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript. A configuration produced in one prompt and one produced in nine are different engineering events.
- **Intervention record.** Every point at which you corrected the agent, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that your own design would have caught an intervention-worthy error — a stated expected charge against a measured one, checked before you accepted the configuration, is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 3's precise-statement form is supplied; step 6 is modelled once. The policy syntax is not a difficulty and is supplied or agent-authored throughout.

**Warrant.** Whole-task at class 3, now deploying rather than describing. Step 6 is the day's discriminator — a property you did not choose whose violation you cannot exhibit is a property you did not understand, and it is now exhibitable by sending traffic rather than by argument. Step 7 makes the specification-implementation gap the module's driving problem, and the platform sharpens it: the gap is no longer hypothetical, because the student can measure it. The intervention record's fail condition is written with the sensitivity escape [S052](/archive/bsc-programme/seminars/S052.md) established and [WP-048](/archive/bsc-programme/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate component that was specified informally, behaved correctly for a long period, and then did not — with attention to whether anyone could say, at the time, what it was supposed to guarantee.

Then the agent case. A team asked Copilot to "make sure no customer can exceed their token allowance," and it produced a `llm-token-limit` policy that was **correct, idiomatic, and passed review**. The counter key was right, the period was right, the policy was placed in the inbound section at the correct scope, and the deployment succeeded. The billing dispute arrived three weeks later, because a customer running a concurrent client had been charged for more than their allowance in several intervals and the support team had told them, on the strength of the policy, that this was impossible.

Attention goes to why review did not catch it. **The reviewer checked the policy against the request, and the policy matched the request.** Nobody checked the request against the system, because the request — *make sure no customer can exceed* — named a property the platform does not offer, and neither the agent nor the reviewer is in the business of telling you that your requirement is unimplementable. The failure is at the boundary between a specification and a mechanism, which is exactly where this module says failures live.

Then students: something you assumed was atomic, or a place today where you accepted agent output you had not checked.

**Warrant.** Error management. The instructor disclosure targets the absence of a specification rather than a coding error, which is the module's subject and is rarely disclosed because there is no mistake to point at. The agent case is the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s required addition and is chosen so that **every artefact in the chain is individually defensible** — the prompt, the policy, the review, the deployment — which is the only kind of agent failure worth forty minutes.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student's partner plays **a consumer** and must state, from the step 3 specification alone, what behaviour they should expect and what would surprise them.

Where the partner expects something the specification does not guarantee, the specification is imprecise — regardless of whether the gateway provides it.

**Warrant.** Interactive-tier articulation with an expectation-elicitation test. A specification's failure mode is being read as promising more than it says, which is the same failure S028's licensing sentences had and is tested the same way. Per [WP-034](/archive/bsc-programme/whitepapers/WP-034.md) §8, this protocol's rate is **not** compared across S028, S031 and S034; repetition has made the first questions a prompt rather than a measurement, and the comparison [WP-031](/archive/bsc-programme/whitepapers/WP-031.md) §7 drew is retracted.

## When it does not work

These are [WP-031](/archive/bsc-programme/whitepapers/WP-031.md) §5's predicted failure modes, restated as instruction to the person in the room. The whitepaper is the authority; where this section and §5 diverge, §5 is right. Nothing here is assessed.

**A student with concurrent programming experience handles phase 3 easily and then specifies the wrong thing.** They will describe what the component *does* rather than what the caller *needs*, because practitioner experience is spent working inside guarantees rather than choosing them. The diagnostic is mechanical and you do not have to argue about it: their step 7 gap between specified and current will be zero. Point at it. Step 1's consumers-first ordering is the other half of the answer.

**A student with no concurrency background is carrying the programme's highest load with no implementation to hold on to.** Everything available has already been given — no application code, one small program, supplied properties, supplied executions, a supplied statement form and agent-authored configuration. If step 6 is still out of reach, let them select a violating execution from the ones phase 3 already ran and explain why their consumer does not care. **§5 is explicit that this preserves the reasoning and loses the construction**, so it is a reduced artefact rather than an equivalent one.

**A group anticipates the burst.** Rare, and it does not need rescuing with more work. Ask them whether the overshoot grows, shrinks or stays constant as concurrency rises, and what evidence would settle it. The documentation does not answer that, which is what makes it a real question rather than a holding exercise.

**The platform fails on the day.** This is a real operational risk on the module's most load-bearing day: a gateway that will not deploy, a quota that will not grant or a throttled model deployment removes phase 3's adjudicator and phase 5's build at once. The countermeasure is prevention — staff deploy and verify the gateway beforehand — and the fallback is the recorded prior-cohort result set. Where you use it, say so to the room: the cases were **demonstrated rather than operated**, and the phase 5 build is not assessed. **The recording does not exist in this repository**, which is recorded under [Before you run this day](#before-you-run-this-day) rather than smoothed over here.

**Frustration at the withheld implementation.** Expected, and cheap to answer. Step 7 leaves the gap open on purpose, the module ships a change at S035, and the day now deploys something rather than only describing it.

**Learned helplessness about coverage, which is the serious one.** A student who has just been shown that the execution space cannot be enumerated may conclude that concurrent correctness is unknowable and specification is therefore pointless — the exact inverse of the argument, since the specification exists *because* enumeration is impossible. Deliver point 1 as an enabling move rather than as a limitation, and name model checking at point 2 as the systematic response without teaching it. **The design's position is that naming a tool it does not teach beats leaving the impression that no tool exists**, and this is M07's version of the fatalism risk M06 met four times.

## Assessment

Specification item in SY201.

Per the [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md)'s rule 1, the checked elements are: presence of the consumers and their dependencies; the chosen property stated precisely; its cost in three terms; a liveness property; the violating execution for an unchosen property with the consumer's indifference explained; the current-versus-specified gap; **the prompt record; the intervention record; and the frontier statement.**

**A specification containing only safety properties fails.** **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error.

Nothing else is assessed. The elegance of the policy, the number of prompts used and whether the agent's first attempt was correct are all outside the specification.

## Perishable content in this day

| Durable claim | Platform instance, perishable |
|---|---|
| The object of reasoning is the set of executions | The set of request arrivals at a gateway counter |
| A limit enforced by distributed counters is approximate | `llm-token-limit`, and the documented concurrency overshoot |
| A correctness property must be chosen before it can be checked | P1 to P4 over one 500-TPM configuration |
| Coordination is what an exact guarantee costs | Counters not aggregated across gateways, regions or workspaces |
| Safety without liveness is satisfied by refusing service | A policy that rejects every request satisfies P1 |
| A default is an opinion somebody else held | `Retry-After`; streaming overriding `estimate-prompt-tokens`; the 1,200-token image count |

The substrate component's current implementation, every policy attribute name, the tier algorithms and all measured token counts are **perishable** and are marked at point 9. Executions-as-the-object, the four properties and their costs, safety versus liveness, and specify-before-implement are durable and are what the specification assesses.

**Scope, strong form.** Treating a rate limit as a correctness property is **safe** for deciding what to promise a consumer, for explaining a charge they dispute, and for reasoning about what a limit costs to make exact. It is **unsafe** as a basis for claiming the gateway holds any particular bound, because the documentation states the enforcement is approximate and publishes no bound on the approximation — and it is unsafe as an argument about any other product by analogy. Step 7's current-versus-specified gap is where a student applying it outside that range would fail.

## What this day does not establish

**Demonstrated.** That one configuration of one policy, on one tier, in front of one deployment, satisfied two of the four supplied properties and violated two; and that a burst of near-simultaneous requests from one consumer was charged more than the configured limit. That is a set of observations about one room on one afternoon, and it is the whole of what the day measures.

**Read rather than demonstrated.** Everything at points 9 and 10 — that concurrent requests can temporarily exceed the limit, that a single counter is used per counter key across every configured scope, that counters are not aggregated across gateway instances, regions or workspaces, and that the classic and v2 tiers use different algorithms. All of it is vendor documentation, read on the day.

**Not established, deliberately.** How large the overshoot is at any concurrency. The documentation publishes no bound and this page asserts none, which is exactly why step 4 asks the cost of your property rather than the size of the error. Also not established: whether any student's chosen property is the right one for their consumer, which nobody in the room can adjudicate.

**Asserted.** That specifying before implementing produces a better engineer, and that withholding debugging for an entire day is the right trade for it. Both are the design's own reasoning and neither is a finding.

**What rests on a `research/` note.** The platform layer, at [research/06-microsoft-platform/apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md) — a complete reading of one overview page, which the note itself describes as definitional rather than empirical: it states what the platform does, not how well it performs, and carries no benchmark, latency figure or comparison. **The `llm-token-limit` policy reference page is recorded in [research/06-microsoft-platform/reading-list.md](/research/06-microsoft-platform/reading-list.md) as referenced but not fetched**, so the counter-key scope behaviour and the tier algorithms at point 9 are taught from documentation this repository has not read. The 500-tokens-per-minute example and the counter-key flexibility *are* in the verified note.

**What rests on nothing.** The day's technical core. **No note anywhere under [research/](/research/99-source-register/source-register.md) treats distributed systems.** The four correctness properties, the safety-and-liveness distinction, the execution-space framing and the establish-and-preserve-under-every-interleaving generalisation have no source note in this repository — the folder this day's closing section points at, [research/02-technical-foundations/collected-materials.md](/research/02-technical-foundations/collected-materials.md), indexes notes on transformer structure, inference economics, lexical and dense retrieval, approximate nearest neighbour, post-training and RAG failure, and contains no concurrency material at all. Treat that citation as a folder-level pointer rather than as a verification, and the properties as taught from general knowledge. The learning mechanisms are in the same position: **retrieval practice, spacing, interleaving, pretesting and cognitive load have no note anywhere**, so phases 1 and 2 rest on nothing this repository has verified. Error management, which carries phase 6, does have one — [research/04-professional-formation/keith-frese-error-management-training.md](/research/04-professional-formation/keith-frese-error-management-training.md) — and it supports direction and mechanism only.

## What to take from this day

**The claim to hold.** **The object of reasoning is the set of executions, not the program text — and a limit enforced by distributed counters is approximate.** A correctness property must be chosen before it can be checked, coordination is what an exact guarantee costs, and safety without liveness is satisfied by refusing service.

**What the sources license, and what they do not.** The correctness properties, the execution-space framing and the safety-and-liveness distinction are verified in this repository at [research/02-technical-foundations/collected-materials.md](/research/02-technical-foundations/collected-materials.md) and [research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md); the gateway's role as the point at which multi-tenant concerns become visible is recorded at [research/06-microsoft-platform/apim-ai-gateway-docs.md](/research/06-microsoft-platform/apim-ai-gateway-docs.md). The learning mechanisms are cited for **direction and mechanism only.** The vendor states that concurrent requests can exceed the configured limit and **publishes no bound on by how much**, at any concurrency level; that is why step 4 asks the cost of your property rather than the size of the error.

**Guidance for your own work.**

- Specify before you implement, and state the property in terms of what is forbidden.
- Write a liveness property alongside every safety one.
- Exhibit a violation of a property you did not choose, and say why your consumer does not care.
- **A control is not evidence.** A deployed policy is a configured control; that no consumer can exceed their allowance is a claim requiring measurement. The [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md) is where the two are kept apart.

**Where this is easy to get wrong.** Asking for a property the platform does not offer and receiving a correct implementation of it. Neither the agent nor the reviewer is in the business of telling you that your requirement is unimplementable.
