# S007 · Decomposition and the Cost of a Bad Seam

**Module:** [M02](/archive/bsc-programme/modules/M02.md) · **Quarter:** [Q1](/archive/bsc-programme/quarters/Q1.md) · **Complexity class:** 1
**Strands:** CF · SY · PE

**Whitepaper:** [WP-007](/archive/bsc-programme/whitepapers/WP-007.md)
**Depends on:** S006
**Re-tests:** S002, S003

---

## What this day is for

Students are taught that programs should be decomposed and given no criterion for doing it. The advice they receive — keep functions short, separate concerns, avoid repetition — is a set of aesthetics, and aesthetics cannot adjudicate between two decompositions that both satisfy them.

This day supplies the criterion. **A seam's cost is the cost of the changes that cross it.** A decomposition is good or bad only relative to the changes that actually arrive, which are not knowable in advance, which is why decomposition is a bet rather than a derivation. The day teaches students to make the bet explicitly, record it, and find out whether they were right within the same six hours.

That structure — commit a prediction, receive the evidence, reconcile — is the shape of every measurement day from S026 onward, and this is its first appearance.

The day has a second object, and it is the same object. **A repository's customization surface is a decomposition, and its seams cost what crosses them.** One always-on instructions file is the eighty-line function. Several `*.instructions.md` files with `applyTo` globs are a split. Prompt files and custom agents are further splits, drawn on a different axis. Every one of these is a bet about which conventions will change together, and — unlike the code decomposition — the bet is settled by running it.

## Phase 1 · Pretest and prediction (25 min)

Students receive a small program written as one function of about eighty lines.

1. Split it. Draw the seams you would put in.
2. Say why, in one sentence per seam.
3. What change to this program would your decomposition make *harder* than leaving it alone?
4. Predict: will your answer to item 3 match anything the day shows you?
5. **Sealed Copilot prediction.** The same function will be handed to Copilot in agent mode with the instruction *split this*. Write down now, and seal it: what seams will the agent draw, and **where will its decomposition be wrong**? Name the change you think it will make expensive.

Item 3 is the day's central move, asked before any instruction, and most students cannot answer it. That inability is the pretest's result. Item 5 is opened at phase 8; the design expects the room to predict the agent's seams accurately and its costs badly, which is the same failure item 3 exposes in their own work.

**Warrant.** Pretesting with generation. Item 3 establishes, before instruction, that students have a decomposition instinct and no cost model — which is the day's thesis produced by the students rather than asserted at them. Item 5 sits before phase 4 and stays there, per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

Groups receive **one problem decomposed three ways**. All three work. All three pass the same tests.

- **Decomposition A** splits by processing stage.
- **Decomposition B** splits by data type.
- **Decomposition C** splits by which part of the system is expected to change.

Groups rank them and commit the ranking in writing, with reasons.

**Then the change request arrives.** It is a single, entirely ordinary change — the kind a real user asks for. Under one decomposition it touches one function. Under another it touches nine and requires a signature change that propagates.

Groups then reconcile: what did your ranking criterion actually predict, and what did it miss?

**Then the same exercise is run, executed, on the repository's customization surface.** Groups receive a workspace whose conventions are already written down, decomposed four ways, and one convention change to apply in agent mode. The change is small and ordinary: *preconditions must be stated in the same comment as the signature they qualify* — specification rule 2, arriving as a real request.

| Case | Decomposition of the customization surface | Files the room expects to touch |
|---|---|---|
| A | One `.github/copilot-instructions.md` holding every convention | One |
| B | Split by file type: several `*.instructions.md`, each with its own `applyTo` glob | Two or three |
| C | Split by volatility: a stable always-on file plus one file-scoped file for the conventions that move | One |
| D | Split by folder: an `AGENTS.md` in each subtree | One |

Groups predict the touch counts, apply the change, then run the identical prompt under each configuration and read the **References** list to see which files were actually in force.

**Case D is the payload.** It is the cleanest-looking split, it touches one file, and under default settings the subfolder files are never read at all — nested `AGENTS.md` support is experimental and gated behind a setting that is off. The decomposition is not merely a bad bet; it is not running. Case B produces the second surprise: groups who split general-to-specific and expect the specific file to refine the general one find that the documentation guarantees no combination order, so the refinement wins or loses without a rule.

Closing generation demand: **what is the cost of a seam you cannot see the other side of?**

**Warrant.** Contrasting cases with a delayed adjudicator. The prediction-then-evidence structure is the day's core mechanism; a ranking made before the change request is a genuine commitment, and the reconciliation is where the criterion is learned. The executed half repeats the structure on a surface where the adjudication is mechanical rather than argued, and cases D and B supply two failures that no amount of ranking would have found.

## Phase 4 · Consolidating instruction (50 min)

1. **A seam is an interface, and an interface is a set of invariants** — S006, directly. A seam you cannot specify is a seam in the wrong place.
2. **The cost of a seam is the cost of the changes that cross it.** Stated plainly; this is the retrievable sentence.
3. **Why aesthetics fail.** Short functions, separated concerns and no repetition are all satisfiable by decompositions with wildly different change costs, as phase 3 demonstrated.
4. **Coupling and cohesion, defined by change** rather than by structure: two things are coupled if changing one requires changing the other, whatever the diagram says.
5. **Decomposition is a bet on the future.** You are predicting which parts will change together. You will sometimes be wrong, and the correct response to being wrong is to move the seam, not to defend it.
6. **The seam you cannot move.** Some seams — a published interface, a stored data format, a protocol another team depends on — become expensive or impossible to relocate. Recognising these in advance is the only part of decomposition where being conservative pays.
7. **Forward link, stated once.** Point 6 is the same idea as a consistency contract at S034, a domain model at S038, a tool boundary at S073 and a handover boundary at S089.
8. **The customization surface is a decomposition and obeys points 1 to 6 without amendment.** An `applyTo` glob is a seam. A prompt file is a seam drawn around a procedure rather than around data. A custom agent is a seam drawn around a **tool list**, which is the first time in this programme a boundary is defined by what may be done rather than by what may be known — and the documentation's own advice for it is least privilege. The cost of each is the cost of the convention changes that cross it, which is point 2 unchanged.
9. **Three defaults the platform chose for you, all perishable, all verified against the Visual Studio Code agent-customization documentation as it stood on 15 July 2026.** *Defaults are opinions and thresholds are policy*, and this is the day where that becomes a seam question.
   - **Parent-repository discovery is off.** In a monorepo, opening a subfolder rather than the repository root means the repository's own conventions are not discovered, unless a setting is enabled and the parent folder is trusted. Nobody drew that seam; the client did, on your behalf, and it is invisible from inside the subfolder. **This is the day's exact subject: a seam that was correct when drawn and became wrong when the working directory changed.**
   - **Nested `AGENTS.md` support is experimental and gated.** Case D's decomposition depends on a flag.
   - **An unavailable tool named in a prompt file or a custom agent is ignored.** The documentation states this for both. A seam defined by a tool list degrades silently to a wider seam when the tool is missing, and nothing in the run says so.
10. **The scope of the cost model, stated at the strength the design can defend.** *A seam's cost is the cost of the changes that cross it* is safe where you can count what a change touched — source files, configuration files, instructions files — and it is what you should use for every decision this quarter. It is unsafe in two conditions. First, where the seam is a **trust boundary**: a boundary drawn around what an agent may do is not evaluated by counting edits, and moving it to reduce change cost can widen what the agent may do. Second, where a seam's cost falls on someone who is not editing — the reader, the operator, the on-call engineer. Both are taken up properly at [S073](/archive/bsc-programme/seminars/S073.md) and [S089](/archive/bsc-programme/seminars/S089.md), and neither is in scope today. **A student who moves a tool-list seam in this day's artefact on change-cost grounds alone fails the specification**, which is the checkable form of this boundary.

**Warrant.** Consolidation indexed to phase 3's reconciliations. Point 2 is deliberately one sentence because it is what the three-year retrieval schedule must carry. Points 8 and 9 consolidate what the executed half produced rather than asserting a claim the room has not met. Point 10 is the strong-form scope statement and is bound to a fail condition, per the widening recorded in the [Whitepaper Standard](/archive/bsc-programme/program/05-Whitepaper-Standard.md).

## Phase 5 · Whole-task learning task (90 min)

Students take a substrate component and:

1. **Predict the change.** From the substrate's actual change history — supplied with dates and descriptions but with the *implementations* withheld — state which two changes are most likely to recur.
2. **Decompose** the component to make those two changes cheap, **and decompose its customization surface with it.** A seam in the code that no instructions file follows is a seam only you can see. Commit both in writing before implementing.
3. **State the bet.** Which changes have you made expensive in exchange? Answer for both decompositions; they can disagree, and where they disagree is the interesting part.
4. **Implement the decomposition** and the instructions files that follow it, in agent mode. Confirm from the References list which files were in force.
5. **Receive a real change** from the substrate's actual future history — one the student has not seen — and implement it. **Count two things: the source files you touched, and the conventions you had to restate in the prompt because no file carried them.**
6. **Reconcile.** Was your bet right? If not, where would the seam have had to be? Answer separately for the code and for the customization surface, and say which of the two counts you would have predicted worse.

Step 5's change is genuinely from the system's history and is chosen so that roughly half the room predicted it and half did not. The second count in step 5 is the day's new instrument: **every convention you had to restate in a prompt is a seam your customization surface does not have**, and the number is exact rather than argued.

The build is steps 4 and 5: a decomposed component and a decomposed customization surface, both running, with a real change pushed through both.

**The artefact carries three additional elements**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** What you asked for, in order, including the instructions you abandoned. On this day the record has a second job: a convention that appears in the prompt record and in no file is exactly the seam step 6 must account for.
- **Intervention record.** Every point at which you corrected the agent and what the correction was. **An intervention record with no entries fails**, unless the artefact shows that your decomposition would have surfaced an intervention-worthy error — for this day, a convention whose violation your instructions surface would have caught.
- **Frontier statement.** One thing the agent did faster than you could have, one thing it did badly that you caught. Both from this build.

**Faded guidance:** step 2 is worked with the room for one seam; steps 3 to 6 are independent.

**Warrant.** Whole-task at class 1. The commit-then-evidence structure repeats phase 3's mechanism at greater length and with the student's own work as the object. Step 6's counterfactual — where would the seam have had to be — is the step that converts a wrong bet into learning rather than into discouragement. The second touch count is added because it is countable, cheap and immune to the narration problem [WP-007](/archive/bsc-programme/whitepapers/WP-007.md) §8 identifies in step 6.

## Phase 6 · Error clinic (40 min)

Instructor first: a seam in the substrate that was drawn in the right place for eight months and in the wrong place afterwards, because the product changed. Emphasis on the fact that **the original decision was correct when it was made**.

Instructor second, an agent case: a set of instructions files whose globs were drawn around one team's folder, correctly, and which stopped being in force the day people began opening that folder as the workspace root instead of the repository. The agent produced code that violated three conventions with complete confidence. **The pull request was approved by two reviewers**, and the clinic's attention is on why: the new code was consistent with the code around it, because the code around it had been written the same way for a fortnight. The seam had moved and nothing announced it.

Then students: a structure you built that made a later change harder than it needed to be.

Classified by whether the seam was wrong when drawn, or became wrong.

**Warrant.** Error management, with a disclosure whose whole point is that being wrong later is not the same as having been wrong. That distinction is what makes step 6's reconciliation safe to do honestly. The agent case is the same classification with a default rather than a product change as the cause, and it is chosen because review passed it.

## Phase 7 · Peer articulation (30 min)

Pairs. Each student describes their step 3 bet — what they made expensive — and the partner's task is to **propose a change that exploits it**: a plausible, ordinary request that the student's decomposition handles badly.

The student then says whether they would move the seam or accept the cost, and why.

**Warrant.** Interactive-tier articulation with an adversarial construction demand, and a decision demand attached. The second half is the day's only class-2-flavoured moment and is deliberately kept as a discussion rather than an artefact.

## Phase 8 · Calibration and commitment (20 min)

- Item 3 and item 4 resolved together: how many students could name a cost before instruction, and how many named the cost the day actually demonstrated.
- **Item 5 unsealed.** Seam predictions and cost predictions scored separately and shown unattributed. The design expects the first to be good and the second to be poor, and the gap is the day's contribution to the frontier map — a sample of one cohort, one component, one model version, and labelled as such.
- The room's step 5 touch-counts are shown as a distribution, unattributed — both counts, source files and restated conventions, side by side.
- Each student names one seam in their own current work that they now believe is in the wrong place, and whether they will move it.
- Retrieval schedule: next morning, day 3, week 2, week 6.

## When it goes wrong

The predicted failures and their countermeasures are argued in [WP-007](/archive/bsc-programme/whitepapers/WP-007.md) §5. Restated here as instruction to the person in the room. Nothing below is assessed.

| What you see | What to do | What the design accepts |
|---|---|---|
| A student who has maintained a codebase over years finds phase 3 obvious and wins the exercise | Hold them to step 3 — *name what you made expensive.* Intuition optimises without articulating, and experienced students fail that step at similar rates to inexperienced ones. Brief their phase 7 partner to press hardest on vague bets | The predicted failure here is winning and learning nothing, because their existing cost model suffices and is never made explicit |
| A student who has never seen a seam become wrong is being asked to predict change in a system they have known six weeks | Point them at the supplied change history — dates and descriptions — so that prediction is inference from evidence rather than from experience, and lean on phase 3's ranking task, which is comparative and needs no cost model | Their step 1 predictions will be poorer and their step 5 counts higher. **The phase 8 distribution is unattributed for exactly this reason, and you say aloud that the spread reflects codebase experience rather than ability** |
| A group ranks decomposition C first, for the right-sounding reason | Usually this is not success. Ask what their criterion *missed*, not whether the ranking was right — a group that ranked correctly because "split by what changes" sounds principled is exposed by that question and not by the ranking | Common, and the reconciliation question is built to catch it |
| A group genuinely resolves everything | Give them the second change request, which favours decomposition A, and ask them to explain why C is still preferable — or to concede that it is not | Both answers are legitimate. Conceding is the better one |
| A student concludes that since the future is unknowable, decomposition cannot be reasoned about at all | **Name fatalism out loud if it surfaces; the unspoken version curdles into cynicism by S039.** Then use phase 4 point 5, which frames wrongness as an expected outcome with a defined response, phase 6's disclosure of a senior engineer treating a wrong seam as ordinary, and step 6's counterfactual, which gives a wrong bet a productive output | This is a live risk with any prediction-under-uncertainty exercise and it is the exact opposite of the intended lesson |
| The executed half will not run: a network failure, or a client update that has moved the References list | Use the recording. Then say out loud that cases A to D were **demonstrated rather than operated**, and that elements 4, 6 and 8 are not assessed; the second touch count falls back to a stated prediction with no adjudicator | §5 calls this a materially weaker day and describes it as one. Do not present the fallback as equivalent |

## Assessment

Specification item in CF101.

The following elements are checked, each as a binary decision:

1. The committed change prediction.
2. The committed decomposition, of the component and of its customization surface.
3. The explicit bet, stated for both.
4. The implementation, with References-list evidence of which instructions files were in force.
5. The source-file touch count for the real change.
6. The restated-convention count for the real change.
7. The reconciliation, including the counterfactual seam placement. **A reconciliation that concludes the bet was right without evidence from step 5 fails.** A reconciliation that concludes the bet was wrong and says where the seam should have been passes.
8. **One named interaction between two of your own customization files that the platform does not define**, and what you did about it. One sentence. A decomposition of a surface with undefined composition that reports no such interaction fails.
9. **The prompt record.**
10. **The intervention record.** No entries fails unless element 4 shows a surface that would have caught a convention violation.
11. **The frontier statement,** both halves, specific to this build.

One fail condition is separate from the list and follows phase 4 point 10: **a student who moves a tool-list seam on change-cost grounds alone fails,** whatever the touch counts say.

**Nothing else is assessed.** The number of files, the elegance of the split and the number of prompts used are not assessed.

## What this day does not establish

The day demonstrates three things, all of them countable and all of them local. Two exact counts — source files touched and conventions restated — for one convention change on one component. That a seam drawn correctly can stop being in force with nothing redrawn, shown by opening a subfolder as the workspace root. And that under default settings the nested subtree files are not read at all. **These are counts from one cohort against one component and one model version, and the day claims no rate and no general magnitude for any of them.**

What the day does *not* establish is that the cost model generalises, and point 10 says so at the strength the design can defend: it is unsafe where the seam is a trust boundary, and unsafe where a seam's cost falls on a reader, an operator or an on-call engineer rather than on an editor. Both are deferred to [S073](/archive/bsc-programme/seminars/S073.md) and [S089](/archive/bsc-programme/seminars/S089.md), and neither is in scope today.

What rests on a note: the change-cost framing of architectural boundaries and the immovable-seam category, at [research/05-fde-craft/evans-domain-driven-design.md](/research/05-fde-craft/evans-domain-driven-design.md); the disposition position behind the specification's honesty clause, at [research/04-professional-formation/bandura-self-efficacy.md](/research/04-professional-formation/bandura-self-efficacy.md). Direction and mechanism only.

What rests on nothing verified here: contrasting cases, the pretesting effect and hindsight bias, none of which has a note under [research/](/research/99-source-register/source-register.md) — nor do retrieval practice, spacing, interleaving or cognitive load. And the restated-convention count is this day's own invention: it measures the surface rather than the model, and the documentation publishes no figure for how often a stated convention is honoured.

**The claim to hold.** **The cost of a seam is the cost of the changes that cross it.** Coupling and cohesion are defined by what changes together and not by any diagram, so a decomposition is a bet — and the correct response to a wrong bet is to move the seam rather than defend it.

**What the sources license, and what they do not.** The change-cost framing of architectural boundaries and the immovable-seam category are verified here, at [research/05-fde-craft/evans-domain-driven-design.md](/research/05-fde-craft/evans-domain-driven-design.md); the disposition position governing the specification's honesty clause at [research/04-professional-formation/bandura-self-efficacy.md](/research/04-professional-formation/bandura-self-efficacy.md). Contrasting cases, the pretesting effect and hindsight bias are cited for **direction and mechanism only** with no effect size asserted, and the jagged-frontier mechanism behind item 5 for direction alone.

**Guidance for your own work.**

- **Commit the bet in writing before you implement**, then count what a real change touched. A reconciliation with no count is a narration.
- **Count the conventions you had to restate in a prompt.** Each is a seam your customization surface does not have, and the number is exact rather than argued.
- **Never move a boundary drawn around what may be *done* on change-cost grounds.** Edit counts do not evaluate a trust boundary.
- **A boundary's force comes from where it sits, not from what it says** — the same shape as a gate whose authority is a property of the tier it runs in rather than of the check, on the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md). A correct file somewhere nothing reads is not a seam.

**Where this is easy to get wrong.** Assuming a seam stays where you drew it. The globs were right when written and stopped being in force the day people opened that folder as the workspace root — and the code that followed matched the code around it, so two reviewers approved it.
