# S066 · The Release Gate as an Evaluation Artefact

**Module:** [M14](/archive/bsc-programme/modules/M14.md) · **Quarter:** [Q7](/archive/bsc-programme/quarters/Q7.md) · **Complexity class:** 5
**Strands:** ME · SY
**Whitepaper:** [WP-066](/archive/bsc-programme/whitepapers/WP-066.md)
**Depends on:** S009, S047, S059
**Platform anchor:** Foundry cloud evaluation run as a CI gate — the `microsoft/ai-agent-evals` GitHub Action (preview) and the Foundry evaluator catalogue · **MCP servers:** Foundry MCP Server (preview) · Azure MCP Server · Microsoft Learn MCP Server

---

## What this day is for

Every organisation these students will work in has a release gate. A regression suite, a metric threshold, a review board, a sign-off. It exists so that nobody has to hold the whole uncertainty of a release at once, and it works well enough that it is almost never examined.

[S009](/archive/bsc-programme/seminars/S009.md) established that a test encodes a claim, and that passing is weak evidence while failing is strong. **A gate is a suite of claims consulted at the moment of maximum consequence, and it is read as though passing were strong.**

[S047](/archive/bsc-programme/seminars/S047.md) established that a criterion drifts, that the first mechanism is optimisation against it, and that the remedy is a check the criterion could fail. **A release gate is the criterion in this programme's whole span that is most consulted, most optimised against, and least validated.** The people who must pass it are the people who design changes, and they adapt. That is not cheating and it is not avoidable.

The target: **a release gate is an evaluation artefact. It has a construct, a criterion, a judge, a threshold and an error structure. It has two error rates and only one of them is ever counted. And it is a long-lived evaluation artefact, consulted for years, which is the case the three-set discipline has no version for.**

---

## The gate you will build today, and why it is the argument

This day used to make its case from four supplied records. It now makes it from a gate the student stands up in a pipeline before lunch.

A Foundry cloud evaluation wired into continuous integration — the `microsoft/ai-agent-evals` GitHub Action, which Microsoft labels preview — takes a dataset of test queries and a list of evaluators from the Foundry evaluator catalogue, invokes the agent, scores the responses, and writes a summary report. That is a release gate. It is the release gate a large number of organisations are standing up this year. **And every claim this day makes about gates is a documented property of it:**

- The quality evaluators are LLM-as-judge, and **no agreement-with-human-judgement figure is published for any of them.** The judge has never been characterised. That is not a criticism of the vendor; it is the state of the field, and it is the reason the day's central claim is not rhetorical.
- The general-purpose evaluators return a one-to-five score with a **default pass threshold of three**, and the documentation says a non-binary score is binarised against a default threshold the user *can* override.
- The unit of judgement is a default too: the documentation states that **how you split a conversation determines what you are evaluating**, and the default is the last turn.
- The action's documented inputs are a project endpoint, a deployment name, a data path and one or more agent identifiers. **The documented output is a report.** Nothing in the documented parameter set states a failure condition, and the documentation's own advice is not to run it on every commit.

So the students will build a gate whose judge is uncalibrated, whose threshold nobody chose, whose unit of judgement is a default, and which — on the documentation in front of them — emits a report rather than a refusal. **That is not a defective product. It is what a release gate is, made legible for the first time**, and the day's argument is that this has always been true of the regression suite in the corner too.

## Phase 1 · Pretest and prediction (25 min)

The substrate's current release gate is supplied, with its complete consultation record: every change it has been consulted on, the verdict, and what happened afterwards. Five items, **sealed and opened at phase 8.**

1. **What is this gate measuring?** One sentence.
2. **Name every way this gate can be wrong.** List them.
3. This gate has blocked nothing in fourteen months. **What does that tell you?**
4. Predict: **what fraction of the changes it passed would you now, with hindsight, have blocked?**
5. **Copilot prediction, sealed.** You will shortly ask the agent to build you a release gate: a Foundry evaluation run, wired into a pipeline, that decides whether a change may ship. Write down what it will produce, and **name the one thing it will get wrong.** Sealed with items 1 to 4 and opened at phase 8.

Item 2 is the day's instrument and is taken before any framework is supplied, so that the enumeration is the student's own rather than a restatement of phase 4.

Item 5 is the day's contribution to the running frontier map. The design's expectation is that most students will predict the agent gets an evaluator or a data mapping wrong, and that few will predict what it actually does — which is to produce a correct, runnable, well-structured pipeline **that accepts the default threshold, accepts the default split, and contains no failure condition**, because none of those is an error and all three are decisions.

**Warrant.** Pretesting on an artefact the students already trust, with the record in front of them. Item 3 is constructed so that both available answers are wrong in interesting ways — *the changes were good* and *the gate is broken* are each half of a claim about a gate whose false-block rate has never been measured. Item 2's placement before phase 4 is deliberate and is defended in [WP-066](/archive/bsc-programme/whitepapers/WP-066.md) §8, which concedes that the placement does not protect the assessed version of the same question. Item 5 is sealed at phase 1 and may not migrate into phase 5, per instrumentation rule 8: an instrument administered after its answer has been taught measures recall.

## Phase 3 · Contrasting cases and generation (45 min)

**Three of the four are executed. The fourth cannot be, and why not is part of the finding.**

Groups receive **four release gates over one change on this substrate**, each with its full consultation record: verdicts, the changes that were released, and the incidents that followed.

| Gate | Construction | Run today? |
|---|---|---|
| **G1** | A threshold on an aggregate offline metric. Passes any change that does not move the mean down. | **Executed** — a Foundry evaluation run over the supplied dataset, read at the aggregate pass rate |
| **G2** | A fixed regression suite of named cases, extended whenever a defect escapes and never reduced. Four years old. | **Executed** — the same suite as a `jsonl` dataset evaluation, one row per named case |
| **G3** | A model judge scoring outputs against a written rubric, with a threshold on the score. | **Executed** — LLM-as-judge evaluators from the Foundry catalogue, at their default threshold |
| **G4** | A sign-off by the staff member accountable for the service, with no written criterion at all. | **Demonstrated rather than operated** — it is a person, and it is on record |

Groups rank the four by trustworthiness and commit. **Then they run G1, G2 and G3 against the same change, and then the outcome records are supplied.**

The execution carries its own surprise and it is a surprise about defaults. **G3 is run twice on the same data — once at the platform's default conversation split, and once with the split set to the full conversation — and the two verdicts are compared.** The documentation states plainly that how you split determines what you are evaluating, and the default is the last turn. Where the two runs disagree, the gate's verdict was a property of a setting nobody in the room chose. Where they agree, that is a result about this change and not about the gate, and the day says so.

Groups also read what each run emitted: a score, a threshold, a pass label, a reason, and — across two versions of the agent — a statistical comparison. **None of the three runs emits an error rate**, because an error rate requires knowing what the right answer was.

The record payload is **G4**. The room ranks it last, unanimously and for good reasons — it is unwritten, unauditable, and irreproducible. On the substrate's record it has the lowest rate of passing a change that should have been blocked, and by a wide margin the highest rate of blocking a change that was fine. Neither figure is available for G1, G2 or G3, **because G4 is the only one anybody distrusted enough to measure.**

Task after: **for each gate, state its construct, its judge, and its two error rates — and say which of the two the organisation currently counts.**

**Warrant.** Contrasting cases across gate constructions with a real outcome record as adjudicator, now with three of the four gates operated rather than described. G4 defeats the room's expectation that a written criterion beats a judgement, and it defeats it twice: first on the false-pass rate, and then on the fact that the comparison is only possible for the gate nobody trusted. The G3 split comparison is the executed defeat and is the cheaper of the two: it puts a documented default in front of a room that has just ranked a judge-based gate on the assumption that its verdict was a property of the change. **G4 is not assessed on any element that depends on running it**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s rule for capabilities the programme cannot operate — and here the reason is not a licence but a person, which is itself the phase's second finding. The task-after is the phase's product and is the sentence the day is built to make available.

## Phase 4 · Consolidating instruction (50 min)

1. **A gate is an evaluation.** It has a construct — *is this change safe to release* — and it measures something else. [S026](/archive/bsc-programme/seminars/S026.md)'s construct-instrument gap, [S046](/archive/bsc-programme/seminars/S046.md)'s traceability requirement and [S048](/archive/bsc-programme/seminars/S048.md)'s judge error all apply without modification, and none of them is usually applied.

2. **A gate has two error rates and they have different costs.** A gate that passes a change which should have been blocked. A gate that blocks a change which should have shipped. **Only the first is counted, because only the first produces an incident with a name, a date and a review.** The second produces work that was not done, by people who did not know they were prevented, and it leaves no record anywhere.

3. **Passing is weak evidence.** [S009](/archive/bsc-programme/seminars/S009.md) point 2 at the moment of release. A green gate licenses *no evidence of the harms this gate is sensitive to* and nothing else. It does not license *safe*, and the [S050](/archive/bsc-programme/seminars/S050.md) standard applies to anyone who reports it as though it did.

4. **The gate is optimised against by the people it constrains.** [S047](/archive/bsc-programme/seminars/S047.md) mechanism 1 at organisational scale. Changes are shaped to pass, which is what a gate is for; the consequence is that the gate's discriminating power decays while its pass rate rises, and both movements look like success.

5. **The gate is a long-lived evaluation artefact and the three-set discipline has no version for it.** [S042](/archive/bsc-programme/seminars/S042.md) required an evaluation set consumed once. A release gate is consulted at every release for years, which is unavoidable consumption, and the remedies are different in kind: **rotation** of cases, **a held-back slice never consulted at release**, and **a stated consumption budget** after which the gate is rebuilt. **This is safe as a discipline for an evaluation artefact you own and can rebuild, and it is unsafe wherever the gate is externally imposed — a certification suite, a contractual acceptance test, a regulator's criterion — where consumption is real, the remedies are unavailable, and the correct move is to state what the gate no longer discriminates rather than to fix it.**

6. **Nobody validates the gate.** [S047](/archive/bsc-programme/seminars/S047.md) point 3 requires a check the criterion could fail. Run it on the gate: take changes whose outcome is known and see what the gate says about them. Any gate can be validated this way and almost none is.

7. **A threshold is a decision about which error you prefer.** It is not a technical parameter and it does not belong to the engineer holding the number. Who it does belong to is [S069](/archive/bsc-programme/seminars/S069.md)'s subject.

8. **A gate that has never blocked anything is not evidence of quality.** It is evidence about the gate, and it is the single most common state a release gate is found in.

9. **Defaults are opinions and thresholds are policy.** Five were chosen for you this morning and none of them was announced. **The pass threshold is three** on a one-to-five scale for the general-purpose evaluators, and three on a zero-to-seven severity scale for the safety ones — the documentation states it as a default the user may override, which means somebody decided which error you prefer and it was not you. **The conversation split defaults to the last turn**, which measures the answer to the most recent question rather than whether the task was completed, and the documentation says in its own words that how you split determines what you are evaluating. **The evaluator list changes under you:** the Agent Framework's Foundry evaluator set runs relevance, coherence and task adherence by default and **adds tool-call accuracy automatically when the items carry tool definitions** — a criterion that moves when the input shape moves, with no edit and no record. **The portal's run comparison uses a statistical t-test** whose bands are drawn at p ≤ 0.001 and p ≤ 0.05, and reports *inconclusive* for too few examples or p ≥ 0.05 — those cut points are somebody's choice about which error to prefer, arriving as a colour. And **the documented inputs to the CI action are an endpoint, a deployment, a data path and agent identifiers; nothing in them states a failure condition.** An engineer who cannot state what was chosen for them does not understand their own system, and this generalises far beyond this vendor.

10. **What the gate's judge has never been shown to do.** The quality evaluators are a model scoring another model's output against a rubric. **No agreement-with-human-judgement figure is published for any evaluator in this catalogue.** The documentation is careful and detailed about scales, thresholds, regions, rate limits, token costs and sampling; it states no accuracy anywhere. That asymmetry is consistent across every source behind [research/06-microsoft-platform/](/research/06-microsoft-platform/collected-materials.md) and is a property of vendor documentation as a genre rather than of this vendor. The consequence is exact and is [S029](/archive/bsc-programme/seminars/S029.md)'s: **every judged score in this stack is uncalibrated, and a gate built on one is an instrument that has never been validated.** You may still use it. You may not report it as though somebody had checked it.

11. **What is perishable here and what is not.** The threshold of three will change. The default split will change. The action is on a preview tag, the sample workflow pins a beta version, and the whole capability is one release note away from a different shape. **None of that touches the durable claim**, which is that a gate has a construct, a judge, a threshold and two error rates, and that the threshold is a policy decision wearing a parameter's clothes. **This is safe for reasoning about any gate you are handed — what is it measuring, who set the cut, which error does it prefer. It is unsafe for reasoning about what this particular service will do next term, and it is unsafe as evidence for the durable claim**: the platform is an instance that makes the claim visible, not a proof of it, and a student who cites the vendor as the reason gates go unvalidated has mistaken an example for an argument.

12. **Two instruments in one document, one mechanically checkable and one not, with nothing marking the difference.** *(Added 2026-07-30.)* The engineering playbook this programme's professional strand runs on defines **code as incomplete if it is not accompanied by tests**, and closes the loophole outright: **tests are committed in the same pull request as the code they cover**, and *I will add tests next* is stated as not acceptable. Its author-side guidance closes the matching loophole from the other end — a requested change that is **within the scope of the task may not be deferred to a later pull request**. **Notice what those two rules have in common.** Neither is a statement about diligence. Both are statements about **what may be observed in one artefact at one moment**, and both are decidable by a reader of the pull request who has no access to the author. The template that carries them has the same property: a work-item link, a description, steps to reproduce and validate, a six-item checklist, an explicit breaking-change question, a testing section naming operating system and scenarios, logs, and known dependencies — **nine fields, every one of them answerable from the pull request itself.**

    **Now the contrast, which is the point.** The same document also carries an engineering fundamentals checklist, and **its items are not uniformly falsifiable as written.** Many are: *the default target branch is locked* is a setting somebody can look at. Several are not: *the agile process is clearly defined within the team* has no observable that separates a team satisfying it from a team that does not — and one section of the list slips out of declarative form partway down and begins asking questions rather than asserting conditions, so two items in the same list are doing different grammatical work. **Nothing in the document marks which is which**, and both instruments are written in the same flat voice, by the same organisation, for the same readers.

    **Put both in the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md)'s five classes and the difference becomes exact.** A pull request checklist item is an **executable check** — a check exists, it can run, and non-conformance of the checked shape can be detected. A checklist item written as an aspiration is a **configured control** at best: it establishes that somebody stated the constraint, and nothing about whether it was applied. Reporting the second as though it were the first is an **unsupported inference**, and it is the commonest thing done with a checklist. Each student writes down, before the classes are named aloud, which class each of the two belongs in; **it is not assessed**, and the distribution is reported at phase 8. **The durable claim is that an instrument's grammar tells you what class of conclusion it licenses**, that one document may carry both kinds without saying so, and that this is the release gate's problem one register up — point 2's uncounted error rate is what happens when nobody asks which class a green result belongs to.

**Warrant.** Consolidation indexed to phase 3. Point 2 is the day's retained content and the one that changes behaviour. Point 5 carries the strong-form scope statement for the consumption remedies and supplies the third scope case the [Whitepaper Standard](/archive/bsc-programme/program/05-Whitepaper-Standard.md)'s compliance register records as owed to this day. Point 6 is the method the artefact assesses. **Points 9 and 10 are the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s two required platform points** — the defaults the platform chose, and the documentation silence that makes point 6 non-negotiable — and point 11 carries the perishability boundary to the students rather than leaving it in the whitepaper. **Point 12 was added 2026-07-30 and is placed after the perishability boundary deliberately**, because point 11 is a disclaimer about material that perishes and point 12's material does not — putting it earlier would have required the perishability statement to disclaim two written instruments that will outlast every figure in points 9 to 11. It is short, its two examples come from a document the cohort's professional strand already runs on, and its whole work is done by the classification demand at the end — which is the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md)'s ladder applied to a checklist rather than to a system, immediately before phase 5 asks the students what their own gate's green result licenses.

## Phase 5 · Whole-task learning task (90 min)

**Class 5. This phase produces a build. The gate, its validation and the consumption position are the student's.**

Students choose **one substrate component and one change they are considering releasing**, and keep both for the rest of the module. They then **stand up a real release gate**, using Copilot in agent mode through the Foundry MCP Server and the Azure MCP Server, and run it.

1. **State the release decision this gate exists to support**, and who is accountable for it.
2. **State the gate's construct** — what it is meant to measure — and what it actually measures.
3. **State the gate's two error rates**, and which one your organisation currently counts. Evidence, not assertion.
4. **Design a validation the gate could fail**, in one of [S047](/archive/bsc-programme/seminars/S047.md) point 4's forms, **and state the threshold at which you would call it broken, before you run it.**
5. **Build the gate and run it.** A Foundry evaluation over a dataset you choose, with evaluators you choose, invoked from a pipeline. **Three settings must be decided rather than accepted, and each decision recorded with its reason: the threshold, the conversation split, and the evaluator list.** **The pipeline must additionally be capable of failing** — a step that compares a result to your threshold and stops the job — **so that not blocking is a decision you made rather than a property of the tooling you inherited.** Then **run the validation from step 4** against the substrate's release history.
6. **Retrieve your own [S050](/archive/bsc-programme/seminars/S050.md) category-3 list** — the failures that occurred and that you did not state — and for each, say whether this gate would have caught it, and **what you have changed in how you enumerate failure modes.**
7. **State the consumption position:** how many decisions this gate has already been consulted for, what is held back and never consulted at release, and what your consumption budget is before the gate is rebuilt.
8. **State what your gate does when it is not consulted.** Name the conditions under which it does not run at all — a path filter, a cost decision, a rate limit, a sampled online rule that has hit its hourly cap — and say **how you would know.**

**The artefact carries three further elements**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. Not a transcript. A gate produced in one prompt and a gate produced in eleven are different engineering events.
- **Intervention record.** Every point at which you corrected it, and what the correction was. **An intervention record with no entries fails**, unless the artefact demonstrates that the gate's own design could have detected an intervention-worthy error — a threshold asserted against a stated policy, a check that the split in use is the split that was decided, or a job step that fails when the evaluation returns fewer rows than it was given.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch. Both specific, both from this build.

**Fading:** step 4 is worked with the room, since the validation forms are retrieved from S047 and the release-history harness is supplied. Step 5's pipeline skeleton and credentials are supplied, because authentication is not this day's content. **Steps 3 and 8 are unsupported.**

**Warrant.** Whole-task at class 5, now shipping a gate rather than describing one, on the artefact the student will carry through S070. Step 3 is the discriminator and step 4 is the method. **Step 5's three forced decisions are the point 9 material made assessable**: a student who accepts three defaults has built the gate the day is about, and a student who decides three settings has made three policy choices they can be asked to defend at [S069](/archive/bsc-programme/seminars/S069.md) and [S070](/archive/bsc-programme/seminars/S070.md). **Step 6 discharges the obligation [WP-050](/archive/bsc-programme/whitepapers/WP-050.md) §8 placed on this day**, which named S066 or S070 as the occasion at which a student's category-3 result would be consumed with a requirement that they say what they have changed; the requirement is to have used the result, not to have scored well on it, and step 6 is not assessed for the size of the category-3 list. **Step 8 is new with the build** and is the day's cheapest connection to [S068](/archive/bsc-programme/seminars/S068.md): a gate that is skipped and a gate that passes are indistinguishable to everyone downstream, and the platform supplies a documented instance in which exactly that happens at a rate limit. The intervention record's fail condition is written with the sensitivity escape [S052](/archive/bsc-programme/seminars/S052.md) established and [WP-048](/archive/bsc-programme/whitepapers/WP-048.md) §8 corrected.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate gate that had blocked nothing in eighteen months and was reported in every quarterly review as a control. When it was finally validated against changes whose outcomes were known, it passed most of the ones that had caused incidents. Attention is directed at two facts — **the gate was correctly implemented and did exactly what it was written to do**, and **the eighteen-month clean record was cited as the reason not to examine it.**

Then the agent case: a Copilot-generated evaluation pipeline that was **confidently wrong and passed review**. It authenticated correctly, mapped the dataset fields correctly, selected sensible evaluators, polled the run to completion, printed the aggregate scores, and read as competent work — and **the job succeeded whatever the scores were.** Nothing in it compared a score to a threshold and nothing in it set a non-zero exit. It had been asked for a release gate and it had built a report. Attention goes to why review did not catch it: the reviewer read the pipeline for correctness and it was correct, the run was green and the scores were good, **and a green pipeline that has never failed is indistinguishable from a green pipeline that cannot fail.** That is point 8, in the room, on the students' own morning's work.

Then students, in threes: a check you have relied on whose failure rate you cannot state — **or a place today where you accepted agent output you had not checked.**

**Warrant.** Error management targeting points 6 and 8. The instructor case contains no defect, no negligence and no incorrect implementation, which is what makes it a lesson about validation rather than about care. The second fact is the harder one: the evidence that the gate was fine was the absence of the only signal the gate could produce. **The agent case is the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md)'s required addition** and is chosen so that the failure is invisible to the review the students would actually have performed — and so that it is the same failure as the instructor's case, arriving from a different direction and in the students' own hands.

## Assessment

**One specification item**, in ME301 with SY301. Per [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md) rule 1, the checked elements are: the release decision and its accountable party; the gate's construct and what it actually measures; both error rates with evidence, and which is counted; the validation design with its pre-committed threshold; **the built gate, with its three decided settings — threshold, split and evaluator list — each carrying the reason it was decided that way in the same field, and its failure condition**; the validation result; the category-3 comparison with a statement of what has changed; the consumption position with its held-back slice and budget; **the not-consulted conditions with how the student would know**; **the prompt record**; **the intervention record**; **the frontier statement**; and the phase 7 outcome. **Nothing else is assessed.**

**A gate whose two error rates are not both stated fails.** This is the day's single hard requirement.

**A pipeline with no failure condition fails.** A gate that cannot block is a report, and the day's whole argument is that the two are confused.

**A validation whose stated threshold could not have been reached fails**, per [S047](/archive/bsc-programme/seminars/S047.md)'s standing condition.

**A setting accepted at its default with no stated reason fails that element.** Accepting the default is a legitimate decision and is frequently the right one; accepting it without noticing is the day's subject.

**An intervention record with no entries fails**, unless the artefact demonstrates that the gate's own design could have detected an intervention-worthy error.

**Nothing that depends on operating G4 is assessed.** The fourth gate is demonstrated rather than operated, and no element turns on a result the students did not produce.

**Step 6 is not assessed for the size of the category-3 list**, only for its presence and for the statement of what changed. The decoupling [S050](/archive/bsc-programme/seminars/S050.md) established is preserved deliberately: an assessed category-3 result stops being a measurement of what students fail to anticipate.

No entrustment judgement. The module's is at [S070](/archive/bsc-programme/seminars/S070.md).

**Rule-6 discharge.** [WP-050](/archive/bsc-programme/whitepapers/WP-050.md) §8 conceded that S050's category-3 prediction check had no later occasion consuming it, and proposed carrying it forward to S066 or S070 with a requirement that the student say what they have changed. **The element exists and is a checked artefact element: phase 5 step 6.** The obligation is discharged here and confirmed again at [S070](/archive/bsc-programme/seminars/S070.md) phase 5.

**Instrumentation under rule 6.** Two instruments with named response occasions:

- **The item 2 and step 3 error-rate results** measure whether the cohort can see the false-block error at all — unprompted at item 2, and applied to their own organisation at step 3. **Response occasion: [S069](/archive/bsc-programme/seminars/S069.md), phase 3, whose four governance arrangements are selected against whichever of the two errors the cohort proved blind to, and whose task-after requires the cost-bearer of each to be named.**
- **The step 6 category-3 recatch rate** — how many of each student's previously unstated failures the gate they designed would now catch. **Response occasion: [S070](/archive/bsc-programme/seminars/S070.md), phase 5, where the cohort rate is reported and each student states what they changed in the decision artefact.**

**A third instrument, under rule 9.** The **item 5 sealed prediction accuracy and the step 5 default-decision rates** are this module's contribution to the running frontier map. Per instrumentation rule 9 the reader is named: **the following year's cohort, through the [Durable and Perishable Register](/archive/bsc-programme/program/09-Durable-and-Perishable-Register.md)**, which carries the re-verification of every platform default named at point 9 before each offering. Per instrumentation rule 3 the sampling is disclosed to the students in the same terms the day would demand of them: one cohort, one substrate, one Foundry project, one model family, on a task staff selected because a known failure was available in it. **A frontier map assembled from these describes this day's task and not the agent.**

## What to take from this day

**The claim to hold.** **A release gate is an evaluation artefact** with a construct, a judge, a threshold and an error structure. It has two error rates and only one is ever counted, because a wrong pass produces an incident with a name and a date, and a wrong block leaves no record at all. **A threshold is a decision about which of the two you prefer.**

**What the sources license, and what they do not.** The criterion-drift and judge-as-instrument material is grounded in [research/03-measurement-evaluation/shankar-evalgen.md](/research/03-measurement-evaluation/shankar-evalgen.md) and [research/03-measurement-evaluation/singh-leaderboard-illusion.md](/research/03-measurement-evaluation/singh-leaderboard-illusion.md), cited for **direction and mechanism only**: a shared criterion decays once a field optimises against it, and a judge carries a systematic error component. **No magnitude is asserted from either.** Point 12's two instruments are quoted from [research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), which records both from a reading of every page — and **that source offers no comparative evidence for any practice it prescribes**, so nothing on this day claims that a same-pull-request test rule produces better code, only that it is checkable and that the item beside it is not. For the catalogue you ran this morning, nothing is published about how it compares with human raters.

**Guidance for your own work.**

- **State both error rates or you have not described the gate.** Evidence, not assertion.
- **Design a validation the gate could fail**, and commit its threshold before you run it.
- **Decide the threshold, the split and the evaluator list**, recording a reason for each. Accepting a default is often right; accepting it without noticing is the day's subject.
- **A check's authority is a property of the tier it runs in rather than of the check**, per the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md). Only the step that compares a result to your threshold makes an evaluation a gate.
- **Read a checklist item for its grammar before you rely on it.** An item answerable from the artefact in front of you is an executable check; an item that describes a state of affairs with no observable is a configured control, and reporting it as a result is unsupported inference. One document will carry both and will not tell you which you are holding.

**Where this is easy to get wrong.** Reading a clean record as evidence of quality. **A green pipeline that has never failed is indistinguishable from one that cannot fail.**
