# S009 · Testing as Hypothesis, Not Ritual

## What this day is for

Students write tests to demonstrate that their code works. That is the wrong activity, and it is wrong in a way that is invisible from inside, because a test suite full of passing tests looks exactly like a test suite that has established something.

A test that cannot fail carries no information. A test suite constructed to pass is a document about the author's expectations, not about the program. The day's target is the inversion: **a test is an attempt to falsify a stated claim, and a claim you cannot state is a claim you cannot test.**

This is the first day where the measurement strand's logic appears, seventeen days before ME101 begins. It is deliberately placed in a programming course, because a student who learns falsification as a statistics topic learns it as a statistics topic.

It is also where the module's second register is closed. S006 said an instructions file is a specification. S007 decomposed it. **This day says that an instructions file which has never produced non-conforming work has never been tested**, and that the way to test one is to write the prompt most likely to defeat it. A specification nobody has attacked is [S029](/archive/bsc-programme/seminars/S029.md)'s unvalidated instrument, arriving twenty days early and cheap enough to fix.

## Phase 1 · Pretest and prediction (25 min)

Students receive a program and a test suite of twelve tests. All pass.

1. What does this suite establish about the program?
2. What does it not establish that you might reasonably have assumed it did?
3. Write one test that would fail.
4. Predict: does the room think this suite is good?
5. **Sealed Copilot prediction.** Later today you will ask an agent to review an instructions file and tell you what is wrong with it. Write down now, and seal it: **what class of defect will it find, and what class will it miss?**

Item 3 is achievable — the program has a defect — and most students do not find it, because they look for a test to add rather than a claim to attack. Item 5 is opened at phase 8; the design expects the room to predict wording defects and to miss the whole class of defects that are invisible in the text.

**Warrant.** Pretesting with generation. Item 1's answers are almost universally overstated, and the overstatement is the day's subject rendered as the students' own words. Item 5 is administered before phase 4 and stays there, per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

Groups receive **four test suites for the same program**. All four pass. All four have similar size.

- **Suite A** exercises many inputs, all from the same region of the input space.
- **Suite B** exercises few inputs, each chosen to attack a different stated claim.
- **Suite C** has high line coverage and tests no boundary.
- **Suite D** tests boundaries thoroughly and never tests the property the program exists to provide.

Then: **the program is modified** — one small change, introducing one defect. Which suites catch it?

Groups predict before being told. Then a second defect is introduced, caught by a different subset.

Task after both: **state what each suite is a hypothesis about.**

**Then the same structure is executed on a specification.** Groups receive one working `*.instructions.md` file and four prompt sets, each of which currently produces conforming output. Every set is run.

| Set | Construction | Hypothesis it encodes |
|---|---|---|
| A | Many prompts, all asking for the same kind of work | The file holds for the work we normally do |
| B | Four prompts, each attacking a different clause | Each clause is individually in force |
| C | Prompts that between them mention every clause in the file, none at a boundary | The file has been "covered" |
| D | Prompts at every boundary the file names, none that asks for the thing the file exists to prevent | The edges are handled |

Then **the file is modified**: one clause's qualification is separated from the quantity it qualifies — specification rule 2, broken deliberately. Groups predict which sets catch it, then run.

Then a **second** modification: the `applyTo` glob is narrowed by one character so that it no longer matches the files under test. Groups predict again.

**The second defect is the payload and no prompt set catches it.** Output degrades, none of the four sets is designed to notice, and every explanation the room reaches for is about the model. The evidence is in the chat **References** list, which stops naming the file. **A defect in your specification can be invisible to every test of its output**, which is the day's asymmetry arriving in a form students did not expect: failing is strong evidence, and here nothing failed.

Finally, groups run the preview customization-analysis extension over the defective file and compare. It reports on wording. It does not report that the file is out of scope.

**Warrant.** Contrasting cases with a delayed adjudicator, reusing S007's mechanism deliberately so that the structure is familiar and the content is not. Two defects rather than one, because a single defect lets a group conclude one suite is simply best. The executed half supplies a third defect class — one that is undetectable from output alone — which no arrangement of the four written suites could have produced.

## Phase 4 · Consolidating instruction (50 min)

1. **A test encodes a claim.** If you cannot say what claim, the test is checking that the program does what it does.
2. **Passing is weak evidence; failing is strong evidence.** The asymmetry is the whole of it, and it is S004's counterexample point in a new setting.
3. **Where claims come from:** the invariants of S006, the seams of S007, the inductive arguments of S008, and the caller's expectations. Every prior day in the module is a claim source.
4. **Coverage measures what was executed, not what was checked.** Suite C. A metric that can be maximised without establishing anything is a metric that will be.
5. **Choosing inputs to falsify**: boundaries, the input the author did not consider, the input that violates an unstated precondition, and the input from the actual usage distribution.
6. **What a passing suite licenses you to say** — and the sentence you are not entitled to say. This is the day's connection to S050, stated once.
7. **The regression test is a different object**: it encodes a claim about a defect that occurred, and its value is historical rather than evidential.
8. **A specification is tested the same way, and by the same asymmetry.** A prompt is a test of an instructions file. Conforming output is weak evidence; non-conforming output is strong. **An instructions file that has never produced non-conforming work has never been tested**, and a repository full of instructions files nobody has attacked is a suite of passing tests written by the author of the code.
9. **Three things that are not tests of your specification.** Reading it is not; it reads correctly, which is why it shipped. Running the analyzer over it is not; it inspects text and the second phase 3 defect was not in the text. And *the output looked right* is not, because that is item 1 of this morning's pretest in a new costume.
10. **A default the platform chose for you, and a silence.** Perishable, marked, verified against the Visual Studio Code agent-customization documentation as it stood on 15 July 2026. The customization-analysis extension is **preview**, is published separately from the editor, and detects a fixed taxonomy somebody chose: logical, behavioural and format contradictions; ambiguous wording; conflicting persona traits; excessive cognitive load from nested conditions; gaps in intent handling and missing error paths; and conflicts between a file and files it links to. That list is a hypothesis about where specification defects live, and it is a good one. **No precision, recall or false-positive rate is published for it.** That is the same silence [research/06-microsoft-platform/](/research/06-microsoft-platform/collected-materials.md) records across every source in the platform folder: bounds and cadences are published, accuracies are not. Until one is published, the analyzer's output is a prompt to look, never a result.
11. **Scope of the asymmetry, at the strength this day can defend.** *Passing is weak, failing is strong* is safe wherever the thing under test is a claim you stated and an outcome you can observe — a program's behaviour, a specification's output, a retrieval's contents. It is unsafe in one condition that arrives immediately: where the observation itself is produced by the system under test. An agent asked to review its own output supplies both the claim and the evidence, and the asymmetry does not hold, because a failure it does not report is indistinguishable from a failure that did not occur. That is [S048](/archive/bsc-programme/seminars/S048.md)'s subject and it is not resolved here. **A student whose phase 5 attack consists of asking the agent whether its own output conformed fails the specification**, which is the checkable form of this boundary.

**Warrant.** Consolidation indexed to phase 3's four suites. Point 4 is given weight because coverage is the ritual the day is displacing and it has institutional force behind it. Points 8 to 10 consolidate the executed half, and point 9 exists because the analyzer is the exact object students will mistake for a test. Point 11 is the strong-form scope statement and carries a fail condition.

## Phase 5 · Whole-task learning task (90 min)

Students take their **own S007 decomposition** — their own prior work, deliberately — and:

1. **State three claims** it makes. Not tests: claims, in prose. **At least one must be a claim made by the customization surface** rather than by the code — a convention the instructions files are supposed to enforce.
2. **For each, design the test most likely to falsify it.** Most likely, not merely capable. For the customization claim, the test is a prompt — **and it is written as a `.github/prompts/<name>.prompt.md` file with a review date**, so that it can be re-run by name, by somebody who is not you, after the file it attacks has been changed. An attack you cannot re-run is a test you ran once.
3. **Predict which will fail.** Commit in writing.
4. **Run them.** For the prompt, record the References list alongside the output, because a claim that failed for want of scope and a claim that failed on its merits are different findings with different repairs.
5. **For any that passed, state what you are still not entitled to conclude.**
6. **For any that failed, decide**: is the claim wrong, or the code? Both are legitimate answers and they have different consequences. For the customization claim there is a third answer — the file was not in force — and it is the one students will not reach for.

Step 6 is the day's hardest step and the first time in the programme a student is asked to consider that their specification, rather than their implementation, is the thing at fault.

The build is steps 4 and 6: a repository whose claims have been attacked and whose specification has been repaired where the attack landed.

**The artefact carries three additional elements**, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md).

- **Prompt record.** What you asked for, in order, including the attacks you designed and abandoned as too weak. On this day the abandoned attacks are the interesting part, because an attack discarded for being too easy is a judgement about claim strength.
- **Intervention record.** Every point at which you corrected the agent and what the correction was. **No entries fails**, unless the artefact shows an attack that would have detected a violation had one occurred — which for this day is exactly step 2 done properly.
- **Frontier statement.** One thing the agent did faster than you could have, one thing it did badly that you caught, both specific to this build.

**Faded guidance:** claim 1 is worked with the room; claim 2 supplies a falsification strategy; claim 3 is independent.

**Warrant.** Whole-task at class 1 on the student's own prior artefact, which supplies motivation and continuity at no load cost. Steps 3 and 5 are the S007 commit-then-reconcile structure on its second application. Step 6's third answer is the executed half's residue and is the sentence the module has been building toward since S006.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate defect that reached users **through a test suite with high coverage**, with attention to what the suite was a hypothesis about and what it was not.

Instructor second, an agent case: a change where the agent was asked to check its own work against the repository conventions and reported that all of them were satisfied. Three were, one was not, and the one that was not is the one the file's wording made unfalsifiable — it asked for output that was *clear*. **The reviewer read the agent's conformance summary instead of the diff and approved it**, and the clinic's attention is on that substitution: a confident summary from the thing under test displaced the evidence, and the reviewer's own judgement was never applied. This is phase 4 point 11 with a person in it.

Then students: a test you wrote that could not have failed.

Classified by the phase 4 point 5 input categories.

**Warrant.** Error management. The high-coverage disclosure is chosen specifically to disarm the institutional authority of the metric, which no amount of argument in phase 4 will fully accomplish. The agent case is chosen because the reviewer's error is the one every member of the room has the means to make by next week.

---

## Phase 7 · Peer articulation (30 min)

Pairs. Each student hands over their step 1 claims and their partner's task is to **write the test they would have written** — then compare against the student's own.

Where the two differ, the pair must decide which test is the better attack on the claim, and why.

**Warrant.** Interactive-tier articulation with an independent-construction comparison. Divergence is the phase's product: two competent attacks on the same claim differ, which establishes that test design is a design activity rather than a derivation.

---

## Phase 8 · Calibration and commitment (20 min)

- Items 1 and 4 resolved. The room's phase 1 claims about the suite are read back, unattributed, alongside what the suite actually established.
- **Item 5 unsealed.** Predictions scored on the second half only: did the student name a defect class the review would miss. The rate goes into the frontier map, labelled as one cohort, one file, one model version.
- Step 3 prediction accuracy shown as a distribution.
- Each student names one claim in their own current work they have never tested and will attack before S010.
- Retrieval schedule: next morning, day 3, week 2, week 6, and the module cumulative set at S010.

## When it goes wrong

The predicted failures and their countermeasures are argued in [WP-009](/archive/bsc-programme/whitepapers/WP-009.md) §5. Restated here as instruction to the person in the room. Nothing below is assessed.

| What you see | What to do | What the design accepts |
|---|---|---|
| A student with professional testing experience performs steps 1 to 4 competently and skips step 5 | **Check step 5 first — it is the most heavily weighted element on this day.** Professional testing culture has no equivalent of *what you are still not entitled to conclude*, which is exactly why their experience does not cover it. Brief their phase 7 partner to press on claim strength rather than on test technique | The predicted failure is competence at everything the day is not about |
| A student whose testing experience is minimal cannot design a test at all, and their step 1 claims are too vague to attack | Run the fading across the three claims, supply the falsification strategy for claim 2, and remind them the object under test is their own two-day-old code. The worked claim 1 is what establishes the required specificity | They have an advantage in habit — no confirmatory practice to unlearn — and a disadvantage in fluency |
| A group predicts the first defect's catchers correctly | The second defect is chosen to be caught by a different subset and reliably breaks the pattern they have just formed. If they predict both, ask them to construct a third defect that suite B misses | Hard, and it establishes that even a claim-directed suite is a bounded hypothesis |
| Defensiveness from students whose testing practice is being devalued | Locate the failure in the practice's structure rather than in the practitioner, and let phase 6's industry-standard case carry the rest | The first of the day's two affective failures, and the visible one |
| **Nihilism: if passing establishes so little, why test at all** | This is the more insidious failure, because the conclusion is superficially consistent with the day's own argument. Use point 2 in the other direction — failing is *strong* evidence, so a well-designed suite that passes has survived genuine attacks and that is worth a great deal. The specification clause requiring an explanation when nothing failed exists partly for this, and it forces the student to say why survival was informative | The same fatalism risk as S007's, and §5 records it as more dangerous here |
| The room does not notice the second executed defect and concludes the model got worse | Say nothing, and wait. No group is told which defect was introduced. **A room that concludes the model got worse has produced the day's finding in its most useful form**, and it should be allowed to hold that conclusion for several minutes before the References list is opened | The payload depends on the room reading a list it has been told about twice, on a day whose subject is that people look in the wrong place |

## Assessment

Specification item in CF101.

The following elements are checked, each as a binary decision:

1. Three prose claims, at least one made by the customization surface rather than by the code.
2. Three falsification-directed tests, each with the design rationale for why it is the *most likely* attack. **The attack on the customization claim is a prompt file with a review date**, runnable by name.
3. The committed prediction.
4. The results, with the References list recorded alongside any prompt-based test.
5. The not-entitled-to-conclude statement for every claim that survived. **A suite in which nothing failed and no explanation is offered fails.**
6. The claim-or-code-or-scope decision for every claim that did not survive.
7. **The prompt record,** including the attacks abandoned as too weak.
8. **The intervention record.** No entries fails unless element 2 shows an attack that would have detected a violation.
9. **The frontier statement,** both halves, specific to this build.

One fail condition is separate from the list and follows phase 4 point 11: **an attack that consists of asking the agent whether its own output conformed fails**, whatever it returned.

**Nothing else is assessed.** The number of tests, the number of prompts and the analyzer's output are not assessed.

## What this day does not establish

The day demonstrates two things and both are observations from one file on one afternoon. That a defect in a specification's *scope* is invisible in the output and visible only in the References list, so that four prompt sets constructed on four different hypotheses all miss it. And that the analysis extension reports on wording and does not report that the file is out of scope. **Neither demonstration is a rate, and the second cannot become one: no precision, recall or false-positive figure is published for that extension anywhere, so nothing about its detection ability is established here or elsewhere.**

What the day explicitly declines to establish is that the asymmetry holds everywhere. Point 11 states the condition under which it does not — where the observation is produced by the system under test, a failure the system does not report is indistinguishable from a failure that did not occur — and defers it to [S048](/archive/bsc-programme/seminars/S048.md) rather than resolving it. The specification carries the fail condition that follows.

What rests on a note: the evidential asymmetry, construct validity and the entitlement-of-conclusion position, at [research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md) and [research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md](/research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md). Direction and mechanism only.

What rests on nothing verified here: confirmation bias, and the tendency of measurable proxies to be optimised at the construct's expense — neither has a note under [research/](/research/99-source-register/source-register.md) — and the phase warrants generally, since no note exists for retrieval practice, spacing, interleaving, pretesting or cognitive load. The coverage critique at point 4 is argued from the phase 3 suites and from the instructor's own disclosure, and is traced to no source in this repository.

## What to take from this day

**The claim to hold.** **A test is an attempt to falsify a stated claim, and a claim you cannot state is a claim you cannot test.** Passing is weak evidence; failing is strong. The same asymmetry governs a specification, so **an instructions file that has never produced non-conforming work has never been tested.**

**What the sources license, and what they do not.** The evidential asymmetry, construct validity and entitlement-of-conclusion positions are verified here, at [research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md](/research/03-measurement-evaluation/miller-adding-error-bars-to-evals.md) and [research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md](/research/03-measurement-evaluation/husain-your-ai-product-needs-evals.md). Confirmation bias and the tendency of measurable proxies to be optimised at the construct's expense are cited for **direction and mechanism only**, with no effect size asserted. The analysis extension publishes **no precision, recall or false-positive rate** — the silence recorded across the whole platform folder at [research/06-microsoft-platform/](/research/06-microsoft-platform/collected-materials.md) — and this day supplies no figure of its own either.

**Guidance for your own work.**

- **State the claim each test encodes.** If you cannot, the test is checking that the program does what it does.
- **Record the delivery evidence beside the result.** A claim that failed for want of scope and one that failed on its merits need different repairs.
- **Never let the system under test supply both the claim and the evidence.** A failure it does not report is indistinguishable from a failure that did not occur.
- **A grader tests the shape it was written to test.** That is the executable-check row of the five classes on the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md): an analyzer that inspects text cannot find a defect that is not in the text, so its output is a prompt to look rather than a result.

**Where this is easy to get wrong.** Reading the conformance summary instead of the diff. It was accurate about the thing it had read, it was confident, and it displaced the only judgement that would have caught anything.
