## What this day is for

**This is the security strand's first seminar day**, and the [Outcomes and Accreditation Map](/archive/bsc-programme/program/01-Outcomes-and-Accreditation-Map.md) records the honest concession that arriving in week forty-four is late. Nothing on this page repairs that. What the day can do is give the strand's first session something with a floor under it: **four published checks, run by hand against the template that will deploy the student's own model the day after tomorrow.**

A learned component has an attack surface the rest of the system does not. Its behaviour depends on data somebody supplied, its decisions can be probed, its outputs may reveal what it was trained on, and its performance can be degraded by inputs that look ordinary. None of these is a code defect and none is found by reading the implementation.

The target: **name an actor, state their access and their goal, and decide which threats you are handling and which you are accepting.** A threat with no actor is a worry, not a threat, and the day's specification says so.

**Contingency:** if the [S043](/archive/bsc-programme/seminars/S043.md) setting D identification rate was low, phase 2's bridge is replaced by a direct re-probe and the phase 5 threat model is scoped to include the evaluation pipeline as an attack surface. This is the branch required by the [Seminar Day Design Pattern](/archive/bsc-programme/program/04-Seminar-Day-Design-Pattern.md)'s instrumentation rule 4.

## Phase 1 · Pretest and prediction (25 min)

Five items on the module's model, which is about to be deployed.

1. List everything that could go wrong with this component.
2. For each, who would have to do what?
3. Which items on your list have no actor?
4. Predict: what fraction of your list survives item 3?
5. **Copilot prediction, sealed.** You will shortly ask the agent to *write me the deployment template for this model.* Write down what it will produce, and **name the one thing it will get wrong**. Sealed with items 1 to 4 and opened at phase 8.

Item 3 is the day's move and typically removes more than half.

Item 5's prompt says nothing about security, which is how such prompts are written. The design's expectation is that a majority predict the agent will produce a working template, and that a minority predict the specific thing: **it will produce a template that works, is publicly reachable, and authenticates with a key** — because that is the fastest path to a working deployment and the agent was asked for a working deployment.

**Warrant.** Pretesting with a self-filtering demand. The list-then-filter construction produces the actor requirement as the student's own finding rather than as a rule. Item 5 is administered here and does not migrate, per instrumentation rule 8.

## Phase 3 · Contrasting cases and generation (45 min)

**Executed, not read.** Groups receive **four actors** and, in front of them, the actual deployment template that will deploy their model at S045.

| Case | Actor |
|---|---|
| A | An ordinary user, no special access, wants a better outcome for themselves |
| B | A competitor with query access, wants to reconstruct the model's behaviour |
| C | A data contributor, upstream, wants the model to behave differently for a class of inputs |
| D | An insider with pipeline access, wants nothing in particular and is careless |

For each, groups state what they can do, what it costs them, and what it costs the system. Then they commit a ranking by expected harm.

### The adjudication is run, not supplied

Groups then apply **four published checks** to the template, by hand, one at a time. These are Defender for Cloud's current infrastructure-as-code AI security checks, and they are stated verbatim because the wording is the specification:

1. **Use Azure AI Service Private Endpoints.**
2. **Restrict Azure AI Service Endpoints.**
3. **Use Managed Identity for Azure AI Service Accounts.**
4. **Use identity-based authentication for Azure AI Service Accounts.**

Each check is a yes or a no about a template the group can read, and every group gets an answer in ten minutes.

**The template fails.** Not because anyone was careless — because the fastest path to a working model deployment is public, with platform-managed storage, and the basic setup **does not support private network isolation at all**; that capability begins at the standard setup, which requires you to bring your own storage, search and database resources. Nobody chose an exposed posture. **Somebody chose a working deployment, and the exposure came attached.**

Then the room is told one further thing about the same template, and it is the phase's payload: **outbound networking cannot be changed later.** The documentation states that you cannot update outbound networking settings on an existing deployment, cannot re-delegate a subnet, and cannot add outbound virtual network injection to a resource that does not have it. **To acquire it you redeploy.** So the check that failed is not a finding to be fixed next sprint. It is a decision that was made at creation time, by whoever typed the first prompt, and it is now load-bearing.

Task after: **re-rank the four actors, and say what changed.** Actor A's feasibility moved.

### Demonstrated rather than operated

Defender for Cloud's own reporting of these checks — the AI bill of materials, the continuous discovery across Azure OpenAI, Foundry, Machine Learning, Amazon Bedrock and Google Vertex AI, and the attack path analysis that composes individually tolerable weaknesses into a route — is **shown and not run**. It requires the Defender CSPM plan and a repository connector with tenant-administration rights the programme does not hold. **The specification does not assess it.**

One screen is shown from it, because it makes a point nothing else can: attack path analysis names **grounding and fine-tuning as the moments data can be exposed** — the two operations in which a model touches proprietary data by design rather than by attack. Yesterday's day was about fine-tuning. Nobody mentioned the data leaving.

**Warrant.** Contrasting cases across actors with a real, executed adjudicator. Actor D remains the payload for expected harm; the template's failure is the phase's second and newer payload, and it defeats expectation in the direction that matters — students expect a security exercise to find carelessness and it finds a default. The four checks are operable by hand, which is why they are assessed; the product that automates them is not, which is why it is not. That division is stated to students in exactly those terms, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md).

## Phase 4 · Consolidating instruction (50 min)

1. **A threat is an actor with access and a goal.** Anything else is a hazard, which is a different thing and is handled differently.
2. **What is different about a learned component:** its behaviour depends on supplied data, it can be probed, its outputs may leak its training data, and its failures can be induced by ordinary-looking inputs.
3. **Four attack families,** mapped to phase 3's actors: evasion at inference, extraction by querying, poisoning upstream, and degradation by distribution manipulation. **This list omits attacks on the surrounding infrastructure rather than on the model, which are SG201's material and are the more common cause of real incidents; and it omits attacks specific to generative components, which arrive at S076. Safe as a starting taxonomy for a supervised component you own; unsafe as a security review of a deployed system, which must cover the infrastructure this list excludes.**
4. **Access determines feasibility,** and access is usually wider than assumed — phase 3's reveal, which today was not a supplied document but the group's own template.
5. **The careless insider,** actor D. Expected harm is probability times damage, and a high-probability low-intent actor frequently exceeds a low-probability high-intent one.
6. **Deciding what to accept,** per S033: name the threats you are not handling, with their probability and consequence. Same discipline, adversarial setting.

   **And adversarial probability is not a failure rate.** An adversary chooses whether to act, and the choice depends on your defence, so the number is conditional on decisions you are in the middle of making. The estimable quantities are **the value of the target and the cost of the attack**, and probability is downstream of both. Where a student cannot estimate a frequency, they estimate those two and say so; a threat that is expensive to mount against a target of low value is deprioritised on that reasoning, which is defensible, rather than on a number, which is not. *(This point was added after [WP-044](/archive/bsc-programme/whitepapers/WP-044.md) §8 recorded that the day asked for a number it had not equipped students to reason about.)*
7. **What a threat model is for:** it is a decision record, not a document. Its output is a list of things you are doing and a list of things you are accepting.

   **And a first threat model mostly produces the second list.** *(Added 2026-07-30, on a reading of the engineering playbook in full.)* The playbook's own worked threat model — a real embedded system, with an architecture diagram, an asset table, a data-flow narrative and an enumerated threat list — marks **every threat in it as not mitigated**, and states its assumptions separately from its threats. That is not a defect in the example and it is not an unfinished document. **It is what the genre produces at the moment it is first written**, because a threat model is written to decide what to do and the deciding has not happened yet. A model whose mitigation column is full on the first pass was either written after the work or written to look complete, and the second is far more common. **You are not marked down for an honest empty column. You are marked down for an empty accept list**, which is the same discipline stated from the other side: not handling something is a decision you record, and pretending to have handled it is not.
8. **The four checks, and what four checks are.** The four run at phase 3 are a floor and are named as one. Three of them are about the same two ideas — **stop being reachable from everywhere, and stop authenticating with a secret that can be copied** — which is why they recur at the gateway in SY202 and at retrieval in SG301. A minimum baseline is not a security review, and this day does not pretend the four constitute one. What they are is **a floor a student can stand on**, checkable in ten minutes, on the template that will actually deploy their model.
9. **Defaults are opinions and thresholds are policy.** Four were chosen for you and all four are security decisions. **The basic setup does not support private network isolation** — not as a setting left off, but as a capability that begins at the standard setup, which requires you to supply your own storage, search and database resources. **Outbound networking cannot be added later**; the resource is redeployed. Model responses pass through a **default guardrail configuration unless a different one is specified**, so a content policy is in force that nobody in the room selected. And keyless authentication with a managed identity is the documented recommendation while key-based authentication remains available — which means **the recommended option and the default option are not the same option**, and the gap between them is where check 4 lives.
10. **Why this instance is perishable, with a date.** The check names will change. The plan boundaries will change. One of them has already announced its change: **from 1 July 2026, AI agent discovery and security posture for Foundry agents require a Microsoft Agent 365 licence**, and Defender CSPM continues to discover accounts and projects but not agents. That is a capability moving out from under this course's anchor on a date the vendor published, and it is shown to students as an instance of what perishable means rather than hidden as an inconvenience. **The durable claim is that governance tooling has a licensing boundary and that the boundary moves.** The dates are the instance.

11. **Inference laundering: how a guess becomes evidence.** *Added 2026-07-30, on a reading of a second internal corpus. Taught and warranted, never assessed — the specification is unchanged.* A customer-embedded engineering organisation within a large technology vendor built a chained agent pipeline that produces a security plan for a system, recorded in [research/05-fde-craft/microsoft-agentic-threat-modelling.md](/research/05-fde-craft/microsoft-agentic-threat-modelling.md). **One path through it is worth tracing end to end, because every step is defensible and the destination is not.**

    **One.** A stage builds a table of security attributes per dataflow — transport, data classification, authentication, authorisation, purpose — and where the architecture documents do not state a value, it is instructed to **infer** one from best practice. Sensible: an empty table is useless.

    **Two.** It is **forbidden to mark the inference inside the cell.** The stated reason is good — a hedge inside a table cell destroys machine consumption downstream — so uncertainty is relocated to a separate justification section pairing each inference with the principle that supports it. That relocation is the better design.

    **Three.** Where the diagram and the surrounding context disagree, the stage resolves **in the more secure direction.** Defensible in isolation, and it biases every unresolved conflict the same way.

    **Four.** The assembly stage, which splices that table into the delivered plan, is instructed to **exclude the justification section.** The provenance does not survive into the document anybody reads.

    **Five.** A later scoring stage assesses authentication, authorisation and transport encryption **by counting non-empty cells in that table.**

    **The pipeline fills in the answers and then grades itself on them.** A plan can score well on encryption because an earlier stage assumed encryption. Nobody was careless, no step is wrong on its own, and **the property is structural rather than accidental** — which is why it is here and not in phase 6. It is also this programme's own [S026](/archive/bsc-programme/seminars/S026.md) apparatus arriving inside a security artefact: the construct is *is this flow encrypted*, the instrument is *is this cell non-empty*, and the two were joined by a stage that was told to guess and forbidden to say so.

    **The room is asked for the smallest change that fixes it, and is not marked on the answer.** The candidates are not equivalent — carry the marker into the cell and accept the machine-consumption cost; keep the justification section in the delivered plan; forbid the scorer from crediting a cell whose value was inferred; or stop inferring and accept an incomplete table. They differ in what they cost, in **which stage bears the cost**, and in whether the pipeline still runs at all. **The point of asking is that the smallest correct fix is usually one stage away from where the damage appears**, and a room that proposes fixing the scorer has located the symptom.

    **What this establishes and what it does not.** It establishes that the path exists in one real system, described by somebody who read all fourteen of its agent definitions. **It establishes nothing about how often such a path exists anywhere else**, and the corpus reports **no outcome for the pipeline at all** — no comparison against a human-authored threat model, no defect-escape figure, no coverage measurement. **No figure from it is reproduced here or anywhere in this wiki.**

**Warrant.** Consolidation indexed to phase 3. Point 3 carries the strong-form scope statement, which is unusually important given that this is the strand's first day. Point 6 imports S033's discipline and now carries the correction WP-044 §8 identified. Points 8, 9 and 10 are the day's platform content, defaults and perishability, per the [Copilot Practice Standard](/archive/bsc-programme/program/12-Copilot-Practice-Standard.md). **Point 11 is a specimen and is not platform content**, which is why it follows the platform layer rather than sitting inside it. It is walked as a five-step trace because the room's instinct on a security day is to hunt for the careless step and there is not one — the finding only becomes visible when the whole path is laid out at once, which is the same construction phase 3 uses on the template. **It is deliberately unassessable and adds no checked element**: the corpus behind it is internal, nothing in it may be linked, and it reports no outcome, so nothing a student says about it could be marked. The *smallest change* question is asked and explicitly not marked, because its value is that the four candidate answers are all defensible and a student who is being graded will pick the one they think is wanted.

## Phase 5 · Whole-task learning task (90 min)

**Class 3. The threat model is the student's, and this phase produces a build.**

Students take their own model, now trained and evaluated, and work through Copilot in agent mode against the Azure MCP Server. They:

1. **State the deployment context:** who can reach it, with what access, through what interface. **Include the infrastructure access paths** — credentials, transport, storage, dependencies — and state which SG201 material you used to identify them.

   *(The infrastructure clause was added after [WP-044](/archive/bsc-programme/whitepapers/WP-044.md) §8 recorded that this day violated the cross-course deferral rule introduced three days earlier: it defers infrastructure security to SG201, that omission is where most real incidents originate, and no artefact element joined it back.)*
2. **Enumerate actors,** each with access and a goal. Include a careless one.
3. **For each, state the attack** they could mount and what it would cost them.
4. **Estimate probability and consequence,** with provenance per the [Assessment Architecture](/archive/bsc-programme/program/03-Assessment-Architecture.md)'s rule 2 — confidence in the same field. Where a frequency is not estimable, give the target's value and the attack's cost instead, per point 6.
5. **Decide what you are handling** and what you are accepting.
6. **State the detection signal** for one accepted threat.
7. **State what would change your acceptance decision.**
8. **Run the four checks against your own S045 deployment template, and remediate or accept each.** For each check: pass, or remediated with the change shown, or accepted with a reason and the actor it exposes you to. **An accepted failure is a pass. An unexamined one is not.**

Step 8 is the day's build and it is deliberately small. It produces a template a student can deploy on Friday and a four-line record of what they decided about their own exposure. Some students will find that remediating check 1 is not available to them at all on the setup they have, which is the correct finding and is recorded as an acceptance with a named reason.

**The artefact carries three further elements**, per the Copilot Practice Standard.

- **Prompt record.** The instructions you gave the agent, in order, including the ones you abandoned. On this day, compare your first template prompt against your sealed item 5.
- **Intervention record.** Every point at which you corrected it. **An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error — a check in the deployment pipeline that refuses a template failing any of the four is the obvious example and is accepted.
- **Frontier statement.** One thing the agent did faster than you could have, and one thing it did badly that you had to catch.

**Fading:** step 2 is worked with the room; step 4's estimation form is supplied; step 8's check list is supplied and its adjudication is not.

**Warrant.** Whole-task at class 3 on the student's own model two days before deploying it. Step 5's accept list is the day's discriminator and step 7 is the expiry discipline the programme has used since S012. Step 8 is the strand's first operable security work and is deliberately a floor rather than a review.

## Phase 6 · Error clinic (40 min)

Instructor first: a substrate incident involving a learned component where the cause was neither an attack nor a bug — a data source changed upstream and nobody owned the boundary — with attention to **why it was not in anyone's threat model**.

Then the agent case: a Copilot session that was **confidently wrong and passed review**. Asked to make a deployment secure, the agent produced a careful piece of work — it enabled managed identity, removed a key from the configuration, added a role assignment with a comment explaining least privilege, and summarised the change as *the deployment now uses identity-based authentication and no longer stores secrets.* Every sentence of that summary was true. The resource remained publicly reachable, because nobody had asked about the network and the network is a different property from the identity.

Review passed it because the diff was good, the summary was accurate, and **the reviewer's mental model of "secure" was the thing the diff had changed.** Two of the four checks passed and the review measured its own success against those two.

Attention goes to why: **the agent answered the question asked, well, and the question was one check wide.** A review whose scope is set by the change under review cannot find what the change did not touch, which is why the four checks are run against the template rather than against the diff.

Then students: something you assumed nobody would do, or a security property you have described as done when one part of it was.

**Warrant.** Error management. The instructor disclosure deliberately concerns a non-attack, because the day's actor requirement risks producing students who only model deliberate harm and the largest category is neither deliberate nor accidental but unowned. The agent case is the required addition and is chosen because the agent's work was correct and its summary was true — the failure is entirely in the scope of the question, which is the failure students are about to make.

## When it does not work

The predicted failures and their countermeasures are argued in [WP-044](/archive/bsc-programme/whitepapers/WP-044.md) §5, which the release rule places after the day rather than before it. Restated here as instruction to the person in the room. Nothing below is assessed.

| What you see | What to do | What the design accepts |
|---|---|---|
| A student with security exposure produces a structured model quickly, with a **short accept list and confident probabilities** | State the empty-accept-list clause before phase 5 rather than at marking. Then let phase 7 do the work: the partner takes the role of an accepted threat's actor, and **a short accept list gives them almost nothing to play**, which the pair notices without being told | Security training rewards comprehensive coverage and rarely rewards stating what you are not doing. The design treats the accept list as the output, not the residue |
| A student meeting adversarial reasoning for the first time stalls at step 4's estimation | Actors are supplied at phase 3, step 2 is worked with the room, and the form is supplied. **Stated low confidence is acceptable.** Where a frequency is not estimable, point 6's substitute stands: give the target's value and the attack's cost and say that is what you have | Residual risk: their probabilities may be arbitrary, and the confidence field travelling in the same field as the number is the only guard. That is specification rule 2 doing the only work available |
| Actors A, B and C are analysed adequately and the room looks finished | Expected. **Actor D's ranking is the difficulty** — a careless insider with no intent frequently exceeds a deliberate attacker on expected harm, and rooms rank on intent | If a group ranks D first unprompted, ask what access actor A would need to become as harmful as D. That forces reasoning about access rather than intent and previews [S078](/archive/bsc-programme/seminars/S078.md) |
| Long threat lists, everything marked handled, nothing shipped | This is **paranoia without proportion**, the day's characteristic affective failure and the security-strand equivalent of the refusal reflex the programme met in M05. Three counters: point 5's expected-harm arithmetic, which deprioritises the dramatic and improbable; point 7's decision-record framing; and the accept list, which makes not-handling a **required output rather than a confession** | A first threat model is mostly acceptances and the published worked example the day treats as the genre's model marks every threat in it not mitigated. **An honest empty mitigation column is not penalised. An empty accept list is** |
| The template fails a check and the room starts looking for who was careless | Nobody was. Say it plainly: the fastest path to a working deployment carries the exposure attached, and **outbound networking cannot be added afterwards** — so the failing check is a creation-time decision that is now load-bearing, not a task for next sprint | Students expect a security exercise to find carelessness. It finds a default, and that reversal is the phase's second payload |

## Assessment

Specification item in SG201 and IS201 jointly. Per rule 1, the checked elements are: a deployment context with access paths and the named SG201 material, actors each carrying access and goal, an attack and cost per actor, probability and consequence with confidence in the same field or the value-and-cost substitute, a handle list, an accept list, a detection signal for one accepted threat, the change-of-decision condition, **the four-check result on the student's own deployment template with each pass, remediation or acceptance**, the phase 7 outcome, **the prompt record, the intervention record and the frontier statement**. **Nothing else is assessed.**

**A threat with no actor fails the specification.** So does an accept list that is empty.

**A threat model in which nothing is marked mitigated is not penalised for that.** *(Added 2026-07-30.)* The published worked example this day treats as the genre's model marks every one of its threats not mitigated, and an honest unmitigated list is worth more than a fabricated mitigated one. **No checked element is added or removed by this sentence** — it constrains how the handle and accept lists are read, and the assessed question remains whether each threat carries an actor, a decision and, where accepted, a reason and a detection signal.

**A check recorded as accepted, with a reason and the actor it exposes you to, passes. A check not run fails.** The specification requires the looking, not the passing — the same discipline S041 applies to the leak audit, applied to a template.

**An intervention record with no entries fails**, unless the artefact demonstrates that the design could have detected an intervention-worthy error.

**Defender for Cloud's own reporting — the AI bill of materials, continuous discovery and attack path analysis — is demonstrated rather than operated and is not assessed**, because it requires a paid plan and a repository connector with tenant-administration rights the programme does not hold.

## What this day does not establish

The day demonstrates two things, both in the room and both narrow. That four published checks, applied by hand to the group's own deployment template, produced four yes-or-no answers and that the template failed at least one. And that the room's actor ranking moved after the checks were run — specifically that actor A's feasibility moved. **Both are observations about one template, one cohort and one afternoon**, and no rate is claimed for either.

**One claim on this day has a named source and it is worth saying so on a page this thin.** Point 7's observation that a first-pass threat model is mostly acceptances rests on [research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), a **complete reading**, which records that the playbook's own worked threat model marks every threat in it as not mitigated and states its assumptions separately from its threats. **That is one document about one system and it licenses the non-penalty clause and nothing else** — not a frequency, not a norm, and nothing about what other organisations produce.

What rests on nothing verified here: **the actor-access-goal frame, the four attack families, and the accept-and-detect discipline**, all of which are held at folder level only. [WP-044](/archive/bsc-programme/whitepapers/WP-044.md) records that as a gap in the source register rather than papering over it. The four families' own scope statement already concedes that the list omits infrastructure attacks, which are the more common cause of real incidents, and generative-component attacks, which arrive at [S076](/archive/bsc-programme/seminars/S076.md).

The checks, the setup tiers and the governance split are recorded at [research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md](/research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md) as vendor documentation. **No detection rate and no false-positive rate is published for any of it**, and none may be asserted — that is a standing prohibition on the [Microsoft AI Platform Map](/archive/bsc-programme/program/11-Microsoft-AI-Platform-Map.md) and it is the reason the checks are taught as a floor rather than as coverage.

Point 11 establishes that one path exists in one real system, described by somebody who read all of its agent definitions. **It establishes nothing about how often such a path exists anywhere else**, the corpus reports no outcome for the pipeline at all — no comparison against a human-authored threat model, no defect-escape figure, no coverage measurement — and no figure from it appears here or anywhere in this wiki. It is taught, warranted and never assessed.

The phase warrants lean on retrieval practice, contrasting cases and variability of practice, **none of which has a note under [research/](/research/99-source-register/source-register.md)**. Error management at phase 6 does have one, at [keith-frese](/research/04-professional-formation/keith-frese-error-management-training.md), for direction and mechanism only.

## What to take from this day

**The claim to hold.** **A threat is an actor with access and a goal**; anything else is a hazard. Access is usually wider than assumed, a minimum baseline is a floor and not a review, and a configuration decision made at creation time can become irreversible.

**What the sources license, and what they do not.** The actor-access-goal frame, the attack families and the accept-and-detect discipline remain **folder-level** here — neither the technical-foundations nor the [fde-craft](/research/05-fde-craft/collected-materials.md) material holds a note carrying them, which [WP-044](/archive/bsc-programme/whitepapers/WP-044.md) records as a gap in the source register. **Direction and mechanism only; no magnitude is asserted.** *Amended 2026-07-30: one claim now has a named source.* The observation at point 7 that a first-pass threat model is mostly acceptances is grounded in [research/05-fde-craft/microsoft-ise-engineering-playbook.md](/research/05-fde-craft/microsoft-ise-engineering-playbook.md), whose complete reading records that the playbook's worked example marks every threat in it as not mitigated — **which is one document about one system and licenses the non-penalty clause and nothing else.** The four checks and the governance split are recorded in [research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md](/research/06-microsoft-platform/purview-dspm-for-ai-and-defender-ai-spm-docs.md); **no detection rate and no false-positive rate is published for any of it**, which is why the checks are taught as a floor.

**Guidance for your own work.**

- **Filter your list by actor.** A threat nobody would carry out is a worry.
- **Do not fill the mitigation column to look finished.** The published example this day works from marks every threat not mitigated, and it is a serious document. An accepted threat with a reason and a signal is a decision; a mitigation you have not made is a claim.
- **Where you cannot estimate a frequency, estimate the target's value and the attack's cost**, and say so.
- **Run the checks against the template, not against the diff.** A review scoped by the change under review cannot find what the change did not touch.
- **Do not read a control as a result.** Per the [Agent Configuration Standard](/archive/bsc-programme/program/13-Agent-Configuration-Standard.md), managed identity enabled and a key removed are *configured controls*; they say nothing about whether the resource is still reachable.

**Where this is easy to get wrong.** Expecting a security exercise to find carelessness. It finds a default. Nobody chose an exposed posture — somebody chose a working deployment and the exposure arrived attached, and outbound networking cannot be added afterwards.
